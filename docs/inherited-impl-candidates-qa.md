# 継承した実装を候補にできていなかった件 — 実装時の QA 一覧

[Issue #131](https://github.com/instreest/java-call-hierarchy-exporter/issues/131)
「具象型が『継承した実装』を持つとき、段2（LOCAL_NEW）と段3（拡張）が無言で解決に失敗する」への対応で、
迷ったこと・困ったことと、その結論を Q&A の形で残す。

対応の要点:

- 段2（`LOCAL_NEW`）と段3（拡張 `TypeCandidateProvider`）の候補引きを、宣言だけを引く
  `MethodTable.idOf(型FQN + "#" + sig)` から、親を辿って本体を持つ宣言を探す
  `CallGraph.implementationIn(型FQN, sig)` に変えた。段1・段4・段5は以前からこちらを使っていた
- 拡張が返した候補を1件も採用できなかったときに警告を出す（同じ候補では1回だけ）。
  継承の件を直しても、FQN の打ち間違いや解析対象外の型は無言のままになるため
- `test/plugin-demo` に `AbstractDao`（`find()` の本体を持つ）と、それを継承するだけの
  `ReportDaoImpl` を足し、対応表が `ReportDaoImpl` を指しても解決できることを回帰テストで固定した
- `test/demo` の期待出力が 2 か所変わった（Q3）

---

## Q1. なぜ段2と段3だけが残っていたのか

段1を `implementationIn` に揃えたのは `docs/code-review-fixes-qa.md` の Q1 で、
そのときの症状は「サブタイプが親から継承した実装を CHA が候補にできない」だった。
直したのは `resolveVirtual`（段1）だけで、同じ形の引き方をしている段2・段3は見ていなかった。

段2は段4（`DATAFLOW_NEW`）が同じ呼び出しを拾うので表に出ず、段3は拡張を使う利用者しか踏まないため、
どちらも回帰テストに現れていなかった。`test/demo` の `fx/inherit/` は段1の形だけを固定していた。

## Q2. 段2は結果が変わらないのに、直す意味はあるか

ある。既定（`dataflow.enabled=true`）では段4 が拾うので出力の行は同じだが、ラベルが
`解決:DATAFLOW_NEW` になる。利用者は注記を見て「どれだけ確かな根拠で絞れたのか」を判断するので、
同一メソッド内の `new` で決まったものは段2 の `解決:LOCAL_NEW` と出るべき。

```
修正前: at fx.app.Main.run(Main.java:50),AbstractDao.findById,...,解決:DATAFLOW_NEW
修正後: at fx.app.Main.run(Main.java:50),AbstractDao.findById,...,解決:LOCAL_NEW
```

また、段2 が候補 0 件で素通りしていたのを段4 が救っているだけの状態は、
段4 を触ったときに静かに壊れる。段の責任を元に戻しておく方が安い。

なお `dataflow.enabled=false` にすると段2 は継承の有無に関係なく発火しない。
`NEW` の証拠（H 行）は dataflow 側のキャッシュに置いているためで、これは本件とは別の話。
今回は触っていない。

## Q3. `test/demo` の `multi` の行が 1 件から 2 件に増えた。精度が落ちたのでは

落ちたように見えるが、**修正前が誤っていた**。

```java
Dao multi = new UserDaoImpl();
multi.findById(6L);            // 52行目
multi = new OrderDaoImpl();
multi.findById(7L);            // 54行目
```

証拠（`NEW`）は変数ごとに溜まるので、`multi` には `UserDaoImpl` と `OrderDaoImpl` の 2 件が付く。
修正前は `UserDaoImpl` が `findById` を宣言していない（`AbstractDao` から継承している）ために
候補から落ち、残った `OrderDaoImpl` だけで「1 件に確定」と出ていた。

つまり 52 行目は、**実際には `UserDaoImpl` が入っているのに `OrderDaoImpl` だと出力していた**。
確定したように見えて誤っており、`AbstractDao.findById` への呼び出しが行ごと消えていた。
`methods.csv` の `AbstractDao.findById` の入次数も 12 と、2 件少なく数えられていた（修正後は 14）。

修正後は 52・54 行とも候補 2 件（`CHA候補2件（未展開）: ローカル変数`）になる。
証拠は変数ごとで文の位置を持たないため、どちらの行でも 2 件に広がるのは避けられない。
54 行目だけを見れば精度は落ちたが、**52 行目の取りこぼしが消えたことの方が重い**。
このツールの方針（絞れないことより誤って絞ることの方が害が大きい）どおりに倒した。

利用者から見える変化として、`new` を複数回代入している変数の行が「1 件確定」から
「候補 N 件」に変わることがある。

## Q4. 警告はうるさくないか

`askProviders` はエッジごとに呼ばれるので、素直に書くと同じ候補で何度も出る。
ラベル・FQN・シグネチャの組で記録して、同じものは 1 回だけにした。

出すのは「拡張が候補を返したのに 1 件も採用できなかった」ときだけで、
拡張が `null` を返したとき（＝その呼び出しについては何も言わない、という正常な応答）には出さない。

```
[WARN] 拡張が返した候補を使えません: jp.co.app.impl.TypoService#execute()
       (jche.builtin.TypeMappingProvider / MAPPING) … この型にも親にもこのメソッドの本体がありません。候補から外します
```

`Plugins.load` が拡張の読み込み失敗を「設定したのに効いていないことに気づけないため必ず出力する」と
しているのと同じ理由。候補を落とすだけなので呼び出しは漏れないが、対応表を書いた側は
「書いたのに絞れない」ことの原因が分からない。

## Q5. 却下した案

**案: 拡張が返した FQN を、宣言を持つ親に利用者側で書き換えてもらう。**
`docs/instance-analysis-plugin.md` に注意点として書いてあった回避策だが、
利用者に「呼び出し先のシグネチャを宣言しているのはどの親か」を調べさせることになる。
DI 設定やファクトリの対応表は具象クラス名で書くのが自然で、そこに解析器側の都合を持ち込むのは筋が悪い。
本体を直したので、この注意点は消した。

**案: 候補が採用できないときに例外にする。**
拡張は利用者が書くもので、対応表に古い型名が残っていることは珍しくない。
解析が止まる方が困るので、警告にして解析は続ける（拡張の読み込み失敗と同じ扱い）。
