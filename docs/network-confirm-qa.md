# ネットワークにアクセスする前に操作者の確認を取る — 実装時の QA 一覧

[Issue #86](https://github.com/instreest/java-call-hierarchy-exporter/issues/86)
「ネットワークにアクセスする場合に操作者の確認を必須としたい」の対応で、迷ったこと・困ったことと、その結論を
Q&A の形で残す。

対応の要点:

- 起動コマンド（`java-call-hierarchy-exporter.sh` / `.cmd`）が jbang を呼ぶ前に、**手元に何が無いかを調べて、
  取りに行くものがあるときだけ尋ねる**ようにした。断れば実行しない
  - 調べるのは 3 つ。JBang 本体（`JBANG_DIR/bin/jbang.jar` ほか）、JDK（ラッパー用と `//JAVA` の求める版）、
    `//DEPS` の座標に対応する jar（`JBANG_REPO` の標準的な Maven のパス）
  - 探す順は `jbangw/jbang` と `jbangw/jbang.cmd` に揃えてあるので、検出の結果はラッパーが実際にすることと一致する
- **検出だけに頼らない。** 許可されていないときは `jbang` に `--offline` も渡す。推移的な依存だけが欠けている
  ような取りこぼしがあっても、黙って外に出ることはなく jbang が「オフラインなので解決できない」と言って止まる
- 決め方は `JCHE_NETWORK`（`ask` / `allow` / `deny`）。`launcher.properties` に書けるし、対話モードの
  「環境設定」5) からも変えられる。空欄は `ask`
- 端末が無いとき（パイプ・CI）は尋ねようがないので取りに行かず、`JCHE_NETWORK=allow` を設定するよう案内する
- いずれ JBang を JBangLite に置き換えることを見越して、JBangLite 側にも同じ約束
  （`JBANGLITE_NETWORK` = `ask` / `allow` / `deny`）を入れた

---

## 仕様

### Q1. なぜ毎回尋ねないのか。「必須」と言われている

Issue の To be は「ネットワークアクセスが**必要な場合は**操作者の確認を必須とする」なので、必要でないときまで
尋ねるのは要求より広い。実際、2 回目以降の実行は JDK も依存 jar も手元にあるので外に出る必要が無く、そこで
毎回尋ねると「とりあえず y」を押す習慣がついて、確認そのものが意味を失う。

そこで「取りに行くものがあるときだけ尋ねる」にした。結果として、これは初回だけの質問になる。

### Q2. 「必要かどうか」をどう判定するか

起動コマンドが、ラッパーと同じ場所を同じ順で見る。

| 見るもの | 場所 |
|---|---|
| JBang 本体 | `jbangw/jbang.jar` → `jbangw/.jbang/jbang.jar` → `JBANG_DIR/bin/jbang.jar` |
| JDK（ラッパー用） | `JAVA_HOME/bin/javac` → PATH の `javac` → `JBANG_DIR/currentjdk` → `JBANG_CACHE_DIR/jdks/17` |
| JDK（ツール用） | `JBANG_CACHE_DIR/jdks/<//JAVA の版>`、または上の javac がその版を名乗る |
| 依存 jar | `JBANG_REPO/<g を / に開いたもの>/<a>/<v>/<a>-<v>.jar` |

順序と条件を `jbangw/jbang`・`jbangw/jbang.cmd` に合わせてあるのが肝で、ここがずれると
「手元にあると判定したのにラッパーがダウンロードを始める」ことになる。`//JAVA` と `//DEPS` は
`src/Jche.java` から読む。ツールの版を上げて座標が変わっても、起動コマンドを直す必要は無い。

### Q3. 推移的な依存まで確かめられるか（Requirements の「推移的確認」）

確かめられない。`//DEPS` に書いた座標が手元にあるかは見られるが、その先が全部あるかは
Maven の解決を回さないと分からない。ここを正確にやろうとすると、jbang のキャッシュの中身に
手を突っ込むことになり、jbang の版が変わるたびに壊れる。

そこで**検出とは別に強制をかけた**。許可されていないときは `jbang run` に `--offline` を渡す。
検出が「何も足りない」と言っても、実際に足りないものがあれば jbang がオフラインで解決できずに止まる。
黙って外に出ることだけは起こらない。AGENTS.md の「迷ったら安全側に倒す」に従った二段構えになっている。

却下した案が 2 つある。

- **先に `--offline` で実行してみて、失敗したら尋ねて再実行する。** 判定は正確になるが、解析が
  別の理由で失敗したときも「ネットワークが要るのでは」と誤解して二重に実行してしまう。失敗理由を
  jbang のメッセージから読み分けるのは、jbang の版に依存しすぎる
- **jbang の依存キャッシュ（`dependency_cache.json` 等）を読む。** jbang の内部形式で、約束が無い

### Q4. `allow` のときに `--offline` を足さないのはなぜか

`allow` は操作者が先に「外に出てよい」と言った状態なので、そこで `--offline` を足すと、
許可したのに取りに行けないという矛盾した動きになる。推移的な依存が欠けているような、検出が
取りこぼす場面こそ許可が効いてほしい。

`ask` で「何も足りない」と判定したときだけ `--offline` を足す。`deny` でも足す。

### Q5. 「引数ありのときは一切尋ねない」（Issue #83）と矛盾しないか

矛盾しうるので、**#86 を優先した**。引数があっても、取りに行くものがあれば尋ねる。

ただし実際にぶつかるのは初回だけで、2 回目以降は Q1 のとおり何も足りないので何も尋ねない。
#83 が避けたかったのは「バッチで回しているのに質問で止まる」ことなので、その狙いは保たれている。
初回から完全に尋ねさせたくない場合は `JCHE_NETWORK=allow` を設定する。

### Q6. GitHub Actions から使うとき（`uses:`）はどうなるか

尋ねない。`.github/action/run.sh` は起動コマンドを通さず `jbangw/jbang` を直接呼ぶので、
そもそもこの確認を通らない。

そのままにした理由は 2 つ。

- ワークフローに `uses: instreest/java-call-hierarchy-exporter@...` と書くこと自体が、
  リポジトリに記録の残る許可にあたる。実行のたびに人が見ているわけでもない
- ランナーには端末が無いので、尋ねても答えようがない

CI で外に出したくない場合は、このアクションを使わずに起動コマンドを直接呼び、`JCHE_NETWORK` を
設定する。

### Q7. `jbangw` の中は塞げているか

塞げていない。`jbangw/` の 3 ファイルは本家 JBang とバイト単位で同一に保つ約束があり
（`jbangw/README.md`、`test/jbangw/run.sh` が検査している）、そこに確認を足せない。

なので起動コマンド側で「ラッパーがダウンロードを始めることになるか」を先に判定している。
判定がずれればラッパーは黙って取りに行ってしまうので、Q2 のとおり探す順と条件をラッパーに
揃えることが、ここでは正しさそのものになる。

この穴は JBang を JBangLite に置き換えると無くなる。JBangLite のブートストラップは自前なので、
確認をその中に置ける（Q11）。

### Q8. 取り消したときの終了コードは

`1`。このツールの約束は「0 = すべて成功、1 = 1 つ以上失敗、2 = 引数が不正」（`cli-noninteractive-qa.md` の Q6）で、
取り消しは解析をしなかったという意味で失敗の側に入る。`JCHE_NETWORK` に知らない値を書いたときも
引数の誤りに近いが、こちらも `1` にした。起動コマンドの段階で終了コードを細かく分けても、
呼び出し側が使い分けられないため。

### Q9. `launcher.properties` の `JCHE_NETWORK` が空欄のとき、環境変数を消さないのはなぜか

他のキーと同じ扱いにすると、README に書いた
`JCHE_NETWORK=allow ./java-call-hierarchy-exporter.sh config/config.properties` が
**`launcher.properties` があるだけで効かなくなる**ため。

`load_settings` は「空欄は既定値」として環境変数を消す。`launcher.properties` は
初回に必ず作られ、そこには `JCHE_NETWORK=` が空欄で入っているので、環境変数で渡した
`allow` がそこで消える。CI のワークフローでステップの `env:` に書いても同じことが起きる。

そこでこの項目だけ、空欄のときは環境変数に触らないことにした。「この 1 回だけ許可する」
という使い方が主なのがこの項目だけで、置き場所（`JBANG_DIR` 等）のように
「設定ファイルが唯一の出どころ」ではないため。`.cmd` 側の `:set_one` も同じにしてある。

これは実際に CI で見つかった。対話モードの「環境設定」でヒープ上限を変えると
`LauncherSettings.save()` が既知のキーを全部書き直すので、そこで `JCHE_NETWORK=` が
書かれ、再起動後の実行が「端末ではないため確認を取れません」で止まった。

### Q10. なぜ標準入力ではなく `/dev/tty` から読むのか

対話モードはメニューの答えを標準入力から読む。テストや自動実行では、その答えをパイプで流し込む。
確認の `read` が標準入力から 1 行取ると、その行がメニューに届かず、以降の入力が 1 行ずつずれる。

`/dev/tty` は「この端末」を指すので、パイプで流し込まれた入力とは別に読める。開けなければ端末が
無いということなので、そこが「尋ねられない」の判定も兼ねている。`.cmd` 側は `timeout /t 0` で
同じ判定をする（標準入力がリダイレクトされていると失敗する。`java-call-hierarchy-exporter.cmd` が
初回の質問で既に使っている手）。

### Q11. JBangLite に置き換えたときどうなるか

同じ約束を JBangLite 側にも入れてある。環境変数の名前が `JBANGLITE_NETWORK` になるだけで、
値（`ask` / `allow` / `deny`）も、端末が無ければ取りに行かないことも同じ。

置き換えると 2 つ良くなる。

- **ブートストラップの中で確認できる。** JBangLite の `jbanglite` / `jbanglite.cmd` は自前なので、
  jar と JDK のダウンロードを直接塞げる。Q7 の穴が無くなる
- **依存の確認が正確になる。** JBangLite の jar は、Maven の解決を始める直前
  （キャッシュに当たらず、かつオフラインでないとき）に尋ねる。推移的な依存も含めて
  「本当に外に出る瞬間」なので、Q3 の取りこぼしが無くなる。起動コマンドで既に許可を得ていれば
  環境変数で引き継ぐので、1 回の実行で二度尋ねることはない

`--update`（JBangLite が自分自身を入れ替えるオプション）も同じ確認を通る。Issue の Requirements に
挙がっていた項目で、JBang には無い機能なのでこのリポジトリ側には対応するものが無い。

## ドキュメント

### Q12. README にどこまで書くか

README には「何が・どこから・どこへ」の表と、`JCHE_NETWORK` の 3 つの値、CI での設定例までを
「ネットワークアクセスの確認」節として置いた。判断の経緯はこのファイルに置き、README からは
リンクだけにしてある（AGENTS.md の「利用者向けの長い説明は README ではなく `docs/` に」）。

Quick start の 1 行は「自動でダウンロードします」から「ダウンロードしてよいかを尋ねます」に直した。
最初に読む場所に事実と違うことが書いてあるのが、この Issue の出発点だったため。

## テスト

### Q13. 本物のダウンロードを起こさずに、どう検査するか

`test/cli/run.sh` の中に作業用のフォルダを作り、起動コマンドと最小限の `src/Jche.java`、
それに「渡された引数を出すだけ」の偽の `jbangw/jbang` を並べて、そこで動かす。起動コマンドは
自分の置かれた場所を起点にするので、これで本物のラッパーには一切触れずに済む。

見ているのは分岐だけで、尋ねる・断る・素通りする・`--offline` を足す、の 4 つ。
手元に何も無いホームと、すべて揃っているホーム（`JBANG_DIR` と `JBANG_REPO` の中に空のファイルを置く）を
`HOME` で切り替えて、判定が変わることを確かめている。

端末があるときの取り消しは `script -qec` で疑似端末を作って確かめる。`script` が無い環境では飛ばす。

### Q14. `.cmd` 側はどう検査するか

Linux 側では読むだけ（ラベルの整合・CRLF・MS932）に加えて、「ダウンロードしてよいですか」の
文言と `JCHE_NETWORK` が `.cmd` にもあることを見る。片方だけ直すと Windows で素通りしてしまうので、
そこだけでも機械的に押さえておく。実際に動かすのは `.github/workflows/smoke.yml` の
`regression-windows` の役目。

### Q15. CI で `JCHE_NETWORK=allow` を明示したのはなぜか

`regression-windows` は「毎回まっさらな状態から取得させて、ブートストラップ経路そのものを検査対象に
含める」ためにキャッシュを使わない。つまり必ずこの確認にかかるし、ランナーに端末は無い。
明示しなければ、意図した検査が「尋ねられないので中止」で止まってしまう。

ubuntu 側の `CLI test` は直前のステップで既に取得が済んでいるので実際には尋ねられないが、
キャッシュが外れた日に赤くなるのを避けるため、同じく明示した。確認そのものを見る検査は、
その中で `JCHE_NETWORK` を明示して行っている。
