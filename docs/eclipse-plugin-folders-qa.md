# Eclipseプラグインの初期状態・設定・置き場所・操作 — QA 一覧

> 使い方（入れ方・操作・設定・つまずきやすいところ）は
> [eclipse-plugin-usage.md](eclipse-plugin-usage.md) にまとめてある。
> 画面の設計は [eclipse-plugin-ui-design.md](eclipse-plugin-ui-design.md)、
> 実装で迷った点は [eclipse-plugin-ui-qa.md](eclipse-plugin-ui-qa.md)。

利用者から挙がった 5 点への対応をまとめる。

| 挙がった点 | 対応 |
|---|---|
| ビューを開いただけでは解析ボタンが押せない | 対象バーにプロジェクト選択を足し、ビュー単体で「選ぶ → 解析する → メソッドを指す」と進めるようにした（Q4） |
| ソースフォルダが既定の場所にないと解析に失敗する | 自動生成した設定の `project.root` が<b>プラグインの作業フォルダ</b>を指していた不具合を直した（Q1）。併せて、使っている設定を見て選び直せるダイアログを足した（Q5） |
| キャッシュとログの置き場所が分からない | 置き場所を 1 か所（`PluginFolders`）に集め、設定画面に実際のパスを出し、変更できるようにした（Q2・Q3） |
| 「呼び出し先を見る」がトグルで分かりにくい | 「呼び出し元を表示」「呼び出し先を表示」の 2 つのボタンに分けた（Q6） |
| ビューの行をコピーできない | 字下げ付きのコピーを足した（Q7） |

---

### Q1. 「ソースフォルダを特定できませんでした: …/.plugins/io.github.instreest.jche.eclipse/config/<プロジェクト名>」は何だったのか

**設定ファイルを書いていない利用者が、必ず踏む不具合だった。** ソースフォルダの配置とは関係ない。

プラグインは設定ファイルが無いとき、Eclipse のプロジェクト構成から設定を組み立て、
**プラグインの作業フォルダ**（`<ワークスペース>/.metadata/.plugins/<バンドルID>/config/<プロジェクト名>/`）に
`generated-config.properties` として書き出して子プロセスへ渡す。
ところがその中身は `project.root=.` だった。

解析側の相対パスの起点は「**設定ファイルを置いたフォルダ**」である
（[config/config.properties](../config/config.properties) 冒頭のコメント）。つまり `.` は
解析対象のプロジェクトではなく、**この作業フォルダ自身**を指していた。作業フォルダには
`generated-config.properties` しか無いので、その下の `source.folders`（`src/main/java` など）は
どれも存在せず、`src/main/java` も `src` も `.classpath` も無いフォルダとして扱われて、
`ProjectLayout` が「ソースフォルダを特定できませんでした」で止まっていた。
エラーに出ていた長いパスが、まさにその作業フォルダである。

直し方は「自動生成した設定のパスはすべて絶対パスで書く」。`project.root` に
プロジェクトの場所（`IProject#getLocation`）をそのまま入れる。

相対パスに寄せる案（`project.root` を作業フォルダからプロジェクトへの相対で書く）は採らなかった。
同じ設定にすでに `library.jars` が絶対パスで入っており、この設定は**その環境でしか通用しない**もので、
起点だけ相対にしても可搬性は得られないからである。Windows ではドライブをまたぐと相対パスが作れない、
という面倒も抱え込まずに済む。

検査は 2 つある。

- `test/plugin-config/run.sh` … `project.root` を含めて、Windows のパスが properties の往復で壊れないこと
  （絶対パスにしたことで、**起点そのものにバックスラッシュが入るようになった**）
- `test/server/run.sh` … 「プロジェクトの外に置いた設定＋絶対パスの `project.root`」で解析が通ること。
  同じ場所に `project.root=.` と書くと失敗することも併せて固定してある（この検査の前提が崩れたら分かるように）

### Q2. キャッシュ・ログ・出力はどこにできるのか

Eclipse のプラグインが自前のファイルを置く場所は `Platform.getStateLocation(bundle)` と決まっている。
ワークスペースごとに分かれ、ワークスペースを消せば一緒に消える。このプラグインもそれに従う。

`<ワークスペース>/.metadata/.plugins/io.github.instreest.jche.eclipse/` の下:

| フォルダ | 中身 | 設定で移せるか |
|---|---|---|
| `cache/` | 解析キャッシュ。実体は `cache/.cache/<プロジェクト名>_<識別子>/analysis-cache.tsv`（1 ファイル。以前の版は `dataflow-cache.tsv` も作っていた） | ○ |
| `log/` | `analysis-<日時>.log`（新しいものから 10 世代） | ○ |
| `output/` | ［CSV出力］の初期フォルダ。自動生成した設定の `output.folder` にもこれを書く | ○ |
| `config/<プロジェクト名>/` | 自動生成した設定（`generated-config.properties`）。解析のたびに書き直す内部の作業ファイル | ×（触る想定のものではない） |
| `jdk/` | 設定画面から取得した JDK | × |

`cache/` の下がもう一段 `.cache/` になっているのは、子プロセスに渡しているのが
「キャッシュの置き場所の親」（解析本体でいう `cache.folder` 未指定時の既定の親）だからである。
プロジェクトごとに分けるのは解析側の仕事で、プラグインはその親を指定しているだけ。

**Eclipse 自身のエラーログ**（`getLog().log(...)` で出すもの）はこれとは別で、
`<ワークスペース>/.metadata/.log` に入る。「ウィンドウ → ビューの表示 → エラー・ログ」で見える。
プラグインの不具合（クラスパス、例外）はそちらへ、解析の進み具合は `log/` へ、と使い分けている。

### Q3. プラグインがファイルを書くのは作法として正しいのか。ログは出さないのが普通ではないか

**状態フォルダに書くのが正しい作法である。** Eclipse が
`Platform.getStateLocation(bundle)` を用意しているのは、まさにこの用途（プラグインごとの
作業ファイル・キャッシュ・ログ）のためで、JDT のインデックスもここに入る。
やってはいけないのは、インストール先や利用者のホーム直下、解析対象のプロジェクトの中に
黙って書くことで、このプラグインはどれもしていない。

「ログはファイルに出さない」が作法というわけでもない。Eclipse の流儀は
**人に見せる短いものは `ILog`（エラー・ログビュー）、量が多く時系列で追うものは自前のファイル**である。
このプラグインの解析ログは後者で、返ってこない解析の原因を後から追うために要る
（[eclipse-plugin-progress-log-qa.md](eclipse-plugin-progress-log-qa.md) の Q2）。

ただし、**どこに書いているかが利用者から見えない**のは作法に反する。
`.metadata/.plugins/<バンドルID>/` は自分で辿り着ける場所ではないので、次のようにした。

- 設定画面（ウィンドウ > 設定 > 影響調査）に「置き場所」の欄を作り、
  **空欄（既定）のときも実際のパスを行の下に出す**。隣に［開く］を置く
- ビューの［▽］メニューからその設定画面を開けるようにする。［解析ログのフォルダを開く］も置く
- ビューのバナーのツールチップに、いまのキャッシュとログの場所を出す
- 3 つとも別の場所へ移せるようにする（閉域の共有フォルダに置きたい、
  ワークスペースを作り直してもキャッシュを残したい、という要望に応えるため）

置き場所を変えたときは、書きかけのログを閉じ（次の 1 行で新しい場所に作り直す）、
動いている解析プロセスを終わらせる（キャッシュの場所は起動時に渡しているため）。

自動生成した設定（`config/<プロジェクト名>/`）だけは移せないままにした。
あれは解析のたびに書き直す内部の作業ファイルで、利用者が触る意味が無い。
触りたい場合の道は別にある（Q5 の「保存して編集」）。

### Q4. ビューを開いただけでは何もできなかったのはなぜか

入口が「メソッドを選んでコマンドを実行する」しか無かったためである。
ビューが持つ状態は「いま指定されているメソッド 1 つ」だけで
（[eclipse-plugin-ui-qa.md](eclipse-plugin-ui-qa.md) の Q1）、
それが無いと**プロジェクトも決まらない**。プロジェクトが決まらなければ解析も始められないので、
「メソッドを選んで…を実行してください」と出して終わるほかなかった。

ここには設計の抜けがあった。**解析はプロジェクト単位、表示はメソッド単位**で、
前者は後者に依存しない。依存していたのは実装の都合だけである。
そこでビューの一番上に対象バーを足し、この 2 つを別々に指定できるようにした。

```
対象プロジェクト: [ spring-petclinic ▾ ]   設定: 自動生成（プロジェクトの構成から）  [解析に使う設定…]
```

- 一覧に出るのは、解析できるプロジェクト（Java プロジェクト、またはこのツールの設定ファイルを持つプロジェクト）
- ビューを開いたときは、エディタで開いているファイルのプロジェクトを選ぶ。
  それも無く、解析できるプロジェクトが 1 つしか無ければ、それを選ぶ
- プロジェクトさえ決まればバナーの［解析する］が効く。解析だけ先に済ませておける
- 解析が済んでメソッドがまだのときは、バナーが［カーソル位置のメソッド］を出す。
  ツールバーにも同じボタンを置いた（コマンドと同じ処理を通る。`MethodPicker`）

エディタの選択に自動で追従する案は、今回も採っていない（同 Q1 の理由のまま。
カーソルを動かすたびに木が作り直されると見比べられない）。
**利用者が押したときだけ**取りに行く、という点は変えていない。

### Q5. 「設定ファイルの source.folders に指定してください」と言われても分からない、にどう答えたか

Q1 の不具合を直せば、この文言自体はほとんど出なくなる。それでも
「いま何を見て解析しているのか」が画面のどこにも無いのは、失敗したときに手の出しようが無い。

そこで［解析に使う設定…］ダイアログ（`ConfigDialog`）を足した。できるのは 3 つだけである。

1. いま使っている設定の**中身をそのまま見る**（自動生成でもファイルでも同じ見え方）。
   組み立てに失敗したときは、例外の文言をその場に出す。**解析を走らせる前に**直すところが分かる
2. プロジェクトの中にある設定ファイルへ**切り替える**（自動判定に戻すのも同じ場所）
3. 自動生成の内容を `config/jche.properties` として**保存して、手で直せるようにする**

値をダイアログの中で直接編集させることはしない。項目は解析側の `config.properties` と同じで数が多く、
中途半端な編集欄を作るより「保存してエディタで開く」ほうが分かりやすい。

これで、以前はビューの［▽］メニューに分かれていた「使う設定ファイルを選ぶ…」と
「設定を config/jche.properties に保存」が 1 か所にまとまった。
どちらも「解析に使う設定をどうするか」という同じ話だったのに、
**中身を見る手段が無いまま選ばせていた**のが分かりにくさの元だった。

### Q6. 向きの切り替えを、トグル 1 つから 2 つのボタンに分けたのはなぜか

トグル（「呼び出し先を見る」のチェックボタン）には次の 2 つの読み方があり、区別できない。

- 「いま呼び出し先を見ている」（状態の表示）
- 「押すと呼び出し先になる」（操作の予告）

押下状態でしか今の向きが分からないうえ、ツールバーのボタンの押下状態は見落としやすい。
影響調査では**向きを取り違えると結論が逆になる**ので、ここは曖昧にしてはいけない。

「呼び出し元を表示」「呼び出し先を表示」のラジオボタン 2 つに分けた。
どちらが効いているかが常に見え、押すべきボタンの名前がそのまま目的になる。
Eclipse 標準の呼び出し階層ビューも同じ作りである。

ラジオボタンは選択が外れる側でも `run()` が呼ばれるので、`isChecked()` を見てから処理する
（見ないと 1 回の切り替えで 2 回木を取り寄せることになる）。

### Q7. コピーの字下げは何を基準にしたか

**画面で見えているとおりの段数**である。行が持っている深さ（`ServerRow#depth`）は使わない。

深さの上限で打ち切った枝を開くと、その節点を根にして木を取り寄せ直す
（継続。`CallersContentProvider#addContinuation`）。取り寄せ直した木の深さは**その枝の中で 0 から
振り直される**ので、行の深さをそのまま字下げにすると、継続の先だけ左へ戻ってしまう。
ツリーの項目（`TreeItem`）の親をたどれば、見えているとおりの段数になる。

1 段は空白 2 つ。タブにすると、表計算ソフトへ貼ったときに階層が列に化けてしまう
（影響調査の結果は 1 列のまま貼れるほうが扱いやすい）。

用意したのは 2 つ。

- **コピー**（`Ctrl+C`・右クリック）… 選んだ行だけ。複数選択の字下げは、
  選んだ中で一番浅い行が左端になるようにそろえる
- **この行から下をコピー**（右クリック）… 選んだ行と、その下にある行。
  **畳んでいる行も含む**（メモリに持っているものはすべて出す）。
  親と子を両方選んでいるときは、親からの書き出しに含まれるので重ねない

`Ctrl+C` は Eclipse の共通のやり方（`ActionFactory.COPY` のグローバルハンドラ）で登録した。
ビューに焦点があるときだけ効き、他のビューのコピーを奪わない。
