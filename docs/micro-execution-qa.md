# 静的解析で解けない断片を実行して補う（断片実行）— 用語・境界と不採用の判断の Q&A

Issue なし（検討の記録）。**断片実行は採らない**と決めた。代わりに、解析器が自分で文字列の計算を評価する方向
（**文字列演算の静的評価**。未実装）で進める。
静的解析では決められない部分（文字列の計算、jar の中からの呼び戻しなど）だけを、
ソースの断片や依存 jar のメソッドとして実際に実行し、その結果を静的解析に活かす案について、
**何と呼ぶか**、**単体テスト・モニタリング・実行トレースとどこで線を引くか**、
**今のプラグインと比べてどうか**、**なぜ採らないか**を残す。
関連: [static-analysis-limits.md](static-analysis-limits.md)（何が静的に解けないか。3節・4節・6節・8節）、
[instance-analysis-plugin.md](instance-analysis-plugin.md)（`TypeCandidateProvider` と証拠 `Hint`）、
[callback-contracts.md](callback-contracts.md)（jar からの呼び戻しの契約表）。

## 結論

### 判断

- **断片実行は採らない**（Q10）。許容できない点が 2 つある
  1. **解析対象のコードを実行する**。このツールは解析対象のソースと jar を読むだけで、対象のコードもビルドも動かさない。
     だから社外のコードやレビュー前の PR も、コードを実行する心配なく解析できる。断片実行はこの性質を捨てる。
     しかもこれは断片実行の定義そのもの（下の条件 4）なので、工夫で消せない
  2. **名前を組み立てる部分が関数として切り出されている必要がある**。どの部分なら安全に呼べるかは
     静的には判断できないので、利用者に関数を指定させるしかなく、切り出せていないコードでは使えない
- 実行して契約表のひな形を作る中間案も採らない（Q11。対象のコードを実行する点が同じ）
- 代わりに、**解析器が自分で文字列の計算を評価する**（文字列演算の静的評価）。計算の「形」をデータフローに記録し、
  呼び出し元のキーが分かった時点で、副作用の無い既知の操作だけで計算する。
  対象のコードは実行せず、関数の切り出しも要らない（Q12〜Q14。**未実装**）

### 用語と境界（断片実行を採るかどうかに関わらず使う）

- この実行を **断片実行**（英語 micro-execution）と呼ぶ。静的解析と組み合わせた方式全体は
  **ハイブリッド解析**（hybrid static/dynamic analysis）の一種と位置づける
- 「動的解析」は誤りではないが広すぎるので、この実行の名前には使わない（Q1）
- 断片実行と呼ぶのは、次の 5 つを**すべて**満たすものだけ（Q3）
  1. 実行を始めるのは**解析器**（人が書いたテストやアプリの入口に頼らない）
  2. 入力は**静的解析が集めた材料**（`Hint` のキー、シグネチャ、設定ファイルの値）から作る
  3. 範囲は**式 1 つ／メソッド 1 つ／jar のメソッド呼び出し 1 つ**
  4. **解析の最中**に、**隔離した使い捨ての JVM** で実行する（本番では動かさない）
  5. 合否を出さない。結果は静的解析の出力に**候補の追加か注記として**合流し、**候補を減らす根拠にしない**
- 1 と 5 を満たさないものは単体テスト（またはテストで駆動した実行トレース）、4 を満たさないものはモニタリング
- コード・出力での表記は英語側に合わせる（例: パッケージ `jche.microexec`、拡張の `label()` は `MICRO_EXEC`）。
  `probe` と `oracle` は使わない（Q6）。採らないと決めたので、これらの名前はいまは使われていない

## 用語

### Q1. 「動的解析」はモニタリングやテレメトリの用語ではないのか

違う。ソフトウェア工学では「動的解析（dynamic program analysis）」は静的解析と対になる正式な用語で、
プログラムを実際に動かして性質を調べる手法の総称である。
モニタリング・テレメトリは本番の稼働を継続して観測する**運用側**の用語で、分野が別である。

ただし「動的解析」は単体テスト、網羅率の計測、プロファイリング、実行トレースまで含む**総称**なので、
今回の「静的解析が解けない断片だけを動かす」という意図を区別して表せない。
だから**分類の名前としては使ってよいが、この実行の名前には使わない**。

### Q2. なぜ「断片実行」なのか。ほかの案は

| 案 | 対応する英語・学術用語 | 良い点 | 気になる点 |
|---|---|---|---|
| **断片実行**（採用） | micro-execution（Godefroid, ICSE 2014。テスト用の駆動コードや入力を人が用意せずに、任意のコード断片を実行する） | 範囲の小ささと「テストではない」が名前に出る。学術用語に対応がある | 「静的解析のため」という目的は名前に出ない（ハイブリッド解析という位置づけで補う） |
| 解析時実行 | analysis-time execution（「コンパイル時評価」と同じ作り） | いつ実行するかでテストともモニタリングとも区別できる | 範囲の小ささが出ない |
| 具体評価 | concrete evaluation（記号実行の対になる「具体実行」） | 記号実行との違いが正確 | 専門的すぎて利用者に伝わりにくい |
| 補助実行 | —（造語） | 目的が伝わる | 何を補助するのかが曖昧。英語の対応が無い |
| 部分実行 | — | 直感的 | **却下**。部分評価（partial evaluation。既知の入力でプログラムを特殊化して**別のプログラムを作る**変換）と紛らわしい |
| 動的解析 | dynamic analysis | 正しい用語ではある | 広すぎる（Q1） |

実行時の情報を静的解析に取り込む先行研究には、TamiFlex（Bodden ら, ICSE 2011。
実行時に記録したリフレクションの呼び出しを静的解析に取り込む）や
HeapDL（Grech ら, OOPSLA 2017。ヒープのスナップショットで静的解析の取りこぼしを補う）がある。
どちらもハイブリッド解析の分野に入るので、方式全体の分類名はこれに合わせた。

## 境界

### Q3. 単体テスト・モニタリング・実行トレースとどこで線を引くか

目的・正解の有無・誰が実行を始めるか・範囲・いつどこで・結果の行き先、の 6 つの軸で比べる。

| 軸 | 単体テスト | モニタリング | 実行トレース（動的解析） | **断片実行** |
|---|---|---|---|---|
| 目的 | 正しさの**合否判定** | 稼働状態の把握 | 実際に起きた振る舞いの収集 | 静的解析が**決められなかった値や辺を確定させる** |
| 正解の有無 | 期待値がある | 閾値やアラート | 無い | **無い**（実行結果そのものが答え） |
| 誰が実行を始めるか | 人が書いたテストコード | 本番の利用者 | 既存のテスト・人の操作 | **解析器が静的に集めた材料から組み立てる** |
| 範囲 | クラス・メソッド単位（人が選ぶ） | システム全体 | 通った経路すべて | **式・メソッド・jar のメソッド呼び出し 1 つ** |
| いつ・どこで | ビルド時 | 本番で常時 | 試験環境 | **解析の最中に、隔離した使い捨ての JVM で** |
| 結果の行き先 | 合否 | ダッシュボード | ログ・呼び出しグラフ | **静的解析の出力に合流**（候補の追加・注記） |

ここから「結論」の 5 条件を引いた。判定の早見は次のとおり。

- 人が書いたコードが実行を始め、期待値と照合する → **単体テスト**
- 既存のテストや操作で通った経路を丸ごと記録する → **実行トレース**
- 本番で常時動かして観測する → **モニタリング**
- 解析器が材料から入力を作り、断片を 1 回だけ動かして答えを拾う → **断片実行**

### Q4. 具体的な実行の手段は、それぞれどれに当たるか

| 手段 | 判定 | 理由 |
|---|---|---|
| 対象のメソッドを別のクラスローダーで読み、リフレクションで呼ぶ | **断片実行** | 範囲が小さく、入力は `Hint` から作れ、期待値を持たない。典型 |
| JShell API（`jdk.jshell`）で式や文を評価する | **断片実行** | 上と同じもので、実行の仕組みが違うだけ。既定で別 JVM なので隔離しやすい |
| jar のメソッドに記録用の `Proxy` を渡して、何が呼び戻されるかを見る | **断片実行**（境界上） | 解析器が組み立てて呼び戻しを観測するなら断片実行。人が特定の jar 向けに書いて assert するなら**単体テスト**（契約のテスト） |
| Java エージェント（ByteBuddy / ASM）や JDI で呼び出しを記録する | **実行トレース**（断片実行ではない） | 既存のテストや利用者の操作に実行を任せ、通った経路を丸ごと記録する。本番に常駐させれば**モニタリング**（APM） |
| JaCoCo | **テストの領域**（網羅率の計測） | どの行が実行されたかしか分からず、呼び出し先は出ない |
| JFR | **モニタリング／プロファイリング** | サンプリングで、常時の観測が前提。呼び出しの抜けが出る |
| 記号実行（Java PathFinder の jpf-symbc 等） | **実行ではない**（静的解析の一手法） | 具体的な値を入れずに式のまま辿る |

実行トレースは断片実行ではないが、「実行では起きたのに `call-hierarchy.csv` に無い辺」を洗い出せるので、
**静的解析が辺を黙って落としていないかの検査**（[static-analysis-limits.md](static-analysis-limits.md) の 7 節の側）には使える。
名前を分けておくのは、この 2 つを混ぜて語らないためである。

### Q5. 断片実行の結果で候補を減らしてはいけないのはなぜか

断片実行を含む動的な手段の答えは「**少なくともこれは起きる**」（取りこぼしうる側）であって、
「これ以外は起きない」を示さない。一方、このツールは漏らさない側に倒している
（[static-analysis-limits.md](static-analysis-limits.md) の 6 節）。
与えた入力以外で別の型が返る可能性は消えないので、実行結果を根拠に CHA の候補を削ると、
影響調査で「呼ばれない」と誤読させることになる。
したがって断片実行の結果は、**候補を足す・注記を付ける・取りこぼしを見つける**ことにだけ使う。

例外は、入力の範囲そのものが静的に閉じていて（`Hint` のキーが有限個の定数に畳めている）、
実行した関数が引数以外の状態（設定ファイル・環境変数・時刻など）を読まない場合で、
このときは「キーごとの答え」として 1 件に確定させてよい。これは既存の拡張（`TypeCandidateProvider`）が
対応表で候補を返すのと同じ扱いである。

## 検討した構成（不採用。参考）

### Q7. 実装するとしたら、どういう構成だったか

解析本体の JVM の外に、関数を 1 つ呼ぶだけの子プロセスの JVM を用意し、そこへ 1 行ずつ問い合わせる構成を考えた。

```
解析本体（フェーズ3 の段3）                       子プロセス（使い捨て）
  MicroExecProvider.candidates(型, シグネチャ, hints)
     「ServiceFactory#toClassName に "user" を入れると？」 ─→ Runner: クラスを読んで 1 回呼ぶ
     ←─────────────────────────────── "jp.co.app.impl.UserService"
  候補として返す（resolved-by は RESOLVED:MICRO_EXEC）
```

| 部品 | 動く場所 | 仕事 |
|---|---|---|
| 問い合わせ口 `MicroExecProvider` | 解析本体 | `TypeCandidateProvider` を実装し、`FACTORY` / `FACTORY_KEY` の証拠から子プロセスに聞く |
| 実行係 `Runner` | 子プロセス | 1 行読んで、指定された関数を呼び、1 行返す。JDK の標準クラスだけで書く |
| 子プロセスの管理 | 解析本体 | 起動、タイムアウト、`-Xmx`、後始末 |
| 設定 | 設定ファイル | どのファクトリの答えを、どの関数で計算するか（利用者が指定する） |
| 答えのメモ | 解析本体 | `(関数, キー) → 答え`。同じ問い合わせで 2 度聞かない |

主な判断は次のとおりだった。

- **別プロセスにする。** 対象のコードの副作用（static 初期化での DB 接続、`System.exit()`）、無限ループ、
  ライブラリの版の衝突を閉じ込めるため。SecurityManager は JDK 24 で無効になったので、同じ JVM の中では止められない
- **子プロセスは 1 回だけ起動して常駐させる。** 問い合わせのたびに JVM を起動すると遅い。
  `TypeCandidateProvider` には終了時の呼び出しが無いので、子プロセスは標準入力が閉じたら自分で終わる
- **問い合わせごとに新しいクラスローダーで読み直す。** static 変数の状態で答えが変わると、
  `CallResolver.resolve` の結果が処理順に依存してしまう（AGENTS.md の決まり）
- **実行するのは名前を返す関数まで。** `newInstance()` まで動かすとコンストラクタの副作用が起きる。
  クラスは `Class.forName(名前, false, ローダー)` で初期化せずに読む
- **ビルド済みの `.class` が要る。** このツールは AST を読むだけで `.class` を作らない
- **置き場所は 2 段階。** 試作は利用者の拡張として `plugin.folders` に置く（本体を変えずに試せるが、
  拡張の `init` には設定しか渡らないので、解決済みの依存 jar の一覧を受け取れない）。
  本採用なら同梱の実装にし、本体から `ProjectLayout.classpathArray()` を渡す
- **失敗しても止めない。** 既存の拡張と同じく `null` を返して CHA に戻し、`Log.warn` を出す

**キャッシュについての訂正**: 最初の版では「`.class` や jar が変わったときに解析し直す条件を用意する」と書いたが、
不正確だった。`TypeCandidateProvider` はキャッシュに何も書かず、毎回の実行でゼロから動く
（[instance-analysis-plugin-qa.md](instance-analysis-plugin-qa.md) の Q11）ので、解析キャッシュが古い答えを持つことは無い。
捨てる条件が要るのは、答えを実行をまたいで保存する専用のメモを作った場合だけである。

## 今のプラグインとの比較

### Q8. 今のプラグイン（契約表・対応表・自前の拡張）と何が違うのか

見た目は似ているが、考え方が正反対である。

- **今のプラグイン**は、**人が答え（または答えの出し方）を書いてツールに教える**。対象のコードは動かさない
- **断片実行**は、**対象のコード自身に答えを計算させる**。人が教えるのは「どの関数に聞けばよいか」だけ

| | やること | たとえ |
|---|---|---|
| 契約表・対応表 | `get("user") => UserService` と答えを並べて書く | 答えの一覧表を手で作る |
| 自前の拡張（`NamingConventionProvider` など） | `"jp.co.app.impl." + capitalize(key) + "Service"` という計算式を拡張に書き写す | 計算式をノートに写して自分で計算する |
| 断片実行 | 対象プロジェクトの `toClassName("user")` を実際に呼ぶ | 本物の電卓を借りて計算させる |

[instance-analysis-plugin.md](instance-analysis-plugin.md) の `NamingConventionProvider` は、対象のコードの式を拡張の中に写し直したもの。
断片実行ではこの写しが要らない。違いの中心はここである。

### Q9. それぞれの良いところと困るところは

| 観点 | 今のプラグイン | 断片実行 |
|---|---|---|
| 人が書くもの | 答えそのもの、または規則の写し | どの関数に聞くか |
| 答えの拠り所 | 人の知識 | ビルドした `.class` |
| 対象のコードが変わったとき | 写しが黙って古くなる | ビルドし直せば追従する |
| 必要なもの | ソースだけ | ソースとビルド済みの `.class`・依存 jar |
| 対象のコードを動かすか | 動かさない | 動かす |
| 速さ | 速い | 遅い（JVM の起動とやり取り） |
| 毎回同じ答えか | 同じ | 関数が環境変数・設定・時刻を読むと変わりうる |
| 答えを人が確かめられるか | 表やコードを読める。git で差分も見られる | 実行ログにしか残らない |
| 作る・保守する手間 | 小さい（仕組みはある） | 大きい（子プロセス・隔離・プロトコル） |

今のプラグインで一番困るのは**写しのずれ**である。ずれた先が存在しないクラスなら警告が出るが、
**実在する別のクラス**を指すと気付けないまま誤った 1 件に絞られる。
「絞れないより誤って絞る方が害が大きい」（[static-analysis-limits.md](static-analysis-limits.md) の 6 節）形である。

断片実行で困るのは、対象のコードを実行すること、ビルド済みの `.class` が要りソースとずれうること、
環境で答えが変わり期待値との比較がしにくいこと、関数の切り出しが要ること、作る量が大きいこと。

どちらも、失敗したときは `null` を返して CHA に戻り、キャッシュに何も書かない。漏らさない側に倒れる点は同じ。

## 判断

### Q10. なぜ断片実行を採らないのか

Q9 の困るところのうち、次の 2 つを許容しないと決めたから。

1. **対象のコードを実行する。** 今のツールは解析対象のソースと jar を読むだけで、解析対象のビルドも実行しない
   （[github-actions.md](github-actions.md) の「セキュリティ上の注意」）。だから社外のコードや、
   GitHub Actions でレビュー前の PR も、そのコードを実行する心配なく解析できる。
   断片実行を入れると、この前提が「設定次第で崩れる」ものになる。
   子プロセスへの隔離は被害を狭めるだけで、実行しないことの代わりにはならない。
   しかも「実行する」ことは断片実行の定義（Q3 の条件 4）そのものなので、設計の工夫では消せない
2. **名前を組み立てる部分を関数に切り出す必要がある。** 丸ごと実行すれば切り出しは要らないが、
   それでは `newInstance()` のコンストラクタまで動き、1 の問題がさらに大きくなる。
   切り出しを求めると、利用者に「解析のためにコードを直す」ことを強いる。
   手段 3（コード側を `switch` + `new` に変える。[static-analysis-limits.md](static-analysis-limits.md) の 8 節）と
   同じ負担を、より弱い効果のために払わせることになる

残りの困るところ（`.class` が要る、遅い、作る量が大きい）は工夫で小さくできるが、
この 2 つは断片実行である限り残る。

### Q11. 実行は表を作るときだけにして、普段の解析は契約表を引く中間案はどうか

断片実行で `get("user") => jp.co.app.impl.UserService` のような行を書き出し、人が確かめて契約表に取り込む案。
普段の解析は対象を実行せず、ソースだけで動き、毎回同じ答えで、レビューもできる。

それでも採らない。表を作るときに**対象のコードを実行する**点と、**関数の切り出しが要る**点は変わらないから。
実行する場面が減るだけで、Q10 の 2 点はどちらも残る。

### Q12. 何をするのか

**解析器が自分で文字列の計算を評価する。** 計算の結果ではなく計算の**形**をデータフローに記録しておき、
呼び出し元のキーが分かった時点で、解析器が持っている操作だけで計算する。

```
ServiceFactory.get(key):
  fqn = "jp.co.app.impl." + capitalize(key) + "Service"
  → 記録する形: 連結("jp.co.app.impl.", capitalize(引数0), "Service")

capitalize(s):
  return Character.toUpperCase(s.charAt(0)) + s.substring(1)
  → 記録する形: 連結(大文字化(文字取得(引数0, 0)), 部分文字列(引数0, 1))

呼び出し元 get("user")
  → 引数0 = "user" を当てはめて解析器が計算する → "jp.co.app.impl.UserService"
```

いまも `Class.forName(className)` は `C:0` として記録され、呼び出し元がリテラルを渡していれば型が決まる
（[static-analysis-limits.md](static-analysis-limits.md) の 3 節）。止まっているのは、その間に文字列の連結や加工が挟まったときだけで、
そこを埋める。分類は**静的解析**で、既存の手続き間の定数伝播を文字列の操作まで広げたもの。
Q2 で「部分実行」を避けた理由に挙げた**部分評価**（partial evaluation）は、本来この種の方法を指す。

Q10 の 2 点はどちらも満たす。

| 許容しない点 | この方法では |
|---|---|
| 対象のコードを実行する | 実行しない。対象のクラスを読み込まず、static 初期化も動かない。javac が `"a" + 定数` を畳み込むのと同じ種類の処理 |
| 関数の切り出しが要る | 要らない。`Class.forName` の引数から遡り、`get` の本体の中で組み立てていれば、そのまま式として読む |

規則の写しも要らない（ソースを直接読む）ので、今のプラグインの「写しのずれ」も起きない。
ビルド済みの `.class` も要らず、答えは入力だけで決まるので、解決の結果が処理順に依存しないという決まりとも衝突しない。

### Q13. 何を計算し、何を計算しないのか

計算するのは、**副作用が無く、答えが入力だけで決まる操作**に限る。知らない操作が出てきたら「判定しない」に倒し、
今までどおり CHA で候補を全部出す。

| 計算する | 計算しない（判定しない） |
|---|---|
| `+`、`concat`、`substring`、`charAt`、`trim` / `strip` | ループ、深すぎる再帰 |
| `Character.toUpperCase` / `toLowerCase` | `final` でない static フィールドを読むもの |
| `String.valueOf`、`replace`（引数がリテラルのとき） | Map / List からの取り出し |
| `StringBuilder` の `append` を 1 本につないだもの | ファイル・DB・環境変数・システムプロパティ |
| `if` / 三項演算子（両方の答えを候補にする） | 知らないメソッド全般 |

決めていないこと:

- 引数なしの `String.toUpperCase()` / `toLowerCase()` は、実行する環境の言語設定で結果が変わる（トルコ語の `i` など）。
  「毎回同じ答え」を守るために、判定しないか、条件付きで計算するかを実装時に決める
- 止まったときは、**どの操作で止まったか**を注記に書く（例: `string operation not evaluated: String.format`）。
  利用者はそれを見て、契約表で補うかコードを直すかを選べる。注記の語は英語で、カンマを入れない
- 依存 jar の中で加工している場合（`StringUtils.capitalize` など）は、ソースが無いので読めない。
  よく使われる純粋な関数の意味をツールに同梱した表で持つ案がある。これも一種の写しだが、写すのは
  利用者のコードではなく意味が安定した有名ライブラリで、書くのも検査するのもツール側である
  （呼び戻しの契約表 `JdkCallbacks` と同じ考え方）。jar のバイトコードを読んで評価する案は、作る量が大きいので後回し

### Q14. それでも残る限界と、作るときに触る場所は

残る限界:

- **外部の入力**（設定ファイル・DB・リクエストの値）で決まるものは解けない。断片実行でも同じだった
  （本番の設定を持っていないため）。今までどおり契約表で人が補う
- Map に名前とクラスの対応を並べたファクトリは別の課題。ただし `static final Map.of(...)` の形なら同じ考え方で読める
- jar の中からの**呼び戻し**（`forEach` など）は、もともと契約表で扱っており、実行は要らない

作るときに触る場所（目安）:

| 場所 | 変更 |
|---|---|
| `jche.cache.Origin` | 「計算の形」を表す種別を足す。**dataflow キャッシュの版を上げる** |
| `jche.analysis.OriginTracker` / `ValueGraph` | 連結や既知の操作の呼び出しを式として記録する。式の大きさに上限を設ける |
| `jche.graph.DataflowResolver` | 呼び出し元のキーを当てはめて計算する（`literalOf` の拡張） |
| `test/demo` と期待値 | 名前を組み立てるファクトリの例を足し、1 件に確定することを確かめる |
