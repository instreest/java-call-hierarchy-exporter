# 構文エラーで読めなかったファイルを報告する — QA 一覧

> 使い方は [eclipse-plugin-usage.md](eclipse-plugin-usage.md)、
> キャッシュの設計は [cache-design.md](cache-design.md) にある。

レガシーなソースの調査中に見つかった不具合。**構文エラーでファイルを読めなくても、
ツールは `失敗=0` と報告して `OK` を返していた。** そのファイルに書かれた呼び出しは
出力に一切出ないのに、利用者が気づく手段が無かった。

このツールが守ると決めている「**呼び出しを静かに落とさない（安全側に倒す）**」
（[AGENTS.md](../AGENTS.md)）に真っ向から反するので直した。

| 変えたところ | 内容 |
|---|---|
| `jche/analysis/CallEdgeExtractor` | 構文エラーだけを別に数える（`IProblem.Syntax`） |
| `jche/cache/FileAnalysis` | `syntaxErrors` を持つ |
| キャッシュの F 行 | 末尾に構文エラー数を足した（形式の版 v21 → **v22**） |
| `jche/Exporter` | フェーズ1の集計に出し、ファイル名を並べて警告する |
| `jche/server/Server` | `ANALYZE` の応答に `syntaxErrors=` を足した |
| `CallHierarchyView`（Eclipse） | バナーに「⚠ n 件のファイルは構文エラーで読めていません」と出す |

---

### Q1. 何が起きていたのか

Java 1.4 の書き方（`enum` を識別子に使う）をしたファイル 1 つを解析させると、こうなった。

| | メソッド数 | エッジ数 |
|---|---|---|
| `enum` を識別子に使ったまま | **4** | **1** |
| `enum` を `it` に直しただけの同じコード | 8 | 6 |

**メソッドの半分と呼び出しの 5/6 が消えている。** それでもログは
`ソース解析: 再利用=1 新規解析=0 失敗=0` で、応答は `OK` だった。

原因は、JDT が構文エラーを出しても**例外を投げない**ことである。壊れた部分を飛ばした AST が
返ってくるので、こちらから見れば「そういう内容のファイルだった」ようにしか見えない。
`sink.failed()` が呼ばれるのは例外が飛んだときだけなので、`失敗` には数えられていなかった。

### Q2. 既存の「エラー数」では足りなかったのか

足りない。F 行には前から `errors`（JDT が報告したエラーの数）があったが、
これは**型が見つからない類のエラーも一緒に数えている**。

| | AST | 呼び出しは拾えているか |
|---|---|---|
| 型解決のエラー（依存 jar の不足） | 最後まで組み上がる | **拾えている**（解決先が分からないだけ） |
| 構文エラー | 壊れた部分が欠ける | **拾えていない** |

前者はごく普通に起きる（`library.folders` を設定していなければ大量に出る）ので、
これを理由に警告を出すと嘘の警告で埋まる。**分けて数えるしかない。**

JDT の分類は使える。実測したところ、構文エラーだけが `IProblem.Syntax` のビットを持つ。

```
enum を識別子に  : syntaxBit=true  catID=20 : Syntax error on token "enum", delete this token
jar 不足        : syntaxBit=false catID=30 : The import com.nope cannot be resolved
jar 不足        : syntaxBit=false catID=40 : Missing cannot be resolved to a type
```

### Q3. なぜキャッシュの形式まで変えたのか（版を上げてまで）

**2 回目以降の実行で警告が消えてしまうから**である。

構文エラーは解析（パース）のときにしか分からない。キャッシュから書き写したファイルは
パースし直さないので、数えるだけでは「1 回目は警告が出て、2 回目からは出ない」ことになる。
ところが**結果の欠けは 2 回目以降も続いている**（欠けたままのブロックを書き写すのだから）。
これでは直したことにならない。

そこで F 行の末尾に構文エラーの数を足し、書き写すときにも数えるようにした
（`CacheFormat#syntaxErrorsOf`）。形式が変わるので `VERSION` を v22 に上げてある。
古いキャッシュは自動的に捨てられ、1 度だけ全件解析が走る。

実際に確かめた挙動:

```
1回目（新規解析）: ソース解析: 再利用=0 新規解析=1 失敗=0 構文エラー=1
2回目（再利用）  : ソース解析: 再利用=1 新規解析=0 失敗=0 構文エラー=1
```

### Q4. 何をどこに出すのか

3 か所に出す。読む人が違う。

1. **フェーズ1の集計**（`構文エラー=n`）… 一目で異常だと分かる数字
2. **警告のブロック**（ファイル名つき）… どれを見ればよいかが分かる。
   多すぎても意味が無いので 20 件まで並べ、残りは件数だけ
3. **Eclipse のバナー**（`⚠ n 件のファイルは構文エラーで読めていません`）…
   ログを開かない利用者にも届く。ここが無いと、画面上は「呼び出し元が無い」と
   区別が付かない

3 のためにサーバーの `ANALYZE` の応答へ `syntaxErrors=` を足した。
画面が「木に出ていないのは、呼び出し元が無いからではなく読めていないからだ」と
言い分けられる唯一の材料である。

### Q5. 解析を失敗させるべきではないのか

しない。**1 ファイル読めないだけで、他の何万ファイルの結果を捨てる理由にはならない。**

このツールの扱いはもともと「読めないものは飛ばして、飛ばしたことを言う」で統一してある
（`sink.failed` も同じ）。今回はその「言う」が抜けていただけなので、そこだけを足した。

`errors` と同じく、`syntaxErrors` が 0 でないファイルは**依存 jar が変わったときの
再解析の対象**にもなる。JDT を新しくしたら直る、という筋もあるので、
次の機会に読み直されるのは都合がよい。

### Q6. どういうときに出るのか

ふたつとも「JDT とソースの版が合っていない」という同じ形をしている。

- **ソースが JDT より新しい**。たとえば Java 27 の新しい文法を、それを知らない JDT で読んだとき。
  `source.level` を上げても、JDT が知らなければ読めない
- **ソースが JDT より古い**。Java 5 より前の `enum` / `assert` を識別子に使っているとき。
  いまの JDT は 1.8 未満の `source.level` を受け付けず 1.8 として読むので、構文エラーになる
  （[eclipse-plugin-java-floor-qa.md](eclipse-plugin-java-floor-qa.md) の Q6）

どちらも警告に「解析に使った Java の版」と「この JDT の対応上限」を添えてあるので、
どちら側にずれているかはその場で分かる。

### Q7. `IProblem.Syntax` のビットだけで「本体を読めなかった」と言ってよいのか

言えない場合があった。JDT は **`var` の使い方の誤り**にも `IProblem.Syntax` のビットを付ける。

```
class var { … }            : syntaxBit=true id=1509 'var' is not a valid type name
var x = 1, y = 2;          : syntaxBit=true id=1500 'var' is not allowed in a compound declaration
var z;                     : syntaxBit=true id=1503 Cannot use 'var' on variable without initializer
```

これらは**文法を最後まで読んだあとで**、`var` の置き場所を JLS 14.4.1・JLS 3.9 に照らして
検査した結果である。構文そのものは読めているので、AST は欠けていない。
実測では、上の誤りをすべて書いたメソッドでも呼び出しは全件解決され、`MALFORMED` / `RECOVERED` の
印の付いたノードは 1 つも無かった。

それでも構文エラーに数えていたので、Java 10 より前のコードで `var` という名前のクラスを持つものを
`source.level` を指定せずに読むと、「構文エラーのため本体を読めませんでした（このファイルの呼び出しは
出力に出ません）」と警告しながら、**そのファイルの呼び出しは出力に出ていた**。
警告が事実と逆のことを言うと、利用者は出力のほうを疑うことになる。

そこで、`var` の誤りを表す 9 個の ID（`IProblem.VarLocalMultipleDeclarators` 〜
`VarCannotBeUsedWithTypeArguments`。すべて `Syntax` のビットを持つ）を
構文エラーの数から外した（`CallEdgeExtractor#isSyntaxError`）。
エラーであることには変わりないので `errors` には数え、「コンパイルエラーのあるファイル」として案内する。
その案内には「Java の版が食い違っている（`source.level`）」が対処として載っているので、
利用者が次にすべきことは変わらない。

外すのは `var` の誤りだけにした。`Syntax` のビットを持つ ID は他にもあるが、本体が欠けないと
実測で確かめたのはこの 9 個だけである。確かめていないものを外すと、今度は
「読めていないのに黙る」側に倒れる（Q1 の不具合そのもの）。

### Q8. キャッシュの版は上げたか

上げた（`jche-cache-v29` → `v30`）。F 行の構文エラー数は Q3 のとおり**書き手が数えてキャッシュに持つ**ので、
古いキャッシュを再利用すると、そのファイルだけ前の数え方の警告が出続ける。

検査は `test/warnings/run.sh` の `varname`。`class var` を持つファイルが、コンパイルエラーとしては案内され、
構文エラーとしては数えられず、本体の呼び出しが出力に出ることを見る。

その後、switch 式の検査（default が無い・列挙定数や sealed の許可リストを網羅していない・switch 式の外への
break / continue / return）にも同じ印が付き、本体は読めているのに構文エラーと報告していたことが分かった。同じく
構文エラーの数から外した（形式 v35。[cache-unification-qa.md](cache-unification-qa.md) の Q58。検査は `test/warnings/run.sh` の `switches`）。
