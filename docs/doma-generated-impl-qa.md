# ORM ライブラリ（Doma）のコンパイル時生成クラスに対応する — 実装時の QA 一覧

[Issue #73](https://github.com/instreest/java-call-hierarchy-exporter/issues/73)
「ORMライブラリのDomaフレームワークに対応したい」の対応で、迷ったこと・困ったことと、その結論を
Q&A の形で残す。

対応の要点:

- キャッシュの `H` 行（型）と `D` 行（メソッド）に、付いているアノテーションのFQNを持たせた（`v13`）。
  選別はせず、付いているものを宣言順に全部残す
- 「アノテーション処理でコンパイル時に実装クラスが生成される型」の定義を
  `src/jche/framework/GeneratedImpl.java` に置き、Doma（`org.seasar.doma.Dao` → `<FQN>Impl`）を同梱した
- 解決ラベルに `GENERATED_IMPL:名前` を足した（`NO_IMPL` の特殊形）
- `call-hierarchy.csv` の注記に
  `実装はコンパイル時生成（Doma）: fx.dao.ItemDaoImpl はアノテーション処理で生成されるためソース上に無い` を出す。
  `methods.csv` の `unresolvedCause` にも `実装はコンパイル時生成（Doma）` を出す
- 回帰テストの `test/demo` に `@Dao` を付けたインターフェースと、その呼び出し元を足した

---

## 設計の選択

### Q1. 生成クラスを呼び出し階層にどう「記載」するか（3 案から選んだ）

Issue の To be は「コンパイル時に自動生成されるクラスは、ソースコードリポジトリ上では存在しないので、
それが分かるように呼び出し階層に記載する」。案は 3 つあった。

| 案 | 内容 | 判断 |
|---|---|---|
| A | 合成ノードを 1 段足す（`fx.dao.ItemDaoImpl.selectById(long)` を階層に出す） | 採らない |
| B | 注記だけ付ける | **採用** |
| C | A に加えて外部 SQL ファイル（`META-INF/<dao>/<method>.sql`）も葉として出す | 採らない（別 issue） |

依頼者の判断は「アノテーションから Doma がコンパイル時生成すると分かる場合、注記だけ付ける」。
理由として素直なのは、生成されたクラスの**本体がソースに無い**こと。ノードを足しても
その先の呼び出しは 1 本も辿れないので、行数が増えるだけで情報は増えない。
「実装はコンパイル時生成」という 1 つの事実は、注記 1 つで過不足なく伝わる。

Dao のメソッドと実際の SQL の対応は別の出力（別ツールになるかもしれない）で扱う予定で、
そのときは AST 解析キャッシュを共有する。だから今回は「キャッシュに事実を持たせる」ところまでを
本体として広めに作り、「呼び出し階層に何を出すか」は最小にした。

### Q2. なぜ設定ファイルに `framework.doma.enabled` のような項目を足さないのか

判定の材料が「宣言型に付いたアノテーションのFQN」だけで済み、誤検出のしようがないため。
`org.seasar.doma.Dao` が付いていないプロジェクトの出力は 1 行も変わらないので、
利用者に設定を書かせる意味がない。設定項目は増やすほど組み合わせが増え、テストも増える。

opt-in が要るのは「プロジェクト固有の命名規則」のような当たり外れのある推定だが、
今回は当たり外れが無い（アノテーションが付いていれば、実装は必ず生成される）。

### Q3. Doma 専用に書かず、汎用の「生成実装」枠組みにしたのはなぜか

同じ形のフレームワークが他にもあるため（MapStruct の `@Mapper` → `XxxImpl`、Dagger の
`@Component` → `DaggerXxx` など）。判定の形は「型に付いたアノテーションのFQN」→
「生成されるクラス名の規則」で共通なので、`GeneratedImpl.DEFINITIONS` に 1 件足せば増やせるようにした。

ただし、今回同梱するのは Doma だけにした。実際に確認していないフレームワークの定義を
先回りで足すと、規則が違ったときに嘘の注記を出すことになる。

### Q4. 既存の拡張点（`jche.extension.TypeCandidateProvider`）ではなくコアに入れたのはなぜか

拡張点は「既に**ソース上にある**型のどれに解決するか」を答える口で、返せるのは
メソッド表に登録済みのFQNだけ（`CallResolver#askProviders` は `methods.idOf(...)` が
引けなかった候補を捨てる）。生成クラスはソースに無いので、拡張からは表現できない。

また、拡張はFQNを設定ファイルに書いて opt-in する仕組みなので、Q2 の「設定を書かせたくない」とも合わない。

## キャッシュ

### Q5. アノテーションはキャッシュに入れてよい「事実」か

よい。`CacheFormat` の原則は「ASTとバインディングから機械的に読み取れ、設定・出力形式・
解決アルゴリズムに依存しない情報だけを持つ」で、「この型に何のアノテーションが付いているか」は
まさにそれ。逆に「`org.seasar.doma.Dao` が付いているから生成される型だ」は判断なので、
読み手（`jche.framework.GeneratedImpl`）に置いた。

この切り分けのおかげで、対応フレームワークを増やしても再解析は要らない。

### Q6. どのアノテーションを残すか選別しなかったのはなぜか

選別は判断であり、キャッシュに焼き込むと「対応フレームワークを 1 つ足すたびに全件再解析」になるため。
`@Override` のようにありふれたものも残るぶんキャッシュは少し大きくなるが、
このリポジトリ自身を解析したキャッシュ（約 1.9MB）で、アノテーションの列が占めるのは
約 1.7KB（0.1% 未満）だった。読み込みは行の分割だけなので、実行時間にも差は出ない。

将来の「Dao メソッドと SQL の対応」でも、必要になるのは `@Select` / `@Insert` のような
メソッドのアノテーションなので、選別しない形のほうが都合がよい。

### Q7. メソッドのアノテーション（`D` 行）まで足したのは、今回の対応には要らないのでは

要らない。今回の判定に使うのは型（`H` 行）のアノテーションだけ。
それでも足したのは、Issue の依頼者から「Dao のメソッドと実際の SQL の対応表は別の issue で扱うが、
AST 解析キャッシュは共有できるようにしたい」という前提が示されていたため。
キャッシュの形式を変えると全件再解析になるので、同じ版で一度に入れておいたほうが利用者の手戻りが少ない。

### Q8. 列を足すだけなのにキャッシュ版（`v13`）を上げる必要があるか

ある。列を増やすと旧形式の行は新しい列を持たないので、`fromRow` は空として読む。
それ自体は動くが、「アノテーションが付いていない」と「古いキャッシュだから記録されていない」が
区別できず、`@Dao` が付いた型を `NO_IMPL` と誤って出し続けることになる。
`CacheFormat` の基準（事実の意味・列・収集範囲が変わったら上げる）どおりに上げた。

## 出力

### Q9. `NO_IMPL` を置き換えず、別ラベル（`GENERATED_IMPL:名前`）にしたのはなぜか

`NO_IMPL`（実装なし）は「実装を書き忘れている」「実装が jar 側にある」など、読み手が
**追いかけるべき**状態を含む。生成クラスは追いかけても出てこないので、同じラベルにすると
`methods.csv` の `unresolvedCause` で件数を数えるときに両者が混ざる。
ラベルを分けたことで、Doma を使っているプロジェクトでは
「実装なし」の件数から DAO のぶんを外して見られる。

フレームワーク名をラベルに含めた（`GENERATED_IMPL:Doma`）のは、複数のフレームワークを
併用しているプロジェクトで、どちらの生成かを CSV のフィルタで分けられるようにするため。

### Q10. 注記に生成クラス名（`fx.dao.ItemDaoImpl`）まで出す意味があるか

生成物を実際に探すときの手がかりになるため（Maven なら `target/generated-sources/annotations/`、
Gradle なら `build/generated/sources/annotationProcessor/`）。
ただし Doma の生成名は `doma.dao.subpackage` / `doma.dao.suffix` オプションで変えられるので、
これはあくまで既定の規則での推定。だから注記に出すだけで、解決（メソッド表の引き当て）には使っていない。

### Q11. `@Dao` インターフェースのデフォルトメソッドはどう出るか

本体がソースにあるので、これまでどおり普通に展開される（`NO_OVERRIDE`）。
生成の対象は本体を持たないメソッドだけなので、`CallResolver` の分岐（本体を持つ候補が皆無のとき）が
そのまま正しい切れ目になっていた。`test/demo` の `ItemDao#selectFirst` がこのケースで、
デフォルトメソッドの中から `selectById` を呼ぶ形（＝注記が階層の途中に出る形）も一緒に見られる。

### Q12. `@Dao` インターフェースに手書きの実装がソースにあったら

そちらが `SINGLE_IMPL` として解決され、注記は付かない。生成の判定は
「本体を持つ候補がソース上に 1 つも無い」ときにしか働かないので、
手書きの実装がある場合は今までどおりの結果になる（テスト用のスタブ実装を置いている場合など）。

## テスト

### Q13. 回帰テストのために Doma の jar を持ち込むか

持ち込まない。`test/demo` は依存 jar を最小限に保っている（`deps/missing-lib.jar` だけ）うえ、
判定に必要なのは**アノテーションのFQNが解決できること**だけで、中身は要らない。
そこで `test/demo/src/org/seasar/doma/Dao.java` に同じ完全修飾名の空のアノテーションを置いた。

副作用として `org.seasar.doma.Dao` 自身も解析対象の型になるが、アノテーション型はメソッドを
持たないので `methods.csv` には 1 行も増えなかった。

### Q14. 既存の期待出力への影響

`test/demo` にクラスを足したので、`whole` / `entry` / `jarchange` の期待出力に行が増える。
差分はすべて追加行（既存行の変化なし）で、`maven` / `mavenmulti` / `gradle` は別プロジェクトを
解析するため無変更であることを確認したうえで、期待出力を更新した。
