# 定数の値とキャッシュの差分更新 — 実装時の QA 一覧

キャッシュの健全性・可用性についてのソースコードレビューで見つかった問題への対応で、
迷ったこと・困ったことと、その結論を Q&A の形で残す（Issue は無し）。

対応の要点:

- **行のエスケープ**: 値に混ざったタブ・改行でキャッシュの行が割れ、以降の呼び出しが
  読めなくなっていた。`CacheFormat.joinRow` で全列を必ず `clean` し、
  `Guard.atom` の出所も落とす。値を作る側（`OriginTracker` / `AnnotationTokens`）でも、
  行形式を壊す値は最初から拾わない
- **定数の連鎖**: コンパイル時定数の値は使う側のファイルに焼き込まれるため、
  「依存は1段で足りる」という差分更新の前提が定数についてだけ成り立たない。
  宣言している側に値を K 行（`jche.cache.ConstantFact`）として残し、解析し直して
  値が変わったときだけ、その型を参照しているファイルも解析し直す
- **注釈型の依存**: `BindingNames.annotationsOf` が注釈の型を「依存する型」（I 行）に
  数えていなかった。注釈のメンバの**既定値**は使う側の行に焼き込まれるので、数える
- キャッシュ形式は v14 → v15（K 行の追加と、収集範囲の変更のため）
- 検査は `test/incremental/run.sh`（差分更新の結果と全件解析の結果を突き合わせる）

## 見つかった問題

### Q1. 「定数の値が古いまま残る」とは、具体的に何が起きるか

3 ファイルあれば再現する。

```java
// P.java
public class P { public static final String KIND = "ALPHA"; }
// X.java
public class X { public static final String KIND = P.KIND; }     // 値が焼き込まれる
// C.java
if (X.KIND.equals("BETA")) { Target.beta(); }                    // ここにも "ALPHA" が焼き込まれる
```

`P.KIND` を `"BETA"` に変えて差分更新すると、`P.java` と `X.java` は解析し直されるが、
`C.java` の I 行（依存する型）には `app.X` しか無いので `C.java` は再利用されてしまう。
結果、`C.java` のキャッシュには古い `V:ALPHA` が残り、

- 条件分岐の打ち切りが逆になる（呼ばれるはずの `Target.beta()` から先が階層に出ない）
- クラス名の文字列を辿るデータフローが、古い具象クラスを**断定して**出す
  （`解決:DATAFLOW_FACTORY` と注記が付くので、読み手には正しく見える）

キャッシュを消すまで直らず、更新時刻もサイズも変わらないので気づけない。
「呼び出しを静かに落とさない」に真正面から反する。

### Q2. 1段（直接参照）なら動いていたのはなぜか

たまたま `FieldAccessRecorder`（A 行の記録）が、参照したフィールドの所有型を
`BindingNames.typeNameOf` に通していて、そこで I 行に載っていたため。
値を畳んでいる `OriginTracker` 自身は依存を宣言していなかったので、A 行の記録の
都合が変わればいつ壊れてもおかしくない状態だった。
今回、畳む場所でも `noteDependency` を呼ぶようにして、この偶然に頼らないようにした。

### Q3. 行が割れる方の問題は何か

複数行の注釈の値だけで起きる。Spring Data の `@Query` はこの形が普通。

```java
@Query("SELECT u\n" + "FROM User u\n" + "WHERE u.name = ?1")
public String findByName(String name) { … }
```

注釈の値は D 行の最後の列に入るので、値の改行でそのまま行が割れる。
さらに 2 行目が `FROM …` だと**行頭が `F`** なので、次回の差分更新で
「別のファイルのブロックが始まった」と読まれ、`copyValidBlocks` がそこで書き写しを止める。
実測では、その注釈より後ろにあったメソッドと呼び出しが新しいキャッシュから丸ごと消え、
`call-hierarchy.csv` からも `methods.csv` からも二度と出てこなくなった。
`char sep = '\t';` のような定数でも、列がずれる形で同じことが起きる。

## 設計

### Q4. 直し方の案を 3 つ比べてどれを選んだか

| | やること | 直る | 触る範囲 | 失敗したときの被害 |
|---|---|---|---|---|
| 案3 | 定数を宣言するファイルを解析し直したら、参照元も連鎖して解析し直す | ○ | 判定だけ（15〜20 行） | 再解析が多いだけ |
| **案1** | 同じ連鎖を、**定数の値が実際に変わったときだけ**行う | ○ | 判定＋K 行（100〜150 行） | 再解析が多い／少ないだけ |
| 案2 | 値を焼き込むのをやめ、`F:型#フィールド` の参照だけ記録して読む側で引く | ○ | 記録する事実の意味（250〜350 行） | **キャッシュ無しでも結果が変わりうる** |

**案1** を選び、段取りとして先に案3 の形（連鎖の仕組みだけ）を入れてから、
K 行で「値が変わったときだけ」に絞った。決め手は 2 つ。

1. 案1・案3 が触るのは「解析し直すかどうか」の判断だけで、キャッシュを消せば必ず
   正しい答えが出る状態が保たれる。案2 は解析の中身を変えるので、しくじると
   キャッシュを消しても間違った答えが出る
2. 案1 なら、注釈の既定値の取りこぼし（Q8）も同じ仕組みで直る

### Q5. 案2（値ではなく参照を記録する）を採らなかった理由

原理的には案2 が根治で、連鎖も要らない。実際にコードを当てて調べたところ、
当初の見積もりが甘かったことが分かったため見送った。

- **宣言している側の J 行を流用できない**。`static final String PHRASE = "hello world";` や
  `JOINED = CLASSLIKE + "X"` の J 行は `U`（追跡不能）で、値を持っていない。
  一方で**使う側**は `getConstantValue()` を使うのでこれらも拾えている。
  そのまま案2 にすると、いま拾えている値を失って打ち切りが効かなくなる
- **既存の表を流用できない**。`CallGraph.fieldOrigins` は `static` フィールドを
  除外している（コンストラクタ注入の判定用のため）ので、定数用の表を新設することになる
- **ガードの両側を直す必要がある**。他ファイルの定数は、判定対象の側にも期待値の側にも現れる
  （`EQ｜A:0｜USER_DAO`、`EQ｜V:false｜true`）ので、`GuardEvaluator` の `holds` / `contains`
  の両方で解決が要る
- **jar の定数を失う**。`SomeLibConstants.PROD` はソースが無いので読む側で引けない。
  `ITypeBinding.isFromSource()` で場合分けすれば防げるが、分岐が 1 つ増える
- 結局**キャッシュ形式の変更は避けられない**（C 行・U 行の出所の意味が変わるので旧キャッシュは必ず捨てる）

案1 も案2 も「利用者が 1 回だけ全件解析になる」点は同じで、そこは差にならない。

### Q6. 連鎖はどこまで広がるか

このリポジトリ自身（116 ファイル）で測った。

```
コンパイル時定数: 127 件 / 定数を宣言しているファイル: 33 件（28%）

1 ファイル書き換えたときの再解析数（平均）
  もとの実装   3.9 件（ただし定数の取りこぼしあり）
  案3          6.3 件（1.6 倍。値を見ずに連鎖するため）
  案1         ≒4   件（値が変わったときだけ連鎖）
```

案3 でも最悪で全体の 2 割程度（2 → 24 件）だったので、正しさだけなら案3 で足りる。
案1 はそこから無駄を削る位置づけで、`test/incremental/run.sh` では
「定数の値を変えた書き換え = 5 件」「コメントだけの書き換え = 3 件」と差が出ることを固定している。

### Q7. K 行に何を入れるか。長い値はどうするか

`K  typeFqn  name  種別(V=値/H=ハッシュ)  値` の 5 列。
`static final` で `getConstantValue()` が値を返すフィールドと、注釈のメンバの文字列の既定値を入れる。

値は基本そのまま持つが、64 文字を超えるものと行形式を壊す文字を含むものはハッシュにする
（`jche.util.FileHash.ofText`）。SQL や Base64 のような長い定数でキャッシュが膨らむのを
避けつつ、変化は取りこぼさないため。種別の列を持つのは、「たまたまハッシュと同じ綴りの
短い値」と区別するため。

### Q8. 注釈の既定値まで見る必要があるか

ある。`@Ann` とだけ書いても、`String value() default "svc"` の `"svc"` は
`IAnnotationBinding.getAllMemberValuePairs()` から返ってきて、使う側の H 行・D 行・V 行に
焼き込まれる。しかも注釈の型が I 行に載っていなかったので、既定値を書き換えても
使う側は再解析されなかった。`annotationsOf` で注釈型を依存に数え、既定値も K 行に入れて、
定数とまったく同じ仕組みで面倒を見ている。

### Q9. 列挙定数は大丈夫か

大丈夫で、今回も変えていない。

- 列挙定数の出所は `V:fx.Mode.FULL` のように**宣言型で修飾された名前**で、値ではない。
  定数の追加・削除・改名は必ず enum のソースの変更になり、参照側の I 行にはその enum 型が
  載っているので、これまでどおり 1 段の依存で追随できる
- `static final Mode MODE = Mode.FULL;` は enum 型なのでコンパイル時定数にならず、
  値の焼き込み自体が起きない（安全側に倒れて打ち切らない）

`test/incremental/run.sh` に「列挙定数の改名」のケースを入れて、この性質を固定した。

### Q10. キャッシュの版を上げる必要はあるか

ある（v14 → v15）。K 行という行種を足したことに加え、行形式を壊す値を
「事実として拾わない」ことにした＝収集範囲が変わったため
（[CacheFormat](../src/jche/cache/CacheFormat.java) の「バージョンを上げる基準」）。

## 実装

### Q11. パス3 を「判定」と「書き写し」に分けたのはなぜか

連鎖するには「再解析する → 変わった型が増える → もう一度判定する」を繰り返す必要があるが、
もとの `copyValidBlocks` は判定と書き写しを 1 回のスキャンで同時にやっていた。
書き写しを始めてしまうと、あとから「やっぱりこのブロックは再解析」と決め直せない。

そこで `selectDependents`（判定だけ。何も書かない）と `copyValidBlocks`（書き写しだけ）に分け、
判定 → 再解析 → 判定 …… を不動点まで回してから、最後に書き写すようにした。
結果として両方のメソッドが短くなり、F 行の先読みのような込み入った扱いも消えた。

代償はキャッシュファイルを読む回数が 1 回増えること（判定 1 回＋書き写し 1 回）。
連鎖が起きない実行では判定で何も動かないので、「変わった型」が 1 つも無いときは
判定そのものを飛ばしている。

### Q12. 連鎖は必ず止まるか

止まる。1 周ごとに `valid`（そのまま書き写す候補）からファイルが減るだけで、
増えることはない。加えて、周回の前後で「変わった型」の数が増えていなければ
そこで打ち切る（`StaleTypes.mark()`）。

### Q13. 旧キャッシュの定数をヒープにどう持つか

ファイルごとに **16 文字のハッシュ 1 つ**だけ持つ（`CacheUpdater.oldConstants`）。
K 行の指紋を並べて `FileHash.ofText` したもので、値そのものは持たない。
既にある「相対パス → 内容ハッシュ」の表（`hashes`）と同じ重さで、
「解析結果をヒープに溜めない」という設計は崩していない。

K 行は指紋の順に並べて書く。同じソースならいつ解析しても同じ並びになるので、
旧キャッシュとの突き合わせが並び順に振り回されない。

### Q14. 制御文字を含む値は、書き出すときに空白へ置き換えるのではだめか

書き出すときの置き換え（`CacheFormat.joinRow` の `clean`）は最後の関所として入れたが、
それだけにはしなかった。`'\t'` と `' '` が同じ値になってしまうと、
`if (SEP == '\t')` のような条件で「成立しない」と**誤って**打ち切りうるため。

値を作る側（`OriginTracker.valueConst` / `AnnotationTokens.token`）では、
行形式を壊す文字を含む値はそもそも拾わない。拾わなければ読み手は判定をしないので、
安全側（打ち切らない）に倒れる。「分からない条件はアトムにしない」という
[branch-pruning-qa.md](branch-pruning-qa.md) の方針と同じ考え方。

### Q15. 注釈の値に長さの上限（64 文字）を入れたのはなぜか

この値を読むのは DI コンテナの Bean 名・Qualifier 名の照合（`jche.graph.SpringBeans`）だけで、
どれも短い識別子だから。一方 `@Query("SELECT …")` のように長い SQL を値に取る注釈は珍しくなく、
上限が無いとキャッシュがその文字列で埋まる。上限を超えたものは「付いていた事実」だけ残す。

値を丸ごと捨てる（空白に置き換えない）のは、別々の値が同じ Bean 名に見えて候補を
誤って絞り込むのを避けるため。絞れない方に倒れる。

## テスト

### Q16. なぜ期待値ファイル（`expected*/`）を持たない検査にしたか

この検査が見たいのは「差分更新と全件解析で結果が違わないこと」で、
**同じソースに対する 2 通りの解析を突き合わせれば足りる**から。期待値を持つと、

- 検査用のソースを 1 行足すたびに期待値の更新が要る
- 期待値を更新するときに、本当は直っていない差分をうっかり取り込みうる

`test/regression/` は「出力の内容」を固定する検査なので期待値が要るが、
こちらは「2 つの経路が一致する」という性質の検査なので要らない。

### Q17. CSV だけでなくキャッシュも比べる理由

CSV に出ない事実の取りこぼしを捕まえるため。注釈の既定値（Q8）がまさにそれで、
H 行の値が古いままでも `call-hierarchy.csv` は変わらない。
キャッシュを突き合わせれば、事実の段階で食い違いを見つけられる。

差分更新ではブロックの並びが変わる（解析し直したブロックが末尾に移る）ので、
行を並べ替えてから比べる。F 行の更新時刻・サイズ・内容ハッシュは
どちらの経路でも「今のファイル」の値になるので、そのまま一致する。

### Q18. 「書き換えが効いている」ことをどう確かめるか

書き換えの仕方を間違えると、差分更新も全件解析も同じ（古い）結果になって検査が素通りする。
そこで書き換え前のキャッシュも取っておき、**F 行以外の行**（＝事実）が変わったかを見る。
F 行を除くのは、書き換えたファイルの更新時刻とサイズは中身に関わらず必ず変わるため。

### Q19. 直す前のコードで、この検査は落ちるか

落ちる。全 4 ケースで「差分更新 == 全件解析」が破れ、`@Query` を含むケースでは
「キャッシュの行が壊れていない」（行頭が既知の種別で、F 行の次は必ず I 行）も落ちる。
検査を書いたあとに必ず旧実装で落ちることを確認してから、直したコードで通した。

## 残っている課題（今回は手を付けていない）

同じレビューで見つかったが、原因も影響範囲も別なので分けてある。

- **`source.encoding` がキャッシュの鍵に入っていない**。文字コードを変える
  （または `pom.xml` の `project.build.sourceEncoding` が増えて自動判定が変わる）と、
  違う文字コードで読んだ事実をそのまま再利用してしまう。`CacheFormat.headerFor` に
  1 項目足せば、`source=` や `jdk=` と同じ仕組みで守れる
- **壊れたキャッシュで実行ごと落ちる**。不正なバイト列が混ざったキャッシュを読むと
  `MalformedInputException` がそのまま上がって設定ごと失敗する。ヘッダ不一致と同じく
  「破棄して全件解析」に倒すのが望ましい。GitHub Actions でキャッシュを復元する
  使い方があるぶん、外から壊れたファイルが来る経路は現実にある
- **同時実行**。同じ `project.root` を指す 2 プロセスが同じ `analysis-cache.tsv.tmp` を
  奪い合う。単独のプロセス内は逐次なので問題ない
