# GitHub Actions での AST 解析キャッシュの引き継ぎ — 実装時の QA 一覧

[Issue #79](https://github.com/instreest/java-call-hierarchy-exporter/issues/79)
「Github Actions で AST 解析キャッシュを利用したい（前回実行時のキャッシュファイルを引き継ぎたい）」への対応で、
迷ったこと・困ったことと、その結論を Q&A の形で残す。

対応の要点:

- ツール側: キャッシュの差分判定に内容ハッシュを足した。更新時刻とサイズが一致すれば従来どおり再利用、
  更新時刻だけが違うときはサイズが同じなら内容ハッシュ（SHA-256 の先頭 16 桁）を突き合わせて、中身が同じなら再利用する。
  `F` 行（ソース）と `L` 行（依存 jar）の末尾にハッシュの列を足し、フェーズAの拡張の指紋も更新時刻ではなく内容ハッシュで作る
- アクション側: `analysis-cache` 入力（既定 `true`）を足し、ツールのフォルダの `.cache/` を
  `actions/cache/restore` / `actions/cache/save` で実行間に引き継ぐ。キーは実行ごとに変え、復元は前方一致で「同じ設定の最新」→「同じ OS の最新」
- 回帰テストに「ソースと jar の更新時刻を全部変えてから実行しても、新規解析が 0 になる」ケースを足した（bash / cmd の両方）。
  `smoke.yml` の `action` ジョブでも、`touch` してから 2 回目の解析をし、`run.log` の集計行で再利用を確かめる

---

## 何が問題だったか

### Q1. 今までキャッシュを引き継いでも効かなかったのはなぜか

差分判定が「更新時刻とサイズの一致」だけだったため。`actions/checkout` は毎回チェックアウト時刻でファイルを作るので、
中身が同じでも更新時刻が必ず変わり、全ファイルが「変更あり」になる。`.cache/` を持ち越しても全件解析し直しになり、
保存と復元の時間だけが増える。この状況は `docs/github-actions-qa.md` の Q12 に「引き継がない」理由として書いてあった。

したがって「アクションに `actions/cache` を足す」だけでは Issue は解決せず、**ツール側の判定を変える**ことが本体になる。

### Q2. `git` から更新時刻を復元する（`git restore-mtime` 相当）案を採らなかったのはなぜか

チェックアウト後に各ファイルの更新時刻を「最後にそのファイルを変えたコミットの時刻」に戻せば、ツールを変えずに済む。
しかし、

- `actions/checkout` の既定は `fetch-depth: 1`（履歴が 1 コミットしか無い）。この状態では全ファイルの「最後のコミット」が
  HEAD になり、push のたびに全ファイルの時刻が変わる。効かせるには利用者に `fetch-depth: 0` を書かせることになり、
  大きなリポジトリでは取得が遅くなる
- ファイルごとに `git log` を引くのは、数千ファイルで数十秒かかる
- 解析対象が git 管理外（ビルドで生成したソース、`library-folders` に置いた jar）だと使えない

ツール側で「更新時刻が違っても中身が同じなら同じ」と判定できれば、これらの前提は要らない。

## ツール側の判定

### Q3. 内容ハッシュを「更新時刻の代わり」にせず「更新時刻が違うときの二次判定」にしたのはなぜか

毎回全ファイルのハッシュを取ると、手元の実行が遅くなる。`docs/cache-dependency-jars-qa.md` の Q2 では
「数十 MB の jar が百本あるプロジェクトで毎回ハッシュを取ると数秒かかる」として更新時刻とサイズを選んでいる。
この判断は変えず、**更新時刻とサイズが一致すればハッシュを計算しない**ようにした。

- 手元の実行（更新時刻が保たれる環境）… ハッシュは一度も計算されない。従来と同じ速さ
- CI（更新時刻が全部変わる環境）… 全ファイルのハッシュを計算する。ソースは小さいので、数千ファイルでも 1 秒前後。
  jar は `library.folders` にコピーしたものだけが対象（`~/.m2` の jar は `actions/cache` が更新時刻を保つので、計算しない）

「サイズが同じ」を先に見るのは、サイズが違えば中身も違うと分かるので、ハッシュを取る必要が無いため。

### Q4. ハッシュで通したブロックの `F` 行は、どう書き写すか

そのまま書き写すと `F` 行の更新時刻は古いままで、次の実行でもまた更新時刻が違い、またハッシュを計算する。
そこでパス3（有効なブロックの書き写し）で **`F` 行だけを今の更新時刻とハッシュに書き直す**ようにした。
CI では毎回チェックアウトし直すのでどうせ更新時刻は変わるが、手元で `cp -r` したプロジェクトのような
「一度だけ更新時刻が変わる」場合は、2 回目以降がまた速い経路に戻る。

### Q5. キャッシュの形式バージョン（`jche-cache-v13`）を上げなかったのはなぜか

`F` 行と `L` 行の**末尾**に列を足しただけで、既存の列の意味は変わらない。`CacheFormat.columnAt` は
「後ろに列が足された旧形式を許容する」ために「無い列は空文字」を返すので、旧キャッシュはそのまま読める。
ハッシュの列が無い旧行は、従来どおり更新時刻とサイズだけで判定され、パス3 で書き写すときにハッシュが補われる
（そのときだけ、その 1 回は全ファイルのハッシュを計算する）。

バージョンを上げると、この変更を入れた直後の 1 回は全利用者のキャッシュが捨てられる。それを避けられるなら避ける。
`CacheFormat` の「バージョンを上げる基準」（事実の意味・列・収集範囲が変わったとき）の「列」に当たるかは迷ったが、
「読み手が旧行を正しく扱える追加」は上げなくてよい、と解釈し、その旨をクラスコメントの一覧に残した。

### Q6. 依存 jar（`L` 行）にもハッシュを入れたのはなぜか

`library.folders` にコピーした jar（リポジトリに `lib/` として入れているプロジェクトは多い）は、
ソースと同じくチェックアウトで更新時刻が変わる。そのまま「変更された jar」と判定されると、
その jar のパッケージを参照している全ファイルと、型解決に失敗していた全ファイルが再解析になり、
ソース側のキャッシュが効いても意味が薄れる。判定の考え方はソースと同じにした
（サイズ一致 → 更新時刻一致なら同じ → 違えばハッシュ → 一致なら `L` 行の更新時刻だけ差し替える）。

クラスフォルダ（`target/classes` 等）はハッシュを取らない。中の `.class` を全部読むことになるうえ、
ビルドのたびに中身が変わるのが普通で、判定を工夫する意味が無い。従来どおり「.class の数と最新の更新時刻」で見る。

### Q7. フェーズAの拡張の指紋も変えたのはなぜか

拡張の指紋（`Config.hintPluginFingerprint`）は拡張フォルダのファイル一覧を「相対パス:更新時刻:サイズ」で
作っていたので、CI では毎回違う指紋になり、ヘッダ行の不一致で**キャッシュ全体**が捨てられる。
拡張を使っている利用者だけがキャッシュを引き継げない、という穴になるので、「相対パス:サイズ:内容ハッシュ」に変えた。
拡張のファイルは少数なので、毎回読んでも時間はかからない。

この変更で、拡張を使っている利用者は、この版に上げた直後の 1 回だけキャッシュが捨てられる（指紋の値が変わるため）。
Q5 の判断と矛盾するように見えるが、拡張を使う利用者は限られ、かつ避ける手が無い（旧指紋を再計算して比べるには
更新時刻が要り、それが変わっているのが問題の状況）。

### Q8. ハッシュは何を使うか。衝突は心配しなくてよいか

SHA-256 の先頭 16 桁（64 ビット）の 16 進。キャッシュフォルダ名の 8 桁（`Config.shortHash`）と同じ流儀で、
桁を増やしたのは「サイズも一致した別内容のファイルが、同じ 64 ビットに衝突する」確率を実用上無視できるところまで
下げるため。全部の 64 桁を書くと `F` 行がその分だけ長くなり、キャッシュファイルが大きくなる。
共通の実装を `jche.util.FileHash` に置き、ソース・jar・拡張ファイルで同じものを使う。

## アクション側

### Q9. 何をどこに保存するか

ツールのフォルダ（`${{ github.action_path }}`）の `.cache/` を丸ごと。`cache.folder` が空欄のときの既定の置き場所で、
生成する設定ファイルは空欄にしてあり、README でも `config` 入力の設定ファイルは空欄を勧めている。
`.cache/` の下は解析対象プロジェクトごと（`<フォルダ名>_<project.root の絶対パスのハッシュ>/`）に分かれているので、
同じアクションの呼び出しで複数の設定ファイルを処理しても 1 つのエントリに収まる。

`project.root` の絶対パスはワークスペース（`/home/runner/work/<repo>/<repo>` 等）から決まり、実行ごとに変わらないので、
フォルダ名も変わらない。`uses: owner/repo@main` のときの `action_path`（`/home/runner/work/_actions/owner/repo/main`）も同様。

利用者が `cache.folder` に別の場所を書いた場合はこの引き継ぎの対象から外れる。設定ファイルを読んで場所を求める案もあったが、
アクションが設定ファイルの中身（相対パスの起点の規則を含む）を解釈し始めると二重管理になる。「空欄のままにすること」を
入力の説明と README に書くにとどめた。

### Q10. キャッシュキーをどう決めるか。なぜ実行ごとに変えるのか

`actions/cache` はキーが一致するエントリがあると保存しない（エントリは不変）。「前回の結果を次回に引き継ぐ」には
**保存のたびに新しいキー**が要る。そこで

```
key:          jche-analysis-<OS>-<設定ファイルの内容ハッシュ>-<run_id>-<run_attempt>
restore-keys: jche-analysis-<OS>-<設定ファイルの内容ハッシュ>-
              jche-analysis-<OS>-
```

とした。復元は前方一致で最新のものが選ばれる。設定ファイルの内容ハッシュをキーに入れるのは、同じリポジトリの別ジョブが
別の設定（別のモジュール、別の起点）でこのアクションを呼んだとき、互いのキャッシュを取り違えないため。
生成した設定ファイルは絶対パス込みで毎回同じ内容になるので、キーも同じになる。

ツール本体の版はキーに入れない。形式が変わったときはツール自身がヘッダ行で見て捨てるので、キーで分ける必要が無い。
古いエントリが当たっても、ツールが判定して合わないものを解析し直すだけで、結果は変わらない。

### Q11. 保存を `actions/cache` の post ステップに任せず、`restore` と `save` に分けたのはなぜか

`actions/cache` の post ステップはジョブが成功したときだけ保存する。このアクションは設定ファイルを複数受け、
1 つが失敗しても残りを処理するので、「途中まで出来たキャッシュ」も次回に活かしたい。
`actions/cache/save` を `if: always()` の明示のステップにすれば、解析ステップが失敗しても保存される
（キャッシュファイルは一時ファイルに書いてから置き換えるので、途中で落ちても壊れた状態にはならない）。

`save` の条件に `steps.restore-analysis.outcome == 'success'` を足してあるのは、`restore` が失敗
（サービス側の障害など）したときに、キーの出力が無いまま `save` へ進んで別のエラーになるのを避けるため。
キャッシュのミス（前回のエントリが無い）は `outcome` としては成功なので、初回でも保存される。

### Q12. エントリが実行のたびに増えて、容量を圧迫しないか

GitHub のキャッシュはリポジトリごとに 10 GB の上限があり、超えると古いものから消える。7 日間使われないエントリも消える。
解析キャッシュはソースの規模に比例するが、テキストなので圧縮が効く（このリポジトリ自身で数 MB）。
実行のたびに 1 エントリ増えても、日常の頻度なら上限に届く前に古いものが消えていく。

`actions/cache` と同じキーで保存し直せない制約は避けられないので、「増えるが自動で消える」を受け入れた。
それでも気になる利用者は `analysis-cache: 'false'` で切れる。

### Q13. ブランチ間でキャッシュは共有されるか

GitHub の規則で、キャッシュはそのブランチ自身と、既定ブランチ（`main`）で作られたものだけが見える。
PR のブランチからは `main` の最新が当たり、変わったファイルだけが解析される。逆に PR で作ったエントリは
`main` からは見えない。この規則はアクション側で変えられないので、そのまま従う。

## 検査

### Q14. 「更新時刻が変わっても再利用される」をどう検査するか

回帰テスト（`test/regression/run.sh` / `run.cmd`）の通常ケースに 3 回目の実行を足した。2 回目の後に
解析対象（`test/demo` 等）と `test/localrepo` の jar の更新時刻を全部「今」にし（`touch`。Windows は PowerShell で
`LastWriteTime` を書く）、同じ設定で実行して、集計行の「再利用」が 0 でなく「新規解析」が 0 であることと、
出力 CSV が期待値と一致することを見る。`maven` / `mavenmulti` / `gradle` のケースでは、`test/localrepo` の jar の
更新時刻も変わっているので、`L` 行のハッシュ判定も同時に通る。

「依存 jar の変更による再解析が 0」を直接見る書き方も試したが、集計行の内訳は新規解析が 0 のときは出ないので
（`reanalysisBreakdown`）、「新規解析=0」で見ることにした。新規解析が 0 なら、jar による再解析も 0 である。

### Q15. アクションの保存・復元そのものは検査しているか

`smoke.yml` の `action` ジョブで、1 回目の解析の後に `test/demo` を `touch` してもう一度同じ入力で解析し、
2 回目の `run.log` の集計行で再利用を確かめる。ただしこれは「同じジョブの中で `.cache/` が残っている」状況で、
`actions/cache/restore` / `save` を通した引き継ぎではない（同じジョブの中では、保存したエントリを復元する経路が作れない）。
実行間の引き継ぎは、`.github/workflows/call-hierarchy.yml`（このリポジトリ自身を解析する）の 2 回目以降の実行で、
「Restore analysis cache」ステップが前回のキーを当てていることと、集計行の再利用の数で確かめる。

### Q16. 回帰テストで `touch` するとき、リポジトリの作業ツリーは汚れないか

git は更新時刻を追跡しないので、`touch` しても `git status` には出ない。`test/demo` 等の中身は変えていない。
