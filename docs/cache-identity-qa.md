# キャッシュの同一性 — 実装時の QA 一覧

キャッシュの「同じファイルか」の判定を**パス・サイズ・内容の指紋**に統一した
（[#103](https://github.com/instreest/java-call-hierarchy-exporter/issues/103)）ときと、
そこで残していたクラスパスの並び順
（[#104](https://github.com/instreest/java-call-hierarchy-exporter/issues/104)）、
サーバーモードの `SHUTDOWN` が実行中の解析を中止していた問題
（[#102](https://github.com/instreest/java-call-hierarchy-exporter/issues/102)）への対応で、
迷ったこと・困ったことと、その結論を Q&A の形で残す。

対応の要点:

- **更新時刻をやめた**（#103）: ソース（`F` 行）も依存 jar（`L` 行）も、更新時刻を
  記録も参照もしない。パスとサイズと内容の指紋だけで見る。更新時刻は中身と関係なく
  変わる（両方向に外れる）ので、当てにしない
- **`F` 行から更新時刻の列を落とした**: `相対パス / サイズ / エラー数 / 内容ハッシュ`
- **`L` 行を「パスと指紋」に置き換えた**: 指紋は jar なら ZIP の中央ディレクトリの
  `名前 / サイズ / CRC`、クラスフォルダなら `.class` の `相対パス / サイズ / 内容ハッシュ`
- **更新時刻を速い経路として維持するための仕組みを消した**: `refreshedFileRow`
  （書き写すときに `F` 行の更新時刻を今のものへ書き直す）と `rememberHash`
  （更新時刻が一致したブロックのハッシュを借りる）
- **キャッシュの版を `v16` に上げた**: 古いキャッシュは 1 行目の不一致で安全に捨てられる
- **クラスパスの並び順も見るようにした**（#104）: jar の集合が同じでも、並びが変われば
  同名クラスの解決先が変わる。効くのは「同じパッケージが 2 つ以上の jar にある」ときだけなので、
  そのパッケージだけを「変わったパッケージ」に入れる
- **`SHUTDOWN` は解析を中止しない**（#102）: 要求は順に処理されるので、`SHUTDOWN` は
  「並んでいる解析が終わったら終了する」の意味にした。中止したいときは `CANCEL` を送る

---

## Q1. なぜ今になって更新時刻をやめるのか。#79 で内容ハッシュを足したときに直さなかったのはなぜか

#79（GitHub Actions でキャッシュを引き継ぐ）で困っていたのは**可用性**だけだった。
`actions/checkout` は毎回チェックアウト時刻でファイルを作るので、中身が同じでも全ファイルが
「変更あり」になり、キャッシュを持ち越しても全件解析し直しになる。
このとき「数十 MB の jar が百本ある環境で毎回ハッシュを取ると数秒かかる」ことを避けたくて、
**更新時刻とサイズが一致すればハッシュを計算しない**という形にした。
つまり内容ハッシュを「更新時刻の代わり」ではなく「更新時刻が違うときの二次判定」として積んだ。

このとき見落としていたのが、**逆向きの外れ方**がある点。
更新時刻を復元する仕組みは実在する（`git restore-mtime` 相当、アーカイブの展開、`rsync -t`、
エディタの「更新時刻を保つ」保存）。そこでは**更新時刻もサイズも同じで中身だけ違う**ファイルが
できる。同じ長さの書き換えなら普通に起きる。

```java
public static final String MODE = "ALPHA";   // -> "OMEGA"
if (n >= 0) { ... }                          // -> if (n >= 1) { ... }
Impl.class                                   // -> Mock.class
```

二次判定の形だと、更新時刻が一致した時点で `true` を返してハッシュを**見ない**ので、
古いブロックがそのまま残る。呼び出し階層に、もう存在しない呼び出しが出る。
しかもログには何も出ないし、次に更新時刻が変わるまで直らない。

`config/config.properties` にはこの穴を「バージョン管理がタイムスタンプを復元する設定だと
検出漏れの可能性があるため、疑わしいときは false にするかキャッシュファイルを削除すること」と
書いてあった。**利用者に注意を求めて回避していた**わけで、これは直せる問題を直さずに
説明で済ませている。ツール側で内容を見れば済む。

## Q2. 遅くならないのか

no-change の実行で全ソースの内容ハッシュを計算するようになる。計測（この環境、`.java` のみ）:

| 対象 | 変更前 | 変更後 |
|---|---|---|
| 500 ファイル / 27MB・無変更 | 773 ms | 980 ms |
| 2000 ファイル / 44MB・無変更 | 1470 ms | 1580 ms |
| 2000 ファイル / 44MB・初回（全件解析） | 5723 ms | 5383 ms |

増えるのは 0.1〜0.2 秒。これで済むのは、**#101 でソース一覧の指紋（`T` 行）を入れたときから、
全ファイルのハッシュはどのみち毎回計算していた**ため。変更前は、更新時刻が一致したブロックの
ハッシュを旧 `F` 行から借りて（`rememberHash`）読み直しを省いていたので、その借りていたぶんだけが
増えた。ハッシュの計算は 1 ファイル 1 回で、サイズが違えば呼ばれないのは変わらない。

jar は逆に速くなっている。Q4 のとおり、jar 本体を読まずに ZIP の中央ディレクトリだけを見るため。

さらに詰めるなら、ハッシュの計算を並列にする手がある。行の並びはキャッシュを読む順で決まるので、
並列にしても出力の決定性は崩れない。今は 0.2 秒のために逐次のままにしている。

## Q3. 内容ハッシュを SHA-256 の先頭 16 桁に切っているが、衝突しないのか

困るのは「中身が違うのに同じとみなす」場合だけで、そのためには**サイズも一致**している必要がある。
64 ビットの一致がサイズ一致のもとで偶然起きる確率は、同じ実行の中でディスクが化ける確率より低い。
16 桁に切っているのはキャッシュの 1 行を短く保つため。
悪意のある衝突を防ぐ用途ではない（キャッシュは自分のディスク上の作業用ファイルで、
信用できない相手から受け取るものではない）。

## Q4. jar の指紋をどう作るか。jar 本体をハッシュすると遅いのでは

遅い。数十 MB の jar が百本あると、毎回全部読むのは数秒かかる。#79 でハッシュを
「二次判定」に留めた理由もそこにあった。

そこで **jar は中身を読まない**ことにした。ZIP の中央ディレクトリ（ファイルの末尾にある索引）から
エントリごとの `名前 / サイズ / CRC` を取り出し、並べ替えて連結したもののハッシュを指紋にする。
CRC は ZIP を作るときに格納されるので、読むのは索引だけで済む。索引は jar の大きさに比べて
ずっと小さく、`ZipFile` を開けば OS のページキャッシュにも乗りやすい。

変更前は、`L` 行の判定に使うハッシュを毎回 `FileHash.of(jar)` で取っていた。
つまり**全 jar を毎回まるごと読んでいた**（更新時刻が一致していても読んでいた）。
目次だけに変えた効果（この環境、JDT の jar 19 本 / 14MB。2 回目以降の値）:

| | 変更前（jar 全体を読む） | 変更後（目次だけ） |
|---|---|---|
| 19 本 / 14MB | 74 ms | 28 ms |

変更前は jar のバイト数に比例するので、数十 MB の jar が百本ある環境では差が開く。
変更後はエントリ数にしか比例しない。

中身が変われば CRC かサイズが変わるので、判定の強さは実質そのまま。
並べ替えるのは、同じ内容の jar を作り直したときにエントリの順だけが変わることがあるため
（再現ビルドでない普通のビルドでは普通に起きる）。

クラスフォルダ（`target/classes`）は ZIP ではないので、`.class` を歩いて
`相対パス / サイズ / 内容ハッシュ` を集める。これは変更前も毎回歩いていた（フォルダ自身の
更新時刻は中のファイルの変更を反映しないため）ので、歩く回数は変わらない。

## Q5. `L` 行からサイズと更新時刻の列を落としたが、情報が減らないか

減らない。`L` 行の「サイズ」は jar のバイト数で、「更新時刻」はファイルの更新時刻だった。
どちらも**指紋の材料**として置いてあっただけで、他の用途は無い。指紋 1 列にまとめたほうが、
「この列は何のためにあるのか」が迷いようがなくなる。

クラスフォルダでは、もともとこの 2 列の意味が jar と違っていた（サイズ＝`.class` の数、
更新時刻＝最も新しい `.class` の更新時刻）。同じ列名で違うものを持つのは読み手に優しくない。
指紋 1 列なら、jar とクラスフォルダで作り方が違っても、列の意味は「中身の指紋」で同じになる。

## Q6. `F` 行を書き写すときに更新時刻を書き直す仕組み（`refreshedFileRow`）はなぜ要らなくなるのか

あれは「更新時刻が違ってハッシュで救われたブロックを、次回は速い経路（更新時刻の一致）に
戻す」ための仕組みだった。速い経路そのものが無くなったので、目的ごと消える。

副作用として、パス5（書き写し）が**旧キャッシュの行をそのまま出す**だけになった。
有効と判定した時点で `F` 行の中身（パス・サイズ・内容ハッシュ）は今のファイルと一致しているので、
書き直すものが無い。中断した実行からの引き継ぎ（#101）の側も同じ理由で単純になった。

## Q7. 判定が「サイズ → ハッシュ」の 2 段なのは、更新時刻を残しているのと同じではないか

違う。サイズは**中身の一部**で、更新時刻は中身と無関係のメタ情報。
サイズが違えば中身も必ず違うので、ハッシュを取らずに「違う」と言い切れる（速いだけで、
判定は変わらない）。サイズが同じならハッシュを見る。**サイズ一致で打ち切ることは無い**。

変更前の問題は「更新時刻が一致したら中身を見ずに打ち切る」ことだった。そこが消えている。

## Q8. 古いキャッシュはどうなるか

1 行目の形式（`jche-cache-v16`）が一致しないので、丸ごと捨てて全件解析し直す。
利用者は何もしなくてよい（破棄した理由はログに出る）。
`F` 行と `L` 行の列が変わるので、版を上げずに読ませると列がずれて静かに壊れる。
事実の意味が変わらない追加（#79 のハッシュ列）では版を上げなかったが、今回は列の**並びが**変わる。

## Q9. 「更新時刻もサイズも同じで中身だけ違う」をどう検査するか

`test/incremental/run.sh` に 1 ケース足した。

```
Base.MODE = "ALPHA" を "OMEGA" に書き換える（同じ長さなのでサイズは変わらない）
touch -r で更新時刻を書き換え前に戻す
差分更新の出力と、キャッシュを消してからの全件解析の出力を比べる
```

このテストは期待値のファイルを持たない。同じソースに対する 2 通りの解析が一致するかだけを見るので、
「差分更新だけ結果が違う」という取りこぼしをそのまま検出できる。

変更前のビルドで走らせると食い違う（実際に食い違うことを確認した）:

```
差分更新: at inc.Branch.run(Branch.java:9),inc.Log.alpha(),...
全件解析: at inc.Branch.run(Branch.java:9),inc.Log.alpha(),...,"[UNREACHABLE] not called on this path: condition 'Switches.MODE.equals(""ALPHA"")' does not hold（定数 = OMEGA）"
```

差分更新の側が「呼ばれる」と言っている。呼ばれないほうが正しい。

## Q10. `test/regression/run.sh` の「更新時刻を全部変えてから実行する」ケースは要らなくなったのでは

残す。検査しているのは「更新時刻が変わってもキャッシュを捨てない」という**利用者から見た振る舞い**で、
実装が更新時刻を見なくなった今も、その振る舞いが保たれているかは検査する意味がある。
実装の都合でテストを消すと、次に実装を変えたときに誰も気づけない。

## Q11. 同一性はこれで全部か

キャッシュの鍵は 3 層ある。今回そろえたのは 3 層目。

1. **作り方の鍵**（1 行目のヘッダ）… 形式の版・ソースレベル・ソースの文字コード・実行 JDK・
   フェーズA拡張の指紋。違えば同じソースでも解析結果が変わるので丸ごと捨てる
   （フェーズA拡張はのちに廃止し、指紋も項目ごと落とした。
   [instance-analysis-plugin-qa.md の Q28](instance-analysis-plugin-qa.md)）
2. **クラスパスの同一性**（`L` 行）… 依存 jar とクラスフォルダの指紋。違えばその
   パッケージの型を参照するファイルだけを解析し直す
3. **ソースの同一性**（`F` 行・`T` 行）… パス・サイズ・内容ハッシュ

`L` 行のクラスパス上の**並び順**も 2 の一部で、Q12 で見る。

## Q12. クラスパスの並び順が変わると何が起きるか（#104）

JDT は同名クラスを**先勝ち**で解決する。同じ FQN が 2 つの jar に入っていると、
並びを入れ替えただけで別の型に解決される。

`L` 行はクラスパス順に並んでいるのに、突き合わせはパスをキーにした集合の比較だけだったので、
**並びだけ変わった場合に追加も変更も削除も 0 件**になり、全ファイルが再利用されていた。

再現（`test/incremental/jarorder/` に入れたもの）:

```java
// dup-a.jar                                  // dup-b.jar
package dup;                                  package dup;
public class Shared {                         public class Shared {
    public void run(long n) { }                   public void run(int n) { }
}                                                 public void run(long n) { }
                                              }
```

```java
new Shared().run(1);   // a が勝てば run(long)、b が勝てば run(int)
```

`library.folders` の順だけを `liba,libb` → `libb,liba` に変えると、差分更新は `run(long)` の
ままで、キャッシュを消してからの全件解析は `run(int)` になる。出力が食い違う。

### どう直したか

並び順が効くのは、**同じパッケージが 2 つ以上の jar に入っているとき**だけ。
1 つの jar にしかないパッケージは、どこに並んでいても解決先が変わらない。

そこでパッケージごとに「そのパッケージを含む jar の、クラスパス順の並び」を作り、
旧 `L` 行から作ったものと突き合わせる。並びが違うパッケージだけを「変わったパッケージ」に入れ、
あとは既存の仕組み（`I` 行の依存でそのパッケージの型を参照するファイルを解析し直す）に乗せる。

突き合わせは**新旧に共通する jar だけ**に絞る。そうしないと jar を 1 本足しただけで
「並びが変わった」と数えてしまう（追加はすでに `added` として数えていて、そのパッケージも
「変わったパッケージ」に入っている）。共通する jar だけに絞ると、ここが数えるのは
「純粋な並び替え」だけになり、追加・変更・削除の検知と重ならない。

`anyAddedOrChanged()` には入れない。jar の集合が同じなら「解決できる型の集合」も同じで、
前回型解決に失敗していたファイルを見直す理由にはならない（変わるのは、複数の jar にある
同名クラスのうちどれが勝つかだけ）。`any()` には入れる。中断した実行からの引き継ぎは
`any()` で見ているので、並びが変わっていたら引き継がない。

### 「同名クラスが複数の jar にある」はどれくらい珍しいか

珍しくはあるが、無くはない。このツール自身が使っている Eclipse JDT のクラスパス
（jar 19 本）を見ると、235 パッケージのうち **6 パッケージが 2 本以上の jar に入っている**。

```
org.eclipse.core.internal.runtime
org.eclipse.core.runtime
org.eclipse.jdt.core
org.eclipse.jdt.core.compiler
org.eclipse.jdt.internal.compiler
org.eclipse.jdt.internal.compiler.parser
```

OSGi のように「同じパッケージを複数のバンドルが分担する」構成や、
shade / shadow で取り込んだ依存が元の jar と共存している構成では普通に起きる。

### 速さ

この 19 本のクラスパスで、変更なしの実行の所要時間は入れる前後で差が出なかった
（500 ファイル / 27MB ＋ jar 19 本 / 15MB で、どちらも 0.8〜1.0 秒。測定誤差に埋もれる）。
突き合わせるのは「2 本以上の jar に入っているパッケージ」だけなので、
上の構成でも比較対象は 6 件しかない。

## Q13. なぜクラスパス全体の並びの指紋をヘッダの鍵に入れなかったのか

そのほうが実装は短い。5 行で済むし、取りこぼしも無い。
採らなかったのは、`pom.xml` の依存を 1 行動かしただけで**全件解析し直し**になるため。

並び順が実際に結果を変えるのは、同名クラスが複数の jar にある構成だけで、これは普通ではない。
めったに起きないことのために、よく起きること（依存の並べ替え）で毎回キャッシュを捨てるのは
可用性を落としすぎる。#103 で「更新時刻を当てにすると捨てすぎる」を直したばかりなので、
同じ形の損を別の場所で作ることになる。

パッケージ単位で見る実装は 40 行ほど。突き合わせるのは「2 つ以上の jar に入っているパッケージ」
だけなので、普通の構成では比較対象が 0 件で、実質ただの早期 return になる。

## Q14. 並び順の変化をどう検査するか

`test/incremental/run.sh` に 1 ケース足した。jar はテストの中で `javac` と `jar` で作る
（`test/incremental/jarorder/libsrc/a` と `b`）。バイナリをリポジトリに置かずに済み、
2 つの jar の違いがソースで読める。

見るのは 4 つ。

- 並びを入れ替えたら解析し直すこと
- 差分更新と全件解析の `call-hierarchy.csv` / `methods.csv` が一致すること
- 入れ替えで解決先が実際に変わっていること（変わらなければ上の比較が素通りする）
- **並びを変えなければ解析し直さないこと**（判定が効きすぎて毎回再解析になっていないか）

直す前のビルドでは 2 つ目が落ちる（`run(long)` と `run(int)` で食い違う）。

## Q15. `SHUTDOWN` が実行中の解析を中止していた（#102）のは、どう直したか

サーバーモードでは、要求を読む側（`readCommands`）と処理する側が別スレッドで、
要求は待ち行列に積まれて順に処理される。`readCommands` は `SHUTDOWN` を読んだ時点で
`cancelled` を立てていたので、**まだ処理中の `ANALYZE` が中止された**。
`ANALYZE` を送ってすぐ `SHUTDOWN` を送ると、解析は `NG cancelled` で終わる。

要求が順に処理されるのだから、`SHUTDOWN` も「並んでいるものが終わったら終了する」でよい。
`readCommands` から `cancelled.set(true)` を外し、待ち行列に積むだけにした。
中止したいときは `CANCEL` を送る（そのための要求が既にある）。

Eclipse プラグイン側（`ServerConnection.close`）は、接続を閉じるときに解析を止めたいので、
`SHUTDOWN` の前に `CANCEL` を送るようにした。`close` の意味は変わらない。

### なぜ「`SHUTDOWN` で中止する」のままにしなかったか（案 A との比較）

案 A は「`SHUTDOWN` は中止も兼ねる」と決めて、そのとおりに文書化するもの。変更は少ない。
採らなかったのは、**中止だけしたい場合と、終了だけしたい場合を呼び分けられなくなる**ため。
`CANCEL` と `SHUTDOWN` の 2 つがあるのに、`SHUTDOWN` が両方の意味を持つと、
「解析を最後まで終わらせてから閉じる」ができない。要求を 1 つの意味に保つほうが、
呼ぶ側で組み合わせられる。

### 検査

`test/server/run.sh` に 2 ケース足した。どちらも標準入力に固定の並びを流すだけで、
