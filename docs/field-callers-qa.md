# フィールドの呼び出し元（Eclipse プラグイン） — QA 一覧

> 使い方は [eclipse-plugin-usage.md](eclipse-plugin-usage.md) の「フィールドから入る」にある。

利用者からの依頼: 「ソースコード上のあるフィールドが設定・参照・判定される階層、およびそのフィールドから
コピーされた変数または判定された処理がどこまで影響するのかを知りたい」。まず今のキャッシュの形式で
何ができて何ができないかを整理し（下の Q11）、そのうえで「**フィールドをもとに、その呼び出し元を出力する**」
機能を Eclipse プラグインに足した。

| 変えたところ | 内容 |
|---|---|
| `src/jche/server/FieldAccesses.java` | 1 つのフィールドの参照を、キャッシュの A 行から拾う（新規）。宣言（V 行）と初期化子（J 行）も見る |
| `src/jche/server/FieldTree.java` | フィールドを根にした木を組む（新規）。深さ 1 が参照しているメソッド、その下が呼び出し元 |
| `src/jche/server/Server.java` / `Protocol.java` / `TreeFilters.java` | `TREE` / `EXPORT` の向きに `field` を足し、読み書きの絞り込み `access=` を受ける |
| `src/jche/server/CallTree.java` | 根を深さ 1 に置いて辿る入口（`walk(id, rootDepth, rowLimit)`）と、行を出してよいかの判定（`accepts`）を公開 |
| `src/jche/cache/FieldAccessFact.java` | A 行の読み戻し（`fromRow`）。これまで書くだけで読み手がいなかった |
| `src/jche/AnalysisSnapshot.java` / `Exporter.java` | グラフを組んだときのキャッシュの印（サイズと更新時刻）を持つ |
| `eclipse-plugin/.../FieldPicker.java` / `ShowFieldCallersHandler.java` | フィールドの特定と、右クリックのコマンド「影響調査: フィールドの呼び出し元を表示」（新規） |
| `eclipse-plugin/.../CallHierarchyView.java` ほか | フィールドを表示するモード（向きのボタンを止める・［▽］で読み書きの絞り込み・根の行から宣言を開く） |
| `test/server/run.sh` / `test/plugin-client/ClientProbe.java` | フィールドの木の検査 |

キャッシュの形式の版（`CacheFormat.VERSION`）は**上げていない**。使った事実（A 行・V 行・J 行）は
どれも前から書かれていた（Q1）。

---

### Q1. キャッシュに事実を足さずにできるのか

できる。要るのは「どのフィールドを、どのメソッドが、どの行で、読んだか書いたか」で、これは A 行
（`A line 呼び出し元の記号 ownerTypeFqn fieldName access mods lambdaDepth`）にそのまま入っている。
A 行は「参照の有無を問う機能を足すときに再解析せずに済むよう」書き手が前から残していて、読み手が
いなかった（`CacheFormat` のコメントにも「今の読み手は使わない」とあった）。

呼び出し元の側は、メソッドの木（`CallTree`）をそのまま使う。A 行の呼び出し元はメソッドのキーなので、
グラフのメソッド表（`MethodTable#idOf`）で引けば、その先はメソッドから入ったときと同じ木になる。

### Q2. A 行をグラフに入れず、要求のたびにキャッシュを読むのはなぜか

A 行はフィールドの参照 1 つにつき 1 行あり、呼び出し（C 行）と同じくらいの数になる。グラフを組むとき
（`CallGraphBuilder`）に全部をメモリに持つと、この機能を使わない解析（CLI、メソッドしか見ない画面）にまで
ヒープを払わせる。このツールは大きなコードベースで `OutOfMemoryError` にならないことを優先してきた
（[cache-design.md](cache-design.md) の 3 点）ので、常駐の費用を増やす形は採らなかった。

代わりに、`TREE … field` を受けたときにだけキャッシュを先頭から読み、そのフィールドの行だけを拾う
（`FieldAccesses#scan`）。

- 行は名前（`in.line().contains(fieldName)`）で篩ってから列に分ける。大半の行は種別の 1 文字を見て捨てる
- 記号表（S 行）は、そのブロックに拾う A 行があったときにだけ読み解く
- 拾ったものは返したら捨てる。何も持ち続けない

費用はキャッシュの大きさに比例する 1 回の走査（読むだけで、グラフは組まない）である。大きなキャッシュでは
メソッドの木より時間がかかりうるので、プラグインは待つ上限をメソッドの木（120 秒）より長く取っている（300 秒）。

**却下した案**

- 解析のたびに全フィールドの索引を作って持つ … 上の理由（使わない人にも費用が掛かる）
- 最初の要求で全フィールドの索引を作り、次からはそれを引く … 一度使うと解析結果を捨てるまで
  ヒープを抱え続ける。フィールドを引くのは調べるときの 1 回ずつなので、毎回読むほうが単純で、持ち続けるものも無い。
  走査が遅くて困るようなら、そのときに考える

### Q3. キャッシュとメモリのグラフが食い違うことはないか

ある。サーバーは `ANALYZE` に失敗・中止すると**前の解析結果を持ったまま**でいるが、フェーズ 1 が終わって
いればキャッシュはもう新しいものに差し替わっている。そのまま A 行を読むと、新しい行のメソッドを古いグラフで
引くことになり、呼び出し元が欠けたり、消したメソッドの行が出たりする。

そこで、グラフを組んだとき（キャッシュの錠を持っている間）のキャッシュの印（サイズと更新時刻。
`Exporter#cacheStampOf`）をスナップショットに持たせ、読む前と読んだ後に突き合わせる。食い違えば
`NG stale-cache` で断り、画面は「再解析してください」と出す。解析し直せば引ける。

ソースの同一性には更新時刻を使わない（[cache-identity-qa.md](cache-identity-qa.md)）が、これは
**このツール自身が書いたファイル**が書き換えられていないかを見るもので、話が違う。キャッシュは一時ファイルに
書いてから差し替えるので、書き換えれば更新時刻もサイズも変わる。

**却下した案**: 読む間キャッシュの錠（`CacheLock`）を取る … サーバーのキャッシュのフォルダはプラグイン専用で、
書くのは同じサーバーの `ANALYZE` だけ（要求は 1 件ずつ処理する）。錠で防げるのは「ほかの実行が書いている途中」
だけで、上の「失敗した後に残った新しいキャッシュ」は防げない。印を見れば両方に気づける。

### Q4. 新しい要求にせず、`TREE` の向き（`field`）にしたのはなぜか

返すものがメソッドの木と同じ形（`R 深さ キー 表示名 ファイル 行 理由 印`）だからである。画面の側は
行を木に組み直す処理（`ServerTree`）・見た目・コピー・CSV 出力をそのまま使え、`EXPORT` も同じ向きを
受ければ済む。プロトコルの版も上げていない。古いサーバーに `field` を送ると、向きを「呼び出し元」と
読んでキーを探し、`NG not-found` になる（黙って別の木を返すことはない）。

行の中身の違いは印（flags）で表す。

| 印 | 行 |
|---|---|
| `field` | 根（フィールドそのもの）。ファイルは宣言しているファイル、行は 0（宣言の行はキャッシュに無い） |
| `access` | 深さ 1。そのフィールドを読み書きしているメソッド。理由の列が `read` / `write` / `read/write` |
| `initializer` | 深さ 1。宣言の初期化子（Q6）。キーは空 |
| `nomethod` | 深さ 1。囲むメソッドが特定できない参照。キーは空 |

理由の列は CSV にもそのまま出るので英語で固定し、画面（`CallersLabelProvider`）で訳す
（[nls-qa.md](nls-qa.md) の Q6）。`read/write` にカンマを使わないのも、CSV のセルを引用符で囲ませないため。

### Q5. 同じメソッドの中の参照を 1 行にまとめるのはなぜか

呼び出し元の木はメソッドで決まるので、参照の数だけ同じ木を繰り返すと、読む量が増えるだけで分かることは
増えない。行番号は最初の参照、理由の列は読み書きを合わせたもの（読んで書くメソッドは `read/write`）にする。
メソッドの木の「同じ相手を 1 回だけ出す」（`dedupe=1`）と揃えてあり、`dedupe=0` のときだけ参照の行ごとに分ける。

### Q6. 宣言の初期化子（`private String status = "NEW";`）はどう出すか

A 行は `SimpleName` のうち「宣言でない」ものだけを拾う（`FieldAccessRecorder`）ので、宣言の初期化子は
A 行に無い。それでも書き込みの 1 つには違いなく、「どこで設定されるか」を見たい人には欠かせない。
J 行（フィールドへの代入）は初期化子を `<field>` として持っているので、それを読んで深さ 1 の先頭に
「（フィールドの初期化子）」の行を置く。

初期化子を通るコンストラクタまでは辿らない（行に呼び出し元を付けない）。インスタンスの初期化子は
すべてのコンストラクタ（`this(...)` で委譲しないもの）で走り、static の初期化子はクラスの初期化で走る。
どちらも「そのクラスを使うところ全部」に広がって木が埋まるだけで、影響調査の答えとしては読みにくい。

### Q7. 宣言がソースに無いフィールド・囲むメソッドの無い参照は

- **宣言が jar にあるフィールド**（`System.out` など）… A 行は所有型をバインディングから書くので、
  ソースからの参照は拾える。根の行はファイルが空になり、印 `nosource` が付く
- **宣言も参照も無い**（解析の後に足した・キーの綴りが違う）… `NG not-found`。「参照が無い」と誤って
  読ませないよう、空の木は返さない
- **宣言はあるが参照が無い** … 根だけの木を返す。画面は「解析したソースには読み書きが無い。リフレクションや
  フレームワークの読み書きは出ない」と添える（「どこからも使われていない」とは言い切れないため）
- **囲むメソッドが特定できない参照** … 落とさずに深さ 1 の行にする（印 `nomethod`、画面では「（メソッドの外）」）

### Q8. 読み書きの分け方と絞り込み（`access=`）

A 行の `access` は `read` / `write`（代入の左辺）/ `readwrite`（複合代入・`++` / `--`）の 3 つ。
`readwrite` は読みでもあり書きでもあるので、`access=write` にも `access=read` にも入れる。
知らない値は `all` として扱う（黙って参照を落とさない側）。

画面では［▽］メニューに［読み取りと書き込みのすべて］［書き込みだけ］［読み取りだけ］を置いた。
「どこで設定されるのか」を知りたいとき、読み取りの行で木が埋まらないようにするためである。
フィールドを選び直したときは［すべて］に戻す（前のフィールドの絞り込みが残っていると、行が足りないことに
気づけない）。

### Q9. Eclipse でフィールドをどう特定するか。メソッドのコマンドと分けたのはなぜか

エディタでは `ICompilationUnit#codeSelect` を使う。カーソルがフィールドの**参照**（`this.status` の `status`）の
上にあっても、そのフィールドが引ける。読んでいるコードの途中で「このフィールドはどこで書かれるのか」と
引きたくなるので、宣言まで移らなくてよいようにした。宣言の上なら `getElementAt` で宣言そのものを引く。
エクスプローラー・アウトラインの選択が先なのは `MethodPicker` と同じ。

キーは `型FQN#フィールド名`。型の綴りはメソッドのキー（`MethodKeys#keyOf`）と同じく
`IType#getFullyQualifiedName('.')`（内部クラスは `Outer.Inner`）で、A 行の所有型の綴りと揃う。

コマンドは「呼び出し元階層を表示」と分けた。1 つにすると、メソッドの本体の中でフィールドの参照に
カーソルがあるとき、メソッドを見たいのかフィールドを見たいのかを決められない。

### Q10. フィールドを表示しているときの画面

- 向きのボタン（↑呼び出し元／↓呼び出し先）は押せなくする。フィールドの木は呼び出し元の向きしか無い
  （フィールドの「呼び出し先」には意味が無い）
- ［カーソル位置のフィールド］は［▽］メニューに置いた。ツールバーの ◎［カーソル位置のメソッド］は
  メソッドに戻る道として残す
- 根の行・初期化子の行をダブルクリックすると、Eclipse のフィールド（`IField`）から宣言を開いて名前を選ぶ。
  宣言の行番号はキャッシュに無いため
- 返事を待つ間に対象・向き・絞り込みが変わったら、古い返事で描き直さない（問い合わせの通し番号で見分ける。
  以前はキーだけを見ていたので、絞り込みを続けて切り替えると古い木が後から出ることがありえた）

### Q11. 依頼のうち、今回できていないことは

依頼には「フィールドからコピーされた変数・判定された処理がどこまで影響するか」も含まれていた。
今のキャッシュでは次の理由で、これは出していない。

| 知りたいこと | 今のキャッシュで |
|---|---|
| フィールドを設定・参照するメソッドと、その呼び出し元 | **できる**（今回の機能。A 行＋C 行） |
| フィールドの値がどの呼び出しの引数・フィールド・戻り値に渡るか | 一部だけ。値グラフ（N 行）は呼び出しの実引数・レシーバ・戻り値・代入の値しか持たず、ローカル変数そのものは持たない。再代入のある変数・加工した値（`f + 1`、三項演算子）・プリミティブや String を返す return は途中で切れる |
| フィールドで分岐した処理とその範囲 | ほぼできない。条件（G 行）は「引数か定数を定数と比べる」形しか持たず、`if (this.flag)` は記録されない。条件は呼び出しにしか付かず、ブロックの範囲も無い |

これらはキャッシュに事実を足す必要がある（形式の版が上がり、全件の再解析になる）ので、今回の範囲からは外した。
画面の「フィールドの呼び出し元」は、その土台（フィールドを起点にした木）として足しておく。

### Q12. VSCode プラグインには足さないのか

今回は Eclipse プラグインだけに足した。サーバー（`TREE … field`）は VSCode プラグインと共通なので、
足すときは画面の側（フィールドの特定と、木の根・深さ 1 の行の見た目）だけで済む。
