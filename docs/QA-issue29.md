# 実装QA — callee列の表記とラムダ／メソッド参照（Issue #29）

`callee` 列を「完全修飾クラス名.メソッド名(引数型略名)」にし、`calleeSignature` 列を
削除したときに迷った点と、その過程で見つかった取りこぼしの記録です。

Issueが「ラムダ式やメソッド参照（関数型インターフェース）、匿名型のメソッドは
どうするかはASTでの扱い方から検討したい」としていたので、まず**現状どう扱われて
いるかを実測**しました。それが Q4 以降です。想定していたより問題があったため、
表記の変更（Q1〜Q3）と合わせて2件の修正を入れています。

判断の軸はこのツールの既定方針、**「絞れないことより、誤って絞ることの方が害が大きい」**
です。出力は「何を再テストするか」を決めるのに使うので、候補が多いのは読む手間で
済みますが、1件に決め打ちして外すと回帰を見逃します。

---

## Q1. 引数型の略名で、別パッケージの同名クラスがぶつかる

Issueの To be は `findOrder(String)` のように**引数型を略名**にする形です。
ところが略名にすると、次の2つが同じ表記になります。

```java
public void save(java.util.List<String> xs) { }
public void save(other.List xs) { }
```

どちらも `fn.Dao.save(List)`。**「パッケージと引数を識別可能にしたい」という
Issueの目的そのものが果たせなくなります。** 机上の懸念ではなく、検証用プロジェクトで
実際に起きました。

そこで、**衝突した組だけ完全修飾の引数リストに戻す**ことにしました。

```csv
at fn.App.overloads(App.java:22),fn.Dao.save(java.util.List),...
at fn.App.overloads(App.java:23),fn.Dao.save(other.List),...
at fn.App.overloads(App.java:20),fn.Dao.save(String),...
```

衝突していない `save(String)` は略名のままです。全部を完全修飾にすると読みにくく、
全部を略名にすると識別できないので、必要なところだけ戻します。

判定は全メソッドを一度走査して作ります。走査用のSetは作業後に捨て、残すのは
衝突したラベルだけ（このリポジトリの自己解析では0件）なので、常時のメモリは増えません。
`methods.csv` の `method` 列にも同じ判定を使っています。

## Q2. 内部クラスを引数に取る場合、どこまで略すか

`fn.Outer.Inner` は `Inner` になります。`Outer.Inner` を残す方が読みやすい場面も
ありますが、**名前だけではどこまでがパッケージでどこからが外側クラスか決められません。**
「パッケージは小文字、クラスは大文字」という慣習に頼ると、その慣習に従っていない
コードで誤ります。誤って外側クラス名を落とすくらいなら、末尾だけを一律に取る方が
予測できます。これで別物とぶつかった場合は Q1 の仕組みが完全修飾へ戻します。

## Q3. `callee` にカンマが入る

引数が2つ以上あると `callee` にカンマが入るため、その値はCSVの引用符で囲まれて出ます。

```csv
at ...,"CallHierarchyExporter.Config.require(Properties,String)",...
```

Excelや標準的なCSVパーサではそのまま1列として読めますが、`cut -d,` のような
素朴な処理では分割されます。`calleeSignature` にも同じ性質はありましたが、
`callee` は今までカンマを含まない列だったので、READMEに明記しました。

## Q4. メソッド参照（`::`）が呼び出しとして記録されていなかった

**実測して見つけた取りこぼしです。** 検証用プロジェクトで確認したところ、
`ExpressionMethodReference` などの visit が無く、次のいずれも呼び出し辺として
記録されていませんでした。

```java
Handler h = dao::save;           // 辺なし
Supplier<String> s = dao::name;  // 辺なし
Runnable r = Outer.Inner::new;   // 辺なし
```

`dao::save` でしか参照されていないメソッドは、`call-hierarchy.csv` にも
`methods.csv` の `inDegree` にも現れず、**「誰からも呼ばれていない」ように見えます。**
影響調査でこれは致命的なので、4種すべてを呼び出しとして記録するようにしました。

| ASTノード | 例 | bindKind |
|---|---|---|
| `ExpressionMethodReference` | `obj::m` / `Type::m` | レシーバから通常どおり判定 |
| `TypeMethodReference` | `List<String>::size` | 同上 |
| `SuperMethodReference` | `super::m` | `U`（SUPER・静的束縛）|
| `CreationReference` | `Type::new` | `C`（CTOR・静的束縛）|

レシーバの扱いは通常の呼び出しと同じにしました。`dao::save` の `dao` が
コンストラクタ注入されたフィールドなら、そのままデータフローで具象型まで絞れます
（実測でも `recvKind=F` / `origin=F:fn.App#dao` が記録されています）。

### `String[]::new` は記録しない

配列生成には呼ぶメソッドがありません。ここを素通りさせると
「型解決に失敗」として件数に混ざり、**自己解析の失敗0件という指標が壊れます。**
配列型のときだけ辺を作らずに抜けます。これは取りこぼしではなく、
そもそも呼び出しではないという判断です。

### 記録はするが、呼ばれる順序は階層と一致しない

`::` を書いた時点ではまだ呼ばれません。実際に動くのは関数型インターフェース経由で、
もっと後です。それでも**囲みメソッドからの呼び出しとして記録します。**
多めに出る側に倒すのが安全という方針どおりで、READMEの「限界」にも書きました。

## Q5. ラムダがあるのに `SINGLE_IMPL` で1件に決め打ちされていた

Q4より深刻な問題です。次のコードで、

```java
Handler h = s -> dao.save(s);   // ラムダによる実装
h.handle("x");
...
Handler h2 = new Handler() { ... };   // 匿名クラスによる実装
```

`h.handle("x")` は `解決:SINGLE_IMPL` で **匿名クラス `App$1.handle` に確定**されて
いました。ラムダが実装として数えられていないため、ソース上の実装が1件しか無いと
見えたためです。実際に `h` に入っているのはラムダで、**別の実装を指しています。**

「絞れないことより誤って絞ることの方が害が大きい」という方針に真正面から反するので、
ラムダとメソッド参照が実装している関数型インターフェースのメソッドを
キャッシュの `M` 行として記録し、その呼び出し先には注記を出すようにしました。

```
at fn.App.viaLambda(App.java:30),fn.App$1.handle(String),...,ラムダ/メソッド参照の実装あり（未展開・本体は定義元メソッドに計上）
```

要点は **`解決:SINGLE_IMPL` と書かなくなったこと**です。候補の絞り込み自体は
変えていません。変えると既存の解決に広く回帰が入るためで、まず「確定したように
見せるのをやめる」ところまでを入れました（残りは提案1）。
`methods.csv` の `unresolvedCalls` にも同じ判定で計上しています。

### `M` 行はファイル単位で重複を除く（件数を持たない）

「N件のラムダが実装している」と件数で持ちたくなりますが、キャッシュは
ファイル単位で部分再利用されるため、**再利用の仕方によって件数がぶれます。**
持つのは「ある／なし」だけにしました。1ファイル内で同じインターフェースを
何度実装しても1件です。

## Q6. ラムダ本体の呼び出しを、合成メソッドへ付け替えるべきか

**検討して、付け替えないことにしました。** これが今回いちばん迷った点です。

現状、ラムダ本体の中の呼び出しは、ラムダを書いた囲みメソッドに計上されます。
一見すると、JDTの `LambdaExpression.resolveMethodBinding()` を使って
`App$$Lambda#handle(String)` のような合成メソッドを作り、そこに付け替える方が
正確に見えます。階層も `App.viaLambda → App$$Lambda.handle → Dao.save` と
実態に近くなります。

しかし**それをすると取りこぼしが増えます。** ラムダの多くは
`list.forEach(...)` や `stream().map(...)` のようにJDKのAPIへ渡されます。
そしてこのツールの既定設定は `exclude.packages=java.**, javax.**` です。
合成メソッドへ付け替えると、そのラムダは**除外されたJDK呼び出しの先にぶら下がる
ことになり、起点から到達できなくなって、本体の呼び出しが出力から丸ごと消えます。**

囲みメソッドに計上したままなら、呼ばれる順序こそ実態とずれますが、
「このメソッドを変えると影響する範囲」には確実に入ります。
**順序の正確さより取りこぼさないことを優先する**、という判断です。

同じ理由で、匿名クラスは今までどおり実型（`fn.App$1`）として扱います。
匿名クラスは型として名前を持ち、`H` 行で階層に載るので、
インターフェース経由の呼び出しから正しく辿れます。実測でも
`fn.App$1.handle(String)` として出ており、変更は要りませんでした。

## Q7. `methods.csv` の `method` 列にも引数を足した

Issueは `call-hierarchy.csv` だけを対象にしていますが、`methods.csv` は
`method` 列が `Dao.save` のままだと、**オーバーロードが行番号以外まったく同じ行として
並び、見分けられません。** 「引数を識別可能にしたい」というIssueの目的からすると
片方だけ直すのは中途半端なので、こちらにも引数型を足しました。

完全修飾クラス名は `declaringType` 列にあるため重複させず、
`Dao.save(String)` のように単純クラス名のままにしています。

**Issueに明記されていない変更なので、不要であれば戻せます**（1行です）。

## 要件・前提についての提案

### 提案1: ラムダを候補に数えるところまで進めるか

今回入れたのは「`SINGLE_IMPL` と言い切るのをやめる」ところまでです。
一歩進めて、ラムダを合成型（`App$$Lambda1 implements Handler`）として
`H` 行・`D` 行に登録すれば、CHAの候補数が正しくなり、
`CHA候補2件（未展開）` として扱えます。

ただし Q6 のとおり、**本体の呼び出しをそちらへ付け替えると取りこぼします。**
「候補としては数えるが、本体は囲みメソッドに計上したまま」という中間状態に
なるため、合成メソッドが呼び出し先の無い末端として出ます。これが読みやすいか
どうかは、実際の案件のCSVを見てから決めた方がよいと考え、今回は見送りました。
→合成メソッドが末端として表示されるとソースコード上の見え方との乖離が発生する
見込みのため、実装しません。

### 提案2: `exclude.packages` の既定を見直す余地

Q6の制約は、`java.**` を除外していることに由来します。除外をやめると
`forEach` 経由でラムダまで辿れるようになりますが、そのかわりJDK内部の呼び出しが
大量に出ます。「除外はするが、除外先を経由した先は親に繋ぎ直す」という
現在の仕組みは既にあるので、**ラムダに限って繋ぎ直しの対象にする**という
折衷案はありえます。設計変更を伴うので提案に留めます。
→設計変更はしません。

### 提案3: `root` と `call-hierarchy` 列の表記は据え置いた

Issueの To be でも短縮表記のままだったのでそれに従いましたが、
`callee` だけが完全修飾になったため、同じメソッドが列によって
`jp.co.example.service.OrderService.findOrder(String)` と
`OrderService.findOrder` の2通りで出ます。

これは意図した役割分担です（フィルタは短い方、特定は `callee`）が、
`call-hierarchy` 列も完全修飾にしたい場合は変更できます。
その場合、階層が深いと1行がかなり横に長くなる点はご承知おきください。
→`root` と `call-hierarchy` 列の表記は据え置きで意図したとおりです。
