# 設定ファイルの読み方（バックスラッシュをそのまま読む）— Q&A

「Windows でも区切りは `/` で書く（`\` で書くなら `\\` のように 2 つ重ねる）」という制約を無くした記録。
関連: [config-file-name-qa.md](config-file-name-qa.md)（`jche.properties` への改名。同時に行った）、
[eclipse-plugin-ui-qa.md](eclipse-plugin-ui-qa.md)（プラグインが自動生成する設定でこの制約を踏んだ経緯）。

## 対応の要点

- 設定ファイルの読み手を `java.util.Properties#load` から自前の `jche.config.ConfigFile` に変えた。
  見た目は今までどおり `項目=値` だが、**バックスラッシュはそのまま読む**。Windows のパスを `C:\work\app` と書ける
- 値を次の行に続ける書き方は properties と同じ「行末の `\`」。ただし次の内容行が `項目=` の形かファイルの末尾なら
  続けず、末尾の `\` を捨てる（末尾が `\` のパスが次の行を飲み込まない。Q10）。字下げした行も `\` 無しで続きになる。
  続きの途中の注釈行は読み飛ばす
- 区切りは `=` だけ。`=` の無い行・項目名がおかしい行は行番号つきのエラーにする
- 書く側（Eclipse プラグインの `EclipseProjectConfig#toFileText`、VSCode プラグインの `generatedConfigText`、
  GitHub Action の `prepare.sh`）は逃がさずにそのまま書く。往復は `test/plugin-config/run.sh` が同じ読み手で確かめる
- 依存は増やしていない（`java.*` だけ）

## Q&A

### Q1. なぜ properties のままでは駄目だったのか

properties ではバックスラッシュがエスケープ文字なので、Windows のパスをそのまま書くと 2 通りに壊れる。

- `C:\users\...` のように `\u` が現れると「Malformed \uxxxx encoding」で読めない（jar の名前が `u` で始まるだけで起きる。
  spring-petclinic は Thymeleaf 経由で unbescape に依存していて、これを踏んだ）
- `C:\temp` は `\t` がタブになって `C:<TAB>emp`、`C:\new` は改行になる。**エラーにならず、静かに別のパスになる**

回避策（`/` にする・`\\` と重ねる）は説明を読まないと分からないうえ、後者は失敗のしかたが静かなので、
設定を書く人の負担として残していた。設定に書く値のほとんどがパスなのだから、読み手を合わせるほうが筋がよい。

### Q2. なぜ形式を丸ごと替えなかったのか（TOML / YAML / JSON）

依存を増やさない方針（利用者は JBang で単体で動かす）なので、外部のパーサは入れられない。
自前で書くなら、`項目=値` 1 行の形が最も小さく、今ある設定ファイル・ひな形・プラグインの書き出しがそのまま使える。
JSON は手で書く設定として注釈が書けず、YAML は自前で正しく読むのが大きすぎる。

### Q3. 読み方の決まりをどう決めたか

properties から**エスケープだけを外す**ことを軸にし、それ以外は properties と同じにした（`#` / `!` の注釈、
空白の除去、後の行が勝つ）。違いは次の 3 点。

1. **バックスラッシュはそのまま。** `\\`・`\uXXXX`・`\n` のエスケープは無い。UTF-8 で読むので `\uXXXX` は要らず、
   パス以外の値（パッケージ名・数値・真偽値）にもバックスラッシュは出てこない
2. **行末の `\` は、次の内容行が値の続きのときだけ続ける。** 次の内容行が `項目=` の形かファイルの末尾なら、
   末尾の `\` を捨ててそこで値を終える。詳しくは Q10
3. **区切りは `=` だけ。** properties は `:` と空白も区切りだが、`:` を区切りにすると字下げした続きの行の
   `C:\lib\a.jar,` を項目の行と見分けられない（続きの行のうち `項目=` の形のものは項目の行として扱うので、
   全項目を字下げして書く人がいても壊れない）。Q10 の「続きか新しい項目か」の見分けもこの形に頼っている

### Q4. 「読めない行」をエラーにするのはなぜか

properties は `=` の無い行を「値の空な項目」として黙って受け入れるが、この設定では意味が無い。
それより、`\` も字下げも無いまま次の行に値を書いた設定（`exclude.packages=` の次の行が `java.**`）を
静かに読み違えないことが重要で、その行は `=` が無いので行番号と直し方（行末に `\` を書くか字下げする）を
添えたエラーになる。「静かに違う結果」より「止まる」を選ぶ方針
（AGENTS.md）のとおり。

### Q5. `\\` と重ねて書いてある既存の設定はどうなるか

`C:\\work\\app` は 2 つのバックスラッシュのまま読まれる。Windows の `java.nio.file.Path` は連続した区切りを 1 つに
まとめるので、パスとしてはそのまま通る（`C:\\work\\app` と `C:\work\app` は同じ場所）。エラーにも静かな取り違えにもならない。
`/` で書いた設定はもちろんそのまま。以前の形からの移行に作業は要らない。

例外は Linux・macOS で**名前に `\` を含むフォルダ**を指す設定で、以前は `x\\y` と重ねて書いていた。今はそれが
`x\\y` という別の名前のまま読まれるので、そのフォルダは見つからず「source.folders のフォルダが見つからない」と
警告する（黙って別のフォルダを使うことはない）。`x\y` と 1 つで書き直す。`test/incremental/run.sh` の
名前に `\` を含むフォルダのケースも、この書き方に合わせて直した（以前の書き方のままだと、フォルダが見つからない
だけになり、JDT が受け付けない題材として効かなくなっていた）。

### Q6. 拡張（`TypeCandidateProvider` など）に渡す型は変えたか

変えていない。`init(Properties, Path)` の `Properties` はキーと値の入れ物として使っているだけなので、
読み手を替えても `Properties` に詰めて渡せば拡張側は変更なしで動く。同梱の `TypeMappingProvider` が自分で読む
対応表ファイルは別の形式（`証拠 @ 具象型`）で、こちらは properties のまま（値にバックスラッシュが出ない）。

### Q7. Gradle の `gradle.properties` はなぜ properties のままか

あれは Gradle の書式で、Gradle 自身が `Properties#load` で読む。同じ読み方をしないと、Gradle が見ている値と
このツールが見る値がずれる。設定ファイルとは別の話。

### Q8. Eclipse プラグインの検査（`test/plugin-config`）はどう変えたか

以前は「逃がし忘れ」を `Properties#load` で読み戻して検出していた。今は「本体と同じ読み手（`ConfigFile`）で
読み戻して一致すること」を見る。そのために `ConfigFile` は `java.*` だけに依存し Java 11 の文法で書いてあり、
プラグイン（`--release 11`）と一緒に単独でコンパイルできる。書く側の `escapeValue` は「そのまま返す」になったが、
書く場所の目印として残してある（次にまた形式が変わったときに直す場所が 1 つ）。

### Q9. 却下した案

- **`Properties#load` の前に `\` を `\\` に前処理する** … `\\` と重ねて書いてある既存の設定を `\\\\` にしてしまう。
  「どちらの意図か」を判定する規則が要り、`\u` の扱いも決めきれない
- **行末の `\` を properties と同じく無条件に続ける** … 末尾が区切りのパスが次の行を飲み込む（Q10）
- **続きは字下げだけで表し、行末の `\` は常に取り除く**（最初の実装） … 拡張子が `.properties` なので、
  字下げせずに `\` で続ける properties の書き癖のまま書く人がいる。エラーで止まるので安全ではあるが、
  properties として正しい書き方を拒むのは不親切なので、Q10 の読み方に改めた
- **継続の印を `\` 以外にする（行末の `,` など）** … `,` はうっかり残すことが多く、`\` と同じ飲み込みが起きる
- **TOML の部分集合など別の文法にする（引用符・`[ ]` の配列）** … 依存無しでも書けるが、既存の設定・ひな形・
  両プラグインの書き出し・Action・docs がすべて変わり、利用者の移行も要る。得るものは Q10 と同じ
- **`:` も区切りとして残す** … Q3 の 3 のとおり、続きの行の `C:\…` と区別できない
- **形式の版を上げる（`CacheFormat.VERSION`）** … 読み手の変更で、キャッシュに入る事実（解析結果）は変わらない。
  設定の値そのものが変われば（`\t` が本当のタブとして読まれていた設定が直る等）キャッシュの鍵（ソースフォルダの
  一覧・文字コード）が変わって捨てられるので、版は上げない

### Q10. 行末の `\` を「続き」と「パスの末尾の区切り」のどちらと読むか

`\` には「Windows のパスの区切り」と「次の行に続く印」の 2 つの役目があり、行末に来たときだけ区別できない。
properties はこれを「値の中の `\` はエスケープ」で解いていたので、パスを `\\` と重ねる制約が生まれていた。

ここでは**次の内容行の形**で見分ける。

- 次の内容行が `項目=` の形（英字で始まり英数字と `. _ -` だけの名前と `=`）かファイルの末尾なら、続けない。
  末尾の `\` は捨てる（`C:\work\app\` は `C:\work\app` になる。無くても同じ場所を指す）
- それ以外の行は続き。前後の空白を除いて値につなぐ
- 続きの途中の注釈行は読み飛ばす（`\` で並べた一覧の 1 要素を `#` で外せる。properties では注釈が続きの値に
  入ってしまい、壊れていた書き方）。空行も `\` の続きの途中なら読み飛ばす（以前のひな形は最後の要素にも `\` を
  付けて空行で終えていた）

取り違えが起きないのは、設定の値（パス・パッケージ名・数値・真偽値）に `項目=` の形の行が現れないためである。
パスの続きに `=` が入っても（`C:\a=b\y.jar`）、区切りの `\` と `:` を含むので項目の行にはならない。
末尾が `\` のパスの次に注釈があっても、注釈を読み飛ばした先の行で判断するので、`C:\work\app# …` のような
フォルダを黙って作ることはない。

字下げした行は `\` が無くても続きとして読む（最初の実装で書いた `exclude.packages=` + 字下げの形も読める）。
ただし空行を挟んだ字下げの行は続きにしない（離れた行を前の項目につながない）。
