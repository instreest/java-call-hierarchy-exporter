# キャッシュを呼び出し階層用とデータフロー用の 2 つに分ける — 実装時の QA 一覧

「呼び出し階層のためのキャッシュと、データフロー解析のためのキャッシュを分けたい。後者は文字列の長さの
上限を設けたくない」への対応で、迷ったこと・困ったことと、その結論を Q&A の形で残す。

対応の要点:

- キャッシュを 2 つに分けた。`analysis-cache.tsv`（呼び出し階層のための構造とバインディングの事実）と
  `dataflow-cache.tsv`（呼び出し階層の出力には要らない、サイドカーの解析のための事実）
- 第 1 段として `A` 行（フィールドの参照箇所）を dataflow 側へ移した。現在この行を読む処理は無く、
  移しても出力は 1 行も変わらない。整合の仕組みだけを、出力への影響なしに入れられる
- **片方だけが新しい状態は作らない。** 両方のヘッダに同じ世代の印（`gen=`）を書き、
  どちらかが無い・形式が違う・世代が食い違えば**両方とも捨てて全件解析し直す**
- そのうえで、再利用するブロックは「両方のキャッシュにあるもの」だけに絞る。片方にしか無いブロックは
  再解析に回すので、ブロック単位のズレも残らない
- `analysis-cache.tsv` は v14 → v15。`dataflow-cache.tsv` は v1

---

## 設計

### Q1. 何を基準に 2 つへ振り分けたか

**「呼び出し階層（`call-hierarchy.csv` / `methods.csv`）の出力に使うか」**の一点で決める。
使うなら analysis 側、使わないなら dataflow 側。

この基準で `A` 行（フィールドの参照箇所）を調べたところ、書き出しと差分更新での書き写しはあるのに、
`jche.graph` にも `jche.report` にも読み手が無かった（`FieldAccessRecorder` が作り、`CacheUpdater` が
書き写すだけ）。つまり最初から「サイドカーのための事実」で、分割の第 1 号にちょうどよかった。

なお「データフローの事実は全部 dataflow 側へ」ではない。出所（`C` 行の `recvOrigin` / `argOrigins`）や
ガード、`R` 行、`J` 行は具象クラスの解決と枝刈りに使う＝呼び出し階層の出力に効くので analysis 側に残す。
これらを dataflow 側へ移すと、dataflow を読まない実行で出力が `CHA` 止まりに変わってしまう。

### Q2. なぜブロック単位のズレを許さないのか

許せば「このファイルは analysis だけ新しいので、データフローの事実は前回のものを使う」という
状態がファイルごとに生まれる。同じソースでも**キャッシュの履歴によって出力が変わる**ことになり、
`docs/deterministic-row-order-qa.md` で守ってきた「環境が違っても同じ出力」と相反する。

そこで不変条件を 1 つ置いた。**2 つのキャッシュは常に同じブロックを同じ順で持つ。**
これを保つために、書くときは必ず両方へ同じ順で書き、読むときは「両方にあるブロック」しか再利用しない。

### Q3. 「同じ実行で書かれた対か」をどう判定するか

両方のヘッダの末尾に、同じ世代の印を書く。

```
jche-cache-v15      source=17  jdk=25  gen=af94c208586d302c
jche-dataflow-v1    source=17  jdk=25  gen=af94c208586d302c
```

世代は乱数（16 桁の 16 進）で、内容から導いてはいない。内容から導くには書き出す前に全体を読む必要があり、
「1 ファイル解析するたびに書き出して破棄する」ストリーミングの作りが壊れる。
ここで要るのは「2 つが同じ実行で書かれたか」だけなので、重複しない値であれば十分。

ヘッダの突き合わせは、形式の互換性（版・ソースレベル・JDK・拡張の指紋）と世代とで別に行う
（`CacheFormat.compatibilityPartOf` / `generationOf`）。前者は期待値と比べ、後者は 2 つの間で比べる。

### Q4. 書き出しの途中で落ちたらどうなるか

どちらもテンポラリに書いてから差し替える（`Files.move`）。差し替えは analysis → dataflow の順。
落ちる場所ごとに次回の実行がどうなるかは次のとおりで、どこで落ちても壊れた対は残らない。

| 落ちた場所 | 次回の状態 | 次回の判定 |
|---|---|---|
| 解析中（どちらも差し替え前） | 両方とも前回のまま（対） | そのまま再利用 |
| analysis を差し替えた直後 | analysis だけ新しい世代 | 世代が食い違う → 両方作り直し |
| 両方を差し替えた後 | 両方とも新しい世代（対） | そのまま再利用 |

### Q5. 世代が一致していれば、ブロックの突き合わせは要らないのでは

理屈ではそのとおりで、世代が一致していればブロックはそろっている。
それでもパス1b でブロックの有無を突き合わせるのは、**世代では捕まえられない壊れ方**があるため。
片方だけを外から消された（`.cache` を部分的に掃除した、CI のキャッシュ復元が片方だけ当たった）、
片方だけを編集された、といった場合は世代が一致したまま中身がずれる。

突き合わせのコストは dataflow 側の F 行を読むだけ（1 スキャン）で、
欠けていたファイルは通常の再解析に回るので自己修復する。安全側に倒すには十分安い。

### Q6. `hints=`（フェーズAの拡張の指紋）はどちらのヘッダに入れるか

今は analysis 側だけ。`X` 行（拡張が拾った証拠）が analysis 側にあるため。
`X` 行を dataflow 側へ移す段では、指紋も一緒に移す。そうすると**拡張を差し替えても
analysis 側のキャッシュが生き残る**ようになる（今は全件捨てられる。回帰テストの `plugin` ケースが
その挙動を検査している）。

### Q7. F 行を両方に書くと重複するが、無駄ではないか

重複する。`test/demo`（62 ファイル）では 4.3KB ぶんで、合計サイズは分割前より 6% 増えた。
それでも F 行を dataflow 側にも置くのは、

- ブロックの区切りとして要る（どの行がどのファイルのものか）
- ブロックの有無の突き合わせ（Q5）が、dataflow 側だけを読んで済む
- dataflow 側を単独で（サイドカーから）読むときに、ファイルの対応が分かる

ため。参照だけにして analysis 側を見に行く作りは、2 つのファイルの結合順に依存が生まれるので採らなかった。

### Q8. サイズはどれだけ変わったか

`test/demo` の実測。

| | 分割前 | 分割後 |
|---|---|---|
| analysis-cache.tsv | 72,816 | **65,909**（90.5%） |
| dataflow-cache.tsv | — | 11,260 |
| 合計 | 72,816 | 77,169（106%） |

第 1 段では `A` 行ぶん（9.5%）しか減らない。狙いはサイズそのものではなく**成長の切り離し**で、
dataflow 側に長い文字列（SQL・ログ文言）や値グラフを入れても analysis 側は太らない、という形にすること。

### Q9. `cache.enabled=false` のときはどうなるか

従来どおり、2 つとも書くが再利用はしない（フェーズ2 が analysis 側を読むため、書くこと自体は必要）。
再利用しないので世代の突き合わせもしない。

## テスト

### Q10. 整合の仕組みをどう検査したか

回帰テストに `cachesplit` ケースを足した。同じソースを 6 回解析し、間でキャッシュを壊し方を変えて壊す。

| 回 | 壊し方 | 期待 |
|---|---|---|
| 1 | なし（キャッシュ無し） | 出力が期待値と一致し、2 つの F 行が一致 |
| 2 | なし | 全件再利用 |
| 3 | dataflow を消す | **両方**作り直し（再利用 0） |
| 4 | dataflow の `gen=` を書き換える | **両方**作り直し（再利用 0） |
| 5 | dataflow から 1 ブロックだけ消す | そのファイルだけ解析し直し、他は再利用。F 行が再び一致 |
| 6 | なし | 全件再利用に戻る |

どの回のあとも「2 つのキャッシュの F 行が完全に一致すること」を検査する。これが不変条件（Q2）で、
ここが崩れると片方だけ新しいブロックが生まれる。

5 の回で「そのファイルだけ」でなく依存先のファイルも解析し直すのは、解析し直したファイルが宣言する型を
「変わった型」に入れる既存の仕組み（改名・追加に備えるため）によるもので、想定どおりの挙動。
