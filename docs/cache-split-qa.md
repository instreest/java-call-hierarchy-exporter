# キャッシュを呼び出し階層用とデータフロー用の 2 つに分ける — 実装時の QA 一覧

「呼び出し階層のためのキャッシュと、データフロー解析のためのキャッシュを分けたい。後者は文字列の長さの
上限を設けたくない」への対応で、迷ったこと・困ったことと、その結論を Q&A の形で残す。

対応の要点:

- キャッシュを 2 つに分けた。`analysis-cache.tsv`（呼び出し階層のための構造とバインディングの事実）と
  `dataflow-cache.tsv`（呼び出し階層の出力には要らない、サイドカーの解析のための事実）
- 第 1 段として `A` 行（フィールドの参照箇所）を dataflow 側へ移した。現在この行を読む処理は無く、
  移しても出力は 1 行も変わらない。整合の仕組みだけを、出力への影響なしに入れられる
- **片方だけが新しい状態は作らない。** 両方のヘッダに同じ世代の印（`gen=`）を書き、
  どちらかが無い・形式が違う・世代が食い違う・最終行（`Z` 行）のブロック数が食い違えば
  **両方とも捨てて全件解析し直す**
- そのうえで、再利用するブロックは「両方のキャッシュにあるもの」だけに絞る。片方にしか無いブロックは
  再解析に回すので、ブロック単位のズレも残らない。中断した実行からの引き継ぎも同じで、
  両方の一時ファイルにそろっているブロックだけを引き継ぐ
- `analysis-cache.tsv` は v16 → v17。`dataflow-cache.tsv` は v1
- 振り分けの境界は最終的に**「構造 / 値」**にした。値に関わる事実（出所・ガード・`R` / `J` / `K` / `X` 行）は
  すべて dataflow 側へ移す。`analysis-cache.tsv` 単独では呼び出し階層が `CHA` 止まりになる（Q11）
- dataflow 側の値はバックスラッシュ・エスケープで符号化し、**長さの上限を設けない**（Q13）

---

## 設計

### Q1. 何を基準に 2 つへ振り分けたか

**「呼び出し階層（`call-hierarchy.csv` / `methods.csv`）の出力に使うか」**の一点で決める。
使うなら analysis 側、使わないなら dataflow 側。

この基準で `A` 行（フィールドの参照箇所）を調べたところ、書き出しと差分更新での書き写しはあるのに、
`jche.graph` にも `jche.report` にも読み手が無かった（`FieldAccessRecorder` が作り、`CacheUpdater` が
書き写すだけ）。つまり最初から「サイドカーのための事実」で、分割の第 1 号にちょうどよかった。

この基準の当初の読みでは、出所（`C` 行の `recvOrigin` / `argOrigins`）・ガード・`R` 行・`J` 行は
「具象クラスの解決と枝刈りに使う＝呼び出し階層の出力に効く」ので analysis 側に残す、としていた。
だがそれだと**同じ値の流れを 2 か所に持つ**（analysis には上限付きの出所文字列、dataflow には
無制限のノード表）ことになる。

そこで方針を変え、**値に関わる事実はすべて dataflow 側へ移す**ことにした（Q11）。
analysis 側は構造（型階層・メソッド宣言・呼び出しの骨格）だけになり、
`analysis-cache.tsv` 単独では呼び出し階層が `CHA` 止まりになる。
2 つは常に対で読まれるので通常の出力は変わらず、`CHA` 止まりになるのは
`dataflow.enabled=false`（dataflow 側を開かない）と決めたときだけ。

### Q2. なぜブロック単位のズレを許さないのか

許せば「このファイルは analysis だけ新しいので、データフローの事実は前回のものを使う」という
状態がファイルごとに生まれる。同じソースでも**キャッシュの履歴によって出力が変わる**ことになり、
`docs/deterministic-row-order-qa.md` で守ってきた「環境が違っても同じ出力」と相反する。

そこで不変条件を 1 つ置いた。**2 つのキャッシュは常に同じブロックを同じ順で持つ。**
これを保つために、書くときは必ず両方へ同じ順で書き、読むときは「両方にあるブロック」しか再利用しない。

### Q3. 「同じ実行で書かれた対か」をどう判定するか

両方のヘッダの末尾に、同じ世代の印を書く。

```
jche-cache-v17      source=17  enc=UTF-8  jdk=25  gen=af94c208586d302c
jche-dataflow-v1    source=17  enc=UTF-8  jdk=25  gen=af94c208586d302c
```

世代は乱数（16 桁の 16 進）で、内容から導いてはいない。内容から導くには書き出す前に全体を読む必要があり、
「1 ファイル解析するたびに書き出して破棄する」ストリーミングの作りが壊れる。
ここで要るのは「2 つが同じ実行で書かれたか」だけなので、重複しない値であれば十分。

ヘッダの突き合わせは、形式の互換性（版・ソースレベル・文字コード・JDK・拡張の指紋）と世代とで別に行う
（`CacheFormat.compatibilityPartOf` / `generationOf`）。前者は期待値と比べ、後者は 2 つの間で比べる。

### Q4. 書き出しの途中で落ちたらどうなるか

どちらも一時ファイル（`.tmp`）に書いてから差し替える（`Files.move`）。差し替えは analysis → dataflow の順。
落ちる場所ごとに次回の実行がどうなるかは次のとおりで、どこで落ちても壊れた対は残らない。

| 落ちた場所 | 次回の状態 | 次回の判定 |
|---|---|---|
| 解析中（どちらも差し替え前） | 両方とも前回のまま（対）＋ `.tmp` が 2 つ残る | そのまま再利用。`.tmp` は引き継ぎに使う（Q4b） |
| analysis を差し替えた直後 | analysis だけ新しい世代 | 世代が食い違う → 両方作り直し |
| 両方を差し替えた後 | 両方とも新しい世代（対） | そのまま再利用 |

### Q4b. 中断した実行からの引き継ぎはどうなるか

中断した実行の一時ファイルから解析済みのブロックを引き継ぐ仕組み（`docs/cache-identity-qa.md`）は、
キャッシュが 2 つになっても同じ不変条件で動かす。**両方の一時ファイルにそろっているブロックだけ**を
引き継ぐ。片方にしか無いものを引き継ぐと、対になっていないブロックが生まれるため。

手順は既存キャッシュの再利用（Q5）と同じ形にした。
dataflow 側の一時ファイルの F 行を先に集め（`blockPathsOf`）、その集合との積を引き継ぎの候補にし、
analysis 側から引き継げたぶんと同じブロックを dataflow 側からも書き写す。
どちらかの一時ファイルが無ければ引き継がない（解析し直すだけで、正しさには影響しない）。

一時ファイルの「最後の F 行から始まるブロック」を使わないのも両方に通す。書き込みバッファの途中で
切れている可能性があるので、次の F 行か最終行の印に出会ったブロックだけを引き継ぐ。

### Q5. 世代が一致していれば、ブロックの突き合わせは要らないのでは

理屈ではそのとおりで、世代とブロック数が一致していればブロックはそろっている。
それでもパス1b でブロックの有無を突き合わせるのは、**世代では捕まえられない壊れ方**があるため。
片方だけを外から消された（`.cache` を部分的に掃除した、CI のキャッシュ復元が片方だけ当たった）、
片方だけを編集された、といった場合は世代が一致したまま中身がずれる。

突き合わせのコストは dataflow 側の F 行を読むだけ（1 スキャン）で、
欠けていたファイルは通常の再解析に回るので自己修復する。安全側に倒すには十分安い。

なお最終行の印（`Z` 行。ブロック数）は analysis 側が元から持っていたので、dataflow 側にも同じ数を書き、
パス0 で突き合わせている。これは「どちらかが途中で切れている」を 1 行読むだけで捕まえられる安い検査で、
ブロックの突き合わせ（こちらはどのブロックが欠けたかまで分かる）と役割が違う。

### Q6. `hints=`（フェーズAの拡張の指紋）はどちらのヘッダに入れるか

今は analysis 側だけ。`X` 行（拡張が拾った証拠）が analysis 側にあるため。
`X` 行を dataflow 側へ移す段では、指紋も一緒に移す。
<b>ただし「拡張を差し替えても analysis 側が生き残る」わけではない（Q12 で訂正）。</b>

### Q7. F 行を両方に書くと重複するが、無駄ではないか

重複する。`test/demo`（62 ファイル）では 4.3KB ぶんで、合計サイズは分割前より 6% 増えた。
それでも F 行を dataflow 側にも置くのは、

- ブロックの区切りとして要る（どの行がどのファイルのものか）
- ブロックの有無の突き合わせ（Q5）が、dataflow 側だけを読んで済む
- dataflow 側を単独で（サイドカーから）読むときに、ファイルの対応が分かる

ため。参照だけにして analysis 側を見に行く作りは、2 つのファイルの結合順に依存が生まれるので採らなかった。

### Q8. サイズはどれだけ変わったか

`test/demo` の実測。

| | 分割前 | 分割後 |
|---|---|---|
| analysis-cache.tsv | 72,816 | **65,909**（90.5%） |
| dataflow-cache.tsv | — | 11,260 |
| 合計 | 72,816 | 77,169（106%） |

（`test/demo` 62 ファイル。分割を入れた時点での実測で、その後の `main` の変更で絶対値は動く）

第 1 段では `A` 行ぶん（9.5%）しか減らない。狙いはサイズそのものではなく**成長の切り離し**で、
dataflow 側に長い文字列（SQL・ログ文言）や値グラフを入れても analysis 側は太らない、という形にすること。

### Q9. `cache.enabled=false` のときはどうなるか

従来どおり、2 つとも書くが再利用はしない（フェーズ2 が analysis 側を読むため、書くこと自体は必要）。
再利用しないので世代の突き合わせもしない。

### Q11. 値に関わる事実をすべて dataflow 側へ移すと何が変わるか

振り分けの境界を「構造 / 値」にした結果、次の 3 つが動く。

**1. 再解析の判断が dataflow 側を見て行われる。**
`K` 行（このファイルが宣言するコンパイル時定数の値）は「定数の連鎖」の判断材料で、
これも値なので dataflow 側へ移る。つまり差分更新の判断の一部が dataflow 側の読み取りになる。
値が変われば **analysis 側も解析し直す**（同じパースから両方を書くので、そこは元から同じ）。

**2. 読み手が 2 つのファイルを突き合わせる必要がある。**
今は `C` 行 1 行に出所まで入っているので、グラフを組む側は 1 行読むだけで済む。
移すと「analysis の `C` 行（エッジ）」と「dataflow の `P` 行（その呼び出しの値）」を
結びつける必要がある。ブロックの並びが常に一致している（Q2 の不変条件）ので、
**2 つのファイルをブロック単位で歩調を合わせて読む**形にすれば、ヒープに載るのは
1 ブロックぶんのノード表だけで、ストリーミングの作りは保てる。

結びつけの鍵は自己記述にする（L1）。`(行番号, 呼び出し元メソッドのキー, 呼び出し先のキー)` と、
**同じ鍵が同じ行に複数あるときの通し番号**。`f(g(), g())` のように同一の鍵が並ぶ場合があるので
通し番号が要る。analysis 側の行の並びを参照する形（`C` 行の何番目か）は採らない。
並びを変えた瞬間に<b>静かに</b>ずれるため。鍵の重複ぶんは払うコストとして受け入れる
（`F` 行を両方に持つ判断（Q7）と同じ理屈）。

**3. `dataflow.enabled=false` の意味がはっきりする。**
「dataflow 側のキャッシュを開かない」になり、具象クラスの解決は `CHA` まで、条件分岐の打ち切りは
起きない（ガードの判定材料が dataflow 側にあるため）。
今の設定コメントも「`dataflow.enabled=false` のときは打ち切りはほとんど起きない」と書いているので、
「ほとんど」が「起きない」になるだけの変化。

### Q12. Q6 の「拡張を差し替えても analysis 側が生き残る」は成り立つか

**成り立たない。** Q6 では「`X` 行と `hints=` を dataflow 側へ移せば、拡張を差し替えても
analysis 側のキャッシュが生き残る」と書いたが、これは誤り。

- 対の不変条件により、どちらかのヘッダが違えば**両方とも**捨てる（Q3）
- 仮に analysis 側を残す作りにしても、dataflow 側を作り直すには**そのファイルをパースし直す**必要があり、
  パースすれば analysis 側の事実も一緒に出来る。つまり「残す」ことで節約できる時間は無い

版を独立に上げられる利点は「影響範囲と出力の安定性」であって「再パースの節約」ではない、
という最初の整理（`main` 取り込み時の議論）と同じ話。`hints=` は `X` 行と同じ側に置く、
という整理のためだけに移す。

### Q13. 値の符号化（dataflow 側だけの規則）

dataflow 側は「長さも中身も選べない文字列をそのまま持つ」のが目的なので、
analysis 側の `clean`（タブ・改行を空白へ置き換えて捨てる）ではなく、
バックスラッシュ・エスケープで符号化する（`CacheFormat.escape` / `unescape`）。

```
\      ->  \\        タブ  ->  \t        LF  ->  \n        CR  ->  \r
その他の制御文字（U+0000〜U+001F と U+007F）  ->  \uXXXX
```

パーセント符号化（`%09`）と、制御文字への写像も検討した。バックスラッシュを選んだのは、
`\n` が Java 開発者に自明で、キャッシュを目で追えるしるべを保てるから。
`%` は書式文字列（`"%s"`）で頻出するので、二重化が必要な文字としては `\` と同程度に出てくる。

`Guard` が区切りに使う `U+0001`〜`U+0003` も「その他の制御文字」として符号化されるので、
ガードを dataflow 側へ移しても値と区切りが衝突しない。

`analysis-cache.tsv` 側の `clean` は**そのまま**。2 つのキャッシュで規則が違ってよいこと自体が、
分けたことで得られた自由度。

## テスト

### Q10. 整合の仕組みをどう検査したか

回帰テストに `cachesplit` ケースを足した。同じソースを 6 回解析し、間でキャッシュを壊し方を変えて壊す。

| 回 | 壊し方 | 期待 |
|---|---|---|
| 1 | なし（キャッシュ無し） | 出力が期待値と一致し、2 つの F 行が一致 |
| 2 | なし | 全件再利用 |
| 3 | dataflow を消す | **両方**作り直し（再利用 0） |
| 4 | dataflow の `gen=` を書き換える | **両方**作り直し（再利用 0） |
| 5 | dataflow から 1 ブロックだけ消す | そのファイルだけ解析し直し、他は再利用。F 行が再び一致 |
| 6 | なし | 全件再利用に戻る |

どの回のあとも「2 つのキャッシュの F 行が完全に一致すること」を検査する。これが不変条件（Q2）で、
ここが崩れると片方だけ新しいブロックが生まれる。

`test/incremental/run.sh`（キャッシュの健全性の検査）にも次を足した。
こちらは期待値を持たず「差分更新の結果 == 全件解析の結果」を見るので、分割で事実が落ちれば捕まる。

- dataflow 側のキャッシュも、差分更新と全件解析で一致すること
- どのケースでも 2 つのキャッシュの F 行が一致すること（`check_paired`）
- dataflow 側の行種別が F / A / Z だけであること（`check_flow_rows`）
- 中断の再現（`make_partial`）で一時ファイルを 2 つ作ること。本物の中断では両方の `.tmp` が残るため

比較からはヘッダの世代の印（`gen=`）を外す。実行ごとに変わる値で、事実ではないため
（外さないと「差分更新と全件解析でキャッシュが違う」と誤検出する）。

5 の回で「そのファイルだけ」でなく依存先のファイルも解析し直すのは、解析し直したファイルが宣言する型を
「変わった型」に入れる既存の仕組み（改名・追加に備えるため）によるもので、想定どおりの挙動。

### Q14. 値の符号化はどう検査したか

`test/cachevalue/run.sh` を足した。見る性質は 2 つだけ。

| 性質 | 内容 |
|---|---|
| 往復 | `unescape(escape(s))` が `s` に戻る |
| 無害化 | `escape(s)` にタブ・改行・制御文字が残らない（行が割れない） |

対象は、ソースに実際に現れる形（SQL、書式文字列、Windows のパス、正規表現）と、
そこには出てこないが形式を壊しうる形（**BMP の全文字**、バックスラッシュの連なり、
`\u0041` のように符号化の形をした文字列、途中で切れた符号、サロゲートペア）。
合わせて 126,998 通り。行に組み込んでも（`joinRow` を通しても）値が変わらないことも見る。

意図的に壊して落ちることも確かめた。「`\` を二重化しない」→ 往復しない、
「制御文字を素通しする」→ 無害化されない、のどちらも検出する。
