# キャッシュを呼び出し階層用とデータフロー用の 2 つに分ける — 実装時の QA 一覧

「呼び出し階層のためのキャッシュと、データフロー解析のためのキャッシュを分けたい。後者は文字列の長さの
上限を設けたくない」への対応で、迷ったこと・困ったことと、その結論を Q&A の形で残す。

対応の要点:

- キャッシュを 2 つに分けた。`analysis-cache.tsv`（呼び出し階層のための構造とバインディングの事実）と
  `dataflow-cache.tsv`（呼び出し階層の出力には要らない、サイドカーの解析のための事実）
- 第 1 段として `A` 行（フィールドの参照箇所）を dataflow 側へ移した。現在この行を読む処理は無く、
  移しても出力は 1 行も変わらない。整合の仕組みだけを、出力への影響なしに入れられる
- **片方だけが新しい状態は作らない。** 両方のヘッダに同じ世代の印（`gen=`）を書き、
  どちらかが無い・形式が違う・世代が食い違う・最終行（`Z` 行）のブロック数が食い違えば
  **両方とも捨てて全件解析し直す**
- そのうえで、再利用するブロックは「両方のキャッシュにあるもの」だけに絞る。片方にしか無いブロックは
  再解析に回すので、ブロック単位のズレも残らない。中断した実行からの引き継ぎも同じで、
  両方の一時ファイルにそろっているブロックだけを引き継ぐ
- `analysis-cache.tsv` は v16 → v17。`dataflow-cache.tsv` は v1
- 振り分けの境界は最終的に**「構造 / 値」**にした。値に関わる事実（出所・ガード・`R` / `J` / `K` / `X` 行）は
  すべて dataflow 側へ移す。`analysis-cache.tsv` 単独では呼び出し階層が `CHA` 止まりになる（Q11）
- dataflow 側の値はバックスラッシュ・エスケープで符号化し、**長さの上限を設けない**（Q13）
- 値グラフ（`N` 行）と呼び出し箇所との結びつけ（`P` 行）を足した。入れ子を展開せずノード番号で参照するので
  深さの上限が要らず、文字列の長さにも上限が無い（Q15）。読み手は今のところ旧来の出所を使うので出力は変わらない
- `K`（定数）・`R`（戻り値の出所）・`X`（拡張の証拠）行を dataflow 側へ移し、`hints=` も同じ側へ。
  定数の連鎖の判断も dataflow 側を読んで行う。`dataflow.enabled=false` は「dataflow 側を開かない」になった（Q18）
- `analysis-cache.tsv` は v18、`dataflow-cache.tsv` は v3

---

## 設計

### Q1. 何を基準に 2 つへ振り分けたか

**「呼び出し階層（`call-hierarchy.csv` / `methods.csv`）の出力に使うか」**の一点で決める。
使うなら analysis 側、使わないなら dataflow 側。

この基準で `A` 行（フィールドの参照箇所）を調べたところ、書き出しと差分更新での書き写しはあるのに、
`jche.graph` にも `jche.report` にも読み手が無かった（`FieldAccessRecorder` が作り、`CacheUpdater` が
書き写すだけ）。つまり最初から「サイドカーのための事実」で、分割の第 1 号にちょうどよかった。

この基準の当初の読みでは、出所（`C` 行の `recvOrigin` / `argOrigins`）・ガード・`R` 行・`J` 行は
「具象クラスの解決と枝刈りに使う＝呼び出し階層の出力に効く」ので analysis 側に残す、としていた。
だがそれだと**同じ値の流れを 2 か所に持つ**（analysis には上限付きの出所文字列、dataflow には
無制限のノード表）ことになる。

そこで方針を変え、**値に関わる事実はすべて dataflow 側へ移す**ことにした（Q11）。
analysis 側は構造（型階層・メソッド宣言・呼び出しの骨格）だけになり、
`analysis-cache.tsv` 単独では呼び出し階層が `CHA` 止まりになる。
2 つは常に対で読まれるので通常の出力は変わらず、`CHA` 止まりになるのは
`dataflow.enabled=false`（dataflow 側を開かない）と決めたときだけ。

### Q2. なぜブロック単位のズレを許さないのか

許せば「このファイルは analysis だけ新しいので、データフローの事実は前回のものを使う」という
状態がファイルごとに生まれる。同じソースでも**キャッシュの履歴によって出力が変わる**ことになり、
`docs/deterministic-row-order-qa.md` で守ってきた「環境が違っても同じ出力」と相反する。

そこで不変条件を 1 つ置いた。**2 つのキャッシュは常に同じブロックを同じ順で持つ。**
これを保つために、書くときは必ず両方へ同じ順で書き、読むときは「両方にあるブロック」しか再利用しない。

### Q3. 「同じ実行で書かれた対か」をどう判定するか

両方のヘッダの末尾に、同じ世代の印を書く。

```
jche-cache-v17      source=17  enc=UTF-8  jdk=25  gen=af94c208586d302c
jche-dataflow-v1    source=17  enc=UTF-8  jdk=25  gen=af94c208586d302c
```

世代は乱数（16 桁の 16 進）で、内容から導いてはいない。内容から導くには書き出す前に全体を読む必要があり、
「1 ファイル解析するたびに書き出して破棄する」ストリーミングの作りが壊れる。
ここで要るのは「2 つが同じ実行で書かれたか」だけなので、重複しない値であれば十分。

ヘッダの突き合わせは、形式の互換性（版・ソースレベル・文字コード・JDK・拡張の指紋）と世代とで別に行う
（`CacheFormat.compatibilityPartOf` / `generationOf`）。前者は期待値と比べ、後者は 2 つの間で比べる。

### Q4. 書き出しの途中で落ちたらどうなるか

どちらも一時ファイル（`.tmp`）に書いてから差し替える（`Files.move`）。差し替えは analysis → dataflow の順。
落ちる場所ごとに次回の実行がどうなるかは次のとおりで、どこで落ちても壊れた対は残らない。

| 落ちた場所 | 次回の状態 | 次回の判定 |
|---|---|---|
| 解析中（どちらも差し替え前） | 両方とも前回のまま（対）＋ `.tmp` が 2 つ残る | そのまま再利用。`.tmp` は引き継ぎに使う（Q4b） |
| analysis を差し替えた直後 | analysis だけ新しい世代 | 世代が食い違う → 両方作り直し |
| 両方を差し替えた後 | 両方とも新しい世代（対） | そのまま再利用 |

### Q4b. 中断した実行からの引き継ぎはどうなるか

中断した実行の一時ファイルから解析済みのブロックを引き継ぐ仕組み（`docs/cache-identity-qa.md`）は、
キャッシュが 2 つになっても同じ不変条件で動かす。**両方の一時ファイルにそろっているブロックだけ**を
引き継ぐ。片方にしか無いものを引き継ぐと、対になっていないブロックが生まれるため。

手順は既存キャッシュの再利用（Q5）と同じ形にした。
dataflow 側の一時ファイルの F 行を先に集め（`blockPathsOf`）、その集合との積を引き継ぎの候補にし、
analysis 側から引き継げたぶんと同じブロックを dataflow 側からも書き写す。
どちらかの一時ファイルが無ければ引き継がない（解析し直すだけで、正しさには影響しない）。

一時ファイルの「最後の F 行から始まるブロック」を使わないのも両方に通す。書き込みバッファの途中で
切れている可能性があるので、次の F 行か最終行の印に出会ったブロックだけを引き継ぐ。

### Q5. 世代が一致していれば、ブロックの突き合わせは要らないのでは

理屈ではそのとおりで、世代とブロック数が一致していればブロックはそろっている。
それでもパス1b でブロックの有無を突き合わせるのは、**世代では捕まえられない壊れ方**があるため。
片方だけを外から消された（`.cache` を部分的に掃除した、CI のキャッシュ復元が片方だけ当たった）、
片方だけを編集された、といった場合は世代が一致したまま中身がずれる。

突き合わせのコストは dataflow 側の F 行を読むだけ（1 スキャン）で、
欠けていたファイルは通常の再解析に回るので自己修復する。安全側に倒すには十分安い。

なお最終行の印（`Z` 行。ブロック数）は analysis 側が元から持っていたので、dataflow 側にも同じ数を書き、
パス0 で突き合わせている。これは「どちらかが途中で切れている」を 1 行読むだけで捕まえられる安い検査で、
ブロックの突き合わせ（こちらはどのブロックが欠けたかまで分かる）と役割が違う。

### Q6. `hints=`（フェーズAの拡張の指紋）はどちらのヘッダに入れるか

今は analysis 側だけ。`X` 行（拡張が拾った証拠）が analysis 側にあるため。
`X` 行を dataflow 側へ移す段では、指紋も一緒に移す。
<b>ただし「拡張を差し替えても analysis 側が生き残る」わけではない（Q12 で訂正）。</b>

### Q7. F 行を両方に書くと重複するが、無駄ではないか

重複する。`test/demo`（62 ファイル）では 4.3KB ぶんで、合計サイズは分割前より 6% 増えた。
それでも F 行を dataflow 側にも置くのは、

- ブロックの区切りとして要る（どの行がどのファイルのものか）
- ブロックの有無の突き合わせ（Q5）が、dataflow 側だけを読んで済む
- dataflow 側を単独で（サイドカーから）読むときに、ファイルの対応が分かる

ため。参照だけにして analysis 側を見に行く作りは、2 つのファイルの結合順に依存が生まれるので採らなかった。

### Q8. サイズはどれだけ変わったか

`test/demo` の実測。

| | 分割前 | 分割後 |
|---|---|---|
| analysis-cache.tsv | 72,816 | **65,909**（90.5%） |
| dataflow-cache.tsv | — | 11,260 |
| 合計 | 72,816 | 77,169（106%） |

（`test/demo` 62 ファイル。分割を入れた時点での実測で、その後の `main` の変更で絶対値は動く）

第 1 段では `A` 行ぶん（9.5%）しか減らない。狙いはサイズそのものではなく**成長の切り離し**で、
dataflow 側に長い文字列（SQL・ログ文言）や値グラフを入れても analysis 側は太らない、という形にすること。

### Q9. `cache.enabled=false` のときはどうなるか

従来どおり、2 つとも書くが再利用はしない（フェーズ2 が analysis 側を読むため、書くこと自体は必要）。
再利用しないので世代の突き合わせもしない。

### Q11. 値に関わる事実をすべて dataflow 側へ移すと何が変わるか

振り分けの境界を「構造 / 値」にした結果、次の 3 つが動く。

**1. 再解析の判断が dataflow 側を見て行われる。**
`K` 行（このファイルが宣言するコンパイル時定数の値）は「定数の連鎖」の判断材料で、
これも値なので dataflow 側へ移る。つまり差分更新の判断の一部が dataflow 側の読み取りになる。
値が変われば **analysis 側も解析し直す**（同じパースから両方を書くので、そこは元から同じ）。

**2. 読み手が 2 つのファイルを突き合わせる必要がある。**
今は `C` 行 1 行に出所まで入っているので、グラフを組む側は 1 行読むだけで済む。
移すと「analysis の `C` 行（エッジ）」と「dataflow の `P` 行（その呼び出しの値）」を
結びつける必要がある。ブロックの並びが常に一致している（Q2 の不変条件）ので、
**2 つのファイルをブロック単位で歩調を合わせて読む**形にすれば、ヒープに載るのは
1 ブロックぶんのノード表だけで、ストリーミングの作りは保てる。

結びつけの鍵は自己記述にする（L1）。`(行番号, 呼び出し元メソッドのキー, 呼び出し先のキー)` と、
**同じ鍵が同じ行に複数あるときの通し番号**。`f(g(), g())` のように同一の鍵が並ぶ場合があるので
通し番号が要る。analysis 側の行の並びを参照する形（`C` 行の何番目か）は採らない。
並びを変えた瞬間に<b>静かに</b>ずれるため。鍵の重複ぶんは払うコストとして受け入れる
（`F` 行を両方に持つ判断（Q7）と同じ理屈）。

**3. `dataflow.enabled=false` の意味がはっきりする。**
「dataflow 側のキャッシュを開かない」になり、具象クラスの解決は `CHA` まで、条件分岐の打ち切りは
起きない（ガードの判定材料が dataflow 側にあるため）。
今の設定コメントも「`dataflow.enabled=false` のときは打ち切りはほとんど起きない」と書いているので、
「ほとんど」が「起きない」になるだけの変化。

### Q12. Q6 の「拡張を差し替えても analysis 側が生き残る」は成り立つか

**成り立たない。** Q6 では「`X` 行と `hints=` を dataflow 側へ移せば、拡張を差し替えても
analysis 側のキャッシュが生き残る」と書いたが、これは誤り。

- 対の不変条件により、どちらかのヘッダが違えば**両方とも**捨てる（Q3）
- 仮に analysis 側を残す作りにしても、dataflow 側を作り直すには**そのファイルをパースし直す**必要があり、
  パースすれば analysis 側の事実も一緒に出来る。つまり「残す」ことで節約できる時間は無い

版を独立に上げられる利点は「影響範囲と出力の安定性」であって「再パースの節約」ではない、
という最初の整理（`main` 取り込み時の議論）と同じ話。`hints=` は `X` 行と同じ側に置く、
という整理のためだけに移す。

### Q13. 値の符号化（dataflow 側だけの規則）

dataflow 側は「長さも中身も選べない文字列をそのまま持つ」のが目的なので、
analysis 側の `clean`（タブ・改行を空白へ置き換えて捨てる）ではなく、
バックスラッシュ・エスケープで符号化する（`CacheFormat.escape` / `unescape`）。

```
\      ->  \\        タブ  ->  \t        LF  ->  \n        CR  ->  \r
その他の制御文字（U+0000〜U+001F と U+007F）  ->  \uXXXX
```

パーセント符号化（`%09`）と、制御文字への写像も検討した。バックスラッシュを選んだのは、
`\n` が Java 開発者に自明で、キャッシュを目で追えるしるべを保てるから。
`%` は書式文字列（`"%s"`）で頻出するので、二重化が必要な文字としては `\` と同程度に出てくる。

`Guard` が区切りに使う `U+0001`〜`U+0003` も「その他の制御文字」として符号化されるので、
ガードを dataflow 側へ移しても値と区切りが衝突しない。

`analysis-cache.tsv` 側の `clean` は**そのまま**。2 つのキャッシュで規則が違ってよいこと自体が、
分けたことで得られた自由度。

### Q18. K・R・X 行を dataflow 側へ移すとき、読み手はどう読むか

これらは<b>ブロックの対応を取る必要が無い</b>。集約の鍵がブロックではなく、
メソッド（`R`）・証拠の鍵（`X`）・宣言している型と名前（`K`）だからである。
そのため `analysis` 側との「歩調を合わせた読み」は要らず、独立した 1 回の走査で読める。

| 行 | 読み手 | 読み方 |
|---|---|---|
| `R` | `CallGraphBuilder`（戻り値の出所） | dataflow 側を 1 回走査（`readValues`）。メソッドごとに集約 |
| `X` | `CallGraphBuilder`（フェーズAの証拠） | 同じ走査で。`呼び出し元キー｜スコープキー` ごとに集約 |
| `K` | `CacheUpdater`（定数の連鎖） | パス1b の走査に相乗り。ブロックごとに指紋をまとめる |

`K` をパス1b に相乗りさせたのは、そこで既に dataflow 側の F 行を走査しているため
（ブロックの有無の突き合わせ。Q5）。走査を増やさずに済む。

<b>残るのは `C` / `U` 行の出所とガード、`J` 行（フィールドへの代入）。</b>
こちらは呼び出し箇所・ファイルごとの対応が要るので、
「2 つのファイルをブロック単位で歩調を合わせて読む」形が必要になる（次の段）。

### Q19. `dataflow.enabled=false` は何をしなくなったか

**dataflow 側のキャッシュを開かなくなった**（`CallGraphBuilder.build` に null を渡す）。
`test/demo` で比べると次のようになる。

| | `true`（既定） | `false` |
|---|---|---|
| `call-hierarchy.csv` の行数 | 205 | 162 |
| `DATAFLOW_*`（データフローで特定） | 18 件 | **0 件** |
| `REFLECTION` / `REFLECTION_INIT` | 9 件 | **0 件** |
| `SPRING_DI` / `SPRING_DI_QUALIFIER` | 3 件 | 3 件（注解は analysis 側なので効く） |

キャッシュは 2 つとも**書かれる**（フェーズ2 が analysis 側を読むため、また対の不変条件のため）。
変わるのは「読むか」だけ。

### Q15. 値グラフ（N 行）と結びつけ（P 行）

`analysis` 側の出所（`Origin`）は入れ子を1本の文字列に展開するので、深さ d・引数 k で
文字列が k^d に膨らむ。だから「実引数は1段」「レシーバは3段」という上限が**構造的に必要**だった。
`N` 行は 1 つの式を 1 ノードとして 1 回だけ書き、参照はノード番号で行うので、
大きさがソースの式の数に比例する（深さは関係しない）。結果、次の 4 つの上限が外れた。

| | analysis 側（残置） | dataflow 側（N 行） |
|---|---|---|
| 実引数の入れ子 | 1段のみ | **無制限** |
| レシーバの入れ子 | 3段まで | **無制限** |
| 文字列リテラル | 64文字以内で、かつ FQN か識別子の形 | **無制限**（SQL・ログ文言もそのまま） |
| 定数の値 | 64文字以内で、制御文字を含まない | **無制限**（制御文字は符号化） |

`test/incremental` の実例。`Log.write("SELECT …\n" + "\tFROM orders" + …)` と
`Log.write(String.valueOf(Factory.create(Names.DAO)))` から出る行。

```
N  1  L  SELECT id, name, kind, created_at\n\tFROM orders\n\tWHERE kind = ? AND created_at > ?\n\tORDER BY id DESC
N  2  L  inc.AlphaDao
N  3  M  inc.Factory#create(java.lang.String)              0=2  1
N  4  M  java.lang.String#valueOf(java.lang.Object)        0=3  1
P  28  inc  inc.Awkward  longLiteral    write  0  -1  0=1
P  39  inc  inc.Awkward  nestedArgs     write  0  -1  0=4
```

1 行目の SQL は analysis 側では**丸ごと捨てられていた**値（64文字超で、FQN の形でもない）。
`N 3` / `N 4` は実引数の入れ子が 2 段あり、analysis 側では `create` の引数が見えなかった。

**リフレクションの扱いが変わる。** analysis 側は
`Class.forName(…).getMethod(…).invoke(…)` を `C:` という専用の種別に畳んでいたが、
`N` 行は連鎖をそのままの構造（`M` ノードのレシーバの鎖）で持つ。畳まずに持つほうが素直で、
読み手が辿れる範囲も広い。

**同じ構造のノードは 1 つにまとめる**（`ValueNode.dedupeKey`）。番号は AST を辿った順に振るので
同じソースなら同じ番号になり、出力の決定性を崩さない。

### Q16. なぜ 2 つの表現を同時に書くのか

読み手（`DataflowResolver` / `GuardEvaluator`）を値グラフへ移すのは次の段（2c）にした。
この段では**出力を 1 行も変えない**ことを保証したいので、
`analysis` 側の出所はそのまま残し、`dataflow` 側に値グラフを並走させている。
回帰テストの期待値がすべてそのまま通ることが、その保証になる。

2 つの表現が別々の判断から出ないよう、**同じ式から一度に作る**
（`OriginTracker.valuesOf` が両方を返す）。葉のうち変数・フィールド・引数の判定は
`OriginTracker` の結果をそのまま使い、同じ判断を 2 か所に書かない。

### Q20. 出所とガードを移したあと、読み手はどう結びつけるか

2c-2a で `C` 行・`U` 行から `recvKey` / `recvOrigin` / `argOrigins` / `guard` を落とし、
`J` 行も `dataflow` 側へ移した。これで **`analysis` 側だけを読むと具象クラスの解決は CHA 止まり**になる
（呼び出しが消えることはない）。読み手は 2 つのキャッシュを**歩調を合わせて**読む。

`DataflowBlockReader` が `dataflow` 側を**ブロック単位で前へ読み進めるだけ**の形で開き、
`analysis` 側の `F` 行に出会うたびに同じパスのブロックへ進む。2 つは常に同じブロックを同じ順で持つ
（Q2 の不変条件）ので、前へ進むだけで対応が取れる。ヒープに載るのは 1 ブロック分だけで、
「キャッシュ全体をヒープに載せない」という既存の作りを崩さない。

`P` 行は `C` 行・`U` 行と**同じブロックの中で同じ順**に書いているので、位置で突き合わせる。
ただし位置だけに頼ると並びを変えた瞬間に静かにずれるので、突き合わせた `P` 行の自己記述の鍵
（行番号・呼び出し元・呼び出し先の表示名）と**通し番号**が一致することを毎回確かめ、食い違えば
その呼び出し箇所は値なし（CHA 止まり）として扱い、1 度だけ警告を出す。通し番号は読み手側でも
書き手と同じく「同じ鍵をこのブロックで何本見たか」で数える。`f(g(), g())` のように同じ鍵が
並ぶ箇所は位置だけの対応が最も弱いので、そこを通し番号で補強している。
`U` 行は候補が無ければ読み飛ばすが、**読み飛ばす行でも位置は 1 つ進める**（進めないとずれる）。

`J` 行だけは順番に注意が要る。フィールドへの代入は同じブロックの `V` 行（`analysis` 側の
フィールド宣言）が揃ってからでないと拾われないので、ブロックの先頭で読んだ `J` 行は溜めておき、
ブロックを読み終えた時点（次の `F` 行、または最終行）で渡す。
先に渡すと宣言が未登録で捨てられ、コンストラクタ注入の解決（`DATAFLOW_FIELD`）が静かに消える。

### Q21. 上限はどう外したか。何が変わったか

2c-2b で、読み手が受け取る出所を**値グラフ（N 行）から組み直す**形にした。
`jche.graph.OriginRenderer` が、`P` 行の `recv` / `args`（ノード番号）と同じブロックの `N` 行から
`Origin` の文字列を作る。これで**読み手を1つも書き換えずに上限だけが外れる**。

`Origin` の文法はもともと入れ子を `{}` で囲めるので、段数に制約が無い。
上限は文法の都合ではなく、**文字列が深さ d・引数 k で k^d に膨らむこと**から来ていた。
値グラフは 1 つの式を 1 ノードとして 1 回だけ持ち、参照はノード番号で行うので、そこが外れる。

| 上限 | 旧 | 新 |
|---|---|---|
| 実引数の入れ子 | 1段（`Origin.head` で剥がす） | 無制限 |
| レシーバの入れ子 | 3段（`MAX_RECEIVER_DEPTH`） | 無制限 |
| 文字列リテラル | 64文字以内で、かつ FQN か識別子の形 | 無制限 |
| 定数の値 | 64文字以内で、かつ制御文字を含まない | 無制限（符号化して持つ） |

#### 出力がどう変わったか

`test/demo/src/fx/deep/` を足して確かめた。**旧の列（上限付き）を読ませた場合と読み比べて**、
どれが上限のせいで追えていなかったのかを確定させた。

| 形 | 旧 | 新 |
|---|---|---|
| 実引数の入れ子。`use(DaoFactory.byName("fx.dao.OrderDaoImpl"))` | 引数の出所が1段で剥がされ、`byName` に渡したクラス名が消えるので CHA 止まり | `解決:DATAFLOW_PARAM` で `OrderDaoImpl.describe()` に確定 |
| 64文字を超えるクラス名。`Class.forName("fx.deep.longnamed.AnExtremely…")`（72文字） | 文字列が落ちるので解決なし | `解決:REFLECTION` で確定 |

既存の経路は 1 行も変わっていない。差分は `fx.deep` の追加分と、
それが既存メソッドを呼ぶことによる被参照数の増加だけ。

#### レシーバの段数と定数の絞りは、出力の差として出せなかった

正直に書くと、この 2 つは**実装では外れているが、出力が変わる題材を作れていない**。

レシーバの段数は、解決に効く情報が 3 段以内に収まるのが実際のところだから
（`invoke ← getMethod ← forName/getClass` で 3 段。もともとその形を数えて 3 にしてある）。
4 段の連鎖（`invoke ← getMethod ← getClass ← get`）を `fx.deep.Deep.deepReceiver` に置いたが、
これは旧の上限でも解決できる。上限を外したのは保険で、今のところ得はしていない。

定数の絞り（64文字・制御文字）は、キャッシュに値が入っていることは
`test/incremental` の `check_unbounded_values` で見ているが、
それが分岐の枝刈りの結論を変える題材は作っていない。

#### 途中で直したもの

読み手を移して初めて表に出た穴が 3 つあった。どれも「入れ子が来ない」前提に頼っていた箇所。

| 穴 | 直し方 |
|---|---|
| `StreamingTreeWalker.resolveArgs` が実引数リストを素の `split(";")` で分け、`{}` も外していなかった。入れ子が来た瞬間に要素が壊れる | `Origin.entriesOf`（入れ子の外の `;` だけで分ける）と `Origin.unnest` を足して、必ずそこを通す |
| 値グラフの葉が、ローカル変数の出所を `Origin.head` で頭だけにしていた。`Class.forName(NAME)` を受けた変数からクラス名が辿れず、**リフレクションの解決が消えた** | `OriginTracker` の変数の表にノード番号も持たせ（`Scope`）、ローカル変数は代入元のノードを直に指す。外側のメソッドから捕捉した変数は従来どおり頭だけ（`frameIndependent` と同じ理由） |
| 呼び出しの形になっていないノード（`argCount` が -1）にも `n=-1` を付けていた | 数が分からないのだから付けない |

`Class.forName(x).newInstance()` 系の認識（連鎖ではなく「生成される型」を持つ）は
`OriginTracker` 側の判断のままにして、`ValueGraph` から同じものを呼んでいる。
2 か所で違う判断をしないため。読み手へ移すのはこの段の範囲外。

### Q22. 使われなくなった列はどう落としたか

2c-2b で読み手が値グラフへ移ったので、`P` 行の `recvOrigin` / `argOrigins`（上限付きの
出所の文字列）は誰も読まなくなった。2c-3 でこの 2 列と、それを作っていた
`OriginTracker.valuesOf` の処理を落とした。

**出力が 1 行も変わらないことが、そのまま「本当にどこも読んでいない」証明になる。**
回帰テストの期待値を一切触らずに全件通した。読み手がまだ使っていたら、
2c-2b で消えた解決（`DATAFLOW_PARAM` や `REFLECTION`）と同じ形で差分が出る。

`Origin` の文字列を作る仕組みそのものは残っている。`R` 行（戻り値の出所）・`J` 行（フィールドへの
代入）・`X` 行（拡張の証拠）はまだ文字列で持っており、値グラフの葉の判定にも使うため
（`docs/cache-split-qa.md` の Q21 の「直したもの」）。落としたのは
**呼び出し箇所ごとに二重に持っていたぶん**だけ。

#### 版を上げ忘れていたのを直した

2c-2a で `C` 行・`U` 行の列を変え、`J` 行を移したのに、`VERSION` と `DATAFLOW_VERSION` を
上げていなかった。古いキャッシュが互換とみなされ、`C` 行の列がずれたまま
（`recvKey` を `recvKind` として、`recvKind` を `lambdaDepth` として）読まれる状態だった。
ここで `jche-cache-v18` -> `v19`、`jche-dataflow-v3` -> `v4` に上げた。
**列を変えたら版を上げる**、が抜けると、壊れ方が「エラー」ではなく「静かに違う結果」になる。

同じ抜けを次は検査で捕まえられるよう、`test/incremental` に「形式の版が古いキャッシュ」の
ケースを 2 つ足した（analysis 側・dataflow 側それぞれ）。ヘッダの版だけを書き換えて、
再利用せず捨てることを見る。

## テスト

### Q10. 整合の仕組みをどう検査したか

回帰テストに `cachesplit` ケースを足した。同じソースを 6 回解析し、間でキャッシュを壊し方を変えて壊す。

| 回 | 壊し方 | 期待 |
|---|---|---|
| 1 | なし（キャッシュ無し） | 出力が期待値と一致し、2 つの F 行が一致 |
| 2 | なし | 全件再利用 |
| 3 | dataflow を消す | **両方**作り直し（再利用 0） |
| 4 | dataflow の `gen=` を書き換える | **両方**作り直し（再利用 0） |
| 5 | dataflow から 1 ブロックだけ消す | そのファイルだけ解析し直し、他は再利用。F 行が再び一致 |
| 6 | なし | 全件再利用に戻る |

どの回のあとも「2 つのキャッシュの F 行が完全に一致すること」を検査する。これが不変条件（Q2）で、
ここが崩れると片方だけ新しいブロックが生まれる。

`test/incremental/run.sh`（キャッシュの健全性の検査）にも次を足した。
こちらは期待値を持たず「差分更新の結果 == 全件解析の結果」を見るので、分割で事実が落ちれば捕まる。

- dataflow 側のキャッシュも、差分更新と全件解析で一致すること
- どのケースでも 2 つのキャッシュの F 行が一致すること（`check_paired`）
- dataflow 側の行種別が F / A / K / N / P / R / X / Z だけであること（`check_flow_rows`）
- 中断の再現（`make_partial`）で一時ファイルを 2 つ作ること。本物の中断では両方の `.tmp` が残るため

比較からはヘッダの世代の印（`gen=`）を外す。実行ごとに変わる値で、事実ではないため
（外さないと「差分更新と全件解析でキャッシュが違う」と誤検出する）。

5 の回で「そのファイルだけ」でなく依存先のファイルも解析し直すのは、解析し直したファイルが宣言する型を
「変わった型」に入れる既存の仕組み（改名・追加に備えるため）によるもので、想定どおりの挙動。

### Q23. 対の判定でキャッシュ全体を読まないようにした

対になっているかの判定は**毎回の実行で走る**。最終行（`Z` 行のブロック数）を取るのに
先頭から 1 行ずつ読んでいたので、2 つのキャッシュそれぞれにフルスキャンが 1 本ずつ増えていた。
数万ファイル規模ではキャッシュが数百MBになるので、`CacheReader.lastLineOf` で
**末尾の 512 バイトだけ**を読む形に変えた。

`Z` 行は `Z<TAB>ブロック数` なので、512 バイトに収まらないことはない。収まらなければ null を返し、
呼び出し側の「最終行が `Z` 行でなければ対でない」という判定と同じ結論になる。改行の手前を探して
そこから復号するので、窓の先頭が多バイト文字の途中に落ちても壊れない（UTF-8 では 0x0A が
継続バイトに現れないため）。書き出しは `BufferedWriter.newLine()` なので Windows では CRLF になり、
そこも両方扱う。

あわせて、世代の印を取るために analysis 側を開き直していたのをやめた（ヘッダを読むのは
1 行だけなので速さの問題ではないが、パス0 で L 行・T 行を読むついでに取れる）。

#### 「壊れているのに気づく場所」が動くことに注意

先頭から読むのをやめると、**文字化けに気づく場所がパス0 から後ろへ動く。** 以前はパス0 で
ファイル全体を読んでいたため、どこが壊れていても `MalformedInputException` がそこで出て、
「読めないので破棄」に倒れていた。末尾だけを読むようにすると、パス0 は壊れた場所を通らない
（ヘッダの読み取りは先頭のバッファぶん、最終行の読み取りは末尾の 512 バイトだけ）。

そのため `dataflow` 側を最初に丸ごと読む**パス1b が、壊れていることに気づく最初の場所**になる。
ここは例外を投げていなかったので、最初の実装では**キャッシュ 1 つが壊れているだけで解析ごと
失敗する**ようになってしまった（終了コード 1）。パス1b でも受け止めて両方を破棄するようにした。
「落ちないこと > 完全であること」の優先順位（`docs/README.md` の設計方針）に反する退行だった。

検査は `test/regression/cachesplit` に置いた（`test/incremental` では**届かない**）。
`test/incremental` の `dataflow` キャッシュは 5.6KB しかなく、`BufferedReader` の最初のバッファ充填
（8192 文字）に全体が収まるので、どこを壊してもパス0 で捕まってしまう。`test/demo` を解析する
`cachesplit` なら 40KB あるので、**最終行の直前**を壊せばパス0 を素通りしてパス1b に届く。
意図的に例外を伝播させると、このケースだけが落ちることも確かめた。

#### 境界はバイト単位なので、機械的に潰した

`test/cachetail/run.sh` を足した。改行で終わる／終わらない、CRLF、1 行だけ、空ファイル、
末尾に空行が続く形、読む量の境目（511・512・513 バイト）、多バイト文字が窓の先頭で切れる形、
窓に収まらない長さの行。あわせて「**先頭から読んで得た最後の非空行と一致する**」ことも見る
（置き換え前と同じ答えになること）。28 通り。

意図的に壊して落ちることも確かめた。「CR を落とさない」「長すぎる行を null にしない」
「改行を探さず窓の先頭から復号する」のどれも検出する。

`test/regression/cachesplit` にも 2 つ足した。**最終行のブロック数だけを書き換えた形**と
**最終行を消した形**で、どちらも両方のキャッシュを作り直すこと。世代の印は合っているので、
ブロック数の突き合わせだけが気づける形になっている（これまでこの経路を通る検査が無かった）。

### Q14. 値の符号化はどう検査したか

`test/cachevalue/run.sh` を足した。見る性質は 2 つだけ。

| 性質 | 内容 |
|---|---|
| 往復 | `unescape(escape(s))` が `s` に戻る |
| 無害化 | `escape(s)` にタブ・改行・制御文字が残らない（行が割れない） |

対象は、ソースに実際に現れる形（SQL、書式文字列、Windows のパス、正規表現）と、
そこには出てこないが形式を壊しうる形（**BMP の全文字**、バックスラッシュの連なり、
`\u0041` のように符号化の形をした文字列、途中で切れた符号、サロゲートペア）。
合わせて 126,998 通り。行に組み込んでも（`joinRow` を通しても）値が変わらないことも見る。

意図的に壊して落ちることも確かめた。「`\` を二重化しない」→ 往復しない、
「制御文字を素通しする」→ 無害化されない、のどちらも検出する。

### Q15b. 値グラフはどう検査したか

`test/incremental/run.sh` に 2 つ足した。どちらもケースごとに走る。

| 検査 | 内容 |
|---|---|
| `check_flow_rows` | 行種別が F / A / J / K / N / P / R / X / Z だけであること。**ノード番号がブロックごとに 0 から詰まっていること**、レシーバ・実引数の参照が同じブロックの範囲に収まっていること。番号はブロック内ローカルなので、ここが崩れると差分更新でブロックを書き写した瞬間に参照がずれる |
| `check_unbounded_values` | 64 文字を超える `L` ノードが実際にあること、タブ・改行が符号化されて 1 行に収まっていること。**「分けたのに上限が外れていない」状態を見逃さないため** |

既存の「差分更新の結果 == 全件解析の結果」も dataflow 側のキャッシュに対して効いているので、
ノードの番号づけが解析の順に依存していれば（＝差分更新と全件解析で違えば）そこで落ちる。
検査用の題材として `test/incremental/src/inc/Awkward.java` に、64 文字超でタブ・改行を含む
SQL を実引数に渡す形と、実引数が 2 段入れ子になる形を足した。

2c-2a で 1 つ直した。「書き換えが事実に効いているか」（何も変わらない編集で比較が素通りするのを
防ぐ検査）が `analysis` 側だけを見ていたので、出所と `J` 行を移したあと、**値だけが変わる書き換え**
（定数の値、列挙定数の名前）で素通りしていた。2 つのキャッシュを合わせて見るようにした。
分けるときは「事実がどちらのファイルに移ったか」を検査側でも追う必要がある、という例。
