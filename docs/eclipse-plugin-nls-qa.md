# Eclipseプラグインの文言を英語・日本語で出し分ける — QA 一覧

> 使い方（入れ方・操作・設定・つまずきやすいところ）は
> [eclipse-plugin-usage.md](eclipse-plugin-usage.md) にまとめてある。

利用者からの指摘: 「私は Pleiades を使っています。使っていない人には英語で表示されるように
修正できますか？」

それまで画面の文言はソースに日本語で直接書いてあった。日本語の Eclipse を使っている人には
読めるが、それ以外の人にはまったく読めない。**既定を英語にし、Eclipse が日本語で動いているときだけ
日本語にする**形に変えた。訳した文言は 190 件（コードが出すもの）＋ 9 件（plugin.xml とバンドルの名前）。

| 変えたところ | 内容 |
|---|---|
| `eclipse-plugin/src-ui/jche/eclipse/Messages.java` | 文言を引くクラス（新規）。JDK の標準 API だけで書いてある |
| `.../jche/eclipse/messages.properties` | 英語（既定。どの言語でも必ず読む） |
| `.../jche/eclipse/messages_ja.properties` | 日本語（英語に重ねる） |
| `eclipse-plugin/plugin.properties` / `plugin_ja.properties` | plugin.xml とバンドルの名前（OSGi が読む） |
| `test/plugin-nls/run.sh` | 上の 6 点の検査（新規） |

---

### Q1. Pleiades を入れていれば日本語になるのではないか

ならない。Pleiades は **Eclipse 本体（と主要プラグイン）の文言を辞書で置き換える**仕組みで、
辞書に無い文字列はそのまま出る。このプラグインの文言は当然 Pleiades の辞書に無いので、
Pleiades を入れても入れなくても、ソースに書いた文字列がそのまま出ていた。

つまり「Pleiades 利用者向けに日本語で書く」という以前の作りは、
**Pleiades のおかげで日本語になっていたのではなく、最初から日本語しか無かった**だけである。
言語ごとのファイルを自分で持つしかない。

### Q2. なぜ既定を英語にしたのか。日本語のままではいけないのか

このツール自体は日本語圏の利用者を想定していて、ログもドキュメントも日本語である
（[AGENTS.md](../AGENTS.md) の「コードの決まり」）。それでも**画面だけは英語を既定にした**。

- Eclipse プラグインの作法は「既定は英語、訳は言語ごとのファイル」である。
  dropins に置いた jar が誰の Eclipse で動くかは配る側に決められない
- 日本語を既定にすると、英語の Eclipse を使う人には**読めない文字列が出る**。
  逆に英語を既定にしても、日本語の Eclipse を使う人は日本語で読める。損をする人が少ない
- 訳が足りない項目は英語のまま出る（英語に重ねる作りにしてある）。
  日本語を土台にしていたら、足りない項目が日本語で出てしまう

解析ログ・ドキュメント・解析本体（`src/`）の文言は日本語のままである（Q6）。

### Q3. `ResourceBundle` でも `org.eclipse.osgi.util.NLS` でもなく、自前で読んでいるのはなぜか

理由は 2 つある。どちらも「このプラグインの事情」であって、一般には NLS でよい。

1. **Java 8 では properties が ISO-8859-1 として読まれる。**
   `java.util.ResourceBundle` も `NLS` も、properties を ISO-8859-1 として読む
   （UTF-8 になるのは Java 9 から）。このプラグインは
   **Java 8 の Eclipse でも動かす**（`Bundle-RequiredExecutionEnvironment: JavaSE-1.8`）ので、
   日本語が丸ごと文字化けする。`\uXXXX` に変換して書く手もあるが、
   訳文が読めない・差分が読めない形になり、直すたびに変換が要る。
   自前で読めば**文字コードを UTF-8 に固定**でき、訳文はそのまま書ける
2. **`NLS` は `org.eclipse.osgi` に入っている。**
   文言は `jche.eclipse.server`（子プロセスとやりとりする層）からも使う。あそこは
   **Eclipse の API に触らない**ことになっていて、Eclipse 無しでコンパイル・実行できることを
   `test/plugin-client/run.sh` が検査している。Eclipse の API に依存させられない

そのため `Messages` は JDK の標準 API だけで書いてある。`jche.eclipse.server` が
`jche.eclipse.Messages` を参照するようになったが、参照先が JDK だけなので
「Eclipse に触らない層」は保たれている（検査もそのまま通る）。

### Q4. 差し込み（`{0}`）に `MessageFormat` を使わなかったのはなぜか

`MessageFormat` は `'` を引用符として解釈する。英語の文に `don't` と書くと、
そこから先の `{0}` が差し込まれなくなり、`'` も消える。**動かすまで気づけない壊れ方**で、
しかも壊れるのは英語の側（日本語に `'` はまず出てこない）なので、日本語で確かめている限り見つからない。

差し込みに要るのは「値をそのまま入れる」ことだけで、桁区切りや日付の書式は要らない。
`{数字}` を引数で置き換えるだけの 20 行を自分で書くことにした。`'` はただの `'` である。

差し込みの数が英語と日本語で食い違うと、値が出ない・`{0}` がそのまま出る。
これは `test/plugin-nls/run.sh` が両方のファイルを突き合わせて検出する。

### Q5. どの言語で表示するかを、何で決めているか

`osgi.nl` システムプロパティを先に見て、無ければ JVM の既定（OS の言語）にする。

`osgi.nl` には Eclipse の `-nl` 引数（や eclipse.ini の指定）が入る。
**OS の言語と Eclipse の言語は別に決められる**（英語の Windows で日本語の Eclipse を使う、
あるいはその逆）ので、Eclipse に合わせるほうが利用者の期待に合う。
Eclipse の外（検査プログラム）ではこの値が無いので、そこでは OS の言語に従う。

国と地域（`ja_JP`）は言語（`ja`）だけ見る。地域まで分ける訳を持つ予定が無く、
持つときになってから `messages_ja_JP.properties` を足せばよい。

### Q6. 訳していないものは何か

**解析本体（`src/`）が出す文言は日本語のまま**である。バナーの
「✖ 解析に失敗しました: …」の「…」の部分（設定の誤りなど、子プロセスから返ってくる理由）が
これにあたる。前半は訳されるが、後半は日本語で出る。

ここを訳すのは、プラグインの話ではなく**ツール全体を多言語にする**という別の決断になる。
CLI・対話モード・ログ・出力 CSV の注記まで一式が対象で、量も桁が違う。
このプラグインの画面を英語にすることとは切り離した。

解析ログ（`analysis-*.log`）とコンソールの行も、解析本体のログがそのまま流れるので日本語である。
ここは利用者に読ませるものというより、うまくいかないときに開発者へ送ってもらうものなので、
優先度を下げた。

### Q7. 文言の置き場所が 2 つに分かれているのはなぜか

読む側が別だからである。

| ファイル | 読む側 | 何の文言か |
|---|---|---|
| `jche/eclipse/messages*.properties` | `Messages`（このプラグインのコード） | ボタン・バナー・ダイアログ・エラー |
| `plugin*.properties`（バンドルの直下） | OSGi のフレームワーク | ビュー名、メニューの見出し、コマンド名、バンドルの名前 |

plugin.xml の `name` / `label` は Eclipse が起動時に読むもので、プラグインのコードは動いていない。
だから `%キー` と書いて OSGi に解決させる（MANIFEST.MF の `Bundle-Localization: plugin` が
その置き場所を指す）。逆に、コードが出す文言を OSGi に読ませることはできない。

分かれてはいるが、どちらも「無いキーを使っている」「片方にしか無い」は
`test/plugin-nls/run.sh` が検出する。

### Q8. 訳し忘れ・消し忘れをどう防ぐか

`test/plugin-nls/run.sh` が 6 つ見ている。いずれも**動かしてみるまで気づけない**壊れ方である。

1. ソースに日本語の文字列リテラルが残っていないこと
   （1 件残ると、その行だけ英語の利用者に日本語が出る）
2. 使っているキーが英語のファイルにあり、使っていないキーが残っていないこと
   （前者は画面に `!キー名!` が出る）
3. 英語と日本語でキーがそろい、差し込みの数も同じこと
4. plugin.xml / MANIFEST.MF の `%キー` が両方のファイルにあること
   （足りないとビュー名が `%view.name` のまま出る）
5. 配布物（`build.properties` と `pom.xml`）に文言のファイルが入ること
   （抜けると全部 `!キー名!` になる）
6. 実際に読ませて、`osgi.nl` で切り替わり、UTF-8 として読めること

6 が要るのは、Java 8 の文字コードの罠（Q3）が**コンパイルでは出ない**ためである。
ここだけは実際に `-Dosgi.nl=ja` で動かして、日本語が正しく出ることを見ている。

### Q9. 文言のファイルが読めなかったらどうなるか

画面に `!キー名!` が出る。**例外にはしない。**

読めないのはバンドルの組み立てを間違えたときで（検査は上の 5）、そのときに
プラグインごと動かなくなるのは割に合わない。文言が出ないだけなら、ボタンは押せるし解析も走る。
ログや設定ファイルの読み書きと同じ「その機能のために本体を止めない」という扱いにそろえてある。
