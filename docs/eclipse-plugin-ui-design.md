# Eclipseプラグイン UI 設計案 — 呼び出し元階層ビュー

[Issue #49](https://github.com/instreest/java-call-hierarchy-exporter/issues/49) の続き。
現状のプラグイン（[eclipse-plugin-qa.md](eclipse-plugin-qa.md)）は「設定ファイルを右クリック → CSV を書く」だけで、
Eclipse 上では結果を見られない。ここでは次の段階として、

- 解析結果（呼び出しグラフ）をプラグインが**裏で持ち続ける**
- UI はその場でフィルタして**呼び出し元の階層**を見せる
- 解析は**非同期**で、他の操作をロックしない
- ソースを変えたら「**再解析が必要**」と分かる

という UI と、その裏側の設計をまとめる。

> **方針変更（実施済み・2026-09-12）**: 解析を Eclipse の中で行う前提を見直し、
> **別プロセス（別 JDK・同梱の JDT）で解析し、プラグインは表示だけを受け持つ**形に作り替えた。
> 設計と実装は [out-of-process-analysis-design.md](out-of-process-analysis-design.md)。
>
> **この文書の読み方**: 画面の作り（§1 画面構成、§2 状態の見せ方、§6 フィルタ、§7 操作、
> §9 あえて採らない案）はそのまま今の実装である。一方、裏側の説明（§3 スナップショット、
> §4 非同期解析、§5 変更検知、§8 既存コードに要る変更）は「Eclipse の中に解析結果を持つ」
> 前提で書かれており、**今は次のように置き換わっている**。
>
> | この文書の記述 | 現在 |
> |---|---|
> | プラグインがスナップショットを常駐で持つ（§3） | **子プロセス**が持つ。プラグインは `TREE` で問い合わせる |
> | 解析は Eclipse の Job（§4） | Job は「子プロセスへ `ANALYZE` を投げて待つ」だけ。解析そのものは別プロセス |
> | フィルタはビューが適用（§6） | 条件を子プロセスへ渡し、切り出した行を受け取る（体感は同じで、解析は起こらない） |
> | 転置索引やフェーズ分割の改修（§8） | 実装済み。いずれも子プロセス側（`jche.graph` / `jche.server`） |
>
> 変更検知（§5）とアイコン・バナーの3段階表示（§2）はそのまま生きている。
>
> **実装状況**（2026-09-09）: §1〜§8 と §10 の M1〜M3 は実装済み（`eclipse-plugin/src-ui/jche/eclipse/`）。
> 設計案から変えたのは 2 点で、いずれも [eclipse-plugin-ui-qa.md](eclipse-plugin-ui-qa.md) に理由がある。
> ・エディタの選択への追従とピン留め（📌）・履歴はやめた。呼び出し元の表示は明示のコマンドだけ（Q1）
> ・外部 jar からの被参照（⧉）はビューには出していない。CSV 出力では今までどおり出る（Q2）

**主ユースケース**: エディタでメソッドにカーソルを置き、そのメソッドの**呼び出し元**を階層で辿る。
以降の設計はすべてこの操作を最短にすることを優先し、呼び出し先方向・CSV 出力はその副産物として扱う。

## 1. 画面構成

ビューは 1 つだけ増やす（**「呼び出し階層 (Exporter)」**）。Eclipse 標準の「呼び出し階層」ビューとは
別物として並べる（相乗りしない理由は §9）。

```
┌ 呼び出し階層 (Exporter) ───────────────────────────────── ⇅ ⟳ ⏻ ▽ ⧉ ┐
│ ⚠ 12 ファイルが変更されています。表示は 10:31:04 時点のものです  [再解析] │ ← 状態バナー（§2）
├──────────────────────────────────────────────────────────────────────┤
│ 🔍 [ Order            ]  深さ:[5▾] 除外:[test ✕][java.** ✕] [+フィルタ]│ ← フィルタバー（§6）
├──────────────────────────────────────────────────────────────────────┤
│ ⬤ OrderService#save(Order)                       ← 選択したメソッド    │
│  ├ ⬤ OrderFacade#register(OrderForm)          OrderFacade.java:88     │
│  │   ├ ⬤ OrderController#post(..)             OrderController.java:41 │
│  │   │   └ ◇ (起点) 呼び出し元なし                                     │
│  │   └ ⚠ BatchJob#run()                       BatchJob.java:23        │ ← 解析後に変更されたファイル
│  ├ ⬤ OrderService#saveAll(List<Order>)        OrderService.java:120   │
│  │   └ ↻ OrderService#saveAll(..)（再帰）                              │
│  ├ ◈ ScheduledTask#execute()  «dataflow: FACTORY»                     │ ← 確度つきの解決（§6）
│  └ ⧉ order-batch.jar / com.example.Runner#main  «外部jarからの被参照»   │ ← 未実装（Q2）
│                                                                       │
│ 表示 27 件 / 全 143 件（フィルタで 116 件を非表示）                      │ ← 件数の説明
└──────────────────────────────────────────────────────────────────────┘
```

ツールバー（左から）:

| 記号 | 機能 | 備考 |
|---|---|---|
| ⇅ | 方向の切り替え（**呼び出し元** ⇄ 呼び出し先） | 既定は呼び出し元。同じ木を反対向きに辿るだけ |
| ⟳ | いま再解析する | 変更が無ければ「変更はありません」とバナーに出して何もしない |
| ⏻ | 自動再解析の ON/OFF | OFF なら変更を数えるだけで走らせない（§4） |
| ▽ | フィルタ設定を開く | フィルタバーに入りきらない項目（§6） |
| ⧉ | この木を CSV に出す | いま見えている（フィルタ後の）内容をそのまま書き出す |

行のアイコン:

| 記号 | 意味 |
|---|---|
| ⬤ | ソースがあるメソッド。ダブルクリックで**呼び出している行**を開く |
| ◈ | データフロー／リフレクションで特定した呼び出し元（確度は行末に理由を出す） |
| ⧉ | 外部 jar からの被参照（ソースが無い） |
| ↻ | 再帰。ここで打ち切って、元のノードへリンクする |
| ⚠ | このメソッドのファイルが、解析後に変更されている（内容が古い可能性がある） |
| ◇ | これ以上呼び出し元が無い（＝起点） |

## 2. 状態と、その見せ方

「解析が要る／いま走っている／結果が古い」を**バナー 1 行**に集約する。木は消さない。
古い結果でも見えているほうが役に立つので、**古い結果を出したまま裏で更新する**（stale-while-revalidate）。

| 状態 | バナー | 木の表示 | 操作 |
|---|---|---|---|
| 未解析 | 「このプロジェクトはまだ解析していません」 | 空。中央に説明と［解析する］ | 解析開始 |
| 解析中（初回） | 「解析中 フェーズ1/3 ソース解析 1,203/5,000 ファイル」＋進捗バー | 空。中央に「解析中です」 | ［中止］ |
| 解析中（2回目以降） | 同上（「更新中」） | **前回の結果を表示したまま**、バナーだけ動く | ［中止］ |
| 最新 | 「10:31:04 時点 / 5,000 ファイル / 143 呼び出し元」（数秒で薄く消す） | 通常 | — |
| 要再解析 | 「⚠ 12 ファイルが変更されています。表示は 10:31:04 時点のものです」 | 通常＋変更ファイルのノードに ⚠ | ［再解析］ |
| 失敗 | 「✖ 解析に失敗しました: (理由)」＋［ログを開く］ | 直前の結果があればそれを表示 | 再試行 |
| 対象外 | 「このプロジェクトには設定ファイルがありません」＋［作る］ | 空 | 設定の作成 |

バナーの色は Eclipse のテーマ色（`INFORMATION` / `WARNING` / `ERROR`）に従う。
同じ状態は**ビューのタイトルにも**出す（`呼び出し階層 (Exporter) — 更新中…`）。
ビューを閉じていても分かるよう、進捗は Eclipse 右下の進捗表示にも出す（`Job` なので自動）。

「見えているものが古い」ことは 3 段階で示す。バナー（全体）、⚠ アイコン（そのノード）、
ノードのツールチップ（「OrderFacade.java は 10:33:12 に変更されました。再解析すると変わる可能性があります」）。
**古いことを理由に木をグレーアウトはしない**。読めなくなるだけで、判断の役に立たないため。

## 3. 裏で持つデータ（スナップショット）

プラグインは解析済みプロジェクトごとに**不変のスナップショット**を 1 つ持つ。

```
GraphSnapshot（不変）
  ├ CallGraph        … CSR の呼び出しグラフ（既存 jche.graph.CallGraph）
  ├ CallResolver     … 具象クラスの解決（既存）
  ├ InboundIndex     … 呼び出し元を引くための転置 CSR（新規。§8-1）
  ├ analyzedAt       … このスナップショットを作った時刻
  └ fileStamps       … 解析したソースの一覧と更新時刻（⚠ 判定に使う）
```

- UI 側は `volatile GraphSnapshot current` を**読むだけ**。ロックを取らない。
- 解析ジョブは新しいスナップショットを**別インスタンスとして組み立て**、最後に参照を差し替える。
  作りかけのグラフが UI に見えることはない。
- 木を 1 回描く間は同じスナップショット参照を握り続ける。途中で差し替わっても、
  その木は最後まで一貫した内容のまま（差し替え後は「更新されました［表示を更新］」をバナーに出す）。
- メモリは常駐 1 プロジェクト分＋LRU。解放してもフェーズ1のキャッシュ（`.cache/`）は残るので、
  作り直しはフェーズ2だけ（数秒）で済む。

## 4. 非同期解析（他の処理をロックしない）

```
          ソース変更                     静止 or 手動
IResourceChangeListener ─► dirtyFiles ─────────────► AnalysisJob（ワーカースレッド）
   （UIスレッド。集合に足すだけ）           debounce      ├ フェーズ1 差分解析（変更＋依存先）
                                                        ├ フェーズ2 グラフ構築＋転置
                                                        └ current = 新しいスナップショット
                                                                    │
                                                          asyncExec ▼ ビューの再描画
```

守る規則:

1. **UI スレッドでは解析しない**。リスナがするのは「変更されたファイルのパスを集合に足す」ことだけ
   （数マイクロ秒）。解析は `org.eclipse.core.runtime.jobs.Job`。
2. **プロジェクト単位のスケジューリングルール**を持たせる。同じプロジェクトの解析ジョブは直列、
   別プロジェクトは並列。ワークスペースのロックは取らない（取ると保存やビルドが止まる）。
3. **自動再解析は `setUser(false)`**（右下で静かに進む）。手動の［再解析］だけ `setUser(true)`。
   どちらもモーダルにはしない。
4. **中止できる**。`IProgressMonitor` の取り消しをフェーズ1のファイルループとフェーズ2のスキャンに伝える
   （§8-2）。中止しても直前のスナップショットとキャッシュは壊れない。
5. **debounce**。変更のたびに走らせない。既定は「自動ビルド完了（`POST_BUILD`）から 3 秒静止したら開始」。
   タイピング中は走らない。［自動再解析 OFF］なら数えるだけ。
6. **差分解析**。フェーズ1は既存のキャッシュを使い、変更ファイルとその依存先だけを解析し直す
   （[cache-dependency-jars-qa.md](cache-dependency-jars-qa.md)）。1 ファイル直しただけなら数秒で終わる。
7. **フィルタ・展開は解析を待たない**。フィルタはスナップショットに対する読み取りだけなので、
   解析中でも古いスナップショットに対して即座に効く（§6）。

## 5. 変更の検知と「再解析が必要」の伝え方

- `IResourceChangeListener`（`POST_CHANGE`）で `*.java` の追加・変更・削除を拾い、`dirtyFiles` に入れる。
  対象は設定ファイルの `source.folders` 配下だけ（それ以外は無視）。
- `config.properties` 自身が変わったときは、差分ではなく**全体を作り直す**（除外パッケージ等が変わるため）。
- 依存 jar（`library.folders`）の変化も検知対象にする。既存のキャッシュ設計がそこまで見ている。
- 見せ方は §2 のとおり 3 段階（バナー／⚠ ／ツールチップ）。加えて、
  **エディタのマーカーは付けない**。ソースに黄色い印を増やしても邪魔なだけで、
  「古い」情報はビューの中で完結させる。

## 6. フィルタ

**フィルタは再解析を起こさない。** すべてスナップショットに対する読み取り時の絞り込みで、
変更した瞬間に木へ反映する。これが「解析は重いがフィルタは軽い」という体感を作る。

フィルタバー（常時表示）:

- 🔍 **絞り込み文字列** … 型名・メソッド名・パッケージの部分一致（`*`, `**` のワイルドカードは
  既存の `PackagePattern` と同じ書き方）。一致した部分は太字にし、
  「一致した子孫を持つ枝だけ残す」（親をたどれるようにするため、枝ごと隠さない）
- **深さ** … 既定 5。木の展開の上限。`config.properties` の `max.depth` とは独立
- **除外チップ** … クリックで外せる。初期値は設定ファイルの `exclude.packages`

フィルタ設定（▽ で開く）:

| 項目 | 既定 | 用途 |
|---|---|---|
| テストコードを含む | 含まない | ソースフォルダ単位（`src/test/java` 等）で切る。「本番から呼ばれているか」を見たいときに効く |
| 外部 jar からの被参照を含む | （未実装） | ⧉ の行。ライブラリとして使われている API を調べるとき |
| 未解決の呼び出しを含む | （未実装） | 型解決に失敗した呼び出し。設定漏れの調査用 |
| 解決の確度 | すべて | 静的束縛 / 単一実装 / データフロー / リフレクション（既存の `BindKind`・`Resolution` の区分）で絞る。「確実な呼び出し元だけ見たい」に応える |
| 呼び出し元が 1 件の枝を畳む | （未実装） | 中継だけのメソッドを飛ばして、意味のある分岐まで一気に見る |
| 同じメソッドを 1 回だけ出す | する | 同じ呼び出し元が複数行から呼んでいるときに木が膨らむのを防ぐ。OFF なら呼び出し行ごとに出す |

フィルタの状態はビューごとに保持し、ワークスペースに保存する（次回起動時も同じ）。
⧉（CSV 出力）は**いま見えている木をそのまま**書き出す。画面で絞ってから CSV にする、という流れになる。

## 7. 操作

| 操作 | 入口 |
|---|---|
| このメソッドの呼び出し元を見る | エディタで右クリック →「呼び出し元階層を表示 (Exporter)」／`Ctrl+Alt+H`／アウトライン・パッケージエクスプローラーの右クリック |
| 呼び出し箇所へ飛ぶ | 木のノードをダブルクリック → **呼び出している行**を開く（宣言ではない。`callLines` を使う） |
| 宣言へ飛ぶ | ノードで `F3` |
| 木の起点を差し替える | ノードを右クリック →「ここを起点にする」 |
| 方向を変える | ⇅（呼び出し元 ⇄ 呼び出し先） |
| 解析する／中止する | バナーのボタン、⟳ |

選択したメソッドがスナップショットに無いとき（新規メソッド・解析前）は、木のかわりに
「このメソッドは 10:31:04 時点の解析結果にありません。［再解析する］」を出す。
黙って空の木を出さない（「呼び出し元が無い」と読み違えるため）。

## 8. 既存コードに要る変更

小さい順に 4 つ。いずれも CLI の出力を変えない範囲でできる。

1. **転置 CSR（呼び出し元の索引）**
   現在の `CallGraph` は下流だけを持つ（クラスコメントに明記されている）。呼び出し元をたどるには
   「解決済みの呼び出し先 → 呼び出し元」の索引が要る。`CallResolver.resolve(edge)` が返す
   ターゲットに対して転置 CSR（`int[]` 2 本）を作る。すでに `CallResolver.inDegrees()` が
   同じ走査をしているので、その結果を捨てずに索引として残す形になる。
   メモリはエッジ数 × int 2 個で、既存のグラフと同じ桁。
   注意点として、インタフェース経由の呼び出しは「実装メソッドの呼び出し元」として見えなければ意味が無いので、
   転置は**解決後**（具象化した後）のエッジに対して作る。
2. **フェーズ1＋2 だけを実行して、グラフをメモリに返す API**
   いまの `Exporter.runOne` はフェーズ1→3 を通しで実行し、CSV を書いて捨てる。
   `AnalysisService.buildSnapshot(config, listener)` を切り出し、CSV 出力（フェーズ3）は
   その上に載せる。CLI 側は「スナップショットを作って CSV を書く」に置き換えるだけで挙動は変わらない。
3. **進捗と中止の受け口**
   `jche` 側を Eclipse に依存させたくないので、`jche.util` に小さなインタフェース
   （`onProgress(phase, done, total)` と `isCancelled()`）を足し、プラグインが `IProgressMonitor` を
   そこへ橋渡しする。既存の `jche.util.Progress` の置き換えでよい。
4. **JDT の `IMethod` からメソッドIDを引く**
   `MethodTable` のキーは `型FQN#メソッド名(引数型,…)`。JDT の `IMethod` からこの形の文字列を組み立てる
   （型変数・内部クラス・可変長引数の表記合わせが要る）。ここは取りこぼしが出やすいので、
   引けなかったときは「見つかりません」と明示する（§7）。

CSV 出力の経路（フェーズ3）はそのまま残す。ビューは「同じスナップショットの別の見せ方」であって、
CSV を置き換えるものではない。

## 9. あえて採らない案

- **Eclipse 標準の「呼び出し階層」ビューに相乗りする**（`org.eclipse.jdt.ui` の拡張点）。
  標準ビューはインデックス済みの JDT モデルを前提にしていて、こちらの「重い解析・古くなる結果」を
  表現する場所（バナーや ⚠）が無い。状態を出せないまま古い結果を見せるのが一番危ないので、別ビューにする。
- **毎回 CSV を書いて、それを読んで表示する**。実装は楽だが、フィルタのたびにファイル入出力が要り、
  「フィルタは軽い」という前提が崩れる。CSV は成果物として残すもので、UI のデータ源にはしない。
- **モーダルな進捗ダイアログ**。解析は分単位になりうる。その間 Eclipse が使えないのは論外。
- **保存のたびに即再解析**。差分解析でも数秒かかるので、タイピングのたびに走ると邪魔になる。
  ビルド後の静止を待つ（§4-5）。

## 10. 段階（この順に作った）

1. **M1** … スナップショットの常駐＋呼び出し元ツリー（フィルタは絞り込み文字列と深さだけ）。
   解析は手動（⟳）のみ。§8 の 1〜4 が要る
2. **M2** … 変更検知・自動再解析・バナー・⚠ の 3 段階表示。§4・§5
3. **M3** … フィルタ設定一式、方向の切り替え、履歴・ピン留め、見えている木の CSV 出力

## 11. 決めきれていない点（実装前に確認したい）

- 対象プロジェクトの設定ファイルをどう選ぶか。プロジェクト直下の `config.properties` を既定にし、
  複数あればビューで選ばせる案を採るつもりだが、プロジェクトごとの記憶をどこに置くかは未定
  （プロジェクトの永続プロパティか、プラグインの設定か）
- 巨大プロジェクトでのスナップショット常駐の上限。1 プロジェクト分でどれくらいのヒープを使うか、
  実測してから上限と LRU の段数を決めたい
- ラムダ・メソッド参照の呼び出し元をどう見せるか（`functionalImpls` があるメソッドは
