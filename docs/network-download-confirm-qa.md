# ネットワークからの取得の前に操作者の確認を必須にする — 実装時の QA 一覧

[Issue #86](https://github.com/instreest/java-call-hierarchy-exporter/issues/86)
「ネットワークにアクセスする場合に操作者の確認を必須としたい」の対応で、迷ったこと・困ったことと、その結論を
Q&A の形で残す。

対応の要点:

- 起動コマンド（`java-call-hierarchy-exporter.sh` / `.cmd`）が、JBang 本体・JDK・依存 jar をネットワークから
  取得する前に**必ず確認**するようにした。`n` なら何も取得せずに終了コード 3 で終わる。
  引数あり（対話なし。Issue #83）でもこの確認だけは出る
- 「取得が必要か」は、まず `jbang run --offline`（取得済みのものだけで動かす）で起動を試み、アプリが始まる前に
  失敗したかどうかで判定する（Q3）。アプリが始まったかは、アプリが置く目印ファイル `.cache/launcher.started` で見る。
  JBang 本体とそれを動かす JDK は `--offline` の外（ラッパースクリプト）で取得されるので、置き場所のファイルの
  有無を見て、無ければ起動を試みる前に確認する
- 端末が無いとき（パイプ・CI・タスクスケジューラ）は確認できないので取得せず、終了コード 3 で終わる。
  無人で動かす環境のために `launcher.properties` の `JCHE_ALLOW_DOWNLOAD`（`yes`: 尋ねずに取得 / `no`: 取得しない /
  空欄: 毎回尋ねる）を足し、対話モードの「環境設定」の 5) からも切り替えられるようにした
- 確認メッセージに**取得するものごとの目安サイズと合計**を出す（通信量 約 165MB / ディスク 約 485MB。
  手元に無いものだけを足す）。サイズをサーバーに問い合わせることはしない（それ自体がネットワークアクセスになる。Q15）
- jbang 自身の更新確認（起動のたびに新しい版があるかを問い合わせる）は `JBANG_NO_VERSION_CHECK=true` で止めた
- ラッパーが JBang を動かすために取得する JDK の版（`JBANG_DEFAULT_JAVA_VERSION`）を 25 にそろえ、
  ツールを動かす JDK 25 と別に JDK 17 まで取得することがないようにした（Q9）
- 確認の答えは標準入力ではなく端末（`/dev/tty`）から読む。端末の口が開いていても、その先に誰も居ないときは
  端末が無いのと同じ扱いにする（Q17。別実装のブランチから移した）
- Windows には `/dev/tty` に当たるものが無い（`CON` はコンソールが無い環境で永久に待つ）。`.cmd` は
  `choice` の `/t` と `/d` で待ちを打ち切り、時間切れなら取りやめに倒す（Q18）
- JBang 本体の判定はラッパーと同じく `bin/jbang.jar` と `bin/jbang` の両方を見る。片方でも欠ければ
  ラッパーは取りに行くので、jar だけを見ていると確認を飛ばしてしまう（Q19）
- Windows の `.cmd` で `%VAR:検索=置換%` の文字列置換を使わない。変数が未定義のとき cmd が展開しきれず、
  バッチごと落ちる（Q16。`test/cli/run.sh` が混入を検出する）
- `test/cli/run.sh` に「端末が無いときは取得しない」「`JCHE_ALLOW_DOWNLOAD=no` / `--offline` なら取得しない」
  「JBang はあるが依存 jar が無いときも取得しない」「環境設定で `JCHE_ALLOW_DOWNLOAD` を書き換えられる」の検査を足した

## 仕様

### Q1. 何をもって「ネットワークにアクセスする」としたか

このツールが動くまでに、ネットワークに出る箇所は次の 5 つ。解析そのものはネットワークに出ない
（依存 jar の自動取得もローカルリポジトリを探すだけ。[build-tool-classpath-qa.md](build-tool-classpath-qa.md) の Q2）。

| # | 何を | 誰が | どこから |
|---|---|---|---|
| a | JBang 本体（`jbang.tar` / `.zip`） | ラッパー `jbangw/jbang`（`.cmd` / `.ps1`） | github.com |
| b | JBang を動かす JDK（既定 17） | 同上（`JAVA_HOME` にも PATH にも javac が無いとき） | api.foojay.io |
| c | ツールを動かす JDK 25（`//JAVA 25`） | jbang | api.foojay.io |
| d | 依存 jar（`//DEPS` の JDT と、その推移的な依存） | jbang（Maven のリゾルバ） | Maven Central |
| e | jbang 自身の更新確認（新しい版があるか） | jbang（起動のたび） | github.com |

Issue の To be は「ネットワークアクセスが必要な場合は操作者の確認を必須とする」なので、a〜d のいずれかが起きる前に
1 回確認する（Q8）。e は「確認するほどのものではないが、黙って出るのも約束に反する」ので止めた（Q4）。

### Q2. 確認をどこに置いたか。Java の中で尋ねられないのか

起動コマンド（シェル / バッチ）側に置いた。Java のコード（`src/jche/Jche.java`）が動くのは c と d が済んだ後なので、
Java の中で「取得してよいか」を尋ねるのは鶏と卵になる（[cli-app-qa.md](cli-app-qa.md) の Q2 と同じ理由）。
Java 側がしているのは「アプリが始まった」目印を置くことだけ（`LauncherSettings.markStarted()`）。

`jbangw/` のラッパースクリプトは本家そのまま（[jbangw-readme-notice-qa.md](jbangw-readme-notice-qa.md)）で、
`test/jbangw/run.sh` が変更を検出するので、そこには手を入れていない。確認はラッパーを呼ぶ前後で行う。

### Q3. 「取得が必要か」をどう判定したか。事前にファイルの有無を見ればよいのでは

2 段構えにした。

1. **a と b**（ラッパーが取得するもの）は、ラッパーが見るのと同じ場所（`$JBANG_DIR/bin/jbang.jar`、`JAVA_HOME` /
   PATH の javac、`currentjdk`、`cache/jdks/<版>`）を起動コマンドが見て、無ければ起動を試みる前に確認する。
   ラッパーには `--offline` のような抑止がなく、呼んだ時点で取得が始まってしまうため
2. **c と d**（jbang が取得するもの）は、`jbang run --offline` で起動を試みて、アプリが始まる前に失敗したら確認する。
   `--offline` は「取得済みのものだけで動かし、足りなければ失敗する」jbang のオプションで、JDK も依存 jar も
   これで止まる（手元で確かめた: 空の置き場所では `No suitable JDK was found for requested version: 25` で止まる）

d を事前にファイルの有無で判定する案は捨てた。依存 jar は JDT の 1 行から POM を辿って推移的に決まるので、
シェルで一覧を持つと `//DEPS` や JDT の版が変わるたびに壊れる。Issue の Requirements にある
「依存モジュールの推移的確認においてもネットワークアクセスが必要なら確認する」は、jbang 自身に
判定させる（`--offline` で失敗させる）のがいちばん確実だと読んだ。

「アプリが始まる前に失敗した」の判定には、アプリが `main` の最初に置く目印ファイル `.cache/launcher.started` を使う。
起動コマンドは起動の前にこれを消し、終わった後に無ければ「jbang がアプリを始められなかった」とみなす。
終了コードだけでは「アプリが 1（解析の失敗）で終わった」のと「jbang が 1 で終わった」のを区別できないため。
目印は引数の検査より前に置く（知らないオプションで 2 を返すのもアプリの判断なので、取得の確認にしない）。

### Q4. Issue の「`--update`」をどう読んだか

このツールにも起動コマンドにも `--update` というオプションは無い。jbang 側の「更新」に当たるのは、

- jbang が起動のたびに行う更新確認（新しい版があると `[jbang] A new release of jbang is available` と出す）
- `jbang version --update`（jbang 自身を更新する）
- `jbang run --fresh`（依存 jar を取り直す）

の 3 つ。1 つ目は `JBANG_NO_VERSION_CHECK=true` を起動コマンドが常に付けて止めた。ツールの動作に関係なく、
ラッパーが取得するのは最新版なので、知らせを見ても利用者にできることが無い。2 つ目は起動コマンドから呼ばれない。
3 つ目は `JCHE_JBANG_OPTS` に書けるが、`--offline` と同時には指定できない（jbang が
`Options --offline and --fresh are mutually exclusive` で終了コード 2）ので、起動コマンドは `--fresh` を
「取り直す」という意思として扱い、`--offline` での起動を飛ばして先に確認する（Q8 の 1 回目の確認と同じ経路）。

### Q5. 端末が無いときに取得しないのはなぜか。CI では自動で取得するほうが便利では

Issue が「必須」と言っている以上、確認できないなら取得しない、が素直な読み方。CI やタスクスケジューラで
黙って取得するのは、これまでの「README で表明するだけ」と変わらない。

無人で動かす環境のために `JCHE_ALLOW_DOWNLOAD=yes` を用意した。これは「確認をあらかじめ済ませた」という
利用者の意思表示で、`launcher.properties` に書くか、環境変数で渡す。端末が無くて取得できずに終わるとき、
そのやり方を出力に書くので、初回に 1 度止まって設定すれば済む。終了コードは新しく 3 にした
（[cli-noninteractive-qa.md](cli-noninteractive-qa.md) の Q6 の 0 / 1 / 2 に続く番号。「解析したが失敗」でも
「呼び方の誤り」でもなく、バッチ側で「取得の許可が要る」と見分けられるようにするため）。

端末の判定は既存の初回の質問と同じ（bash は標準入力と標準出力の両方が端末、cmd は `timeout /t 0` が成功する）。
`| tee log` のように標準出力だけを流したときも「端末が無い」と扱う。確認の文言が画面に出ないまま入力待ちになるより、
はっきり止まるほうがよい。

### Q6. 確認の既定を `[y/N]`（Enter で取りやめ）にした理由

インストーラの慣習は `[Y/n]` だが、Issue の趣旨は「操作者が明示的に許可する」ことなので、Enter の空打ちで
数百 MB の取得が始まらないようにした。`y` / `yes`（大文字小文字は問わない）だけを許可とみなす。

### Q7. `JCHE_ALLOW_DOWNLOAD` の値と、`--offline` との関係

| 値 | 動き |
|---|---|
| 空欄（既定） | 取得の前に毎回尋ねる。端末が無ければ取得しない |
| `yes`（`y` / `true` / `1` も） | 尋ねずに取得する |
| `no`（`n` / `false` / `0` も） | 端末があっても取得しない（閉域ネットワーク向け） |

`JCHE_JBANG_OPTS` に `--offline` を書いた場合は `no` と同じ。`--offline` は起動コマンド自身が付けるので、
利用者の指定は「ネットワークに出ない」という意思として読み替える（jbang は同じオプションの重複を受け付けるが、
意思を汲むために取り除いている）。`.cmd` は `-o`（短い形）を見分けないので、Windows では `--offline` と書く。

`launcher.properties` の空欄は他のキーでは「環境変数を消す（既定に戻す）」だが、`JCHE_ALLOW_DOWNLOAD` だけは
空欄でも環境変数を消さない。「ふだんは毎回尋ねるが、今回だけ `JCHE_ALLOW_DOWNLOAD=yes ./java-call-hierarchy-exporter.sh …` で
通す」という使い方ができるようにするため。

### Q8. 確認は何回出るか

多くて 1 回。JBang 本体か JBang を動かす JDK が無いとき（初回）は、そのあと jbang が取得する JDK 25 と依存 jar も
まとめて 1 回で確認し、`--offline` を付けずに起動する。JBang はあるが JDK 25 か依存 jar が無いとき
（置き場所を変えた直後や、`//DEPS` の版を上げた直後）は、`--offline` の起動が失敗してから 1 回確認する。
どちらも「取得するもの」に該当するものを並べて出す（後者は jbang のエラーがその直前に出ているので、
「取得済みの JDK と依存 jar だけでは起動できませんでした（原因は上のメッセージ）」と添える）。

置き場所の質問（Issue #63 の初回の設定）とは別にした。置き場所は「どこに置くか」、確認は「取ってよいか」で、
引数ありのときは前者を尋ねず後者だけ尋ねるため。置き場所の質問の末尾に「取得そのものは、このあと
ネットワークに出る前にもう一度確認する」と 1 行足して、続けて聞かれても驚かないようにした。

### Q9. `JBANG_DEFAULT_JAVA_VERSION` を 25 にしたのはなぜか

ラッパーは、`JAVA_HOME` にも PATH にも javac が無い環境では「jbang を動かすための JDK」を取得する。
その版の既定は 17 で、そのあと jbang がツールのために JDK 25 を取得するので、まっさらな環境では JDK が 2 つ
（17 と 25）取得されていた。確認の文言に「取得するもの」を書く以上、要らないものを取らせたくないので、
起動コマンドが `JBANG_DEFAULT_JAVA_VERSION=25`（利用者が設定していなければ）を渡すようにした。
jbang は取得した JDK を `cache/jdks/25` に置き、ツールの `//JAVA 25` もそこを使うので、1 つで済む。
版は `.sh` が `src/jche/Jche.java` の `//JAVA` から読む。定数で持つとソース側を上げたときに黙ってずれ、
ラッパーとツールで別々の JDK を取ってしまう。`.cmd` は定数のままで（cmd でのファイル読み取りは Windows でしか
検証できず、壊すと気づきにくい）、`test/cli/run.sh` が `//JAVA` との一致を検査する。
手元でまっさらな置き場所に対して `y` で通したところ、`cache/jdks` にできたのは 25 だけで、
JBang 本体・JDK・依存 jar の合計は約 500 MB だった。

### Q10. `--offline` で起動できなかった原因が取得以外（コンパイルエラー等）でも確認が出てしまう

出る。目印ファイルが無い理由を起動コマンドは区別できない。取得しても直らないので、`y` と答えると同じエラーが
もう一度出るだけになる。jbang のエラーメッセージの文言で見分ける案は、ラッパーが取得するのが最新版の jbang で
文言が変わりうるのでやめた。確認の直前に「原因は上のメッセージ」と添えて、読めば分かるようにするにとどめた。
ソースを編集するのは開発者だけで、その場合は jbang のエラーを直接読むはず。

### Q11. 目印ファイルが書けなかったら

`.cache/` が作れない（権限が無い等）と目印が置けず、アプリが正常に終わっても「始められなかった」とみなして
確認が出る（端末があれば尋ね、`y` ならもう一度アプリが動いて二重に解析する）。ただし `.cache/` は解析キャッシュの
置き場所でもあり、作れなければ解析自体が失敗するので、実害はほぼ無い。目印を置く処理は例外を握りつぶして
アプリを続ける（目印のためにアプリを止めない）。

### Q12. Windows（`.cmd`）で終了コードを見ないのはなぜか

`jbangw\jbang.cmd`（本家そのまま）は jbang の終了コードを呼び出し元へ返さない既知の問題があり
（`smoke.yml` の「known to fail」、[jbangw/README.md](../jbangw/README.md)）、常に 0 になる。
bash 版は「終了コード 0 なら成功、それ以外で目印が無ければ確認」とできるが、`.cmd` では終了コードを見ると
オフラインの失敗を成功と誤認するので、目印ファイルの有無だけで判定する。

### Q13. `jbangw/jbang` の直接実行と GitHub Actions を対象外にした理由

- `./jbangw/jbang src/jche/CallHierarchyExporter.java …`（README の「JBangによる実行」）は、JBang の作法そのもので
  動かす経路で、起動コマンドを通らない。ラッパーは本家のままにしているので（Q2）確認は入れられない。
  README とラッパーの README に「確認なしで取得する。確認してほしければ起動コマンドを使う」と明記した
- `action.yml`（GitHub Actions）は `.github/action/run.sh` がラッパーを直接呼ぶ。CI に操作者はおらず、
  ワークフローに `uses:` を書いた人が取得を承知しているとみなす。`java-version` 入力の `setup-java` も
  ネットワークから JDK を取るので、そこだけ確認しても意味が無い

### Q14. 依存キャッシュがあると `JBANG_REPO` が空でもオフラインで動く

テストを書いていて気づいた。jbang は解決した依存 jar のパスを `$JBANG_DIR/cache/dependency_cache.json` に
覚えていて、次回はローカルリポジトリを見ずにそのパスを使う。そのため `JBANG_REPO` を空のフォルダに向けても、
別の場所にある jar が指されていれば `--offline` で起動できる。ネットワークに出ていないので判定としては正しい。
「依存 jar が無い」経路の検査は、JBang をコピーした**新しい置き場所**（依存キャッシュも JDK も無い）と
空のリポジトリで行う（Q16）。

### Q15. 取得予定のサイズをどう出すか。サーバーに問い合わせて正確な値を出せないか

**実測しておいた目安を、取得するものごとに出す**。サーバーへの問い合わせはしない。

確認の直前に `HEAD` を投げれば `Content-Length` は取れる（確かめた: JBang 本体 14,940,160 バイト、
Temurin 25 の linux x64 tar.gz 141,329,719 バイト、windows x64 zip 141,167,264 バイト）。それでもやらない理由は、

- **サイズを知ることがすでにネットワークアクセス**。「出てよいか」を尋ねる前に相手先へ接続して
  こちらの存在を知らせることになる。この Issue が守ろうとしているものを、確認の実装自体が破ってしまう
- 閉域ネットワークでは問い合わせが失敗するか、応答を待って固まる。取得しないと決めている人ほど待たされる
- 依存 jar は推移的な依存まで数えないと総量が出ない（Q3）。それを起動コマンドの側で数えるのは無理筋

そこで、次の実測値を起動コマンドの中に定数として持ち、「約」を付けて出す。取得するものごとに書き、
手元に無いものだけを足して合計する（JBang 本体があるなら、その分は合計に入らない）。

| 取得するもの | 通信量 | 置き場所が増える量 |
|---|---:|---:|
| JBang 本体 | 約 15MB | 約 30MB（展開した `bin/` と、`cache/urls/` に残るアーカイブ） |
| ツールを動かす JDK 25 | 約 135MB | 約 440MB（展開後 約 300MB + アーカイブ 約 135MB） |
| 依存 jar（JDT 一式 19 個） | 約 15MB | 約 15MB |
| 3 つとも（初回） | 約 165MB | 約 485MB |

通信量と置き場所の量を分けて出すのは、JDK が**展開したものとアーカイブの両方**残り、ディスクの増え方が
ダウンロード量の 3 倍以上になるため。これまでの「初回は合わせて数百 MB」は後者だけを指していて、
通信量を知りたい人（従量課金の回線、プロキシの制限）には答えになっていなかった。

測り直し方（版を上げたときや、目安が実態と離れたとき）:

```bash
# 通信量 … 取得元に HEAD を投げる（この確認機能の外での、開発時の作業として行う）
curl -sSIL https://github.com/jbangdev/jbang/releases/latest/download/jbang.tar | grep -i content-length
curl -sSi "https://api.foojay.io/disco/v3.0/directuris?distro=temurin&archive_type=tar.gz&operating_system=linux&package_type=jdk&version=25&architecture=x64&latest=available" \
  | grep -i '^location:'      # ここで出た URL に HEAD を投げる

# 置き場所が増える量 … まっさらな置き場所で 1 回通してから測る
du -sh ~/.jbang/bin ~/.jbang/cache/urls ~/.jbang/cache/jdks/*
bash jbangw/jbang info classpath src/jche/CallHierarchyExporter.java | tr ':' '\n' | grep -v '/cache/jars/' | xargs du -cb | tail -1
```

数字は 2 つの起動コマンド（`.sh` と `.cmd`）にそれぞれ持たせている。`launcher.properties` のひな形や
設定ファイルの書き出しと同じで、Java が動く前に使う値は両方に写すのがこのリポジトリの形
（[cli-app-qa.md](cli-app-qa.md) の Q2）。Windows と Linux で通信量がほぼ同じ（JDK は 135MB 対 135MB、
JBang は 12.8MB 対 14.9MB）だったので、OS ごとに数字を分けることはしていない。

### Q16. Windows の CI だけが落ちた（`set was unexpected at this time.`）

起動コマンドの `.cmd` で、`launcher.properties` 由来の変数に **`%VAR:検索=置換%` の文字列置換**を使ったのが原因。
`JCHE_JBANG_OPTS` を書いていない（＝変数が未定義の）環境で、cmd がこの書き方を展開しきれず、壊れた `if` 行になって
バッチ処理ごと打ち切られていた。CI のトレース（`@echo on`）が示した実際の展開結果:

```
>if defined JCHE_JBANG_OPTS set "JB_OPTS=--offline="
>if defined JCHE_JBANG_OPTS if not "" == "" set "OFFLINE_FORCED=1"
set was unexpected at this time.
>if defined JB_OPTS if not "--fresh=JB_OPTS" set "FRESH=1"
```

`%JCHE_JBANG_OPTS:--offline=%` が置換として働かず、`--offline=` という文字列に化けている。
`if defined` で囲ってあっても、**行は実行前にまるごと展開される**ので、条件が偽でも壊れた行になる。

直し方は、文字列置換をやめて `for %%O in (%JCHE_JBANG_OPTS%) do call :one_jbang_opt "%%~O"` と
オプションを 1 つずつ見る形にした。ついでに短い `-o` も `--offline` と同じ扱いにできた（それまでは見分けていなかった）。

この失敗の性質が厄介だったのは次の 3 点。

- **終了コードが 255 で、出力が何も残らない**。cmd は構文エラーでバッチ処理の連鎖ごと打ち切るので、
  呼び出し元の `type launcher-batch.log` にも到達しない。CI の手順が起動コマンドの出力を
  ログファイルへリダイレクトしていたため、原因のメッセージはそのファイルの中に消えていた。
  `smoke.yml` の該当ステップはリダイレクトをやめ、出力をそのまま CI のログへ流すようにした
- **手元で再現できない**。`.cmd` は cmd.exe でしか動かせず、`test/cli/run.sh` の `.cmd` 検査は
  「中身を読むだけ」（ラベル・改行・文字コード）なので、実行時の構文エラーは拾えない。
  Linux 側のテストが全部通っても Windows が落ちうる、という前提を忘れないこと
- **`@echo off` のままでは落ちた行が分からない**。一時的に `@echo on` にしたコミットを CI に通して
  トレースを取り、原因を特定してから元に戻した

再発を防ぐため、`test/cli/run.sh` に「`JBANG_*` / `JCHE_*` / `JB_OPTS` / `R_OPTS` に
`%VAR:検索=置換%` を使っていないこと」の検査を足した（`%VAR:~0,1%` の部分文字列は対象外）。
これらは設定が空欄なら未定義になる変数で、同じ壊れ方をする。

### Q17. 確認の答えを標準入力ではなく端末（`/dev/tty`）から読む理由

標準入力は対話モードのメニュー操作に使われる。確認をそこから読むと、アプリに渡るはずの入力を
1 行食べてしまう。いまは確認が Java の起動前なので実害は出にくいが、答えをパイプで流し込んで
自動化する使い方では取り合いになる。`/dev/tty` は「今この端末を操作している人」への口なので、
パイプやリダイレクトの影響を受けずに尋ねられる。案内の本文（取得するもの・サイズ・取得元）は
これまでどおり標準出力に出す。端末が無い環境でも、なぜ止まったのかがログに残るようにするため。

あわせて、**端末の口が開いても、その先に誰も居ない**場合を端末が無いのと同じ扱いにした。
Git Bash はパイプで動かしていても `/dev/tty` を渡すので、`read` がすぐ終わる。
`[ -t 0 ]` の判定だけではこの形を取りこぼし、質問を出したまま「答えなし」で進んでしまう。

この 2 点は、同じ Issue を別に実装したブランチ `claude/issue-86-network-confirmation`（未マージ）から
移した。Windows には `/dev/tty` に当たるものが無いので、`.cmd` は別の手段で同じ穴を塞いでいる（Q18）。

手元で確かめたこと（`script -qec` の擬似端末）:

| 状況 | 結果 |
|---|---|
| 端末が無い（パイプ） | 質問を出さずに取得しない。終了コード 3 |
| 擬似端末で `n` | 取りやめ。終了コード 3 |
| 擬似端末だが入力元が空（誰も居ない） | 質問を出したあと端末が無い扱いに落ちる。終了コード 3 |
| 擬似端末で `y` | 取得して解析まで完走。終了コード 0 |

常設の検査にしていないのは [cli-noninteractive-qa.md](cli-noninteractive-qa.md) の Q9 と同じ理由
（`script` はオプションの綴りが環境で違い、CI の OS 差で落ちやすい）。`test/cli/run.sh` の
「端末が無いときは取得しない」の検査が、この変更の回帰も兼ねる（`/dev/tty` を開けない環境で
案内を出して 3 で終わること）。

### Q18. Windows（`.cmd`）で「端末はあるが誰も居ない」をどう判定するか

**`choice` の `/t`（待ち時間）と `/d`（既定）で待ちを打ち切る。** `CON` からは読まない。

bash 側は `/dev/tty` を開いて `read` が即座に終わることを「誰も居ない」の合図に使える（Q17）。
cmd には同じ合図が無い。手元に cmd.exe が無く、ドキュメントにも書かれていないので、
GitHub の Windows ランナー（`windows-latest`）で実際に測った。

| 試したこと | 結果 |
|---|---|
| `timeout /t 0`（リダイレクト無し） | 失敗（端末ではないと判定）。従来の判定は正しく働く |
| `set /p` に `< nul` | 変数は書き換わらず `errorlevel=1` |
| `set /p` に空ファイル | 同上 |
| `set /p` に値を与える（対照） | 変数に値が入り `errorlevel=0` |
| `choice /c yn /n /t 1 /d n` | `errorlevel=255`（読めないときのエラー） |
| 同上に `< nul` | 既定の `n` が選ばれ `errorlevel=2`。固まらない |
| `choice /c yn /n`（`/t` `/d` 無し）に `< nul` | `errorlevel=255`。固まらない |
| `set /p` を `< CON` から | **5 分間ブロックし、ジョブが打ち切られた** |

最後の行が決め手で、**`CON` は `/dev/tty` の代わりにならない**。コンソールが無い環境でも
失敗も EOF も返さず、ただ待ち続ける。したがって Windows では「標準入力を消費しない」ための
`CON` 読みは採れず、確認は標準入力から読むしかない（Q17 の 1 点目は bash 側だけの対応になる）。

`set /p` は入力が無いまま終われば変数を書き換えず `errorlevel=1` を返すので、EOF は番兵で拾える。
ただし**コンソールがあって誰も居ない場合は EOF が来ず、待ち続ける**。そこを塞げるのは
待ち時間に上限を設ける `choice` だけなので、こちらを使う。

```bat
2>nul >nul timeout /t 0 || goto :approve_notty
choice /c yn /n /t 60 /d n /m "ネットワークにアクセスして取得しますか？ [y/N]（60 秒で取りやめ）: "
if errorlevel 255 goto :approve_notty
if errorlevel 2 goto :approve_declined
if errorlevel 1 exit /b 0
rem 0 は Ctrl+C / Ctrl+Break。ここへ落ちる
```

`choice` の仕様（[Microsoft Learn の choice](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/choice)）:

- `ERRORLEVEL` は選んだキーの番号。一覧の 1 つ目が 1、2 つ目が 2
- エラーを検出したときは 255、Ctrl+C / Ctrl+Break なら 0
- `/t <秒>` は `/d <既定>` と対で使い、時間切れなら既定を返す（例に「5 秒押されなければ N を選び 2 を返す」とある）
- 「`ERRORLEVEL` をバッチで使うときは大きい順に並べること」。`if errorlevel N` は「N 以上」なので、
  255 → 2 → 1 の順に見る

既定を `n`（取りやめ）にしてあるので、無人なら 60 秒後に安全側へ倒れる。`choice` が見つからない
環境でも `errorlevel` は 9009 になり、255 以上として「尋ねられない」経路に落ちる。

リダイレクト時の挙動はドキュメントに書かれていないが、上の実測のとおり `/t` `/d` があれば既定に倒れ、
無ければ 255 で終わる。どちらも固まらない。なお `set /p` の「入力が無いと変数を書き換えない」挙動も
[Microsoft Learn の set](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/set_1)
には書かれていない（`/p` は「入力した 1 行を変数に入れる」としか書いていない）。上の実測が根拠。

`test/cli/run.sh` は「確認の `choice` が `/t` と `/d` を伴うこと」と「`CON` から読んでいないこと」を
静的に検査する。Windows でしか実行できない分岐なので、書き方が戻っていないことだけでも Linux 側で押さえる。

### Q19. 別実装のブランチから、ほかに取り込んだもの・取り込まなかったもの

同じ Issue を別に実装した `claude/issue-86-network-confirmation`（未マージ）を、現在の main と
突き合わせて見直した。Q17 と Q18 で扱った 2 点のほかに、次を取り込んだ。

**取り込んだもの**

- **JBang 本体の判定を 2 ファイルにした**（`jbang_jar_available`）。ラッパー（`jbangw/jbang`）は
  `bin/jbang.jar` と `bin/jbang` の**どちらかが欠けていても**取りに行く。`jar` だけを見ていると、
  取りに行くのに「ある」と判断して**確認を飛ばしてしまう**。Issue の「必須」を破る穴なので直した。
  Windows のラッパー（`jbangw\jbang.cmd`）は `jbang.jar` の有無だけで決めるので、`.cmd` 側は変えていない
- **JDK の版をソースの `//JAVA` から読む**（Q9 に追記）。定数のままだと、ソース側を上げたときに
  ラッパーとツールが別々の JDK を取りに行く

**取り込まなかったもの**

| 向こうにあるもの | 取り込まなかった理由 |
|---|---|
| `//DEPS` の座標を見て、足りない依存 jar を名指しする | 直接の依存しか見られず、推移的な依存は結局分からない。`.cmd` で同じことをするとファイル読みと座標の分解が要り、Windows でしか検証できない分岐が増える。いまは常に「依存 jar」と出す（多めに見積もる側）ので、安全側には倒れている |
| `javac -version` を実行して JDK の実際の版を確かめる | 同上で `.cmd` に持ち込みにくい。手元に該当版の JDK があるのに「取得する」と数えてしまう取りこぼしはあるが、多めに見積もる側で、文言にも「すでに手元にあるものは取得しないので、実際はこれ以下になる」と書いてある |
| 設定値が `ask` / `allow` / `deny` のどれでもなければエラーで止める | こちらは知らない値を「毎回尋ねる」として扱う。書き間違いがあっても、黙って取りに行くのではなく尋ねる側（安全側）に倒れるので、止める必要が無い |
| 偽の `jbang` を置いて「どんな引数で起動したか」を検査する仕掛け | 検査としては上等だが、向こうは「足りないものを事前に数え、揃っていれば `--offline` を足す」設計で、こちらの「まず `--offline` で試す」設計とは見るべき点が違う。こちらの経路は既存の検査でおおむね押さえられている |
| JBangLite（将来 JBang を置き換える想定）との既定値の対応表 | この場からは JBangLite 側の仕様を確かめられないので、書き写さない。置き換えを検討するときに向こうのブランチを読むこと |

上 2 つ（名指しと実測）を見送ったことで、`.sh` と `.cmd` が同じものを同じように数える状態を保っている。
どちらも「多めに見積もる」側の誤差なので、確認の判断を誤らせる向きではない。

## テスト

### Q20. 端末ありの経路（`y` / `n`）をどう確かめたか

`test/cli/run.sh` はパイプで答えを流し込むので端末が無く、常設できるのは「確認できないので取得しない」経路だけ
（Issue #83 の Q9 と同じ理由で `script` に頼る検査は常設しない）。端末ありの経路は手元で `script -qec` で確かめた。

- `n` … 「取得を取りやめました。」を出して終了コード 3。置き場所には何もできない
- `y` … まっさらな置き場所に JBang 本体・JDK 25・依存 jar を取得して解析まで完走（Q9）。
  同じ置き場所でもう一度起動すると、確認は出ずに `--offline` で起動する
- 端末の口は開いているが、その先に誰も居ない … 端末が無いのと同じ扱いに落ちる（Q17）

### Q21. 「取得しない」ことをどう検査するか

`test/cli/run.sh` で、使い捨てのフォルダを置き場所にして引数ありで起動し、終了コード 3・確認の文言・
ラッパーの `Downloading` が出ていないこと・置き場所が空のままであることを見る。4 つの状況を通す。

- JBang 本体が無い（`JBANG_DIR` が無いフォルダ）… 起動を試みる前に止まる
- `JCHE_ALLOW_DOWNLOAD=no` … 理由を出して止まる
- `JCHE_JBANG_OPTS=--offline` … 理由を出して止まる
- JBang 本体はあるが JDK 25 と依存 jar が無い（`~/.jbang/bin` を新しい置き場所にコピーし、空のリポジトリ）
  … `jbang run --offline` が失敗し、目印 `.cache/launcher.started` ができず、確認の段階で止まる

`.cmd` は cmd.exe でしか動かせないので、ラベルの整合・CRLF・MS932 の「中身を読むだけ」の検査（Issue #83 の Q10）に
頼る。今回ラベルを増やした（`run_offline` / `run_online` / `abort` / `done` / `confirm_first` /
`missing_bootstrap` / `approve_download` ほか）。Windows の CI（`smoke.yml` の Launcher test）は取得済みの
状態で起動コマンドを通すので、「確認に掛からずに起動する」経路の検査になる（掛かると出力フォルダができず失敗する）。
