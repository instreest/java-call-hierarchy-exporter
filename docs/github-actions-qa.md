# GitHub Actions からの利用 — 実装時の QA 一覧

[Issue #48](https://github.com/instreest/java-call-hierarchy-exporter/issues/48)
「GitHubActionから使用できるようにしたい」への対応で、迷ったこと・困ったことと、その結論を Q&A の形で残す。

対応の要点:

- リポジトリ直下に `action.yml`（複合アクション）を置き、利用者のワークフローから
  `uses: instreest/java-call-hierarchy-exporter@main` で呼べるようにする（タグは必須ではない。Q24）
- 解析対象は入力（`project-root` / `source-folders` …）から設定ファイルを生成して指定する。
  用意済みの設定ファイルを `config` で渡すこともできる（複数可）
- ステップの中身は `.github/action/prepare.sh` / `run.sh` / `collect.sh` の 3 本
- 出力フォルダの場所は、ツールに足した環境変数 `JCHE_OUTPUT_DIR_FILE` で受け取り、
  アクションの出力（`output-dir` / `csv` / `methods-csv` / `run-log`）とアーティファクトにする
- このリポジトリ自身の CI（`.github/workflows/smoke.yml`）に `action` ジョブを足し、
  `uses: ./` で利用者と同じ経路を毎回通す

---

## 何を作るかの解釈

### Q1. Issue の「GitHubActions から使用できるか不明」をどう解釈したか

「このリポジトリの CI が GitHub Actions で動くか」ではなく、**「利用者のリポジトリのワークフローから、
このツールを呼んで解析させられるか」** と解釈した。前者は既に `smoke.yml` があり動いている。
Issue の To be が「GitHubActions から使用できるようにしたい」なので、足りないのは
「外から呼べる入口」＝アクション定義（`action.yml`）である。

判断の根拠として、アクション無しでも次のように書けば動く（JBang ラッパーが同梱されているため）。

```yaml
      - run: |
          git clone --depth 1 https://github.com/instreest/java-call-hierarchy-exporter tool
          ./tool/jbangw/jbang tool/src/jche/CallHierarchyExporter.java ci/app.properties
```

しかしこれだと、利用者は「JDK 25 を用意する」「設定ファイルの相対パスの起点を理解する」
「実行のたびに変わる出力フォルダ名（`<日時>_<プロジェクト名>`）を自分で見つける」
「キャッシュを自分で書く」を全部やることになる。アクションはその定型部分を引き受けるもの、と位置づけた。

### Q2. アクションの種類は composite / Docker / JavaScript のどれにしたか

**composite（複合アクション）**にした。

- **Docker** … 解析に必要なのは JDK と JDT の jar だけで、どちらも JBang が取得する。
  イメージのビルドと公開（GHCR 等）を増やす価値が無い。Docker コンテナアクションは
  Linux ランナーでしか動かないので、Windows ランナーでの利用も落ちる
- **JavaScript** … `node_modules` を含めたビルド成果物のコミットが要る。やることは
  「設定ファイルを作って 1 コマンド動かす」だけなので、TypeScript 一式を持ち込むのは重い
- **composite** … ランナー上でそのままシェルを動かす。同梱の `jbangw/` をそのまま使え、
  `actions/setup-java` や `actions/cache` を中から呼べる（複合アクションは `uses:` を書ける）

### Q3. 入力に全部の設定項目を並べなかったのはなぜか

設定項目は 20 以上あり、全部を入力にすると `action.yml` が設定ファイルの二重管理になる。
新しい項目を足すたびに 2 か所（`config/config.properties` のコメントと `action.yml`）を直すことになり、
片方が古くなる。

そこで **「よく使うものだけ入力にし、残りは `extra-config` に生の行で書く」** 形にした。

```yaml
        with:
          source-folders: src/main/java
          extra-config: |
            max.depth=30
            dataflow.enabled=false
            output.encoding=MS932
```

設定ファイルを丸ごと用意したい人向けには `config` 入力がある。こちらが最も自由度が高い
（ツールが読む設定ファイルそのものなので、書ける内容は README と `config/config.properties` の説明がそのまま効く）。

## 設定ファイルの扱い

### Q4. 生成した設定ファイルをどこに置くか

`RUNNER_TEMP`（`$RUNNER_TEMP/java-call-hierarchy-exporter/config.properties`）に置く。
解析対象リポジトリのチェックアウト（`GITHUB_WORKSPACE`）には書かない。利用者のワークフローが
`git diff --exit-code` や `git status --porcelain` で作業ツリーの汚れを見ていることがあり、
アクションが勝手にファイルを置くとそれを壊す。

ただし置き場所を変えると **相対パスの起点が変わる**。設定ファイルの `project.root` と `output.folder` は
「設定ファイルのフォルダ」からの相対で解決されるので、`RUNNER_TEMP` を起点にした相対パスでは
ワークスペースを指せない（`..` で外へ出る指定は `Config` が拒否する）。
そのため生成する設定ファイルには **絶対パスだけを書く**（`prepare.sh` の `abspath`）。
利用者から見た入力はワークスペースからの相対パスのままで、変換はアクションが行う。

### Q5. Windows ランナーのパスをそのまま書けなかった話

`properties` ファイルではバックスラッシュがエスケープ文字になる。Windows ランナーの
`GITHUB_WORKSPACE` は `D:\a\repo\repo` の形なので、そのまま書くと `java.util.Properties` が
`\a` `\r` を食って `D:arepo` のような別のパスになる。**値に書く前に `\` を `/` へ直している**
（`prepare.sh` の `prop`）。Java は Windows でも `/` を区切りとして扱うので、これで通る。

`config` 入力で渡された設定ファイルは書き換えないので、この処理は生成する側にだけ要る。
渡されたパスはコマンドライン引数として渡すだけなので、エスケープの問題は起きない。

### Q6. `config` を複数渡せるようにしたのはなぜか

ツール自体が設定ファイルを複数受け取れる（Issue #60）ので、その入口をふさぐ理由が無い。
モノレポで「アプリ」「バッチ」を別々に解析する用途がそのまま CI に載る。
改行区切りとカンマ区切りの両方を受ける（YAML の `|` で書くのが読みやすいが、1 行で書く人もいる）。

### Q7. `config` と生成用の入力を両方書かれたらどうするか

`config` を優先し、生成用の入力は使わない。両方を混ぜて「入力で設定ファイルを上書きする」形にしなかったのは、
上書きの規則（どちらが勝つか、既定値と明示指定をどう区別するか）を説明しなければならなくなるから。
「設定ファイルを渡すなら、その内容が全て」のほうが読み手に説明が要らない。

## 実行

### Q8. 作業ディレクトリをツール側（`github.action_path`）にしたのはなぜか

解析キャッシュの置き場所（`.cache/`）は `ToolRoot` が「作業ディレクトリとその上位から
`src/jche/CallHierarchyExporter.java` を探す」ことで決まる。作業ディレクトリを利用者の
ワークスペースのままにすると目印が見つからず、警告を出したうえで **ワークスペース直下に `.cache/` を作る**。
利用者のチェックアウトを汚さないため、作業ディレクトリをアクションのフォルダ
（`$GITHUB_ACTION_PATH`。ツールのチェックアウトそのもの）にした。

設定ファイルは絶対パスで渡すので、作業ディレクトリを変えても解決結果は変わらない。

### Q9. 起動コマンド（`java-call-hierarchy-exporter.sh` / `java-call-hierarchy-exporter.cmd`）ではなく `jbangw/jbang` を直接呼ぶのはなぜか

起動コマンドは人が使うための入口で、`launcher.properties` の作成（初回は JDK / JBang の置き場所を尋ねる）、
対話メニュー、設定を反映するための再起動ループを持つ。CI では JDK は `actions/setup-java`、
JBang の置き場所とキャッシュはアクション自身が決めるので、その層を挟む利点が無い。
`bash jbangw/jbang run src/jche/CallHierarchyExporter.java <設定ファイル…>` を直接呼ぶ。

なお `JCHE_OUTPUT_DIR_FILE`（Q14）は `runAll` に置いてあるので、起動コマンド経由でも対話モードでも同じように効く。
CI 以外で起動コマンドを使っている人が、その出力の場所を機械的に受け取りたいときにも使える。

### Q10. ツールを動かす JDK は誰が用意するか

既定では `actions/setup-java` で JDK 25（`java-version` 入力、`//JAVA 25` と同じ版）を用意する。
JBang は JDK が無ければ自分で取得できるが、それに任せると毎回 200MB 近い JDK の取得が走る
（`~/.jbang` をキャッシュしても、キャッシュが無い初回と、キーが変わったときは必ず走る）。
ランナーの `setup-java` は Actions 側のツールキャッシュから入るので速い。

`java-version` を空欄にすると `setup-java` のステップを飛ばす。
解析対象のビルドで既に JDK を用意している場合や、ランナーの既定 JDK を使いたい場合のための逃げ道。
その場合も、ツールが要求するのは 25 である（用意した版が古いと JBang が JDK を取得しに行く）。

### Q11. 何をキャッシュするか。`~/.m2/repository` 全体にしなかったのはなぜか

キャッシュするのは `~/.jbang`（JBang 本体とスクリプトのビルド結果）と
`~/.m2/repository/org/eclipse`（JBang が解決した JDT 一式）だけにした。

`~/.m2/repository` 全体を保存すると、**解析対象プロジェクトの依存 jar**（利用者が
`mvn dependency:go-offline` 等で取得したもの）まで、このアクションのキーで保存・復元することになる。
利用者側も `setup-java` の `cache: maven` で同じ場所を扱っているのが普通で、
二重に保存されるうえ、どちらのキャッシュが当たったかで挙動が変わる状態を作ってしまう。
「アクションが動くのに要るもの」だけを持つ。

キーはツール本体（`//DEPS` の版を含む `src/jche/CallHierarchyExporter.java`）と `jbangw/jbang` の
ハッシュから作る。`hashFiles()` は `GITHUB_WORKSPACE` 配下しか見られず、アクションのフォルダを
見られないので、シェルで `sha256sum`（macOS には無いので `shasum -a 256` にフォールバック）で計算している。

### Q12. 解析結果のキャッシュ（`.cache/`）はワークフロー実行間で持ち越さないのか

持ち越さない。持ち越しても効かないため。

このツールの差分判定は「最終更新時刻」と「ファイルサイズ」の一致で行う。`actions/checkout` は
毎回チェックアウト時刻でファイルを作るので、内容が同じでも更新時刻が必ず変わり、
全ファイルが「変更あり」になる。キャッシュを復元しても全件解析し直すので、
保存・復元の時間だけが増える。README にもその旨を書いた。

（内容ハッシュでの差分判定にすればキャッシュが効くようになるが、それはこの Issue の範囲を超える。
`docs/cache-dependency-jars-qa.md` にある「タイムスタンプで判定する」設計そのものの変更になる。）

**追記（Issue #79）**: その後、更新時刻だけが違うファイルはサイズと内容ハッシュで突き合わせるようにし、
`analysis-cache` 入力で `.cache/` を実行間で引き継ぐようにした。経緯は
[actions-analysis-cache-qa.md](actions-analysis-cache-qa.md)。

### Q13. 解析対象の依存 jar をアクションが取りに行かないのはなぜか

`library.folders` を空欄にしたときの依存 jar の自動取得は、**ローカルリポジトリにある jar を探すだけ**で、
ネットワークには出ない（この設計は `docs/build-tool-classpath-qa.md`）。ランナーの `~/.m2/repository` は
空なので、利用者が先に `mvn -B dependency:go-offline` などを走らせておく必要がある。

アクションの中で `mvn` を呼ぶ案もあったが、採らなかった。

- 解析対象が Maven とは限らない（Gradle、ビルドツール無しで `library.folders` 指定、もある）
- ビルドの前提（プロファイル、`settings.xml`、認証が要る社内リポジトリ、マルチモジュールの一部だけ）は
  プロジェクトごとに違い、アクションの入力で表現しきれない
- 利用者のワークフローには、たいてい既にビルドのステップがある。その後ろにこのアクションを置けば良い

README の使うときの注意に、この 1 手が要ることと、しない場合に何が起きるか（jar の型が解決できず
呼び出しが欠ける）を書いた。

## 結果の受け渡し

### Q14. 出力フォルダの場所を、アクションはどうやって知るか

ツールに環境変数 **`JCHE_OUTPUT_DIR_FILE`** を足した。指定すると、設定ファイルごとの出力フォルダの
絶対パスを、成功した順に 1 行ずつ UTF-8 でそのファイルへ書く（`CallHierarchyExporter.main`）。
アクションはそれを読んで `output-dir` / `output-dirs` / `csv` / `methods-csv` / `run-log` を出力にする。

出力フォルダ名は `<解析開始日時>_<プロジェクト名>`（同じ秒に重なれば `_2`）で、実行のたびに変わる。
外から確実に知る手段がツールに無かったので、そこだけを足した形。Actions 以外の CI からも使えるよう、
GitHub 固有の書式（`::set-output` 相当）ではなく、ただのテキストファイルにしている。

### Q15. 「最新のフォルダを取る」「ログから読む」で済ませなかったのはなぜか

どちらも採らなかった。

- **最新のフォルダを取る**（回帰テストの `ls | sort | tail -1`）… 出力フォルダの場所を
  アクションが知っている場合しか使えない。`config` で設定ファイルを渡された場合、`output.folder` の
  既定値と相対パスの解決をシェル側で再実装することになり、ツールと二重管理になる
- **標準出力のログから読む**（`出力フォルダ: ...` の行）… 標準出力の文字コードは環境依存で
  （ツールは意図的に固定していない。`Log` のクラスコメント）、日本語のメッセージを外から
  機械的に読むのは不安定。実際、ランナーの既定のままだと日本語が `?` に化ける。
  メッセージの文言を変えただけでアクションが黙って壊れる結合も避けたい

### Q16. それでもログの文字化けは直したのか

直した。`JAVA_TOOL_OPTIONS: -Dstdout.encoding=UTF-8 -Dstderr.encoding=UTF-8` を実行ステップに置いている。
JDK 19 以降、コンソールが無い（ランナーのようにパイプへ書く）環境では `native.encoding` が使われるため、
ロケール次第で日本語が化ける。ランナーのログは人が読むものなので、ここは UTF-8 に固定した。
`JAVA_TOOL_OPTIONS` は起動する JVM が「Picked up JAVA_TOOL_OPTIONS: ...」を標準エラーに出すが、
ログの読みやすさのほうが優先。出力フォルダの `run.log` は元から常に UTF-8 なので影響を受けない。

### Q17. アーティファクトのアップロードをアクションに含めたのはなぜか

CI で解析する目的は、ほとんどの場合「結果の CSV を持ち帰る」ことなので、既定で
`actions/upload-artifact` まで行う（`upload-artifact: false` で切れる）。
利用者が自分でアップロードしたい場合も、`output-dir` 出力を使えば同じことができる。

失敗したときこそ `run.log` が要るので、収集とアップロードのステップは `if: always()` にした。
ただし出力フォルダが 1 つも無い（設定ファイルが読めない等、解析が始まる前の失敗）ときは、
アップロードするものが無いのでステップごと飛ばす（`artifact-path != ''` の条件）。
`if-no-files-found: warn` は、フォルダはあるが中身が無い場合の保険。

### Q18. ジョブサマリに何を出すか

出力フォルダ名と、`call-hierarchy.csv` / `methods.csv` の行数（ヘッダを除く）を表で出す。
アーティファクトを落とす前に「解析が空振りしていないか」（行数が 0 でないか、前回と桁が違わないか）を
見られるようにするため。ログを開かずに済む情報だけに絞った。

## スクリプトの書き方

### Q19. ステップの中身を YAML に埋め込まず、`.github/action/*.sh` に分けたのはなぜか

`action.yml` の `run: |` に 100 行のシェルを書くと、手元で動かして直すことができない。
別ファイルにしておけば、環境変数（`GITHUB_WORKSPACE`、`RUNNER_TEMP`、`GITHUB_OUTPUT` …）を
渡すだけで、そのままローカルで実行して確認できる。実際、この対応でも 3 本ともローカルで動かして詰めた。

置き場所を `.github/action/` にしたのは、`action.yml` から使うものだと分かる位置で、
かつツールの本体（`src/`）や利用者が触る設定（`config/`）と混ざらないため。
アクションとして呼ばれるときはリポジトリ全体がチェックアウトされるので、`.github/` の下でも問題なく読める。

### Q20. シェルの書き方で気をつけたこと

- **macOS ランナーの bash は 3.2** … `mapfile`、連想配列、`${var,,}` は使えない。
  設定ファイルの一覧は `while IFS= read -r` で配列に読んでいる
- **パスに空白が入りうる** … 一覧はファイルに 1 行 1 パスで持ち、配列にしてから `"${configs[@]}"` で渡す
- **`set -e` と `[ ... ] && ...`** … 最後の文が偽だとスクリプトが落ちるので、条件は `if` で書く
- **`::error::`** … 失敗はワークフローのアノテーションに出す

### Q21. `run:` の中に `${{ }}` を直接書かなかったのはなぜか

アクションの出力をチェックするステップ（`smoke.yml`）では、`${{ steps.x.outputs.csv }}` を
`env:` 経由で渡している。`run:` に直接埋め込むと、値の中身がそのままシェルのソースに展開される
（スクリプトインジェクション）。ここで扱う値は自分のツールが書いたパスだが、
利用者がまねる書き方でもあるので、安全な形を README の例にも載せた。

## 検査

### Q22. アクション自体をどう検査するか

`.github/workflows/smoke.yml` に `action` ジョブを足し、`uses: ./` で**このリポジトリ自身のアクションを
利用者と同じ経路で動かす**。2 つの経路を通す。

1. 入力から設定ファイルを生成する経路（`test/demo` を解析）。出力の `csv` / `methods-csv` / `run-log` が
   実在し、生成した設定ファイルの複製が出力フォルダにあることを確認する
2. 用意済みの設定ファイルを渡す経路（回帰テストの設定 2 つ）。出力フォルダが 2 つ並ぶこと、
   `java-version: ''`（`setup-java` を飛ばす）と `cache: 'false'` の分岐が通ることを確認する

これで、`action.yml`・3 本のシェル・ツールの `JCHE_OUTPUT_DIR_FILE` が push のたびに一度は通る。

### Q23. ツール側に足した `JCHE_OUTPUT_DIR_FILE` の検査はどこか

回帰テストの `multi` ケース（`test/regression/run.sh` と `run.cmd`）に足した。
このケースは「設定 3 つのうち 1 つが失敗する」形なので、
**成功した 2 件だけが 1 行ずつ入る**という仕様がそのまま検査できる。
Windows 側（`run.cmd`）にも同じ検査を入れてある（環境変数の受け渡しは OS で書き方が違うため）。

### Q24. アクションの版はどう配るか。タグは要るか

**要らない。** `uses:` の `@` の後ろは Git の参照であればよく、ブランチ名も書ける。
タグを運用しない間は `@main` で使える（README の例もこの形にしてある）。

| 書き方 | 向いている場面 |
| --- | --- |
| `@main` | タグを運用しない。ツール側の修正がすぐ利用者に届く。逆に、こちらの変更で利用者のワークフローの挙動が黙って変わりうる |
| `@<コミットSHA>` | 再現性が要る。`main` が動いても影響を受けない。更新は利用者が SHA を書き換える |
| `@v1` などのタグ | 利用者を書き換えずに版を切り替えたい。GitHub Marketplace に出す場合も、通常はこの形 |

`action.yml` はリポジトリ直下に置く必要があるので、その位置だけは動かせない
（`@main` でも `@<SHA>` でも、参照先のリポジトリ直下が見られる）。

同じリポジトリのワークフローからは参照そのものが要らず、`uses: ./` で動く（`smoke.yml` の `action` ジョブ）。
別の取得の仕方として、`actions/checkout` の `repository:` / `ref:` / `path:` でツールを
別フォルダへ取り出し、`uses: ./<path>` とローカル参照する形もある。この場合もアクションの場所は
`path:` のフォルダ、解析対象はワークスペース（1 つ目のチェックアウト）になり、
生成する設定ファイルが絶対パスなので（Q4）そのまま動く。

### Q25. このリポジトリ自身を解析するワークフローを別に置いた理由

`smoke.yml` の `action` ジョブ（Q22）とは目的が違うので、`call-hierarchy.yml` として分けた。

| | `smoke.yml` の `action` ジョブ | `call-hierarchy.yml` |
| --- | --- | --- |
| 目的 | アクションが壊れていないかの検査 | 実際の使い方の例と、自分自身を対象にした通し確認 |
| 解析対象 | `test/demo`（小さなサンプル） | `src/`（JDT を使う実際のコード。依存 jar は `pom.xml` から自動取得） |
| いつ動くか | push / pull request のたび | `main` への push（解析結果が変わりうるパスだけ）と手動実行 |
| 出力 | 検査したら捨てる | `call-hierarchy-self` アーティファクト |
| 失敗の意味 | アクションの不具合 | 実コードの解析で落ちた・空振りした |

分けた理由は 3 つ。

- **押し付けたくない** … `smoke.yml` は push のたびに全部動く。41 万行の CSV（アーティファクトで zip 約 3.3MB）を
  毎回作って持ち帰るのは、検査の速さに対して割に合わない
- **失敗の意味が混ざらない** … 同じジョブに入れると、「アクションが壊れた」のか「実コードの解析で落ちた」のかが
  ジョブの赤だけでは分からない
- **例として読める** … 利用者が写す対象は「1 つのことだけをする短いワークフロー」であってほしい。
  `smoke.yml` の `action` ジョブは検査のためのステップ（出力の存在確認、2 経路の切り替え）が混ざっていて、
  写す例には向かない

自分自身の解析には、依存 jar の自動取得（`pom.xml` → `~/.m2/repository`）と、
19 個の jar を渡した状態での JDT の型解決という、`test/demo` では通らない経路が含まれる。
`mvn -B dependency:go-offline` を先に置くのは README の注意と同じで、この形が実際に要ることの確認でもある。

### Q26. 呼び出す GitHub 公式アクションの版

`actions/checkout@v5` / `actions/setup-java@v5` / `actions/cache@v5` / `actions/setup-node@v5` /
`actions/upload-artifact@v7` を使う（`action.yml` の中と、このリポジトリのワークフロー全部で揃えてある）。

v4 系のままだと、実行のたびに次の警告が付く。

```
Node.js 20 is deprecated. The following actions target Node.js 20 but are being forced to run on
Node.js 24: actions/cache@v4, actions/checkout@v4, actions/setup-java@v4, actions/upload-artifact@v4
setup-java v4 is deprecated and will no longer receive updates. Please migrate to actions/setup-java@v5.
```

**JavaScript アクション**（`action.yml` に `runs: using: node20` と書いてあるもの）は、ランナー同梱の Node で
動く。ランナーが Node 20 の同梱をやめる過程で、`node20` 指定のアクションは Node 24 に載せ替えられて動いており、
その旨が警告として出ている。上に挙げた版はいずれも `using: node24` を宣言しているので警告が消える。
入力は今まで使っているもの（`distribution` / `java-version` / `cache` / `path` / `key` / `name` /
`retention-days` / `if-no-files-found`）がそのまま残っているので、版を上げるだけで済む。

このツール自身と `action.yml` は Node を使わない。`action.yml` は複合アクション（`runs: using: composite`）で、
中身は `.github/action/*.sh` のシェルと、JBang 経由の Java だけ。Node が要るのは上記の公式アクションだけである。

`upload-artifact` だけ v7 なのは、v5 / v6 の時点ではまだ `node20` 宣言のままで警告が消えないため
（`node24` になったのは v7）。v7 では単一ファイルを zip せずにアップロードする `archive` 入力も増えている（Q27）。

選ぶ基準は「最新の版」ではなく「`node24` を宣言している最小の版」である。より新しい major も出ているが
（checkout v7・setup-java v6・cache v6・setup-node v7）、警告の原因は Node の版だけなので、
上げる理由が無いものは揃えたままにしておく。入力の名前が変わっていないことを確かめてから上げること
（setup-node は v7 で `always-auth` が消えているが、ここで使っているのは
`node-version` / `cache` / `cache-dependency-path` だけなので、上げるとしても影響は無い）。

### Q27. アーティファクトを zip せず、CSV のまま置けるか

**GitHub のアーティファクトは zip で保存される**（ブラウザからのダウンロードも zip）。
`compression-level: 0` は zip の中を無圧縮にするだけで、zip という入れ物は変わらない。

`actions/upload-artifact@v7` には `archive: false` があり、これを使うと**単一ファイル**を zip せずに
そのままアップロードできる（glob が複数ファイルに当たると失敗する。アーティファクト名は
`name` ではなくファイル名になる）。ただし今回は使わず、フォルダごとの zip のままにした。

- このツールの出力は 1 ファイルではない。`call-hierarchy.csv` のほかに `methods.csv`、`run.log`、
  使った設定ファイルの複製、`resolved-classpath.txt` があり、失敗時に効くのはむしろ `run.log` のほう。
  `archive: false` は 1 ファイルずつしか置けないので、ステップを増やして分割することになる
- 生のままだと保存量が増える。このリポジトリ自身の解析で `call-hierarchy.csv` は 41 万行あり、
  生のままなら 100MB 台になるところ、zip では約 3.3MB に収まる。プライベートリポジトリでは
  この容量が利用者のストレージから引かれるので、差は小さくない（Q29）
- 取り出す側の手間はほとんど変わらない。`gh run download -n call-hierarchy-self` は展開まで済ませる

「ブラウザから 1 クリックで CSV を開きたい」のように zip を挟みたくない用途がはっきりしたら、
`archive: false` のステップを足すか、リリースのアセットとして置く（生のファイルに直リンクが張れる）
のが選択肢になる。

### Q28. 依存 jar の取得をアクションに入れず、セキュリティの注意を docs に書いた理由

Q13 で「依存 jar の取得はアクションに入れない」と決めたが、その後、利用者から
「自動実行で勝手に依存を取ってよいのか。社内のリポジトリ設定やプロキシを使わないよう制限するといった
セキュリティ対策が要るのでは」と問われた。整理した結論は次のとおり。

- **ツール自身はネットワークに出ないので、制限を掛ける対象がツール側に無い。** 危険なのは前段の
  `mvn` / `gradle` の実行（`pom.xml` の `<repositories>` やプラグインがランナーの権限と設定で動く）で、
  それは利用者のワークフローの責任範囲にある。アクションの中で `mvn` を呼ばない Q13 の判断は、
  この観点でも正しい（呼ぶなら settings.xml の扱いまでアクションが引き受けることになる）
- **危険が具体化するのは 2 つの場面**に絞れる。`pull_request_target` で第三者の `pom.xml` をベースの権限で
  処理する場合と、self-hosted ランナーで社内の `~/.m2/settings.xml` / プロキシが暗黙に使われる場合。
  どちらもツールの作りではなくワークフローの書き方で防ぐものなので、`docs/github-actions.md` の
  「セキュリティ上の注意」に、避け方（`pull_request` を使う、`-s` で settings.xml を明示する）と、
  取得そのものを省く 3 つの方法（`library-folders` / `library-repositories` / `library-build-tool: none`）を書いた
- 却下した案: `resolve-dependencies: maven|gradle|none` のようなオプトイン入力でアクション内から取得する。
  既定オフ・`-s` 必須・`pull_request_target` 禁止と条件を付ければ成り立つが、Q13 の「ビルド前提は
  プロジェクトごとに違う」はそのまま残り、利用者の既存のビルドステップの後ろに置くのと比べて楽にならない。
  用途がはっきりしたら再検討する


### Q29. アーティファクトとキャッシュはどれだけ残るのか。`artifact-retention-days` の既定を短くしないのはなぜか

利用者から「プライベートリポジトリで使うとアーティファクトの容量が利用者の無料枠から引かれる。
`artifact-retention-days` の既定が空欄（リポジトリの既定＝通常 90 日）なので、業務システム規模で
全体モードを定期実行すると積み上がりやすい」という指摘があった。まず実測で整理した
（このリポジトリ自身を解析する `call-hierarchy.yml` の実行。ソース 131 ファイル・2.4 万行）。

| 残るもの | 実測 | 増え方 | 課金 |
| --- | --- | --- | --- |
| アーティファクト | zip 3,350,978 バイト（5 ファイル。`call-hierarchy.csv` は 413,671 行） | 実行ごとに 1 つ | **する**（パブリックは無料） |
| JBang と JDT のキャッシュ | 52,973,917 バイト | ツール本体が変わるまで 1 エントリのまま | しない |
| AST 解析キャッシュ | 数 MB（このツール自身のソースで約 2 MB。数万ファイル規模なら数百 MB。`cache-unification-qa.md` の「数字」） | 実行ごとに 1 エントリ増える（`actions-analysis-cache-qa.md` Q10） | しない |

指摘のとおりで、**課金されるのはアーティファクトだけ**だった。加えて、指摘に無かった点として
**解析キャッシュは実行ごとにエントリが増え、リポジトリごとの 10 GB 枠は
利用者のほかのキャッシュ（`actions/setup-java` の Maven キャッシュなど）と共通**である。
課金はされないが、大きいリポジトリでは利用者のビルドキャッシュを押し出しうるので、こちらも書いた。

**既定は空欄のまま変えない。** 案内とサンプルで補う。

- パブリックリポジトリではストレージが無料なので、90 日のほうが素直に便利（あとから結果を見返せる）。
  利用者の過半がこちらだと見込んでいる
- 既定を 7 に変えると、**今このアクションを使っている利用者の挙動が、こちらの都合で黙って変わる**。
  「90 日あると思っていたアーティファクトが消えていた」は、容量が増えるより困る向きの事故である
- 空欄は「リポジトリ・組織の設定に従う」という意味を持つ。組織で保持日数を定めている利用者の設定を
  アクションが上書きしないほうがよい

代わりに、`docs/github-actions.md` に「保存量と保持期間」の節を足し、実測値・積み上がりの表
（90 日で約 300MB / 7 日で約 23MB）・プライベートで `artifact-retention-days: 7` を勧める旨・
減らす手段を効く順（保持日数 → `entry-packages` で起点を絞る → `max.depth` と `exclude-packages` →
実行回数）で書いた。入力の説明（`action.yml`）と README の注意にも 1 行ずつ足した。

規模の見当が付くように、換算の目安も書いた。このリポジトリでは**ソース 1 行あたり約 17 行**
（2.4 万行 → 41 万行）、**ソース 1 万行あたり zip で 1〜2MB**。行数はソースの行数にほぼ比例し、
`call-hierarchy` 列に経路の全体が入るので深いほど 1 行が長くなる。枝分かれの多さで上下するので
幅を持たせてある。`max.rows` の既定は 500 万行なので、この換算だとソース 30 万行あたりで上限に達する。

### Q30. 実行時間の課金（ランナーの係数）は書くべきか

書いた。1 行だけ。このリポジトリはパブリックなので実行時間も無料で、ワークフローも `ubuntu-latest`
だから当事者としては関係が無い。ただし `prepare.sh` は macOS（bash 3.2）と Windows（パスの区切り）に
対応しており、利用者が `windows-latest` で動かすことはできる。プライベートリポジトリでは

「解析結果はランナーによらず同じなので Linux で動かすのを勧める」とだけ添えた。

料金そのもの（1 GB あたりいくら、プランごとの無料枠）は、プランや価格の改定で古くなるので
書かない。GitHub の課金の説明へリンクし、無料枠は「GitHub Free なら 500MB」の 1 例に留めた。

### Q31. 依存 jar の警告が英語のログでジョブに出ていなかった

アクションは `run.log` から `[WARN] 依存jar:` で始まる行を探して warning アノテーションとジョブサマリに出していたが、
ツールの表示言語が英語（既定。[nls-qa.md](nls-qa.md)）になってからはログの書き出しが `[WARN] Dependency jars:` になり、
英語のランナーでは警告が 1 件も拾われず、黙ってジョブが緑になっていた。

**英語と日本語の両方の書き出しを探す**ようにした（`.github/action/run.sh` の `DEPS_WARN_PREFIXES`）。
`test/action/run.sh` が、`MessagesEn.java` / `MessagesJa.java` の `config.deps.missingJars` の文言をそのまま
`run.log` に書いてアクションを動かし（jbang はスタブ）、両方の言語で拾えることと、警告ではない
`Dependency jars: N` の行を拾わないことを確かめる。文言の書き出しを変えてアクション側を直し忘れると落ちる。

却下した案:

- **アクションで表示言語を英語に固定する（`JCHE_LANG=en`）** … 利用者が設定ファイルに `message.language=ja` と
  書いても `run.log` が英語になり、設定を黙って上書きする。探す側を両方に対応させるほうが影響が小さい
- **警告の行に言語に依存しない印（例: `[WARN:DEPS]`）を付ける** … 利用者が見るログの形が変わり、
  他の `[WARN]` 行と揃わなくなる。2 言語だけなので書き出しの一覧で足りる
