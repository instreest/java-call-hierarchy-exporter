# 初見の人向けの入口を整える（CONTRIBUTING・全体図・用語集・test の案内）— 実装時の QA 一覧

このリポジトリを初めて開いた Java 開発者（利用者・貢献者）の視点でリポジトリ全体を見直し、
「中身は良いが入口が無い」という結論になった件の記録。設計の芯（解決 → キャッシュ → 選択の 3 層、
呼び出しを静かに落とさない）と文書・テストの厚さは強みで、弱いのは「最初に何を読むか」「この用語は何か」
「どこに何があるか」を 1 枚で答えるものが無いことだった。

対応の要点:

- `CONTRIBUTING.md` を新設し、`AGENTS.md` の本文（構成・動かす・テスト・決まり・Git）をそこへ移した。`AGENTS.md` は
  「CONTRIBUTING.md を読む」の案内と、エージェントが特にやりがちな失敗の再掲だけにした
- `docs/architecture.md`（3 フェーズと 3 層・1 回の実行が通る道・入口 3 つの関係・パッケージの依存の向き・主要クラスの表・
  デバッグの最初の一手）と `docs/glossary.md`（用語 → コード上の名前 → 意味。キャッシュの行種別の表も）を新設した
- `test/README.md` を新設し、`test/` の 34 フォルダを検査・題材・道具に分類した。各検査が何を守っているかの詳細は
  `AGENTS.md` の表からここへ移した
- `docs/README.md` に「最初に読む順」を置き、`*-qa.md` が経緯の記録であって仕様の正本ではないことを明記した
- README の「ドキュメント」の表に、開発に参加する人と内部の作りを知りたい人の行を足した（日本語・英語の両方）
- `.gitattributes` で 1 ファイル版の生成物に `linguist-generated` を付け、PR の diff で折りたたまれるようにした

## Q2. AGENTS.md の本文を CONTRIBUTING.md に移したのはなぜか。AGENTS.md に残す案は

移した理由は、AGENTS.md の中身（構成・動かす・テスト・決まり）がそのまま人向けの貢献ガイドで、
それを AI 向けの名前のファイルにだけ置くと人が開かないから。GitHub は `CONTRIBUTING.md` を PR 作成画面から案内するので、
貢献者はこの名前を探す。

却下した案:

- **AGENTS.md をそのまま残して README からリンクする**: 最小だが、ファイル名で人が開かない問題は残る。
  同じ内容を 2 か所に置くと片方が古くなる
- **AGENTS.md を削除する**: AI エージェントは `AGENTS.md` / `CLAUDE.md` を自動で読むが `CONTRIBUTING.md` は読まない。
  入口として残し、「CONTRIBUTING.md を読む」と書く

残した AGENTS.md には、決まりの再掲を「静かに壊れるものだけ」に絞って置いた。全部を再掲すると二重管理になる。
再掲するものの基準は「テストが赤くならない・後で気づく失敗」（1 ファイル版の生成し直し、キャッシュの版、対訳、MS932）。

## Q3. 全体図（architecture.md）を `package-info.java` や `resolution-selection-design.md` と別に置いたのはなぜか

- `package-info.java` は 3 本しか無く、パッケージごとの「決まり」と「読む順」であって、パッケージをまたぐ 1 回の実行の流れは書けない
- `resolution-selection-design.md` は規則ごとの深い対応表で、場所をつかんでから読むもの
- 初見の人が最初に欲しいのは「起動コマンドから CSV までどのクラスを通るか」の 1 枚で、これはどこにも無かった

`architecture.md` はその 1 枚に絞り、深い説明は既存の文書へのリンクにした。パッケージを足した・クラスの役割を変えたら
表と `package-info.java` を直す決まりを CONTRIBUTING.md に置いた。

## Q4. 用語集に「コード上の名前」の列を置いたのはなぜか

コメント・文書は日本語、識別子は英語なので、「書き手」が `jche.analysis`、「選択」が `MethodSelection`、
「検査値」が `BlockChecksum` だと分かるまでに時間がかかる。用語 → コード上の名前 → 意味の 3 列にすると、
文書からコードへも、コードから文書へも引ける。キャッシュの行種別（F・I・H…）も同じ表の形で、record 名と対応づけた。

## Q5. test/README.md に AGENTS.md の長い説明を移したのはなぜか

AGENTS.md のテスト表は 1 セルに 3,000 字の行があり、「まずどれを回すか」「触った場所に対応する検査はどれか」が読めなかった。
一方でその説明は「各検査が何を守っているか」の仕様そのもので、捨てられない。
そこで `test/README.md` を「まず回すもの」「一覧（目的 1 文・触ったら回す・前提・CI のジョブ）」「題材」「道具」「決まり」
「詳細」の順にし、長い説明は「詳細」の節に検査ごとの見出しで置いた。CONTRIBUTING.md の「テスト」の節は決まりだけを残し、
一覧はここへリンクする。

所要時間の目安は書かなかった。環境で大きく変わり、測っていない数字を書くと信用されなくなる。

## Q6. README の縮小と `package-info.java` の追加を今回に含めなかったのはなぜか

README を宣言どおり（目的・Quick start・CSV の読み方）に絞るには、出力ファイル・解決の段・ラムダ・キャッシュの節を
`docs/output-format.md` などへ移し、日本語と英語の両方を書き直す必要がある。文書だけで直せるが量が多く、
今回の「入口を作る」とは別の変更なので分けた。残り 10 パッケージの `package-info.java` は `src/jche` に触るので
1 ファイル版の生成し直しが伴い、これも分けた。どちらも次の段で行う。

## Q7. 見送った案

- **JUnit への移行**: 主な検査が「題材プロジェクトを解析して、期待値の CSV や全件解析の結果と比べる」形で、
  JUnit にしても速くも読みやすくもならない。依存ゼロ・実行 JDK 固定の利点も失う。理由を CONTRIBUTING.md に書くことで足りる
- **`src/main/java` への移動**: JBang の `//SOURCES`・`ToolRoot.locate` の目印・1 ファイル版の生成器・Eclipse 用 `pom.xml` の
  `sourceDirectory` に波及する。得るものは「見慣れた形」だけ
- **`docs/` の英訳**: 方針（[nls-qa.md](nls-qa.md) の Q12）どおり日本語のまま。索引の冒頭に英語の 1 行で「docs は日本語。使い方は
  README の英語側」とだけ書いた
- **`jche` パッケージ名の変更**: 拡張 API `jche.extension` の互換と 1 ファイル版の生成名に波及する
- **`Exporter` の改名（`Analysis` など）と `test/plugin*` の改名**: 効果はあるが `src/jche`・`smoke.yml`・文書に波及するので、
  文書だけの今回とは分けて判断する
- **`test/run-all.sh`**: 各検査の前提（Node・Maven・JDK 26）が違い、全部を 1 回で回す形は CI の分け方と合わない。
  「まず回すもの」の 3 つを test/README.md の先頭に置くことで代えた
