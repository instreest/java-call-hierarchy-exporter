# ツール全体の文言を英語・日本語で出し分ける — QA 一覧

> 画面の文言だけを英語・日本語にした Eclipse プラグインの話は
> [eclipse-plugin-nls-qa.md](eclipse-plugin-nls-qa.md) にある。こちらはその続きで、
> **解析本体（`src/`）・対話モード・起動コマンド**を対象にしたもの。

[eclipse-plugin-nls-qa.md](eclipse-plugin-nls-qa.md) の Q6 で
「ここを訳すのは、プラグインの話ではなく**ツール全体を多言語にする**という別の決断になる」と
宿題にしていた部分に着手した。**既定は英語**で、日本語を選んだときだけ日本語になる。
訳した文言は 418 件（`src/` が出すもの）＋ 42 件（起動コマンドが出すもの）。

| 変えたところ | 内容 |
|---|---|
| `src/jche/util/Messages.java` | 文言を引くクラス（新規）。JDK の標準 API だけで書いてある |
| `src/jche/util/MessagesEn.java` | 英語（既定。どの言語でも土台になる） |
| `src/jche/util/MessagesJa.java` | 日本語（英語に重ねる） |
| `java-call-hierarchy-exporter.sh` / `.cmd` | `msg <キー> [値…]` で 1 行出す。表は同じファイルの中に持つ |
| `config/config.properties` | `message.language`（空欄なら OS の言語）を足した |
| CSV を書く側（`report` / `server` / `graph` / `analysis`） | **セルの中身は言語に関わらず英語で固定**（Q6） |
| `eclipse-plugin/.../ServerLauncher.java` | 解析の子プロセスに `-Djche.lang=<画面の言語>` を渡す（Q8） |
| `test/nls/run.sh` | 上の一式の検査（新規） |

---

### Q1. なぜ既定を英語にしたのか。このツールは日本語圏向けではないのか

想定している利用者は日本語圏で、コメントもドキュメントも日本語である
（[AGENTS.md](../AGENTS.md) の「コードの決まり」）。それでも**出す文言は英語を既定にした**。
理由は Eclipse プラグインのときと同じで、**損をする人が少ない**からである。

- 日本語を既定にすると、英語の環境で使う人には**読めない文字列**が出る。
  逆に英語を既定にしても、日本語を選んだ人は日本語で読める
- 訳が足りない項目は英語のまま出る（英語に重ねる作りにしてある）。
  日本語を土台にしていたら、足りない項目が日本語で出てしまう
- Eclipse プラグインの画面が既に英語既定なので、そこだけ英語で解析ログだけ日本語、
  という食い違いが無くなる（Q8）

副産物として、**日本語 Windows 以外での文字化けが減る**。標準出力の文字コードは
コンソールに任せているので（`src/jche/CallHierarchyExporter.java` の冒頭）、
UTF-8 でないコンソールに日本語を出すと化ける。英語なら化けない。

### Q2. 表示言語は何で決まるのか

先に決まったものが勝つ。

| 順 | 決め方 | 効く範囲 |
|---|---|---|
| 1 | 環境変数 `JCHE_LANG`（`en` / `ja`） | 起動コマンドと解析の両方 |
| 2 | システムプロパティ `jche.lang` | 解析（プラグインが子プロセスに渡す。Q8） |
| 3 | 設定ファイルの `message.language` | 解析（設定ファイルを読んだあと） |
| 4 | OS（JVM の既定ロケール） | 全部 |

**環境変数を一番強くしてある**のは、検査スクリプトと CI が言語を固定できるようにするためである。
固定できないと、実行環境のロケールが違うだけでログの照合が壊れる
（`test/*/run.sh` は `JCHE_LANG=en` を輸出している）。設定ファイルより先に決まるので、
設定ファイルを読む前に出るエラー（ファイルが無い等）にも効く。

`message.language` を設定ファイルに置いたのは、設定ごとに言語を変えたい場合
（英語の同僚に渡すログだけ英語にする、など）のため。`launcher.properties` に
`JCHE_LANG=ja` と書けば、起動コマンドの文言もまとめて決まる。

地域（`ja_JP`）は言語（`ja`）だけ見る。地域まで分ける訳を持つ予定が無く、
持つときになってから足せばよい。訳を持たない言語（`fr` 等）は英語に落ちる。

### Q3. なぜ properties ファイルではなく Java のクラスに文言を置いたのか

Eclipse プラグインは `messages.properties` を `ResourceBundle` で読んでいる。
同じ作法にしたかったが、`src/` では**採れなかった**。

`src/` のクラスは、次のすべてから使われる。

- jbang（`//SOURCES`）
- ルートの `pom.xml`（`<sourceDirectory>src</sourceDirectory>` だけで、リソースの指定が無い）
- `eclipse-plugin/pom.xml`（`jche/**` を取り込んでプラグインの jar に入れる）
- VSCode プラグインの配布物（`.vsix`）
- GitHub Actions の複合アクション
- **`javac -d <出力先>` で直接コンパイルしている 7 本の検査スクリプト**
  （`test/cachetail` / `cachevalue` / `conditions` / `contracts` / `dataflow` / `incremental` / `server`）

properties にすると、このすべてに「リソースを一緒に配る」処理が要る。
そして 1 か所でも漏れると、**例外も警告も出ずに画面にキー名（`!キー!`）が出るだけ**になる。
動かしてみるまで気づけない壊れ方なので採らなかった。

文言の表を**ただの Java のクラス**（`MessagesEn` / `MessagesJa`）にすれば、
`//SOURCES *.java **/*.java` が既に拾うのでビルド側の変更が 1 つも要らず、
「表が配られていない」状態がコンパイル時に起きえない。

分野ごとにメソッドを分けてあるのは、メソッド 1 つ（とクラス初期化）の大きさの
上限が 64KB だからである。文言が増えても、分野を足せば上限に当たらない。

### Q4. `Messages` が 2 つあるのは重複ではないのか

`jche.util.Messages`（解析本体）と `jche.eclipse.Messages`（プラグインの画面）の 2 つがある。
重複だが、**1 つにはできない**。

- プラグインは `--release 11` でコンパイルする（下限が Eclipse 4.17 / Java 11。
  [eclipse-plugin-java-floor-qa.md](eclipse-plugin-java-floor-qa.md)）。
  解析本体は `--release 17` で、別のコンパイル単位である
- 文言の置き場所も別である（Q3 のとおり、片方は properties、片方は Java のクラス）
- 画面の文言と解析の文言は、そもそも別の集合である

引き方（`get` / `format`、英語に日本語を重ねる 2 段、自前の `{0}` 置換）は
完全にそろえてあるので、読む側が迷うことは無い。

### Q5. 差し込みに `MessageFormat` を使わないのはなぜか

Eclipse プラグインと同じ理由である。`MessageFormat` は `'` を引用符として解釈するので、
英語の文に `don't` と書くと、そこから先の `{0}` が差し込まれなくなり `'` も消える。
**動かすまで気づけない壊れ方**で、しかも壊れるのは英語の側（日本語に `'` はまず出てこない）なので、
日本語で確かめている限り見つからない。

差し込みに要るのは「値をそのまま入れる」ことだけで、桁区切りや日付の書式は要らない。
`{数字}` を引数で置き換えるだけの 20 行を自分で書いてある。`'` はただの `'` である。

差し込みの番号と数が英語と日本語で食い違うと、値が出ない・`{0}` がそのまま出る。
これは `test/nls/run.sh` が両方の表を突き合わせて検出する。

### Q6. 出力 CSV を訳さないのはなぜか

**CSV のセルの中身は、表示言語に関わらず英語で固定**した。対象は次のもので、
どれも以前は日本語だった。

| 出力 | どの列 | 例 |
|---|---|---|
| `call-hierarchy.csv` | 階層の末尾の注記 | `[UNEXPANDED:CHA] 2 candidates: field` |
| `methods.csv` | `unresolvedCause` / `absentCause` | `[NOT_REACHED] no caller row was emitted` |
| `call-conditions.csv` | `condition` / `subjectKind` | `switch (kind) case 1` / `param 1` |
| 被参照の行 | `call-hierarchy` 列 | `external-ref:EXACT` |
| プラグインの `EXPORT` | `note` 列 | `recursive` / `depth-limit` |

**あれは人向けの文章ではなく、出力のデータだから**である。

- 回帰テストの期待値（`test/regression/*/expected*/`）と突き合わせる。
  言語で変わると、実行環境のロケール次第で CI が落ちる
- Excel のフィルタや `grep` の条件として、利用者自身が書き写して使う
  （[note-tags-qa.md](note-tags-qa.md) の「タグで一括で拾える」）
- 他のツールへ渡したとき、受け取る側が言語を選べない

言語の設定を変えたら CSV の中身も変わる、という作りにすると、
**同じプロジェクトの 2 回の出力を diff できなくなる**。これが決め手になった。

あわせて、注記に**カンマを入れないこと**にした。カンマがあると `Csv.esc` がセルを
引用符で囲むので、行末の `grep` が効かなくなる。区切りが要るところは `/` を使う
（`type resolution failed (missing classpath / dynamic call / etc.)`）。

期待値（`expected*/`）は、新しい出力をコピーするのではなく**置換で訳した**。
言語以外の差（行の増減・列の変化）が紛れ込んでいないことを、
回帰テストが通ることで保証するためである。

### Q7. 文言を変えただけなのに、なぜ dataflow キャッシュの版を上げたのか

[cache-design.md](cache-design.md) と `CacheFormat` の決まりでは、
「読み手だけの変更（解決ラベル、CSV の列、フィルタ、**文言**）では版を上げない」。
今回の変更はほとんどそれに当たるが、**1 つだけ例外があった**。

条件式の説明（`GuardCollector` が作る `text`。`switch (kind) case 1` のような文字列）は、
**読み手ではなく書き手が作って、キャッシュの P 行に焼き込まれる**。
版を上げずにおくと、古いキャッシュを再利用したファイルだけ日本語の注記が出て、
**同じ CSV に 2 つの言語が混ざる**。

そこで `DATAFLOW_VERSION` を v5 → v6 に上げた。上げる側は
「呼び出し階層の出力には影響しない」ほう（`docs/cache-split-qa.md`）なので、
全件再解析は起きるが出力とその期待値は動かない。

判断の基準はこうなる。**その文字列を作っているのが書き手か読み手か**を見る。
読み手（`StreamingTreeWalker` の注記、`UnresolvedReport` の理由）なら版は要らない。
書き手（`Guard` の `text`）なら要る。

### Q8. プラグインの画面と解析ログの言語をどうそろえたか

解析は別プロセス（`--server`）で動き、そのログはプラグインの画面のコンソールに流れる
（[out-of-process-analysis-design.md](out-of-process-analysis-design.md)）。
プロセスが別なので、プラグインの画面が英語でも、解析側は OS の言語で動いてしまう。

Eclipse プラグインは、子プロセスを起こすときに
`-Djche.lang=<画面の言語>`（`Messages.language()`）を渡すようにした。
これで画面と解析ログが必ずそろう。[eclipse-plugin-nls-qa.md](eclipse-plugin-nls-qa.md) の Q6 で
「バナーの前半は訳されるが、後半（子プロセスから返ってくる理由）は日本語で出る」と
書いていた食い違いが、これで無くなる。

VSCode プラグインは**画面がまだ日本語だけ**なので、そろえて `ja` を渡している。
画面を多言語にするときに `vscode.env.language` から決めるようにする（Q12）。

### Q9. 起動コマンド（`.sh` / `.cmd`）はどう出し分けているのか

シェルには `ResourceBundle` が無いので、`msg <キー> [値…]` で 1 行出す関数を置き、
英語と日本語の表を同じファイルの中に持つ。日本語に無いキーは英語へ落ちる（`.sh`）。
表の外に日本語の出力が残っていないことは `test/nls/run.sh` が見る。

言語の決め方はファイルごとに違う。

- `.sh` … `JCHE_LANG` → ロケール（`LC_ALL` → `LC_MESSAGES` → `LANG`）
- `.cmd` … `JCHE_LANG` → **画面のコードページ**（932 なら日本語）

`.cmd` でロケールを照会しないのは、**このファイルが MS932 だから**である
（[cli-app-qa.md](cli-app-qa.md) の Q15）。日本語を化けずに出せるのはコードページが
932 のときだけなので、「出せるかどうか」と「出すかどうか」がそろう。
`chcp` の出力から番号を取るとき `%VAR:検索=置換%` を使わないのは、
未定義のとき cmd がバッチごと落ちるためである
（[network-download-confirm-qa.md](network-download-confirm-qa.md) の Q16。
`test/cli/run.sh` がこの書き方を検出する）。

どちらも `launcher.properties` を読んだあとに言語を決め直すので、
そこに `JCHE_LANG=ja` と書いておけば取得の確認も日本語で出る。
初回の置き場所の質問だけは `launcher.properties` がまだ無い時点なので、
そこは環境変数か OS の言語で決まる。

### Q10. 画面の桁合わせはどうしたのか

対話モードの状態表示のように、ラベルの幅をそろえている画面がある。
`" ツールのフォルダ : " + root` のように**ラベルだけ**をキーにすると、
英語と日本語で幅が違うので、どちらかの桁が崩れる。

**1 行をまるごと 1 つのキー**にした（`cli.status.toolDir = " Tool folder             : {0}"`）。
こうすると言語ごとに自分で桁を合わせられる。訳す量は増えるが、
「訳したら画面が崩れた」が起きない。

### Q11. コメントとドキュメントはなぜ日本語のままなのか

読む相手が違うからである。文言は**利用者**が読み、コメントとドキュメントは
**このリポジトリを触る人**が読む。後者は日本語で書くと決めてある
（[AGENTS.md](../AGENTS.md)）。Eclipse プラグインのときと同じ切り分けである。

コミットメッセージも日本語のまま。

### Q12. 訳していないものは何か

| もの | 状態 | 理由 |
|---|---|---|
| `docs/` と `README.md` | 日本語のまま | 量が桁違い。引用されている CSV の値だけは実際の出力（英語）に合わせた |
| `config/config.properties` のコメント | 日本語のまま（`message.language` の項だけ英語を併記） | 設定を書く人向けの長い説明。訳すなら言語ごとのひな形を持つ形になる |
| VSCode プラグインの画面 | 日本語のまま | `package.nls.json` と `vscode.l10n` という別の仕組みが要る。解析ログはそろえて `ja` を渡している（Q8） |
| `action.yml` の入力の説明 | 日本語のまま | CI の利用者向け |
| `single-file/` のログ | 日本語のまま | お試し版の 1 ファイルに `Messages` を丸ごと持ち込む価値が無い。**CSV の注記だけ**は本体に合わせた（「タグは本体と同じ」を保つため） |

### Q13. 検査は何を見ているのか

`test/nls/run.sh` が 6 点を見る。どれも「動かしてみるまで気づけない」ものである。

1. `src/` に日本語の文字列リテラルが残っていないこと
2. 使っているキーが英語の表にあり、使っていないキーが残っていないこと
3. 英語と日本語でキーと差し込み（`{0}` `{1}` …）の番号・数がそろうこと
4. 起動コマンドの表でキーがそろい、表の外に日本語の出力が無いこと
5. 実際に読ませて、既定が英語・優先順位どおりに切り替わること。
   訳の無い言語は英語に落ち、無いキーは `!キー!` で見えること
6. 同じ設定を英語と日本語で解析し、**出力 CSV が 1 バイトも変わらない**こと
   （ログのほうは変わること。変わらないなら、そもそも言語が切り替わっていない）

6 を入れたのは、Q6 の決まりがコードの都合で崩れるのを止めるためである。
CSV を書く経路のどこかで `Messages` を呼んでしまうと、この 1 つで落ちる。

### Q14. 既存の検査（`test/plugin-nls/run.sh`）が何も見ていなかった件

プラグイン側の「日本語の文字列リテラルが残っていないこと」の検査は、
**1 件も検出できない状態だった**。原因は 2 つ重なっていた。

- perl に `-CSD` が無く、ファイルを元のバイト列のまま扱っていた。
  `\x{3040}-` のような範囲は、UTF-8 のバイト列には 1 文字も当たらない
- コメントを先に消してから文字列を探していた。文字列の中に `//` や `/*`
  （URL や正規表現）があると、そこから先を消してしまう

実際、`server/JdkDownload.java` の日本語 10 件が素通りしていた
（取得の失敗を知らせる文言で、英語の Eclipse でも日本語で出ていた）。

コメント・文字列・文字リテラルを**頭から順に読み分ける**形に直した
（この並びの最初に当たったものを 1 つの塊として食べる）。これで
「文字列の中のコメントらしきもの」で消えることが無くなる。
`test/nls/run.sh` も同じ書き方にしてある。

検査を書いたら**わざと壊して落ちることを確かめる**、が教訓である。
今回の 6 点はすべて、1 つずつ壊して落ちることを確認した。
