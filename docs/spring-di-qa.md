# Spring による DI の解決 — 実装時の QA 一覧

[Issue #66](https://github.com/instreest/java-call-hierarchy-exporter/issues/66)
「Spring により DI されたインスタンスによるメソッド呼び出し階層を解析したい」への対応で、
迷ったこと・困ったことと、その結論を Q&A の形で残す。

対応の要点:

- キャッシュ（v13）に、型（H 行）・メソッド（D 行）・フィールド（V 行）のアノテーションを
  「事実」として追加する（`jche.cache.AnnotationTokens`）
- 読み手に `jche.graph.SpringBeans` を足し、ステレオタイプ注釈の付いた具象型と
  `@Bean` メソッドが返す具象型を Bean として集める
- `CallResolver` に段5 `SPRING_DI` / `SPRING_DI_QUALIFIER` を足し、CHA で絞れなかった候補を
  「コンテナが実際に注入しうる Bean」だけに絞る。1 つに定まるときだけ確定する
- 設定に `spring.di.enabled`（既定 true）と `spring.di.bean.annotations`（独自のステレオタイプ注釈）を足す
- `test/demo/src/fx/di/` に確認用のソースを置く（Spring の注釈は
  `test/demo/src/org/springframework/` にスタブを置き、本物の Spring には依存させない）
- （PR #167 の見直しで改めた）段 5 を、レシーバがコンテナの値を入れうる注入点のときだけに限り、経路で具象型が
  分かればそちらを採る（Q5・Q6。`docs/value-safety-qa.md` の Q23）

---

## 設計の判断

### Q1. アノテーションはキャッシュに入れる「事実」か、読み手の「判断」か

`CacheFormat` の原則は「キャッシュは AST から分かった事実だけを持ち、判断は読み手でする」。
アノテーションが宣言に付いているかどうかは AST から機械的に読み取れる事実なので、キャッシュに入れる。
一方「`@Service` が付いていたら Bean」「`@Qualifier` の値は Bean 名」は解決方針そのものなので、
読み手（`SpringBeans`）に置いた。Spring 以外の DI コンテナに対応したくなっても、
キャッシュを作り直さずに読み手だけを変えれば済む。

### Q2. すべてのアノテーションを記録すると、キャッシュが太らないか

太る。`@Override` は多くのメソッドに付くので、全件記録すると D 行が軒並み伸びる。
そこで**書き手の打ち切り**として `java.lang` のアノテーション（`Override`、`SuppressWarnings`、
`Deprecated` 等）は落とした。どの型が動くかに一切関わらないうえ、数が多いのはこの一群だから。
「どの注釈が DI の印か」で絞らなかったのは、それを書き手に持たせると読み手の方針を変えるたびに
全件再解析になるため（Q1 と同じ理由）。

値は「単一メンバ」または `value` / `name` が文字列のものだけ残す。DI コンテナが Bean を
見分けるのに使うのは名前の文字列だけで、クラス参照や配列（`@Transactional(rollbackFor=...)` 等）は
使い道が無いのに長い。

### Q3. 注釈は FQN と単純名のどちらで照合するか

キャッシュには FQN を書き、照合は**単純名でも通す**ようにした（`AnnotationTokens.has`）。
理由は2つ。

- Spring のステレオタイプ注釈は `@Service` を合成した独自注釈（メタアノテーション）として
  定義されることが多い。`jp.co.xxx.MyDomainService` のような名前でも、
  `spring.di.bean.annotations=MyDomainService` と単純名で書けるほうが設定しやすい
- 解析対象に Spring の jar が渡っていない場合、JDT は注釈の型を解決できず FQN を取れないことがある。
  単純名なら、その場合でも印として拾える

副作用として、たまたま同じ単純名の別パッケージの注釈も Bean の印として拾ってしまう。
Bean が複数になれば絞らずに候補を残すだけなので、誤って絞る方向には効きにくいと判断した。

### Q4. どの段に入れるか（拡張・データフローとの順番）

段5、拡張（段3）とデータフロー（段4）の**後**、CHA（段6）の直前に置いた。

- 拡張はプロジェクト固有の知識で、利用者が明示的に差し込んだもの。汎用の推定より優先する
- データフローは「実際に代入された値」を追った結果で、コンテナの構成から推定する DI より根拠が強い
- どちらでも決まらず、そのままなら `CHA`（低確度・複数候補）で終わる呼び出しだけを対象にする。
  すでに1つに定まっている呼び出しの結論を、DI の推定で**上書きしない**
- 逆に、段 5 で絞った結論は、経路を歩く側で実際に渡った値の具象型が分かればそちらで置き換える（Q5）

### Q5. どの呼び出しに適用するか

レシーバがコンテナの値を入れうる**注入点**のときだけに限る（`CallResolver.isInjectionPoint`。PR #167 の見直しで改めた）。

| レシーバ | 注入点とみなす条件 |
|---|---|
| フィールド（`RecvKind.FIELD`） | 値の表で `this` のフィールドと分かり（`F:型#名前`。`other.f` は値にしない。`docs/value-safety-qa.md` の Q19）、`@Autowired` / `@Inject` / `@Resource` が付いているか、ステレオタイプ注釈の Bean（またはその部分型が Bean である基底クラス）の static でないフィールド |
| 引数（`RecvKind.PARAM`） | その呼び出しを書いたメソッドが、`@Autowired` / `@Inject` / `@Resource` を付けたメソッド・コンストラクタ、`@Bean` メソッド、ステレオタイプ注釈の Bean（またはその基底クラス）のコンストラクタのどれか。値の表で引数（`A:`）と分かること（本体で書き換えた引数は外れる）。ラムダの本体の引数は含めない |

DI で受け取ったインスタンスは、フィールド注入・コンストラクタ注入・setter 注入のいずれでも最終的にこの形で現れる。
その場で `new` したレシーバ（段2で解決済み）や static 呼び出しは今までどおり対象にしない。

段 5 で絞った呼び出しも、経路を歩く側（`CallResolver.resolveOnPath`）で、実際に渡った値の具象型が分かればそちらを採る。
Bean のコンストラクタや `@Autowired` のメソッドも、利用者のコード（テスト・手組みの生成）が直接呼んで Bean でない
実装を渡せるからである。値を追った結果はコンテナの構成からの推定より根拠が強い（Q4 と同じ理由）。

**値を読まない指定**（`dataflow.enabled=false`）では、レシーバがどのフィールドかが値の表にしか無いので、
フィールドは「呼び出しを書いたメソッドの型が Bean（またはその基底）か、その型か親に `@Autowired` 等の付いたフィールドが
ある」とき、引数は上と同じ条件（メソッドで決まる）で注入点とみなす。値を読むときより粗く、Bean の中で static
フィールドや別のインスタンスのフィールドを呼ぶ形は絞りうる。値を読まない指定でも DI の絞り込みが効くことは
`config/config.properties` が約束しているので、フィールドを識別できないからといって段 5 をまるごと止めることはしなかった。

以前は「レシーバがフィールドか引数なら何でも」絞っていた。次の形で、実際に動く実装の呼び出しを落としていた
（`docs/value-safety-qa.md` の Q23。`test/pruning/run.sh` の SbPlainParam・SbPlainField・SbManual と、値を読まない指定の Plain.proc）。

```java
@Repository class DaoA implements Dao { … }
class DaoB implements Dao { … }
public class S1 {                          // Bean ではない
    static void process(Dao d) { d.find(); }          // → DaoA.find だけ（実際は DaoB）
    public static void main(String[] a) { process(new DaoB()); }
}
public class S2 {                          // Bean ではない
    private final Dao dao;
    S2(Dao d) { this.dao = d; }
    void go() { dao.find(); }                          // → DaoA.find だけ（DaoA か DaoB）
}
```

却下した案:

- **`@Autowired` 等の注釈が付いた注入点だけに限る**。注釈を付けないコンストラクタ注入（Q6）がまるごと外れる
- **引数はどれも対象にしない**。`@Autowired` の setter・`@Bean` メソッドの引数・Bean のコンストラクタの引数を
  その場で呼ぶ形（`Svc(Repo r) { r.init(); }`）が絞れなくなる
- **経路の値で覆さない**（以前の Q4 の「上書きしない」をそのまま当てる）。Bean のコンストラクタを利用者が
  `new Svc(new StubRepo())` と呼ぶ経路で、渡したスタブの呼び出しを落とす。Q4 の「上書きしない」は、段 1〜4 で
  既に 1 つに決まった結論を DI の推定で覆さないという意味で、DI の推定を後から分かった値で覆すことは妨げない

### Q6. 注入点（`@Autowired` が付いたフィールド）であることを条件にしなかったのはなぜか

（PR #167 の見直しで改めた。以前は「条件にしない」だった。）

注入点であることは条件にする（Q5）。ただし **`@Autowired` の注釈は必須にしない**。Spring のコンストラクタ注入は、
注釈を付けずに「コンストラクタが1つだけならそれを使う」形が推奨されており、フィールドにも注釈が付かない。
そこで、ステレオタイプ注釈の Bean（コンテナがインスタンスを作る型）のコンストラクタの引数と static でない
フィールドも注入点に数える。`@Bean` メソッドが返す型は数えない（その型のコンストラクタは利用者のコード＝`@Bean`
メソッドが呼ぶので、何を渡すかはそのコード次第）。

以前は「候補を Bean だけに絞る条件は注入点の有無と独立に効く」として、注入点かどうかを見ていなかった。
これは「そのレシーバにはコンテナが入れた値しか来ない」ことを暗黙に仮定しており、Bean でないクラスの引数や
フィールド（利用者が何を入れてもよい）では成り立たない。**呼び出しを静かに落とさない**方針に反するので改めた。
`@Qualifier` / `@Resource(name)` の指名を読むのは、これまでどおり注釈の付いたフィールドだけ。

### Q7. `@Primary` で1つに決めてよいか

決めない。`@Primary` は「同じ型の Bean が複数あるときの既定」だが、
`@Qualifier` の指定や `@Profile` / `@Conditional` の条件、テスト用の上書き定義で簡単に覆る。
`FieldFacts` と同じ判断（「絞れないことより、誤って絞ることの方が害が大きい」）で、
候補が複数のままなら CHA として複数を残す。同じ理由で `@Profile` / `@Conditional` も見ない。

### Q8. コンストラクタ引数の `@Qualifier` を読まないのはなぜか

事実として持っていないため。いまのキャッシュはメソッドの**引数**のアノテーションを記録していない
（D 行はメソッド自身の注釈だけ）。引数ごとの注釈を足すと列が増え、
どの引数がどのフィールドに入るかを追う判定（`FieldFacts` の経路）も必要になる。
`@Qualifier` が無くても「候補のうち Bean が1つだけ」なら解決できるので、
まずはフィールド単位の注入点だけを見る形にした。必要になった時点で D 行に足せる。

### Q9. `@Bean` メソッドが登録する型はどう決めたか

`@Bean` メソッドの戻り値の宣言型はインターフェース（`Clock` など）であることが多く、
それだけでは具象型が分からない。そこで R 行（戻り値の出所）を使い、
**返しうる出所がすべて同じ `new 具象型`** のときだけ、その具象型を Bean として登録する。
分岐して複数の型を返しうるメソッドは、どれが登録されるか静的には決まらないので登録しない。
R 行はメソッドの ID が全部揃ってからでないと引けないので、
`CallGraphBuilder` の1回目のスキャンの直後（`allocateEdges`）で確定させている。

（あとから直した）登録しないだけでは足りなかった。返す具象型の決まらない `@Bean` メソッドの Bean が数えられず、
ステレオタイプの Bean が 1 つだけ残ると段5がそれに絞って、`@Bean` の実装への呼び出しを落とした。値を読まない指定
（`dataflow.enabled=false`）では R 行を読まないので、すべての `@Bean` メソッドがこの形になっていた。今は、決まらない
`@Bean` メソッドの Bean を「宣言した戻り値の型（D 行）とその部分型のどれか」として数え、候補の型が触れる呼び出しは
段5で絞らない（[value-safety-qa.md](value-safety-qa.md) の Q17）。

### Q10. Bean がメソッドをオーバーライドしていない場合に取りこぼさないか

取りこぼす形だったので、候補の作り方を変えた。CHA の候補は「そのメソッドを**オーバーライドしている
宣言**」の集合なので、`@Service class CardPayment extends AbstractPayment` が `pay` を
オーバーライドしていないと、候補には `AbstractPayment#pay` しか現れず「その型が Bean か」を
照合できない。そこで段5では候補を作り直し、宣言型の下位型のうち Bean であるものから
`CallGraph.implementationIn`（親クラスを辿って実装を探す）で実装を引く。
`test/demo/src/fx/di/CardPayment.java` がこの形。

### Q11. Bean 名の既定（`@Service` に値が無いとき）は何か

Spring の既定と同じく「単純名の先頭を小文字にしたもの」（`CardPayment` → `cardPayment`）。
ただし先頭2文字が大文字のとき（`URLShortener`）は Spring も小文字化しないので、そのままにした。
この名前は `@Qualifier` の指名と突き合わせるときにだけ使う。

## テストで困ったこと

### Q12. Spring の jar が無い環境で、どうやってテストするか

`test/demo` は依存 jar 無しで解析できることが前提なので、Spring 本体は入れられない。
`test/demo/src/org/springframework/` に注釈のスタブ（`@Service` 等の `@interface`）を置き、
解析対象のソースとして一緒に読ませた。実際のパッケージ名と同じにしてあるので、
FQN での照合も単純名での照合も同じように通る。

### Q13. 期待出力（`expected/`）の作り直しで、既存の行が変わっていないか

`test/demo/src` にソースを足したので、`whole` / `entry` / `jarchange` の期待出力を作り直した。
差分が**追加だけ**（削除・変更が 0 行）であることを `diff` の `<` 行が空であることで確認してから
コピーした。既存の解決結果を変えていないことの確認になる。

### Q14. キャッシュのバージョンは上げる必要があるか

上げた（v12 → v13）。H 行・D 行・V 行に列が増え、収集する事実の範囲も変わったので、
`CacheFormat` の基準どおり。古いキャッシュは自動的に破棄され、次の実行で全件解析し直される。
