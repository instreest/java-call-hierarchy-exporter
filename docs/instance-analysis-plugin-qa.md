# インスタンス解析条件を外部からプラグインする — 実装時の QA 一覧

[Issue #68](https://github.com/instreest/java-call-hierarchy-exporter/issues/68)
「インスタンス解析条件を外部からプラグインしたい」の対応で、迷ったこと・困ったことと、その結論を
Q&A の形で残す。

対応の要点:

- 拡張クラスの置き場所 `plugin.folders` を足した。**`.java` を置くと実行時にコンパイルされる**
  （`.class` / `.jar` を置いてもよい）。利用者はビルドツールを用意しなくてよい
  （[PluginClassLoaders](../src/jche/config/PluginClassLoaders.java)）
- 対応表だけで済む用途のために、拡張の実装を 2 つ同梱した
  （[FactoryKeyCollector](../src/jche/builtin/FactoryKeyCollector.java) /
  [TypeMappingProvider](../src/jche/builtin/TypeMappingProvider.java)）。Java を書かずに設定と対応表ファイルだけで使える
- 手がかり（証拠）を結び付けるキーの作り方を [HintKeys](../src/jche/extension/HintKeys.java) に一本化した。
  本体（`FactVisitor`）も同じものを使う
- フェーズAの拡張はキャッシュの中身を変えるので、その指紋をキャッシュのヘッダ行に入れ、
  拡張を変えたら自動で作り直すようにした
- 回帰テストに `plugin` ケースを足した（`test/regression/plugin`、解析対象は `test/plugin-demo`）

---

## 設計（どの方式にするか）

### Q1. 「プラグイン方法が確立していない」とは、何が足りなかったのか

拡張ポイントのインターフェース（`CallSiteHintCollector` / `TypeCandidateProvider`）と、
設定に書かれた FQN を `Class.forName` で読む仕組みは以前からあった。足りなかったのは
**利用者が書いたクラスをそのクラスパスに載せる手段**。このツールは JBang でソースのまま動くので、
利用者のクラスを置く場所がどこにも無く、`Class.forName` は必ず `ClassNotFoundException` になっていた。
つまり「拡張ポイントはあるが、拡張を届ける経路が無い」状態だった。

### Q2. 読み込み方式は何を検討し、なぜ「.java を実行時にコンパイル」にしたのか

4 案を比べた。

| 案 | 内容 | 採否 |
| --- | --- | --- |
| A | `plugin.folders` の `.java` を実行時にコンパイルして読む | **採用** |
| B | `plugin.folders` の `.jar` / `.class` だけを読む | 採用（Aに含まれる。単体では不採用） |
| C | `ServiceLoader`（`META-INF/services`）＋ JBang の `//DEPS` | 不採用 |
| D | 外部プロセスを起動し、標準入出力で証拠と候補をやり取りする | 不採用 |

決め手は**利用者の手間がツール本体の流儀と釣り合うか**。このツール自身が「JDK も依存 jar も自動で
取ってきてソースのまま動く」ことを売りにしているのに、拡張のためだけに Maven や Gradle を用意させ、
jar を作らせるのは釣り合わない。A なら `.java` を 1 つ置くだけで済む。

B は実装は最小だが、利用者に別途ビルド環境を要求する。ただし「社内で共有する拡張を jar で配りたい」
需要はあるので、同じフォルダに `.jar` / `.class` があれば読む形で取り込んだ（A は B を含む）。

C は Maven Central に公開された拡張なら綺麗だが、今回の用途（社内の DI 設定に合わせた一回限りの拡張）には
公開・版管理の手間が重すぎる。D は言語を選ばない代わりに遅く、AST 相当の情報を渡す形式を決めるだけで
大仕事になる。呼び出し 1 件ごとにプロセス間通信するのは現実的な速度にならない。

### Q3. なぜ「対応表を読む実装」を同梱したのか。仕組みだけで十分ではないか

Issue が挙げるユースケース（DI 設定ファイルによるインスタンス特定、ファクトリメソッドの生成条件）を
突き詰めると、どちらも**「この宣言型（またはこの手がかり）のときは、この具象クラス」という対応表**になる。
その形なら Java を書かせる必要が無い。DI 設定ファイルからの対応表は、利用者が既に持っている設定ファイルから
機械的に書き出せることが多い（`grep` と置換で済む程度）。

同梱したのは、`plugin.folders` に置いた自前の実装と同じインターフェースの、ただの実装クラスである。
特別扱いはしておらず、設定に FQN を書いて読み込む点も同じ。そのため**書き方の手本**にもなる。
自分で書く必要があるのは、設定ファイルの形式が独自で対応表に落とせない場合だけ。

### Q4. 同梱の実装を「設定にキーがあれば自動で有効」にしなかったのはなぜか

`plugin.mapping.files` を書いたら `TypeMappingProvider` が勝手に動く、という形も考えたが採らなかった。
拡張は解析結果を変えるものなので、「何が効いているか」が設定ファイルの 1 行を見て分かるほうがよい。
自動で有効になると、キーの書き間違い（`plugin.mapping.file` と単数で書く等）が「何も起きない」で終わり、
原因を追いにくい。`resolver.candidate.providers` に FQN を書く形なら、読み込みの成否がログに必ず出る。

## 実行時コンパイル

### Q5. コンパイルのクラスパスに何を渡すか

このツール自身のクラスパス（`java.class.path`）をそのまま渡し、`plugin.folders` の jar を足す。
拡張は `jche.extension.*` を実装し、フェーズAの拡張は JDT の AST（`MethodInvocation` 等）を触るので、
どちらも本体と同じクラスパスが要る。JBang が組み立てたクラスパスがそのまま `java.class.path` に入るため、
JBang 経由でも `java -cp` 経由でも同じように動く。

### Q6. コンパイル結果をどこに置くか。毎回コンパイルし直して遅くないか

キャッシュフォルダの下（`<cache.folder>/<プロジェクト>_<ハッシュ>/plugin-classes_<plugin.folders のハッシュ>`）に置き、**毎回作り直す**（同じプロジェクトを指す別設定が別の plugin.folders を持っても取り合わないよう、フォルダ名に plugin.folders のハッシュを添える）。

差分コンパイル（`.java` が新しいときだけ）も考えたが、拡張は普通 1〜数ファイルで、コンパイルは 1 秒未満。
一方で「消した `.java` のクラスが残って動き続ける」事故は原因が分かりにくい。速度の利得より
確実さを採った。出力先を毎回消してから作り直すのはこのため。

### Q7. コンパイルに失敗したらどうするか

警告としてコンパイラのメッセージを 1 行ずつ出し、**拡張なしで解析を続ける**。
解析そのものは拡張が無くても成立する（CHA で候補が広がるだけ）ので、止める理由が無い。
ただし黙って続けると「拡張を置いたのに効かない」ことに気づけないため、メッセージは必ず出す。
読み込み失敗・初期化失敗も同じ方針にした。

### Q8. `ToolProvider.getSystemJavaCompiler()` が null になる場合は

JRE で動いている場合に null になる。JBang は JDK を取ってくるので通常は起きないが、
起きたときは「JDK ではなく JRE で動いています。コンパイル済みの `.class` か `.jar` を置いてください」と
警告して続ける。`.jar` / `.class` を置く経路は生きているので、この環境でも拡張自体は使える。

### Q9. クラスローダの親を何にするか

`PluginClassLoaders` 自身のクラスローダ（＝本体のクラスローダ）を親にした。
親を `null`（ブートストラップ）にすると、拡張が実装する `TypeCandidateProvider` が別のクラスローダから
読まれた同名の別クラスになり、`type.cast(o)` が `ClassCastException` になる。
親優先の通常の委譲なので、拡張が独自に持ち込んだ jar だけがこちらで読まれる。

## キャッシュとの関係

### Q10. 拡張を変えたのにキャッシュが古いまま、にならないか

なる。それを防ぐために、**フェーズAの拡張の指紋をキャッシュのヘッダ行に入れた**。
指紋は「拡張クラス名 ＋ `plugin.` で始まる設定 ＋ `plugin.folders` 配下のファイルの更新時刻とサイズ」の
ハッシュ。ヘッダ行が違えば旧キャッシュは丸ごと捨てられる（ソースレベルや JDK と同じ扱い）。
これで、拡張の実装を書き換えても、対応表のキーを増やしても、次の実行で自動的に解析し直しになる。

### Q11. なぜフェーズAだけで、フェーズBは指紋に入れないのか

フェーズA（`CallSiteHintCollector`）はキャッシュに X 行（手がかり）を書き込むので、
拡張が変われば**キャッシュの中身**が変わる。フェーズB（`TypeCandidateProvider`）は
キャッシュを読んだ後のグラフ構築時に働くだけで、キャッシュには何も書かない。
毎回ゼロから実行されるので、指紋に入れる必要が無い（入れると無駄な再解析になる）。

### Q12. 拡張を使っていない利用者のキャッシュまで捨てさせないか

フェーズAの拡張が 1 つも設定されていないときは、指紋を空文字にしてヘッダ行に項目自体を足さない。
そのため、拡張を使わない利用者のヘッダ行は従来と 1 バイトも変わらず、既存のキャッシュはそのまま有効。
「機能を足しただけで全員が全件再解析」を避けるための作り。

## 手がかりを結び付けるキー

### Q13. `HintSink.add` の scopeKey が合っていないと、どうなるか

**何も起きない**。手がかりは `呼び出し元メソッドのキー|レシーバのキー` で呼び出しに結び付くので、
1 文字でも違えば結び付かず、拡張は正しく動いているのに解決だけされない。しかも警告も出ない
（「結び付かなかった手がかり」は、単に別の呼び出し用の手がかりかもしれないので、警告にはできない）。

拡張の作者が一番はまりやすいのはここだと考え、キーの計算を
[HintKeys](../src/jche/extension/HintKeys.java) に一本化した。本体の `FactVisitor` も同じものを使うので、
実装が 2 つに分かれて食い違うことがない。

### Q14. `HintKeys` を作ったとき、本体側の挙動は変わったか

1 か所だけ変わった。レシーバのキーは空白を `_` に潰していた（キャッシュがタブ区切りの 1 行なので、
バインディングキーに空白が入ると列が崩れる）が、`new` の手がかりを書く側はそれをしていなかった。
バインディングキーに空白が入る形（ジェネリクスやラムダを含むもの）では、この 2 つが食い違って
手がかりが結び付かなくなる。`HintKeys` に寄せたことで両者が同じになり、この食い違いは消えた。
回帰テストの期待出力は変わらなかった（既存のサンプルには空白を含むキーが無かった）。

### Q15. 変数に受けない呼び出し（`DaoFactory.get("K").find()`）はどう扱うか

レシーバが変数でない場合、キーは式の開始位置（`"@位置"`）になる。同梱の `FactoryKeyCollector` は
まず「戻り値を受けている変数」を探し、無ければ呼び出し式そのものの位置をキーにする。
`HintKeys.ofAssignedVariable` が変数宣言（`Dao d = ...`）と代入（`d = ...`）の両方を見るので、
どちらの書き方でも後続の `d.find()` と結び付く。回帰テストではこの 2 通りを別々のメソッドで確認している。

## 対応表の形式

### Q16. 手がかりの区切りに `:` を使えなかった理由

最初は `FACTORY_KEY:USER_DAO = jp.co.xxx.UserDaoImpl` と書く形にしたが、**動かなかった**。
`java.util.Properties` は `:` と `=` のどちらもキーと値の区切りとして読むので、この行はキー
`FACTORY_KEY`、値 `USER_DAO = jp.co.xxx.UserDaoImpl` になってしまう。
書き手が気づきにくく、症状は「対応表の件数が合わない」だけなので、区切りを `@` に変えた
（`FACTORY_KEY@USER_DAO`）。`\:` とエスケープさせる案は、対応表を機械的に書き出すときに面倒なので採らなかった。

### Q17. 対応表を properties 形式にしたのはなぜか。CSV や YAML ではなく

- 設定ファイル（`config.properties`）と同じ形式なので、利用者が新しい書式を覚えなくてよい
- 1 行 1 対応で `grep` しやすく、DI 設定ファイルからの機械的な書き出しが容易
- コメントが書ける（どの画面のための対応か、といった注記が残せる）
- YAML はパーサの依存が増える。CSV は「値に複数の候補を書く」ときの引用符が煩わしい

なお、値のカンマ区切りで候補を複数書ける（絞り切れないが CHA よりは狭められる場合のため）。

### Q18. 引く順番（手がかり → 型＋メソッド → 型）はなぜこの順か

呼び出し箇所ごとの情報である**手がかりを最優先**にする。手がかりは「その 1 回の呼び出しで
どのキーが使われたか」を示すので、型全体に対する既定より確実に狭い。
手がかりが無ければ「型＋メソッド」、それも無ければ「型」に落とす。
DI の対応表（型 → 具象型）を既定として置きつつ、ファクトリ経由の箇所だけキーで上書きする、という
書き方ができる。

## 回帰テスト

### Q19. 何を確認すれば「プラグインできている」と言えるか

`test/regression/plugin` で、同じソース（`test/plugin-demo`）を 3 通りの設定で解析し、比較する。

| 設定 | 内容 | 期待 |
| --- | --- | --- |
| `config-before.properties` | 拡張なし | `CHA候補2件（未展開）` に広がる |
| `config.properties` | 同梱の拡張＋対応表 | `解決:MAPPING` で 1 件に絞れる |
| `config-custom.properties` | 自前の拡張（`plugins/DiXmlProvider.java`） | `解決:DI_XML` で 1 件に絞れる |

3 番目は、独自形式の DI 設定ファイル（`di.xml`）を読む拡張を `.java` のまま置いてある。
実行時コンパイルの経路がそのまま検査されるうえ、拡張の書き方の実例にもなっている。
対応表とは**別の実装クラス**（`fxp.Service` → `ReportService`。対応表は `BillingService`）を返すようにしてあり、
「自前の拡張が本当に読まれ、その設定ファイルが効いている」ことが出力の差で分かる。

### Q20. キャッシュの作り直しはどう検査したか

`plugin` ケースは 4 回実行する。2 回目（拡張なし → 同梱の拡張）で「キャッシュの再利用が 0 件」＝
捨てられたこと、3 回目（同じ設定でもう一度）で「再利用が 1 件以上」＝拡張が同じなら再利用されることを、
どちらもログの集計行で確認している。ログ検査は既存のケースと同じく ASCII の部分だけを見る
（標準出力の文字コードは環境依存のため）。

## その他

### Q21. `Plugins.load` の引数に `Config` を渡すようにしたのはなぜか

クラスローダを作るのに `plugin.folders` とキャッシュフォルダが要り、読み込んだ拡張に `init` で
設定を渡す必要もあるため。従来は呼び出し側（`CallHierarchyExporter`）がフェーズBの拡張だけ
`init` を呼んでいて、フェーズAの拡張には設定を渡す口が無かった。
`Plugins` に寄せたことで、両フェーズとも「読み込み → `init` → ログ」が同じ道を通る。

### Q22. 両フェーズのインターフェースに共通の親を作らなかったのはなぜか

`init(Properties, Path)` は同じ形なので、共通の親インターフェース（`Plugin` など）を作って
`Plugins.load` を単純にすることもできた。採らなかったのは、**拡張ポイントが 2 つあること自体が
利用者に伝えるべき設計**だから。共通の親があると「1 つの拡張ポイントに 2 つの顔がある」ように見えてしまう。
実際には、必要な情報が手に入るタイミングが違うので 1 つにはまとめられない
（フェーズA は AST が手元にあるが全体が見えない、フェーズB は全体が見えるが AST が無い）。
振り分けは `Plugins.init` の `instanceof` 数行で済むので、そちらを負担した。

### Q23. `appliesToStaticBound()` は今回どう扱ったか

既存のまま（既定 `false`）。同梱の `TypeMappingProvider` では
`plugin.mapping.applies.to.static.bound=true` で切り替えられるようにした。
`private` / `static` / `final` の呼び出しは Java の言語仕様上ディスパッチされないので、
通常は拡張に尋ねる必要が無い。ただしバイトコード織り込み（AspectJ の CTW 等）を使う環境では
前提が崩れるため、逃げ道は残してある。

### Q24. Spring の DI 解決（#66）と役割が重ならないか

重ならない。作業中に [#66](https://github.com/instreest/java-call-hierarchy-exporter/issues/66)
（Spring による DI の解決）が main に入ったので、取り込んだうえで住み分けを確認した。

| | 判定の材料 | 設定 |
| --- | --- | --- |
| Spring の DI 解決（段5・`SPRING_DI`） | ソース上の注釈（`@Service` 等）と Bean 定義 | 不要（既定で有効） |
| この拡張（段3・拡張が返すラベル） | 利用者が与える対応表・独自の設定ファイル | 必要 |

注釈が書かれていれば材料はソースの中にあるので、外から与えるまでもない。逆に XML や独自形式の
DI 設定ファイルは、ソースを読んでも分からないので外から与えるしかない。両者は同じ「DI の解決」でも
材料が違う。

呼ぶ順番は拡張（段3）が先で、Spring の判定（段5）は後。利用者が明示的に書いた条件のほうが、
ツールの推測より確かなので、上書きできるようにしてある。
