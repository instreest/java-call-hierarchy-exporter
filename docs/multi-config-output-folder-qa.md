# 複数の設定ファイルと実行ごとの出力フォルダ — 実装時の QA 一覧

[Issue #60](https://github.com/instreest/java-call-hierarchy-exporter/issues/60)
「コンフィグ複数ファイル指定を可能としたい」の対応で、迷ったこと・困ったことと、その結論を Q&A の形で残す。

対応の要点:

- 設定ファイルを引数に複数渡せる。順に独立して処理し、1 つが失敗しても残りを続け、最後に一覧を出す（1 つでも失敗なら終了コード 1）
- 出力は設定ファイルごとに `output.folder`（既定 `./output`）の下の `<解析開始日時>_<project.root のフォルダ名>/` へ。
  CSV のファイル名は固定。同じフォルダに設定ファイルの複製と標準出力の複写 `run.log`（UTF-8）を置く
- キャッシュは出力フォルダに置かず、ツール自身のプロジェクトフォルダの `.cache/<プロジェクト名>_<ハッシュ>/` に
  解析対象プロジェクトごとのサイドカーとして置く（`ToolRoot` が場所を特定）
- 既定の設定ファイルを `config/config.properties` からリポジトリ直下の `config.properties` へ移す
- 旧項目 `output.csv` / `methods.csv` / `cache.folders` は、新しい書き方を示すエラーにする

## 出力フォルダ

### Q1. 出力フォルダ名はどういう形にするか

`<yyyyMMdd-HHmmss>_<project.root のフォルダ名>` にした（例: `20260907-163000_myapp`）。

- 日時を先頭にしたのは、名前順がそのまま時系列になるから。回帰テストの「最新のフォルダ」も
  `ls | sort | tail -1`（Windows は `dir /o-n` の先頭）で取れる。プロジェクト名を先頭にすると
  プロジェクトごとにまとまるが、同じ親フォルダには同じ設定ファイル（= 同じプロジェクト）の結果が並ぶのが
  普通なので、まとまりの利点は薄い
- 「どのプロジェクトか」は `project.root` のフォルダ名で表す。Issue の「どのプロジェクトを対象としたか
  フォルダ名から分かるように」に対して、設定ファイル名やパス全体より短く、人が読んで分かる。
  設定ファイル名はフォルダ名に入れない。同じフォルダに設定ファイルの複製が入るので、開けば分かる
- 同じ秒に同じプロジェクトを解析すると名前がぶつかるので、`_2`, `_3` … を足す（`Config.uniqueOutputDir`）。
  回帰テストでは小さなプロジェクトを続けて動かすので実際に起きる（`multi` ケースで whole と entry が
  同じ秒に走っても、別の設定フォルダなのでぶつからないが、同じフォルダの別設定なら起きる）
- 秒までにしたのは、フォルダ名として読める長さとの折り合い。ミリ秒を足せば衝突はほぼ無くなるが、
  人が見るには長い。衝突は `_2` で吸収できる

### Q2. 「解析開始日時」は起動した時刻か、設定ごとの開始時刻か

設定ごとの開始時刻にした。設定ファイルを 3 つ渡して 1 時間かかる場合、3 つ目のフォルダが起動時刻の名前だと
中の `run.log` の内容（経過時間は設定ごとに 0 から）と合わない。「この解析がいつ始まったか」を素直に表す。
1 回の起動でできたフォルダをまとめて見たければ、最後に出る一覧（`OK <設定> -> <出力フォルダ>`）を使う。

### Q3. 出力ファイル名を固定にし、`output.csv` / `methods.csv` を廃止したのはなぜか

Issue の To be が「出力フォルダを作る」なので、指定するのはフォルダ（`output.folder`）で、その中のファイル名は
固定にした。ファイル名まで設定できるようにすると「フォルダは自動、ファイル名は設定」の 2 段になり、
`output.csv=../x.csv` のような指定と実行ごとのフォルダの関係を説明しなければならない。
CSV を開く側（Excel、`diff`）も名前が固定のほうが扱いやすい。

### Q4. 旧項目が設定ファイルに残っていたら、無視するか、警告か、エラーか

エラー（`IllegalArgumentException`）にした。`Config.rejectRemovedKeys`。
黙って無視すると、利用者は今までどおり `output/call-hierarchy.csv` を探して「出力されない」と思う。
警告でも、ログの途中に出るだけで見落とす。メッセージに新しい項目名と「この行を消す」を書いておけば、
対処は 1 分で終わる。`cache.folders` も同じ扱い（Q9）。

### Q5. 設定ファイルの複製と実行ログは、いつ出力フォルダに書くか

出力フォルダは `Config` を読んだ直後、解析より前に作り、その時点で設定ファイルを複製してログの複写を始める。
解析の途中で落ちても「何を渡して、どこまで進んで、何で落ちたか」がフォルダに残る。
設定ファイル自体が読めない（無い、旧項目が残っている、`project.root` が無い）ときは出力フォルダの場所が
決まらないので、フォルダは作らず標準出力にだけエラーを出す。

複製は `Files.copy` でバイトのまま。渡したファイル名のまま置く（`config.properties` とは限らない。
回帰テストの `config-before.properties` のように、名前自体に意味があることがある）。

### Q6. `resolved-classpath.txt`（ビルドファイルから集めた依存 jar の一覧）はどこに置くか

以前はキャッシュフォルダに置いていたが、出力フォルダに移した。
「この実行で JDT に何を渡したか」の記録であり、キャッシュが複数の設定・実行で共有されるようになると
キャッシュフォルダには「最後の実行のもの」しか残らない。出力フォルダなら実行ごとに残る。
`BuildFileClasspath.writeListing` の書き先を `config.outputDir` に変えただけで、内容は同じ。

## 標準出力ログの複写

### Q7. 標準出力をファイルにも残す方法として、`System.setOut` の差し替えではなく `Log` の付け替えにしたのはなぜか

このツールの標準出力は全部 `jche.util.Log` を通る（`Progress` も `Log.info` を呼ぶ。`System.out` を直接使う
箇所は無いことを grep で確認した）。そこで `Log` に「もう 1 本の書き先」（`attachFile` / `detachFile`）を足した。

- `System.setOut` で tee にすると、標準出力の文字コード（コンソール依存。固定しない方針は
  [cache-dependency-jars-qa.md](cache-dependency-jars-qa.md) の Q21）とファイルの文字コード（UTF-8 に固定したい）を
  同じストリームで扱うことになり、`PrintStream` を 2 つ束ねる小細工が要る
- `Log` なら、コンソールには今までどおり文字コード指定なしで書き、ファイルには UTF-8 で書ける。
  後から別の環境（Windows の MS932 コンソールで動かしたログを Linux で読む等）で開くのはファイルのほうなので、
  ファイル側だけ文字コードを固定する意味がある
- 設定ごとに出力フォルダが変わるので、設定の処理を始めるときに `attachFile`、終わり（`finally`）に `detachFile`。
  複数設定の区切り行や最後の一覧は、どの設定のフォルダにも属さないので標準出力にだけ出る

1 行ごとに `flush` する。途中で落ちたときも直前の行までファイルに残すため。行数は多くても数千で、性能上の影響は無い。

例外のスタックトレースも `Log.error` で標準出力とファイルの両方に出す。以前は `main` から投げっぱなしで
JVM が標準エラーに出していたが、それだとファイルに残らない。

### Q8. ログの経過時間 `[分:秒.ミリ秒s]` は起動からの通算か、設定ごとか

設定ごとに 0 から数え直す（`Log.resetClock`）。「このプロジェクトの解析に何分かかったか」を
`run.log` だけで読めるようにするため。標準出力を通しで見ている人には時刻が戻って見えるが、
区切り行（`######## 設定 2/3 ########`）があるので混乱はしない。

## キャッシュの置き場所

### Q9. キャッシュを「ツールのプロジェクトフォルダ内」に置くために、その場所をどう特定するか

`jche.config.ToolRoot`。目印 `src/CallHierarchyExporter.java` を、作業ディレクトリとその上位、次に実行中の
クラスの置き場所（`CodeSource`）とその上位から探す。

- jbang 経由では、クラスは `~/.jbang/cache/jars/` の下の jar から読み込まれるので `CodeSource` は使えない。
  jbang がスクリプトの場所をシステムプロパティで渡してくれることも無い
- README の手順は jbang でも `java -cp bin` でも「リポジトリ直下を作業ディレクトリにして」実行する形
  （`src/CallHierarchyExporter.java` や `bin` を相対パスで指している）なので、作業ディレクトリから上へ探せば
  ほぼ決まる。サブフォルダから実行しても上位で見つかる
- `java -cp bin` を別の場所から動かしたときは `bin/` の親に目印があるので `CodeSource` で見つかる
- どちらでも見つからなければ、警告を出して作業ディレクトリの `.cache/` にする。黙って別の場所にできるのが
  一番困るので、場所をログに出す（`キャッシュ: <パス>` の行は毎回出す）

`cache.folder`（単数）で置き場所の親を指定できる形は残した。回帰テストでケースごとにキャッシュを分けるのに要る
（同じ `test/demo` を指す whole / entry / jarchange が 1 つのキャッシュを共有すると、「1 回目はキャッシュ無し」
という前提が崩れる）。指定してもその下にプロジェクト別のフォルダを切るのは同じ。

### Q10. キャッシュフォルダの名前を `<プロジェクト名>_<ハッシュ>` にした理由

`project.root` のフォルダ名だけだと、`C:\work\main\myapp` と `C:\work\release\myapp` のように
ブランチごとのチェックアウトが同じ名前で混ざる。混ざると、片方のファイルが他方に無い扱い（消えたファイル）に
なって毎回全件解析になるうえ、更新時刻とサイズがたまたま同じファイルは他方の解析結果を再利用してしまう。
絶対パスの SHA-256 の先頭 8 桁を添えて区別する。8 桁（32 ビット）で、手元にあるプロジェクト数（数十）では
衝突しない。名前を残すのは、`.cache/` を見たときに人が判別できるようにするため。

Windows では `C:\Work\myapp` と `c:\work\myapp` が別のハッシュになる。同じ書き方で指定していれば同じになるし、
違っても「別のキャッシュができる」だけで結果は変わらないので、大文字小文字の正規化はしていない。

### Q11. 同じ `project.root` を指す複数の設定でキャッシュを共有して問題ないか

問題ない。キャッシュは「AST から分かった事実」だけを持ち、`entry.packages` や `exclude.packages` のような
出力側の設定に依存しない（[CacheFormat](../src/jche/cache/CacheFormat.java) の原則）。
回帰テストの `multi` ケースは whole（全体モード）と entry（起点指定）を同じキャッシュで続けて動かし、
期待出力と一致することを見ている。

事実に影響する設定が違う場合は次のとおり。

- `source.level` … ヘッダ行に入っているので、違えば全件解析し直す（既存の仕組み）。交互に使うと毎回全件になる
- 依存 jar（`library.folders` / ビルドファイル）… `L` 行の差分で影響ファイルだけ解析し直す（既存の仕組み）
- `source.folders` … キャッシュにあって今回の一覧に無いファイルは「消えた」扱いで捨て、無いファイルは新規解析。
  main と test で別々の設定にすると交互に全件解析になるが、結果は正しい
- `source.encoding` … ヘッダには入れていない。同じソースを違う文字コードで読む設定を交互に使うことは
  考えにくく、違っても影響は非 ASCII の識別子と文字列リテラルだけ。必要になればヘッダに足す
  （`CacheFormat.headerFor` に引数を足すだけ）

### Q12. `cache.enabled=false` のときのキャッシュファイルはどこにできるか

同じ場所。`cache.enabled=false` は「前回のキャッシュを再利用しない」であって、フェーズ 2 がキャッシュファイルを
読む構造は変わらないので、ファイル自体は書く。以前と同じ挙動で、場所だけがサイドカーに変わった。

## 複数の設定ファイル

### Q13. 1 つの設定が失敗したとき、残りを続けるか、止めるか

続ける。夜間に複数プロジェクトをまとめて回す使い方で、2 つ目の設定ミスで 3 つ目以降が動かないと翌朝に
やり直しになる。失敗した設定は `FAIL <設定> : <例外>` として最後の一覧に出し、終了コードを 1 にして
スクリプトからは検知できるようにする。

`catch (Throwable)` にしたのは `OutOfMemoryError` や `StackOverflowError` も「その設定の失敗」として
次へ進めるため。ただし OOM の後はヒープの状態が信用できないので、実際には次の設定も失敗しうる。
その場合も一覧に FAIL が並ぶだけで、黙って止まることはない。

### Q14. 設定ファイルを続けて処理するとき、前の設定の状態が残らないか

`static` な可変状態が無いことを確認した（`Log` の経過時間の基準点とファイルの書き先を除く。どちらも設定ごとに
付け替える）。`JavaCore.getOptions()` は `Config` が複製を取って `setComplianceOptions` するので、
JDT のグローバルな設定は変えていない。`ASTParser` は設定ごとに `CallEdgeExtractor` が作り直す。

### Q15. 引数を省略したときの既定を `config.properties`（作業ディレクトリ）にした

Issue の「既定のコンフィグはプロジェクト root 直下に config.properties として格納する」に従い、
ファイルを `config/config.properties` から `config.properties` へ移した（`git mv`）。
`project.root` の既定値は `../../java-call-hierarchy-exporter`（設定ファイルの 2 つ上の兄弟）から
`../java-call-hierarchy-exporter`（1 つ上の兄弟）に変わる。設定ファイルからの相対パスなので、
ファイルの場所が 1 段上がったぶん `..` が 1 つ減る。
`.gitignore` の `/config/.cache/` `/config/output/` は `/.cache/` `/output/` に変えた。

## 回帰テスト

### Q16. 出力先が実行ごとに変わるので、比較の対象をどう決めるか

`<case>/output/` の中で名前順の末尾（= 最新）のフォルダと比較する（`run.sh` の `latest_output`、
`run.cmd` の `:latest`。後者は `dir /b /ad /o-n` の先頭）。フォルダ名の先頭が日時なので名前順が時系列になる（Q1）。
各ケースの最初に `output/` を消すのは以前と同じ。

2 回目の実行で出力フォルダが 2 つになることも検査する（`実行ごとに出力フォルダが分かれる`）。
出力フォルダに設定ファイルの複製（`cmp` でバイト一致）と `run.log`（`call-hierarchy.csv` を含む行がある = 完了行）が
あることも見る。`run.log` は UTF-8 なので日本語でも検査できるが、既存の方針（ログの検査は ASCII だけ）に揃えた。

### Q17. 既定のキャッシュの場所（サイドカー）をどのケースで検査するか

`whole` だけ `cache.folder` を空欄にし、`<リポジトリ>/.cache/demo_<ハッシュ>/analysis-cache.tsv` ができること、
`whole/.cache` ができないことを見る。他のケースは `cache.folder=./.cache` でケースごとに分ける（Q9）。
`whole` の前に `<リポジトリ>/.cache/demo_*` を消す。ハッシュはスクリプトからは分からないので名前の前半で
glob する。`demo_*` 以外（利用者が手元で作った他プロジェクトのキャッシュ）には触らない。

### Q18. 複数設定の処理をどう検査するか

最後に `multi` ケースを足した。`whole/config.properties no-such-config.properties entry/config.properties` を
1 回の起動で渡し、

- 終了コードが 1（存在しない設定が失敗）
- 最後の一覧が `OK` / `FAIL` / `OK` の順
- whole と entry の最新の出力フォルダの CSV が、単独で動かしたときの期待出力と一致し、複製と `run.log` がある

を見る。whole と entry のキャッシュは直前のケースで作ったものを再利用する形になり、
「別の設定で作ったキャッシュを共有しても出力が変わらない」（Q11）の検査を兼ねる。

### Q19. この作業環境での確認

jbang が JDK 25 を取得できない環境（JDK の配布サイトへの接続がプロキシで拒否される。Maven Central には届く）
だったので、`jbang run --java 21` で手元の JDK 21 を使って回帰テストを動かした。変更前の状態でも同じ JDK 21 で
全ケース PASS することを先に確かめ（`expected` は JDK 25 で作られているが、`test/demo` 程度の内容では差が出ない）、
変更後も全ケース（`multi` を含む）PASS を確認した。
`javac --release 17 -Xlint:all -Werror -Xdoclint:all,-missing` も通る。
Windows の `run.cmd` はこの環境では動かせないので、CI（`.github/workflows/smoke.yml` の `regression-windows`）に委ねる。
`run.cmd` の `multi` ケースでは終了コードの検査を失敗扱いにしていない。現在の `jbangw\jbang.cmd`（本家そのまま）は
jbang 本体の終了コードを呼び出し元へ返さない既知の問題があり（`smoke.yml` の「known to fail」の項）、
検査すると必ず落ちるため。ログの `OK` / `FAIL` / `OK` の一覧と出力フォルダの検査で挙動は押さえている。

## 文書

### Q20. `prompts/`（再実装用の仕様プロンプト）はどこまで直すか

仕様として変わった点だけ直した。起動（複数の設定、出力フォルダ、キャッシュの場所）、設定項目の表
（`cache.folder` / `output.folder`、旧項目のエラー）、`resolved-classpath.txt` の場所、
プロンプト B の fixture の設定と検証項目（T44 に旧項目のエラー、T45 に複数設定）。
出力の列や解決の挙動は変わっていないので、他は触っていない。
`prompts/feature-difficulty.md` の 1-1（設定ファイルの読み込み）は難易度・規模とも変わらないので据え置いた。

### Q21. 過去の QA ドキュメントにある `config/config.properties` や `cache.folders` の記述は書き換えるか

書き換えていない。`docs/*-qa.md` は当時の作業記録であり、[samples-demo-move-qa.md](samples-demo-move-qa.md) の Q5 と
同じ判断。実行時に参照されるパスは README・`config.properties`・`test/regression/` にしか無く、そちらは全部直した。
