# データフローを独立したフェーズにする提案 — 役割分担の整理

Eclipse プラグインの呼び出し元索引を作るときに見つかった
「`CallResolver.resolve(edge)` が初回と2回目で違う答えを返す」件
（[eclipse-plugin-ui-qa.md](eclipse-plugin-ui-qa.md) の Q9）への対応案。
**まだ実装していない。** 何を誰の仕事にするかの整理と、段階の提案である。

結論から言うと、提案は次の2点。

1. フェーズ2を「グラフ構築」「**データフロー確定（新設）**」「解決」の3つに割る
2. `CallResolver.resolve(edge)` を**純粋な関数**にする（同じグラフなら、何回呼んでも、
   どの順で呼んでも同じ答え。副作用でメモを育てない）

---

## 1. いま何が起きているか

### 1.1 症状

`test/demo` を解析し、全エッジを 2 周 `resolve` すると、1 周目と 2 周目で答えが違うエッジがある。

```
edge 34  fx.app.Main#run(String[]) -> fx.dao.Dao#describe()
  1周目 = [OrderDaoImpl#describe, UserDaoImpl#describe]  CHA          （候補2件）
  2周目 = [UserDaoImpl#describe]                          DATAFLOW_FACTORY（1件に確定）
```

### 1.2 原因

`DataflowResolver.factoryReturnOrigin(methodId)` は**要求されたときに計算し、結果をメモに残す**。
委譲（`return create();`）は `dataflow.max.depth` 段まで辿るが、**上限で打ち切った「不明」はメモに残さない**
（残すと、そのファクトリを別の浅い箇所から呼んだときも不明のままになるため。コード中のコメントにも
「解決結果がエッジの処理順に依存してしまう」と書かれている）。

ここに抜け道がある。**メモに当たった時点で深さの数え直しが起きない**ので、
「途中のファクトリが先に単独で計算されてメモに載っていたか」で、辿れる実質的な深さが変わる。

```
初回:  A -> B -> C -> D   （深さ上限 3 に当たって不明 = CHA のまま）
その後: どこかの別のエッジが C を深さ0から評価してメモに載せる
以降:  A -> B -> C(メモ命中！) …で残りの予算が余り、D まで畳めて確定する
```

つまり**「解決」という読み取り操作が、副作用として事実の在庫を育てている**。
在庫の育ち方は、どのエッジをどの順で解決したかに依存する。

### 1.3 いま何を壊しているか / 壊していないか

| | 影響 |
|---|---|
| CSV 出力（CLI） | **実害なし**。走査の順が固定なので毎回同じ結果。回帰テストも一致する |
| Eclipse プラグインの呼び出し元索引 | 影響あり。転置索引と、あとから画面が出す「解決の理由」が食い違いうる。いまは索引を作る前に全エッジを1周させて（`InboundIndex.warmUp`）落ち着かせている **＝暫定の回避** |
| これから足す機能 | 危険。「resolve は決定的」という自然な前提が成り立たないので、部分的に解決する処理（差分更新、並列化、途中から辿る画面）を書くたびに同じ罠を踏む |

`usesParameters`・`reflectKinds`・`methodsByName` も遅延で作られるが、こちらは
**初回に一度だけグラフ全体を見て作る**ので順序に依存しない。問題は `factoryOrigin` だけである。
裏を返せば、「全体を一度に作る」という形はすでにこのクラスの中にあり、
それを `factoryOrigin` にも広げてフェーズとして外に出す、というのが今回の提案になる。

## 2. 提案する役割分担

`事実（fact）` と `判断（policy）` と `経路（context）` を、はっきり別の層に置く。

| 層 | 誰が | 何を持つか | 性質 |
|---|---|---|---|
| フェーズ1 | `jche.analysis` → `jche.cache` | ソース上の事実（呼び出し・宣言・**出所（origin）**・return・フィールド代入） | ファイル単位。差分更新できる |
| フェーズ2a | `jche.graph.CallGraphBuilder` | 呼び出しグラフ（CSR）・型階層 | グラフ1つ。決定的 |
| **フェーズ2b（新設）** | `jche.dataflow.DataflowBuilder` → `DataflowFacts` | **出所を畳んだ結果**（ファクトリの戻り値の具象型、フィールドの具象型、リフレクション種別、経路情報を使う意味があるメソッド） | グラフ全体から一括で作る。**不変・決定的** |
| フェーズ2c | `jche.graph.CallResolver` | 候補の絞り込みとラベル付け（CHA / LOCAL_NEW / DATAFLOW_* / 静的束縛） | **純粋関数**。事実を読むだけ |
| フェーズ3 | `jche.report.StreamingTreeWalker` | 経路で分かったこと（`DataflowContext`）を足して、もう一段絞る | 経路ごと。呼び出し側が持つ |

いまとの違いは1点だけ。**「出所を畳む」仕事を、解決の中の遅延計算から、独立したフェーズへ出す。**

```
現状                                   提案
──────────────────────────────────    ──────────────────────────────────
フェーズ2 グラフ構築                    フェーズ2a グラフ構築
フェーズ2 解決 ─┐                      フェーズ2b データフロー確定（一括・不変）
                └→ 必要になったら         　  ↓ DataflowFacts（読み取り専用）
                   出所を畳む（メモ）     フェーズ2c 解決（純粋・事実を読むだけ）
フェーズ3 経路つき解決                  フェーズ3 経路つき解決（変更なし）
```

### 2.1 新しい形

```java
// フェーズ2b: グラフから一括で作る。作ったら書き換えない
public final class DataflowFacts {
    String factoryReturnOrigin(int methodId);   // 畳んだ結果（不明は null で確定）
    String fieldConcreteType(String fieldKey);
    int reflectiveKind(int methodId);
    boolean usesContext(int methodId);
}

// フェーズ2c: 事実を読むだけ。ctx が null なら結果は edge だけで決まる
public Resolution resolve(int edgeIndex);                       // 純粋
public Resolution resolveOnPath(int edgeIndex, DataflowContext ctx);  // 経路の分だけ上書き
```

`DataflowResolver` は「出所 → 具象型」の**問い合わせ器**だけになり、
畳み込みのアルゴリズムは `DataflowBuilder` へ移る。経路依存（`ctx` を伴う分）はそのまま残す。
これは**責務の移動であって、解決ロジックの作り直しではない**。

### 2.2 畳み込みを決定的にする方法

いまの「相対的な深さ上限つきの再帰」をやめ、**ワークリストによる不動点計算**にする。

- 値の領域は 3 つ … `未計算` / `具象型（または C: A: の形）` / `決められない`
- メソッド間の依存（`return create();`）は有向グラフ。**強連結成分に縮約して逆順に1回**評価すれば、
  循環（相互再帰するファクトリ）は「決められない」で確定し、それ以外は深さに関係なく畳める
- 順序も深さ予算も結果に影響しない。`dataflow.max.depth` は畳み込みには不要になる

ここで**振る舞いが変わる**点に注意が要る。いまは深さ上限で諦めていた深い委譲が畳めるようになるので、
**解決できる呼び出しが増える＝CSV の内容が変わりうる**。そこで段階を2つに分ける（§3）。

### 2.3 `dataflow.max.depth` の扱い（3案）

| 案 | 畳み込み | 設定の意味 | 出力の変化 |
|---|---|---|---|
| A | 不動点（上限なし） | 廃止（互換のため読み捨て、警告） | 増える方向に変わる |
| B | 上限を残すが**絶対深さ**で数える（メモ命中でも予算を消費したものとして扱う） | 現状どおり | ほぼ変わらない見込み（要実測） |
| C | 不動点にしたうえで、`max.depth` は**経路依存の探索**（`classOf` / `literalOf`、フェーズ3）にだけ効かせる | 意味を絞る | A と同じ方向 |

**推奨は B → C**。まず「振る舞いを変えずに決定性だけ取る」（B）。
そのうえで「深い委譲も畳めるようにする」（C）を、CSV の差分を見ながら別の変更として入れる。
2つを一度にやると、差分が「決定化のせい」か「畳み込みが強くなったせい」か分からなくなる。

## 3. 段階

| 段 | やること | 検証 |
|---|---|---|
| S1 | `DataflowFacts` / `DataflowBuilder` を切り出し、フェーズ2bとして一括計算する（案B: 深さの数え方を絶対にして、順序依存だけ消す） | **新テスト**「全エッジを2周 resolve して、1周目と2周目が完全一致する」／回帰テストの CSV が**変わらない**こと |
| S2 | `InboundIndex.warmUp` を削除。プラグインの索引は確定した事実を見る | 回帰テスト＋プラグインのビルド |
| S3 | 不動点化（案C）。`max.depth` の意味を経路探索だけに絞る | 回帰テストの差分を1件ずつ確認して `expected` を更新。ログに「畳めた件数」を出して増加分を説明できるようにする |
| S4（任意） | `DataflowFacts` をダンプできるようにする（`dataflow-facts.csv`）。「なぜこの解決になったか」を追える | 出力の目視 |

S1 と S2 で今回の症状は消える。S3 は「解析の質を上げる」別の話なので、切り離して判断できる。

### 3.1 コストの見込み

- 一括計算はメソッド数に比例（`returnOrigins` を持つメソッドだけが対象）。いまも同じ計算を
  遅延でやっているので、**総量はほとんど変わらない**。フェーズ2の中で位置が前に動くだけ
- メモリは `DataflowFacts` のぶん（メソッド数 × 参照1本 ＋ フィールド辞書）。既存のメモと同じ
- 差分更新（フェーズ1のキャッシュ）には影響しない。`DataflowFacts` はグラフから毎回作る

---

## 4. この整理でうれしいこと

- **決定的**: 「resolve は純粋」と言い切れる。部分的に解決する処理（画面、差分、並列）を安心して足せる
- **暫定の回避を消せる**: `InboundIndex.warmUp` は要らなくなる
- **説明できる**: 「どのファクトリがどう畳まれたか」が1つの表になる。いまは解決の途中に埋もれている
- **測れる**: フェーズごとの件数と時間をログに出せる（「データフロー確定: 1,204 メソッド中 317 件を確定」）
- **キャッシュの余地**: 将来 `DataflowFacts` をキャッシュに載せるなら、フェーズが分かれていることが前提になる

## 5. 決めてほしいこと

1. `dataflow.max.depth` の扱い … **B → C** を推奨（§2.3）。A を一気にやるなら回帰の期待値を同時に更新する
2. CSV の内容が変わること（S3）を許容するか。許容しないなら S1・S2 だけで止めても、今回の症状は消える
3. 置き場所 … `jche.dataflow` を新設するか、`jche.graph` に置くか。フェーズと対応させる意味で**新設を推奨**
   （`jche.analysis` = フェーズ1、`jche.graph` = 2a・2c、`jche.dataflow` = 2b、`jche.report` = 3）
4. `DataflowResolver` の名前 … 問い合わせ器に縮むので `DataflowQuery` などへ改名するか（機能に影響なし）
