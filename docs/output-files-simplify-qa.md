# 出力ファイルの整理 — Q&A

出力フォルダのファイルが増えてきたので、役割を整理する。
1 つ目として、ビルドファイルから集めた依存 jar の一覧（`resolved-classpath.txt`）を実行ログ（`run.log`）にまとめた（Q1・Q2）。
2 つ目として、想定どおりの状態で動かなかった実行でだけ、確認してほしいことと対処を書いた `warnings.txt` を出すようにした（Q3〜Q9）。
関連: [build-tool-classpath-qa.md](build-tool-classpath-qa.md)（依存 jar の集め方）、
[multi-config-output-folder-qa.md](multi-config-output-folder-qa.md) の Q6（一覧の置き場所の前回の判断）。

## 対応の要点

- `BuildFileClasspath` は一覧をファイルに書かず、`Log.plain` で 1 行ずつログに書く。
  形は旧ファイルと同じタブ区切り（`path<TAB>coordinates<TAB>via`）で、先頭に字下げを付ける
- 出力フォルダに残るのは `call-hierarchy.csv` / `methods.csv` / 設定ファイルの複製 / `run.log`、
  条件付きで `call-conditions.csv` / `contracts-suggested.txt`
- 一覧を書けなかったときの警告（`config.deps.listingFailed`）と、ファイルの場所を添える文言
  （`config.deps.collected.listing`）は要らなくなったので消した
- 出力フォルダのファイルの役割を次のように分けた

  | ファイル | いつできるか | 役割 |
  |---|---|---|
  | `call-hierarchy.csv` / `methods.csv` | 毎回 | 成果物 |
  | 設定ファイルの複製 / `run.log` | 毎回 | 後から追うための記録（どの設定で何が動いたか、どこに何を保存したか。警告・エラーも含む） |
  | `warnings.txt` | `run.log` に `[WARN]` / `[ERROR]` が出た実行だけ | 確認してほしいことと対処の案内。**あったら開く**ファイル |
  | `contracts-suggested.txt` / `call-conditions.csv` | 条件付き | 次の作業のための材料 |

- `warnings.txt` の本体は `jche.util.Warnings`。`Log.warn` / `Log.error` の行を集め、典型（`Warnings.Topic`）に
  当たるものは「何が起きたか・影響・対処・該当」の項目に、それ以外は末尾の「その他の警告」に並べる
- ビルドが通っていないことを直接言えるよう、コンパイルエラーのあるファイルを数えて警告するようにした（Q6）
- ローカルリポジトリについての警告（`config.repos.*`）の書き出しを `依存jar:` / `Dependency jars:` にそろえた（Q9）

## Q&A

### Q1. 一覧は `run.log` だけに書くか、標準出力にも出すか

**標準出力にも出す（`Log.plain`）。** `run.log` は「標準出力と同じ内容」と README・設定ファイルのコメント・
cli.md で約束しており、ファイルにだけ書く口を作るとその約束が崩れる。
Eclipse / VSCode プラグインのコンソール（`Log.attachSink`）にも同じものが流れるので、
画面で依存 jar の不足に気づいたときにその場で要求元まで追える。

依存 jar が数百あると画面に数百行出るが、ビルドファイルから集めたとき（`library.folders` が空欄）だけで、
`library.folders` / `library.jars` を書いた場合は出ない。時刻の付かない字下げ行なので、前後のログとは見分けられる。

却下した案:

- **`Log` にファイル専用の口を足す** … 上の約束が崩れるうえ、プラグインのコンソールからは見えなくなる
- **件数が多いときだけ省略する** … 省略した部分を見たいときに見る場所が無くなる。記録としての役割を果たさない

### Q2. 依存 jar を取得（ダウンロード）しないのは現状のままでよいか

**よい。仕様として維持する。** 解析時の依存 jar の解決はローカルにあるものだけを使い、ネットワークには出ない。

- ビルドツール（`mvn` / `gradle`）を実行しない。`ProcessBuilder` / `Runtime.exec` は解析側のコードに無い
- `pom.xml` / `build.gradle` をこのツールが読み、jar と POM を `~/.m2/repository`（`~/.m2/settings.xml` の
  `localRepository` があればそこ）、`~/.gradle/caches`（`library.repositories` を書けばその場所）から**ファイルとして**探すだけ
  （`LocalRepositories`）。`settings.xml` のミラーやリモートリポジトリの設定は読まない
- XML の読み取り（`ProjectLayout.parseXml`）は DOCTYPE を拒否するので、外部実体の参照でネットワークに出ることもない
- 無い jar は数えて警告（`[WARN]`）とともに座標と要求元の経路をログに出し、その型を使う呼び出しは欠けたまま解析を続ける

解析のたびに社内リポジトリへ勝手に問い合わせないよう、安全側に倒した仕様である。
依存を揃えたいときは、利用者が Eclipse や `mvn dependency:go-offline` などで事前にローカルへ取得する。
起動コマンドがネットワークから取得するのは JBang・JDK・このツール自身の依存（JDT の jar）だけで、
それも必ず確認を出す（[network-download-confirm-qa.md](network-download-confirm-qa.md)）。

### Q3. `run.log` と `warnings.txt` はどう役割を分けるか

- **`run.log`** … 実行ごとに必ず作る。どの設定で何が動き、どこに何を保存したかを後から追うための記録で、
  警告やエラーもここに出る。標準出力と同じ内容（Q1）
- **`warnings.txt`** … 想定どおりの状態で動かなかったときにだけ作る。**ファイルがあること自体が合図**で、
  中身は初めて使う人向けの「何が起きたか・何に響くか・どう直すか」

このツールの正常な状態は「ビルドが通り、実行時の依存（依存 jar）もすべて解決できている」ことである。
設定の誤りでソースフォルダを読めていない、依存 jar が無い、コンパイルエラーがある、といった状態でも解析は
最後まで動いて CSV を出す（止めると、分かる範囲の結果まで失うため）。そのぶん利用者は抜けに気づきにくい。
`run.log` は長く、警告は経過の行に埋もれるので、「開くべきファイルがある」という形で気づけるようにした。

却下した案:

- **毎回作り、問題が無ければ「問題なし」と書く** … 毎回あるファイルは開かれなくなる。無いことが「正常」の印になるほうが強い
- **警告があれば終了コードを変える** … 解析は成功しており、CI や対話モードの扱いが変わる。まずはファイルで知らせる

### Q4. 何が出たら `warnings.txt` を作るか

**`run.log` に `[WARN]` か `[ERROR]` の行が 1 行でも出たら作る。** 逆に、出ていなければ作らない。
`Log.warn` はもともと「利用者が対処すべきこと（設定漏れ・読み飛ばし等）」を出す口（`Log` の javadoc）なので、
その定義をそのまま「確認してほしいこと」に使える。約束が 1 行で言え、`test/warnings/run.sh` で機械的に確かめられる。

`Log.warn` を通った行は、典型の項目に当たらないものも末尾の「その他の警告」に全部載せる（上限 200 行。
超えた分は件数だけ書いて `run.log` を見てもらう）。典型だけを拾う作りにすると、新しく足した警告が黙って
ファイルに載らなくなる（呼び出しを静かに落とさない、と同じ考え方）。

裏返しに、対処の要らない経過を `Log.warn` で出してはいけない（AGENTS.md の「コードの決まり」に書いた）。

### Q5. 典型の項目は何にしたか。どう載せるか

初めて使う人がつまずく順に、次の 5 つ（`Warnings.Topic`。ファイルでもこの順に並ぶ）。

| 項目 | 載る警告 |
|---|---|
| 実行が失敗した | 設定 1 つ分の処理が例外で止まった（`exporter.configFailed`）。原因の例外の文も載せる |
| 設定ファイルで指定したフォルダやファイルが見つからない | `source.folders` / `library.folders` / `library.jars` / `.classpath` の lib / `external.library.folders` の指定先が無い等（`config.layout.*`、`external.folderMissing`） |
| 依存 jar が解決できていない | ローカルリポジトリに無い jar・POM、版が決まらない依存、ビルドファイルを読めない、ローカルリポジトリが無い（`config.deps.*`、`config.repos.*`、`config.maven.warn`、`config.gradle.settingsUnreadable`）。無い jar の座標と要求元も明細に並べる |
| ソースにコンパイルエラーがある | コンパイルエラーのあるファイル（Q6）、構文エラーのファイル、型解決できなかった呼び出しの件数 |
| 解析や出力が途中で打ち切られた | ファイルの解析の失敗（`analysis.fileFailed`）、行数の上限（`report.walker.maxRows`） |

載せ方は、警告を出す箇所で `Log.warn(…)` の代わりに `Warnings.warn(Topic, …)` を呼ぶだけ。ログへの出方は変わらない。
項目の説明（影響と対処）は文言の表（`exporter.warnings.<項目>.*`）に置き、明細には警告の文そのものを並べる。

拡張・契約表・キャッシュの作り直しなど、使いこなす段階の機能の警告は典型にせず「その他の警告」に出す。
それぞれの文に対処が書いてある（AGENTS.md の「ログは利用者が次に何をすればよいか分かる書き方にする」）。

### Q6. 「ビルドが通っていない」をどう判定するか

JDT が報告したエラー（`IProblem.isError()`）が 1 件でもあるファイルを数える。数はもともとキャッシュの F 行の
3 列目（エラー数）に入っていたので、新しく数えるものは無く、**キャッシュの版は上げていない**。
新規解析・再利用・中断からの引き継ぎのどの経路でも同じように数える（`CachePhaseResult#countErrors`）。
再利用で数えないと 2 回目の実行で警告が消えてしまう。

あわせて、中断からの引き継ぎの経路では構文エラーのファイルを数えていなかった（引き継いだ実行でだけ警告が消えていた）
ので、同じ `countErrors` で数えるようにした。

ビルドは通るのにここに出る典型は、依存 jar の不足、Java の版の食い違い（`source.level`）、ビルド時に生成される
ソース（Lombok・アノテーション処理）が解析の対象に無いこと。どれも実際にその箇所の呼び出しが型解決に失敗して
階層から抜けるので、「解析にとっては正常でない」として知らせるのが正しい。対処の説明にこの 3 つを挙げた。

エラーの内容（「X cannot be resolved to a type」など）はファイルに載せていない。キャッシュに持たせるには
形式を変えて版を上げる必要があり、まずはファイル名と件数で足りるとした。

### Q7. 表示言語・文字コード・名前

- 表示言語に合わせる（英語が既定、日本語を選べば日本語）。人が読んで対処を選ぶ案内で、`contracts-suggested.txt` と
  同じ扱い（`docs/nls-qa.md` の Q16）。CSV のように他のツールへ渡すデータではない
- 文字コードは UTF-8（`run.log` と同じ）。`output.encoding` には従わない（CSV を Excel で開くための設定なので）
- 名前は `warnings.txt`。エラー（実行の失敗）も載るが、初めての人が「何か言われている」と分かる素直な名前を選んだ

### Q8. `warnings.txt` を作れない・作らない場合

- 設定ファイルそのものの誤り（読めない、値の形が違う等）で、出力フォルダを作る前に失敗した場合は作れない。
  このときは終了コード 1 で止まり、画面にエラーが出る（出力フォルダが無いので `run.log` も無い）
- 出力フォルダを作った後の失敗（ソースフォルダが 1 つも無い、`project.root` が無い等）では、「実行が失敗した」の項目で作る
- サーバーモード（Eclipse / VSCode プラグインの別プロセス）では作らない。出力フォルダを持たず、
  利用者はプラグインの画面とログで状態を見るため。`Warnings.begin` を呼ばない限り何も溜めない作りにしてある
- 作ったときは、実行の最後に `[WARN]` で場所を知らせる（画面の最後の行になるので、対話モードでも気づける）

### Q9. ローカルリポジトリの警告の書き出しをそろえた理由

GitHub Actions のアクションは `run.log` から依存 jar の警告（`[WARN] Dependency jars:` / `[WARN] 依存jar:`）を
拾ってジョブに出す（`docs/github-actions-qa.md` の Q31）。ローカルリポジトリが無い・`library.repositories` の
指定先が無い・`settings.xml` を読めない、の警告だけ書き出しが違い、アクションが拾っていなかった。
どれも依存 jar が解決できない原因そのものなので、書き出しを `依存jar:` / `Dependency jars:` にそろえた
（`warnings.txt` でも同じ「依存 jar が解決できていない」の項目に載る）。
