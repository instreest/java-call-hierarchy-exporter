# VSCode プラグイン — 設計時の QA 一覧

VSCode 向けプラグインの設計（[vscode-plugin-design.md](vscode-plugin-design.md)）で迷ったこと・困ったことと、
その結論を Q&A の形で残す。Issue: —（設計のみ。切り出した宿題は
[#115](https://github.com/instreest/java-call-hierarchy-exporter/issues/115)・
[#116](https://github.com/instreest/java-call-hierarchy-exporter/issues/116)）

対応の要点:

- 解析はすでに別プロセス（`--server`）へ切り出してあるので、**拡張側は画面と子プロセスの世話だけ**を持つ。
  拡張ホストは Node.js なので、Java のコードは1行も置かない
- 標準の呼び出し階層（`CallHierarchyProvider`）には相乗りせず、**「影響調査 (Call Hierarchy Exporter)」**という
  独立したビューにする。重い一括解析を前提にしたレポートツールとして名乗る
- カーソル位置のメソッドは、拡張側でキーを組み立てるのをやめ、**ファイルと行を送って
  サーバーに引かせる**（`AT` を追加。実装済み）
- 解析の状態（未解析・解析中・古い）は Language Status Item に出す。自動再解析の既定は OFF

---

## 設計

### Q1. 裏で一括解析して結果を見せるのは、VSCode の文化として無作法ではないか

無作法ではない。ただし**やり方の細部**で決まる。

重い一括解析を持つ拡張は多数派である。vscode-java（JDT LS）自身が、開いた直後に
"Importing projects…" でワークスペース全体をビルドして結果を持ち続ける。rust-analyzer・clangd・
C# Dev Kit も同じで、Test Explorer や CodeQL は「重い処理を明示的に走らせ、結果をツリーで見せる」そのものである。

VSCode の作法は「軽くなければならない」ではなく、**「重さを隠さず、利用者の許可のもとでやる」**である。
嫌われるのは次のほうで、設計ではすべて避けている。

| 嫌われる作り | 避け方 |
|---|---|
| 起動しただけで重い処理が始まる | `activationEvents` はコマンドとビューだけ。`onLanguage:java` では起こさない |
| UI をブロックする・モーダルな進捗 | 出さない |
| 数百 MB を黙って落とす | JDK の取得前に必ず確認する |
| 状態を独自の場所に出す | Language Status Item（標準の置き場所）に出す（Q2） |
| 標準機能と同名の別物を置く | 名前を変える（Q3） |

### Q2. 解析の状態をどこに出すか

**Language Status Item**（`vscode.languages.createLanguageStatusItem`。エディタ右下の `{}` に出る、
vscode-java の "Java: Ready" と同じ場所）を主にする。

Eclipse 版はビューの上に1行のバナーを置いていたが、VSCode にはバナーに当たる部品が無い。
`TreeView#message` に全部書くこともできるが、それは自前の作法で、しかも**ビューを開いていないと見えない**。
言語ツールの状態を出すための標準の場所があるのだから、そこを使う。

`TreeView#message` は補助に降格し、絞り込み中の件数などビュー固有の話だけを書く。

### Q3. ビューの名前を Eclipse 版と揃えないのはなぜか

VSCode には標準の「呼び出し階層」（`Shift+Alt+H`、vscode-java が提供）がある。
同じ名前で並ぶと「同じものの劣化版が2つある」ように見え、どちらを見ているのか分からなくなる。

**「影響調査 (Call Hierarchy Exporter)」**にする。このツールの目的（改修時の影響調査で呼び出しを漏らさない）にも
そのほうが正確で、呼び出し階層はその手段である。あわせて独自のビューコンテナに置き、
既定のキーバインドは割り当てない。

2つのプラグインで名前が揃うことより、**それぞれのホストで標準機能と紛れないこと**を優先した。
Eclipse 版も揃えるかは [#116](https://github.com/instreest/java-call-hierarchy-exporter/issues/116) で検討する。

### Q4. 標準の `CallHierarchyProvider` として実装しなかったのはなぜか

2つの理由がある。

1. 同じ言語に複数のプロバイダが登録されても、VSCode は**どれを使うか利用者に選ばせない**。
   vscode-java と奪い合いになる
2. このツールの結果は**重くて古くなる**。標準ビューには「12 ファイルが変更されています」
   「この枝は確度が低い（dataflow で推定）」を出す場所が無い。状態を言えないまま古い結果を見せるのが一番危ない

Eclipse 版が標準の「呼び出し階層」ビューに相乗りしなかったのと同じ判断である
（[eclipse-plugin-ui-design.md](eclipse-plugin-ui-design.md) §9）。

### Q5. カーソル位置のメソッドを、なぜ拡張側で特定しないのか

解析側のキーは `型FQN#メソッド名(消去型の完全修飾名,…)` である。Eclipse 版は JDT のモデル（`IMethod`）から
これを組み立てていた（`MethodKeys`）が、型変数・内部クラス・可変長引数の綴り合わせが要る繊細な処理で、
寄せ切れないぶんはサーバー側のゆるい照合（`findLoosely`）が救っていた。

VSCode には JDT のモデルが無い。`executeDocumentSymbolProvider` が返すのは**表示用の文字列**
（`OrderService.save(Order)`）で、完全修飾もされておらず、プロバイダの都合で変わる。
これを FQN に直すには import を自前で解く簡易パーサが要る。

そこで向きを変えた。**ファイルと行を送り、サーバーが自分の解析結果から囲みメソッドを引く**（`AT`）。
サーバーは全メソッドの宣言位置（`MethodTable#declFile` / `#declLine`）を持っているので、
「同じファイルで、宣言行が指定行以下のもののうち最大のもの」を選べばよい。
拡張側の仕事は「パスと行番号を送る」だけになり、綴り合わせの問題が丸ごと消えた。

この考え方は Eclipse 版にも効く（将来 `MethodKeys` を `AT` に寄せれば、あの処理を消せる）。
ただし今回は VSCode 側だけで使い、Eclipse 版はそのままにした。二重に壊す危険を冒さない。

### Q6. `AT` を足してプロトコルの版を上げなかったのはなぜか

版を上げるのは**既存の行の意味を変えるとき**だけと決めてある（`Protocol#VERSION`）。
要求を足すのは該当しない。知らない要求には `NG unknown-command` が返るので、
新しいクライアントが古いサーバーに当たっても壊れず、「この機能は使えない」と分かる。

版を上げると、既存の Eclipse プラグインが `HELLO` の応答を見て断る作りだった場合に
動かなくなる。足しただけで壊す理由は無い。

### Q7. `AT` の断り方を4つに分けたのはなぜか

`NG not-found` ひとつで済ませると、画面が「次に何をすればよいか」を言えないためである。

| 応答 | 状況 | 画面 |
|---|---|---|
| `not-analyzed` | まだ解析していない | ［解析する］ |
| `file-not-analyzed` | そのファイルが解析結果に無い（`source.folders` の外・除外・新規ファイル） | 「解析対象に入っていません」＋［再解析］ |
| `not-found` | ファイルはあるが、その行を囲むメソッドが無い（import 文や宣言部） | 「メソッドの中にカーソルを置いてください」 |
| `bad-line` | 行番号が壊れている | 拡張の不具合。ログへ |

とくに `file-not-analyzed` と `not-found` は原因も対処もまったく違う（設定の問題か、
カーソルの位置の問題か）。ここを混ぜると、設定漏れを「呼び出し元が無い」と読み違える。

### Q8. `AT` はメソッドの終了行を持つか

設計の時点では**持たない割り切り**で進めるつもりだった。宣言の開始行しか無ければ
「同じファイルで宣言行が指定行以下のうち最大のもの」を選ぶしかなく、メソッドの外を指されると
直前のメソッドを返す。それは `MethodTable` とキャッシュの形式変更を伴うので、この設計とは切り離して
[#115](https://github.com/instreest/java-call-hierarchy-exporter/issues/115) にした。

結論は**持つ**（[method-decl-range-qa.md](method-decl-range-qa.md)）。「正しく見えるが間違っている答え」を
返すのはこのツールの方針（黙って取り違えない）に反する、という判断で、キャッシュの D 行に終了行を1列足した。
`AT` はメソッドの外なら `not-found` を返す。

VSCode 版の `AT` は、この変更（#124）と VSCode 版（#123）が別々に同じメソッドを足す形になり、
マージで二重定義になった。統合したものが今の `Server#at` で、#124 の「終了行で判定する」を採り、
#123 の「絶対パスも受ける」「`file-not-analyzed` を言い分ける」を残した。

### Q9. `AT` が絶対パスも受けるのはなぜか

拡張が持っているのは絶対パス（`Uri#fsPath`）だからである。相対パスへの変換を拡張側でやると、
「プロジェクトルートをどう知るか」「区切り文字をどうするか」を2言語で二重に実装することになる。

サーバーは `project.root` を知っているので、ここで受けてしまうほうが安い。
区切りを `/` に直し、ルート配下なら相対にする（`jche.config.ProjectLayout#relativeOf` と同じ綴りに寄せる）。

### Q10. 解析の設定（`config.properties`）をどう用意するか

`config.properties` があればそれを使い、無ければ **`project.root` だけ書いた最小の設定を生成**して、
残りは本体の `ProjectDetector` に決めさせる。`pom.xml` / `build.gradle` を読む仕組みが既にあるので
（[build-tool-classpath.md](build-tool-classpath.md)）、Maven / Gradle のプロジェクトはこれで足りる。

vscode-java の内部コマンドでクラスパスを取る案は採らなかった。精度は上がるが、
**公開 API でないコマンドに寄りかかる**ことになり、版が上がると黙って壊れる。
閉域環境で vscode-java が入っていないこともある。あくまで「あれば使う」任意の上乗せにとどめる。

Eclipse 版が `IJavaProject#getResolvedClasspath` から組み立てている（`EclipseProjectConfig`）のとは
対照的だが、これは Eclipse が標準でその情報を持っているのに対し、VSCode は持っていないという差である。

### Q11. 自動再解析の既定を Eclipse 版（ON）と変えて OFF にしたのはなぜか

VSCode は軽い編集に使われることが多く、「保存したら裏で数十秒の解析が始まる」は
最も嫌われる挙動のひとつだからである。まず ⚠ で「12 ファイルが変更されています」と知らせ、
利用者が ⟳ を押したときに走らせる。

ホストの文化が違えば既定が違ってよい、と割り切った。設定（`jche.autoAnalyze`）で ON にはできる。

### Q12. 木を一括で送るか、開いたときに取りに行くか

**一括のまま作り、測ってから決める。**

呼び出し元の木は深さに対して掛け算で増える（分岐 10・深さ 5 で 11 万行）。歯止めは既に入っていて、
`TreeFilters` の `maxDepth=5` / `maxRows=20000` / `dedupe=true` により最悪でも 2 万行、約 4 MB である。
心配なのは量そのものではなく**一度に届くこと**で、VSCode の拡張ホストは 1 本のスレッドなので、
分解している間はビューが固まって見える。

Eclipse 版は同じ作りで足りているため、先に複雑にはしない。判断の目安だけ先に決めた
（[vscode-plugin-design.md](vscode-plugin-design.md) §11）。1 回の `TREE` が 5,000 行・1 MB・300 ms 未満に
収まるなら一括のまま、超えるなら折衷案（深さ 2 まで一括、以降は節点を開いたときに取り直す）へ移る。

遅延取得は新しい仕組みではない。深さ上限で切った枝には既に `truncated` の印が付いており、
その節点を根にして `TREE` を投げ直す経路は Eclipse 版で動いている。

### Q13. リポジトリを分けるか

**同居させる**（`vscode-plugin/`）。`npm` のビルドがこのリポジトリに入るのは受け入れる。

分けると、同梱する JDT の版合わせ（`//DEPS` が唯一の出どころ）と、`AT` のような
プロトコルの変更への追従が面倒になる。Eclipse プラグインを同居させているのと同じ判断である。

### Q14. vscode-java との違いをどこで説明するか

**拡張の画面で完結させる**。`vscode-plugin/README.md`（Marketplace のページ）に
「標準の呼び出し階層との違い」の節を置き、未解析のときのビュー（`viewsWelcome`）にも1行で書く。

起動時に1回きりの通知を出す案は採らなかった。**頼んでいない通知は、1回でも嫌われる**。
知りたい人が見に行ける場所に置いてあれば足りる。

### Q15. `.vsix` を配るのに専用のワークフローを足したのはなぜか

**欲しいときに、任意のブランチ・タグから起こせる経路が要るため**（`.github/workflows/vsix.yml`、`workflow_dispatch` のみ）。

マーケットプレイスには出していないので、利用者は `.vsix` を「VSIX からのインストール」で入れる。
`.vsix` 自体は `smoke.yml` の `vscode-plugin` ジョブでもできていたが、あれは push / PR ごとの
**検査の副産物**である。配りたい版が古いコミットのときは、そのコミットを push し直すまで成果物が手に入らない。

`smoke.yml` に `workflow_dispatch` を足すだけでは足りない。重い回帰テストまで一式動いてしまい、
`.vsix` が欲しいだけのときに待たされる。

組み立てと中身の確認は `test/vscode/package.sh` に任せ、`smoke.yml` と同じものを使う。
配布物の作り方を 2 か所に書くと、片方だけが古くなって気づけない（`scripts/collect-lib.sh` の
「出どころを1つにする」と同じ理由）。

拡張の中身の検査（`npm test`）はこのワークフローでは動かさない。`npm test` は素で動かせるものではなく、
解析本体のクラスパスと `java` の場所（`JCHE_CP` / `JCHE_JAVA` ほか）を渡してもらう前提で、
渡さないと「解析に使う java が見つかりません」で落ちる（最初の版はここで失敗した）。
渡す役は `test/vscode/run.sh` で、そのために jbang で依存を解決して `src/` 全体をコンパイルする（JDK 25）。
配布物を作るだけのここでそれを繰り返す値打ちは無いので、検査は `smoke.yml` の `vscode-plugin` ジョブに任せる
（`eclipse-plugin-jar.yml` の「中身の検査は smoke.yml が受け持つ」と同じ切り分け）。

成果物の名前には `vscode-plugin/package.json` の版を入れる（`java-call-hierarchy-exporter-<版>-vsix`）。
`.vsix` のファイル名は版を持たない固定名なので、落としたものが何の版か分からなくなるため。
