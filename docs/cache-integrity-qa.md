# キャッシュの健全性と可用性 — 実装時の QA 一覧

キャッシュの健全性・可用性についてのソースコードレビューで見つかった 4 件
（[#97](https://github.com/instreest/java-call-hierarchy-exporter/issues/97)
[#98](https://github.com/instreest/java-call-hierarchy-exporter/issues/98)
[#99](https://github.com/instreest/java-call-hierarchy-exporter/issues/99)
[#100](https://github.com/instreest/java-call-hierarchy-exporter/issues/100)）と、
そこから派生した改善 1 件
（[#101](https://github.com/instreest/java-call-hierarchy-exporter/issues/101)）への対応で、
迷ったこと・困ったことと、その結論を Q&A の形で残す。

前の 4 件はどれも「キャッシュが静かに嘘をつく」形の不具合で、共通して
**更新時刻もサイズも変わらないのでキャッシュを消すまで直らない**という性質を持つ。

対応の要点:

- **行のエスケープ**（#97）: 値に混ざったタブ・改行でキャッシュの行が割れ、以降の呼び出しが
  読めなくなっていた。`CacheFormat.joinRow` で全列を必ず `clean` し、`Guard.atom` の出所も落とす。
  値を作る側（`OriginTracker` / `AnnotationTokens`）でも、行形式を壊す値は最初から拾わない
- **定数の連鎖**（#98）: コンパイル時定数の値は使う側のファイルに焼き込まれるため、
  「依存は1段で足りる」という差分更新の前提が定数についてだけ成り立たない。
  宣言している側に値を K 行（`jche.cache.ConstantFact`）として残し、解析し直して
  値が変わったときだけ、その型を参照しているファイルも解析し直す
- **注釈型の依存**（#98）: `BindingNames.annotationsOf` が注釈の型を「依存する型」（I 行）に
  数えていなかった。注釈のメンバの**既定値**は使う側の行に焼き込まれるので、数える
- **文字コードを鍵に入れる**（#99）: `source.level` と実行 JDK は鍵に入っていたが、
  ソースの文字コードだけ抜けていた。`headerFor` に `enc=` を足す
- **壊れたキャッシュ**（#100）: 途中で切れたキャッシュを気づかずに再利用していた。
  最終行に「ここまで書き終えた」印（Z 行）を置き、印が無ければ丸ごと捨てる。
  読めないキャッシュで解析ごと落ちていたのも、破棄して全件解析に倒す
- **中断した実行の引き継ぎ**（#101）: フェーズ1の途中で実行が終わると、そこまでの解析が
  丸ごと捨てられていた。残った一時ファイルを「パースの使い回し」として引き継ぐ
- キャッシュ形式は v14 → v15（K 行・T 行・Z 行の追加と、収集範囲・ヘッダの変更のため）
- 検査は `test/incremental/run.sh`（差分更新の結果と全件解析の結果を突き合わせる）

## 見つかった問題

### Q1. 「定数の値が古いまま残る」とは、具体的に何が起きるか

3 ファイルあれば再現する。

```java
// P.java
public class P { public static final String KIND = "ALPHA"; }
// X.java
public class X { public static final String KIND = P.KIND; }     // 値が焼き込まれる
// C.java
if (X.KIND.equals("BETA")) { Target.beta(); }                    // ここにも "ALPHA" が焼き込まれる
```

`P.KIND` を `"BETA"` に変えて差分更新すると、`P.java` と `X.java` は解析し直されるが、
`C.java` の I 行（依存する型）には `app.X` しか無いので `C.java` は再利用されてしまう。
結果、`C.java` のキャッシュには古い `V:ALPHA` が残り、

- 条件分岐の打ち切りが逆になる（呼ばれるはずの `Target.beta()` から先が階層に出ない）
- クラス名の文字列を辿るデータフローが、古い具象クラスを**断定して**出す
  （`[RESOLVED:DATAFLOW_FACTORY]` と注記が付くので、読み手には正しく見える）

キャッシュを消すまで直らず、更新時刻もサイズも変わらないので気づけない。
「呼び出しを静かに落とさない」に真正面から反する。

### Q2. 1段（直接参照）なら動いていたのはなぜか

たまたま `FieldAccessRecorder`（A 行の記録）が、参照したフィールドの所有型を
`BindingNames.typeNameOf` に通していて、そこで I 行に載っていたため。
値を畳んでいる `OriginTracker` 自身は依存を宣言していなかったので、A 行の記録の
都合が変わればいつ壊れてもおかしくない状態だった。
今回、畳む場所でも `noteDependency` を呼ぶようにして、この偶然に頼らないようにした。

### Q3. 行が割れる方の問題は何か

複数行の注釈の値だけで起きる。Spring Data の `@Query` はこの形が普通。

```java
@Query("SELECT u\n" + "FROM User u\n" + "WHERE u.name = ?1")
public String findByName(String name) { … }
```

注釈の値は D 行の最後の列に入るので、値の改行でそのまま行が割れる。
さらに 2 行目が `FROM …` だと**行頭が `F`** なので、次回の差分更新で
「別のファイルのブロックが始まった」と読まれ、`copyValidBlocks` がそこで書き写しを止める。
実測では、その注釈より後ろにあったメソッドと呼び出しが新しいキャッシュから丸ごと消え、
`call-hierarchy.csv` からも `methods.csv` からも二度と出てこなくなった。
`char sep = '\t';` のような定数でも、列がずれる形で同じことが起きる。

### Q3b. 文字コードはなぜ鍵に入っていなかったのか

`source.level` と実行 JDK は「同じソースでも解析結果が変わるから鍵に入れる」という理由で
1 行目に入っていたが、文字コードだけ抜けていた。実測すると、UTF-8 で作ったキャッシュを
`source.encoding=MS932` に変えた実行がそのまま再利用し、`"あいう"` の比較で
打ち切られた枝が打ち切られたまま残った。

`source.encoding` は空欄なら `pom.xml` の `project.build.sourceEncoding` から決まるので、
**`.java` を 1 行も触らずに**（pom に 1 行足しただけで）解釈が変わりうる。

### Q3c. 壊れたキャッシュはどうなっていたか

2 通りの壊れ方で、どちらも困る状態だった。

- **途中で切れたキャッシュ**: 切れた場所より前のブロックは「更新時刻もサイズも一致する」ように
  見えるので、そのまま再利用される。18 ファイルのプロジェクトでキャッシュの末尾 3 行を削ると、
  18 件すべてを再利用して出力が壊れる前と変わってしまった。ログにも何も出ない
- **文字が壊れたキャッシュ**: `MalformedInputException` がそのまま上がって設定ごと失敗する。
  全件解析し直せば済む話で、解析を止める理由が無い

キャッシュは一時ファイルへ書いてから移すので、このツール自身が半端なファイルを残すことはない。
それでも起きるのは、外から壊れたファイルが来る経路があるため（GitHub Actions のキャッシュの
復元、コピーの失敗、ディスクの異常）。

## 設計

### Q4. 直し方の案を 3 つ比べてどれを選んだか

| | やること | 直る | 触る範囲 | 失敗したときの被害 |
|---|---|---|---|---|
| 案3 | 定数を宣言するファイルを解析し直したら、参照元も連鎖して解析し直す | ○ | 判定だけ（15〜20 行） | 再解析が多いだけ |
| **案1** | 同じ連鎖を、**定数の値が実際に変わったときだけ**行う | ○ | 判定＋K 行（100〜150 行） | 再解析が多い／少ないだけ |
| 案2 | 値を焼き込むのをやめ、`F:型#フィールド` の参照だけ記録して読む側で引く | ○ | 記録する事実の意味（250〜350 行） | **キャッシュ無しでも結果が変わりうる** |

**案1** を選び、段取りとして先に案3 の形（連鎖の仕組みだけ）を入れてから、
K 行で「値が変わったときだけ」に絞った。決め手は 2 つ。

1. 案1・案3 が触るのは「解析し直すかどうか」の判断だけで、キャッシュを消せば必ず
   正しい答えが出る状態が保たれる。案2 は解析の中身を変えるので、しくじると
   キャッシュを消しても間違った答えが出る
2. 案1 なら、注釈の既定値の取りこぼし（Q8）も同じ仕組みで直る

### Q5. 案2（値ではなく参照を記録する）を採らなかった理由

原理的には案2 が根治で、連鎖も要らない。実際にコードを当てて調べたところ、
当初の見積もりが甘かったことが分かったため見送った。

- **宣言している側の J 行を流用できない**。`static final String PHRASE = "hello world";` や
  `JOINED = CLASSLIKE + "X"` の J 行は `U`（追跡不能）で、値を持っていない。
  一方で**使う側**は `getConstantValue()` を使うのでこれらも拾えている。
  そのまま案2 にすると、いま拾えている値を失って打ち切りが効かなくなる
- **既存の表を流用できない**。`CallGraph.fieldOrigins` は `static` フィールドを
  除外している（コンストラクタ注入の判定用のため）ので、定数用の表を新設することになる
- **ガードの両側を直す必要がある**。他ファイルの定数は、判定対象の側にも期待値の側にも現れる
  （`EQ｜A:0｜USER_DAO`、`EQ｜V:false｜true`）ので、`GuardEvaluator` の `holds` / `contains`
  の両方で解決が要る
- **jar の定数を失う**。`SomeLibConstants.PROD` はソースが無いので読む側で引けない。
  `ITypeBinding.isFromSource()` で場合分けすれば防げるが、分岐が 1 つ増える
- 結局**キャッシュ形式の変更は避けられない**（C 行・U 行の出所の意味が変わるので旧キャッシュは必ず捨てる）

案1 も案2 も「利用者が 1 回だけ全件解析になる」点は同じで、そこは差にならない。

### Q6. 連鎖はどこまで広がるか

このリポジトリ自身（116 ファイル）で測った。

```
コンパイル時定数: 127 件 / 定数を宣言しているファイル: 33 件（28%）

1 ファイル書き換えたときの再解析数（平均）
  もとの実装   3.9 件（ただし定数の取りこぼしあり）
  案3          6.3 件（1.6 倍。値を見ずに連鎖するため）
  案1         ≒4   件（値が変わったときだけ連鎖）
```

案3 でも最悪で全体の 2 割程度（2 → 24 件）だったので、正しさだけなら案3 で足りる。
案1 はそこから無駄を削る位置づけで、`test/incremental/run.sh` では
「定数の値を変えた書き換え = 5 件」「コメントだけの書き換え = 3 件」と差が出ることを固定している。

### Q7. K 行に何を入れるか。長い値はどうするか

`K  typeFqn  name  種別(V=値/H=ハッシュ)  値` の 5 列。
`static final` で `getConstantValue()` が値を返すフィールドと、注釈のメンバの文字列の既定値を入れる。

値は基本そのまま持つが、64 文字を超えるものと行形式を壊す文字を含むものはハッシュにする
（`jche.util.FileHash.ofText`）。SQL や Base64 のような長い定数でキャッシュが膨らむのを
避けつつ、変化は取りこぼさないため。種別の列を持つのは、「たまたまハッシュと同じ綴りの
短い値」と区別するため。

### Q8. 注釈の既定値まで見る必要があるか

ある。`@Ann` とだけ書いても、`String value() default "svc"` の `"svc"` は
`IAnnotationBinding.getAllMemberValuePairs()` から返ってきて、使う側の H 行・D 行・V 行に
焼き込まれる。しかも注釈の型が I 行に載っていなかったので、既定値を書き換えても
使う側は再解析されなかった。`annotationsOf` で注釈型を依存に数え、既定値も K 行に入れて、
定数とまったく同じ仕組みで面倒を見ている。

### Q9. 列挙定数は大丈夫か

大丈夫で、今回も変えていない。

- 列挙定数の出所は `V:fx.Mode.FULL` のように**宣言型で修飾された名前**で、値ではない。
  定数の追加・削除・改名は必ず enum のソースの変更になり、参照側の I 行にはその enum 型が
  載っているので、これまでどおり 1 段の依存で追随できる
- `static final Mode MODE = Mode.FULL;` は enum 型なのでコンパイル時定数にならず、
  値の焼き込み自体が起きない（安全側に倒れて打ち切らない）

`test/incremental/run.sh` に「列挙定数の改名」のケースを入れて、この性質を固定した。

### Q10. キャッシュの版を上げる必要はあるか

ある（v14 → v15）。K 行という行種を足したことに加え、行形式を壊す値を
「事実として拾わない」ことにした＝収集範囲が変わったため
（[CacheFormat](../src/jche/cache/CacheFormat.java) の「バージョンを上げる基準」）。

### Q10b. 文字コードは正規名にそろえる必要があるか

ある。`utf-8` と `UTF-8` のような表記の揺れでヘッダが変わってしまうと、設定を何も変えて
いないのに全件解析し直しになる。`source.encoding` に書いた場合は既に `Charset#name()` を
通していたが、`pom.xml` から自動判定した場合は pom の記述がそのまま入っていたので、
そちらも正規名にそろえた。ついでに、pom に不正な文字コード名が書いてあったときの
エラーが設定読み込みの時点で出るようになる（以前は解析中に出ていた）。

### Q10c. 壊れたキャッシュをどう見分けるか

**最終行に「ここまで書き終えた」印を置く**（`Z` 行。ブロック数つき）。
読むときに印が無い・数が合わなければ、丸ごと捨てて全件解析し直す。

「ファイルの大きさを記録する」「全体のハッシュを持つ」も考えたが、

- 途中で切れたキャッシュは**行の途中で終わる**とは限らない。切れた場所より前のブロックは
  文法的に正しいままなので、行単位の検査では気づけない。「終わりまで書いた」という
  印そのものが要る
- ブロック数まで見るのは、途中のブロックが抜けた場合にも気づけるようにするため
- 全体のハッシュは、書くときに digest を通す仕組みが要るわりに、検出できる範囲が
  「印＋数」とほとんど変わらない（実際に起きるのは切り詰めとバイト化け）

バイト化けの方は、読むときに `MalformedInputException` になるので印を見る前に分かる。
「読めなければ破棄」に倒せば十分で、こちらに印は要らない。

なお、読み込み時に不正なバイトを `U+FFFD` に置き換える（寛容なデコード）案は採らなかった。
それだと**有効なブロックの中の型名が静かに化けて**そのまま再利用されうるので、
「読めない＝捨てる」の方が安全側。

## 実装

### Q11. パス3 を「判定」と「書き写し」に分けたのはなぜか

連鎖するには「再解析する → 変わった型が増える → もう一度判定する」を繰り返す必要があるが、
もとの `copyValidBlocks` は判定と書き写しを 1 回のスキャンで同時にやっていた。
書き写しを始めてしまうと、あとから「やっぱりこのブロックは再解析」と決め直せない。

そこで `selectDependents`（判定だけ。何も書かない）と `copyValidBlocks`（書き写しだけ）に分け、
判定 → 再解析 → 判定 …… を不動点まで回してから、最後に書き写すようにした。
結果として両方のメソッドが短くなり、F 行の先読みのような込み入った扱いも消えた。

代償はキャッシュファイルを読む回数が 1 回増えること（判定 1 回＋書き写し 1 回）。
連鎖が起きない実行では判定で何も動かないので、「変わった型」が 1 つも無いときは
判定そのものを飛ばしている。

### Q12. 連鎖は必ず止まるか

止まる。1 周ごとに `valid`（そのまま書き写す候補）からファイルが減るだけで、
増えることはない。加えて、周回の前後で「変わった型」の数が増えていなければ
そこで打ち切る（`StaleTypes.mark()`）。

### Q13. 旧キャッシュの定数をヒープにどう持つか

ファイルごとに **16 文字のハッシュ 1 つ**だけ持つ（`CacheUpdater.oldConstants`）。
K 行の指紋を並べて `FileHash.ofText` したもので、値そのものは持たない。
既にある「相対パス → 内容ハッシュ」の表（`hashes`）と同じ重さで、
「解析結果をヒープに溜めない」という設計は崩していない。

K 行は指紋の順に並べて書く。同じソースならいつ解析しても同じ並びになるので、
旧キャッシュとの突き合わせが並び順に振り回されない。

### Q14. 制御文字を含む値は、書き出すときに空白へ置き換えるのではだめか

書き出すときの置き換え（`CacheFormat.joinRow` の `clean`）は最後の関所として入れたが、
それだけにはしなかった。`'\t'` と `' '` が同じ値になってしまうと、
`if (SEP == '\t')` のような条件で「成立しない」と**誤って**打ち切りうるため。

値を作る側（`OriginTracker.valueConst` / `AnnotationTokens.token`）では、
行形式を壊す文字を含む値はそもそも拾わない。拾わなければ読み手は判定をしないので、
安全側（打ち切らない）に倒れる。「分からない条件はアトムにしない」という
[branch-pruning-qa.md](branch-pruning-qa.md) の方針と同じ考え方。

### Q15. 注釈の値に長さの上限（64 文字）を入れたのはなぜか

この値を読むのは DI コンテナの Bean 名・Qualifier 名の照合（`jche.graph.SpringBeans`）だけで、
どれも短い識別子だから。一方 `@Query("SELECT …")` のように長い SQL を値に取る注釈は珍しくなく、
上限が無いとキャッシュがその文字列で埋まる。上限を超えたものは「付いていた事実」だけ残す。

値を丸ごと捨てる（空白に置き換えない）のは、別々の値が同じ Bean 名に見えて候補を
誤って絞り込むのを避けるため。絞れない方に倒れる。

### Q15b. 「印が無い」の検査はどのパスで行うか

**パス1**（旧キャッシュを頭から読んで、有効なブロックを集めるところ）。理由は 2 つ。

- パス1 はもともとキャッシュを最後まで読むので、印を見るための追加の読み込みが要らない
- パス1 は解析も書き出しも始まる前なので、そこで「丸ごと捨てる」に切り替えれば
  中途半端な状態が残らない。パス3 以降で気づいても、もう新しいキャッシュを書き始めている

パス0（ヘッダと L 行だけ読む）では最終行まで届かないので、印は見られない。
パス0 で読んだ L 行が切れたキャッシュ由来でも、L 行はファイルの先頭にあるので影響しない。

### Q15c. 書き写すときに、旧キャッシュの印まで写してしまわないか

写してしまい、印が 2 行に増えていた（差分更新のキャッシュと全件解析のキャッシュを
突き合わせる検査で見つかった）。`copyValidBlocks` は最後のブロックを書き写している途中で
最終行に出会うため。`Z` 行に当たったらそこで書き写しを止め、新しい印は最後に 1 行だけ書く。

印の行は、キャッシュを読む他の経路（グラフ構築・未解決の一覧）では知らない行種別として
読み飛ばされる。

## テスト

### Q16. なぜ期待値ファイル（`expected*/`）を持たない検査にしたか

この検査が見たいのは「差分更新と全件解析で結果が違わないこと」で、
**同じソースに対する 2 通りの解析を突き合わせれば足りる**から。期待値を持つと、

- 検査用のソースを 1 行足すたびに期待値の更新が要る
- 期待値を更新するときに、本当は直っていない差分をうっかり取り込みうる

`test/regression/` は「出力の内容」を固定する検査なので期待値が要るが、
こちらは「2 つの経路が一致する」という性質の検査なので要らない。

### Q17. CSV だけでなくキャッシュも比べる理由

CSV に出ない事実の取りこぼしを捕まえるため。注釈の既定値（Q8）がまさにそれで、
H 行の値が古いままでも `call-hierarchy.csv` は変わらない。
キャッシュを突き合わせれば、事実の段階で食い違いを見つけられる。

差分更新ではブロックの並びが変わる（解析し直したブロックが末尾に移る）ので、
行を並べ替えてから比べる。F 行の更新時刻・サイズ・内容ハッシュは
どちらの経路でも「今のファイル」の値になるので、そのまま一致する。

### Q18. 「書き換えが効いている」ことをどう確かめるか

書き換えの仕方を間違えると、差分更新も全件解析も同じ（古い）結果になって検査が素通りする。
そこで書き換え前のキャッシュも取っておき、**F 行以外の行**（＝事実）が変わったかを見る。
F 行を除くのは、書き換えたファイルの更新時刻とサイズは中身に関わらず必ず変わるため。

### Q19. 直す前のコードで、この検査は落ちるか

落ちる。検査を書いたあとに必ず旧実装で落ちることを確認してから、直したコードで通した。

| ケース | 旧実装での結果 |
|---|---|
| 2段の定数 / 注釈の既定値 / 列挙定数の改名 / コメントだけ変更 | 「差分更新 == 全件解析」が破れる。`@Query` を含むので「キャッシュの行が壊れていない」も落ちる |
| 文字コードの変更 | 違う文字コードのまま 18 件すべてを再利用する |
| 途中で切れたキャッシュ | 18 件すべてを再利用し、出力が壊れる前と変わる |
| 文字が壊れたキャッシュ | 解析ごと失敗する |

「途中で切れたキャッシュ」は、切り方を誤ると旧実装でも偶然通ってしまう。
最初に「先頭 5 行だけ残す」で書いたところ、残った 1 ブロックが他のファイルの変更に
巻き込まれて再解析され、旧実装でも再利用 0 になった。
**末尾を数行削る**形に変えて、旧実装がちゃんと 18 件を再利用してしまうことを確かめている。

## 中断した実行の引き継ぎ（#101）

### Q20. 中断すると何が失われていたか

フェーズ1（ソース解析）の途中で実行が終わると、**そこまでの解析が丸ごと捨てられていた**。
2000 ファイルのプロジェクトで開始 4 秒後に `kill -INT` した実測:

```
中断時点     : ソース解析 700/2000
.cache の中身: analysis-cache.tsv.tmp だけ（745KB、779 ファイルぶん）
次回の実行   : .tmp を読まないので 779 ファイルぶん（全体の 39%）を解析し直す
```

中断のされ方は 2 通りある。CLI は `RunControl` に受け口が付かないので `checkCancelled()` が
素通りし、**Ctrl+C で JVM ごと即死**する（一時ファイルの最終行は書き込みバッファの途中で切れる）。
Eclipse プラグインだけが `CancelledException` でバッチの切れ目から抜ける。
どちらも一時ファイルは次の実行が同じ名前で開き直すまで残りっぱなしで、掃除もされなかった。

失われるのはフェーズ1の途中で中断したときだけで、フェーズ2・3 まで進んでいればキャッシュは
既に差し替わっている。

### Q21. 一時ファイルをそのまま本物に差し替えてはいけないのはなぜか

2 つ理由がある。

- **再利用ぶんが消える**。書き写し（パス5）は一番最後なので、中断時の一時ファイルには
  「新しく解析したブロック」しか入っていない。差し替えると、再利用するはずだったブロックが
  全部消え、次回は結局ほぼ全件解析になる（差分更新では今より悪化する）
- **依存の判定を通っていない**。パス3 がまだなので、本来無効化されるはずのブロックが
  「有効」のまま残り、次回は更新時刻もサイズも一致するので古い事実を引きずる

中断した実行には出力が無いので、気にすべきは「その実行の結果」ではなく
**「次回の実行が正しくなるか」だけ**。

### Q22. どういう位置づけで使うことにしたか

**正しいキャッシュとしては使わず、パースの使い回しにだけ使う。**

```
次回の実行
  旧 analysis-cache.tsv … 今までどおり「どのブロックが有効か」を決める（判定は一切変えない）
  退避した .partial     … これから解析するファイルについて、条件が合えばパースの代わりに書き写す
```

引き継いだファイルは引き続き「変わったファイル」として扱う（宣言する型は「変わった型」に入り、
依存の判定も連鎖も回る）。変わるのは **JDT でパースするか、書き写すか**だけ。

### Q23. 「そのファイルが変わっていなければ引き継いでよい」で足りるか

**足りなかった**。検査を書いて初めて分かった。

最初は「更新時刻とサイズが一致するファイルのブロックは、そのまま書き写してよい」で実装した。
ところが `test/incremental/run.sh` の「中断後にソースが変わったら引き継がない」ケースが落ちた。

```
中断 → Base.java の定数を書き換えて実行
  引き継ぎあり: inc.AlphaDao.select(),[RESOLVED:DATAFLOW_FACTORY]   ← 古い値のまま
  引き継ぎ無し: inc.BetaDao.select(),[RESOLVED:DATAFLOW_FACTORY]
```

`Names.java` と `Client.java` は自分自身が変わっていないので「一致」と判定されるが、
その中身（`L:inc.AlphaDao`）は **`Base.java` の内容から来ている**。呼び出し先・親型・
コンパイル時定数の値はどれもバインディング解決の結果なので、
**別のファイルが変われば、そのファイル自身が変わっていなくてもブロックは古い**。

差分更新はこれを I 行の依存（パス3）で見分けるが、引き継ぎのブロックは
「今このファイルを解析した結果」として書き込むので、その判定を通らない。

### Q24. どう直したか。もっと細かく判定できないか

**ソース一覧（相対パス・サイズ・内容ハッシュ）の指紋を T 行として持ち、丸ごと一致するときだけ
引き継ぐ**ことにした。1 つでも変わっていれば引き継がない（差分更新はこれまでどおり働く）。

細かく判定する案も考えた。退避した一時ファイルを「既存キャッシュと同じ扱い」で
パス1・パス3・パス5 に読ませれば、引き継いだブロックも依存の判定を通せる。
ただし 2 つのファイルを併読することになり（同じファイルのブロックが両方にある場合の
優先順位も要る）、だいたい 80 行の追加になる。

引き継ぎが効いてほしいのは「中断してすぐ、同じソースで実行し直す」場面
（CI のタイムアウト、OOM、`kill -9`、中止ボタン）なので、そこは一覧が丸ごと一致する。
簡単で明らかに正しい形を選んだ。細かい判定が要るようになったら、そのとき別の変更として入れればよい。

### Q24b. 指紋に更新時刻を入れないのはなぜか。全ファイルのハッシュを取ると遅くならないか

**更新時刻は中身と関係なく変わる**（git のチェックアウト、コピー、CI のたびに作り直される
ワークスペース）。指紋に入れると「中身は同じなのに引き継げない」が頻発する。
差分更新の判定が内容ハッシュで救っているのと同じ考え方
（[actions-analysis-cache-qa.md](actions-analysis-cache-qa.md)）。

全ファイルのハッシュが要るように見えるが、**ほとんどは読み直さずに済む**。
更新時刻とサイズが旧キャッシュの F 行と一致するファイルは、記録されているハッシュが
そのまま「今の内容のハッシュ」なので、パス1 でそれを覚えておいて使い回す。
残るのは「これから解析するファイル」だけで、そのハッシュはどのみち F 行に書くために計算する。

実測（26MB・500 ファイルのプロジェクト、変更なしの実行を 3 回平均）:

```
更新時刻ベース: 844ms
ハッシュベース: 854ms   （ソースを読み直していないので差が出ない）
```

2000 ファイルの初回（全件解析）でも、A/B で差は測定誤差に埋もれた
（6.2〜6.6 秒、どちらも同じ範囲）。ハッシュはパースよりはるかに軽い。

### Q25. ほかにどんな条件を付けたか

- **ヘッダ**（形式・ソースレベル・文字コード・JDK・拡張の指紋）が一致すること
- **依存 jar が変わっていないこと**。ブロックは当時のクラスパスでのバインディング解決の結果なので
- **最後の F 行から始まるブロックは使わない**。そこだけ書き込みバッファの途中で切れている
  可能性があるため。次の F 行か、最後まで書き終えた印（Z 行、#100）に出会ったブロックだけを使う。
  実測では、切れた一時ファイルでもそれより前の 778 ブロックは「F 行の次は必ず I 行」を満たしていた
- ファイル単位の一致は差分更新と同じ判定（更新時刻とサイズ、更新時刻だけ違うならサイズと
  内容ハッシュ）を使う。こちらも更新時刻だけの違いでは弾かれない
- `cache.enabled=false` のときは引き継がない（再利用を止める指定のため）

効果（2000 ファイル、開始 6 秒で中断した実測）:

```
引き継ぎあり: 新規解析=112  引き継ぎ=1888  フェーズ1 2.2 秒（全体 2.8 秒）
引き継ぎ無し: 新規解析=2000               フェーズ1 5.2 秒（全体 5.7 秒）
```

### Q26. 一時ファイルの名前をどう扱うか

起動時に `.tmp` が残っていれば `.partial` に改名してから、新しい `.tmp` を開く。
これから書く一時ファイルと名前がぶつかるのを避けるためで、ついでに
**残りっぱなしだった一時ファイルの掃除**にもなる（従来は次の実行が上書きするまで残っていた）。
引き継ぎが終わったら `.partial` は消す。`.tmp` が無くても `.partial` が残っていれば使う
（退避した直後に落ちた場合のため）。

### Q27. 得をするのはどこまでか

パス2（変更・追加されたファイルの解析）だけで、パス4（依存で再解析するファイル）は対象外にした。
パス4 の対象は退避ファイルをもう一度読まないと拾えないのに対し、中断が一番痛いのは
初回の全件解析で、そこは全ファイルがパス2 を通るため。

## 限界（対応しないと決めたこと）

- **同時実行**。同じ `project.root` を指す 2 プロセス（CLI と Eclipse プラグインのサーバーなど）が
  同じ `analysis-cache.tsv.tmp` を奪い合う。1 つのプロセスの中は逐次なので単独なら問題ない。
  ロックファイルか、一時ファイルの名前に PID を入れれば防げるが、今回の 4 件とは別の話として残す
- **更新時刻とサイズが一致するのに中身が違うファイル**。差分更新の基本方針どおり、
  更新時刻が一致していれば内容ハッシュは取らない（`cache.enabled=false` にするか
  キャッシュを消す、という既存の逃げ道のまま）
- **jar の中の定数**。jar にはソースが無いので K 行を作れないが、jar の変更は L 行の仕組みで
  検知され、その jar のパッケージの型を参照しているファイルが解析し直されるので取りこぼさない
