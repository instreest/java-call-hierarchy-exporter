# `callee` 列の表記と `NO_IMPL` の注記 — Q&A

`call-hierarchy.csv` の `callee` 列を「クラス名.メソッド名」だけにし、
本体を持つ実装が無い呼び出し（`NO_IMPL`）の注記を出さなくした判断を残す。
関連: [prompt-B-detailed.md](prompt-B-detailed.md) 4.1（列の仕様）、
[doma-generated-impl-qa.md](doma-generated-impl-qa.md)（同じ「実装が無い」でも言い分ける場合）。

## 結論

- `callee` は `クラス単純名.メソッド名`。完全修飾のパッケージも引数型も付けない
- 外部 jar からの被参照の行（`被参照:*`）の `callee` も同じ表記に揃えた
- `NO_IMPL`（本体を持つ実装がソース上に1つも無い）の注記
  `実装なし（宣言のまま）: 理由` は `call-hierarchy.csv` に出さない
- 絞れなかった事実そのものは `methods.csv` の `unresolvedCalls` / `unresolvedCause` に残る

### Q1. なぜ完全修飾と引数型をやめたのか

この列の用途は Excel のフィルタで「どの呼び出し先か」を選ぶこと。パッケージと引数型が付くと
1 つの呼び出し先がオーバーロードの数だけ選択肢に分かれ、列幅も広く、目で追う階層列
（`call-hierarchy`）とも表記が食い違っていた。フィルタで選ぶ単位は
「クラスとメソッド」でよい、というのが利用者の実感に合う。

### Q2. オーバーロードとパッケージ違いの同名クラスは見分けられなくなるのでは

`callee` だけでは見分けられなくなる。ただし行そのものは 1 呼び出し 1 行のままで、
`caller` 列に呼び出し箇所のファイルと行番号が出ているので、行が混ざったり消えたりはしない。
引数型まで込みで識別したいときは `methods.csv` の `method` 列（`Repo.save(java.util.List)` の形。
略名が衝突する組だけ完全修飾に戻す仕組みもそのまま）を使う。

### Q3. `NO_IMPL` の注記を消すのは「呼び出しを静かに落とす」ことにならないか

ならない。消えるのは注記だけで、**行は出したまま**（宣言のまま 1 行）。
インターフェースが多いプロジェクトではこの注記が何百行にも付き、
`[CYCLE]`・深さ制限・`CHA候補N件` のような「読み手が次に動くための注記」が埋もれていた。
「実装がソースに無い」ことは `methods.csv` の `unresolvedCause` に残るので、
まとめて調べたいときはそちらを見る。

### Q4. 「実装はコンパイル時生成」の注記も消すのか

消さない。あれは「ソースに実装が無い」理由が分かっていて、
生成されるクラス名まで出せる（読み手が次に見る場所が決まる）注記なので残す。
