# call-hierarchy.csv の行順の固定 — 実装時の QA 一覧

[Issue #43](https://github.com/instreest/java-call-hierarchy-exporter/issues/43)
「call-hierarchy.csv の行順はファイルシステムが違っても同じとしたい」への対応で、
迷ったこと・困ったことと、その結論を Q&A の形で残す。

対応の要点:

- `ProjectLayout.listJavaFiles()` が返す .java ファイルの並びを「ソースフォルダの宣言順 →
  フォルダ内は相対パス（`/` 区切り）の文字列順」に固定する。`Files.walk` の順（ファイルシステム依存）を
  そのまま使わない
- `UnresolvedReport`（`type resolution failed …` の行）の並びも「ソースフォルダの宣言順 → 相対パス順 →
  ファイル内の出現順」に固定する。これまではキャッシュのブロック順のままだった
- 回帰テストの期待出力（`whole` / `entry` / `jarchange` の `expected-before`）を JDK 25 で作り直す。
  差分は `型解決に失敗` の行 1 件の位置だけ

---

## 調査

### Q1. 行順は本当に「木の内部まで」解析順に依存していたか

Issue の見立ては「MethodTable の ID が初出順で振られ、StreamingTreeWalker は格納順のまま辿るので、
木の内部の並びは解析順のまま」だった。直す前に、これがどこまで本当かを実測した。

`listJavaFiles()` の並びを **名前順** と **その逆順** にして `whole` ケースを実行し、
2 つの `call-hierarchy.csv` を比べた。違ったのは末尾の `type resolution failed …` の節にある 1 行の位置だけで、
呼び出し階層（木）の部分と `methods.csv` は完全に一致した。

木の部分がファイル順に影響されない理由は、並びを決める箇所がすべて明示的に決まっているから。

| 並び | 決めている場所 | 何順か |
|---|---|---|
| 起点 | `SourceOrder.sortedBySource` | ソースフォルダ順 → 型 FQN 順 → 宣言行順 → ID 順 |
| 起点の呼び出し先（エッジ） | `CallGraphBuilder.secondPass` | キャッシュの `C` / `U` 行の順。1 つのメソッドのエッジは全部そのメソッドのファイルのブロックにあるので、ファイル内の出現順 |
| CHA の候補 | `TypeHierarchy.sortForDeterminism` + `transitiveSubtypes` | 宣言型自身 → 下位型。直接の下位型は型 FQN 順で、そこから深さ優先に辿る（差分更新でブロックが動くことへの対策として、すでにソート済みだった） |
| リフレクションの候補 | `DataflowResolver.methodsNamed` | ID 順。ただし同じ型の同名メソッドなので同じブロック内で決まる |

ID 順が効くのは、起点の並びで「同じ型・同じ宣言行」に複数のメソッドがある場合（暗黙コンストラクタと
`<clinit>` 等）の同着だけで、それは同じファイルの中の行順で決まる。つまり **ID の絶対値はファイル順で変わるが、
出力に効く相対順はファイルの中で閉じている**。

（後日注: この「ファイルの中で閉じている」は厳密には成り立っていなかった。同じファイルのメソッドでも、
別のファイルのブロックで先に ID 化されることがある。同着を ID で決めるのはやめた。Q14〜Q19）

### Q2. では NTFS と ext4 で何が変わっていたのか

`type resolution failed …` の節。`UnresolvedReport` はキャッシュを頭から読み、`U` 行が出てきた順に書いていた。
キャッシュのブロック順は初回実行では `listJavaFiles()` の順なので、ext4（`fx/dao` が `fx/app` より先に
列挙される）と NTFS（名前順）で `LibBackedDao.findById` と `Legacy.callRemote` の行の前後が入れ替わる。
回帰テストの期待出力は ext4 で作られていたので、Windows では毎回この 1 行が DIFF になっていたはず。

### Q3. `型解決に失敗` の節は、同じ環境でも実行のたびに変わりうるか

変わりうる。差分更新（`CacheUpdater`）は「今回解析したファイルのブロック → 旧キャッシュから写した
有効ブロック → 依存で解析し直したブロック」の順に新しいキャッシュを書く。ファイルを 1 つ直して再実行すると、
そのファイルのブロックがキャッシュの先頭へ移り、その `U` 行も節の先頭へ移る。

Issue の題はファイルシステムの違いだが、「行順を環境や履歴に依存させない」という目的は同じなので、
この節の並びも明示的に決めることにした（Q6）。`listJavaFiles()` のソートだけでは、初回実行の並びは
固定できても、その後の差分更新でまた崩れる。

## 設計

### Q4. ファイルの並びの鍵に何を使うか

候補は `Path#compareTo` と、相対パス文字列の `String#compareTo`。相対パス文字列にした。

- `Path#compareTo` は OS で挙動が違う。Windows（`WindowsPath`）は大文字小文字を無視して比べ、
  Unix はバイト列で比べる。`Zoo.java` と `abc.java` の前後が OS で変わる
- `ProjectLayout.relativeOf` は区切りを `/` に揃えた相対パスを返す。これは `methods.csv` の並び
  （`SourceOrder.declaredMethodsInSourceOrder` が `declFile` で整列）とキャッシュの `F` 行が使っている
  のと同じ文字列なので、同じ鍵にすれば「ファイルの並び」がツール全体で 1 つになる

`/`（0x2F）は英数字より小さいので、`fx/dao/Dao.java` → `fx/dao/DaoFactory.java` のように、
ディレクトリの中身が先に並ぶ自然な順になる。

### Q5. NTFS の並び（大文字小文字を無視した名前順）に合わせなくてよいか

合わせない。NTFS の順は「NTFS の upcase テーブル」で決まる OS 依存のもので、Java から同じ順を
再現するにも `Collator` 等の別の定義を持ち込むことになる。`methods.csv` はすでに `String#compareTo` の順で
出ているので、それに揃える方が一貫する。大文字小文字だけが違うファイル名の前後が NTFS の表示順と
食い違うことはあるが、「どの環境でも同じ順」が目的なので許容した。

### Q6. `UnresolvedReport` は全件をためて sort すればよいのではないか

しなかった。このクラスは「件数ぶんをヒープに載せない」ためのストリーミング処理として書かれている
（クラスコメント）。依存 jar がほとんど無い状態で大きなプロジェクトを解析すると `U` 行は呼び出し箇所の
数だけ出るので、その設計は残したい。

代わりに、ブロックの並びを先に決めてから合流させる方式にした。

1. キャッシュを 1 回読んで `F` 行の相対パスを集め、出力順（Q4 と同じ鍵）に並べて順位を振る
2. もう 1 回読みながら、「次に出すべき順位」のブロックの `U` 行はそのまま書く。順番がまだ来ていない
   ブロックの `U` 行は生の行文字列のまま順位ごとに保留し、そのブロックの番が来たら書く
3. ブロックを読み終えるたびに「次に出すべき順位」を進め、保留分があれば書く

キャッシュが出力順どおりに並んでいれば（初回実行、全ファイル再利用）何も保留しない。
差分更新でブロックが先頭へ移った場合は、そのファイルの `U` 行だけを保留する。
全ブロックが逆順に並ぶ最悪ケースでは全件をためることになるが、`CacheUpdater` の書き方では
「解析し直したファイル」だけが前へ来るので、実際の保留は解析し直した分に留まる。

### Q7. `F` 行の並びのために、キャッシュをもう 1 回読むのは重くないか

読む回数は 1 回増える（`CallGraphBuilder` が 2 回、`UnresolvedReport` が従来 1 回 → 2 回）。
`F` 行の相対パスを集めるだけの逐次読みで、ファイル数ぶんの文字列しか持たない。`CacheUpdater` が
全ファイルの `live` マップをヒープに載せているのと同じ規模なので許容した。

`ProjectLayout.listJavaFiles()` の結果を渡せば読まずに済むが、`UnresolvedReport` はキャッシュを
読む処理なので「キャッシュに何のブロックがあるか」はキャッシュ自身から取る方が素直で、
呼び出し側との結合も増えない。

### Q8. `CacheUpdater` 側でブロックを出力順に書けば済むのではないか

済まない。差分更新は「解析したものから順に書く」「旧キャッシュは読みながら写す」ストリーム処理で、
書く順を変えるには解析結果か旧ブロックのどちらかを溜めるか、書いた後に並べ替える必要がある。
それより読む側（`UnresolvedReport`）で並びを決める方が、キャッシュの形式も書き手も変えずに済む。

### Q9. `F` 行が無い `U` 行や、同じ相対パスの `F` 行が 2 つある場合は

どちらも通常は起こらないが、行を落とさないようにしている。順位が引けない `U` 行はその場で書き、
同じ相対パスの 2 つ目のブロックは（順位がもう進んでいれば）その場で書く。
並びは崩れうるが、行が消えるよりよい。

### Q10. `listJavaFiles()` の `LinkedHashSet` は残す必要があるか

残した。`source.folders` に親子関係のフォルダを指定すると同じファイルが 2 回列挙されるので、
その重複を落とす役目が残っている。ソートはフォルダごとに行い、フォルダの宣言順は変えない
（`SourceOrder` の「ソースフォルダの宣言順」と揃える）。

## テスト

### Q11. 期待出力の再生成に JDK 25 が要るが、この作業環境では取れなかった

`//JAVA 25` の指定により、JBang は無ければ JDK 25 を foojay（Disco API）から取得する。
今回の作業環境はそこへの接続が遮断されており、`jbang jdk install 25` は
`JDK is not available for installation` で失敗した。

Temurin の GitHub リリース（`github.com/adoptium/temurin25-binaries/releases/download/...`）は
通ったので、そこから tar.gz を取って展開し、`jbang jdk install 25 <展開先>` で JBang に登録して
回帰テストを実行した。期待出力は README の原則どおり JDK 25 で生成している。
以前の対応（[fatjar-external-usage-qa.md](fatjar-external-usage-qa.md) の Q18）では JDK 21 で
代用したが、今回は JDK 25 そのもので作った。

### Q12. 期待出力の差分はどれだけか

3 ファイル（`whole/expected`、`entry/expected`、`jarchange/expected-before` の `call-hierarchy.csv`）で、
いずれも `型解決に失敗` の節の `fx.dao.LibBackedDao.findById` の行が `fx.app.Legacy.callRemote` の
3 行の後ろへ移っただけ。木の部分と `methods.csv` は変わらない（Q1）。
`jarchange/expected-after` は jar があると `LibBackedDao.findById` が解決されて `U` 行が無くなるので
変化なし。

### Q13. 差分更新でブロックが動くケース（Q3）はどう確認したか

`whole` ケースを 1 回実行してキャッシュを作ったあと、`samples/demo/src/fx/dao/LibBackedDao.java` を
`touch` して再実行した。キャッシュの先頭ブロックが `LibBackedDao.java` になったことを `F` 行で確認し、
`call-hierarchy.csv` が期待出力と完全一致することを確認した（保留 → 順番が来てから書く経路）。
`Legacy.java` を `touch` した場合も同様に一致した（出力順で先頭のファイルなので保留は起きない経路）。

回帰テストのスクリプト（`run.sh` / `run.cmd`）にこのケースを足すことは見送った。
サンプルの mtime を変える操作が要り、2 つのスクリプトに同じ手順を足す割に守れるのがこの 1 点だけなので、
手動確認の手順としてここに残す。

## 追記: 同じ行に並ぶ宣言の前後を ID で決めていた

Q1 の「出力に効く ID の相対順はファイルの中で閉じている」が成り立たない場合が見つかったので、
同着の決め手を ID から外した。キャッシュを 1 ファイルにまとめる作業（ブロックの中で行を並べ替えると
ID の振られ方が変わる）の下調べで、並べ替える前からあった問題として見つかった。

対応の要点:

- 同じ行に並ぶ宣言の前後を、ID ではなく「宣言行 → ファイルの中の宣言の順番（ブロックの `D` 行の位置）→
  キーの文字列」で決める（`MethodTable.compareDeclarationOrder`）。使うのは `methods.csv` の並び
  （`SourceOrder.declaredMethodsInSourceOrder`）、起点の並び（`SourceOrder.sortedBySource`）、
  サーバーの `AT`（`MethodTable.enclosingMethod` で範囲の広さが同じもの）
- 名前だけで照合したリフレクションの候補（`DataflowBuilder.methodsByName`）も ID 順をやめ、
  宣言ファイル → 同じ鍵の順にした
- キャッシュの形式と書き手は変えていない（版は上げない）。回帰テストの期待出力は 1 行も変わらない
- `test/incremental` に同じ行の宣言のケース、`test/server` に `AT` の同着のケースを足した

### Q14. 何が ID に依存していたか

メソッドの ID は、キャッシュを読みながら**初めて ID 化した順**に振られる（`MethodTable.intern`）。
1 つのブロックの中では「戻り値の出所（`R` 行）→ 宣言（`D` 行）→ 上書き（`O` 行）→ 呼び出し（`C` / `U` 行）」の
順に ID 化するので、次の 2 つで ID の前後がソースの並びとずれる。

- **`R` 行を持つメソッドは宣言より先に ID 化される。** `R` 行はブロックの `D` 行より前にある
- **別のファイルから呼ばれているメソッドは、そのファイルのブロックで ID 化される。** 差分更新
  （`CacheUpdater`）は解析し直したファイルのブロックを先頭に書くので、呼び出し側のファイルだけを直すと、
  呼ばれる側のメソッドが自分のブロックより先に ID 化される

同着を ID で決めていたのは次の 4 か所で、どれも出力に出うる。

| 箇所 | 同着になる場合 | 出る先 |
|---|---|---|
| `SourceOrder.declaredMethodsInSourceOrder` | 同じファイル・同じ宣言行（1 行に書いたメソッド） | `methods.csv` の行順 |
| `SourceOrder.sortedBySource` | 同じ型・同じ宣言行（1 行に書いたメソッド、同じ行のラムダ） | `call-hierarchy.csv` の起点の並び |
| `MethodTable.enclosingMethod` | 範囲の広さが同じ（1 行に書いたメソッドとその中のラムダ等） | サーバーの `AT` が返すメソッド |
| `DataflowBuilder.methodsByName` | 同じ型の同じ名前（オーバーロード） | リフレクションの候補の並び（Q18） |

例: `A.java` に `int a() { return 1; } Object b() { return new Object(); }` を 1 行で書く。`b` だけが `R` 行を持つ
（`int` を返す `a` は記録しない）。全件解析では `b` が先に ID 化され、`methods.csv` は `b`、`a` の順になる。
`a()` を呼ぶ `B.java` だけを直して差分更新すると、`B.java` のブロックが先頭に来て `a` が先に ID 化され、
`a`、`b` の順になる。同じソースなのに、前回の実行で何を直したかで行の並びが変わっていた。

ラムダも同じで、`void pair() { use(() -> ready(), () -> make()); }` では `Object` を返す 2 つ目のラムダだけが
`R` 行を持つ。全件解析でも起点が「2 つ目のラムダ → `pair` → 1 つ目のラムダ」とソースと違う順に並び、
`pair` を呼ぶ別のファイルを直すと「`pair` → 2 つ目 → 1 つ目」に変わる（`entry.packages` がその型を
選んでいるとき）。サーバーの `AT` は 1 行目で `b()`、2 行目で 2 つ目のラムダを返していた。

### Q15. 新しい鍵は何か。重複した宣言ではどうなるか

**宣言行 → ファイルの中の宣言の順番 → キーの文字列**。宣言の順番は、そのメソッドの `D` 行がブロックの中で
何番目か（0 始まり）で、`CallGraphBuilder` が `D` 行を読むたびに数える。

- `D` 行は書き手が AST を訪ねた順に並べる（`FactVisitor` / `TypeContextTracker`）。同じソースからは必ず同じ並びに
  なるので、いつ・どの実行で解析したブロックでも同じ値になる。ID と違って、ほかのブロックの影響を受けない
- 読めない `D` 行（記号がブロックの外を指す等）も数える。順番は書き手が並べた位置そのもので、
  どの行が読めたかに左右させない
- 同じキーの宣言が複数のファイルにあると、宣言ファイル・宣言行は後から読んだものが勝つ
  （`MethodTable.setDeclaration`）。宣言の順番も同じ呼び出しで記録するので、ファイル・行・順番は
  必ず同じ宣言のものになる
- キーの文字列は最後の決め手。ファイルの中では順番が重ならないので、効くのは別々のファイルの宣言を比べるとき
  （起点の並びは型で比べるので、同じ FQN の型が 2 つのファイルにあるとき）だけ。どちらにしても ID には依らない

`methods.csv` は「ソースフォルダ → ファイル → この鍵」、起点は「ソースフォルダ → 型 → この鍵」で、
鍵を差し替えたのは最後の段だけ。同着でない行の並びは変わらない。

### Q16. なぜソース上の桁ではなく宣言の順番を使うのか

- **桁はキャッシュに無い。** `D` 行が持つのは宣言行と終了行だけで、桁を足すには形式を変えて版を上げ
  （全員のキャッシュが捨てられる）、書き手も変えることになる。宣言の順番は今ある行の並びから決まるので、
  形式も書き手も変えずに済む
- **合成した宣言には自分の桁が無い。** 暗黙のコンストラクタ・`<clinit>`・record の正準コンストラクタは
  型の宣言行を借りているだけで、桁を決めるなら作り話の値になる。宣言の順番はどの宣言にも決まる
- **入れ子の前後が自然に決まる。** メソッドの `D` 行は本体を訪ねる前に書くので、同じ行のラムダ・匿名クラスの
  メソッドより必ず前になる（外側が先）。桁で比べても同じ結果にはなるが、上の 2 つの理由で割に合わない

却下した案:

- **キーの文字列だけで決める。** ID には依らないが、同着の並びがソースの並びでなく名前順になる。
  利用者が読むのはソースなので、`a`・`b` のような 1 行の並びも書いた順で見せたい
- **読み手の ID 化の順を直す（`D` 行を `R` 行より先に ID 化する）。** 1 つ目の原因は消えるが、
  別のファイルのブロックで先に ID 化される 2 つ目の原因は残る。ID を決め手にする限り、ブロックの並び
  （＝実行の履歴）から逃げられない

### Q17. `AT` で範囲の広さが同じとき、どちらを返すか

宣言の位置が先のもの（同じ行なら先に宣言したもの。入れ子なら外側）を返す。
`R` 行も別のファイルからの参照も無ければ、ID の順は `D` 行の順と同じだったので、よくある形
（1 行のメソッドの中のラムダ等）で返すものは以前と変わらない。変わるのは `R` 行や参照で ID がずれていた場合だけ。

内側（後に宣言したもの）を返す案も考えた。`method-decl-range-qa.md` の Q4 は「範囲が最も狭いもの＝一番内側」を
選ぶ理由を「カーソルのある位置で利用者が思うのは一番内側」としているので、それに寄せる形である。
採らなかったのは、行番号しか受け取らないので行のどこにカーソルがあるかは分からず、
`void run() { list.forEach(x -> foo(x)); }` の行で利用者が知りたいのはたいてい `run` のほうだから。
よくある形で返すものが変わるのも避けたかった。

### Q18. リフレクションの候補の並びは出力に効くのか

`Method.invoke` の引数型が分からず名前だけで照合したとき（`[UNEXPANDED:REFLECTION] N candidates: matched by name`）、
候補は `DataflowBuilder.methodsByName` の並びのまま行になる。`call-hierarchy.csv` の呼び出し先はオーバーロードを

Q1 の表は「同じ型の同名メソッドなので同じブロック内で決まる」としていたが、Q14 と同じ理由で成り立たないので、
宣言ファイル → Q15 の鍵の順に並べ替えた。並べ替えるのは同じ名前が 2 つ以上ある組だけ。
