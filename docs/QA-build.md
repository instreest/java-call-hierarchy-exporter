# 実装QA — ビルド・実行環境（Issue #26）

Quick startを1コマンドにし、Gradle・依存jar・JDKをすべてプロジェクトフォルダ内に
収めるようにしたときに、迷った点とその判断を残します。

判断の軸は **「利用者の環境を汚さない」** と **「手元のJDKが何であっても同じ結果になる」**
の2つです。前者はこのツールが業務端末に一時的に置かれて使われることを想定しているため、
後者は解析結果がJDTを動かすJDKに左右されるためです。

---

## Q1. なぜ Gradle Wrapper（gradlew）を追加したのか

**依存jarとJDKの置き場所をプロジェクト内に向ける手段が、他に無いためです。**

Gradleがダウンロードしたものを置く場所は `GRADLE_USER_HOME`（既定は `~/.gradle`）で決まり、
これは **`gradle.properties` では指定できません**。Gradleが `gradle.properties` を読むには
先に `GRADLE_USER_HOME` が決まっている必要があり、鶏と卵になるためです。

環境変数を利用者に設定させる方法もありますが、それでは「1コマンド」になりません。
`gradlew` / `gradlew.bat` の中で設定すれば、利用者は何も意識せずに済みます。

```sh
if [ -z "${GRADLE_USER_HOME:-}" ]; then
    GRADLE_USER_HOME="$APP_HOME/.gradle-home"
    export GRADLE_USER_HOME
fi
```

利用者が明示的に `GRADLE_USER_HOME` を設定している場合はそちらを尊重します。
社内で共通のキャッシュを指定している環境を壊さないためです。

Wrapperには副次的な利点もあります。Gradle本体が入っていない端末でも動きます。

## Q2. Gradle本体の置き場所で一度失敗した

最初は `gradle-wrapper.properties` に `distributionBase=PROJECT` を指定しました。
これだと配布物は `distributionPath` の相対起点がプロジェクトルートになり、
**`<プロジェクト>/wrapper/dists`** に展開されます（`gradle/wrapper/dists` ではありません）。

`.gitignore` には `gradle/wrapper/dists/` と書いてあったため一致せず、
146MBのGradle本体が未追跡ファイルとして `git status` に並ぶ状態になっていました。

`distributionBase=GRADLE_USER_HOME`（既定）に戻しました。Q1で `GRADLE_USER_HOME` を
プロジェクト内に向けてあるので、これで配布物も `.gradle-home/wrapper/dists` に入ります。
結果として **Gradle本体・依存jar・取得したJDKがすべて `.gradle-home/` の下に集まり**、
「やめるときはこのフォルダを消す」で完結するようになりました。
役目を終えた `.gitignore` の `gradle/wrapper/dists/` は削除しています。

## Q3. ツールチェーンのバージョンを固定するか、「17以上なら何でもよい」にするか

**17に固定しました。** Gradleのツールチェーンはメジャーバージョンの完全一致で選ぶため、
そもそも「17以上」という指定はできません。選択肢は次の2つでした。

| 方針 | 手元がJDK 21のとき | 手元がJDK 11のとき |
|---|---|---|
| ツールチェーン17に固定 | JDK 17を取得（数十MB） | JDK 17を取得。**動く** |
| ツールチェーンを使わない | そのまま動く | **動かない**（JDT 3.46がJDK 17を要求） |

固定すると、既に新しいJDKを持っている利用者に不要なダウンロードが発生します。
それでも固定を選んだのは、**解析結果がJDTを動かすJDKに左右される**ためです。
「同じソース・同じ設定なのに端末によって結果が違う」という状態は、
このツールの用途（改修時の影響調査）では原因の切り分けを著しく難しくします。
再現性を取りました。

なお、この取得は初回だけで、2回目以降は `.gradle-home/jdks` のものが使われます。

## Q4. gradlew.bat の `%APP_HOME%` には区切り文字が付かない

Windows側のスクリプトで一度間違えました。

```bat
set APP_HOME=%DIRNAME%
for %%i in ("%APP_HOME%") do set APP_HOME=%%~fi
```

`%~fi` は末尾のバックスラッシュを落とすため、`%APP_HOME%` は `C:\path` の形になります
（Gradle純正の行が `"%APP_HOME%\gradle\wrapper\gradle-wrapper.jar"` と `\` を補っているのが根拠）。
`%APP_HOME%.gradle-home` と書くと `C:\path.gradle-home` という別物になります。
`%APP_HOME%\.gradle-home` が正解です。

**Linuxでは再現しない不具合**なので、Windows側の記述はGradle純正のコードの
書き方を根拠に合わせるのが確実です。

## Q5. 「1コマンド」の下限 — Gradle自身を起動するJavaは消せない

ツール本体が使うJDKは自動取得できますが、**その取得を行うGradle自身がJavaで動いている**ため、
Javaがまったく入っていない端末では `gradlew` を起動できません。これは原理的な下限です。

Issueの「gradleの実行に必要なJREバージョンがある場合は、必要なJava実行環境の表を
Quick startではなく後続の説明にて記載する」という指示は、まさにこの点だと解釈しました。
Quick startには表を置かず、「Javaが入っていない環境」という後続の節に移しています。

想定利用者はPleiades/Eclipseが入っている端末なので、同梱のJavaで起動できます。
Gradle 8.14 は Java 8〜24 のいずれでも起動できるため、実質的に問題になりません。

## Q6. 自動取得を無効化する手段を残すか

**残しました。** `gradle.properties` の `org.gradle.java.installations.auto-download`
（既定 `true`）を `false` にすると取得を試みなくなります。

社内プロキシで外部への到達が制限されている環境では、取得が失敗して
「JDKが見つからない」で止まります。そのとき利用者が取れる行動
（JDKを自分で入れる／取得を止める）をREADMEに書いておく必要があると考えました。
既定値のままの設定を明示的に書いているのは、この前提を目に見える形で残すためです。

## Q7. この環境で検証できなかったこと

**JDKの自動取得そのものは、この開発環境では実行できませんでした。**
ツールチェーンの取得元 `api.foojay.io` が、開発コンテナのネットワークポリシーで
拒否されているためです（CONNECT に 403）。

確認できたのは次のとおりです。

| 項目 | 結果 |
|---|---|
| `gradlew` が動き、Gradle本体を取得して実行できる | 確認済み |
| foojayリゾルバが解決され、取得を試みるところまで到達する | 確認済み（403で失敗するエラーが出る＝配線は正しい） |
| 取得できない場合のエラーが原因を示すか | 確認済み（`Cannot find a Java installation ... matching {languageVersion=17}` と、リゾルバの失敗理由が併記される） |
| 手元にJDK 17がある場合に取得せず使うか | 確認済み（JDK 17を導入して再実行、`build/classes` のクラスファイルが major=61） |
| 依存jar・Gradle本体がプロジェクト内に入るか | 確認済み（`.gradle-home/` 168MB、`~/.gradle` は42MBのまま不変） |
| **取得が成功する経路** | **未確認**（この環境では到達不可） |

取得経路そのものはGradleの標準機能であり、こちらで書いたのは
`settings.gradle` のプラグイン宣言だけです。とはいえ未確認は未確認なので、
外部に出られる端末での初回実行を確認していただくのが確実です。

## 要件・前提についての提案

### 提案1: `lib/` を使う手順（Pleiades/Eclipse）は残す価値がある

Issueの狙いはGradle経路の簡潔化なので今回は触れていませんが、
Gradle経路が使えない状況（外部への到達が一切無い端末）は現実にあります。
`javac` + `java` の手順はその場合の唯一の道なので、Quick startの下に残しました。

### 提案2: 同梱設定のままの1コマンド実行は、型解決に198件失敗する

今回の変更とは別の、既存の挙動です（変更前の `main` でも同じ結果でした）。

同梱の `config/config.properties` はこのリポジトリ自身を解析する設定になっていて、
`library.folders=./lib` を指しています。ところが `lib/` を用意するのは `copyLibs` タスクで、
`run` はこれを実行しません。そのため編集せずに `gradlew run` すると
`lib/` が空のままJDTのjarが解析クラスパスに乗らず、型解決に198件失敗します。

READMEのQuick startは「まず設定ファイルを編集する」→「実行する」の順なので、
利用者が自分のプロジェクトを指すよう編集していれば問題は起きません。
とはいえ「ゴールデンケースを1コマンドで」という観点では、
同梱設定のまま試した人が警告を見ることになります。対処の候補は次のとおりです。

| 案 | 内容 | 懸念 |
|---|---|---|
| A | `run` を `copyLibs` に依存させる | `lib/` は本来「解析対象の依存jar」であって「このツールの依存jar」ではない。自己解析のときだけ両者がたまたま一致する |
| B | READMEに「このリポジトリ自身を試すときは先に `gradlew copyLibs`」と書く | 1コマンドでなくなる |
| C | 同梱設定の `library.folders` を空にする | 自己解析の失敗件数は変わらない |

意味の正しさを取るならB、体験を取るならAです。
どちらもIssue #26 の範囲（Gradle・JDKの簡潔化）から外れるため、
今回は判断を委ねて変更していません。

### 提案3: ツールチェーンのバージョンとJDT版は連動させたい

現状、JDT版を下げるとき（`-PjdtVersion=3.33.0`）は `build.gradle` の
`toolchain` も手で下げる必要があり、片方だけ変えると分かりにくく失敗します。
`jdtVersion` から必要なJDKを導出して `toolchain` に渡すこともできますが、
対応表をビルドスクリプトに埋め込むことになり、JDT側の変更に追従できなくなります。
利用頻度が低い操作なので、現状は手順として書くに留めています。
頻繁に切り替える運用が出てきたら、そのときに自動化を検討するのが良いと考えます。
