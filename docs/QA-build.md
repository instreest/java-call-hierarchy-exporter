# 実装QA — ビルド・実行環境（Issue #26 → #31）

ビルド・実行環境まわりで迷った点とその判断を残します。
Issue #26 で Gradle Wrapper による1コマンド化を行い、**Issue #31 で依存性解決を
JBang に置き換えました**。Gradle 時代の記録はこの改訂で置き換えていますが、
そこで踏んだ罠のうち今も効いているものは、対応する質問の中に引き継いでいます。

判断の軸は Gradle 時代から変わらず、**「利用者の環境を汚さない」** と
**「手元のJDKが何であっても同じ結果になる」** の2つです。前者はこのツールが
業務端末に一時的に置かれて使われることを想定しているため、後者は解析結果が
JDTを動かすJDKに左右されるためです。

---

## Q1. なぜ Gradle から JBang に替えたのか

理由は3つです（Issue #31）。

1. **JVMの版指定と自動取得が1行で済む。** Gradleでは toolchain の宣言
   （build.gradle）、リゾルバプラグイン（settings.gradle）、自動取得の既定
   （gradle.properties）、実行側への適用（`javaLauncher`）と4箇所に散っていた。
   JBangではソース冒頭の `//JAVA 25` だけで、コンパイルと実行の両方が固定される。
   Gradle時代に「コンパイルだけtoolchainで実行は別JVM」という罠を実際に踏んだ
   （旧Q3b）ことを考えると、**分けようがない**構造そのものが利点。
2. **設定ファイルが減る。** build.gradle / settings.gradle / gradle.properties /
   gradle/wrapper/* が消え、増えたのはソース冒頭の3行と jbangw / jbang-catalog.json。
   依存の宣言（`//DEPS`）がソースと同じファイルにあるので、乖離しようがない。
3. **javac / java 直接実行と干渉しない。** `//DEPS` も `//JAVA` も javac には
   ただのコメント。ロックダウンされた端末向けの javac 経路（README）は
   一切変更なしで生き続ける。単一ファイル・デフォルトパッケージという
   このツールの前提（DESIGN.md §3）と、JBangの「1ファイル＝1スクリプト」は
   相性がよい。

## Q2. jbang本体をどう配るか — jarはコミットせず、SHA-256固定で取得する

`jbang wrapper install` が作る公式ラッパーは `.jbang/jbang.jar`（約9.5MB）を
リポジトリにコミットする方式です。gradle-wrapper.jar（43KB）と同じ発想ですが、
**9.5MBは版を上げるたびに履歴へ積まれる**ため、コミットはやめました。

代わりに `jbangw` が初回実行時に **Maven Central から取得し、スクリプトに
埋め込んだ SHA-256 と照合してから使います**。一致しなければ削除して失敗します。
取得先がMaven Centralなのは、どのみち依存jar（JDT）の解決で到達できる必要がある
ホストだからで、jbang本体のためだけに新しい到達先が増えるわけではありません。
社内ミラーを使う場合は環境変数 `JBANGW_JAR_URL` でURLごと差し替えられます。

なお公式のラッパースクリプトを同梱できなかった事情もあります。`wrapper install` は
「インストール済みのjbangの起動スクリプト」をコピーする作りで、この開発環境では
jbang配布zip（www.jbang.dev / GitHub releases）への到達が遮断されており入手
できませんでした。`jbangw` / `jbangw.cmd` は実行規約（Q3）に合わせて書き起こした
ものです。

## Q3. jbang.jar は「コマンドラインを出力して255で終わる」

ラッパーを自作して分かった、jbangの実行規約です。`java -jar jbang.jar run script.java`
は **スクリプトを実行しません**。実行すべき java コマンドライン（クラスパス展開済み）を
標準出力に書き、**終了コード255**で終わります。それを受けてシェル側が `eval exec` する
のが公式スクリプトの動きで、`jbangw` も同じことをしています。

- sh側: `set -e` のままだと255で即終了してしまうため、この呼び出しだけ `set +e` で囲む
  （実際に踏みました）
- cmd側: コマンドラインはクラスパスを含み4KBを超える（実測）ため、環境変数
  （上限8191文字）で受けず、一時cmdファイルに書いて `call` する

255以外で終わった場合（`version` 等のサブコマンドや失敗）は、出力をそのまま表示して
その終了コードで終わります。

## Q4. 取得物の置き場所 — JBANG_DIR と JBANG_REPO の両方を固定する

「利用者の環境を汚さない」ために、`jbangw` は未設定の場合に限り

| 環境変数 | 既定 | 入るもの |
|---|---|---|
| `JBANG_DIR` | `<プロジェクト>/.jbang` | jbang本体・ビルド済みjar・取得したJDK（`cache/jdks/`）|
| `JBANG_REPO` | `$JBANG_DIR/repository` | 依存jar（Maven形式のローカルリポジトリ）|

を設定します。**`JBANG_REPO` を忘れると依存jarだけ `~/.m2` 相当に落ちて、
「プロジェクト内で完結」が崩れます**（実測で確認）。jbang本体のjarも
`$JBANG_DIR` の下に置くので、外から共有キャッシュを指された場合に
プロジェクト内へ二重に置くことはありません（これも当初はプロジェクト直下
固定にしていて、外部 `JBANG_DIR` 指定時に `.jbang/` が余計に作られる形で発覚）。

ファイル名は `jbang-cli-<版>-all.jar` と版を含めます。`jbangw` の
`JBANG_VERSION` を上げたときに、古いjarを黙って使い続けないためです。

## Q5. Javaが1つも入っていない環境 — 本家に合わせてJDKを取得する

**当初はここでエラー終了させていましたが、本家の実装を調べて改めました。**

本家の `jbang` / `jbang.cmd` は、JDKが1つも無い場合に
**自分でJDKをダウンロードして展開してから**起動します。jbang.jar を動かすにも
JDKが要る以上、そこは jbang より前に誰かがやるしかなく、ラッパーの仕事です。
エラー終了させる実装は「JVMも自動取得する」というIssueの要件からも外れていました。

`jbangw` / `jbangw.cmd` は本家と同じ探索順・同じ取得元にしました。

| 順 | 探す場所 | 備考 |
|---|---|---|
| 1 | `JAVA_HOME/bin/javac` | javac が無ければ「JDKではない」と警告して次へ |
| 2 | `PATH` の `javac` | |
| 3 | `$JBANG_DIR/currentjdk/bin/javac` | jbang が既定に設定したJDK |
| 4 | `$JBANG_DIR/cache/jdks/<版>` | 前回 jbangw が取得したもの |
| 5 | foojay の Disco API から取得 | 失敗時は回避方法を出して終了 |

### `java` ではなく `javac` を見る

これは本家に倣った修正点です。jbangは実行前にソースをコンパイルするので
JREでは足りません。当初の実装は `java` の有無だけを見ていたため、JREしか
無い端末では**この時点では通り、後段のコンパイルで分かりにくく落ちる**
形になっていました。JAVA_HOMEがJREを指す場合にPATH側へフォールバックすることは
実測で確認しています。

### 取得する版は 17 ではなく 25（本家との意図的な差）

本家の既定は `JBANG_DEFAULT_JAVA_VERSION=17` です。そのままだと、
Javaが無い端末では **起動用の17と、`//JAVA 25` を満たす実行用の25で
JDKが2つ**入ります（合計300MB超）。

`jbangw` は既定を **25** にしました。取得先を jbang 自身が見る
`$JBANG_DIR/cache/jdks/25` に揃えてあるので、**取得した1つが起動にも実行にも
使われます**。「そこに置けば jbang が `//JAVA 25` の解決に使う」ことは、
システムのJavaを完全に隠した環境で実測して確認しました
（`jdk list` に出ること、実行JVMがそのパスになること、追加のダウンロードが
発生しないこと）。環境変数 `JBANG_DEFAULT_JAVA_VERSION` で変更できます。

なお「1コマンドの下限」という論点自体は解消しました。Gradle時代（旧Q5）は
「Gradleを起動するJavaだけは利用者が用意する必要がある」でしたが、
今回はそれも自動取得の対象です。

## Q6. Windowsの文字化け対策 — chcp をやめ、端末の文字コードに合わせる

**報告を受けて方針ごと変えた項目です。** 当初は Issue #31 の要件
「Windows上で実行した場合にターミナルのエンコーディングをUTF-8とする」を
文字どおり実装し、`jbangw.cmd` で `chcp 65001` を実行していました。
これが**コンソールの表示内容を消してしまう**という報告を受けています。

### 何が起きたか

日本語・中国語・韓国語版のWindowsでは、コンソールのコードページを
DBCS（932等）と非DBCS（65001）の間で切り替えると、conhost が画面バッファを
作り直すため**画面が消えます**。`jbangw.cmd` は終了時に元のコードページへ
戻していたので、**ツールが出力し終えたログをその復元処理が消していました。**
PowerShell でも cmd.exe でも同じことが起きます（どちらも同じコンソールAPIを使うため）。

復元処理を入れたのは「利用者の端末設定を変えたまま返さない」ためでしたが、
その結果**ログが1行も読めない**という、より重い不具合になりました。

### なぜ chcp をやめる判断にしたか

復元をやめれば消去は1回（起動時）で済みますが、それでも利用者の
スクロールバックを消し、端末を65001のまま返すことになります。
そもそも**コードページを触ること自体が目的ではありません。**
要件の意図は「Windowsで日本語ログが読めること」であり、chcp はその手段の
1つにすぎません。そして日本語Windowsでは、この手段は副作用の方が大きい。

そこで、**端末を変えるのではなく、端末の文字コードに合わせて出力する**方式に
切り替えました。具体的には次の2つを両方やめます。

- `jbangw.cmd` の `chcp 65001`（と復元）
- ソースの `//JAVA_OPTIONS -Dstdout.encoding=UTF-8 -Dstderr.encoding=UTF-8`

JDK 19以降、`System.out` は**コンソール自身の文字コード**で書き出します。
MS932のコンソールならMS932で、UTF-8のコンソールならUTF-8で出るので、
どちらの設定の端末でも正しく読めます。画面は消えず、端末の設定も変わりません。

これは DESIGN.md 11章に元から記録されていた原則
**「標準出力の文字コードを固定しない。端末に任せる」** そのものです。
Issue の要件に引きずられて、いったんこの原則から離れていました。

### 2つはセットで外す必要がある

`chcp` だけをやめて `-Dstdout.encoding=UTF-8` を残すと、MS932のままの
コンソールにUTF-8のバイト列を書くことになり、**まさに11章の罠どおりに
ログだけ文字化けします**。片方だけ外してはいけません。

CSV等のファイル入出力はコード側で常に明示的な文字コードを使っているため、
いずれの変更の影響も受けません（`output.encoding` / `source.encoding` はそのまま）。
UTF-8のコンソールで使いたい利用者が自分で `chcp 65001` しておけば、
ツールはそれに追従してUTF-8で出力します。

### PowerShell での `.\jbangw` の解決

このリポジトリには拡張子なしの `jbangw`（Linux/macOS用のシェルスクリプト）と
`jbangw.cmd` が並んでいます。cmd.exe は PATHEXT に従って `.cmd` を選びますが、
PowerShell で `.\jbangw` と書いた場合に拡張子なしの方を拾う可能性があります。
その場合は `.\jbangw.cmd` と明示すれば確実です（READMEにも注記）。
**この挙動はLinux環境のため未確認**で、本家 jbang が `jbang.ps1` を同梱して
いるのは、この種の問題を避けるためと思われます。PowerShell用のラッパーを
足すかどうかは、実機での挙動を見てから判断するのが妥当です。

## Q8. `jbangw CallHierarchyExporter.java` — src/ プレフィックスを消す方法

Issueの To be は `jbangw CallHierarchyExporter.java` で、実ファイルは
`src/CallHierarchyExporter.java` にあります。ソースを直下へ動かすことも
考えましたが、`source.folders=./src` を前提にした設定・ドキュメント・
自己解析の構図が全部動くため、**jbangのカタログ（`jbang-catalog.json`）で
別名を張る**方にしました。

```json
{ "aliases": { "CallHierarchyExporter.java": { "script-ref": "src/CallHierarchyExporter.java" } } }
```

`.java` で終わる別名が有効かは仕様上不明だったので実測で確認しました
（jbangは実在ファイルを先に探し、無ければカタログを引く。どちらの経路でも
同じ結果になることを確認済み）。`jbangw src/CallHierarchyExporter.java` の
直接指定も従来どおり使えます。

設定ファイルのパスは**普通の第1引数**です。当初は gradlew 時代の見た目に
寄せて `--args="…"` の形を採り、`main()` 側で先頭の `--args=` を剥がして
いましたが、Issue #31 の To be が素のパス渡しに変わったため、この糖衣は
外しました。`--args=` を剥がす処理を残すと、`--args=foo` という値を
設定ファイルのパスとして黙って受け付けることになり、CLIとして素直ではありません。

jbang はスクリプト名より後ろの引数をそのまま渡すので、`jbangw` 経由でも
`java -cp ...` の直接実行でも、引数の形はまったく同じです。

## Q9. `copyLibs` の代替 — lib/ は find で集める

Gradleの `copyLibs` タスクは廃止しました（Issue #31 の「build.gradleのタスクは
移行不要」）。`lib/` フォルダが要るのは javac 経路と自己解析（`library.folders=./lib`）
だけで、`jbangw` で一度実行した後なら

```bash
find .jbang/repository -name "*.jar" -exec cp {} lib/ \;
```

で同じものが集まります（`.jbang/repository` はMaven形式で入れ子のため、
`library.folders` に直接指定しても直下しか見ない仕様上、拾われません）。

**同梱設定のまま Quick start を実行すると、初回は型解決失敗が220件出ます**
（`lib/` が無いため）。これはGradle時代の旧提案2と同じ既知事象で、上の1コマンドで
`lib/` を作って再実行すると0件になります。恒久的な解決案として「自分の実行時
クラスパス（java.class.path）を解析クラスパスに自動で足す」ことも考えられますが、
実行経路（jbangw / javac）によって解析クラスパスが変わる＝**「どの経路で実行しても
同じ結果」という保証が壊れる**ため、設定キーとして切るかどうかの判断が必要です。
提案に留めます。

## Q10. jbangの版は jbangw に固定し、無断で上がらないようにした

`jbangw` は `JBANG_VERSION=0.132.1` と、そのjarの SHA-256 を持ちます。
「latestを取る」方式にしなかったのは、jbang本体の挙動が変わると
実行コマンドの組み立て（Q3の規約を含む）ごと変わりうるためです。
版を上げるときは jbangw / jbangw.cmd の2箇所（版とハッシュ）を同時に
書き換えます。JDTの版（`//DEPS`）とは独立です。

## Q11. jbangw.cmd に日本語を書いてはいけない（PowerShellで実行時エラー）

**報告を受けて直した不具合です。** PowerShellのターミナルから `jbangw.cmd` を
実行すると、`rem` のコメント行の一部がコメントとして扱われず、
「コマンドが見つからない」というエラーになりました。

### 原因

cmd.exe はバッチファイルを一括で読み込まず、**1行実行するたびにファイルを開き直し、
保存しておいた位置から次の行を読みます。** このとき、位置はバイト単位で持っている
一方、進める量をコードページ65001（UTF-8）では**デコード後の文字数**で計算して
しまいます。マルチバイト文字が1つあるごとに再開位置が手前へずれ、ずれが1行分を
超えると**行の途中から再開**します。その結果、`rem` の後ろに書かれていた日本語の
断片がコマンドとして実行され、「そんなコマンドは無い」となります。

修正前の `jbangw.cmd` は147行中38行が非ASCIIで、
ファイル全体でバイト数と文字数が **1682バイトぶんずれて**いました。
これがそのままズレの燃料になります。

### なぜ PowerShell でだけ出たのか

この経路に入るのはコンソールのコードページが65001のときだけです。

| 実行元 | バッチ開始時のコードページ | 結果 |
|---|---|---|
| 日本語版の cmd.exe | 932 | 前半はcp932として読まれる（文字化けはするがズレは出にくい）|
| PowerShell | 65001 になっていることがある | **1行目からズレが蓄積して破綻** |

当時はスクリプト自身も `chcp 65001` を実行していたため、cmd.exe から起動した
場合でもそれ以降は同じ条件になっていました。その `chcp` は Q6 のとおり
削除しましたが、**利用者が自分で65001にしている端末は依然あり得る**ので、
純ASCIIの制約は引き続き必要です。

### 対処: `jbangw.cmd` は純ASCIIにする

コメントもメッセージも英語にし、非ASCII文字を1つも置かないようにしました
（バイト数＝文字数になり、ズレが原理的に発生しません）。
参照実装を確認したところ、本家の `jbang.cmd` / `jbang.ps1` も、以前使っていた
`gradlew.bat` も**すべて純ASCII**でした。バッチファイルの定石です。

あわせて次も直しています。

- 括弧ブロックの中に置いていた `rem` を撤去した（バッチでは壊れやすい書き方）
- `echo` に素で埋めていた変数を引用符で囲んだ。URLやフォルダ名に `&` が
  含まれるとコマンドの区切りとして解釈されるため

このファイルの日本語の解説は、ファイル先頭から本ドキュメントへの参照に置き換えました。
Windows側のメッセージだけ英語になりますが、日本語を戻したい場合は本家と同じく
`jbangw.ps1`（PowerShellはUTF-8を正しく扱える）へ処理を委譲する構成にする手が
あります。スクリプトが1本増えるので、今回は採りませんでした。

**この制約は再発しやすいので、CLAUDE.md の Conventions にも明記しています。**
