# メソッドの宣言範囲（終了行）を持つか（#115）

`MethodTable` とキャッシュがメソッドについて持っている位置は、長らく**宣言の開始行だけ**だった。
「エディタのカーソル位置（ファイルと行）から、囲んでいるメソッドを引く」という使い方を入れるにあたって、
終了行も持つかどうかを検討した記録。

**結論: 持つことにした**（キャッシュ `jche-cache-v19` → `v20`、D 行の末尾に `endLine` を 1 列）。
あわせてサーバーモードに `AT ファイル 行` を足し、`FIND` の応答にも `endLine=` を返すようにした。

## Q1. 開始行だけで済ませる案（近似）はなぜ採らなかったか

開始行しか無い場合、囲むメソッドは

> 同じファイルの、行番号が指定行以下で最大のもの

という近似でしか引けない。これはメソッドの**中**にいる限り当たるが、外にいるときに黙って直前のメソッドを返す。

```java
public void save(Order o) {   // ← 38行目
    ...
}                              // ← 45行目
                               // ← 46行目（空行）でも save() が返る
private int count;             // ← 47行目（フィールド）でも save() が返る
```

返ってくるのが「別のメソッドの呼び出し元一覧」なので、利用者から見ると**正しく見えるが間違っている答え**になる。
このツールの方針は「呼び出しを静かに落とさない／黙って取り違えない」なので、
表示で気づかせる（返した位置を画面に出す）よりも、事実として範囲を持って `not-found` と言える方を採った。

## Q2. コストはどれくらいか

- 解析側: `MethodDeclaration` の `getStartPosition() + getLength() - 1` を行番号に直すだけ（`FactVisitor.endLineOf`）。
  AST は既に持っているので追加の走査は無い
- キャッシュ: D 行に 10 進の整数が 1 列増えるだけ。`test/demo` で D 行 1 行あたり数バイト
- 読み手: `MethodTable` に `IntArray` が 1 本増える（メソッド 1 件あたり 4 バイト）

近似の取り違えを消すのに払う値段としては小さいと判断した。

## Q3. 本体が書かれていないメソッドはどうするか

暗黙のデフォルトコンストラクタ・`<clinit>`・インターフェースの抽象メソッドなど、
「そこに範囲が無い」ものがある。これらは `endLine = declLine`（その行だけの範囲）にしている。
`MethodDeclFact` のコンパクトコンストラクタで `endLine < declLine` を開始行に丸めているので、
壊れた値や古い列が入っても範囲が逆転することはない。

合成された暗黙のコンストラクタの開始行は型の宣言行なので、`AT` で型宣言の行を指すとそれが返る。
「クラス宣言の行 = そのクラスの暗黙コンストラクタ」は嘘ではないので、そのままにした。

## Q4. 入れ子（内部クラス・匿名クラス）はどう選ぶか

範囲は入れ子になりうる（内部クラスのメソッドは外側のメソッドの中にあることもある）。
`MethodTable.enclosingMethod` は、範囲に入るものの中で**最も狭いもの**を選ぶ。
カーソルがある位置で利用者が「このメソッド」と思うのは一番内側なので、それに合わせている。

## Q5. 古いキャッシュはどう捨てるか

形式バージョンを `jche-cache-v20` に上げた（`docs/cache-dependency-jars-qa.md` の方針どおり）。
1 行目のヘッダが一致しないので、v19 以前のキャッシュは丸ごと捨てられて全件解析になる。
`MethodDeclFact.fromRow` は列が無いときに `declLine` へ倒すので、
何かの経路で古い D 行を読んでしまっても範囲が壊れることはない（安全側）。

## Q6. `methods.csv` に終了行の列を足すか

**足していない。** `methods.csv` は「改修時の影響調査で読む表」で、宣言の位置は
その行へ飛ぶための手がかりとして持っている。終了行はそこには効かない一方、
列を足すと既存の期待値（`test/regression/expected*/`）と利用者の後処理が全部動く。
必要になった時点で足せる（キャッシュには既にあるので、解析のやり直しは要らない）。

## Q7. サーバーモードには何を足したか

```
→ AT  src/main/java/com/example/OrderService.java  43
← OK  how=enclosing  key=...  label=...  file=...  line=38  endLine=45  callers=12
```

- ファイルはプロジェクトルートからの相対パス（D 行の綴りと同じ）。行は 1 始まり
- 見つかったときの応答は `FIND` と同じ形にそろえてある（`Server.respondFound`）。
  呼び出し側は `AT` で引いてから、そのまま `TREE` に渡せる
- どのメソッドの範囲にも入らない行は `NG not-found`。近似で直前のメソッドを返すことはしない
- 引数が足りなければ `NG missing-position`、行が数値でなければ `NG bad-line`

プロトコルの版（`Protocol.VERSION`）は上げていない。既存の行の意味は変えておらず、
要求を 1 つと応答の項目を 1 つ足しただけなので、古いクライアントはそのまま動く。
