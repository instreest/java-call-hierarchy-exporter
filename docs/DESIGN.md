# 設計書 — java-call-hierarchy-exporter

このツールを**ゼロから再実装するために必要な情報**をまとめたものです。
利用方法は [README.md](../README.md)、設定項目は
[config/config.properties](../config/config.properties) を参照してください。
この文書は「なぜそう作るか」「どこで必ず失敗するか」を残すことが目的で、
利用者向けドキュメントには書かない実装レベルの決定事項を扱います。

---

## 0. この文書の使い方（再実装の手順）

README と config だけでは再実装できません。外形（設定キー・CSVの列）は分かっても、
**JDTの正しい初期化方法・キャッシュ形式・名前の正規化規則**が分からないためです。
それらはこの文書の 3章以降にあります。

推奨する順序:

1. 2章でスコープと非目標を確認する
2. 4章のフェーズ構成どおりに骨組みを作る
3. 5章（JDT）を**先に**読む。ここを間違えると出力が全滅する
4. 6章（名前の正規化）を実装する。ここも間違えると出力が静かに壊れる
5. 7〜9章で解決・探索・出力を実装する
6. 11章の落とし穴を一通り確認する
7. 12章の受け入れ基準で検証する

データフロー解析（7.5）の実装で迷いやすい点は
[QA.md](QA.md) に判断の理由付きでまとめてあります。

## 1. 何を解決するツールか

レガシーJavaプロジェクトの改修時に「このメソッドを直すと、どこまで影響するか」を
機械的に洗い出す。EclipseのGUIの「呼び出し階層」ビューは、
コピーすると階層が失われる・再帰的に一括出力できない・
ワークスペース全体を一度に処理できない、という制約がある。
それをCSV出力で置き換える。

**Eclipse IDEを起動せず**、通常のJavaアプリとして動かす。
解析エンジンだけEclipse JDT Coreを使う。

## 2. スコープと非目標

### やること
- ソースコードの静的解析による呼び出し関係の抽出
- インターフェース型の呼び出しに対する実装クラスの推定（CHA）
- 外部jarからの被参照スキャン（classファイルの定数プール）

### やらないこと（意図的な非目標）
| 項目 | 理由 |
|---|---|
| バイトコード解析 | ソースの行番号が必要。Eclipseへのジャンプが主要機能のため |
| データフロー解析 | コストに見合わない。`new` 追跡はフロー非依存の近似で十分と割り切る |
| フレームワークのディスパッチ解決 | プロジェクト固有すぎる。拡張ポイント（7.3）で外出しする |
| 実行時情報の利用 | 静的解析のみ。エージェントやプロファイラは使わない |
| GUI | CSVを出してExcelとgrepに任せる |

### 設計上の優先順位
1. **漏れないこと** > 正確であること
   - 呼び出し階層から静かに消えるのが最悪。確信が持てないものは
     注記付きで出す（例: `CHA候補N件（未展開）`、`外部ライブラリ（import推定・未検証）`）
2. **落ちないこと** > 完全であること
   - 1ファイルの解析失敗で全体を止めない。警告を出してスキップする
3. **メモリが破綻しないこと**
   - 数万ファイル規模で `OutOfMemoryError` にしない（10章）

## 3. 全体構成

単一ファイル `src/CallHierarchyExporter.java`（デフォルトパッケージ）。
すべての機能を `static` な入れ子クラスとして持つ。

### なぜ単一ファイルか
配布と実行を最も簡単にするため。README のとおり
`javac -cp "lib\*" -d bin -encoding UTF-8 src\CallHierarchyExporter.java` の
1コマンドでビルドでき、ビルドツールもパッケージ構成も要らない。
**デフォルトパッケージ**なのも同じ理由（ディレクトリ階層を作らせない）。

分割してもよいが、その場合は README のビルド手順も併せて更新すること。

### 依存関係
- **Eclipse JDT Core のみ**（`org.eclipse.jdt.core`）。実行時は
  その推移的依存も含めて11〜17個程度のjarが必要（README の Quick start 参照）
- JUnit等のテストフレームワークは使わない
- ロギングフレームワークも使わない（`System.out` に直接書く）

## 4. 処理フェーズ

```
フェーズ1  ソース解析           .java  → キャッシュ(TSV)
フェーズ2  グラフ構築           キャッシュ → CSRグラフ（メモリ）
フェーズ3  出力                 CSRグラフ → methods.csv, call-hierarchy.csv
```

フェーズ間の受け渡しを**ファイル（キャッシュ）にしている**のが重要な設計判断。
これにより (a) 2回目以降は差分ファイルだけ解析すればよくなり、
(b) フェーズ1の解析結果をヒープに溜めずに済む。

**件数単位の進捗ログを出すのはフェーズ1だけ。** 支配的なのは1ファイルあたり
数十msかかるJDTの解析で、ここだけが「止まっているように見える」時間になる。
フェーズ2・3は1件あたりが桁違いに速く、件数はフェーズ1より1〜2桁多いので、
進捗を出すとログが流れて肝心の警告（型解決の失敗件数など）が埋もれる。

## 5. フェーズ1: JDTによるソース解析

### 5.1 ASTParser の初期化（ここを間違えると全滅する）

```java
ASTParser parser = ASTParser.newParser(AST.getJLSLatest());
parser.setKind(ASTParser.K_COMPILATION_UNIT);
parser.setCompilerOptions(options);          // ★ 5.2
parser.setResolveBindings(true);             // ★ 必須。型解決の本体
parser.setBindingsRecovery(true);            // 一部解決できなくても諦めない
parser.setEnvironment(classpath, sourcepath, encodings, true);  // ★ 5.3
parser.setUnitName(層からの相対パス);          // ★ 必須。無いとバインディングが解決されない
parser.setSource(source);
CompilationUnit cu = (CompilationUnit) parser.createAST(null);
```

**`setUnitName()` は必須。** 省略するとバインディング解決が静かに失敗する。
渡す値は「ソースフォルダからの相対パス」（`jp/co/xxx/Foo.java`）。

### 5.2 コンパイラ準拠レベル（最頻出の罠）

`JavaCore.getOptions()` の既定値は **JDTの古いデフォルト（source=1.3 / compliance=1.4）**。
そのままでは generics・diamond演算子(`<>`)・ラムダ式・enum・default method が
すべて構文エラーになり、**大半の呼び出しが型解決に失敗する**。

必ず準拠レベルを上げること。

```java
Map<String,String> options = JavaCore.getOptions();
JavaCore.setComplianceOptions(JavaCore.latestSupportedJavaVersion(), options);
```

解析対象のJavaバージョンは事前に分からないため、**読み込んでいるJDT自身が
対応する最新版**に合わせる。新しい言語機能の解釈を許可するだけなので、
対象が古いJavaでも副作用はない。

> 検証方法: `cu.getProblems()` を出力する使い捨てのコードを書き、
> `'<>' operator is not allowed for source level below 1.7` のような
> エラーが出ていないことを確認する。

### 5.3 クラスパスとソースパス

`setEnvironment(classpath, sourcepath, encodings, includeRunningVMBootclasspath=true)`。

- `includeRunningVMBootclasspath=true` にすると、JDK標準クラスは
  実行中のJVMから解決される（JDKのパス指定が不要になる）
- `classpath` には**依存jarを1つずつ**渡す。フォルダを渡しても展開されない。
  `library.folders` にフォルダが指定されたら、直下の `*.jar` を列挙して展開すること
- Eclipseの `.classpath` があれば `kind="src"` / `kind="lib"` を補助的に読む。
  **`kind="con"`（Gradle/Mavenのクラスパス・コンテナ）は解決できない**。
  Buildship/m2e連携のプロジェクトは依存jarの実体が `.classpath` に書かれていないため、
  `library.folders` の指定が必須になる

### 5.4 ASTVisitor で拾うもの

| 対象 | ノード | 備考 |
|---|---|---|
| 型階層 | `TypeDeclaration` / `AnonymousClassDeclaration` | 匿名クラスも登録する。しないとオーバーライド候補から漏れる |
| メソッド宣言 | `MethodDeclaration` | `hasBody` を記録（IFの抽象メソッドとdefaultメソッドの区別に必要） |
| 呼び出し | `MethodInvocation` / `SuperMethodInvocation` / `ClassInstanceCreation` / `ConstructorInvocation` | |
| new追跡の証拠 | `VariableDeclarationFragment` / `Assignment` | 変数の同定は名前でなく `IVariableBinding.getKey()` |

### 5.5 「今どのメソッドの中にいるか」の管理

呼び出し元を決めるためにスタックで管理する。ここに3つの罠がある。

**(a) 匿名クラス・ローカルクラス**
匿名クラス内の `MethodDeclaration` は、囲みメソッドの `MethodDeclaration` の
内側にネストして現れる。単一スロットで持つと内側を抜けた時点で囲みメソッドの
情報が失われ、**匿名クラスより後ろの呼び出しが全部「メソッド外」に落ちる**。
必ずスタックにすること。`visit` で push したら `endVisit` で必ず pop する
（JDTは `visit` が `false` を返した場合も `endVisit` を呼ぶ）。

**(b) フィールド初期化子・初期化ブロック**
これらは `MethodDeclaration` ではないため、素朴に実装すると
「メソッド外の呼び出し」になって捨てられる。実際にはコンパイラが合成メソッドに畳み込む。

| ソース上の位置 | 実際の帰属先 |
|---|---|
| `static` フィールド初期化子 / `static {}` | クラスに1つだけの `<clinit>` |
| インスタンスフィールド初期化子 / `{}` | **`this(...)`委譲していない全コンストラクタ**の先頭 |

インスタンス側は1対多になる。「漏れないこと」を優先し、
**該当する全コンストラクタに対して1本ずつエッジを張る**。
実際にコンパイル後それぞれから1回ずつ呼ばれるので、これは近似ではなく正確。
`this(...)`委譲するコンストラクタには複製されない（二重初期化を防ぐ言語規則）。

したがって「現在の呼び出し元」は**単数ではなくリスト**で持つ必要がある。

**(c) 暗黙のデフォルトコンストラクタ**
明示コンストラクタが1つも無いクラスには、暗黙の `<init>()` が存在する。
ソース上に宣言が無いので、型を訪問した時点で**宣言を合成しておく**こと。
これを怠ると `new B()` の呼び出し先が「宣言の無いメソッド」になり、
ソースがあるのに `ソースなし（展開不可）` と誤表示される。

**(d) ラムダ式**
`MethodDeclaration` ではないので、中の呼び出しは自動的に囲みメソッドに帰属する。
これはソース上の見え方と一致するので、特別扱いは不要。

### 5.6 型解決に失敗した呼び出し

バインディングが解決できない呼び出しは2段構えで扱う。

1. レシーバが単純名で、そのファイルの**単一型インポート**（`import a.b.C;`）と
   一致すれば、そのFQNを呼び出し先の型として採用する。ラベルは `EXTERNAL_GUESS`。
   JDTによる検証を経ていない（メンバの実在もオーバーロードも未確認）ので、
   出力には `外部ライブラリ（import推定・未検証）` と明記する
2. それも無理なら「型解決失敗」として件数を数え、キャッシュに `U` 行として残す

**失敗件数は必ず実行ログに出し、かつ失敗した呼び出し自体も出力に残すこと。**
これはユーザーが最もハマる「`library.folders` の設定漏れ」を検知する手掛かりになる。
解決できないものを黙って捨てると「呼び出しが無い」ように見えてしまい、
影響調査の結論を誤らせる。

## 6. 名前の正規化（静かに壊れる箇所）

3種類の名前を明確に区別する。混同すると出力が壊れるが、
エラーにはならないので気付きにくい。

| 用途 | 形式 | 例 |
|---|---|---|
| 内部ID・型階層の照合 | ソース上の正規名 | `jp.co.xxx.Outer.Inner` |
| `callee` / `root` / `call-hierarchy` 列 | クラス名.メソッド名（パッケージ無し） | `Outer.Inner.method` |
| `caller` 列（スタックトレース） | **バイナリ名**（内部クラスは `$`） | `at jp.co.xxx.Outer$Inner.method(Foo.java:12)` |

### 6.1 内部クラスは `$` で区切る（`caller` 列）

Eclipseの「Javaスタック・トレース・コンソール」が期待するのは
**JVMのバイナリ名**。ドット区切りのままだと内部クラスのメソッドへ
ジャンプできない（`Outer.Inner のソースが見つかりませんでした` になる）。

### 6.2 デフォルトパッケージでの単純名の切り出し

「型FQNからパッケージを除いた部分」を得るとき、
`lastIndexOf('.')` で末尾だけ取ると**デフォルトパッケージ上の内部クラスで
外側のクラス名が消える**（`Outer.Inner` → `Inner`）。

パッケージが空の場合は型FQN全体がそのまま入れ子構造を表すので、
そのまま返すこと。

```java
String simpleTypeName(int id) {
    String t = typeFqn(id), p = pkg(id);
    if (p.isEmpty()) return t;                       // ← ここ
    if (t.startsWith(p + ".")) return t.substring(p.length() + 1);
    int i = t.lastIndexOf('.');
    return (i >= 0) ? t.substring(i + 1) : t;
}
```

### 6.3 匿名クラスの型名

`ITypeBinding.getQualifiedName()` は匿名クラスに対して**空文字を返す**。
そこでスキップすると匿名クラスによるオーバーライドと中の呼び出しが丸ごと落ちる。
`getQualifiedName()` → `getBinaryName()`（`Outer$1`）→ `getKey()` の順に
フォールバックすること。

### 6.4 ジェネリクス

型は常に `getErasure()` を通す。メソッドは `getMethodDeclaration()` で
宣言側を基準にする。実体化された型のままだと同じメソッドが別IDになる。

## 7. フェーズ2: グラフ構築と具象クラス解決

### 7.1 キャッシュ形式（TSV）

外部ライブラリ不要でデバッグしやすいタブ区切り。1行目はバージョン文字列
（`jche-cache-v4`）。形式を変えたら上げること。読み込み側は不一致なら破棄する。

```
F  相対パス  更新時刻  サイズ
H  typeFqn  kind(I=IF/A=抽象/C=具象)  親型をカンマ区切り
D  pkg  typeFqn  method  paramSig  declLine  hasBody(1/0)
C  callerPkg callerType callerMethod callerParams
   calleePkg calleeType calleeMethod calleeParams  callLine  bindKind  recvKey  recvKind
   recvOrigin  argOrigins
R  pkg  typeFqn  method  paramSig  origin      （そのメソッドが返しうる値の出所）
J  typeFqn  fieldName  origin                   （コンストラクタ注入されたフィールド）
X  callerMethodキー  scopeKey  種別  値        （拡張フェーズAが拾った証拠）
U  行  呼び出し元メソッドキー  式  理由          （型解決に失敗した呼び出し）
```

`C` 行の `recvKind` は**レシーバ（呼び出し先のインスタンス）がAST上どこから来たか**を
1文字で持つ。解決に失敗したときの理由表示（8.4）に使う。
AST走査時にしか分からない情報なので、フェーズ1でキャッシュに残す必要がある。

| 値 | 由来 | ASTノード |
|---|---|---|
| `M` | 戻り値（ファクトリメソッド等） | `MethodInvocation` |
| `P` | 引数（メソッド外から渡される） | `IVariableBinding.isParameter()` |
| `F` | フィールド変数 | `FieldAccess` / フィールドの `SimpleName` |
| `L` | ローカル変数 | ローカルの `SimpleName` / `ClassInstanceCreation` |
| `T` | 自クラス（this） | レシーバ式なし |
| `S` | 型名（static） | 名前が `ITypeBinding` に解決される |
| `O` | レシーバ不明 | 上記以外 |

`recvOrigin` / `argOrigins` / `R` 行の `origin` は**出所（Origin）**という共通の表現で、
「次にどこを見れば具象型が決まるか」を持つ（7.5）。

| 表記 | 意味 | 確定するタイミング |
|---|---|---|
| `T:jp.co.xxx.UserDaoImpl` | `new` された具象型 | その場（キャッシュを読んだ時点） |
| `A:2` | 囲みメソッドの3番目の引数 | 経路を降りて呼び出し元が決まったとき |
| `M:jp.co.xxx.Factory#create()` | そのメソッドの戻り値 | そのメソッドの `R` 行を見たとき |
| `F:jp.co.xxx.Service#dao` | フィールド | `J` 行と、経路上の生成箇所を見たとき |
| `L:jp.co.xxx.UserDaoImpl` | 文字列リテラル（またはコンパイル時定数） | その場 |
| `C:0` | `Class.forName(引数)` で名前指定された型 | その呼び出しの実引数を見たとき |
| `U` | 追跡できない | 決まらない |

`argOrigins` は `0=T:jp.co.X;2=A:1` のように `位置=出所` を `;` で並べる。
追跡できない引数は載せない（載っていないこと自体が「不明」を意味する）。

`new` とメソッド呼び出しの出所には、**その呼び出しの実引数も付ける**。
区切りは `|`（値の側が既に括弧を含むため、括弧だと対応の判定が要る）。

```
T:jp.co.Service|0=T:jp.co.UserDaoImpl                     コンストラクタ注入を追うのに使う
M:jp.co.Factory#create(java.lang.String)|0=L:jp.co.UserDaoImpl   C:n を埋めるのに使う
```

実引数の出所は**入れ子にしない**（付いていたら剥がす）。段数を増やすほど
「どの推測が結論に効いたか」が追えなくなるうえ、文字列も長くなる。
一方 `R` 行では `U` を**明示的に書く**——書かないと「分かった分だけ」で
戻り値の型を1つに決め打ちしてしまう。ただし全ての return が `U` のメソッドは
判定に寄与しないので行そのものを書かない（キャッシュを膨らませないため）。

`F` 行が現れるたび、以降の行はそのファイルに属する。
値にタブ・改行が混ざると形式が壊れるので、書き出す前に除去する。

**差分判定は「最終更新時刻」と「ファイルサイズ」の両方の一致**。
更新は「旧キャッシュを先頭から読み、まだ有効なブロックだけを新キャッシュへ
書き写す」ストリーミングマージで行う。ランダムアクセスも全件保持も不要。

### 7.2 CSR形式の呼び出しグラフ

メソッドを `int` のIDに内部化（intern）し、呼び出し関係を
CSR（Compressed Sparse Row）のプリミティブ配列で持つ。

```
offsets[callerId] .. offsets[callerId+1]   その呼び出し元のエッジ範囲
calleeIds[e], callLines[e], bindKinds[e]   各エッジの内容
```

キャッシュを2回スキャンして構築する（1回目でID化と本数カウント、
累積和で `offsets` を作り、2回目で流し込む）。
エッジ1本が `int` 2個で済み、オブジェクトで持つ場合より桁違いに省メモリ。

現在の出力は下流（呼び出し先）しか使わないので、逆引きCSRは作っていない。

### 7.3 解決パイプライン

エッジ単位で段階的に判定し、先に確定した段で打ち切る。

| 段 | ラベル | 判定 |
|---|---|---|
| — | `EXTERNAL_GUESS` | import推定（5.6）。型階層情報が無いので常に単一 |
| 0 | `STATIC_BOUND:{PRIVATE,STATIC,FINAL_METHOD,FINAL_CLASS,CTOR,SUPER}` | 仮想ディスパッチされない |
| 1 | `NO_OVERRIDE` / `SINGLE_IMPL` / `NO_IMPL` | 候補が1つに定まる |
| 2 | `LOCAL_NEW` / `LOCAL_NEW_MULTI` | 同一メソッド内で `new` された型 |
| 3 | 拡張が返すラベル | ファクトリ・DI設定など（7.4） |
| 4 | `DATAFLOW_FACTORY` | レシーバがメソッドの戻り値。その宣言の `return` から決める（7.5） |
| 5 | `CHA` | 候補が複数のまま（低確度） |

段4より段3（拡張）を先に試すのは、拡張がプロジェクト固有の確かな知識
（DI設定の対応表など）を持っているのに対し、段4は汎用の推論だから。

このほかに、経路が決まって初めて判定できる `DATAFLOW_PARAM`（引数由来）と
`DATAFLOW_FIELD`（コンストラクタ注入されたフィールド由来）がある。
これらはエッジ単位で決まらないので `resolveEdge()` の中にはなく、
フェーズ3の探索中に適用する（7.5）。

**段0の判定軸は「静的束縛か仮想呼び出しか」。**
「宣言型が具象クラスだから確定」は誤り
（`Base b = new Derived(); b.m();` で実際に走るのは `Derived.m`）。
判定理由まで記録しておくと、後から「この確定は妥当か」を監査できる。

**候補数は「サブクラス数」ではなく「そのメソッドをオーバーライドしている宣言の数」。**
サブクラスが多くてもオーバーライドが1件なら候補は1件。

段2はフロー依存解析をしない割り切り。「そのメソッド内でその変数に代入される
`new` を全部集める」フロー非依存・安全側の方針。1件なら確定、複数なら候補集合。

### 7.4 拡張ポイント

具象クラスの特定方法はプロジェクトごとに違うので、2フェーズの差し込み口を用意する。
必要な情報が手に入るタイミングが2つに分かれるため、1つのインターフェースにはできない。

- **フェーズA `CallSiteHintCollector`** … AST走査中に証拠を拾う（キャッシュの `X` 行に残る）
  - 例: `DaoFactory.get("USER_DAO")` の文字列リテラルを、戻り値を受けている変数のキーに紐づける
- **フェーズB `TypeCandidateProvider`** … 証拠から具象型を返す（グラフ構築後）
  - 例: `"USER_DAO"` → `jp.co.xxx.UserDaoImpl` の対応表を引く

証拠は**呼び出し元ごとに**記録する。呼び出し元が複数ある場合（5.5(b)）に
一部にしか紐づけないと、その経路だけ解決できなくなる。

`appliesToStaticBound()` が `true` の拡張には、段0で確定した呼び出しにも声をかける。
段0で打ち切ると拡張に到達せず、バイトコード織り込み等で前提が崩れるケースを救えないため。

### 7.5 データフロー解析

CHAで候補が複数になった呼び出しのうち、**ファクトリメソッドの戻り値**と
**呼び出し元から渡された引数**の2つを追って具象クラスを1つに決める。
`dataflow.enabled=false` で丸ごと止められる。

判断の軸は **「絞れないことより、間違って絞ることの方が有害」**。
このツールの出力は改修時の影響調査に使われるため、
「候補が多くて絞れなかった」は追加調査で済むが、
「1つに絞ったが実は違った」は調査対象の取りこぼしになる。
迷った点と判断の理由は [QA.md](QA.md) にまとめてある。

#### 7.5.1 出所（Origin）の収集 — フェーズ1

メソッド本体に入る**前に**本体を1回だけ先読みして「変数 -> 出所」の表を作る。
走査しながら作ってはいけない。

```java
Dao d = new UserDao();
for (int i = 0; i < n; i++) {
    d.select();          // 走査順に作ると、ここでは UserDao に見える
    d = new OrderDao();  // だが2周目以降は OrderDao
}
```

先読みして**同じ変数に出所の違う代入が複数あれば `U` に倒す**ことで、
フロー非依存・安全側に寄せる（段2の `LOCAL_NEW_MULTI` と同じ考え方）。

`return` の出所は `R` 行に記録する。**ラムダ式の中の `return` は
囲みメソッドの戻り値ではない**ので除外する。ラムダの入れ子の深さを数え、
0 のときだけ記録する（呼び出しの帰属はこれまで通り囲みメソッドでよい——
ラムダの中の呼び出しは実際にその囲みメソッドの一部として書かれている）。
匿名クラスのメソッドはラムダの中に現れうるので、`MethodDeclaration` に入るときに
深さを一旦0に戻し、抜けるときに復元する。

#### 7.5.2 ファクトリの戻り値（経路に依存しない）

`R` 行から「そのメソッドが必ず返す値の出所」を求める。
**1つでも追跡できない `return` があれば、または複数の出所を返すなら特定しない。**
委譲（`return create();`）は `dataflow.max.depth` 段まで辿り、循環は打ち切る。

畳んだ結果は具象型（`T:`）とは限らない。次の2つは
**そのファクトリを呼んでいる箇所の実引数**を見て初めて確定するので、
そのまま返して呼び出し側で埋める。

| 戻り値の出所 | 埋める材料 | 例 |
|---|---|---|
| `C:n` | n番目の実引数が `L:`（クラス名の文字列）なら、その型 | `return (Dao) Class.forName(name).newInstance();` |
| `A:n` | n番目の実引数の出所 | `return flag ? a : b;` |

`C:n` で得た型名が**解析対象に存在しない場合は使わない**。
文字列の見た目だけで決めると、たまたまクラス名の形をした文字列
（設定キーなど）を型と誤認する。

対応する生成の形は `Class.forName(x).newInstance()` と、
`getDeclaredConstructor()` / `getConstructor()` を1段挟んだ形。
`x` が文字列リテラルなら、その場で `T:` に確定する。

経路に依存しないのでメソッド単位でメモ化でき、`resolveEdge()` の段4に置ける。
`methods.csv` の `unresolvedCalls` にもそのまま効く。

具象型が決まったら、その型から**親クラスへ幅優先で辿って**本体を持つ実装を探す。
`UserDao extends AbstractDao` で `select()` の宣言が親にしかない場合、
型名だけで引くと見つからないため。このため型階層は
「親 -> 子」に加えて「子 -> 親」の向きも持つ。

#### 7.5.3 引数（経路に依存する）

```java
void rootA() { shared(new UserDao()); }
void rootB() { shared(new OrderDao()); }
void shared(Dao dao) { dao.select(); }
```

`shared` の中の `dao.select()` は、`rootA` から来たなら `UserDao.select`、
`rootB` から来たなら `OrderDao.select`。**同じ呼び出し箇所でも経路が違えば
答えが違う**ので、エッジ単位ではメモ化できない。これは実装の都合ではなく
「起点からの経路のデータフローを解析する」という要件そのものの帰結。

実装は探索の中に置く。`pathParamTypes[深さ]` に「この経路で、その深さの
メソッドの各引数に何が渡ってきているか」を持ち、経路を降りるたびに
呼び出し箇所の `argOrigins` と1つ上の環境から次の環境を作る。
深さぶんの配列だけなので、8.2 のメモリ設計を崩さない。

**やらないのは逆向きの推論。** 「`shared` の呼び出し元を全部集めると引数は
`UserDao` か `OrderDao`」という遡り方はしない。呼び出し元が多いと候補が発散し、
実際には通らない経路の型が混ざり、結果が経路と対応しなくなる。
やっているのは前向きに持ち回るだけで、1本の経路に対して答えは決定的に決まる。

#### 7.5.4 コンストラクタ注入されたフィールド（7.5.3 の1段延長）

```java
class Service {
    private final Dao dao;
    Service(Dao dao) { this.dao = dao; }
    void exec() { dao.select(); }
}
new Service(new UserDaoImpl()).exec();   // この経路なら dao は UserDaoImpl
```

「このフィールドには必ずコンストラクタのn番目の引数が入る」と言い切れる
フィールドだけを `J` 行に記録し、経路上の `new` の実引数と突き合わせる。
引数（7.5.3）の仕組みを、メソッドの引数からオブジェクトの生成へ1段延ばしただけ。

言い切る条件は次の4つ。**1つでも崩れたら記録しない。**

| # | 条件 | なぜ必要か |
|---|---|---|
| a | `private` または `final` | クラスの外からの代入を数え上げられるようにする |
| b | 代入がコンストラクタ本体かフィールド初期化子の中だけ | setter で後から差し替わらない |
| c | 初期化子を持つか、`this(...)`委譲していない**全ての**コンストラクタで代入される | 代入されない生成経路が無い |
| d | それらの代入の出所が全て一致する | コンストラクタごとに別物が入らない |

(c) が要点。「あるコンストラクタでは代入するが別のでは代入しない」型は、
後者の経路で中身が別物になる。(a) のおかげで、そのフィールドへの代入が
そのファイルの外に無いと言えるので、判定は1ファイルで完結する。

探索側では `pathParamTypes` と並べて `pathCtorArgs`（今メソッドを実行している
オブジェクトのコンストラクタ実引数）を持ち回る。レシーバが無い呼び出し
（`this` への呼び出し）は同じオブジェクトなので、そのまま引き継ぐ。

**親クラスのフィールドは追わない。** `Sub extends Base` で `Base` の
フィールドの出所が「`Base` のコンストラクタの0番目」でも、経路上で
分かっているのは「`Sub` のコンストラクタに何を渡したか」。
`super(...)` を通じた受け渡しを追跡していないため繋がらない。
繋げてはいけないので、環境には**どの型のコンストラクタ実引数かを必ず持たせ**、
フィールドの宣言型と一致しなければ使わない。

#### 7.5.5 「必要な場合のみ」の担保

| 場所 | 絞り方 |
|---|---|
| 呼び出しの解決 | CHAで**候補が複数になった**呼び出しだけ試す |
| 経路を降りるとき | 呼び出し先が引数をレシーバに使うか次へ渡すメソッドのときだけ環境を作る（`usesContext`。O(エッジ数) を1回） |
| コンストラクタ実引数 | 呼び出し先の型が `J` 行を持つときだけ持ち回る |
| ファクトリの戻り値 | メソッド単位でメモ化。同じファクトリを何度呼んでも解析は1回 |
| 文字列リテラル | 完全修飾クラス名の形（ドットを含み、各要素が識別子で、最後が英大文字始まり）だけ記録する。ログ文言やSQLまで載せるとキャッシュが文字列で埋まる |

実測では**遅くなるどころか速くなった**。40実装のインターフェースを
引数で受け渡す合成プロジェクト（841ファイル）で、
0.65〜0.70秒 / 19,200行（あり）に対し 1.01〜1.29秒 / 100,800行（なし）。
具象クラスが1つに定まると、CHAの候補数ぶんの枝分かれが消えるため。

#### 7.5.6 追わないもの

| 対象 | 理由 |
|---|---|
| setter/DI設定で入るフィールド | 代入がソースの外。静的解析では原理的に追えない |
| 7.5.4 の条件を満たさないフィールド | 代入されない生成経路や、後からの差し替えがありうる |
| 親クラスのフィールド | `super(...)` を通じた受け渡しを追跡していない（7.5.4） |
| インターフェース越しのファクトリ | ファクトリ自身の具象クラスが不明。多段の推測は根拠を追えなくなる |
| 実行時に決まるクラス名 | `Class.forName(System.getProperty("dao"))` など |
| 起点メソッドの引数・起点オブジェクトの生成箇所 | 経路の中に渡し元がない |

いずれも `CHA候補N件（未展開）: 理由` として**追えなかったこと自体は必ず出力**する。

## 8. フェーズ3: 探索と出力

### 8.1 起点（エントリポイント）の選定

- `entry.packages` 指定時 … パターンに一致し、ソース上に宣言があるメソッド。
  出力順を安定させるため `型FQN#メソッド名` でソートする
- 未指定時（全体モード） … **入次数0**かつソースがあり本体を持つメソッド

全体モードの起点順は次の優先順で並べる。実行のたびに順序が変わらないようにするため。

1. ソースフォルダの宣言順（`source.folders` / `.classpath` の記載順）
   — main と test が混ざらないようにする
2. 型FQN順（`.` は英数字よりコード上小さいので、単純な文字列比較で
   「パッケージ自身 → そのサブパッケージ → 次のパッケージ」の順になる）
3. 同じ型内はソース上の宣言行順

### 8.2 深さ優先で1行ずつ書き出す

ツリーを組み立てない。ヒープに載るのは「現在の経路（深さぶんの配列）」だけ。

安全策:

| 仕組み | 内容 |
|---|---|
| `max.depth` | 深さ制限。0以下は無制限だが、**再帰なので実効上限を設ける**（512） |
| `max.rows` | 出力行数の上限。組合せ爆発への最後の砦 |
| 循環検出 | 経路（rootから現ノードまでの祖先）に同じメソッドがあれば1行だけ出して降りない |
| 除外パッケージ | 除外ノード自身は出さないが、その先は親に繋ぎ直して辿り続ける |

**循環検出は経路単位。** グローバルな訪問済み集合は持たない。
別の経路で同じ呼び出しが現れたらそちらでも出力する（ダイヤモンド依存を潰さない）。

CHAで候補が複数のときは候補を列挙するが**その先へは降りない**
（候補数^深さで爆発するため）。

### 8.3 出力形式

列の詳細は README にあるので、ここでは設計上の制約だけ書く。

- **`call-hierarchy` 列は必ず最終列**。可変長なので、後ろに固定列を置くと
  階層が途中で切れる
- 注記（`[CYCLE]`・深さ制限・CHA候補・import推定）は
  **`call-hierarchy` の最後の要素**として追記する。
  独立した列にすると上記の制約に反する。行末grepは効かなくなるが許容する
- `callee` 列に行番号を混ぜない。混ぜるとExcelのフィルタの選択肢が
  呼び出し箇所ごとに散らばって使い物にならなくなる
- `callee`（短い名前）と `calleeSignature`（完全修飾クラス名＋引数の型）を**両方**出す。
  短い名前だけだと別パッケージの同名クラスやオーバーロードが1つのフィルタ値に
  混ざってしまい、完全修飾名だけだとフィルタの選択肢が細かすぎて使えない。
  **フィルタは `callee`、特定は `calleeSignature`** という役割分担にする
- **コンストラクタ呼び出しそのものは行にしない**。`new` したこと自体より
  「そのコンストラクタの中で何を呼んでいるか」が知りたいため。
  経路には積むので、コンストラクタ内からの呼び出しはコンストラクタを含んだ階層で出る
- **コンストラクタの表示名は `<init>` ではなくクラス名**（`Sample.Sample`）。
  `<init>` はJVMの内部名で、ソースを読む人が探す名前ではない。
  ソースに宣言が無い暗黙のデフォルトコンストラクタも、補完される名前で出す。
  ただし `caller` 列だけは例外で `<init>` のまま
  ——Eclipseのスタックトレース・コンソールが解釈する形式に合わせる必要があるため
- `methods.csv` からもコンストラクタを除く。2つの一覧で扱いが違うと
  「片方にあって片方に無い」の理由をユーザーが推測する羽目になる
- `call-hierarchy.csv` には性質の違う3種類の行が混在する。`root` 列で区別できる:
  1. 呼び出し階層（`root` = 起点メソッド）
  2. 型解決に失敗した呼び出し（`root` = `(型解決失敗)`）
  3. 被参照スキャン（`root` = jar名）
- 型解決に失敗した行は、キャッシュの `U` 行を読み直してストリーミングで書く。
  呼び出し元のキーは `D` 行と同じ形式なのでIDが引け、`caller` 列を
  スタックトレース形式にできる（Eclipseから失敗箇所へ飛べる）
- 被参照スキャンの行は定数プールしか読まないので、
  呼び出し元のメソッドも行番号も分からない（README参照）

### 8.4 note（注記）の出力仕様

注記は**独立した列にせず、`call-hierarchy` 列の最後の要素として追記する**
（8.3の可変長制約のため）。

出力するのは「その行の呼び出し先から先へ、なぜ降りていないか／何を根拠に
その具象クラスにしたか」だけ。**降りている行には注記を付けない**
——全行に何か書くと、注記が付いている行を目で拾えなくなる。

判定は次の順で、先に当たったものを採る（前半グループ）。

| 順 | 条件 | 出力 |
|---|---|---|
| 1 | この経路上に既に現れたメソッドへ戻る | `[CYCLE]` |
| 2 | `EXTERNAL_GUESS`（import推定） | `外部ライブラリ（import推定・未検証）` |
| 3 | 呼び出し先の宣言ファイルが無い | `ソースなし（展開不可）` |
| 4 | 次の深さが `max.depth` に達する | `深さ制限(N)のため打ち切り` |

続けて、解決結果についての注記を付ける（後半グループ）。
前半が付いている場合は ` / ` で連結する。

| 条件 | 出力 |
|---|---|
| 候補が複数 | `CHA候補N件（未展開）: {理由}` |
| `NO_IMPL`（本体を持つ実装が皆無） | `実装なし（宣言のまま）: {理由}` |
| 解決先が宣言型と違う | `解決:{ラベル}` |
| データフローで決めた（`DATAFLOW_*`） | `解決:{ラベル}`（結論が宣言型と同じでも出す） |
| 上記以外（宣言型のまま確定） | なし |

`DATAFLOW_*` だけ「宣言型と同じでも出す」のは、CHAでは候補が複数あったものを
1つに定めたという事実に意味があるため。出さないと
「候補が複数のまま出力された行」と見分けが付かない。

**`{理由}` は 7.1 の `recvKind` の説明文**（`戻り値（ファクトリメソッド等）`
`引数（メソッド外から渡される）` `フィールド変数` `ローカル変数` など）。

理由をレシーバの由来で出すのは、**次に調べる場所が由来ごとに違うから**。
`CHA候補3件` とだけ書かれても利用者にできることは無いが、
「戻り値だから絞れない」なら**そのファクトリメソッドの `return` を見る**、
「引数だから絞れない」なら**このメソッドの呼び出し元を見る**、
「フィールドだから絞れない」なら**代入箇所とDI設定を見る**、と行動が決まる。
言い換えると、注記は**失敗の報告ではなく次の調査手順**として書く。

同じ判定を `methods.csv` の `unresolvedCalls` / `unresolvedCause` 列でも使う。
そのメソッドが出しているエッジを走査し、絞れなかった件数と理由（重複排除・`;` 区切り）を
出す。**階層を追う前に「穴のあるメソッド」を一覧できる**ようにするのが狙いで、
これが無いと利用者は「出ていない＝呼んでいない」と誤読する。
判定は `resolveEdge` の結果をメモ化して共有するので、二重の解決コストはかからない。

## 9. 被参照スキャン

外部jarのclassファイルの**定数プールだけ**を読む。命令列（Code属性）は読まない。
そのため「どのjar・どのクラスが参照しているか」までは分かるが、
「どのメソッドから呼んでいるか」は分からない。外部ライブラリは不要。

照合結果は3種類。

| 種別 | 意味 |
|---|---|
| `EXACT` | そのクラスで宣言されているメソッドへの参照 |
| `INHERITED` | 親クラスから継承したメソッドへの参照 |
| `IMPLICIT_CTOR` | 暗黙のデフォルトコンストラクタ（＝そのクラスを生成している） |

自分の型を参照しているのにメソッドが一致しないものは
「相手が古い版のjarに対してビルドされている」可能性がある。
`使われていない` と即断させないよう、件数をログに出す。

**自プロジェクトのクラスを含むclassは読み飛ばす。** 指定されたフォルダに
自分のビルド成果物のjarが混ざっていると（`build/libs` や `dist` を丸ごと
指定した場合など）、自分から自分への呼び出しが「他リポジトリからの被参照」として
出てしまう。判定は「そのclassの `this_class` が解析済みの自プロジェクトの型か」で、
参照先ではなく**参照している側**の型で見る。除外件数はログに出す
（0件でないのに被参照も0件なら、指定フォルダを間違えている）。

指定パスの相対起点は `project.root`。ソースや依存jarと同じ起点に揃える
——利用者が意識するのは「解析対象プロジェクトの周辺」であって設定ファイルの置き場所ではない。

## 10. メモリ設計

数万ファイル規模で `OutOfMemoryError` にしないための3点。
これは後付けできない設計なので、最初から守ること。

1. **解析結果をヒープに溜めない** — 1ファイル解析するたびにキャッシュへ
   書き出して破棄する。ヒープ常駐は「ソースファイルのパス・更新時刻・サイズ」のみ
2. **エッジをオブジェクトで持たない** — 7.2 のCSR。
   出所（7.5）の文字列も同様で、実体は共有プールに1つずつ置き、
   エッジ側は `int` のインデックスで参照する（`A:0` や型名は激しく重複する）
3. **ツリーを組み立てない** — 8.2 の逐次書き出し。
   `max.depth=6` / 分岐50 でも最悪 50^6 ≒ 1.5億ノードになりうる

各フェーズの終わりにヒープ使用量をログに出す（`-Xmx` の目安になる）。
最大になるのは通常フェーズ2。

## 11. 落とし穴（実際に踏んだもの）

| 罠 | 症状 | 対処 |
|---|---|---|
| コンパイラ準拠レベルが既定のまま | 大量の「型解決に失敗」 | 5.2 |
| `setUnitName()` の省略 | バインディングが解決されない | 5.1 |
| `.classpath` の `kind="con"` | 依存jarを1つも認識できない | 5.3 |
| クラスパスにフォルダを渡す | 展開されず0件扱い | 5.3。展開後の件数をログに出すと気付ける |

| 内部クラスを `.` 区切りのまま出力 | Eclipseからジャンプできない | 6.1 |
| デフォルトパッケージで `lastIndexOf('.')` | 内部クラスの外側クラス名が消える | 6.2 |
| 匿名クラスで `getQualifiedName()` が空 | 匿名クラス経由の呼び出しが丸ごと落ちる | 6.3 |
| 「現在のメソッド」を単一スロットで管理 | 匿名クラスより後ろの呼び出しが全部落ちる | 5.5(a) |
| フィールド初期化子を「メソッド外」で捨てる | `<clinit>` / `<init>` 内の呼び出しが落ちる | 5.5(b) |
| 暗黙コンストラクタの宣言を作らない | `new B()` が `ソースなし` と誤表示 | 5.5(c) |
| MS932に変換できない文字 | 書き出しで例外 | エンコーダを置換動作にする（`CodingErrorAction.REPLACE`） |
| BOM無しUTF-8 | ExcelでCSVが文字化け | 既定を UTF-8-BOM にする |
| 標準出力の文字コードを固定 | Windowsコンソールで**ログだけ**文字化け | `-Dfile.encoding` を固定しない。端末に任せる |
| 出力の区切り文字をタブにする | `.csv` 拡張子だとExcelがカンマ区切りとして開く | 既定はカンマ |
| 被参照スキャンのフォルダに自分のjarが混ざる | 自分から自分への呼び出しが「被参照」として出る | 9。参照する側の型で除外 |
| 全フェーズで進捗を出す | ログが流れて型解決の失敗件数が埋もれる | 4。進捗はフェーズ1だけ |
| コンストラクタを `<init>` のまま表示 | ソースを読む人が探す名前と一致しない | 8.3。`caller` 列だけ例外 |
| ラムダ式の中の `return` を囲みメソッドの戻り値として記録 | ファクトリの戻り値型を誤って狭める | 7.5.1 |
| 追跡できない `return` を記録しない | 複数の型を返すメソッドを1つに決め打ちする | 7.5.1 |
| 変数の出所を走査順に作る | ループ内で再代入される変数の型を誤る | 7.5.1 |
| 具象型が分かった後、その型名だけでメソッドを引く | 親クラスから継承した実装が見つからない | 7.5.2 |
| 引数由来の解決をエッジ単位でメモ化 | 別経路の結果を使い回して誤る | 7.5.3 |
| 一部のコンストラクタしか代入しないフィールドを追跡 | 代入されない生成経路で別の型を割り当てる | 7.5.4(c) |
| コンストラクタ実引数に「どの型のものか」を持たせない | 親クラスのフィールドにサブクラスの実引数を当てる | 7.5.4 |
| 文字列リテラルを全部出所として記録 | キャッシュがログ文言とSQLで埋まる | 7.5.5 |
| 文字列から得た型名を存在確認せずに使う | 設定キー等をクラス名と誤認する | 7.5.2 |

## 12. 受け入れ基準

再実装が正しいかを確認するための最小セット。
**自分自身のソースを解析する（self-analysis）のが最も手軽で効果的。**

### 12.1 基本

- [ ] `javac -cp "lib/*" -d bin -encoding UTF-8 src/CallHierarchyExporter.java` が
      警告なしで通る（`-Xlint:all`）
- [ ] 引数なしで実行すると、既定パスを使う旨をエラー出力に出す
- [ ] 出力は `call-hierarchy.csv` と `methods.csv` の2つだけ
- [ ] 両CSVがUTF-8 BOM付きで、Excelで文字化けせずに開ける

### 12.2 型解決

- [ ] 自分自身を `library.folders` 付きで解析したとき、
      **型解決の失敗が0件**になる
- [ ] `library.folders` を空にすると失敗件数が0でなくなり、警告がログに出る
- [ ] そのとき `call-hierarchy.csv` にも `root` が `(型解決失敗)` の行が
      **ログの件数と同数**出る
- [ ] 依存jarを集めたフォルダを1つ指定するだけで、
      展開後のjar数がログに出る

### 12.3 名前の正規化

- [ ] 内部クラスのメソッドの `caller` 列が
      `at Outer$Inner.method(File.java:行)` になっている
- [ ] 同じ行の `callee` 列は `Outer.Inner.method`（`$` ではない）
- [ ] `caller` 列をEclipseの「Javaスタック・トレース・コンソール」に
      貼るとソースへジャンプできる

### 12.4 初期化子

次のクラスを解析して確認する。

```java
public class Sample {
    private static final long START = compute();
    private int x = init();
    static { staticBlockCall(); }
    { instanceBlockCall(); }
    Sample() { }
    Sample(int y) { }
    Sample(String s) { this(0); }          // 委譲 → 複製されない
    static long compute() { return 1L; }
    int init() { return 2; }
    static void staticBlockCall() { }
    void instanceBlockCall() { }
}
```

- [ ] `compute` / `staticBlockCall` の呼び出し元が `Sample.<clinit>`
- [ ] `init` / `instanceBlockCall` の呼び出し元が
      `Sample.<init>()` と `Sample.<init>(int)` の**2つ**
      （`Sample(String)` は `this(0)` 委譲なので含まれない）
- [ ] 明示コンストラクタが無いクラスを `new` したとき、
      その `<init>` が `methods.csv` に載り、`ソースなし` 注記が付かない

### 12.5 探索

- [ ] 自己再帰・相互再帰で無限ループせず、`[CYCLE]` 注記が付く
- [ ] 別経路で同じ呼び出しが現れたら、それぞれ独立して出力される
      （ダイヤモンド依存が潰れない）
- [ ] `max.depth` に達した行に `深さ制限(N)のため打ち切り` が付く
- [ ] `max.rows` に達したら打ち切られ、警告がログに出る
- [ ] `exclude.packages` に一致するノードは出力されないが、
      その先のノードは親に繋ぎ直されて出力される
- [ ] コンストラクタ呼び出しそのものの行は1つも出ない
- [ ] コンストラクタ内から呼ばれたメソッドは、`call-hierarchy` 列に
      コンストラクタを含んだ経路で出力される
- [ ] `callee` / `call-hierarchy` / `methods.csv` に `<init>` は現れない
      （`caller` 列にだけ現れる）
- [ ] `methods.csv` にコンストラクタの行が無く、除外件数がログに出る

### 12.6 キャッシュ

- [ ] 1回目 `新規解析=N 再利用=0`、2回目 `新規解析=0 再利用=N`
- [ ] 1ファイルだけ書き換えると、そのファイルだけ再解析される
- [ ] キャッシュのバージョン文字列を変えると全件再解析される

### 12.7 データフロー解析

- [ ] `Factory.create().m()` が、`create()` の `return new X()` から `X.m` に解決される
- [ ] ローカル変数で受けた形（`Dao d = Factory.create(); d.m();`）でも解決される
- [ ] 委譲（`return create();`）を辿って解決される
