# 依存 jar の変更とキャッシュ — 実装時の QA 一覧

[Issue #36](https://github.com/instreest/java-call-hierarchy-exporter/issues/36)
「型解決もキャッシュされ、依存 jar を変更しても再解析されない」への対応で、
迷ったこと・困ったことと、その結論を Q&A の形で残す。

対応の要点:

- キャッシュに解析時の依存 jar を `L` 行として残す（パス・サイズ・更新時刻・含まれるパッケージ）
- 各ファイルの `F` 行に JDT が報告したエラー数を持つ（解決が不完全だった印）
- 次回の実行で jar の追加・変更・削除を検知し、その jar のパッケージの型を参照しているファイル
  （`I` 行）と、型解決に失敗していたファイル（`F` 行のエラー数、`U` 行の `BINDING_FAILED`）だけを解析し直す
- ヘッダ行に実行 JDK の版を含め、JDK が変われば全件解析し直す
- `H` 行の親型に、jar の型を経由して到達するソース上の親型も含める（jar の基底クラスが
  ソースのインターフェースを実装している構成で、その子を CHA の候補に入れるため。キャッシュ版 v12）

後半の Q18〜Q21 は、レビューで指摘された 4 点（CHA の候補が増える変更を検知できるか、
「AST の事実だけでは足りない」の初心者向け説明、ログの文字コード、実行 JDK による違い）への回答。

## 設計

### Q1. Issue の提案どおり「① AST の事実」「② 型解決の情報」の 2 段キャッシュにしなかったのはなぜか

JDT では型解決（バインディング）はパースと同時に行われ、後から「解決だけやり直す」手段が無い。
しかもキャッシュの事実はほぼ全部が解決結果でできている。呼び出し先の型と名前、引数の型、
フィールドの所有型、親型、修飾子のどれも、AST の字面ではなくバインディングから取っている。
字面だけの「① AST の事実」に残るのは「`x.foo(a)` という呼び出しが N 行目にある」程度で、
これだけでは呼び出しグラフを組めない。

したがって ② を作り直すには結局ファイルをパースし直すしかなく、① と ② を分けても
依存の変更時に節約できる仕事は無い。節約できるのは「どのファイルをパースし直すか」だけである。
そこで、キャッシュは 1 段のまま、ファイル単位で「この jar の変更が影響するか」を判定する設計にした。
Issue の意図（ソース変更なら全部、依存変更なら影響分だけ）は、この形で満たしている。
初心者向けの詳しい説明は Q19。

### Q2. jar の同一性はハッシュで見るべきか

サイズと更新時刻で見ることにした。ソースファイルの再利用判定と同じ基準で、利用者にも説明しやすい。
数十 MB の jar が百本あるプロジェクトで毎回ハッシュを取ると、それだけで数秒かかる。
コピーし直して更新時刻だけ変わった jar は「変更」と見なされて影響ファイルが解析し直されるが、
それは安全側の誤りで、結果は変わらない。

### Q3. 変更された jar の影響範囲を、型ではなくパッケージで持つのはなぜか

`I` 行には「このファイルの解決が参照した型」が FQN で入っているので、
jar の中の型一覧と突き合わせれば型単位で判定できそうに見える。しかし、

- jar の版を差し替えると型の増減がある。旧版にだけあった型は新しい jar からは分からない
- jar が削除されると、もう中身を開けない
- `I` 行の FQN からは「どこまでがパッケージで、どこからが内部クラスか」が分からない

ので、jar が含むパッケージの一覧を `L` 行に残し、`I` 行の型名は "." 区切りの前方部分を
全部試してパッケージ一覧と照合する（`a.b.C.D` なら `a`、`a.b`、`a.b.C` を試す）。
パッケージ単位は型単位より広めに再解析するが、jar の版差し替えのような普通の操作で
取りこぼさないことを優先した。

### Q4. jar が「追加」されたとき、パッケージの照合だけでは足りないのはなぜか

前回その型が無かったのだから、`I` 行には正しい FQN が入っていないことがある。
実際、サンプルの `fx.app.Legacy` は `missing.lib.RemoteClient` が無い状態で解析すると、
JDT のバインディング回復が同じパッケージにあると推定して `I` 行に `fx.app.RemoteClient` と残る。
import 文の `missing.lib.RemoteClient` も `I` 行に入るので今回のサンプルでは照合できるが、
FQN を直書きした参照や、親クラス経由で継承したメソッドの呼び出しなどは import に現れない。

そのため jar が追加・変更されたときは、「前回型解決に失敗していたファイル」を無条件に解析し直す。
失敗していたかは `F` 行のエラー数（JDT が報告したエラーの件数）と、
`U` 行の `BINDING_FAILED` で判定する。この 2 つは重なるが、片方だけでは拾えない場合が
あり得る（エラーとして報告されないまま呼び出し先が null になるケース、
呼び出しは無いが宣言の引数型が解決できていないケース）ので両方見る。

### Q5. エラー数をキャッシュに入れるのは「事実だけを入れる」原則に合うか

合うと判断した。「JDT がこのファイルに対してエラーを N 件報告した」は解析から機械的に得られる事実で、
出力形式や解決方針を変えても変わらない。「N が 0 でなければ jar 追加時に解析し直す」という判断は
読み手（`CacheUpdater`）に置いている。何のエラーかまでは持たない。
構文エラーもエラー数に含まれ、そういうファイルは jar が追加されるたびに解析し直されるが、
数は少ないはずで、安全側に倒した。

### Q6. jar 追加で解析し直したファイルの「依存先」も解析し直す必要があるか

ある。例えば `Legacy` に `handle(RemoteClient c)` という宣言があれば、jar 無しの解析では引数型が
回復バインディングの名前（`fx.app.RemoteClient`）で記録され、jar を足すと
`handle(missing.lib.RemoteClient)` に変わる。`Legacy` を呼ぶ側の `C` 行も前回の名前で記録されているので、
呼ぶ側も解析し直さないと呼び出し先が食い違う。

そこで、型解決に失敗していたファイルは「変更されたファイル」と同じ扱い（パス 2）で解析し、
それが宣言する型を「変わった型」に加える。すると `I` 行でその型を参照しているファイルが
パス 3 で再解析に回る（既存の 1 段の依存伝播）。サンプルでは `Legacy` を呼ぶ `Main` がこれで
解析し直される。

jar の「削除」で解析し直すファイルはパス 4（依存先の変更による再解析）で扱い、そこからの伝播はしない。
削除の場合は前回の解決が正しかったので、jar の型を事実に含むファイルは必ず `I` 行にもその型を
持っており、パッケージの照合で直接拾えるためである。
CHA の候補が増える・減る変更については Q18。

### Q7. 実行 JDK が変わったときは

JDT は実行中の JVM のブートクラスパスも解析対象のクラスパスに含めるため、
JDK の版が変われば標準 API の解決結果が変わりうる（新しい API の呼び出しが解決できる・できない）。
これも「依存の変更」なので、ヘッダ行に `jdk=<java.specification.version>` を含め、
違えばキャッシュ全体を捨てる。JDK の切り替えは jar の追加より稀で、影響範囲の特定も難しいので、
丸ごと作り直す。jbang 経由なら常に JDK 25 なので、通常は起きない。
実際に何が変わるかは Q20 で JDK 17 / 21 / 25 を並べて確かめた。

### Q8. `L` 行のパスは絶対パスか相対パスか

`F` 行と同じ考え方で、project.root 配下なら相対パス、外なら絶対パスにした。
プロジェクトを別のフォルダに移しても、中に置いた jar は同じものと分かる。
外の jar（`library.folders` に絶対パスで指定したもの）は絶対パスなので、移せば「削除＋追加」
に見え、そのパッケージを参照するファイルが解析し直される。結果は変わらず、安全側。

### Q9. 同じパッケージを複数の jar が持つ場合、クラスパスの順が変わった場合は

同じクラスが 2 つの jar にあるとき、JDT はクラスパス順で先に見つかった方を使う。
順序の変化や、同じパッケージを持つ別 jar の追加も「パッケージが変わった」として影響ファイルが
解析し直されるので、結果は正しくなる。ただし jar の順序だけが変わった（追加も変更も削除も無い）
場合は検知しない。`library.folders` はフォルダ直下の jar をファイル名順に並べるので、
順序だけが変わる状況は設定を書き換えたときに限られる。

## 実装

### Q10. `L` 行はブロックの外に置けるか。読み手はそれを読み飛ばせるか

ヘッダ行の直後、最初の `F` 行の前に置いた。`CallGraphBuilder` と `UnresolvedReport` は行の種別で
分岐しており、知らない種別は読み飛ばすので変更は要らなかった。
`CacheUpdater` のパス 3（有効ブロックの書き写し）は、`F` 行が現れるまで何も書かないので、
旧キャッシュの `L` 行は自然に捨てられ、新しい `L` 行はパス 0 で書いたものだけが残る。

### Q11. 変わっていない jar のパッケージ一覧を毎回取り直すか

取り直さない。パスとサイズと更新時刻が一致する jar は旧 `L` 行のパッケージ一覧をそのまま使う。
追加・変更された jar だけ開いてエントリ名からパッケージを集める（中央ディレクトリを読むだけなので速い）。
`META-INF/` 配下（マルチリリース jar の版別クラス）とデフォルトパッケージのクラス
（他パッケージのソースから参照できない）は除く。

### Q12. jar が読めなかったら

警告を出してパッケージ一覧は空のままにする。その jar の変更はパッケージ照合には効かないが、
Q4 の「型解決に失敗していたファイルの再解析」は動くので、jar 追加の効果は最低限反映される。

### Q13. 「新規解析」の内訳をどう見せるか

`ソース解析: 再利用=25 新規解析=2（うち依存先の変更による再解析=1、依存jarの変更による再解析=1）`
のように、自分が変わったわけではないファイルの再解析を理由別に出す。
jar の変更を検知したときは、その前に `[cache] 依存jarの変更を検知: 追加=1 変更=0 削除=0
（影響するパッケージ 1 件）` を出す。何が起きて何が解析し直されたかをログだけで追えるようにした。

### Q14. キャッシュの版を上げる必要はあるか

上げた（v10 → v11）。`F` 行に列を足し、`L` 行を加え、ヘッダに `jdk=` を足したため。
その後 Q18 の対応で `H` 行の親型の収集範囲を広げ、v12 にした。旧キャッシュは自動的に捨てられる。

## テスト

### Q15. 「jar を足す・外す」を回帰テストでどう再現するか

設定ファイルを 2 枚用意した。`config-before.properties`（`library.folders` 空）と
`config-after.properties`（`library.folders=deps`）で、違いはその 1 行だけ。
同じフォルダにあるので `cache.folders` と `output.csv` を共有する。
before → after → before の順に実行し、それぞれの出力を `expected-before/` `expected-after/` と比較する。
加えて、2 回目と 3 回目の実行ログで「依存jarの変更による再解析=N」の N が 0 でないこと、
2 回目で「再利用=N」の N が 0 でないこと（他のファイルはキャッシュから読まれたこと）を確認する
（ログの読み方は Q21）。
ソースツリーや jar を実行中に動かさないので、テストの前後で追跡対象のファイルは変わらない。
起点には `fx.app.Legacy` に加えて `fx.service.OrderService#execute` を入れ、
jar の追加で `dao.findById` の CHA 候補が 2 件から 3 件に増えること（Q18）も同時に確認する。

### Q16. サンプルの jar はどこに置くか

`samples/demo/deps/missing-lib.jar`（元ソースは `deps-src/`）。最初は `lib/` にしたが、
リポジトリの `.gitignore` が `lib/` を無視する（利用者が Eclipse から集めた JDT の jar を置く場所）ため
追跡されず、`deps/` に改めた。`whole` / `entry` ケースの `library.folders` は空のままなので、
`fx.app.Legacy` はこれまでどおり「型解決に失敗する例」として残る。

### Q17. `methods.csv` は before と after で変わるか

変わる。`Legacy.callRemote` の outDegree が、解決できた呼び出しの数だけ増える。
そのため `methods.csv` も before / after で別々に持つ。

## レビュー指摘への回答

### Q18. 型解決に失敗したファイルだけを解析し直すと、CHA の候補が 1 件から 2 件に増えるような変更を見落とさないか

見落とさない。ただし調べる過程で、この形の変更をそもそも記録できていなかった箇所が見つかり、直した。

**候補はキャッシュしていない。** CHA の候補（「`Dao#findById` の実装はどれか」）は、キャッシュの
`H` 行（型と親型）と `D` 行（メソッド宣言）から、読み手（`CallResolver`）が実行のたびに計算する。
呼び出し側のファイルの `C` 行には「宣言型のメソッド `fx.dao.Dao#findById(long)` を呼んでいる」としか
書いておらず、候補の数は入っていない。だから候補が増えるためには、どこかのファイルの `H` 行か `D` 行が
変わればよく、**呼び出し側のファイルを解析し直す必要は無い**。

**jar の追加で `H` 行・`D` 行が変わりうるファイルは、必ずエラーを持っていた。** `H` 行は
`extends` / `implements` に書いた型から、`D` 行の引数型は宣言に書いた型から作る。jar の追加でそれらが
変わるのは、その型が前回は無かった（見つからなかった）ときだけで、そのとき JDT はそのファイルに
「型が見つからない」エラーを報告する。エラー数は `F` 行に残しており、jar が追加・変更されたときは
エラー数が 0 でないファイルを全部解析し直す（Q4）。
つまり再解析の条件は「型解決に失敗した**呼び出し**（`U` 行）があるファイル」だけではなく、
「JDT がエラーを 1 件でも報告したファイル」を含む。`extends LibBase` のように呼び出しを伴わない
宣言だけの失敗も、この条件で拾う。

**見つかった欠落と修正。** ところが「jar の基底クラスがソースのインターフェースを実装している」構成
（例: ソースの `interface Dao`、jar の `abstract class LibDao implements Dao`、ソースの
`class LibBackedDao extends LibDao`）では、jar があっても `LibBackedDao` が `Dao` の実装として
候補に入らなかった。`H` 行に書いていた親型が「直接の親」だけ（`LibDao`）で、`LibDao` は jar の型なので
`H` 行が無く、読み手が `LibBackedDao → LibDao → Dao` とたどれなかったためである。
これはキャッシュの差分更新に関係なく、全件解析でも起きる。
v12 で、jar の型を経由して到達するソース上の親型も `H` 行に書くようにした
（`LibBackedDao` の親型は `missing.lib.LibDao,fx.dao.Dao`）。ソース上の親型の先は、その型自身の
`H` 行が持つので辿らない。

**確認。** 回帰テスト `jarchange` にこの構成を入れた。`OrderService.execute` の `dao.findById(10L)` は
jar 無しで `CHA候補2件`（`AbstractDao`、`OrderDaoImpl`）、jar を足した 2 回目の実行で `CHA候補3件`
（`LibBackedDao` が加わる）になる。このとき解析し直したのは `Legacy` と `LibBackedDao`
（エラーがあった 2 ファイル）と、`Legacy` を参照する `Main` の計 3 ファイルで、`OrderService.java` は
キャッシュから読んだまま（`再利用=25`）である。jar を外した 3 回目は 2 件に戻る。

jar 無しのときの `LibBackedDao` の `H` 行は `fx.dao.LibDao`（JDT が同じパッケージにあると推定した
回復バインディングの名前）で、`F` 行のエラー数は 4。jar 有りでは `missing.lib.LibDao,fx.dao.Dao`、
エラー数 0。エラー数を持つ理由がこの例で確認できる。

### Q19. 「呼び出しの型だけを事実として記録しても、結局再解析が必要」を初心者向けに

**ソースの字面（AST）から分かること、分からないこと。** 次の 1 行を考える。

```java
dao.findById(10L);      // OrderService.java の 24 行目
```

ソースを構文解析（パース）して得られる木構造が AST で、そこから分かるのは
「`dao` という名前のものに対して、`findById` というメソッドを、引数 1 個で呼んでいる。24 行目」までである。
呼び出し階層を作るのに必要なのは、その先の

- `dao` は何型か（フィールド？ 引数？ どこで宣言されているか）
- `findById` はどのクラスで宣言されたメソッドか（`fx.dao.Dao#findById(long)` か、別のパッケージの同名メソッドか）
- `10L` を受けるのは `findById(long)` か、`findById(Object)` のようなオーバーロードか

で、これを決める作業が「型解決（バインディング）」である。決めるには、`dao` の宣言、その型の定義、
その親クラス、import 先、そして**依存 jar の中のクラス定義**まで読む必要がある。
CSV の「呼び出し先」列に出る `fx.dao.Dao.findById(long)` は、字面ではなくこの解決結果そのものである。

**「AST の事実」だけを別に保存しても、jar が変わったときに役に立たない。** Issue の案は、
① AST から分かること（`dao`、`findById`、引数 1 個、24 行目）と ② 型解決の結果
（`fx.dao.Dao#findById(long)`）を別々に保存し、jar が変わったら ② だけ作り直す、というものだった。
しかし ② を作り直すために必要な材料は、① ではなく「`dao` の型を決めるための情報」で、
それはファイル全体（変数の宣言、import、クラスの継承関係）と依存 jar である。
JDT には「保存しておいた AST を後から解決し直す」機能も無く、解決はパースと同時にしか行えない。
したがって ② の作り直しは、そのファイルを JDT にもう一度読ませること（再パース）と同じ作業になり、
① を保存しておいても省ける仕事が無い。

たとえるなら、「田中さんに電話した」という記録（①）だけ残しても、どの田中さんかは名簿（クラスパス）を
引かないと分からない（②）。名簿が差し替わったら、記録を見返すのではなく、電話をかけた場面をもう一度
名簿と突き合わせる必要がある。

**節約できるのは「どのファイルを読み直すか」だけ。** ファイルが 1000 個あって jar を 1 つ足したとき、
1000 個全部を読み直すのが従来の「キャッシュを消す」で、今回の対応は「その jar に関係する数個だけを
読み直す」ことである。どれが関係するかは、各ファイルが参照した型の一覧（`I` 行）と、前回エラーが
あったか（`F` 行）で決める。Q1 で「① と ② を分けても節約できる仕事は無い」と書いたのはこの意味で、
分けるのが悪いのではなく、分けても jar 変更時の仕事量が減らない、ということである。

### Q20. 実行 JDK が違うと解析結果はどう変わるか。実際の出力に影響するか

JDT は `setEnvironment(..., includeRunningVMBootclasspath=true)` で、**実行中の JVM の標準クラス**
（`java.*` など）を解析対象のクラスパスに含める。つまり実行 JDK は「暗黙の依存 jar」である。
どこまで影響するかを、JDK 17 / 21 / 25 で同じソースを解析して確かめた（JDT は 3.46.0、
`source.level` 未指定 → 3 つとも「ソースレベル: 26」。構文の対応範囲は JDT の版で決まり、JDK には依らない）。

**回帰テストのサンプル（`samples/demo`、新しい API を使っていない）**: CSV もキャッシュの中身
（ヘッダ・`L` 行・`F` 行の更新時刻を除く全行）も、3 つの JDK で完全に同一。

**JDK の版で存在が変わる API を並べた調査用ファイル**（`fx.app.ModernApi`、サンプルに一時的に追加）:

| 呼び出し | JDK 17 | JDK 21 | JDK 25 |
|---|---|---|---|
| `daos.reversed()`（`List#reversed` は 21 から） | 失敗 | 解決 | 解決 |
| `first.findById(1L)`（`var first = daos.reversed().get(0)`） | **失敗**（`first` の型が分からない） | 解決 → `CHA候補2件` | 解決 |
| `declared.findById(2L)`（`Dao declared = daos.reversed().get(0)`） | 解決 | 解決 | 解決 |
| `new StringBuilder().repeat("ab", 2)`（21 から） | 失敗 | 解決 | 解決 |
| `Thread.currentThread().threadId()`（19 から） | 失敗 | 解決 | 解決 |
| `java.lang.Compiler.disable()`（21 で削除） | 解決 | 失敗 | 失敗 |
| `java.lang.IO.println("x")`（25 から） | 失敗 | 失敗 | 解決 |
| `"x".repeat(3)`（11 から） | 解決 | 解決 | 解決 |

出力への影響は次の 4 種類。

1. **JDK API の呼び出し自体**は、解決できても `exclude.packages=java.**` で CSV に出ない。
   解決できないと「(型解決失敗)」の行として出る。`ModernApi` の分は JDK 17 で `reversed` / `get` /
   `findById` / `repeat` / `threadId` / `println` の 8 行、21 で `disable` と `println` の 2 行、
   25 で `disable` の 1 行。CSV 全体の行数はヘッダ込みで 17: 16 行、21: 12 行、25: 11 行
   （ほかのファイルの型解決失敗 4 行を含む）。
2. **自プロジェクトのメソッド呼び出しが欠ける。** `var first = daos.reversed().get(0); first.findById(1L);`
   は、JDK 17 では `reversed()` の戻り値の型が分からないので `first` の型も分からず、
   `Dao#findById` への呼び出しが「型解決失敗」になる。21 / 25 では `AbstractDao.findById` と
   `OrderDaoImpl.findById` への `CHA候補2件` の 2 行が出る。これが一番影響が大きい。
   `var` やメソッドチェーンで JDK メソッドの戻り値を受けている箇所が対象で、宣言型を書いた
   `Dao declared = ...` は影響を受けない。
3. **methods.csv の数値と列**。`ModernApi.run` の outDegree は 9 / 15 / 16、
   `AbstractDao.findById` の inDegree は 13 / 14 / 14、解決手段の列も変わる。
4. **削除された API**（`java.lang.Compiler`）は新しい JDK で失敗する。方向が逆なだけで 1 と同じ。

結論:

- 実行 JDK は「解析対象のソースが使っている JDK API の版以上」であればよい。jbang 経由の JDK 25 固定は
  これを満たす。Pleiades 経路で JDK 17 を使う場合、対象プロジェクトが Java 21 の API を使っていると
  2 の形で階層が欠けるので、JDK を合わせる（README の Pleiades 節に注記した）。
- 新しい API を使っていないプロジェクトでは JDK の版で結果は変わらない。
- ヘッダの `jdk=` は維持する。版が違えば結果が変わりうることが確認できたので、更新時刻とサイズが
  一致しても再利用してはいけない。JDK の切り替えは稀なので、影響範囲を絞らず丸ごと作り直す（Q7）。

### Q21. 進捗ログの文字コードを UTF-8 に固定してよいか

しない。ツールは標準出力を端末の文字コードで書く方針で、UTF-8 に固定すると MS932 のままの Windows の
画面でログが化ける（README の設計方針、`CallHierarchyExporter.java` の冒頭コメント）。
回帰テストの `run.sh` / `run.cmd` でも固定しない。

代わりに、テストでのログ検査は文字コードに依らない形にした。フェーズ 1 の集計行
`ソース解析: 再利用=25 新規解析=3（うち依存先の変更による再解析=1、依存jarの変更による再解析=2） 失敗=0`
を「`=数字` が 3 つ以上あって数字で終わる最初の行」として探し（同じ形の `型数=…` の行はフェーズ 2 なので
後ろに出る）、最初の `=N`（再利用）と `jar` の直後の `=N`（依存jarの変更による再解析）だけを見る。
日本語部分が `?` に化けていても（この作業環境は POSIX ロケールで実際に化ける）、MS932 でも、
`=` と数字と `jar` は変わらないので判定できる。実行ログは 1 回ごとに `run-<回数>.log` に分けて残す。

## 限界（対応しないと決めたこと）

- `.classpath` の `kind="con"`（Maven / Gradle のコンテナ）は元から解決しておらず、今回の対象外
  （その後 [Issue #44](https://github.com/instreest/java-call-hierarchy-exporter/issues/44) で、`library.folders` が空欄なら
  Maven / Gradle を実行して解決済みのクラスパスを受け取る形で対応した。[build-tool-classpath-qa.md](build-tool-classpath-qa.md)）
- jar の順序だけの変化は検知しない（Q9）
- 同じ jar が 2 つのフォルダにあるとき、どちらから解決されたかは区別しない
- FatJar の中の jar は展開しない（[Issue #35](https://github.com/instreest/java-call-hierarchy-exporter/issues/35) の範囲）
