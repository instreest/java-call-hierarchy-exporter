# ワークスペースの他プロジェクトからの被参照 — 調査と設計（`workspace.projects`）

> **状態: 段階 1（本体・CLI）と段階 2（Eclipse / VSCode プラグイン）を実装済み。段階 0（クラスフォルダの被参照）は見送り（Q12）。**
> 「被参照メソッドの検索に、jar の代わりに Eclipse のワークスペース内の他のプロジェクトを対象にできないか」の調査と、
> 機能仕様の検討の記録。Eclipse の Java 検索（ワークスペースを対象にメソッドの参照箇所を探す）と呼び出し階層
> （`Ctrl+Alt+H`。ワークスペース全体から呼び出し元を辿る）を真似て、**呼び出し元を他のプロジェクトの起点まで詳しく辿れる
> ようにする**のが狙い。今の被参照（jar）の仕組みは [external-usage.md](external-usage.md)、別プロセスの解析とプラグインは
> [out-of-process-analysis-design.md](out-of-process-analysis-design.md) にある。
> 設定の書き方は [config/jche.properties](../config/jche.properties) の `workspace.projects` / `workspace.scope` のコメント、
> 検査は `test/regression/run.sh` の `workspace` ケース（題材は `test/workspace-demo`）。

---

## 0. 結論（要約）

- **今の被参照（`external.library.folders`）は jar の class ファイルの命令列を読む独立した機能**で、出るのは
  「jar のどのクラスのどのメソッドの何行目から参照しているか」の **1 段（`depth` = 1）だけ**である。キャッシュにも
  メモリ上のグラフにも入らないので、その先（相手の jar の中の呼び出し元の呼び出し元 … 起点）は辿れず、
  Eclipse / VSCode のビューにも出ない（[eclipse-plugin-ui-qa.md](eclipse-plugin-ui-qa.md) の Q2）
- **解析の単位は `project.root` 1 つ**で、他のプロジェクトは「依存 jar / クラスフォルダ」としてしか見えない。
  `.classpath` の他プロジェクト参照（`/OtherProject`）は読み飛ばし、Eclipse プラグインは依存プロジェクトの出力フォルダ
  （`bin`）を `library.jars` に渡す。つまり **他のプロジェクトは「呼び出し先」としては解決できるが、本体は展開されず、
  「呼び出し元」としては一切出ない**
- Eclipse の「ワークスペースを対象にした検索」に相当するものを実現する本線は、**相手のプロジェクトを相手自身の設定で
  解析したキャッシュを、名前で結合する**こと（モデル B。3.1 節）。キャッシュの中でメソッドと型を指す列はどれも名前
  （記号表の 4 列・型の完全修飾名）で、番号はブロックの中で閉じているので、別々に作ったキャッシュでもそのまま
  つながる。相手のクラスパスは相手の設定が持つので、クラスパスの和集合も版の衝突も起きない
- **実装した形（段階 1）**: 設定 `workspace.projects` に相手の設定ファイルかフォルダを並べると、相手を相手の設定で
  フェーズ 1（差分更新）し、相手のキャッシュをこの実行のグラフに結合する。呼び出し階層は相手の起点まで伸び、
  依存先の中へも本体を展開し、相手にある自分のインターフェースの実装が CHA の候補に入る。既定 `workspace.scope=callers`
  では、相手のメソッドは「`project.root` のメソッドに届く経路」の上にあるものだけを起点・階層・`methods.csv` に出す
- **コードを変えなくても、プロジェクトが 1 つの親フォルダの下にあれば、ソースを 1 つの解析に入れる形（モデル A）で
  今日できる**（2 節。マルチモジュールと同じ形）。相手に設定もキャッシュも要らない代わりに、クラスパスが和集合になり、
  自分に関係ない階層まで出る

## 1. 現状の整理（実装前）

### 1.1 jar からの被参照（`external.library.folders`）が何をしているか

| 項目 | 実装 |
|---|---|
| 入力 | jar / war / ear（FatJar の中の jar も）。`jche.external.ExternalUsageScanner#collectJars` がフォルダ配下の jar を集める |
| 読み方 | class ファイルの定数プールと命令列（`ClassFileRefs`）。`invoke*` と `invokedynamic`（ラムダ・メソッド参照）から参照先と行番号を拾う |
| 照合 | 参照先が **自分のソースの型**（H 行の型名 `graph.hierarchy().typeNames()`）なら、JVM の解決（`MethodSelection#resolvedDeclaration`）で宣言に結び付ける。自プロジェクトの class が混ざった jar は読み飛ばす |
| 出力 | `call-hierarchy.csv` に直接書く（`CallHierarchyCsvWriter#writeExternalUsageRow`）。`caller` はスタックトレース形式、`root` は jar 名、`depth` は 1、`resolved-by` は `EXTERNAL_USAGE:…`、`call-hierarchy` の末尾は `external-ref:EXACT / INHERITED / MISSING_NOARG_CTOR` |
| 持たないもの | キャッシュ（毎回 jar を読む）、メモリ上のグラフ（ビューに出ない）、相手側の呼び出し階層（jar の中の呼び出し元の呼び出し元は辿らない） |

「jar の中の呼び出し元の呼び出し元」を命令列から辿る拡張も理屈では書けるが、それは **ソース解析器をもう 1 つ
（バイトコード版で）作る**ことで、具象クラスの解決・DI・データフロー・ライブラリ呼び出し規則をすべて二重に持つことになる。
相手のソースがワークスペースにあるなら、ソースを解析するほうが同じ結果を 1 つの仕組みで得られる。

### 1.2 解析の単位が `project.root` 1 つであること

| 場所 | 決まり |
|---|---|
| `source.folders` / `library.folders` / `external.library.folders` | `project.root` からの相対で、**配下しか指定できない**（`Config#resolveAllUnderProject`） |
| `.classpath` の `kind="src"` で `/` 始まり（他プロジェクトへの参照） | 読み飛ばす（`ProjectLayout#readDotClasspath`。`config.layout.skipOtherProject`） |
| ビルドファイル（pom / gradle） | **ソースフォルダごと**に上位へ辿って読む（`BuildFileClasspath#candidateDirs`）。マルチモジュールはモジュールごとに読み、兄弟は `target/classes` とその pom で解決する（`MavenReactor`） |
| キャッシュの置き場所 | `project.root` のフォルダ名と絶対パスのハッシュで 1 つ（`Config#cacheDirOf`） |
| キャッシュ・出力の `file` 列 | `project.root` からの相対パス（`CacheFormat#fileRow`、`methods.csv` の `file`） |
| 解析サーバー（`--server`） | `ANALYZE` 1 回 = 設定ファイル 1 つ |
| Eclipse プラグイン | `IProject` ごとに `ProjectAnalysis` と子プロセスを 1 つ。依存プロジェクト（`CPE_PROJECT`）は**出力フォルダを `library.jars` に**入れる |

マルチモジュール（`test/maven-multi`）は「1 つの `project.root` の下に複数のモジュールのソースフォルダを並べる」形で
既に扱えていて、`app` から `core` への呼び出しは普通の辺になる。

### 1.3 Eclipse の機能との対応

| Eclipse | 範囲 | 実装前 | 実装後（段階 1） |
|---|---|---|---|
| 検索 → Java 検索 → 参照（ワークスペース） | ワークスペースの全プロジェクトから参照箇所を列挙 | `external.library.folders`（相手が jar のときだけ・1 段） | `workspace.projects` の相手なら通常の呼び出しの行 |
| 呼び出し階層（`Ctrl+Alt+H`。ワークスペース） | 全プロジェクトを横断して呼び出し元を根まで展開 | `project.root` の中だけ | 相手の起点まで伸びる |
| 依存プロジェクト（ビルド・パスの「プロジェクト」） | 参照先の型をソースから解決 | 出力フォルダ（`bin`）を class として解決。本体は展開しない | 相手のソースで解析した事実で本体を展開し、相手にある実装が候補に入る |

Eclipse の検索は JDT のワークスペース索引を使う。このツールは Eclipse の外の別プロセスで JDT をスタンドアロンで動かすので
その索引は使えず、相手のキャッシュ（解決済みの事実）がそれに当たる。Eclipse の「参照」は宣言への**静的な参照**の列挙で、
このツールは呼び出しを**実際に動く本体（具象クラス）に解決**して並べる。相手を入れてもこの違いはそのまま。

## 2. コードを変えずにできること（モデル A。回避策）

Eclipse の標準の配置（ワークスペースのフォルダ直下にプロジェクトを置く）なら、ワークスペースのフォルダを
`project.root` にし、各プロジェクトのソースフォルダを並べれば、他プロジェクトからの呼び出し元が普通の辺として出る
（`test/maven-multi` と同じ形）。

```properties
project.root=C:\work\ws
source.folders=app-core/src/main/java,app-batch/src/main/java,app-web/src/main/java
library.folders=
```

| 制約 | 中身 |
|---|---|
| 配置 | 全プロジェクトが **1 つの親フォルダの配下**にないと書けない |
| プロジェクトの `.classpath` | `project.root` 直下の `.classpath` しか読まない。Eclipse だけで管理したプロジェクトの依存 jar は `library.jars` に手で書く |
| クラスパス | 全プロジェクトのクラスパスの**和集合**を 1 つにして JDT に渡す。同じライブラリの版が違えば先のものが勝つ |
| 出力の量 | 全体モードでは、他のプロジェクトの「自分に届かない」階層もすべて起点として出る |
| 同じ型の二重宣言 | 同じ完全修飾名の型が 2 つのプロジェクトにあると `graph.duplicateType` の警告が出る |

相手に設定もキャッシュも無いときの代替として残す。`workspace.scope=all` の出力は、この形とほぼ同じになる
（違いは、相手がクラスパスを別に持つことと、相手のファイルのパスが `../` 付きになること）。

## 3. 設計

### 3.1 方針: 相手のキャッシュを名前で結合する（モデル B）

| | モデル A: 1 つの解析に複数プロジェクトのソースを入れる | モデル B: 相手を相手の設定で解析し、キャッシュを結合する（採用） |
|---|---|---|
| JDT の環境 | 1 つ（ソースパスは全プロジェクト、クラスパスは和集合） | プロジェクトごと（Eclipse と同じく、クラスパスを分けられる） |
| キャッシュ | 1 ファイルにソースフォルダが増える | プロジェクトごとに 1 ファイル。読み手が複数のファイルを順に読む |
| 型・メソッドの同一性 | JDT が 1 つの世界として解決する | 完全修飾名・記号表の 4 列で結合する（番号はブロックの中で閉じているので結合に要らない） |
| 相手に要るもの | ソースだけ | 設定ファイル（または自動判定できるプロジェクト構成）とキャッシュ。無ければ相手の設定で 1 回解析する |
| 弱点 | 依存 jar の版の衝突（和集合）。同じ型を二重に宣言できない | 相手が古い `bin` に対して解析していると名前が合わない（版ずれ）。相手のキャッシュの鮮度 |
| 前例 | マルチモジュール（`test/maven-multi`） | 差分更新（ブロックの書き写し）が「番号はブロックの中だけ」に依っている |

当初はモデル A を本線にしていたが、**値グラフの結合を心配したのが杞憂だった**（ノードの番号はブロックの中で閉じている）
ので、クラスパスを分けられるモデル B に改めた。結合の層は「複数のキャッシュを順に読んで同じ記号表に取り込む」だけで、
`CallGraphBuilder#build(List<Source>, …)` に収まった。

キャッシュのどの要素が名前でつながるか:

| キャッシュの要素 | 中身 | 別のキャッシュとつなぐ鍵 |
|---|---|---|
| メソッド（S 行の記号表） | `pkg・typeFqn・名前・引数のシグネチャ` の 4 列。番号は**ブロックの中だけ**で通じる | 4 列そのもの（`MethodRef`） |
| 型（H 行） | 完全修飾名、親型の完全修飾名、親クラスの連鎖 | 完全修飾名 |
| 呼び出し（C 行）・上書き（O 行）・継承した実装（H 行 8 列目） | メソッドの記号 | 同上 |
| 値グラフ（N 行）・条件（G 行） | ブロックの中の番号 | **結合不要** |

相手を相手自身の `project.root` として解析したとき、この実行の `project.root` の型は相手のクラスパス（`bin` や jar）から
解決された「jar の型」として記録される。相手の C 行の呼び出し先はこの実行のメソッドを 4 列の名前で指し、相手のクラスが
この実行のインターフェースを実装していれば H 行の親型にその完全修飾名が入る。これをこの実行のキャッシュ（同じメソッドを
4 列の名前で宣言し、H 行を持つ）と名前で突き合わせれば、辺も型階層も上書きもつながる。

### 3.2 設定

```properties
workspace.projects=../app-batch,../app-web/config/jche.properties
workspace.scope=callers
```

- `workspace.projects` の各要素は、相手の**設定ファイル**（`source.folders` / `library.*` / `source.encoding` をそこから読む）か、
  相手の**フォルダ**（`project.root` だけを書いた設定として読み、`.classpath` の `kind="src"` / `"lib"`、pom.xml /
  build.gradle、無ければ `src/main/java` → `src` で中身を決める）。起点は `project.root` と同じく設定ファイルのフォルダで、
  配下の制限は掛けない（`Config#forWorkspaceProject`）
- フォルダの形では、キャッシュの置き場所（`cache.folder`）・ローカルリポジトリ・ビルドツールの指定だけをこの設定から引き継ぐ。
  相手の設定ファイルの `message.language` は読み終えたら元に戻し、相手の `workspace.projects` は辿らない
- 参照元（`project.root` を呼ぶ側）でも依存先（`project.root` が依存する側）でもよい。仕組みは同じ（キャッシュが増えるだけ）
- `workspace.scope` は `callers`（既定）か `all`

### 3.3 解析（フェーズ 1）と結合（フェーズ 2）

- **錠**: この実行自身と相手のキャッシュのフォルダの錠（`CacheLock`）を、キャッシュのパスの順にすべて取ってから、
  相手のフェーズ 1 → 自分のフェーズ 1 → グラフの構築まで持つ（`Exporter#acquireLocks`）。2 つの実行が互いを相手に
  指していても、同じ順で取れば行き違いにならない。相手のプラグインのサーバーが書いている最中に読まない
- **相手のフェーズ 1**: 相手の設定で `CacheUpdater` を走らせる（差分更新なので普段は速い）。相手のコンパイルエラーの一覧は、
  パスに `../app-batch/` を前置してこの実行の `warnings.txt` に載せる
- **パスの形**: 相手のファイルは、グラフと出力（`methods.csv` の `file`、サーバーの R 行の `file`、`AT` のパス）で
  この実行の `project.root` からの相対パス（`../app-batch/src/...`。`WorkspaceProject#prefix`）になる。相対にできない
  （Windows の別ドライブ）ときだけ絶対パス。相手のキャッシュの中身（F 行）は相手の `project.root` からの相対のままで、
  読むときに前置する。読み手（出力・`AT`・プラグインがファイルを開く処理）は「`project.root` と連結して正規化する」
  今までの読み方のまま届く。**キャッシュの形式は変えていない**（`CacheFormat.VERSION` はそのまま）
- **ソースフォルダの並び**: この実行の `project.root` のフォルダを先に、次に `workspace.projects` を書いた順。出力の行順と、
  同じ型を 2 つのファイルが宣言したときの勝ち負け（`project.root` が勝つ）はこの並びで決まる
- **同じ型の二重宣言**: 今の `graph.duplicateType` の警告がそのまま効く（相手のファイルは `../` 付きのパスで挙がる）
- **DI・値・ライブラリ呼び出し規則**: グラフが 1 つになるので、相手の `@Bean` がこの実行のインターフェースに実装を注入する形も、
  フィールドへの代入の集まりも、全体で確定する

### 3.4 選択と出力（フェーズ 2・3）

- **起点**: 全体モードの起点は「呼び出し元の無いメソッド」のまま。相手からしか呼ばれない自分のメソッドは起点でなくなり、
  その行は相手の起点から始まる階層の中に出る
- **`workspace.scope=callers`（既定）**: 相手のメソッドは、**そこから `project.root` のメソッドに届く経路の上にあるときだけ**
  起点にし、階層に降り、`methods.csv` に載せる。判定は `project.root` の全メソッドを根にした**呼び出し元の向きの到達集合**
  （解決後の辺の転置索引 `InboundIndex` を逆に辿る。ライブラリ呼び出し規則で呼び戻される側（`Thread#start()` → `run()`、
  `forEach` に渡したラムダの本体）も辺に数える。入次数・到達の判定と同じ辺の集合で、規則を落とすと規則でしか
  `project.root` に届かない相手の起点が静かに消える。`WorkspaceScope#callers`）を 1 回求めて引く。
  絞るのは**経路が `project.root` のメソッドに届くまでの間だけ**（`PathFrame#mainSeen`。除外パッケージの読み飛ばしと
  ラムダの畳み込みで枠を差し替えるときも引き継ぐ）で、届いた後の呼び出し先
  （依存先のプロジェクトの中への展開、自分のインターフェースの実装が依存先にある形）は絞らない。
  `methods.csv` には、届くものに加えて階層に出た相手のメソッド（降りた先の実装）も載せる（階層に出た行は必ず一覧にもある）。
  **解決（CHA の候補・データフロー・DI・規則）には一切使わない**（絞るのは出す行だけ。解決は全体で行う）
- **`workspace.scope=all`**: 絞らない
- **`call-hierarchy.csv`**: 列は変えない。相手の行も通常の行（`caller` はスタックトレース形式、`root` は起点）。どのプロジェクトの
  行かは `methods.csv` の `file` 列の `../` の前置きで分かる。`project` 列は足していない（`file` 列で分かり、足すと回帰テストの
  期待値がすべて変わる）
- **jar の被参照（`external.library.folders`）**: 「自分の型」は結合した全ソースの型のまま。相手の jar が `dist` に混ざっていても
  「他リポジトリからの被参照」としては数えない（自己除外と同じ）

### 3.5 解析サーバーとプラグイン

- **サーバー**（実装済み）: `ANALYZE` は設定ファイルを受けるだけ。`AT` / `FIELDAT` は相手の `project.root` 配下の絶対パスも受け、
  グラフの綴り（`../app-batch/...`）に直す。`FIELDAT` は相手のファイルなら相手のキャッシュ（と相手のキャッシュの印）から引く。
  R 行の `file` は `../` 付きで、プラグインは今までどおり `root` と連結して開く
- **Eclipse / VSCode プラグイン**（段階 2。実装済み）: **既定では相手を解析しない。** ワークスペース全体の AST 解析は費用（時間・
  子プロセスのメモリ）が大きく、利用者が明示したときだけ行う。明示のしかたは「設定ファイルに書く」の 1 つに統一する:
  - 解析が読むのは**設定ファイルの `workspace.projects` だけ**。プラグインの自動生成（③ 設定ファイルが無いときの生成）は
    `workspace.projects` を書かず、画面の状態（チェック・ラジオ）で解析の範囲を変えることもしない。何で解析したかの正本は
    常に 1 つ（`run.log` に複製される設定ファイル）で、CLI で同じ設定を使えば同じ結果になる
  - プラグインが見つけた `config/jche.properties` に `workspace.projects` があれば、段階 1 の実装でそのまま相手まで伸びる
    （追加の実装は要らない）
  - ［解析に使う設定…］（`ConfigDialog`）に**［ワークスペースの参照元・依存先を `workspace.projects` に書き足す…］**を足す
    （実装: 候補を集める `WorkspaceReferences`、選ぶ `WorkspaceProjectsDialog`、読み書きする `WorkspaceProjectsConfig`）。
    押すと、対象プロジェクトを参照している（解決済みクラスパスに対象への `CPE_PROJECT` を持つ。推移的に固定点まで）
    プロジェクトと、対象が参照しているプロジェクトを集め、チェック付きの一覧（参照元／依存先の別と場所）で見せる。
    ［書き足す］で、設定ファイル（無ければ［保存して編集］と同じ手順で `config/jche.properties` を作る）の
    `workspace.projects=` にチェックしたプロジェクトを設定ファイルのフォルダからの相対パス（`../app-batch`）で書き、
    既にある行は差し替える。書いた内容はダイアログの「内容」にそのまま出る
  - 対象バーの「設定: …」のツールチップに、設定ファイルの `workspace.projects` の件数（見つからない指定があればその旨）を出す。
    参照元・依存先が増えたときの更新も同じボタン（上書き）で、自動では追従しない
  - ⚠（解析後に変わったファイル）は、設定ファイルの `workspace.projects` が指すプロジェクトの資源変更も見る
    （`AnalysisService#resourceChanged` の振り分けを「そのプロジェクトを `workspace.projects` に持つ `ProjectAnalysis`」にも広げる）
  - エディタのカーソルから入るとき（`ShowCallersHandler`・◎）、カーソルのファイルのプロジェクトが、いま表示中の対象の
    `workspace.projects` に入っていれば対象を切り替えず、その解析結果から引く（`FIND` はキー、`AT` はパスで引けるので、
    相手のファイルでも届く）
  - VSCode は参照関係を知らないので、コマンド「ワークスペースの他のフォルダを `workspace.projects` に書き足す」で
    ワークスペースの他のフォルダを複数選択（QuickPick）して設定ファイルに書く（`vscode-plugin/src/workspaceProjects.ts`。
    読み方は本体の設定ファイルの読み方と同じで、`test/vscode` が見る）。設定項目（`jche.workspaceProjects`）は置かない。
    相手のフォルダの `*.java` の変更も ⚠ にし、カーソルのフォルダが表示中の木の `workspace.projects` に入っていれば
    そのセッションから引く

### 3.6 段階 0: クラスフォルダの被参照（見送り）

`external.library.folders` にクラスフォルダ（Eclipse の `bin`、`target/classes`）を書いたとき、jar と同じ走査をする案。
`workspace.projects` が入ったことで、ソースのある相手は相手のキャッシュを結合する形（相手の起点まで辿れ、相手の実装が
候補に入る）が `bin` 経由の 1 段の被参照の上位互換になり、ソースの無い相手は今までどおり jar を `external.library.folders`
に置けば足りる。`bin` を直接読む形は、その間を埋めるものとして要らなくなったので見送る（Q12）。

### 3.7 対応しないこと・限界

- 相手が古い `bin` / jar に対して解析していると、相手の呼び出し先の名前が今のソースと合わず、辺がつながらない
  （`external-ref:MISSING_NOARG_CTOR` と同じ性質の版ずれ）。相手の `bin` をビルドし直してから解析し直す。検出と案内は今後の課題
- 相手のキャッシュの鮮度は、この実行が相手のフェーズ 1 を走らせることで保つ。読むだけにする指定は無い
- 相手の `workspace.projects` は辿らない（A ← B ← C の C は自分の設定に並べる）
- 同じ完全修飾名の型を 2 つのプロジェクトに持つ形は警告して、並びで先（`project.root`）を採る
- `test/incremental` に相当する「相手のソースを書き換えたあとの差分更新が全件解析と同じ」検査は、相手の差分更新が
  今の `CacheUpdater` そのもの（設定が違うだけ）なので別に持たない。結合の検査は `test/regression` の `workspace`
  （再利用・`all`・設定ファイルの形）

## 5. 迷ったこと（Q&A）

### Q1. jar の被参照（`external.library.folders`）の延長として「ソースも読む被参照」にしないのはなぜか

被参照の行は「1 段・起点無し・`root` は参照元の名前」という独立した形で、呼び出し階層とは意味が違う。
欲しいのは「他のプロジェクトの起点まで辿る」ことで、それは呼び出し階層そのものである。jar の被参照は「ソースの無い相手」の
道具として残し、ソースのある相手は解析の単位に入れる。

### Q2. `project.root` を複数にする（`project.roots=`）形にしないのはなぜか

`project.root` は相対パスの起点・キャッシュと出力のフォルダ名・`file` 列の起点・サーバーの `AT` の起点で、「主役」が 1 つで
あることに多くの約束が乗っている。ワークスペースの用途でも主役は 1 つ（影響調査の対象）で、他のプロジェクトは「そこへ届く
呼び出し元」「そこから降りる依存先」として見たいので、主役を `project.root` のまま、相手を `workspace.projects` に分ける。
`scope=callers` の既定もこの非対称から自然に出る。

### Q3. `workspace.scope` の既定を `callers` にするのはなぜか

Eclipse の参照検索・呼び出し階層は「このメソッドに届く経路」だけを見せる。全体モードで他プロジェクトの階層を全部出すと、
相手の自分に関係ない全起点の階層が CSV に混ざり、影響調査の答えが薄まる。`all` も残すのは、「ワークスペースをまとめて
1 つとして棚卸しする」用途を塞がないため。

### Q4. 絞り込みは「呼び出しを静かに落とす」にならないか

ならない。落とすのは「相手のメソッドで、そこから `project.root` のどのメソッドにも届かず、`project.root` から降りた先でもないもの」
だけで、それは定義上 `project.root` の影響調査の答えに含まれない。経路の上のノードはすべて到達集合に入るので、届く経路は
途中で切れない。解決には集合を使わず、全体で行う。絞るのは出す行だけである。
相手のメソッドの呼び出し先のうち、自分に届かないもの（`BatchJob.run` が呼ぶ `Helper.log`）はその経路では出ない。
`project.root` のメソッドから降りて届いたとき（`RemoteDao.findById` → `Helper.log`）は出る。

### Q5. `file` 列を `..` を含む相対パスにし、ラベル付き（`app-batch:src/...`）にしないのはなぜか

F 行の読み手・`AT` のパスの照合・プラグインの `EditorOpener` は「`project.root` と連結して正規化する」の 1 つの約束で動いている。
`..` はこの約束のまま通る。ラベルは 3 か所に新しい文法を持ち込み、VSCode 側にも同じ読み手が要る。
別ドライブで相対にできないときだけ絶対パスにするのは、Eclipse プラグインの生成する設定が元から絶対パスなのと同じ割り切り。

### Q6. 依存先（ビルド・パスの「プロジェクト」参照）も `workspace.projects` に入れるのはなぜか

依存先を `bin` で渡す形には 2 つの穴がある。依存先のメソッドは本体が無い（D 行が無い）ので呼び出し先として名前が出るだけで中を
展開できず、依存先にある自分のインターフェースの実装は CHA の候補に入らない。どちらも相手のキャッシュを結合すれば消える。
仕組みは参照元とまったく同じなので項目を分けず、`scope=callers` の絞り込みだけを「`project.root` に届くまで」に限って
依存先の展開を落とさないようにした。

### Q7. なぜモデル A（ソースを 1 つの解析に入れる）を本線にしなかったか

当初はモデル A を選んでいた（結合の層が大きいと見たため）。その見立ては値グラフの結合を心配したもので、キャッシュの番号が
ブロックの中で閉じている以上、結合は名前の突き合わせだけで済む。名前で結合できるなら、クラスパスを分けられる
モデル B のほうが筋がよい。モデル A は「共通の親フォルダに並べる」形として今でも動くので、相手に設定もキャッシュも無いときの
代替として残す。

### Q8. 相手のキャッシュは「読むだけ」にせず、この実行が相手のフェーズ 1 を走らせるのはなぜか

相手のキャッシュは相手が解析したときのもので、相手のソースが変わっていれば古い。相手の設定が分かる（設定ファイルを指すか、
フォルダから組む）ので、この実行の中で相手の差分更新を先に走らせれば、鮮度の問題が消える。差分更新なので普段は速い。
「読むだけ」の指定は、古い結果を正しいものとして出す経路になるので置かない。

### Q9. Eclipse のような名前の索引（構文だけの全件読み取り → 候補を絞って型解決）にしないのはなぜか

相手のキャッシュがあるなら、それが「解決済みの索引」そのものである。結合は TSV を読むだけで型解決は走らない。
相手のキャッシュが無いときだけ相手のフェーズ 1 を 1 回走らせるが、それは相手がこのツールを使っていれば済んでいる作業である。
名前の索引で候補を絞って都度型解決する遅延の仕組みは、相手のキャッシュを持たない前提でだけ意味があり、要らなくなった。

### Q10. `methods.csv` に `project` 列を足さないのはなぜか

`file` 列の `../app-batch/` の前置きでプロジェクトが分かる（Excel の「で始まる」で絞れる）。列を足すと `methods.csv` を比べる
すべての回帰テストの期待値が変わる。`call-hierarchy.csv` に `root` の左に `project` 列を足す案も同じ理由で見送った
（[call-hierarchy-columns-qa.md](call-hierarchy-columns-qa.md)）。

### Q11. プラグインの段階 2 で、ラジオボタンや［ワークスペースを解析する］ボタンではなく「設定ファイルに書く」にしたのはなぜか

3 つを比べた。

| 案 | 中身 | 問題 |
|---|---|---|
| ラジオ／チェック（対象バー） | 画面の状態で、生成する設定に `workspace.projects` を足す | 「何で解析したか」の正本が設定ファイルと画面の状態の 2 つになる。設定ファイルがあるとき（②）に画面の状態が勝つのか負けるのかを決めて説明しなければならず、`run.log` の設定の複製と結果が食い違う。状態はプロジェクトごとに覚える必要があり、Eclipse を立ち上げ直すと消えるか、残って意図せず全体解析が走る |
| ［ワークスペースを解析する］ボタン | 1 回だけ相手を足した設定で解析する | ［再解析］（⟳）が「同じ解析をやり直す」ものなので、どちらの設定で解析したかを結局は状態として持つ。設定ファイルがあるときは、その中身に相手を足した一時の設定を作ることになり、正本が 2 つになるのは同じ |
| **設定ファイルに書く（採用）** | ダイアログのボタンで参照元・依存先を集め、`config/jche.properties` の `workspace.projects` に書く。解析はファイルだけを読む | 正本が 1 つ（設定ファイル）。明示の操作が要る（既定では走らない）。ファイルに残るので、CLI・GitHub Actions でも同じ設定で同じ結果になり、チームで共有できる。費用はプロジェクトに設定ファイルを置くことだが、［保存して編集］で既にある手順 |

プラグインの方針（画面の状態で勝手に振る舞いを変えない。[eclipse-plugin-ui-simplify-qa.md](eclipse-plugin-ui-simplify-qa.md)）
とも合う。自動生成の設定に `workspace.projects` を入れないのは、ワークスペースを開いただけで全体の AST 解析が走る経路を
作らないため。

### Q12. 段階 0（`external.library.folders` にクラスフォルダ）を見送ったのはなぜか

Eclipse のプロジェクト参照は相手の `bin`（class）を読む形で、段階 0 はそれを被参照の走査に流用して「jar に固めなくても
1 段の被参照が出る」ようにする案だった。`workspace.projects` が入ると、ソースのある相手については相手のキャッシュを結合する
ほうが上位互換になる（1 段ではなく相手の起点まで辿れ、相手にある実装が CHA の候補に入り、ビューにも出る）。
ソースの無い相手（他チームの配布物）は今までどおり jar を `external.library.folders` に置けば読める。
`bin` を直接読む形は、この 2 つの間を埋める中途半端な位置になるので、要望が出るまで作らない。
