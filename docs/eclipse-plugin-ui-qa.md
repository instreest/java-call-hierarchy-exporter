# 呼び出し元階層ビューの実装 — QA 一覧

[Issue #49](https://github.com/instreest/java-call-hierarchy-exporter/issues/49) の続きとして、
[eclipse-plugin-ui-design.md](eclipse-plugin-ui-design.md) の設計案を実装したときに、
迷ったこと・設計案から変えたことを Q&A で残す。

実装したもの:

- 解析結果（`AnalysisSnapshot`）をプラグインが常駐で持つ。UI はロックを取らずに読む
- 呼び出し元ツリー（主ユースケース）と、向きを変えた呼び出し先ツリー
- 絞り込み（文字列・深さ・テスト除外・推測の除外・exclude.packages・呼び出し元の重複）
- 変更検知と自動再解析（ビルド後に静止してから）、バナー・⚠アイコン・ツールチップの3段階表示
- 画面の木をそのまま CSV に書き出す

設計案から変えた点は Q1（追従とピン留めをやめた）と Q2（外部 jar からの被参照は未実装）。

---

### Q1. エディタの選択に追従する案とピン留めをやめたのはなぜか

「選んだメソッドの呼び出し元を見る」は、**明示のコマンド**（右クリック、または `Ctrl+Alt+Shift+H`）
だけにした。カーソルを動かすたびに木が作り直されると、見比べている最中に表示が飛ぶ。
Eclipse 標準の呼び出し階層も追従しない。追従しないなら、追従を止めるためのピン留めも要らない。

結果としてビューの状態は「いま指定されているメソッド1つ」だけになり、
解析し直したときの復元も単純になった（Q3）。

### Q2. 外部 jar からの被参照（⧉）を出していないのはなぜか

まだ実装していない。既存の `ExternalUsageScanner` は結果を CSV ライターへ直接書く作りで、
メモリ上のグラフには載らない。ビューへ出すには「書き出し先の抽象化」か
「被参照をスナップショットへ取り込む」かのどちらかが要る。
本筋（ソース内の呼び出し元）を先に動かすため、ここは次の段階に回した。
設定ファイルからの CSV 出力では今までどおり出る。

### Q3. 解析し直すとメソッドIDが変わるが、表示中の木はどうするか

ビューが覚えているのは Eclipse 側の `IMethod` で、メソッドIDではない。
スナップショットが差し替わるたびに ID を引き直す（`MethodKeys.find`）。
IDは解析ごとに変わるため、覚えていると別のメソッドを表示してしまう。

引き直せなかったとき（新規メソッド、解析前）は、空の木ではなく
「このメソッドは 10:31:04 時点の解析結果にありません」とバナーに出す。
空の木は「呼び出し元が無い」と読み違えられるので、出してはいけない。

### Q4. 「一致した子孫を持つ枝だけ残す」をどう安く実現したか

絞り込み文字列に一致したメソッドの集合から、**呼び出し先の向きに到達できるメソッド**を
1回だけ求めて（既存の `CallResolver.reachableFrom`）、その集合に入っている行を残している。
「x が c の（間接的な）呼び出し元」ということは「c は x から呼び出し先をたどって到達できる」なので、
これで「その先に一致がある枝」を落とさずに済む。計算はグラフ全体を2回舐めるだけで、
フィルタ文字列を変えたときに1度だけ走る。

打鍵のたびに走らせないよう、入力が止まってから 250 ミリ秒後にまとめて作り直す。

呼び出し先の向きのときは、この理屈が逆になって同じ手が使えない（逆向きの到達可能性が要る）。
その向きでは一致した行だけを絞り込みの対象にしている。主ユースケースは呼び出し元なので、
そちらを優先した。

### Q5. 解析ジョブのスケジューリング規則に、プロジェクトそのものを使わなかったのはなぜか

プロジェクトやワークスペースを規則にすると、解析中は保存もビルドも待たされる。
「他の処理をロックしない」という要件に反するので、**自分自身としか衝突しない規則**を
プロジェクトごとに1つ持たせた。これで「同じプロジェクトの解析は直列、別プロジェクトは並列、
他の作業は止めない」になる。

解析は読み取りしかしない（書くのはワークスペース外のキャッシュだけ）ので、
ワークスペースのロックはそもそも要らない。

### Q6. 進捗と中止を、解析本体にどう伝えたか

`jche` 側を Eclipse に依存させたくないので、`jche.util.RunControl` という
小さな受け口を足した。付けるのは呼び出し側で、CLI は何も付けない（今までどおり）。

受け口は **スレッドごと**（`ThreadLocal`）に持つ。静的な1個だと、
2つのプロジェクトを同時に解析したときに進捗と中止が混ざる。

中止の確認はフェーズ1のバッチの切れ目とフェーズ2の走査中に置いた。どちらも
キャッシュをテンポラリに書いている途中なので、放り出しても既存のキャッシュは壊れない。
中止は失敗ではないので、専用の `CancelledException` で区別して
Job は `CANCEL_STATUS` で終わる。

### Q7. SWT の依存に Linux 用の断片を書いてあるのはなぜか

`org.eclipse.platform:org.eclipse.swt` には `Composite` などの実クラスが入っておらず、
実体はプラットフォームごとの断片（fragment）にある。Maven でのビルドは
「Eclipse 無しでコンパイルが通るか」を確かめるためのものなので、断片を1つだけ足せばよい。
API はどの断片でも同じなので、Windows で `mvn package` しても結果は変わらない。
実行時に使われるのは Eclipse 本体の断片で、この依存は jar には入らない（provided）。

### Q8. 転置索引はいつ作るか

解析ジョブの中（`AnalysisSnapshot.inbound()` の初回呼び出し）で作る。
ビューを開いた瞬間に UI スレッドで作られると、その間だけ画面が固まるため。
CSV 出力しか使わない CLI では作られない。

### Q9. 転置索引を「数えてから書く」2パスで作らなかったのはなぜか

`CallResolver.resolve(edgeIndex)` が、**同じエッジでも初回と2回目で違う答えを返すこと**が
あるためである。実装しながら `test/demo` で気づいた。データフローによる解決に使う情報が、
他のエッジを解決する過程で埋まるので、たとえば次のようになる。

```
edge 34  fx.app.Main#run(String[]) -> fx.dao.Dao#describe()
  1回目 = [OrderDaoImpl#describe, UserDaoImpl#describe]  CHA
  2回目 = [UserDaoImpl#describe]                          DATAFLOW_FACTORY
```

CSR を「1回目に本数を数え、2回目に書き込む」作りにすると、この差で本数が食い違い、
書き込み位置が隣の範囲へずれて索引が静かに壊れる。そこで
**3つ組（呼び出し先・呼び出し元・エッジ）を1回の走査で集めてから計数ソートで並べる**形にした。
数える回と書く回が同じ結果を見るので、resolve が何を返しても壊れない。

さらに索引を作る前に全エッジを1度解決して落ち着かせている（`warmUp`）。そうしないと、
索引に入った呼び出し関係と、画面が後から表示する解決の理由（`resolutionLabel`）が
食い違う（上の例なら、消えたはずの `OrderDaoImpl` が呼び出し元の一覧に残る）。

この「解決が事実の在庫を副作用で育てる」構造そのものを直す案は
[dataflow-phase-proposal.md](dataflow-phase-proposal.md) にまとめた（データフローを独立した
フェーズにして、resolve を純粋な関数にする）。そちらを入れれば `warmUp` は不要になる。

なお、CSV 出力はこの影響を受けていない。走査の順番が固定なので、毎回同じ順で同じ結果になる
（回帰テストの期待値どおり）。ただし「resolve は決定的」という前提でコードを足すと危ないので、
ここに残しておく。

### Q10. ツリーの子はどこまで先に計算するか

開いたノードの1階層ぶんだけ。CSR の配列を範囲で舐めるだけなので、
「そのメソッドの呼び出し元の数」に比例した時間しかかからない。
深さの上限（既定5）は打ち切りの位置を決めるだけで、先に計算はしない。
既に開いたノードの子は覚えておき、モデルが差し替わったら捨てる。

### Q11. 何を自動で検査しているか

`test/plugin/run.sh` に足したのは、版・ID・クラスの実在の突き合わせである
（plugin.xml の `class`／`defaultHandler`、`Bundle-Activator`、
コマンド ID とキーバインド、ビュー ID とソースの定数）。
これらは食い違っても**ビルドは通り、実行時に初めて壊れる**種類の間違いなので、
ファイルを読むだけの検査に価値がある。

画面操作そのもの（右クリック→ツリーが出る）は自動化していない。理由は
[eclipse-plugin-qa.md](eclipse-plugin-qa.md) の Q11 と同じで、
解析結果の正しさは CLI と同じコードなので `test/regression` が引き続き受け持つ。
