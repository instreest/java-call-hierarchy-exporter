# 呼び出し元階層ビューの実装 — QA 一覧

[Issue #49](https://github.com/instreest/java-call-hierarchy-exporter/issues/49) の続きとして、
[eclipse-plugin-ui-design.md](eclipse-plugin-ui-design.md) の設計案を実装したときに、
迷ったこと・設計案から変えたことを Q&A で残す。

実装したもの:

- 解析結果（`AnalysisSnapshot`）をプラグインが常駐で持つ。UI はロックを取らずに読む
- 呼び出し元ツリー（主ユースケース）と、向きを変えた呼び出し先ツリー
- 絞り込み（文字列・深さ・テスト除外・推測の除外・exclude.packages・呼び出し元の重複）
- 変更検知と自動再解析（ビルド後に静止してから）、バナー・⚠アイコン・ツールチップの3段階表示
- 画面の木をそのまま CSV に書き出す

設計案から変えた点は Q1（追従とピン留めをやめた）と Q2（外部 jar からの被参照は未実装）。

---

### Q1. エディタの選択に追従する案とピン留めをやめたのはなぜか

「選んだメソッドの呼び出し元を見る」は、**明示のコマンド**（右クリック、または `Ctrl+Alt+Shift+H`）
だけにした。カーソルを動かすたびに木が作り直されると、見比べている最中に表示が飛ぶ。
Eclipse 標準の呼び出し階層も追従しない。追従しないなら、追従を止めるためのピン留めも要らない。

結果としてビューの状態は「いま指定されているメソッド1つ」だけになり、
解析し直したときの復元も単純になった（Q3）。

### Q2. 外部 jar からの被参照（⧉）を出していないのはなぜか

まだ実装していない。既存の `ExternalUsageScanner` は結果を CSV ライターへ直接書く作りで、
メモリ上のグラフには載らない。ビューへ出すには「書き出し先の抽象化」か
「被参照をスナップショットへ取り込む」かのどちらかが要る。
本筋（ソース内の呼び出し元）を先に動かすため、ここは次の段階に回した。
設定ファイルからの CSV 出力では今までどおり出る。

### Q3. 解析し直すとメソッドIDが変わるが、表示中の木はどうするか

ビューが覚えているのは Eclipse 側の `IMethod` で、メソッドIDではない。
スナップショットが差し替わるたびに ID を引き直す（`MethodKeys.find`）。
IDは解析ごとに変わるため、覚えていると別のメソッドを表示してしまう。

引き直せなかったとき（新規メソッド、解析前）は、空の木ではなく
「このメソッドは 10:31:04 時点の解析結果にありません」とバナーに出す。
空の木は「呼び出し元が無い」と読み違えられるので、出してはいけない。

### Q4. 「一致した子孫を持つ枝だけ残す」をどう安く実現したか

絞り込み文字列に一致したメソッドの集合から、**呼び出し先の向きに到達できるメソッド**を
1回だけ求めて（既存の `CallResolver.reachableFrom`）、その集合に入っている行を残している。
「x が c の（間接的な）呼び出し元」ということは「c は x から呼び出し先をたどって到達できる」なので、
これで「その先に一致がある枝」を落とさずに済む。計算はグラフ全体を2回舐めるだけで、
フィルタ文字列を変えたときに1度だけ走る。

打鍵のたびに走らせないよう、入力が止まってから 250 ミリ秒後にまとめて作り直す。

呼び出し先の向きのときは、この理屈が逆になって同じ手が使えない（逆向きの到達可能性が要る）。
その向きでは一致した行だけを絞り込みの対象にしている。主ユースケースは呼び出し元なので、
そちらを優先した。

### Q5. 解析ジョブのスケジューリング規則に、プロジェクトそのものを使わなかったのはなぜか

プロジェクトやワークスペースを規則にすると、解析中は保存もビルドも待たされる。
「他の処理をロックしない」という要件に反するので、**自分自身としか衝突しない規則**を
プロジェクトごとに1つ持たせた。これで「同じプロジェクトの解析は直列、別プロジェクトは並列、
他の作業は止めない」になる。

解析は読み取りしかしない（書くのはワークスペース外のキャッシュだけ）ので、
ワークスペースのロックはそもそも要らない。

### Q6. 進捗と中止を、解析本体にどう伝えたか

`jche` 側を Eclipse に依存させたくないので、`jche.util.RunControl` という
小さな受け口を足した。付けるのは呼び出し側で、CLI は何も付けない（今までどおり）。

受け口は **スレッドごと**（`ThreadLocal`）に持つ。静的な1個だと、
2つのプロジェクトを同時に解析したときに進捗と中止が混ざる。

中止の確認はフェーズ1のバッチの切れ目とフェーズ2の走査中に置いた。どちらも
キャッシュをテンポラリに書いている途中なので、放り出しても既存のキャッシュは壊れない。
中止は失敗ではないので、専用の `CancelledException` で区別して
Job は `CANCEL_STATUS` で終わる。

### Q7. SWT の依存に Linux 用の断片を書いてあるのはなぜか

`org.eclipse.platform:org.eclipse.swt` には `Composite` などの実クラスが入っておらず、
実体はプラットフォームごとの断片（fragment）にある。Maven でのビルドは
「Eclipse 無しでコンパイルが通るか」を確かめるためのものなので、断片を1つだけ足せばよい。
API はどの断片でも同じなので、Windows で `mvn package` しても結果は変わらない。
実行時に使われるのは Eclipse 本体の断片で、この依存は jar には入らない（provided）。

### Q8. 転置索引はいつ作るか

解析ジョブの中（`AnalysisSnapshot.inbound()` の初回呼び出し）で作る。
ビューを開いた瞬間に UI スレッドで作られると、その間だけ画面が固まるため。
CSV 出力しか使わない CLI では作られない。

### Q9. 転置索引を「数えてから書く」2パスで作らなかったのはなぜか

`CallResolver.resolve(edgeIndex)` が、**同じエッジでも初回と2回目で違う答えを返すこと**が
あるためである。実装しながら `test/demo` で気づいた。データフローによる解決に使う情報が、
他のエッジを解決する過程で埋まるので、たとえば次のようになる。

```
edge 34  fx.app.Main#run(String[]) -> fx.dao.Dao#describe()
  1回目 = [OrderDaoImpl#describe, UserDaoImpl#describe]  CHA
  2回目 = [UserDaoImpl#describe]                          DATAFLOW_FACTORY
```

CSR を「1回目に本数を数え、2回目に書き込む」作りにすると、この差で本数が食い違い、
書き込み位置が隣の範囲へずれて索引が静かに壊れる。そこで
**3つ組（呼び出し先・呼び出し元・エッジ）を1回の走査で集めてから計数ソートで並べる**形にした。
数える回と書く回が同じ結果を見るので、resolve が何を返しても壊れない。

さらに索引を作る前に全エッジを1度解決して落ち着かせている（`warmUp`）。そうしないと、
索引に入った呼び出し関係と、画面が後から表示する解決の理由（`resolutionLabel`）が
食い違う（上の例なら、消えたはずの `OrderDaoImpl` が呼び出し元の一覧に残る）。

この「解決が事実の在庫を副作用で育てる」構造そのものを直す案は
[dataflow-phase-proposal.md](dataflow-phase-proposal.md) にまとめた（データフローを独立した
フェーズにして、resolve を純粋な関数にする）。そちらを入れれば `warmUp` は不要になる。

なお、CSV 出力はこの影響を受けていない。走査の順番が固定なので、毎回同じ順で同じ結果になる
（回帰テストの期待値どおり）。ただし「resolve は決定的」という前提でコードを足すと危ないので、
ここに残しておく。

### Q10. ツリーの子はどこまで先に計算するか

開いたノードの1階層ぶんだけ。CSR の配列を範囲で舐めるだけなので、
「そのメソッドの呼び出し元の数」に比例した時間しかかからない。
深さの上限（既定5）は打ち切りの位置を決めるだけで、先に計算はしない。
既に開いたノードの子は覚えておき、モデルが差し替わったら捨てる。

### Q11. 何を自動で検査しているか

`test/plugin/run.sh` に足したのは、版・ID・クラスの実在の突き合わせである
（plugin.xml の `class`／`defaultHandler`、`Bundle-Activator`、
コマンド ID とキーバインド、ビュー ID とソースの定数）。
これらは食い違っても**ビルドは通り、実行時に初めて壊れる**種類の間違いなので、
ファイルを読むだけの検査に価値がある。

GitHub Actions の `eclipse-plugin` ジョブは、JDT の**下限の版と最新版の2通り**でバンドル jar を組み立てる（Q12）。

画面操作そのもの（右クリック→ツリーが出る）は自動化していない。理由は
[eclipse-plugin-qa.md](eclipse-plugin-qa.md) の Q11 と同じで、
解析結果の正しさは CLI と同じコードなので `test/regression` が引き続き受け持つ。

## 導入してからの問題（Eclipse 側の版・設定ファイル）

### Q12. 「Eclipse の JDT が古いと入らない」をどう直したか

`Require-Bundle` の下限を、**コンパイルに使った版ではなく、実際に必要な最小の版**にした。

最初は下限を 3.46.0（`//DEPS` 行と同じ最新版）にしていたが、これは「コンパイルした版をそのまま
下限にした」だけで根拠が無く、少し古い Eclipse では何もせずに弾かれてしまう。
どこまで下げられるかは、版を変えてビルドして確かめた。

| JDT Core | Eclipse | 結果 |
|---|---|---|
| 3.28.0 以上 | 2021-12 以降 | ○ |
| **3.27.0** | **2021-09** | **○ ← ここが下限** |
| 3.26.0 | 2021-06 | ✗ `AST.getJLSLatest()` が無い |
| 3.24.0 | 2020-12 | ✗ 同上 |

採ったのは **3.27.0**（Eclipse 2021-09 相当）。API 上の限界そのものである。
Eclipse 本体を動かす JDK は版に関わらず 17 以上が要る（`Bundle-RequiredExecutionEnvironment:
JavaSE-17`。本体のソースが record・sealed・switch 式を使うため）。Eclipse 2021-09 は
Java 11 でも 17 でも動くので、**17 で起動すれば入る**。版の対応表は
[eclipse-pleiades-versions.md](eclipse-pleiades-versions.md) にまとめた。

大事なのは宣言だけで終わらせないことで、次の2つを併せて入れた。

- **下限の版でコンパイルする**（`eclipse-plugin/pom.xml` の `jdt.version` = 3.27.0）。
  それより新しい API を使った時点でビルドが落ちる
- **CI で下限と最新の両方をビルドする**（`eclipse-plugin` ジョブの matrix）。
  最新版は `//DEPS` 行から読むので、版の出どころは1か所のまま

この作業中に、依存の推移をすべて切っている副作用で `org.eclipse.equinox.registry`
（`IExecutableExtension` などが入っている）が JDT の版によって入ったり入らなかったりすることが
分かったので、明示的な依存に足した。下限でのビルドを試さなければ気づかない類の穴だった。

実行時に使われるのは Eclipse 側の JDT なので、新しい Eclipse では新しい版がそのまま使われる
（バイナリ互換）。古い JDT で起きるのは「動かない」ではなく「解析できる Java の版が下がる」だけで、
本体はすでに `source.level` を丸めてログに出す作りになっている。

### Q13. 「Eclipse の JDK が古い」問題にどう対処したか

JDT は**動いている JVM の標準クラス**を解析対象のクラスパスに含める
（`ASTParser.setEnvironment(..., includeRunningVMBootclasspath=true)`）。
プラグインでは Eclipse の JVM がそれになるため、jbang（`//JAVA 25`）とは結果が変わりうる。

対処は「隠さずに見えるようにする」ことにした。

- 解析ログに**実行 JVM の版**を出す（CLI も同じ。`Exporter.logAnalysisSettings`）
- ビューのバナーのツールチップに、**設定の出どころ・解析した Java の版・実行 JVM・JDT の版・
  その JDT が解析できる Java の上限**を出す（`EnvironmentInfo`）。結果の差はほぼこれで説明できる
- 利用者の対処は eclipse.ini の `-vm` で新しい JDK を指すこと。README に書いた

キャッシュは以前から `jdk=<版>` をヘッダに持っているので、JVM を変えれば自動で作り直される
（壊れた結果が残ることはない）。プラグインのキャッシュは CLI と別フォルダなので、
両方を使っても互いのキャッシュを潰し合わない。

**採らなかった案**: `includeRunningVMBootclasspath=false` にして解析対象の JDK を明示指定する。
JDK 9 以降は `jrt-fs` の扱いが要り、CLI の結果も変える大きな変更になる。
なお、自動生成した設定では**プロジェクトのクラスパス（JRE コンテナを解決したものを含む）**を
`library.jars` で渡しているので、その範囲では実行 JVM 以外の JDK のクラスも参照される。

### Q14. config.properties を必須にしないために何をしたか

Eclipse は必要な情報をすでに持っているので、**プロジェクトの構成から設定をその場で組み立てる**
（`EclipseProjectConfig`）。優先順位は次のとおり（`ConfigSource`）。

1. ビューで選んだ設定ファイル（「使う設定ファイルを選ぶ…」）
2. プロジェクト直下の `config.properties`
3. 自動生成（Java プロジェクトなら常に可能）

| 設定項目 | Eclipse 側の出どころ |
|---|---|
| `project.root` | プロジェクトの場所 |
| `source.folders` | クラスパスのソースフォルダ（プロジェクトの外のリンクは除いて警告） |
| `library.jars` | 解決済みクラスパスの jar と、依存プロジェクトの出力フォルダ |
| `source.encoding` | プロジェクトの文字コード |
| `source.level` | プロジェクトのコンパイラー準拠レベル |

本体側に足したのは2つだけで、どちらも設定ファイル経由と**同じ結果**になる。

- `Config(Properties, configDir, toolRoot, startedAt)` … ファイルを介さずに設定を作る。
  ファイル版はこれに委譲する。`configPath` は自動生成のとき null（javadoc に明記）
- `library.jars` … 依存 jar を1件ずつ指定する項目。Eclipse のクラスパスは jar が方々
  （`~/.m2` など）に散らばっていて、既存の `library.folders`（フォルダ単位）では表現できない。
  `library.folders` と `library.jars` がどちらも空のときだけ、従来どおりビルドファイルからの
  自動取得が働く

検証は、同じ `test/demo` を「設定ファイル経由」と「メモリ上の設定（プラグインと同じ形）」の
両方で解析し、メソッド数・エッジ数が一致することを確認した（149 メソッド / 201 エッジ）。

自動生成のままでは `entry.packages` などを細かく指定できないので、ビューのメニューに
「設定を config.properties に保存」を置いた。自動生成を出発点にして手で直せる。
また、設定を自動生成しているときはクラスパスの変更も解析の前提が変わることを意味するので、
変更検知の対象に `.classpath` を加えた。

### Q15. Eclipse が Java 11 で動いている環境に対応しないのはなぜか

対応できないわけではないが、**割に合わない**と判断した。

このプラグインは Eclipse と同じ JVM で動く。したがって Java 11 の Eclipse に入れるには、
**Eclipse の中で動くコードすべてを Java 11 の文法に落とす**必要がある。
`--release 11` でコンパイルして数えたところ、こうなった。

| 使っている機能 | 箇所 |
|---|---|
| record | 22 |
| switch のアロー構文・switch 式 | 12 |
| instanceof のパターン | 4 |
| sealed インタフェース | 1 |
| 合計（コンパイルエラー） | **53** |

分布も偏っていない。`jche.cache` は 18 ファイル中 15、プラグインの UI も 21 ファイル中 11 が
該当する。つまり局所的な修正では済まず、**キャッシュの「事実」を表す record 群を
すべて手書きのクラスに戻す**ことになる。読みやすさの低下は全利用者に効くのに、
得られるのは「2021〜2022 年の Eclipse を Java 11 のまま使っている環境」だけである。

代わりに案内する道は3つある。

1. **`-vm` で 17 以上の JDK を指す**（正攻法）。Pleiades なら同梱の新しい JDK が
   すでに手元にあることが多い（[eclipse-pleiades-versions.md](eclipse-pleiades-versions.md)）
2. **コマンドライン版を使う**。jbang は必要な JDK を自動で取得するので、
   手元の JDK が 11 だけでも動く（閉域なら JDK を1つ置いてもらう）
3. 将来 **フェーズ1を別プロセス・別 JDK で動かす**案を入れる場合、「Eclipse 内には
   薄い画面だけを置き、解析も含めて子プロセスに持たせる」形にすれば Java 11 でも
   動かせる余地はある。ただしそれは別 Issue の設計判断に含める話で、
   いまのように解析結果をプラグインが常駐で持つ作りのままでは解決しない

判断を変える材料があるとすれば「Java 11 でしか動かせない Eclipse を使い続ける必要がある」
という具体的な事情なので、そのときはこの Q を根拠ごと見直すこと。
