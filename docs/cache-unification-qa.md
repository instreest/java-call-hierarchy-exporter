# キャッシュを 1 ファイルにまとめる — 実装時の QA 一覧

（執筆中）

## 値をすべて値グラフのノードで持つ（形式 v33）

対応の要点:

- キャッシュの値は、どれも N 行（値グラフ）のノードを番号で指す。戻り値（R 行 `R 記号 node`）・フィールドへの
  代入（J 行 `J typeFqn field site node`）は出所の文字列をやめてノード番号にした（`-1` は「追跡できない」）
- 条件はブロックの表（G 行 `G ガード番号 op subject text 値1 値2 …`）にし、C 行・U 行はガード番号で指す。
  アトム 1 つにつき 1 行、subject はノード番号、値は後ろの列に 1 つずつで、切り詰めない
- new の証拠の X 行と、C 行・U 行の recvKey 列を無くした。書き手がファイルの中で結びつけた結果を
  C 行・U 行の hints 列（型の FQN のカンマ区切り）に書く
- ブロックの並びは `F I S N G R H D O V C/U M A K J`
- 読み手（`CallGraphBuilder`）は読む直前に以前と同じ文字列へ組み直す（R 行は丸ごと、J 行はノードの頭、
  条件は以前の guard 列の形）。R 行の値そのものがクラス名・識別子の形でない文字列リテラルなら、
  今の読み手が読み違えるので暫定で U として渡す（Q9）。`test/regression` の期待出力は変わっていない
  （組み直しと暫定の扱いは stage B で外した。読み手は値の表を読む。下の「読み手が値の表を読む」）
- R 行を書くかどうかを、return の式の型ではなく、囲むメソッド・ラムダの宣言の戻り値の型で決める（Q8）
- test/demo のキャッシュは 96,628 バイトから 90,711 バイトになった（このツール自身のソースでは
  2,592,398 バイトから 1,937,633 バイト。多くは C 行・U 行ごとの recvKey（長いバインディングキー）と、
  同じ条件の書き並べが無くなった分）

### Q1. なぜ R 行・J 行・条件もノードにするのか

呼び出し箇所の値は既にノードで持っていたが、R 行・J 行・条件は `OriginTracker` が作る出所の文字列のままで、
文字列の側にだけ上限（実引数は 1 段・レシーバは 3 段・文字列は 64 文字で識別子の形だけ）があった。
同じ式が、どこに書かれるかで細かさの違う 2 通りの表し方になっていた。すべてをノードにすれば表し方が 1 つになり、
読み手をノードで読む形に移すとき（次の段）に文字列の読み口を残さずに済む。

### Q2. 条件をなぜ別の行（G 行）の表にするのか

同じ分岐の中の呼び出しは同じ条件を持つので、呼び出しごとに書き並べると同じ文字列が何度も出る。
ブロックの表にして番号で指せば 1 回で済む。また、以前は値を区切り文字で並べていたので、
「値が 1 つも無い」と「空文字の値が 1 つ」を見分けられなかった（Q6）。値を列に 1 つずつ置けば、
値の中にどんな文字があっても区切りは崩れない。

### Q3. 条件の subject にはどのノードを通すのか

以前と同じく、引数（A）と定数（V）だけ。`nodeOf(unwrapValue(subject))` の種別で見る。違いは 2 つある。

- 定数フィールドを写したローカル変数（`int m = MODE;`）は、以前は出所の文字列が `F:` になって条件にならなかったが、
  ノードでは `V:3` になるので条件になる。呼び出し元へ渡す実引数としては以前から `V:3` だったので、揃った形になる。
  変数の値が 1 つに決まるのは、先読みで代入がすべて同じノードだったときだけ（書き換えがあれば「分からない」）
- 文字列のコンパイル時定数は、値グラフではリテラル（L）のノードになる。以前はここを定数（`V:`）として
  条件にしていたので、`OriginTracker.constantOf`（64 文字以内・制御文字を含まない）で拾える定数は V のノードを作る

メソッド呼び出し・new・定数でないフィールドなど、A にも V にもなりえない式のノードは作らない
（ノードは作ると消せず、どこからも指されない行が残るため）。

### Q4. 期待値を切り詰めないのに、なぜ出力が変わらないのか

以前の書き手は期待値を出所の文字列から取り出していた（`Origin.valueOf`）ので、最初の `|` で切れていた
（`"a|b"` が `"a"`）。G 行は値そのものを持つ。一方、読み手が経路の値（呼び出し元が渡した実引数・定数の subject）を
取り出すところは、まだ出所の文字列を通るので同じところで切れる。期待値だけを正確にすると、`"a|b"` を渡した
経路で `s.equals("a|b")` を「成立しない」と誤って判定する。そこで `GuardEvaluator` が期待値に以前の切り方
（`legacyCut`）を当てて、両方を同じ形にそろえる。読み手を値のまま比べる形に移すときに一緒に外す
（`test/pruning` の `PipeEq` / `PipeConst` が両方の組み合わせを見る）。

stage B で外した。`GuardEvaluator` は条件の表（`jche.graph.GuardTable`）の期待値と、値の表・経路の環境の
実際の値を、どちらも切り詰めずに値の番号で比べる（`test/regression/values` の `Pipe` も見る）。

### Q5. new の証拠を、なぜ C 行・U 行に直接持つのか

X 行は「呼び出し元のキー＋変数のキー」で、読み手がキャッシュ全体から集めて呼び出し箇所の recvKey に結びつけていた。
変数のキー（バインディングキー）はそのファイルの宣言を指すので、結びつけはファイルの中で閉じる。書き手が
ブロックを書くときに結びつければ、X 行も recvKey も要らない。変数でないレシーバの recvKey（`@位置`）は
X 行と一致することが無く、もともと使われていなかった。

1 つだけ違うのは、同じメソッドキーが 2 つのファイルにある（同じクラスが重複している）場合で、以前は両方の
ファイルの証拠が混ざっていたが、今はそれぞれのファイルの証拠がそれぞれの呼び出し箇所にだけ付く。

却下した案: 証拠を値グラフのノード（変数ごとの代入の集まり）にする。値グラフは代入が食い違えば「分からない」に
倒すが、証拠は食い違う new の型をすべて残す（`LOCAL_NEW_MULTI`）ので、1 つのノードに畳めない。

### Q6. `default` しか無い `switch` は、なぜ条件にしないのか

`switch (s) { default -> hit(); }` の `default` は必ず通る。以前は「どの case とも一致しない」（NI）を値なしで
書いていたが、値を区切り文字で並べる形では「値なし」が「空文字の値 1 つ」と同じ文字列になり、`sel("")` の経路で
`hit` を `[UNREACHABLE]` にしていた（この形式に移す前からの誤り）。条件ではないので、アトムを作らない
（`test/pruning` の `DefaultOnly`）。

条件の調査（`conditions.target` を書いたときの `call-conditions.csv`）も同じアトムから作るので、出方が変わる。
以前はこの呼び出しに `switch (s) default` の条件を「どの値とも一致しない（`∉ {}`）」として出していたが、
今は条件の無い呼び出しと同じく、その呼び出しの行の条件の列（`condIndex` 以降）が空になる。この `default` は
どの値でも通るので、条件として出していた方が誤りである。`case` が 1 つでもある `switch` の `default` は、
以前と同じく `∉ {case の値…}` の条件として出る。

### Q7. 何が変わるか

- R 行を組み直した文字列は、呼び出し箇所と同じく上限が無くなる（実引数の入れ子・レシーバ・`s=`）。ローカル変数は
  代入元のノードに畳まれる。`static final int` のフィールドは `F:` ではなく `V:` になる。
  `L:` も `V:` も戻り値の型は決めないが、読み手は「メソッドが返す値が 1 つに決まる」とき、その値を経路の値として
  使う（`DataflowResolver` の戻り値の文字列。条件の打ち切りと契約表のキー）。値そのものが識別子の形でない
  文字列は、今の読み手が出所の文法の文字で切ってしまうので、以前と同じく U として渡す（Q9）
- R 行を宣言の戻り値の型で書くようになったので（Q8）、`Object` を返すメソッドの `return "x";` も R 行になる。
  どの return も同じ識別子の形の文字列を返すメソッドでは、その値で条件を打ち切る（`test/pruning` の `LitRet`。
  メソッドは必ずその値を返すので、実際にも通らない）。値の食い違う return があれば値は決まらない
- J 行も同じく、識別子の形でない文字列が `L:`、`static final int` が `V:` になる。コンストラクタ注入の判定で
  「出所が一致する」フィールドが増えることがあるが、具象型に使うのは `T:` と `A:` だけ
- 条件は Q3 のとおり、定数フィールドを写したローカル変数と定数の式（`MODE + 1 == 5`）が条件になり、
  その値で成立しない呼び出しは `[UNREACHABLE]` になる（コンパイル時定数なので、実際にも通らない）
- 条件の調査（`call-conditions.csv`）も同じ条件を「判定できる」と出す。期待値は切り詰めずに出す。
  `default` しか無い `switch` の呼び出しには条件を出さない（Q6）

### Q8. R 行を書くかどうかを、なぜ宣言の戻り値の型で決めるのか

以前の書き手は、return の**式の型**がプリミティブ・配列・`String` なら、その return を R 行にしなかった。
すると `Object key(boolean b) { if (b) return "x"; Object v = "y z"; return v; }` の `return "x"` だけが抜け、
R 行は `v` の値 1 つになる。読み手は R 行の値が 1 つに決まれば「このメソッドは必ずその値を返す」と読むので、
`run((String) key(b))` の先の `if (s.equals("x")) hit();` を `[UNREACHABLE]` にしていた。

この誤りはこの形式に移す前からあった（残りの return が識別子の形の文字列 `"yz"` なら、以前も打ち切っていた）。
R 行を値グラフのノードで書くようになって、識別子の形でない `"y z"` も `L:` として残るようになり、当たる形が増えた。

そこで、囲むメソッドの宣言（ラムダなら関数型インターフェースのメソッド）の戻り値の型で決める。1 つのメソッドの
return はどれも同じ宣言から決まるので、全部記録するか、全部しないかのどちらかになり、一部だけ抜けることが無い。
宣言の型が `String` などのメソッドは、以前と同じく記録しない（具象クラスの絞り込みに使えない）。
宣言の型が引けないときは記録する。`void` のラムダの式本体（`() -> dao.save(x)`）は値を返さないので記録しなくなった
（以前は式の型で決めていたので、`save` の戻り値が R 行になっていた。読む者はいない）。

却下した案:

- 読み手の側（Q9 の暫定の扱い）だけで直す。識別子の形でない文字列は U になるので `"y z"` は直るが、`"yz"` の
  形は以前から誤っていたまま残る（`test/pruning` の `MixedRetId`）
- 式の型が `String` の return を U として書く。一部だけ抜けることは無くなるが、`Object key() { return "A"; }` の
  ように値が 1 つに決まるメソッドも「分からない」になり、書き方で結果が変わる

### Q9. R 行の文字列リテラルを、なぜ読むところで U にするのか（暫定）

**stage B で外した。** 読み手（`DataflowResolver`・`GuardEvaluator`・`FactoryCalls` など）が出所の文字列ではなく
値の表（`jche.graph.ValueStore`）を読み、値を切り詰めずに比べるようになったので、R 行の文字列リテラルも
そのまま読む。下の 3 つの検査はそのまま通り、`test/pruning` の `PipeRetEq`・`PipeRetSwitch`・`SemiRetKey`
（`|` `;` を含む戻り値で、正しく打ち切る・契約表の書いたとおりの行に当てる）を足した。以下は外す前の記録。

今の読み手は、組み直した出所の文字列から値を `Origin.valueOf` で取り出すので、値が出所の文法の文字
（`|` `;` `{` `}`）を含むと途中で切れる。R 行の値が `"a|b"` のメソッドは `"a"` を返すように見え、
次のように誤る（どれも呼び出しが消える）。

- `if (!s.equals("a")) hit();` を `[UNREACHABLE]` にする（`test/pruning` の `NePipeRet`）
- `switch (s) { case "ORDER" -> …; default -> other(); }` に `"ORDER|DESC"` が渡る経路で、`default` を
  `[UNREACHABLE]` にする（`PipeRetLocal`）
- 契約表の `KeyFactory#get("A") => DaoA` に `"A|B"` を当て、`DaoB` の実装を落とす（`FacPipeRet`）

条件の期待値に当てている以前の切り方（Q4 の `legacyCut`）は、`EQ` / `IN` を以前と同じ答えにするだけで、
切れた値が期待値と一致してしまう `NE` / `NI`・契約表のキーは救えない。

以前の書き手（形式 v32 まで）は、クラス名・識別子の形（64 文字以内）でない文字列リテラルを R 行に `U` として
書いていた。そこで `CallGraphBuilder.readReturn` が、R 行の値そのもの（木の頂点）が文字列リテラルで
その形でなければ `U` として渡す（判定は以前の書き手と同じ `Origin.isNameShaped`）。キャッシュには値をそのまま持つ
ので、読み手を直せばキャッシュを作り直さずに外せる。外すときは `CallGraphBuilder.unreadableLiteral`、
`docs/static-analysis-limits.md` の 64 文字の行、上の 3 つの検査（外した後も通ること）を一緒に見直す。

実引数・レシーバの入れ子の中の文字列は対象にしない。呼び出し箇所の実引数（`run("a|b")`・`Fac.get("A|B")`・
`static final String MODE = "a|b"` を渡す形）も、この形式に移す前から同じところで切れて同じ誤りをする。
R 行だけを以前に戻すのは、この形式で新たに増えた誤りを増やさないためで、残りは stage B で値を正確に読むときに直す。

### Q10. 戻り値の値を、なぜ上書きされうるメソッドでは使わないのか

R 行はメソッドの**本体**が返す値で、呼び出し箇所に書いてあるのは呼び出し先の**宣言**（静的なキー）である。
`Base b; b.mode()` の `mode` を部分型 `Sub` が上書きしていれば、実際に動くのは `Sub.mode` かもしれない。
それなのに `Base.mode` の R 行を「この呼び出しの戻り値」として読むと、次のように呼び出しを黙って落とす。

- `Base.mode()` が `"a|b"`、`Sub.mode()` が `"x"` を返すとき、`chk((String) b.mode())` の先の
  `if (s.equals("x")) isX();` を `[UNREACHABLE]` にする（`test/pruning` の `OvrLit`）
- `c.key()` の値を契約表のキーにして、宣言の値の行（`get("USER|X") => DaoB`）だけに絞り、上書きした本体の値の
  行（`get("S") => DaoA`）の実装を落とす（`OvrKey`）
- `f.make()` を宣言の `return new DaoA();` と畳んで `DATAFLOW_FACTORY` で `DaoA` に絞り、`Sub.make` が返す
  `DaoB` を落とす。委譲 `return f.make();`・実引数 `id(f.make())`・型の分からないレシーバを束縛した
  メソッド参照 `b::make` を畳むときも同じ（`OvrFac`・`OvrFacDel`・`OvrFacArg`・`OvrRef`）
- `b.type()` が返す `Class` を宣言の `return OvrClsA.class;` と読んで、リフレクションを `OvrClsA.go` に繋ぐ（`OvrCls`）

この穴は stage B より前からあった（識別子の形の文字列や `new` を返すメソッドでは以前から起きていた）。
stage B で R 行の文字列リテラルをそのまま読むようになって（Q9）、当たる形が増えた。

そこで、R 行（と、それを畳んだ `DataflowFacts` の `factoryKind`）を呼び出しの戻り値として使うのは、
呼び出しがその宣言の本体でしか動かないときに限る（`CallGraph#hasOverriders` が false）。

- static・private・final のメソッド、コンストラクタ、static 初期化子、ラムダの本体は静的に束縛される。
  static と private は、部分型が同じシグネチャを宣言しても隠蔽か別のメソッドで上書きではない（JLS 8.4.8）ので、
  部分型を調べる前に決める（`OvrStatic`・`OvrPriv` が対照）
- それ以外は、宣言した型のソース上の部分型それぞれで実際に動く実装を `CallGraph#implementationOf` で引き、
  どれもその宣言のままなら使う（部分型が継承しているだけ＝`OvrInh`、final＝`OvrFinal`、final クラス）。
  CHA と同じ引き方なので、匿名クラス・列挙定数の本体・インターフェースの default メソッドの上書き・
  型引数を具体化した上書きも拾い、別パッケージの同じシグネチャ（パッケージアクセスは上書きしない）は拾わない
- 束縛したレシーバの具象型から引いた実装（`new Sub()::make` の `Sub.make`）は、その型で実際に動く本体なので使う（`OvrRef` の対照）
- 使わない場合は「分からない」に倒す（打ち切らない・絞らない。CHA のまま）

使う場所はすべて同じ判定を通す: `DataflowResolver` の `concreteSlotOf`（`bodyOf`）・`classOf`・`literalOf`、
`DataflowBuilder` の委譲の畳み込み（`reduce`）と実引数の畳み込み（`concreteTypeOf`）。

`@Bean` メソッド（`SpringBeans`）だけは向きが逆になる。コンテナは設定クラスのインスタンスで `@Bean` メソッドを
呼ぶので、部分型の設定クラスが上書きしていれば（`@Bean` を付け直していなくても）登録されるのは上書きした本体が
返す型になる。Bean の登録を「分からない」にして減らすと、段 5 がもう一方の Bean へ誤って絞る。
そこで宣言の本体が返す型に加えて、上書きした本体（`CallGraph#overridingImplementations`）が返す型も
同じ名前で登録する（Bean を多く数える側は絞り込みを減らすだけ。`test/pruning` の `SbOver`、対照は `SbKeep`）。

却下した案:

- レシーバの具象型が分かるとき（`new Sub().mode()`・経路で型の決まった引数）は、その型で実際に動く実装の
  R 行を使う。精度は上がるが、レシーバの型を引く経路（経路の環境・フィールド・ファクトリ）をこの判定に持ち込む
  ことになり、今回は「上書きされうるなら使わない」の安全側だけにした。落とす呼び出しは無い（CHA が全部出す）
- `super.m()` を静的束縛として扱う。値の表のノードには `super` の印が無く、区別できない。仮想の呼び出しとして
  扱っても使わない側に倒れるだけで、呼び出しは落とさない
- 上書きした実装も含めて R 行を集め、すべて同じ値ならその値を使う。精度は上がるが、畳み込み
  （`DataflowBuilder`）の事実をメソッド単位から「呼び出し先で動きうる実装の集合」単位に変えることになる。
  これも今回は見送り、使わない側だけにした

## 読み手が値の表を読む（stage B）

対応の要点:

- 読み手（`DataflowResolver`・`GuardEvaluator`・`FactoryCalls`・`TypeContracts`・`CallbackContracts`・`CallResolver`・
  `SpringBeans`・`DataflowBuilder`・`StreamingTreeWalker`・`CallConditionScanner`）は、値グラフを出所の文字列に
  組み直したもの（`OriginRenderer`）を読むのをやめた。`CallGraphBuilder` が N・G・R・J 行と C・U 行の値を
  値の表（`jche.graph.ValueStore`）・条件の表（`GuardTable`）・文字列の置き場（`StringPool`）に取り込み、読み手は
  それを番号で引く。経路ごとの束縛（引数・コンストラクタの実引数・捕捉した値）は型付きの枠（`Slot`。種別と番号を
  詰めた `long`）で、経路を歩く間に文字列を作らない
- 値が `| ; { }` を含んでも正確に読む（Q11）。`test/regression/values` の期待値は、特性として記録していた誤った出力から
  正しい出力に変わった。ほかの `expected*/` は変わらない
- 引数を使うメソッドかの判定（`DataflowFacts.usesParameters`）は、文字列の中の `=A:` を探すのをやめ、部分木の種別で
  決める（文字列リテラルの中の `=A:` を数えない。数えても束縛する値が増えるだけで、出力は変わらない）
- 消したもの: `OriginRenderer`、`CallGraph` の文字列の列と読み口（`recvOrigin` / `argOrigins` / `guard` /
  `returnOriginsOf` / `fieldOrigin`、共有プール `originPool` と `internOrigin`）、`FieldFacts` の文字列での判定、
  `DataflowFacts.factoryOrigin`、`Origin` の読み口（`argsOf`・`argAt`・`entryAt`・`entriesOf`・`unnest`・`receiverOf`・
  `staticReceiverOf`・`argCountOf`・`constantValueOf`）、`Guard` の読み口と読み手に渡していた文字列の形
  （`atomsOf`・`fieldOf`・`valuesOf`・`atom`・`join`・`ATOM_SEP`・`FIELD_SEP`）。`Origin` に残るのは種別の文字と、
  書き手（`OriginTracker`・`ValueGraph`）と人が読むための出力（`CacheDump`）が使う道具だけ
- 修飾する型（C 行の qualifier）も文字列の置き場に置く。エッジの一時ファイルの記録は、移し替えの間の 46 バイトから
  34 バイトに戻った
- キャッシュの形式は変えていない（版も上げていない）。書き手も変えていない
- 解析結果が持ち続けるヒープは、このツールの src で 17%、長いメソッドチェーンの題材で 73% 減った（Q17）

### Q11. なぜ出所の文字列ではなく、ノードの表で読むのか

出所の文字列の文法は `|`（実引数リスト）・`;`（要素）・`{}`（入れ子）・`=`（鍵）を区切りに使い、エスケープを持たない。
値そのもの（文字列リテラル・定数）がこれらを含むと、読み手が途中で切って別の値に読み違えていた。どれも呼び出しを
黙って落とすか、違う先へ繋ぐ（`test/regression/values` の V2〜V7、`test/pruning` の `SemiArg`・`PipeArg`・
`BraceArg`・`SepPipeKey`・`SepSemiKey`・`HolderSemi`）。

- `parse("x", ";")` の先の `if (";".equals(delim)) semicolon();` を `[UNREACHABLE] … = )` にする（実引数が空文字に見える）
- `"a|c"` を渡した経路で `if (!mode.equals("a|b")) notAb();` を `a` どうしと見て打ち切る
- 契約表のキー `get("USER|X")` を `get("USER")` の行に当てる
- `new Holder("a;r=K:x.Y")` のコンストラクタ注入の値を `a` と読み、残りをレシーバと取り違える

表はノードの構造（種別・値・実引数・レシーバ・書かれた型）を列で持ち、値は文字列の置き場の番号で指すので、
区切りと値を取り違えようがない。ほかにも次の点で文字列より良い。

- **大きさ**: 文字列は入れ子を親ごとに展開し直すので、同じ部分式を何度も持つ。`append(…)` が 300 段続く
  メソッドチェーン（計測の題材 `Chain.java`）では共有プールが 3.26 MB で、段数の 2 乗で伸びる。表は部分式を 1 つの
  参照で指すので 36 KB（Q17）
- **比較**: 値どうしは文字列の置き場の番号の比較、頭（種別と値）どうしは葉の参照の比較で済む（置き場は同じ中身を
  2 つ持たず、葉は種別と値の組ごとに 1 つ。test/dataflow の ValueStoreCheck が確かめる）
- **経路の値**: 以前は `"K:" + クラス名` / `"L:" + 文字列` を経路の段ごとに作っていた。枠は種別と番号の `long` なので作らない

却下した案:

- 文法にエスケープを足す。キャッシュは既に値をノードで持っているので、読み手のためだけの文法を直すことになる。
  読むたびに文字列を解析し直す手間と、入れ子を展開する大きさの問題も残る
- 読み口（`Origin.valueOf` など）を、境界を見て切るように直す。`a;r=K:x.Y` のように、文法の上でどちらにも
  読める文字列があるので、読み口をどう直しても区別できない
- 表を作らず、ブロックの値グラフ（`ValueNode` の並び）を持ち続ける。ブロックの番号はブロックの中でしか通じない
  ので、全体で比べるには結局番号を振り直すことになる。葉をまとめられないので頭の比較が文字列の比較になり、
  どこからも指されないノードも持ち続ける

### Q12. 表の形はどう決めたか

- **取り込むもの**: 戻り値（R 行は丸ごと）・フィールドへの代入（J 行は頭の葉だけ）・条件の判定される式（頭の葉だけ）・
  呼び出し箇所のレシーバと実引数から辿れるノードだけ。ブロックの番号から全体の参照へは、指されたときに子から順に
  移す（明示的なスタックで。子の参照は必ず親の参照より小さく、読み手は前から 1 回の走査で部分木を畳める）
- **項目の有無**: 以前の組み直しが文字列に書き出していたものとそろえた（new は実引数だけ、メソッド呼び出しと
  レシーバを束縛したメソッド参照は実引数・`n=`・`r=`・`s=`、それ以外は葉）。`n=` の有無などが読み手の分かれ道を
  決めるので、振る舞いを変えないため（`jche.graph.ValueStoreBuilder` の説明）
- **まとめ方**: 文字列はグラフ全体で 1 つ（開番地法の索引は作り終えたら捨てる。メソッドキーと同じ中身は
  メソッド表の `String` を共有する）、葉は全体で種別と値の組ごとに 1 つ、項目を持つノードはブロックの中だけ
  （書き手が同じ式を 1 ノードにした番号のまま）、呼び出し箇所の実引数の並びはブロックの中で列の文字列が同じなら 1 つ
- 作った後は変わらない。解析サーバーで複数のスレッドから読んでも鍵が要らない。解決の結果もエッジの処理順に
  依存しない（`test/dataflow` の ResolveOrderCheck）

却下した案: 項目を持つノードをブロックをまたいでまとめる。このツールの src で 3,457 個が約 3,446 個になるだけ
（1% 未満。設計時の見積もり）で、まとめるには構築中に表を読み返す索引が要る（構築は書き足すだけにしておきたい。Q18）。

### Q13. 条件の期待値を切り詰めないこと（P-G）を、なぜ切り替えの前提にしたのか

以前の書き手は期待値を出所の文字列から取り出していたので、最初の `|` で切れていた（`"a|b"` が `"a"`）。
読み手の側（経路の実際の値）だけを正確にすると、次の 2 つが**新しく**誤って打ち切られる。

- `eq("a|b")` の先の `if (m.equals("a|b")) hit();`（期待値 `a`、実際の値 `a|b`）
- `static final String MODE = "a|b";` の `if (MODE.equals("a|b")) hitConst();`（どの経路でも打ち切る）

そこで期待値を正確に持つこと（形式 v33 の G 行。Q4）を先に済ませ、読み手を移すまでは `GuardEvaluator` が期待値に
以前の切り方（`legacyCut`）を当てて出力を変えず、切り替えのコミットで一緒に外した。
`test/regression/values` の `Pipe`（`hit`・`hitConst`）と `test/pruning` の `PipeEq`・`PipeConst` が、
どちらか片方だけを直した状態で落ちる。

### Q14. 文字列の側の誤り 2 つ（B0a・B0b）を、なぜ切り替えの前に別に直したのか

切り替えは「経路の記録が 1 文字も変わらない」ことで確かめる（Q16）。型付きの枠では起きようのない誤りが
文字列の側に残っていると、切り替えで記録が変わり、どこまでが直したもので、どこからが移し替えの誤りか
見分けられない。そこで次の 2 つを先に文字列の側で直し、記録はその後で取った。

- **B0a**（`GuardEvaluator`）: 経路で束縛した引数が型（`:` を含まない FQN）でも、値として読んでいた。無名パッケージの
  型 `Kind` は先頭の `K` がクラスオブジェクトの種別に見え、値が空文字になって `k.equals("x")` を打ち切っていた。
  値（`:` を含むもの）だけを使うようにした（型付きの枠では、リテラル・クラス・定数の枠だけが値）。
  `test/pruning` の `/Kind`、`test/regression/values` の `Kind.java`
- **B0b**（`DataflowResolver` の `getClass()`）: コンストラクタ注入のフィールドを通って来た値（`L:x`）を型とみなし、
  リフレクションのシグネチャを `take(L:x)` と組んで、呼び出し `run → take` を黙って落としていた。型だけを使う
  ようにした（どの型のメソッドか分からなければ、名前の一致するメソッドを候補に残す側に倒れる）。
  `test/pruning` の `ReflField`、`test/regression/values` の `vals/Refl.java`

### Q15. 切り替えで見つかった、上書きされうるメソッドの戻り値の穴は

R 行の文字列リテラルをそのまま読むようになって（Q9）、「呼び出し先の宣言の本体が返す値」を「その呼び出しの
戻り値」として使っていた穴に当たる形が増えた。部分型が上書きしていれば、実際に動くのは上書きした本体かもしれない。
戻り値の値（R 行と、それを畳んだファクトリの事実）を使うのは、呼び出しがその宣言の本体でしか動かないとき
（`CallGraph#hasOverriders` が false）に限った。判定は CHA と同じ `implementationOf` で部分型ごとに引き、
`@Bean` メソッドだけは上書きした本体が返す型も登録する。詳しくは Q10。

### Q16. 切り替えが振る舞いを変えないことを、どう確かめたか。その検査をなぜ消したのか

移し替えの間（B1〜B5）は、文字列の側と表を両方作り（二重に持つ）、次の 2 つで確かめた。

- **ValueStoreCheck（文字列との突き合わせ）**: エッジごとのレシーバ・実引数・条件、メソッドごとの戻り値、
  フィールドの値について、表から組み直した文字列が文字列の側と 1 文字も違わないこと。さらに、組み直した文字列を
  以前の読み口で読んだ結果（種別・値・レシーバ・実引数の数・書かれた型・位置ごとの実引数・引数を含むか）が
  表の構造と一致すること。一致しない参照（あいまいな参照）は、値に文法の文字を含まない 10 設定で 0、
  `test/regression/values` では 12 個で、どれも部分木の値が `; | {` を含む（読み違いの原因がその文字である）
- **TraceCheck（経路の記録）**: 呼び出し階層を歩く中の差し込み口（`StreamingTreeWalker` の一時的な probe）で、
  段ごとの解決・打ち切りの理由・束縛した値・呼び戻し・ファクトリのキー・ひな形の左辺と、経路によらない事実
  （ファクトリの戻り値・戻り値の並び・フィールド・Bean・全エッジの解決・被参照数）を書き出し、切り替えの前に
  取った記録（10 設定・約 8,900 行）と比べた。B2・切り替え（B3・B4）・文字列の側を消した後（B5）のどれでも
  1 文字も変わらなかった（B5 は、消した差し込み口を使い捨ての複製にだけ戻し、消した読み口の出力は値の表から
  同じ形に作り直して比べた）

TraceCheck を消す前に、それが守っていた範囲を残す検査が守れているかを変異で測った。型付きの読み手の分かれ道
（`DataflowResolver`・`DataflowBuilder`・`GuardEvaluator`・`StreamingTreeWalker`・`FactoryCalls`・
`CallbackContracts`・`FieldFacts`・`SpringBeans`・`CallGraph` の上書きの判定・`CallGraphBuilder` の値の取り込み）を
1 行ずつ壊す変異 96 個を、1 つずつ植えて検査を流した（`test/pruning` → `test/regression` → `test/dataflow` の順に流し、
最初に落ちた検査に数える）。

| 検査 | 検出した変異 |
|---|---|
| TraceCheck があったとき（当時の `test/dataflow` ＋ `test/pruning` ＋ `test/regression`） | 80/96 |
| TraceCheck を消しただけ（`test/pruning` ＋ `test/regression` ＋ 今の `test/dataflow`） | 66/96 |
| 洗い出した穴の 18 ケースを `test/pruning` に足した後（今の形） | **82/96**（`test/pruning` で 66、残りを `test/regression` で 16。今の `test/dataflow` だけでは 0） |

TraceCheck を消しただけでは、TraceCheck だけが検出していた 14 個が素通りになり、うち 8 個は呼び出しを
黙って落とす取り違えだった（親のフィールドの持ち主・リフレクションの受け手の具象型・引数で渡った Class・契約表の実引数の位置・
呼び戻しの 2 番目以降の実引数・継承したメソッドへのコンストラクタ実引数・static や値の食い違うフィールド）。
TraceCheck も含めてどの検査も検出していなかった 4 個（引数で渡ったメソッド参照・return が 2 通りの `@Bean`・
private でも final でもないフィールド・setter でも代入するフィールド）もあわせて、`test/pruning` の
「経路の記録（TraceCheck）を消すときに…洗い出した穴」の節にケースを足した。

足した後も残る 14 個と理由は次のとおり。同値か保守側に倒れるだけのものが大半だが、最後の 3 個は
検出できていない（試した題材では出力が変わらなかった）ことをそのまま記録しておく。

- 同値（後段が同じ判定をしている）: `DataflowResolver#typeAt` の型の枠の絞り込み（DR03。呼び手が
  `Slot.isType` を見直す）、`paramValueOf` の値の枠の絞り込み（DR15。受け取る側が枠の種別を見る）、
  `CallGraph#dispatchesElsewhere` の final とラムダの本体の早期の判定（F3・F12。後の `implementationOf` の探索でも
  上書きは見つからない）、`FieldFacts#agreedHeadOf` の頭が分からない代入の除外（FF08。頭の無い代入の除外に含まれる）
- 解析対象に無い型名の除外（DR05・DR11・`DataflowBuilder` の DB04）。外しても、その型名からは実装も
  コンストラクタも引けず、同じく決まらない側に倒れる（DB04 は 3 つの出力が 1 バイトも変わらないことを確かめた。
  TraceCheck が検出していたのは、出力に出ないファクトリの戻り値の事実まで書き出していたため）
- 保守側に倒れるだけ: 委譲するコンストラクタを起点から外す判定（FF07。外さないと代入がそろわず絞らない）、
  呼び戻しのコンストラクタ実引数をレシーバが `new` のときだけ読む判定（CB03。外すと候補が増えるだけ）、
  レシーバの部分木の引数を「経路の引数を使う」に数える判定（DB01。外すと経路の値を渡さず、分からない側に倒れる）
- 検出できていない: メソッドが返す Class を文字列の枠で渡す（DR16。違いが出るのは Class が引数を通って
  ファクトリに届いたときのひな形のキーだけで、TraceCheck はその左辺を書き出していたので検出していた）、
  捕捉した引数を値として渡す枠（DR18）、戻り値を畳むときの種別の比べ（S5。値の番号が同じで種別だけが違う
  戻り値の組、たとえば同じ名前の `new` と文字列が要る）

移し替えが終わったので、文字列の側と比べる部分（差し込み口・TraceCheck と記録・`LegacyRender`・`LegacyOrigin`・
ValueStoreCheck の突き合わせ）と、記録のためだけの題材 `test/dataflow/projects/paths` を消した。比べる相手の
文字列の側がもう無く、記録は行番号や並びまで固定するので、正当な変更のたびに取り直すことになり、取り直しが
素通しになるため。残したのは次のとおり。

- 振る舞い: `test/pruning`（値の読み取りの分かれ道ごとの呼び出しの有無）と `test/regression/values`（期待値の比較）
- 表の決まり: `test/dataflow` の ValueStoreCheck（子 < 親、項目の並び、葉と文字列の一意、メソッドキーの共有、
  頭は葉、戻り値の重なり、修飾する型の番号、I0 / I1 ＝ new の型・型階層の型名・メソッド表の型が `:` を含まない。
  I0 / I1 は、枠が型とそれ以外を取り違えないための前提）と StoreUnitCheck（書き手が作らない行の扱い）

却下した案:

- 以前の読み手を丸ごと凍結した複製（2,000 行を超える）と比べ続ける。複製の保守が本体の保守より重くなる
- 記録（golden）を恒久の検査として残す。上のとおり、取り直しが素通しになる

### Q18. 表の列をメモリに置かない形（一時ファイルへの写像）は、なぜ見送ったか

設計はしてある。列はどれも固定長で、構築は書き足すだけ（構築中に表を読み返さない。葉は一時的な索引で、
ほかはブロックの番号の対応で引く）なので、列のバイト数がしきい値を超えたらキャッシュのフォルダの一時ファイル
（エッジの一時ファイルと同じ命名・開始時の掃除・`finally` での削除）へ書き流し、作り終えたら読み取り専用で写像して
`IntBuffer` などで引ける。列は外に出さず番号で引く作り（`ValueStore` の説明）にしてあるので、変えるのはクラスの中だけで済む。

見送ったのは、Q17 の数字では割に合わないため。

- このツールの src で、表は解析結果 2.91 MB のうち 377 KB（13%）。写像できるのは列の 194 KB（7%）だけで、
  文字列の置き場は写像できない（読むたびに文字列を作り直すことになる）
- 呼び出し箇所 100 万（このツールの src の約 90 倍）に伸ばすと、列はおよそ 17 MB、文字列の置き場はおよそ 15 MB。
  一方、エッジの CSR（エッジ 1 本あたり 30 バイト）は 30 MB で、こちらの方が大きい。写像するならエッジの配列と
  同じ仕組みでまとめて行うべきで、表だけを先にする理由が無い
- ヒープの山はフェーズ 1（JDT の構文解析と型解決）で、1,000 ファイルの解析で回収前の最大 842 MB に対し、
  生きている量は 20 MB だった（`ast-analysis-performance-qa.md` の「計測のしかた」）
- Windows は写像を外すまでファイルを消せないので、残ったファイルを次の起動で掃除する経路が要る。解析サーバーは
  解析をやり直すたびに写像の寿命を管理することになる

却下した案（写像以外）:

- 構築の始めから列を塊ごとに分けた `IntBuffer` にして写像できる形で持つ。値の表は小さいので、Windows と解析サーバー
  での寿命の管理が、減るヒープに見合わない
- 経路の文脈（`DataflowContext`）を書き換えられる形にして枠を使い回す。経路の段ごとに持つ文脈を別の段と
  取り違える（エイリアス）誤りを招く。今の形は段ごとに作った文脈を書き換えず、段の中で 1 つを使い回す
- 束縛した値を小さなレコード（オブジェクト）にする。読みやすいが、経路を歩くたびに束縛した値の数だけ作る
- 文字列の置き場を作り終えた後も伸ばせる形にして、B0b の誤った値（型の位置に来た値の文字列）も置けるようにする。
  誤りを残すためだけの仕組みになるので、先に誤りを直した（Q14）
