# キャッシュを 1 ファイルにまとめる — 実装時の QA 一覧

Issue なし（2 ファイルに分けたキャッシュ（[cache-split-qa.md](cache-split-qa.md)）を見直した一連の作業）。

解析結果のキャッシュは `analysis-cache.tsv` と `dataflow-cache.tsv` の 2 ファイルに分かれていた。
分けた基準（「呼び出し階層の出力に使うか」）は成り立っておらず、2 つを対に保つ仕組みだけが増えていた。
これを 1 ファイルにまとめ、値の持ち方と読み方をそれぞれ 1 通りにし、1 回の実行でキャッシュを読む回数を減らした。
その中で迷ったこと・困ったことと、その結論を Q&A の形で残す。

対応の要点（コミットの順）:

- **鍵と版の方針**（Q19〜Q21）: JDT の版（core と ecj）をヘッダ行の鍵 `jdt=` に入れた。読めなければ `?` と書き、
  `?` を含む鍵は一致しないとみなす。形式の版は「迷ったら上げる」に改め、上げ忘れは `test/cacheversion`
  （決まった題材の事実の指紋を記録と比べる）が捕まえる
- **1 ファイルにする**（形式 v31。Q22〜Q29）: ソースファイル 1 つにつき 1 ブロックで、構造と値を同じブロックに持つ。
  メソッドはブロック内の記号表（S 行）の番号で指し、呼び出し箇所の値は C 行・U 行が直接持つ（結びつけの P 行を無くした）。
  列の符号化は 1 つの規則、行は OS によらず `\n` で終える。F 行にブロックの検査値（crc）を持ち、合わないブロックは
  ソースが変わったブロックと同じく無効にする（そのファイルと、そのファイルの型を使うファイルを解析し直し、ほかは
  再利用する。Q25）。世代の印・ブロックの突き合わせ・歩調を合わせた読み・末尾だけの読み取りを無くした。
  以前の形式が残した `dataflow-cache.tsv` は消す
- **出力の並びをメソッド ID に依らせない**（Q30。詳しくは [deterministic-row-order-qa.md](deterministic-row-order-qa.md) の Q14〜Q19）
- **読む回数を減らす**（Q31〜Q37）: キャッシュをバイト単位で読み、有効なブロックの位置を覚え、依存は一時ファイルの索引に
  置き、書き写しはバイトの範囲のまま行う。何も変わっていなければキャッシュに触らない。グラフは 1 回の読み取りで組み
  （エッジはいったん一時ファイルへ）、型解決に失敗した呼び出しの一覧もその読み取りで集める。一時ファイルは一意の名前で作り、
  `finally`・JVM の終了フック・次の実行の掃除で残さない。どれも「ヒープを増やさない」を優先した
- **書き手の値の読み違いを直す**（形式 v32。[value-safety-qa.md](value-safety-qa.md)）
- **値をすべて値グラフのノードで持つ**（形式 v33。Q1〜Q10）: 戻り値（R 行）・フィールドへの代入（J 行）はノード番号、
  条件は G 行の表、new の証拠は C 行・U 行の hints 列。X 行と recvKey 列を無くした
- **読み手が値の表を読む**（stage B。Q11〜Q18）: 出所の文字列（`Origin` の文法）に組み直さず、値の表（`ValueStore`）を
  番号で引く。値が `| ; { }` を含んでも読み違えない。`OriginRenderer` と文字列の読み口を消した
- **差分更新が見落としていた依存を拾う**（最終レビューとその修正のレビュー。形式 v34。Q42〜Q50）: 無かった型を足したら型解決に失敗していたブロックを、
  同じパッケージに型を足したら名前を隠されうるブロックを解析し直す。解析し直したファイルの親型が変わっていれば
  その型も連鎖させる。ラムダの目標の型、宣言にだけ書いた型の名前、呼び出しの受け手と実引数の式の型・修飾された名前の
  左側の型を I 行に載せる。warnings.txt に並べるエラーのファイルをパスの順で選ぶ。対になっていないサロゲートを符号化する
- **値の読み違いの残り**（52453ae に対する 3 回目のレビュー。形式 v35。[value-safety-qa.md](value-safety-qa.md) の
  Q18〜Q24）: フィールドへの書き込みを漏れなく拾い、生成のたびに必ず通るとは言えない書き込みは site を `?` にする。
  `this` 以外で修飾したフィールドの読み取りを値にしない。拡張 for の要素・型名で書いたメソッド参照の実引数・
  リフレクションの invoke・DI の段 5（注入点だけ）を直す。v35 はこの段で push した
- **差分更新が見落としていた依存を拾う**（3 回目のレビュー。形式 v36。Q51〜Q55）: 型の形に可変長引数と throws を入れ、
  親のメンバーと名前の当たらない私的メンバーを外す（親に私的な補助メソッドを足しても部分型の利用者へ連鎖しない）。
  型解決に失敗したファイルは参照した型の親を依存に持つ。拡張 for 文・switch・throw・アノテーション・呼び出し先の throws・
  case の型の親を I 行に載せる。解決できなかった名前を変わった型すべてと突き合わせる。jar が同じパッケージに足した型の
  隠蔽を拾う
- **キャッシュの健全性と一括解析の頑健さ**（3 回目のレビュー。形式 v36。Q56〜Q63）: 同じキャッシュのフォルダを使う実行を錠で 1 つずつにし、
  グラフを組む側も書き終えたキャッシュかを確かめる。解析のあいだに書き換えられたソースは次の実行で解析し直す。
  ソースフォルダの並びを鍵に入れ、F 行と先頭の行も検査値で守る。同じクラスが 2 つのソースフォルダにあれば同じバッチで
  解析する。JDT のスタックの溢れを 1 ファイルの失敗にし、網羅していない switch 式を構文エラーに数えない。
  v36 は、3 回目のレビューの 2 つの修正（差分更新の依存、キャッシュの健全性）を合わせた版（どちらも先に v35 を使って
  いたが、値の側の修正が v35 を push 済みだったので 1 つ進めた）
- **解決できなかった名前にパスを拾わない**（形式 v37。Q64）: 型が重複しているエラーの引数にあるソースファイルの絶対パスを
  I 行の 3 列目に入れない（キャッシュの事実がチェックアウトの場所で変わっていた）
- 回帰テストの期待出力は、stage B で直した読み違いを記録していた `test/regression/values` と、v35 で `new Thread(this::hook)` の
  注記の理由が `receiver unknown` から `own class (this)` に変わった 1 か所（`fx.lambda.CallbackRefs.viaThread`。test/demo を
  解析するケースの期待出力それぞれ。[value-safety-qa.md](value-safety-qa.md) の Q24）のほかは変わっていない

見送った案・却下した案（ソースファイルごとのファイル、フェーズ1 と 2 をまとめる、値の表の写像）は Q38〜Q40、
残っている限界は Q41。差分更新が見落としていた依存は、形式 v34 のぶんが Q42〜Q50、v36 のぶんが Q51〜Q55。
キャッシュの健全性と一括解析の頑健さ（形式 v36）は Q56〜Q63、解決できなかった名前にパスを拾わない件（形式 v37）は Q64。
レビューの呼び方は、6c41201 に対するものが「最終レビュー」、その修正（52453ae になる前）に対するものが「2 回目のレビュー」、
52453ae に対するものが「3 回目のレビュー」（PR #167 の見直し。値の側・差分更新の依存・キャッシュの健全性の 3 つの修正に

## 値をすべて値グラフのノードで持つ（形式 v33）

対応の要点:

- キャッシュの値は、どれも N 行（値グラフ）のノードを番号で指す。戻り値（R 行 `R 記号 node`）・フィールドへの
  代入（J 行 `J typeFqn field site node`）は出所の文字列をやめてノード番号にした（`-1` は「追跡できない」）
- 条件はブロックの表（G 行 `G ガード番号 op subject text 値1 値2 …`）にし、C 行・U 行はガード番号で指す。
  アトム 1 つにつき 1 行、subject はノード番号、値は後ろの列に 1 つずつで、切り詰めない
- new の証拠の X 行と、C 行・U 行の recvKey 列を無くした。書き手がファイルの中で結びつけた結果を
  C 行・U 行の hints 列（型の FQN のカンマ区切り）に書く
- ブロックの並びは `F I S N G R H D O V C/U M A K J`
- 読み手（`CallGraphBuilder`）は読む直前に以前と同じ文字列へ組み直す（R 行は丸ごと、J 行はノードの頭、
  条件は以前の guard 列の形）。R 行の値そのものがクラス名・識別子の形でない文字列リテラルなら、
  今の読み手が読み違えるので暫定で U として渡す（Q9）。`test/regression` の期待出力は変わっていない
  （組み直しと暫定の扱いは stage B で外した。読み手は値の表を読む。下の「読み手が値の表を読む」）
- R 行を書くかどうかを、return の式の型ではなく、囲むメソッド・ラムダの宣言の戻り値の型で決める（Q8）
- test/demo のキャッシュは 96,628 バイトから 90,579 バイトになった（このツール自身のソース（c0007c4 の src）では
  2,592,398 バイトから 1,937,633 バイト。多くは C 行・U 行ごとの recvKey（長いバインディングキー）と、
  同じ条件の書き並べが無くなった分）

### Q1. なぜ R 行・J 行・条件もノードにするのか

呼び出し箇所の値は既にノードで持っていたが、R 行・J 行・条件は `OriginTracker` が作る出所の文字列のままで、
文字列の側にだけ上限（実引数は 1 段・レシーバは 3 段・文字列は 64 文字で識別子の形だけ）があった。
同じ式が、どこに書かれるかで細かさの違う 2 通りの表し方になっていた。すべてをノードにすれば表し方が 1 つになり、
読み手をノードで読む形に移すとき（次の段）に文字列の読み口を残さずに済む。

### Q2. 条件をなぜ別の行（G 行）の表にするのか

同じ分岐の中の呼び出しは同じ条件を持つので、呼び出しごとに書き並べると同じ文字列が何度も出る。
ブロックの表にして番号で指せば 1 回で済む。また、以前は値を区切り文字で並べていたので、
「値が 1 つも無い」と「空文字の値が 1 つ」を見分けられなかった（Q6）。値を列に 1 つずつ置けば、
値の中にどんな文字があっても区切りは崩れない。

### Q3. 条件の subject にはどのノードを通すのか

以前と同じく、引数（A）と定数（V）だけ。`nodeOf(unwrapValue(subject))` の種別で見る。違いは 2 つある。

- 定数フィールドを写したローカル変数（`int m = MODE;`）は、以前は出所の文字列が `F:` になって条件にならなかったが、
  ノードでは `V:3` になるので条件になる。呼び出し元へ渡す実引数としては以前から `V:3` だったので、揃った形になる。
  変数の値が 1 つに決まるのは、先読みで代入がすべて同じノードだったときだけ（書き換えがあれば「分からない」）
- 文字列のコンパイル時定数は、値グラフではリテラル（L）のノードになる。以前はここを定数（`V:`）として
  条件にしていたので、`OriginTracker.constantOf`（64 文字以内・制御文字を含まない）で拾える定数は V のノードを作る

メソッド呼び出し・new・定数でないフィールドなど、A にも V にもなりえない式のノードは作らない
（ノードは作ると消せず、どこからも指されない行が残るため）。

### Q4. 期待値を切り詰めないのに、なぜ出力が変わらないのか

以前の書き手は期待値を出所の文字列から取り出していた（`Origin.valueOf`）ので、最初の `|` で切れていた
（`"a|b"` が `"a"`）。G 行は値そのものを持つ。一方、読み手が経路の値（呼び出し元が渡した実引数・定数の subject）を
取り出すところは、まだ出所の文字列を通るので同じところで切れる。期待値だけを正確にすると、`"a|b"` を渡した
経路で `s.equals("a|b")` を「成立しない」と誤って判定する。そこで `GuardEvaluator` が期待値に以前の切り方
（`legacyCut`）を当てて、両方を同じ形にそろえる。読み手を値のまま比べる形に移すときに一緒に外す
（`test/pruning` の `PipeEq` / `PipeConst` が両方の組み合わせを見る）。

stage B で外した。`GuardEvaluator` は条件の表（`jche.graph.GuardTable`）の期待値と、値の表・経路の環境の
実際の値を、どちらも切り詰めずに値の番号で比べる（`test/regression/values` の `Pipe` も見る）。

### Q5. new の証拠を、なぜ C 行・U 行に直接持つのか

X 行は「呼び出し元のキー＋変数のキー」で、読み手がキャッシュ全体から集めて呼び出し箇所の recvKey に結びつけていた。
変数のキー（バインディングキー）はそのファイルの宣言を指すので、結びつけはファイルの中で閉じる。書き手が
ブロックを書くときに結びつければ、X 行も recvKey も要らない。変数でないレシーバの recvKey（`@位置`）は
X 行と一致することが無く、もともと使われていなかった。

1 つだけ違うのは、同じメソッドキーが 2 つのファイルにある（同じクラスが重複している）場合で、以前は両方の
ファイルの証拠が混ざっていたが、今はそれぞれのファイルの証拠がそれぞれの呼び出し箇所にだけ付く。

却下した案: 証拠を値グラフのノード（変数ごとの代入の集まり）にする。値グラフは代入が食い違えば「分からない」に
倒すが、証拠は食い違う new の型をすべて残す（`LOCAL_NEW_MULTI`）ので、1 つのノードに畳めない。

### Q6. `default` しか無い `switch` は、なぜ条件にしないのか

`switch (s) { default -> hit(); }` の `default` は必ず通る。以前は「どの case とも一致しない」（NI）を値なしで
書いていたが、値を区切り文字で並べる形では「値なし」が「空文字の値 1 つ」と同じ文字列になり、`sel("")` の経路で
`hit` を `[UNREACHABLE]` にしていた（この形式に移す前からの誤り）。条件ではないので、アトムを作らない
（`test/pruning` の `DefaultOnly`）。

条件の調査（`conditions.target` を書いたときの `call-conditions.csv`）も同じアトムから作るので、出方が変わる。
以前はこの呼び出しに `switch (s) default` の条件を「どの値とも一致しない（`∉ {}`）」として出していたが、
今は条件の無い呼び出しと同じく、その呼び出しの行の条件の列（`condIndex` 以降）が空になる。この `default` は
どの値でも通るので、条件として出していた方が誤りである。`case` が 1 つでもある `switch` の `default` は、
以前と同じく `∉ {case の値…}` の条件として出る。

### Q7. 何が変わるか

（v33 の時点の記録。ここで言う「組み直した文字列」と、識別子の形でない文字列を U として渡す暫定の扱い（Q9）は、
stage B で読み手が値の表を読むようになって無くなった。値は切り詰めずにそのまま読む）

- R 行を組み直した文字列は、呼び出し箇所と同じく上限が無くなる（実引数の入れ子・レシーバ・`s=`）。ローカル変数は
  代入元のノードに畳まれる。`static final int` のフィールドは `F:` ではなく `V:` になる。
  `L:` も `V:` も戻り値の型は決めないが、読み手は「メソッドが返す値が 1 つに決まる」とき、その値を経路の値として
  使う（`DataflowResolver` の戻り値の文字列。条件の打ち切りと契約表のキー）。値そのものが識別子の形でない
  文字列は、今の読み手が出所の文法の文字で切ってしまうので、以前と同じく U として渡す（Q9）
- R 行を宣言の戻り値の型で書くようになったので（Q8）、`Object` を返すメソッドの `return "x";` も R 行になる。
  どの return も同じ識別子の形の文字列を返すメソッドでは、その値で条件を打ち切る（`test/pruning` の `LitRet`。
  メソッドは必ずその値を返すので、実際にも通らない）。値の食い違う return があれば値は決まらない
- J 行も同じく、識別子の形でない文字列が `L:`、`static final int` が `V:` になる。コンストラクタ注入の判定で
  「出所が一致する」フィールドが増えることがあるが、具象型に使うのは `T:` と `A:` だけ
- 条件は Q3 のとおり、定数フィールドを写したローカル変数と定数の式（`MODE + 1 == 5`）が条件になり、
  その値で成立しない呼び出しは `[UNREACHABLE]` になる（コンパイル時定数なので、実際にも通らない）
- 条件の調査（`call-conditions.csv`）も同じ条件を「判定できる」と出す。期待値は切り詰めずに出す。
  `default` しか無い `switch` の呼び出しには条件を出さない（Q6）

### Q8. R 行を書くかどうかを、なぜ宣言の戻り値の型で決めるのか

以前の書き手は、return の**式の型**がプリミティブ・配列・`String` なら、その return を R 行にしなかった。
すると `Object key(boolean b) { if (b) return "x"; Object v = "y z"; return v; }` の `return "x"` だけが抜け、
R 行は `v` の値 1 つになる。読み手は R 行の値が 1 つに決まれば「このメソッドは必ずその値を返す」と読むので、
`run((String) key(b))` の先の `if (s.equals("x")) hit();` を `[UNREACHABLE]` にしていた。

この誤りはこの形式に移す前からあった（残りの return が識別子の形の文字列 `"yz"` なら、以前も打ち切っていた）。
R 行を値グラフのノードで書くようになって、識別子の形でない `"y z"` も `L:` として残るようになり、当たる形が増えた。

そこで、囲むメソッドの宣言（ラムダなら関数型インターフェースのメソッド）の戻り値の型で決める。1 つのメソッドの
return はどれも同じ宣言から決まるので、全部記録するか、全部しないかのどちらかになり、一部だけ抜けることが無い。
宣言の型が `String` などのメソッドは、以前と同じく記録しない（具象クラスの絞り込みに使えない）。
宣言の型が引けないときは記録する。`void` のラムダの式本体（`() -> dao.save(x)`）は値を返さないので記録しなくなった
（以前は式の型で決めていたので、`save` の戻り値が R 行になっていた。読む者はいない）。

却下した案:

- 読み手の側（Q9 の暫定の扱い）だけで直す。識別子の形でない文字列は U になるので `"y z"` は直るが、`"yz"` の
  形は以前から誤っていたまま残る（`test/pruning` の `MixedRetId`）
- 式の型が `String` の return を U として書く。一部だけ抜けることは無くなるが、`Object key() { return "A"; }` の
  ように値が 1 つに決まるメソッドも「分からない」になり、書き方で結果が変わる

### Q9. R 行の文字列リテラルを、なぜ読むところで U にするのか（暫定）

**stage B で外した。** 読み手（`DataflowResolver`・`GuardEvaluator`・`FactoryCalls` など）が出所の文字列ではなく
値の表（`jche.graph.ValueStore`）を読み、値を切り詰めずに比べるようになったので、R 行の文字列リテラルも
そのまま読む。下の 3 つの検査はそのまま通り、`test/pruning` の `PipeRetEq`・`PipeRetSwitch`・`SemiRetKey`
（`|` `;` を含む戻り値で、正しく打ち切る・契約表の書いたとおりの行に当てる）を足した。以下は外す前の記録。

今の読み手は、組み直した出所の文字列から値を `Origin.valueOf` で取り出すので、値が出所の文法の文字
（`|` `;` `{` `}`）を含むと途中で切れる。R 行の値が `"a|b"` のメソッドは `"a"` を返すように見え、
次のように誤る（どれも呼び出しが消える）。

- `if (!s.equals("a")) hit();` を `[UNREACHABLE]` にする（`test/pruning` の `NePipeRet`）
- `switch (s) { case "ORDER" -> …; default -> other(); }` に `"ORDER|DESC"` が渡る経路で、`default` を
  `[UNREACHABLE]` にする（`PipeRetLocal`）
- 契約表の `KeyFactory#get("A") => DaoA` に `"A|B"` を当て、`DaoB` の実装を落とす（`FacPipeRet`）

条件の期待値に当てている以前の切り方（Q4 の `legacyCut`）は、`EQ` / `IN` を以前と同じ答えにするだけで、
切れた値が期待値と一致してしまう `NE` / `NI`・契約表のキーは救えない。

以前の書き手（形式 v32 まで）は、クラス名・識別子の形（64 文字以内）でない文字列リテラルを R 行に `U` として
書いていた。そこで `CallGraphBuilder.readReturn` が、R 行の値そのもの（木の頂点）が文字列リテラルで
その形でなければ `U` として渡す（判定は以前の書き手と同じ `Origin.isNameShaped`）。キャッシュには値をそのまま持つ
ので、読み手を直せばキャッシュを作り直さずに外せる。外すときは `CallGraphBuilder.unreadableLiteral`、
`docs/static-analysis-limits.md` の 64 文字の行、上の 3 つの検査（外した後も通ること）を一緒に見直す。

実引数・レシーバの入れ子の中の文字列は対象にしない。呼び出し箇所の実引数（`run("a|b")`・`Fac.get("A|B")`・
`static final String MODE = "a|b"` を渡す形）も、この形式に移す前から同じところで切れて同じ誤りをする。
R 行だけを以前に戻すのは、この形式で新たに増えた誤りを増やさないためで、残りは stage B で値を正確に読むときに直す。

### Q10. 戻り値の値を、なぜ上書きされうるメソッドでは使わないのか

R 行はメソッドの**本体**が返す値で、呼び出し箇所に書いてあるのは呼び出し先の**宣言**（静的なキー）である。
`Base b; b.mode()` の `mode` を部分型 `Sub` が上書きしていれば、実際に動くのは `Sub.mode` かもしれない。
それなのに `Base.mode` の R 行を「この呼び出しの戻り値」として読むと、次のように呼び出しを黙って落とす。

- `Base.mode()` が `"a|b"`、`Sub.mode()` が `"x"` を返すとき、`chk((String) b.mode())` の先の
  `if (s.equals("x")) isX();` を `[UNREACHABLE]` にする（`test/pruning` の `OvrLit`）
- `c.key()` の値を契約表のキーにして、宣言の値の行（`get("USER|X") => DaoB`）だけに絞り、上書きした本体の値の
  行（`get("S") => DaoA`）の実装を落とす（`OvrKey`）
- `f.make()` を宣言の `return new DaoA();` と畳んで `DATAFLOW_FACTORY` で `DaoA` に絞り、`Sub.make` が返す
  `DaoB` を落とす。委譲 `return f.make();`・実引数 `id(f.make())`・型の分からないレシーバを束縛した
  メソッド参照 `b::make` を畳むときも同じ（`OvrFac`・`OvrFacDel`・`OvrFacArg`・`OvrRef`）
- `b.type()` が返す `Class` を宣言の `return OvrClsA.class;` と読んで、リフレクションを `OvrClsA.go` に繋ぐ（`OvrCls`）

この穴は stage B より前からあった（識別子の形の文字列や `new` を返すメソッドでは以前から起きていた）。
stage B で R 行の文字列リテラルをそのまま読むようになって（Q9）、当たる形が増えた。

そこで、R 行（と、それを畳んだ `DataflowFacts` の `factoryKind`）を呼び出しの戻り値として使うのは、
呼び出しがその宣言の本体でしか動かないときに限る（`CallGraph#hasOverriders` が false）。

- static・private・final のメソッド、コンストラクタ、static 初期化子、ラムダの本体は静的に束縛される。
  static と private は、部分型が同じシグネチャを宣言しても隠蔽か別のメソッドで上書きではない（JLS 8.4.8）ので、
  部分型を調べる前に決める（`OvrStatic`・`OvrPriv` が対照）
- それ以外は、宣言した型のソース上の部分型それぞれで実際に動く実装を `CallGraph#implementationOf` で引き、
  どれもその宣言のままなら使う（部分型が継承しているだけ＝`OvrInh`、final＝`OvrFinal`、final クラス）。
  CHA と同じ引き方なので、匿名クラス・列挙定数の本体・インターフェースの default メソッドの上書き・
  型引数を具体化した上書きも拾い、別パッケージの同じシグネチャ（パッケージアクセスは上書きしない）は拾わない
- 束縛したレシーバの具象型から引いた実装（`new Sub()::make` の `Sub.make`）は、その型で実際に動く本体なので使う（`OvrRef` の対照）
- 使わない場合は「分からない」に倒す（打ち切らない・絞らない。CHA のまま）

使う場所はすべて同じ判定を通す: `DataflowResolver` の `concreteSlotOf`（`bodyOf`）・`classOf`・`literalOf`、
`DataflowBuilder` の委譲の畳み込み（`reduce`）と実引数の畳み込み（`concreteTypeOf`）。

`@Bean` メソッド（`SpringBeans`）だけは向きが逆になる。コンテナは設定クラスのインスタンスで `@Bean` メソッドを
呼ぶので、部分型の設定クラスが上書きしていれば（`@Bean` を付け直していなくても）登録されるのは上書きした本体が
返す型になる。Bean の登録を「分からない」にして減らすと、段 5 がもう一方の Bean へ誤って絞る。
そこで宣言の本体が返す型に加えて、上書きした本体（`CallGraph#overridingImplementations`）が返す型も
同じ名前で登録する（Bean を多く数える側は絞り込みを減らすだけ。`test/pruning` の `SbOver`、対照は `SbKeep`）。

却下した案:

- レシーバの具象型が分かるとき（`new Sub().mode()`・経路で型の決まった引数）は、その型で実際に動く実装の
  R 行を使う。精度は上がるが、レシーバの型を引く経路（経路の環境・フィールド・ファクトリ）をこの判定に持ち込む
  ことになり、今回は「上書きされうるなら使わない」の安全側だけにした。落とす呼び出しは無い（CHA が全部出す）
- `super.m()` を静的束縛として扱う。値の表のノードには `super` の印が無く、区別できない。仮想の呼び出しとして
  扱っても使わない側に倒れるだけで、呼び出しは落とさない
- 上書きした実装も含めて R 行を集め、すべて同じ値ならその値を使う。精度は上がるが、畳み込み
  （`DataflowBuilder`）の事実をメソッド単位から「呼び出し先で動きうる実装の集合」単位に変えることになる。
  これも今回は見送り、使わない側だけにした

## 読み手が値の表を読む（stage B）

対応の要点:

- 読み手（`DataflowResolver`・`GuardEvaluator`・`FactoryCalls`・`TypeContracts`・`CallbackContracts`・`CallResolver`・
  `SpringBeans`・`DataflowBuilder`・`StreamingTreeWalker`・`CallConditionScanner`）は、値グラフを出所の文字列に
  組み直したもの（`OriginRenderer`）を読むのをやめた。`CallGraphBuilder` が N・G・R・J 行と C・U 行の値を
  値の表（`jche.graph.ValueStore`）・条件の表（`GuardTable`）・文字列の置き場（`StringPool`）に取り込み、読み手は
  それを番号で引く。経路ごとの束縛（引数・コンストラクタの実引数・捕捉した値）は型付きの枠（`Slot`。種別と番号を
  詰めた `long`）で、経路を歩く間に文字列を作らない
- 値が `| ; { }` を含んでも正確に読む（Q11）。`test/regression/values` の期待値は、特性として記録していた誤った出力から
  正しい出力に変わった。ほかの `expected*/` は変わらない
- 引数を使うメソッドかの判定（`DataflowFacts.usesParameters`）は、文字列の中の `=A:` を探すのをやめ、部分木の種別で
  決める（文字列リテラルの中の `=A:` を数えない。数えても束縛する値が増えるだけで、出力は変わらない）
- 消したもの: `OriginRenderer`、`CallGraph` の文字列の列と読み口（`recvOrigin` / `argOrigins` / `guard` /
  `returnOriginsOf` / `fieldOrigin`、共有プール `originPool` と `internOrigin`）、`FieldFacts` の文字列での判定、
  `DataflowFacts.factoryOrigin`、`Origin` の読み口（`argsOf`・`argAt`・`entryAt`・`entriesOf`・`unnest`・`receiverOf`・
  `staticReceiverOf`・`argCountOf`・`constantValueOf`）、`Guard` の読み口と読み手に渡していた文字列の形
  （`atomsOf`・`fieldOf`・`valuesOf`・`atom`・`join`・`ATOM_SEP`・`FIELD_SEP`）。`Origin` に残るのは種別の文字と、
  書き手（`OriginTracker`・`ValueGraph`）と人が読むための出力（`CacheDump`）が使う道具だけ
- 修飾する型（C 行の qualifier）も文字列の置き場に置く。エッジの一時ファイルの記録は、移し替えの間の 46 バイトから
  34 バイトに戻った
- キャッシュの形式は変えていない（版も上げていない）。書き手も変えていない
- 解析結果が持ち続けるヒープは、このツールの src で 17%、長いメソッドチェーンの題材で 73% 減った（Q17）

### Q11. なぜ出所の文字列ではなく、ノードの表で読むのか

出所の文字列の文法は `|`（実引数リスト）・`;`（要素）・`{}`（入れ子）・`=`（鍵）を区切りに使い、エスケープを持たない。
値そのもの（文字列リテラル・定数）がこれらを含むと、読み手が途中で切って別の値に読み違えていた。どれも呼び出しを
黙って落とすか、違う先へ繋ぐ（`test/regression/values` の V2〜V7、`test/pruning` の `SemiArg`・`PipeArg`・
`BraceArg`・`SepPipeKey`・`SepSemiKey`・`HolderSemi`）。

- `parse("x", ";")` の先の `if (";".equals(delim)) semicolon();` を `[UNREACHABLE] … = )` にする（実引数が空文字に見える）
- `"a|c"` を渡した経路で `if (!mode.equals("a|b")) notAb();` を `a` どうしと見て打ち切る
- 契約表のキー `get("USER|X")` を `get("USER")` の行に当てる
- `new Holder("a;r=K:x.Y")` のコンストラクタ注入の値を `a` と読み、残りをレシーバと取り違える

表はノードの構造（種別・値・実引数・レシーバ・書かれた型）を列で持ち、値は文字列の置き場の番号で指すので、
区切りと値を取り違えようがない。ほかにも次の点で文字列より良い。

- **大きさ**: 文字列は入れ子を親ごとに展開し直すので、同じ部分式を何度も持つ。`append(…)` が 300 段続く
  メソッドチェーン（計測の題材 `Chain.java`）では共有プールが 3.26 MB で、段数の 2 乗で伸びる。表は部分式を 1 つの
  参照で指すので 36 KB（Q17）
- **比較**: 値どうしは文字列の置き場の番号の比較、頭（種別と値）どうしは葉の参照の比較で済む（置き場は同じ中身を
  2 つ持たず、葉は種別と値の組ごとに 1 つ。test/dataflow の ValueStoreCheck が確かめる）
- **経路の値**: 以前は `"K:" + クラス名` / `"L:" + 文字列` を経路の段ごとに作っていた。枠は種別と番号の `long` なので作らない

却下した案:

- 文法にエスケープを足す。キャッシュは既に値をノードで持っているので、読み手のためだけの文法を直すことになる。
  読むたびに文字列を解析し直す手間と、入れ子を展開する大きさの問題も残る
- 読み口（`Origin.valueOf` など）を、境界を見て切るように直す。`a;r=K:x.Y` のように、文法の上でどちらにも
  読める文字列があるので、読み口をどう直しても区別できない
- 表を作らず、ブロックの値グラフ（`ValueNode` の並び）を持ち続ける。ブロックの番号はブロックの中でしか通じない
  ので、全体で比べるには結局番号を振り直すことになる。葉をまとめられないので頭の比較が文字列の比較になり、
  どこからも指されないノードも持ち続ける

### Q12. 表の形はどう決めたか

- **取り込むもの**: 戻り値（R 行は丸ごと）・フィールドへの代入（J 行は頭の葉だけ）・条件の判定される式（頭の葉だけ）・
  呼び出し箇所のレシーバと実引数から辿れるノードだけ。ブロックの番号から全体の参照へは、指されたときに子から順に
  移す（明示的なスタックで。子の参照は必ず親の参照より小さく、読み手は前から 1 回の走査で部分木を畳める）
- **項目の有無**: 以前の組み直しが文字列に書き出していたものとそろえた（new は実引数だけ、メソッド呼び出しと
  レシーバを束縛したメソッド参照は実引数・`n=`・`r=`・`s=`、それ以外は葉）。`n=` の有無などが読み手の分かれ道を
  決めるので、振る舞いを変えないため（`jche.graph.ValueStoreBuilder` の説明）
- **まとめ方**: 文字列はグラフ全体で 1 つ（開番地法の索引は作り終えたら捨てる。メソッドキーと同じ中身は
  メソッド表の `String` を共有する）、葉は全体で種別と値の組ごとに 1 つ、項目を持つノードはブロックの中だけ
  （書き手が同じ式を 1 ノードにした番号のまま）、呼び出し箇所の実引数の並びはブロックの中で列の文字列が同じなら 1 つ
- 作った後は変わらない。解析サーバーで複数のスレッドから読んでも鍵が要らない。解決の結果もエッジの処理順に
  依存しない（`test/dataflow` の ResolveOrderCheck）

却下した案: 項目を持つノードをブロックをまたいでまとめる。このツールの src で 3,457 個が約 3,446 個になるだけ
（1% 未満。設計時の見積もり）で、まとめるには構築中に表を読み返す索引が要る（構築は書き足すだけにしておきたい。Q18）。

### Q13. 条件の期待値を切り詰めないこと（P-G）を、なぜ切り替えの前提にしたのか

以前の書き手は期待値を出所の文字列から取り出していたので、最初の `|` で切れていた（`"a|b"` が `"a"`）。
読み手の側（経路の実際の値）だけを正確にすると、次の 2 つが**新しく**誤って打ち切られる。

- `eq("a|b")` の先の `if (m.equals("a|b")) hit();`（期待値 `a`、実際の値 `a|b`）
- `static final String MODE = "a|b";` の `if (MODE.equals("a|b")) hitConst();`（どの経路でも打ち切る）

そこで期待値を正確に持つこと（形式 v33 の G 行。Q4）を先に済ませ、読み手を移すまでは `GuardEvaluator` が期待値に
以前の切り方（`legacyCut`）を当てて出力を変えず、切り替えのコミットで一緒に外した。
`test/regression/values` の `Pipe`（`hit`・`hitConst`）と `test/pruning` の `PipeEq`・`PipeConst` が、
どちらか片方だけを直した状態で落ちる。

### Q14. 文字列の側の誤り 2 つ（B0a・B0b）を、なぜ切り替えの前に別に直したのか

切り替えは「経路の記録が 1 文字も変わらない」ことで確かめる（Q16）。型付きの枠では起きようのない誤りが
文字列の側に残っていると、切り替えで記録が変わり、どこまでが直したもので、どこからが移し替えの誤りか
見分けられない。そこで次の 2 つを先に文字列の側で直し、記録はその後で取った。

- **B0a**（`GuardEvaluator`）: 経路で束縛した引数が型（`:` を含まない FQN）でも、値として読んでいた。無名パッケージの
  型 `Kind` は先頭の `K` がクラスオブジェクトの種別に見え、値が空文字になって `k.equals("x")` を打ち切っていた。
  値（`:` を含むもの）だけを使うようにした（型付きの枠では、リテラル・クラス・定数の枠だけが値）。
  `test/pruning` の `/Kind`、`test/regression/values` の `Kind.java`
- **B0b**（`DataflowResolver` の `getClass()`）: コンストラクタ注入のフィールドを通って来た値（`L:x`）を型とみなし、
  リフレクションのシグネチャを `take(L:x)` と組んで、呼び出し `run → take` を黙って落としていた。型だけを使う
  ようにした（どの型のメソッドか分からなければ、名前の一致するメソッドを候補に残す側に倒れる）。
  `test/pruning` の `ReflField`、`test/regression/values` の `vals/Refl.java`

### Q15. 切り替えで見つかった、上書きされうるメソッドの戻り値の穴は

R 行の文字列リテラルをそのまま読むようになって（Q9）、「呼び出し先の宣言の本体が返す値」を「その呼び出しの
戻り値」として使っていた穴に当たる形が増えた。部分型が上書きしていれば、実際に動くのは上書きした本体かもしれない。
戻り値の値（R 行と、それを畳んだファクトリの事実）を使うのは、呼び出しがその宣言の本体でしか動かないとき
（`CallGraph#hasOverriders` が false）に限った。判定は CHA と同じ `implementationOf` で部分型ごとに引き、
`@Bean` メソッドだけは上書きした本体が返す型も登録する。詳しくは Q10。

### Q16. 切り替えが振る舞いを変えないことを、どう確かめたか。その検査をなぜ消したのか

移し替えの間（B1〜B5）は、文字列の側と表を両方作り（二重に持つ）、次の 2 つで確かめた。

- **ValueStoreCheck（文字列との突き合わせ）**: エッジごとのレシーバ・実引数・条件、メソッドごとの戻り値、
  フィールドの値について、表から組み直した文字列が文字列の側と 1 文字も違わないこと。さらに、組み直した文字列を
  以前の読み口で読んだ結果（種別・値・レシーバ・実引数の数・書かれた型・位置ごとの実引数・引数を含むか）が
  表の構造と一致すること。一致しない参照（あいまいな参照）は、値に文法の文字を含まない 10 設定で 0、
  `test/regression/values` では 12 個で、どれも部分木の値が `; | {` を含む（読み違いの原因がその文字である）
- **TraceCheck（経路の記録）**: 呼び出し階層を歩く中の差し込み口（`StreamingTreeWalker` の一時的な probe）で、
  段ごとの解決・打ち切りの理由・束縛した値・呼び戻し・ファクトリのキー・ひな形の左辺と、経路によらない事実
  （ファクトリの戻り値・戻り値の並び・フィールド・Bean・全エッジの解決・被参照数）を書き出し、切り替えの前に
  取った記録（10 設定・約 8,900 行）と比べた。B2・切り替え（B3・B4）・文字列の側を消した後（B5）のどれでも
  1 文字も変わらなかった（B5 は、消した差し込み口を使い捨ての複製にだけ戻し、消した読み口の出力は値の表から
  同じ形に作り直して比べた）

TraceCheck を消す前に、それが守っていた範囲を残す検査が守れているかを変異で測った。型付きの読み手の分かれ道
（`DataflowResolver`・`DataflowBuilder`・`GuardEvaluator`・`StreamingTreeWalker`・`FactoryCalls`・
`CallbackContracts`・`FieldFacts`・`SpringBeans`・`CallGraph` の上書きの判定・`CallGraphBuilder` の値の取り込み）を
1 行ずつ壊す変異 96 個を、1 つずつ植えて検査を流した（`test/pruning` → `test/regression` → `test/dataflow` の順に流し、
最初に落ちた検査に数える）。

| 検査 | 検出した変異 |
|---|---|
| TraceCheck があったとき（当時の `test/dataflow` ＋ `test/pruning` ＋ `test/regression`） | 80/96 |
| TraceCheck を消しただけ（`test/pruning` ＋ `test/regression` ＋ 今の `test/dataflow`） | 66/96 |
| 洗い出した穴の 18 ケースを `test/pruning` に足した後（今の形） | **82/96**（`test/pruning` で 66、残りを `test/regression` で 16。今の `test/dataflow` だけでは 0） |

TraceCheck を消しただけでは、TraceCheck だけが検出していた 14 個が素通りになり、うち 8 個は呼び出しを
黙って落とす取り違えだった（親のフィールドの持ち主・リフレクションの受け手の具象型・引数で渡った Class・契約表の実引数の位置・
呼び戻しの 2 番目以降の実引数・継承したメソッドへのコンストラクタ実引数・static や値の食い違うフィールド）。
TraceCheck も含めてどの検査も検出していなかった 4 個（引数で渡ったメソッド参照・return が 2 通りの `@Bean`・
private でも final でもないフィールド・setter でも代入するフィールド）もあわせて、`test/pruning` の
「経路の記録（TraceCheck）を消すときに…洗い出した穴」の節にケースを足した。

足した後も残る 14 個と理由は次のとおり。同値か保守側に倒れるだけのものが大半だが、最後の 3 個は
検出できていない（試した題材では出力が変わらなかった）ことをそのまま記録しておく。

- 同値（後段が同じ判定をしている）: `DataflowResolver#typeAt` の型の枠の絞り込み（DR03。呼び手が
  `Slot.isType` を見直す）、`paramValueOf` の値の枠の絞り込み（DR15。受け取る側が枠の種別を見る）、
  `CallGraph#dispatchesElsewhere` の final とラムダの本体の早期の判定（F3・F12。後の `implementationOf` の探索でも
  上書きは見つからない）、`FieldFacts#agreedHeadOf` の頭が分からない代入の除外（FF08。頭の無い代入の除外に含まれる）
- 解析対象に無い型名の除外（DR05・DR11・`DataflowBuilder` の DB04）。外しても、その型名からは実装も
  コンストラクタも引けず、同じく決まらない側に倒れる（DB04 は 3 つの出力が 1 バイトも変わらないことを確かめた。
  TraceCheck が検出していたのは、出力に出ないファクトリの戻り値の事実まで書き出していたため）
- 保守側に倒れるだけ: 委譲するコンストラクタを起点から外す判定（FF07。外さないと代入がそろわず絞らない）、
  呼び戻しのコンストラクタ実引数をレシーバが `new` のときだけ読む判定（CB03。外すと候補が増えるだけ）、
  レシーバの部分木の引数を「経路の引数を使う」に数える判定（DB01。外すと経路の値を渡さず、分からない側に倒れる）
- 検出できていない: メソッドが返す Class を文字列の枠で渡す（DR16。違いが出るのは Class が引数を通って
  ファクトリに届いたときのひな形のキーだけで、TraceCheck はその左辺を書き出していたので検出していた）、
  捕捉した引数を値として渡す枠（DR18）、戻り値を畳むときの種別の比べ（S5。値の番号が同じで種別だけが違う
  戻り値の組、たとえば同じ名前の `new` と文字列が要る）

移し替えが終わったので、文字列の側と比べる部分（差し込み口・TraceCheck と記録・`LegacyRender`・`LegacyOrigin`・
ValueStoreCheck の突き合わせ）と、記録のためだけの題材 `test/dataflow/projects/paths` を消した。比べる相手の
文字列の側がもう無く、記録は行番号や並びまで固定するので、正当な変更のたびに取り直すことになり、取り直しが
素通しになるため。残したのは次のとおり。

- 振る舞い: `test/pruning`（値の読み取りの分かれ道ごとの呼び出しの有無）と `test/regression/values`（期待値の比較）
- 表の決まり: `test/dataflow` の ValueStoreCheck（子 < 親、項目の並び、葉と文字列の一意、メソッドキーの共有、
  頭は葉、戻り値の重なり、修飾する型の番号、I0 / I1 ＝ new の型・型階層の型名・メソッド表の型が `:` を含まない。
  I0 / I1 は、枠が型とそれ以外を取り違えないための前提）と StoreUnitCheck（書き手が作らない行の扱い）

却下した案:

- 以前の読み手を丸ごと凍結した複製（2,000 行を超える）と比べ続ける。複製の保守が本体の保守より重くなる
- 記録（golden）を恒久の検査として残す。上のとおり、取り直しが素通しになる

### Q18. 表の列をメモリに置かない形（一時ファイルへの写像）は、なぜ見送ったか

設計はしてある。列はどれも固定長で、構築は書き足すだけ（構築中に表を読み返さない。葉は一時的な索引で、
ほかはブロックの番号の対応で引く）なので、列のバイト数がしきい値を超えたらキャッシュのフォルダの一時ファイル
（エッジの一時ファイルと同じ命名・開始時の掃除・`finally` での削除）へ書き流し、作り終えたら読み取り専用で写像して
`IntBuffer` などで引ける。列は外に出さず番号で引く作り（`ValueStore` の説明）にしてあるので、変えるのはクラスの中だけで済む。

見送ったのは、Q17 の数字では割に合わないため。

- このツールの src で、表は解析結果 2.91 MB のうち 377 KB（13%）。写像できるのは列の 194 KB（7%）だけで、
  文字列の置き場は写像できない（読むたびに文字列を作り直すことになる）
- 呼び出し箇所 100 万（このツールの src の約 90 倍）に伸ばすと、列はおよそ 17 MB、文字列の置き場はおよそ 15 MB。
  一方、エッジの CSR（エッジ 1 本あたり 30 バイト）は 30 MB で、こちらの方が大きい。写像するならエッジの配列と
  同じ仕組みでまとめて行うべきで、表だけを先にする理由が無い
- ヒープの山はフェーズ 1（JDT の構文解析と型解決）で、1,000 ファイルの解析で回収前の最大 842 MB に対し、
  生きている量は 20 MB だった（`ast-analysis-performance-qa.md` の「計測のしかた」）
- Windows は写像を外すまでファイルを消せないので、残ったファイルを次の起動で掃除する経路が要る。解析サーバーは
  解析をやり直すたびに写像の寿命を管理することになる

却下した案（写像以外）:

- 構築の始めから列を塊ごとに分けた `IntBuffer` にして写像できる形で持つ。値の表は小さいので、Windows と解析サーバー
  での寿命の管理が、減るヒープに見合わない
- 経路の文脈（`DataflowContext`）を書き換えられる形にして枠を使い回す。経路の段ごとに持つ文脈を別の段と
  取り違える（エイリアス）誤りを招く。今の形は段ごとに作った文脈を書き換えず、段の中で 1 つを使い回す
- 束縛した値を小さなレコード（オブジェクト）にする。読みやすいが、経路を歩くたびに束縛した値の数だけ作る
- 文字列の置き場を作り終えた後も伸ばせる形にして、B0b の誤った値（型の位置に来た値の文字列）も置けるようにする。
  誤りを残すためだけの仕組みになるので、先に誤りを直した（Q14）

## 鍵と版の上げ忘れ（形式を変える前の準備）

対応の要点:

- ヘッダ行の鍵に JDT の版 `jdt=<core の Bundle-Version>+<ecj の Bundle-Version>` を足した（`jche.analysis.JdtVersion`）。
  サーバーモードの `HELLO` も同じ値を返す
- 版が読めなければ `?` と書き、`?` を含む鍵は一致しないとみなす（`CacheReader.headerMatches`）
- 形式の版（`CacheFormat.VERSION`）の方針を「事実の意味・列・収集範囲が変わったときだけ上げる」から
  「迷ったら上げる。上げ忘れは検査で捕まえる」に改めた（AGENTS.md・`CacheFormat`・cache-design.md）
- `test/cacheversion/run.sh` を足した（CI にも足した）

### Q19. JDT の版をなぜ鍵に入れたのか。`?` はなぜ一致しないとみなすのか

キャッシュの事実のうち、呼び出し先・親型・定数の値はバインディング解決の結果で、JLS の読み方や
条件の説明の文字列（`Guard` の text）も JDT が決める。JDT を上げると同じソースから違う事実が出うるのに、
鍵に入っていなかったので、JDT を上げても古い事実を再利用していた。実行 JDK（`jdk=`）はもう鍵に入っていたので
（[cache-dependency-jars-qa.md](cache-dependency-jars-qa.md) の Q20）、それと同じ扱いにした。

- **core と ecj の両方を持つ。** AST と `JavaCore` は `org.eclipse.jdt.core`、型解決をするコンパイラ本体は
  `ecj`（Bundle-SymbolicName は `org.eclipse.jdt.core.compiler.batch`）で、同じ 3.46.0 でも日付の修飾子が違う。
  片方だけでは、もう片方だけを差し替えたときに気づけない
- **実行時に jar の MANIFEST から読む。** `//DEPS` の版は実行時に読めず、プラグインの `lib/` から動くときは
  `//DEPS` 自体が無い
- **`?` は一致しないとみなす。** クラスフォルダから動かしている等で MANIFEST が読めないと版が分からない。
  `?` どうしを一致とみなすと、JDT を差し替えても `?` のままなので古い事実を再利用してしまう。
  分からないなら再利用しない（毎回全件解析になるが、結果は正しい）

JDT の版と JDK のメジャー版は鍵に入っているので、それらを変えるだけなら形式の版は上げなくてよい
（古いキャッシュはヘッダ行で自動で捨てられる）。

### Q20. 形式の版を上げる基準を、なぜ「迷ったら上げる」にしたのか

以前の基準は「事実の意味・列・収集範囲が変わったときだけ上げる。読み手だけの変更では上げない」だった。
基準そのものは正しいが、「この変更は事実を変えるか」を人が判断するところで上げ忘れが起きていた。

- 列を変えたのに上げず、`recvKey` を `recvKind` として読んでいた（[cache-split-qa.md](cache-split-qa.md) の Q22）
- 条件の説明の文字列（`Guard` の text）は書き手が作るので、文言を変えるだけでも上げる必要があった
  （[nls-qa.md](nls-qa.md) の Q7）

上げ忘れの壊れ方は「エラー」ではなく「再利用したファイルだけ古い事実のまま残る、静かに違う結果」で、
差分更新の履歴によって出力が変わる。上げたときの費用は「利用者の手元で 1 回だけ全件解析になる」だけで、
結果は正しい。費用が片側に偏っているので、迷ったら上げる側に倒し、判断の誤りは検査で捕まえることにした。

読み手だけの変更（解決の方針・CSV の列・フィルタ・注記の文言）では事実が変わらないので、上げなくてよいことは変わらない。
stage B（読み手を値の表へ移した）がその例で、書き手を変えていないので版は v33 のまま。

### Q21. 上げ忘れをどう捕まえるのか。何を捕まえられないのか

`test/cacheversion/run.sh` は、決まった題材（`test/demo`・`test/incremental`・`test/jls/project`）を全件解析した
キャッシュのブロックの中身から指紋を作り、`test/cacheversion/facts.txt` の記録と比べる。記録には版・環境
（`jdk=` と `jdt=`）・題材の指紋・事実の指紋を持つ。

| 状態 | 判定 |
|---|---|
| 版・環境・題材が記録と同じなのに、事実の指紋が違う | **落とす**（書き手の変更で事実が変わった。版を上げてから `--update`） |
| 版が記録と違う | 落とす（版を上げた。`--update` で記録を合わせる） |
| 環境が記録と違う | 落とす（鍵に入っているので版は上げなくてよい。`--update` で記録を合わせる） |
| 題材が記録と違う | 落とす（題材の変更だけなら版は上げずに `--update`。書き手も変えたなら版も上げる） |

比べるのはブロックの中身だけで、ヘッダ行・L 行（jar の絶対パスを含む）・T 行・最終行は外す。ブロックはパスの順に
並べ替える（差分更新でブロックの並びが変わっても、同じ事実なら同じ指紋になる）。記号や値の番号はブロックの中だけで
振るので、ブロックを並べ替えても変わらない。

捕まえられないもの:

- **題材に現れない事実の変更。** 題材に無い構文の書き方だけを変えた場合は指紋が変わらない
- **題材と書き手を同じコミットで変えた場合。** 「題材が変わった」としか言えず、版を上げるかどうかは人が判断する
- 逆に、事実の意味が同じでもバイト列が変わる変更（行の並び・書式）は落ちる。これは「迷ったら上げる」側の
  誤りなので受け入れる

却下した案: キャッシュのヘッダにツール自身のソースのハッシュを入れる。書き手と関係の無い変更（読み手・CSV・文言）の
たびに全員のキャッシュが捨てられ、差分更新の意味が薄れる。

## 1 ファイルにまとめる（形式 v31）

対応の要点:

- `analysis-cache.tsv` の 1 ファイルにした。`DATAFLOW_VERSION` は無くし、版は 1 つ（`jche-cache-v31`）
- ファイルの並びは「ヘッダ行（`jdt=` まで。`gen=` は無い）→ L 行 → T 行 → ブロック → Z 行」。ブロックの中の並びは
  v31 では `F I S N R H D O V C/U M A K J X`（v33 で `F I S N G R H D O V C/U M A K J`）
- 呼び出し箇所の値（レシーバ・実引数のノード番号、ガード）は C 行・U 行の末尾の列に持つ。P 行と、それを結びつける
  鍵（行番号・呼び出し元・呼び出し先の表示名・通し番号）を無くした
- メソッドを指す列は、ブロック内の記号表（S 行）の番号にした。目で追うときは `jche.cache.CacheDump` で
  以前の 4 列の形に戻せる
- 列の符号化を 1 つの規則（`escape` / `unescape`）にし、行は OS によらず `\n` で終える
- F 行に未解決数（使える候補の無い U 行の数）と crc（ブロックの残りの行の CRC32。v36 から F 行自身も入れる。Q59）を
  足した。crc が合わないブロックは無効にして、そのファイルと、そのファイルの型を使うファイルを解析し直す（Q25）。
  中断した実行からの引き継ぎでも同じ検査をする（合わないブロックは引き継がず、そのファイルを解析し直す）
- 以前の形式の `dataflow-cache.tsv`（と `.tmp` / `.partial`）が残っていれば、実行の最初に消す（`Log.info`）
- 読み手はメソッドを以前と同じ順に ID 化する（R 行を D 行より前に置く）ので、出力は 1 バイトも変わらない
- test/demo のキャッシュは 2 ファイル合計 154,741 バイト（6227970）から 97,760 バイト（212d497。−37%）になった

### Q22. なぜ 1 ファイルにしたのか

分けた基準は「呼び出し階層（`call-hierarchy.csv` / `methods.csv`）の出力に使うか」だった
（[cache-split-qa.md](cache-split-qa.md) の Q1）。だが値（値グラフ・戻り値・代入・ガード）も、具象クラスの解決
（`DATAFLOW_*`・`REFLECTION`・`@Bean` の登録）と条件分岐の打ち切り（`[UNREACHABLE]`）を通じて出力に効く。
cache-split-qa.md 自身も途中で「値に関わる事実はすべて dataflow 側へ」と境界を動かし（Q11）、analysis 側だけでは
CHA 止まりになると認めていた。つまり 2 つはいつも対で読まれ、片方だけでは出力が作れない。

分けたことの利点として挙げていたものも成り立っていなかった。

- **再パースの節約**: どちらかを作り直すにはそのファイルをパースし直すことになり、パースすれば両方の事実が出来る。
  「片方だけ生き残る」ことで節約できる時間は無い（cache-split-qa.md の Q12 がそう書いている）
- **版を独立に上げられる**: 対の不変条件でどちらかの版が違えば両方捨てるので、捨てる範囲は同じ。
  片方の版だけ上げて起きた不具合もあった（中断した実行の dataflow 側の退避ファイルのヘッダを確かめていなかった）

残っていたのは、対を保つための仕組みだけだった。

- 両方のヘッダの世代の印（`gen=`）と、最終行のブロック数の突き合わせ（末尾だけを読む `lastLineOf`）
- 片方にしか無いブロックを落とすパス1b、dataflow 側を書き写すパス5b
- 2 つを歩調を合わせて読む `DataflowBlockReader`
- P 行を C 行・U 行に結びつける自己記述の鍵（行番号・呼び出し元・表示名・通し番号）と、食い違ったときに値を捨てる経路
  （ダイヤモンドの `new`（`<factory>`）で実際に食い違い、値を捨てて警告を出していた）
- 一時ファイル・退避ファイルが 2 つずつ

1 ファイルにすると、これらはどれも要らなくなる。値は呼び出し箇所の行に直接持つので結びつけ自体が無く、
食い違いようが無い。読む回数も、ファイルごとに数えて 10 回（何も変わらない実行）が 6 回になった。

却下した案: 2 ファイルのまま、対の仕組みを直す（退避ファイルのヘッダも確かめる、結びつけの鍵を強くする）。
直すたびに仕組みが増えるだけで、分けたことで得るものが無い。

### Q23. ブロックの中の行の並びはどう決めたか

読み手は 1 ブロックを前から 1 回読むだけで済むように、「指される側を先に」並べる。v33 で決めた並び（v37 の今も同じ）と理由:

| 行 | 置き場所の理由 |
|---|---|
| F | ブロックの区切り。同一性（パス・サイズ・内容ハッシュ）と件数と検査値を持つ |
| I | 必ず F の直後。差分更新のパス1 は F と I だけで依存の索引を作れる |
| S | 記号を使う行（R・D・O・C・U・M・A）より前 |
| N・G | 値を指す行（R・J・C・U）より前。G の subject は N を指す |
| R | D より前。読み手は行を読んだ順にメソッドを ID 化するので、以前の形式（R 行を F 行の時点で ID 化していた）と同じ ID の順になる |
| H・D・O・V | 型・宣言・上書き・フィールド宣言。O は D の後 |
| C / U | ソース上の順のまま混ぜる（import からの推定をエッジにしたとき、元の呼び出しの並びが保たれる） |
| M・A・K | ラムダの実装箇所・フィールドの参照箇所・定数。K はフェーズ1（定数の連鎖）だけが読む |
| J | 最後。フィールドへの代入は同じブロックの V 行・D 行と組で判定するので、読み手はブロックを読み終えてから渡す |

R を D より前に置いたのは、この段で出力を 1 バイトも変えないため（メソッド ID の順で同着を決めている出力が
あった）。その後、同着を ID で決めるのをやめたので（Q30）、今は ID の順が変わっても出力は変わらない。
並びを変えるときは、書き手（`CacheUpdater.writeBlock`）・読み手・`test/incremental` の `check_rows` をそろえて直す。

見送った案: 構造の行と値の行をブロックの中で分け、F 行に構造の部分の長さを持たせて、値を読まない指定
（`dataflow.enabled=false`）のときに値の部分をバイトで飛ばす。1 ファイルにして、値を読まない指定でも読む量は値の分
（2 ファイルのころの test/demo で 4 割ほど）増えたが、値を読まない指定は既定ではなく、読み手は行を種別で読み飛ばすだけで済むので見送った。

### Q24. メソッドをなぜ記号表で指すのか。なぜファイル全体で 1 つの表にしないのか

C 行は呼び出し元と呼び出し先をそれぞれ 4 列（パッケージ・型・名前・引数）で書いていて、同じメソッドが
ブロックの中で何度も繰り返されていた。ブロックの先頭の S 行（`S 番号 pkg typeFqn name paramSig`）に 1 回だけ書き、
ほかの行は番号で指す。test/demo で 2 ファイル合計から 36% 減ったうちの多くがこれと、P 行の鍵が無くなった分。

番号はブロックの中だけで通じる（0 から詰めて、行を書く順に初めて現れた順に振る。同じ解析結果からは同じ番号）。
ファイル全体の表にしない理由は、**差分更新がブロックをそのまま書き写すため**。全体の表では、1 つのファイルを
解析し直すたびに番号が変わりうるので、書き写すブロックの番号を振り直すことになる。そうすると書き写しで
全ブロックを読み直して書き換えることになり、バイトの範囲のまま写す（Q31）ことも、中断した実行の退避ファイルから
ブロックを引き継ぐこともできなくなる。値グラフのノード番号（N 行）・ガード番号（G 行）も同じ理由でブロックの中だけで通じる。

読み手は S 行を読んだ時点ではメソッドを ID 化せず、その番号を指す行を読んだときに ID 化する（以前と同じ ID の順にするため）。
番号がブロックの外を指す行（手で編集したキャッシュ）は、1 度だけ警告して（`cache.badReference`）その行・その値を使わない。

### Q25. 壊れたブロックのファイルだけを（全件ではなく）解析し直すのはなぜか。どう見分けるのか

以前、キャッシュの壊れ方への備えは 2 つだけだった。最終行の印（Z 行とブロック数）で途中で切れたことに気づき、
UTF-8 として読めないバイトで気づく。どちらも丸ごと捨てて全件解析し直す。行の形を保ったまま中身だけ変わった
ブロック（手で編集した、ディスクやコピーの異常で文字が別の正しい文字に化けた）には気づけず、そのまま再利用していた。

F 行の最後の列に、ブロックの残りの行（F 行の次から、次の F 行・Z 行の手前まで。各行に `\n` を付けたバイト列）の
CRC32 を持つ（v36 からは F 行自身も crc 列を空にした形で先頭に入れる。Q59）。書き手はブロックをメモリ上で組んでから検査値を求めて書く（記号表を先に書くには、どのみちブロックを
組み終える必要がある）。差分更新のパス1 はブロックごとに生のバイトから計算し直し、合わなければそのブロックだけを
無効にする。

- **全件ではなく、そのファイルと、それに依存するファイルを解析し直す。** 1 ブロックが壊れただけで全件解析にする
  理由は無い。ほかのブロックの事実は無傷で、差分更新と同じく「そのファイルが変わった」として扱えば、依存するファイルも
  通常どおり解析し直される（壊れたブロックが宣言していた型を「変わった型」に入れる。壊れたブロックからは前回の事実の
  何が変わったかを言えないので、型の形や定数を比べて連鎖を止めることはしない）。`test/regression` の `cacheblocks` の
  3 回目（ほかから参照されない型だけを宣言する Deep.java を壊す）は 1 件、8 回目（F 行の件数を書き換えたファイル。
  その型を使うファイルが 1 つある）は 2 件を解析し直す
- **番号がブロックの外を指す壊れ方もこれで捕まる。** 記号やノードの番号を書き換えた行は検査値が合わない。
  それでも読み手は番号の範囲を確かめる（Q24。呼び出しを黙って落とさないため）
- **利用者が対処することではない**ので、`[cache]` で始まる情報のログを 1 行出すだけで、`warnings.txt` には載せない
- 型解決できなかった呼び出しの件数（ログの警告）は、F 行の未解決数から数える。再利用したファイルの件数も
  U 行を読まずに同じ値になる（`test/regression` の `cacheblocks` が、再利用・1 ブロックの解析し直しで件数が変わらないことを見る）

最終行の印と UTF-8 の厳密な読み取りは残した。途中で切れた・読めないキャッシュは、どのブロックが無事かを
言えないので、これまでどおり丸ごと捨てる。

却下した案:

- **ファイル全体の検査値。** 壊れたことは分かるが、どのブロックかは分からず全件解析になる。書き写しのたびに
  全体を計算し直すことにもなる
- **行ごとの検査値。** 行が増えるぶん大きくなり、ブロック単位で再利用を決めるのに行単位の細かさは要らない
- **暗号学的なハッシュ（SHA-256 など）。** 守りたいのは偶然の壊れ方で、わざと作った衝突ではない。CRC32 は
  `java.util.zip` にあって速い

### Q26. 列の符号化を、なぜ 1 つの規則にしたのか

以前は 2 つの規則があった。analysis 側はタブ・改行を空白に置き換えて捨てる（`clean`。値を失う）、dataflow 側は
バックスラッシュで符号化する（`escape`。値を失わない）。1 ファイルに 2 つの規則が混ざると、列ごとに「どちらで
書いたか」を書き手と読み手で覚えておくことになり、取り違えると静かに値が変わる。

どの列も `CacheFormat.joinRow` が `escape` で書き、`CacheFormat.columnsOf`（`CacheReader.columns`）が `unescape` で戻す。
record の `toRow` は生の値を渡し、`fromRow` は戻した値を受け取る（二重に符号化しない）。バックスラッシュを含まない列は
そのまま返すので、読む手間はほとんど増えない。値を**拾わない**判断（タブ・改行を含む定数の値を K 行ではハッシュにする、
注釈の値を持たない）は事実を作る側の判断で、符号化とは別のまま残した。`test/cachevalue` が全列で往復することを見る。

### Q27. 行の区切りを、なぜ OS によらず `\n` にしたのか

以前は `BufferedWriter.newLine()` で書いていたので、Windows では CRLF になっていた。次の段（読む回数を減らす。Q31）で
ブロックの位置をバイトで覚え、バイトの範囲のまま書き写すことを見込んで、行の区切りのバイト数を OS で変えないことにした。
どの OS で書いても同じバイト列になり、検査値（Q25）も同じになる。

読むときは CRLF も受け付ける（以前の版や、改行を変えるツールを通したキャッシュ）。そういうキャッシュは
「書き手の書くとおりの形ではない」ので、何も変わっていなくても 1 回だけ `\n` で書き直す（Q33）。

### Q28. 人が目で追うにはどうするか

記号表の番号では、どのメソッドの行かが目で追えない。`jche.cache.CacheDump` はキャッシュを、記号を以前の 4 列に
戻し、R 行・J 行・G 行の値のノードを出所の表記（`T:…` / `M:…|0=L:…`）にした形で書き出す（S 行は出さない）。
1 行 1 行のまま出すので `grep` できる。`test/jls` と `test/ctorbody` は、このダンプに対して列を当てる。

```bash
java -cp <ツールのクラスと JDT の jar> jche.cache.CacheDump .cache/<プロジェクト>/analysis-cache.tsv
```

### Q29. ほかに何を消し、何を直したか。どう検査したか

消したもの:

- ヘッダの世代の印（`gen=`）と、それを作る・比べる道具（`withGeneration`・`generationOf` など）
- 末尾の 512 バイトだけを読む `CacheReader.lastLineOf` と、その境界を検査していた `test/cachetail`。
  2 つのファイルの最終行を安く突き合わせるためだけにあった。最終行の印はパス1 が先頭から読んで確かめる
- パス1b・パス5b、`DataflowBlockReader`、P 行の結びつけの鍵と、結びつけの食い違いの警告
- `Config` の `dataflowCacheFile`（以前のファイル名は、消すためだけに `LEGACY_DATAFLOW_CACHE_FILE_NAME` に残す）

あわせて直したもの（この形式に移す前からの不具合）:

- 一括解析の途中で書き出し側が実行時例外を投げると、そのファイルが失敗とも報告されずにキャッシュと出力から
  黙って欠けていた（`CallEdgeExtractor`）。失敗したファイルとして数えて報告する。書き手は呼び出し箇所と値の数が
  食い違えば例外にするので、この経路が要る
- 中断した実行の dataflow 側の退避ファイルは、ヘッダと世代を確かめずに書き写していた（1 ファイルにする直前に
  直し、1 ファイルにして仕組みごと無くなった）

検査:

- `test/regression` の `cachesplit` を `cacheblocks` にした。そのまま再利用、1 ブロックの中身を書き換える（検査値が合わない）
  とそのファイル（ほかから参照されない型だけを宣言するファイルを選んである）だけ解析し直す、最終行のブロック数の書き換え・削除と先頭 8 KB より後ろの文字化けでは丸ごと作り直し、
  解析は失敗させない。どの実行のあとも、キャッシュが 1 ファイルだけで、各ブロックの検査値とブロック数が合っていること、
  型解決できなかった呼び出しの件数が変わらないこと
- `test/regression` に `novalues`（`dataflow.enabled=false`）を足した。期待値は 1 ファイルにする前のコードの出力
- `test/incremental` は、ブロックごとに（F 行のパスの順に並べ、ブロックの中の並びは保って）差分更新と全件解析を比べる。
  番号がブロックの中だけで通じるので、全行をまとめて並べ替えると比較の意味が無くなるため。行の種別と並び（`check_rows`）、
  記号・ノード・ガードの番号の範囲（`check_refs`）、1 ブロックの中身を壊したら全件ではなくそのファイル（と依存するファイル）だけ
  解析し直すこと、
  退避ファイルの壊れたブロックを引き継がないこと、以前の `dataflow-cache.tsv` を消して `warnings.txt` を作らないことを見る
- `test/cachevalue` は `joinRow` とキャッシュの読み取りを通して往復することを見る

## 出力の並びをメソッド ID に依らせない

### Q30. 1 ファイルにしたことと、どう関わるのか

メソッド ID はキャッシュを読んで初めて ID 化した順に振られ、その順はブロックの並び（差分更新で解析し直したファイルが
先頭に来る）と、どの行が先に指したかで変わる。`methods.csv` の行順・起点の並び・サーバーの `AT`・名前だけで引く
リフレクションの候補が、同じ行に並ぶ宣言の前後を ID で決めていたので、同じソースでも全件解析と差分更新とで
並びが入れ替わっていた。1 ファイルにする段で R 行を D 行より前に置いたのは、この依存を崩さないためだった（Q23）。

宣言行 → ファイルの中の宣言の順番（ブロックの何番目の D 行か）→ キーの文字列で決めるようにした。これで
ブロックの中の行の並びを変えても出力の並びは変わらない。詳しくは
[deterministic-row-order-qa.md](deterministic-row-order-qa.md) の Q14〜Q19。

## 読む回数を減らす（ヒープは増やさず、一時ファイルで補う）

対応の要点:

- `CacheReader` をバイト単位の読み取りにした。`\n` で分け、行末の `\r` を落とし、厳密な UTF-8 で復号する
  （化けたバイトはこれまでどおり例外にして、キャッシュを捨てる）。行の位置がバイトで分かり、検査値も生のバイトで取る
- 差分更新のパス1 で、有効なブロックの位置（バイト）と F 行の件数を配列に覚え、依存（I 行）を一時ファイルの索引に書く。
  パス3（定数の連鎖の周回ごと）はその索引だけを読む。パス5 は有効なブロックをバイトの範囲のまま写す（復号しない）
- 何も変わっていなければ（書き直しても同じバイト列になるなら）、キャッシュに触らない
- 中断した実行からの引き継ぎで、クラスパスを走査し直さず、退避ファイルの L 行と今回の走査の結果を比べる
- グラフを 1 回の読み取りで組む。エッジはいったん一時ファイルへ固定長で書き、呼び出し元ごとの本数が分かってから
  ちょうどの大きさの配列へ読み戻す
- 型解決に失敗した呼び出しの一覧（`call-hierarchy.csv` の末尾）は、グラフを組む読み取りで一時ファイルへ集める
  （解析サーバーは一覧を書かないので集めない）。一覧を書くときにキャッシュを読み直さない
- 一時ファイルは一意の名前で作り、開いたまま使い、`finally`・JVM の終了フック・次の実行の最初の掃除で消す。
  GitHub Actions のアクションもキャッシュの保存の前に消す
- 出力は変わらない（回帰テストの期待値はそのまま。2,000 ファイルの合成プロジェクトでも、変更前と CSV・キャッシュの
  バイト列が一致することを確かめた）

### Q31. 何回読んでいたのか。何回になったのか

1 ファイルにした時点（v31）で、1 回の実行はキャッシュを次のように読んでいた（先頭のヘッダ・L 行・T 行だけを読むものは数えない）。

| 段 | 読み方 | 何も変わらない | 1 ファイル変えた | キャッシュ無し |
|---|---|---|---|---|
| フェーズ1 パス1 | 同一性・検査値・K 行の指紋 | 1 | 1 | 0 |
| フェーズ1 パス3 | 依存（F 行の次の I 行）。連鎖の周回ごと | 0 | 1 | 0 |
| フェーズ1 パス5 | 有効なブロックを行に戻して書き写す | 1 | 1 | 0 |
| フェーズ2 | ID 化と本数の数え上げ、エッジの流し込み | 2 | 2 | 2 |
| フェーズ3 | 型解決に失敗した呼び出しの一覧（順位づけと書き出し） | 2 | 2 | 2 |
| 計 | | **6** | **7** | **4** |

今は次のとおり。

| 段 | 読み方 | 何も変わらない | 1 ファイル変えた | キャッシュ無し |
|---|---|---|---|---|
| フェーズ1 パス1 | 同一性・検査値・K 行の指紋。位置と件数を配列に、依存を索引に | 1 | 1 | 0 |
| フェーズ1 パス3 | 依存の索引（小さな一時ファイル）だけを読む | 0 | 0 | 0 |
| フェーズ1 パス5 | バイトの範囲のまま写す（復号しない。何も変わらなければ写さない） | 0 | 0 | 0 |
| フェーズ2 | 1 回。エッジは一時ファイルへ | 1 | 1 | 1 |
| フェーズ3 | 一時ファイルから | 0 | 0 | 0 |
| 計 | | **2** | **2** | **1** |

どれも、読む手間を減らすためにヒープを増やさないことを条件にした（Q32）。

却下した案: キャッシュの中にブロックの目録（ブロックごとの位置・同一性・件数・依存を並べた末尾の表）を持ち、
パス1 も行を読まずに済ませる。読む回数はさらに 1 回減るが、書き写すたびに目録を作り直すことになり、目録と
ブロックの食い違いという、2 ファイルの対と同じ種類の整合の問題を持ち込む。パス1 は検査値を確かめるために
どのみち全ブロックのバイトを読むので、減るのは復号の手間だけである。

### Q32. 索引や中間のデータを、なぜヒープではなく一時ファイルに置くのか

利用者の優先順位が「ヒープを小さく保つ方が、読む回数を減らすより大事」だから。大規模なコードベースで
`OutOfMemoryError` にならないことはこのツールの前提で（[cache-design.md](cache-design.md)）、読む回数を減らすために
キャッシュの中身をヒープに溜めると、その前提を崩す。一時ファイルはキャッシュと同じフォルダに置き、順に書いて
順に（または位置を指定して）読むだけなので、ヒープに残るのはブロックあたり数十バイトの配列だけになる。

| 中間のデータ | ヒープに置いた場合 | 一時ファイルにした形 |
|---|---|---|
| 有効なブロックの依存（I 行） | 依存の型名の総数に比例する文字列 | `analysis-cache.tsv.deps-*.tmp`（依存の無いブロックは書かない） |
| エッジ（呼び出し元ごとの本数が分かるまで） | 呼び出し元と呼び出し先の配列を足して、エッジ 1 本あたりおよそ 42 バイトの山 | `analysis-cache.tsv.edges-*.tmp`（1 本 34 バイト） |
| 型解決に失敗した呼び出しの行 | クラスパスが足りないと呼び出し箇所の数割になり、フェーズ2 からフェーズ3 の木の出力まで持ち続ける | `analysis-cache.tsv.unresolved-*.tmp`（行のあるブロックだけ位置の索引を持つ） |

ヒープに残すのは、有効なブロックのバイトの位置（開始・終了）と F 行の件数（エラー数・構文エラー数・未解決数）だけ。
以前は F 行ごとにパスの文字列を持っていたので、ブロックあたりでは同じくらいか少ない。

依存の索引を書けない（ディスクの空きが無い・権限が無い）ときは、パス3 はキャッシュから I 行を読む（以前と同じ読み方で、
結果は変わらない）。書けないことを「キャッシュが読めない」と取り違えて全件解析にしない。

### Q33. 何も変わっていないとき、なぜキャッシュに触らないのか。条件は

書き直しても同じバイト列になるなら、書き直す意味が無い。差分更新は旧キャッシュを読みながら一時ファイルに書き、
最後に差し替えるので、何も変わらない実行でもキャッシュ全体を書いていた。次の条件がすべてそろうときは、
旧キャッシュのファイルをそのまま残す（`CacheUpdater.canKeepAsIs`）。

- 解析するファイルが 1 つも無い（変更・追加・削除されたファイル、壊れたブロック、jar の変化で解析し直すファイル、
  依存で解析し直すファイルが無い。「変わった型」も「変わった jar のパッケージ」も無い）
- 旧キャッシュのどのブロックも有効
- 先頭の行（ヘッダ・L 行の中身と並び・T 行）が、今回書くものとバイト単位で同じ
- 旧キャッシュが書き手の書くとおりの形（空行・CR が無く、最終行の Z 行が 1 つだけ）。そうでなければ書き直すと
  形が整うぶんだけバイト列が変わるので、1 回は書き直す

残したときも、再利用の件数・エラー数・未解決数は書き直したときと同じに数える（ログと `warnings.txt` が変わらない）。
ログには `[cache] Nothing changed; the cache is kept as is` を出す。
`test/incremental` は、2 回目の実行でファイルの inode と更新時刻が変わらないことを見る。

### Q34. グラフを 1 回の読み取りで組むには、何が要ったのか

呼び出しグラフは CSR（呼び出し元ごとに連続したエッジの配列）で持つ。エッジを置く位置を決めるには、呼び出し元ごとの
本数が先に分かっていなければならない。以前は 1 回目の読み取りで数え、2 回目で流し込んでいた。

1 回の読み取りで、エッジごとに固定長のバイナリの記録（呼び出し元・呼び出し先・行・束縛の種別・レシーバの種別・
修飾する型・レシーバと実引数の値の参照・ガード・証拠。1 本 34 バイト）を一時ファイルへ書き、本数を数える。
読み終えたら数えた本数からちょうどの長さの配列を作り、一時ファイルを先頭から読み直して `cursor[呼び出し元]++` の
位置に置く。ファイル上の順に処理するので、ID の振られ方も、呼び出し元ごとのエッジの並びも、2 回読んでいたときと
同じになる。1 回目と 2 回目で行の解釈（読めない行・候補の無い U 行の扱い）がそろわないと、流し込みが隣の呼び出し元の
範囲へはみ出すという、2 回読む形の弱点も無くなった。

進捗はブロックごとに（読んだバイト数 / ファイルの大きさで）知らせ、中止はブロックごとと、配置の 65,536 本ごとに確かめる
（Eclipse・VSCode のプラグインが進捗を出し、中止できるため）。

却下した案:

- **呼び出し元と呼び出し先の組をヒープに溜め、読み終えてから並べ替える（COO から CSR へ）。** 作りは一番素直だが、
  エッジ 1 本あたりの山がおよそ 42 バイトになり、CSR の 30 バイトより大きい。ヒープを優先して採らなかった
- **ブロックごとに呼び出し元でまとめて足していく。** 配列の長さを先に知るには、エッジの数を別に持つ必要がある。
  同じキーのメソッドが 2 つのファイルにあると呼び出し元のエッジが連続しないので、その手当ても要る

### Q35. 型解決に失敗した呼び出しの一覧は、なぜキャッシュを読み直さないのか

一覧（`call-hierarchy.csv` の末尾の `(unresolved)` の行）は、ソースフォルダの指定順 → ファイルの相対パスの順に並べる
（[deterministic-row-order-qa.md](deterministic-row-order-qa.md)）。キャッシュのブロックの並びは差分更新で変わるので、
以前は 1 回目の読み取りでブロックの順位を振り、2 回目で順番の来たブロックの U 行を書いていた。

グラフを組む読み取りで、一覧に出す U 行（使える候補が無いか、呼び出し元が分からないもの）だけを一時ファイルに
ブロックごとにまとめて書き、行のあるブロックだけ（パス・位置・長さ）を覚える。一覧を書くときに以前と同じ順位で
ブロックを並べ、位置を指定して読む。呼び出し元の ID は、書くときに引くだけで ID 化しない（以前と同じ）。
行が少ないときにヒープに置く形も考えたが、クラスパスが足りないプロジェクトで山が高くなるので、いつも一時ファイルにした
（経路を 1 つにしておく）。解析サーバーは一覧を書かないので、集めない。

### Q36. 一時ファイルの名前と後始末はどう決めたか

一時ファイルはどれもキャッシュと同じフォルダに `<キャッシュのファイル名>.<種類>-<乱数>.tmp` で作る（`jche.cache.TempFiles`）。

| 種類 | 作る | 消す |
|---|---|---|
| `deps` | 差分更新のパス1（依存のある有効なブロックがあるとき） | 差分更新の終わり（失敗しても） |
| `edges` | グラフの構築（最初のエッジ） | 構築の終わり（失敗・中止でも） |
| `unresolved` | グラフの構築（一覧に出す行が最初に出たとき。CLI だけ） | 一覧を書き終えたとき（解析に失敗したときも） |

- **名前を実行ごとに変える。** 解析サーバーと CLI が同じキャッシュのフォルダでたまたま重なっても、互いの一時ファイルを
  上書きせず、前の実行の残り物を読むこともない。作ったファイルは開いたまま使い、名前で開き直さない（依存の索引は
  最初は固定の名前だったが、ほかの実行が消したり書いたりしうるので一意の名前にした）
- **`finally` が動かない終わり方に備える。** Ctrl+C・`kill`（SIGINT / SIGTERM）、GitHub Actions の中止・時間切れ、
  IDE による解析サーバーの停止では `finally` が動かない。GitHub Actions はキャッシュのフォルダを `if: always()` で
  丸ごと保存するので、残ると大きな一時ファイル（エッジはおよそ 1 本 34 バイト）を保存してしまう。
  そこで作ったファイルを覚えておき、JVM の終了フック（最初に作るときに 1 回だけ登録する）がまだ消していないものを消す。
  フックが動き始めた後は新しい一時ファイルを作らせない（作っても消す機会が無い）
- **それでも残ったもの**（SIGKILL・停電）は、次の実行の最初に消す（`TempFiles.deleteLeftovers`）。アクションも保存の前に消す
- キャッシュ本体の一時ファイル（`analysis-cache.tsv.tmp`）と退避ファイル（`.partial`）は、中断からの引き継ぎに使うので
  この仕組みに入れない。強制終了でも消さない

`test/incremental` はどの実行のあとも `*.tmp`・`*.partial` が残っていないことを見る。`test/server` は解析の途中の
中止のあとに一時ファイルが残らないことを見る。

### Q37. ヒープはどうなったか（計測）

2,000 ファイルの合成プロジェクト（エッジ 29 万本、キャッシュ 30.5 MB）で、変更前と比べた。

- 動く最小のヒープは変わらない（`-Xmx42m` で動き、40m で落ちる。限界はフェーズ3 の木の出力）
- フェーズ2 の完全 GC 後の山は、`-Xmx42m` で 97% → 84%、`-Xmx44m` で 97% → 80%、`-Xmx48m` で 98% → 87%
- `-Xmx512m` では、フェーズ2 の割り当ての総量が 859 MB → 522 MB、フェーズ3 がおよそ 1,160 MB → 935 MB
- フェーズ1 の山は、どちらも JDT のバッチのばらつき（48〜56%）に埋もれて差が見えない

ヒープに増えたのは、有効なブロックごとの位置と件数（ブロックあたりおよそ 36 バイト）と、フェーズ2 から 3 の間の
ブロックのパスの参照（ブロックあたり 4〜8 バイト。一覧に出す行のあるブロックはさらに 16 バイト）。代わりに
F 行ごとのパスの文字列と、一覧のための行の保留が無くなった。

## 見送った案・却下した案

### Q38. ソースファイルごとに別のファイルにする、追記していく置き場にする案は

どちらも見送った（将来、書き写しの費用が問題になったら考え直す）。

- **ソースファイルごとに 1 ファイル（シャード）。** 書き写しが要らず、変わったファイルだけを書けばよい。だが数万ファイルの
  プロジェクトでは数万の小さなファイルになり、ファイルシステム（特に Windows）の負担と、GitHub Actions のキャッシュの
  保存・復元（tar）の手間が増える。「最後まで書き終えた」をまとめて言う手段（今の Z 行と一時ファイルからの差し替え）も
  別に作ることになる。削除されたファイルのキャッシュを掃除する経路も要る
- **追記型の置き場（セグメントと、ときどきの詰め直し）。** 書き直さずに済むが、同じファイルの古いブロックと新しい
  ブロックが並ぶので、どれが生きているかの目録と、詰め直しの規則が要る。これは 2 ファイルの対と同じ種類の整合の問題になる

今の 1 ファイルでも、何も変わらない実行はキャッシュに触らず、変わった実行もバイトの範囲のまま写すだけで、
書き写しは復号しない（Q31・Q33）。残る費用は「変わった実行でキャッシュの大きさぶんを書く」ことで、
キャッシュの大きさ（test/demo で約 93 KB（v36）、このツールの src で約 2 MB（v34）。「数字」）に比例する。

### Q39. フェーズ1 とフェーズ2 をまとめる（解析しながらグラフを組む）案は

却下した。解析したブロックと書き写したブロックを読みながらグラフを組めば、フェーズ2 の読み取りは 0 回にでき、
ID の順も同じにできる。だがそうすると、組み途中のグラフが JDT のバッチ（フェーズ1 のヒープの山。1,000 ファイルの
解析で回収前の最大 842 MB。[ast-analysis-performance-qa.md](ast-analysis-performance-qa.md)）と同じ時間にヒープに載る。
ヒープの山を下げる方を優先し、フェーズを分けたままにした。減らせる読み取りも 1 回だけである。

### Q40. 値の表をメモリに置かない（一時ファイルへ写像する）案は

見送った。数字と理由は Q18。値の表はこのツールの src で解析結果のヒープの 13% で、写像できるのはそのうち列の 7% だけ。
写像するなら、もっと大きいエッジの配列と同じ仕組みでまとめて行うべきである。

## 残っている限界

### Q41. 何が残っているか

- ~~**同じキャッシュのフォルダを 2 つの実行で同時に使うこと。**~~ （その後、フォルダの錠で 1 つずつにした。Q56）
  キャッシュ本体の一時ファイル `analysis-cache.tsv.tmp` と退避ファイル `.partial` は、中断からの引き継ぎのために
  決まった名前のままで、2 つの実行（CLI と Eclipse プラグインの解析サーバーなど）が同じものを奪い合っていた。
  ここには「気づける食い違いは内部エラーとして止める」と書いていたが、グラフの構築はヘッダも最終行も確かめずに読んでいて、
  書きかけのキャッシュから呼び出しの 1 本も無い CSV を「成功」として出すことがあった。今は錠（`analysis-cache.tsv.lock`）で
  同じフォルダを使う実行を 1 つずつにし、グラフの構築も書き終えたキャッシュでなければ止める（`graph.cacheIncomplete`）。
  差分更新は旧キャッシュを 1 回だけ開いて読み、読んでいるあいだに大きさが変われば止める
  （`analysis.cache.changedWhileReading`。[cache-integrity-qa.md](cache-integrity-qa.md) の「限界」も参照）
- **ファイルの錠の仕組みが無いファイルシステム（一部のネットワークドライブ）では、錠なしで続ける。** 同じフォルダを
  同時に使わないよう警告する（`cache.lock.unsupported`）だけで、そこで 2 つの実行が重なれば、以前と同じく書きかけを
  奪い合いうる（グラフの構築が書き終えたキャッシュかを確かめるので、空の CSV を「成功」として出すことは無い）
- **解決できなかった名前（I 行の 3 列目）は、エラーの種類で絞らずに拾う。** 型の名前でないもの（メソッド名・
  `long` など）も混じるので、型を足したときに、当たる必要の無いブロックまで解析し直すことがある（余計に解析し直すだけで、
  結果は変わらない。Q42・Q64）
- **UTF-8 として読めないバイトは、キャッシュ全体を捨てる。** 厳密に復号するので、1 バイトの化けでも全件解析になる
  （安全側）。ブロックの中の化けでも、どのブロックかを確かめずに捨てている
- **ブロックの中の空行は検査値に数えない。** 読み手は空行を読み飛ばす。書き手は空行を書かず、空行は事実を持たないので
  結果は変わらない（そういうキャッシュは書き手の形ではないので、次の実行で書き直す）
- **値を読まない指定（`dataflow.enabled=false`）でも、値の行のバイトは読む**（種別で読み飛ばすだけ。Q23）
- **版の上げ忘れの検査は、題材に現れる事実しか見ない**（Q21）
- **名前の違う 2 つのファイルが同じ型を宣言していると、差分更新と全件解析が食い違いうる**（Q68）。JDT は同じバッチなら
  後ろのファイルの型を「重複している」として読まず、別々のバッチなら両方を読む。ファイル名からは組にできず、どちらになるかは
  一緒に解析したファイルで決まる。ビルドの通らない状態なので、警告（`graph.duplicateType`。両方を読んだとき）と
  コンパイルエラーの一覧（片方を読まなかったとき）で案内し、文言は「出ないこともまとめられることもあり、実行で変わりうる」と
  そのまま伝える

## 差分更新が見落としていた依存（形式 v34）

最終レビュー（6c41201 に対するもの）で、差分更新の結果が「キャッシュを消してからの全件解析」と食い違う場面が 5 通り
見つかった。その修正のレビュー（2 回目のレビュー）で、さらに 2 通り（親型の連鎖が処理の順に依る・式の型にだけ現れる型のメンバー）と、
修正が増やした再解析 2 通り（新しい型で失敗していたブロックをすべて解析し直す・親の本体だけの変更でも連鎖する）が
見つかり、あわせて直した。
どれも「別のファイルの変化が、そのファイルの I 行（依存する型）に触れない」形で、呼び出しが未解決のまま残る・
上書きの事実や M 行が欠ける・別のクラスに解決される・コンパイルエラーの数が古いまま残る、のどれかになる。
エラーにも警告にもならず、そのファイル自身を書き換えるまで直らない。どれもこの作業より前（6227970）からあった。

対応の要点:

- 前回どのブロックも宣言していなかった型（新しい型）を見分け、新しい型があれば、型解決に失敗していたブロックのうち
  解決できなかった名前（I 行の 3 列目。エラーの引数）が新しい型に当たるものと、同じパッケージで名前を隠されうる
  ブロックを解析し直す（Q42・Q43）
- 各ブロックの I 行に型の形（継承したものを含むメンバーの署名）の指紋を書き、パス4 で解析し直したファイルの形が
  前回と違えば、そのファイルの型も「変わった型」に加えて連鎖させる（Q44）
- ラムダの目標の型とその親、ソースに書かれた型の名前（戻り値・throws・ローカル変数・キャストなど）、呼び出しの受け手と
  実引数の式の型・修飾された名前の左側の型を I 行に載せる（Q45・Q46・Q50）
- warnings.txt に並べるエラーのファイルを、数えた順ではなくパスの順で選ぶ（Q48）
- 対になっていないサロゲートを符号化し、条件の文字列をサロゲートペアの途中で切らない（Q49）
- `test/incremental/run.sh` に 7 ケース（無かった型を足す 2 通り・祖父母の型の変更 2 通り・ラムダの目標の型・
  同じパッケージの隠蔽・宣言にだけ書いた型）を足した。どれも 6c41201 では落ち、今は通る。2 回目のレビューのぶんで
  さらに 10 ケース（部分型のパスが親より前 2 通り・式の型にだけ現れる型 3 通り・実引数の式の型の親・フィールドの隠蔽・
  無名クラスを足す・名前の当たるブロック・親の本体だけの変更）を足した。どれも最初の修正では落ち、今は通る（Q47）
- 形式を v34 に上げた（I 行が変わり 3 列になる。D 行にアノテーションの付いたメソッドの戻り値の型を足した。符号化の規則が変わる）

### Q42. 無かった型のソースを足したとき、参照していたファイルをなぜ見落としたのか

I 行は「バインディング解決で名前にした型」なので、**解決できなかった型は載らない**。`Foo.run()` のように型の名前だけを
書いた呼び出しでは、`Foo` が無いと JDT はバインディングを返さず、I 行には何も残らない（`new Foo()` や `Foo f` なら
JDT がバインディングを `miss.Foo` として復元するので載る。検査の題材が名前だけの形なのはこのため）。あとから `Foo.java`
を足しても、どのブロックの I 行にも触れないので、参照していたファイルは `BINDING_FAILED` のまま再利用され、
`Foo.run` から先の階層がまるごと欠け、warnings.txt もそのファイルをコンパイルエラーとして挙げ続けた。
消したファイルを戻したとき（git stash / checkout）と、既存のファイルに型を書き足したときも同じである。

型解決に失敗していたブロックを解析し直す仕組みは、jar を足したとき（`libraryAffected`）にだけあった。
今は、パス2 で解析したファイル（変わった・増えたファイル。中断からの引き継ぎも含む）が宣言する型のうち、
パス1 で無効になったブロックの H 行に無かった型を「新しい型」とする。新しい型があれば、F 行のエラー数が 0 でないか
U 行に `BINDING_FAILED` があるブロックのうち、**解決できなかった名前が新しい型に当たるもの**を解析し直す。
`BINDING_FAILED` はこれまで jar が変わったときにしか見ていなかったので、常に見るようにした（パス1 で U 行の理由の列を
比べるだけ）。

解決できなかった名前は、書き手がエラー（`IProblem`）の引数から取って I 行の 3 列目に書く。「Foo cannot be resolved」
「The import org.missing cannot be resolved」「The type q.Bar cannot be resolved. It is indirectly referenced…」の
引数には、解決できなかった名前が書いたとおりに入るので、点区切りの識別子（`Foo`・`org.missing`・`q.Bar`）を拾う。
エラーの種類では絞らず、どのエラーの引数も拾う（型の名前が入りうるものを種類の表で取りこぼさないため。余分に拾っても
解析し直すファイルが増えるだけ）。当たりの判定は、名前の点区切りのどれかが新しい型の単純名であるか（`Foo`・`q.Foo`・
`Foo.Inner`）、名前が新しい型の FQN の頭の部分であるか（パッケージごと無かったときの「The import org cannot be
resolved」に `org.acme.New` が当たる）。名前を 1 つも拾えなかったブロック（エラーが無いのに `BINDING_FAILED` がある）は
`*` と書き、どの新しい型にも当たるとみなす。

無名クラス・ローカルクラス（`Main$1`）は名前で参照できないので、エラーの名前に当たらない。入れ子の型（`Main.Inner`）は
単純名 `Inner` で当たる（`Main.Inner x;` の「Main.Inner cannot be resolved」）。同じパッケージの隠蔽（Q43）で数えるのは
トップレベルの型だけにした（入れ子の型は外側の型を通してしか名前にならず、外側の型は前回もあった）。

費用: 最初の修正は、新しい型が 1 つでもあれば型解決に失敗していたブロックを**すべて**解析し直していた。レビューが測った
とおり、無名クラスを 1 つ足す・入れ子の型を足すだけの書き換えでも、`org.missing.Lib` で失敗する 10 ファイルと Main の
題材で解析し直すのが 1 件から 11 件になり、test/demo（失敗していたのは 2 ファイル）でも無名クラス・入れ子の型・
新しいファイルで 1 件から 3 件になった。依存 jar を置かずに動かすと大半のファイルがエラーを持つので、全件解析に近くなる。
今はどれも 6c41201 と同じ 1 件で、差分更新と全件解析は一致する。名前の当たるファイルは解析し直す（`org.missing.Lib` で失敗する 3 ファイルの
題材に `org/missing/Lib.java` を足すと、I 行の名前 `Lib,org.missing` が当たって 3 ファイルとも解析し直し、全件解析と一致する）。test/incremental の
「無名クラス・入れ子の型を足す」「無かった型を足す（名前の当たるブロックだけ）」が件数（1 件・2 件）まで見る。

却下した案:
- 新しい型のうちトップレベルの型だけを数える。無名クラス・入れ子の型では増えなくなるが、ファイルを足すたびに
  失敗していたブロックをすべて解析し直すのは変わらない
- AST の単純名から失敗した名前を集める。無い型にはバインディングが無いので、入れ子の型・修飾した名前・import との
  対応を自前で組むことになる。エラーの引数は JDT が解決できなかった名前そのものなので、組まずに済む

### Q43. 同じパッケージに足した型が import を隠すのを、なぜ見落としたのか

単純名の解決は「単一型 import ＞ 同じパッケージの型 ＞ オンデマンド import と `java.lang`」の順である（JLS 6.4.1）。
`import q.*;` で `q.Helper` を使っていたファイルは、同じパッケージに `p.Helper` を足すと `p.Helper` に解決が変わる。
I 行は `q.*,q.Helper` で、`q.*` はパッケージ `q` の変化にだけ触れ、自分のパッケージ `p` は I 行に無い。
`java.lang.Math` と `p.Math` も同じである。

今は、新しいトップレベルの型（パッケージ `p`・単純名 `N`）があれば、自分のパッケージが `p` で、I 行のどれかの型名を
`.` で区切ったときに `N` を含むブロックを解析し直す。自分のパッケージはパス1 でブロックの最初の H 行から取り、
書き写す候補の表（`OldCache`）に持つ（同じ中身の文字列は 1 つを共有する）。依存の索引は、パスの代わりに
この表の添字を書く。

却下した案: I 行に自分のパッケージを「暗黙のオンデマンド import」として足し、変わった型のパッケージと突き合わせる。
同じパッケージのどのファイルを書き換えても、パッケージ全体を解析し直すことになる。新しい型に限り、単純名でも絞った。

### Q44. 親の親が変わったとき、子の利用者をなぜ見落としたのか

`D extends E`、`E extends F<String>` で、F に `abstract void m(T t)` を足し、F を引数にした呼び出しを `f.m("x")` に
変えた例。D の I 行は `…,sup.E` だけで F は無い。F が変わったので E は解析し直すが、パス4 で解析し直したファイルの型を
「変わった型」に加えるのは定数（K 行）の値が変わったときだけだったので、D は再利用され、D の O 行
（`D#m(String)` が `F#m(Object)` を上書きする）が欠けたまま、`f.m("x")` は「実装が無い」になった。祖父母の型に
オーバーロードを足したとき（`new B().m(1)` が `B#m(long)` から `C#m(int)` に変わる）も同じである。

最初の修正は、パス4 で解析し直したファイルの型の親（H 行の親型）が、そのときの「変わった型」か変わった jar の
パッケージの型なら、その型も「変わった型」に加えるものだった。レビューで 2 つの問題が見つかった。

- **処理の順に依る。** 同じ周回で子（`D`）が親（`E`）より先に解析し直されると、子を見た時点では親がまだ「変わった型」に
  入っていないので連鎖しない。解析し直した子はもう有効ではないので、あとの周回でも見直されない。`F` に `m(int)` を足すと、
  `D`（`F<String> self()` を持つので `F` を参照し、`E` と同じ周回に入る）の利用者 `U` の `d.m(1)` が `D#m(long)` のまま
  残った。`D` を `Z` に改名する（`E` より後に並ぶ）と一致した。インターフェース（`A implements I2`、`I2 extends I1` の
  `I1` に default メソッドを足す）でも同じで、`a.m2()` が BINDING_FAILED のまま残った
- **本体だけの変更でも連鎖する。** 親が「変わった型」に入る理由を問わないので、親のメソッドの本体やコメントを変えても
  子の利用者まで解析し直した。test/demo の全 107 ファイルに 1 行のコメントを足した再解析の合計は 6c41201 の 261 件に
  対して 284 件で、`fx/dao/AbstractDao.java` は 4 件から 20 件になった

今は、各ブロックの I 行の 2 列目に**型の形の指紋**を書く（`TypeShape`）。形は、ファイルが宣言する型ごとに、その型と
親型（推移的に。`java.*` の型はメンバーを辿らない）について、JDT のバインディングのキー（型引数を含む）・修飾子・種類、
宣言したメソッドのキーと修飾子と戻り値・引数の型、フィールド、入れ子の型、型変数と上限を行にし、並べ替えてハッシュにした
頭の 16 文字である。無い型を復元したバインディングには印を付ける（あとで型ができたら形が変わる）。パス4 で解析し直した
ファイルの形が旧キャッシュと違えば、そのファイルの型を「変わった型」に加える（`BlockWriter.shouldCascade`）。

- 連鎖するかは、そのファイルの解析結果と旧キャッシュの比較だけで決まる。親と子をどの順に解析し直しても、同じ答えになる
- `F` にメソッドを足すと、継承したものを含む `E` の形も `D` の形も変わるので、`E` の利用者も `D` の利用者も解析し直す
- 親のメソッドの本体・コメントだけの変更では、子の形は変わらないので連鎖しない
- jar の親型の版を変えたときも、jar の型のメンバーが形に入っているので、変わったときだけ連鎖する

費用（test/demo の全 107 ファイルに 1 行のコメントを足したときの再解析の合計。6c41201 → 最初の修正 → 52453ae）: 261 → 284 → 264。
107 ファイルのどれでも、差分更新の結果（CSV とキャッシュ）は全件解析と一致する。`AbstractDao.java` は 4 件（最初の修正では
20 件）、`CtorBase`・`PaymentGateway` は 4 件（同 5 件）、`fx/model/Base.java` は 2 件（同 3 件）に戻った。6c41201 より
多いのは 3 ファイルで、どれも連鎖ではなく、I 行に載る型が増えて利用者が 1 件ずつ増えたもの: `fx/dao/Dao.java`
21 → 22（`Chain.java` の `DaoFactory.get(…).find()` の受け手の型。Q50）、`fx/di/Clock.java` 4 → 5（`AppConfig.java` の
`@Bean` メソッドの戻り値の型。Q46）、`fx/lambda/Door.java` 1 → 2（`TwoParents.java` のラムダの目標の型。Q45）。
I 行は 1 ブロックあたり 17 文字ほど長くなる。

却下した案:
- 連鎖しなかったファイルの（型・親型）を覚えておき、周回ごとに「変わった型」と突き合わせ直す（レビューの提案）。
  順には依らなくなるが、本体だけの変更で連鎖する問題は残る
- 親の H・D・O 行の指紋が旧ブロックと違うときだけ親を「構造が変わった型」とし、それを子の判定に使う（レビューの提案）。
  子のブロックの行は、祖父母が変わっても変わらない（`E` の D 行は `F` にメソッドを足しても同じ）ので、判定には親の
  親を辿る別の仕組みが要る。H 行の親型は消去した名前なので、`E extends F<String>` を `F<Integer>` に変えたことも
  見えない。継承したものを含む形なら、1 つの規則で両方に届く
- すべての I 行に、参照した型の推移的な親を載せる。I 行がどのファイルでも広がり、親が変わらない限り使わない名前で
  キャッシュが嵩む。連鎖なら、費用は親の形が実際に変わった実行にだけかかる

### Q45. ラムダの目標の型が I 行に無かったのはなぜか

`Door d = () -> …;` の M 行（ラムダが実装するメソッドの鍵）は、目標の型 Door とその親を辿り、SAM と上書き同等な
抽象メソッドを集めて作る（`BindingNames.functionalKeysOf`）。名前にしていたのはメソッドを宣言した型（Opener）だけで、
何も宣言していない Door は I 行に載らなかった。Door を `extends Opener, Closer` に変えると、全件解析では M 行に
`Closer#act()` が増え、`Closer` で受けた呼び出しがラムダに繋がるのに、差分更新ではラムダを使うファイルが再利用され、
`Closer.act` は「実装が無い」のままだった。

今は、辿った型（目標の型とその親すべて。交差型は各成分）を I 行に数える。親のさらに親が変わった場合は、Q44 の連鎖が
Door まで運ぶので、目標の型だけでも足りるが、辿ったものは全部載せた（載るのは関数型インターフェースとその親で、
多くは `java.util.function` の型）。

### Q46. 宣言にだけ書いた型が I 行に無かったのはなぜか

I 行に載るのは、事実を作るときに名前にした型（呼び出し先・フィールド・メソッドの鍵の引数型・注釈など）だけで、
戻り値・throws・ローカル変数・キャスト・型引数のように「書いてあるが事実にはならない」型は載らなかった。その型を
消すと、全件解析ではそのファイルがコンパイルエラーになるのに、差分更新では F 行のエラー数 0 のまま残り、warnings.txt の
件数が食い違う（test/demo で `fx/dao/Dao.java` を消すと 22 件と 23 件）。エラー数は jar を足したときに解析し直すかの
判定にも使うので、古い 0 はその判定も止める。

今は、AST の型の名前の節（`SimpleType`・`QualifiedType`・`NameQualifiedType`）ごとにバインディングを I 行に数える
（`FactVisitor`）。ソースに書かれた型の名前はすべて載る。最初は戻り値と throws だけに絞る案だったが、ローカル変数と
キャストの型も同じ問題を持つので、節で拾った。

費用: I 行が長くなる。この変更（と D 行の戻り値の型の列）で、test/demo のキャッシュは 90,579 バイトから 91,056 バイト
（+0.5%）、このツールの src（6c41201）は 2,002,703 バイトから 2,004,840 バイトになった（2 回目のレビューのぶんを含む
v34 の最終の大きさは Q50）。

### Q48. warnings.txt に並べるエラーのファイルが、なぜキャッシュの状態で変わったのか

コンパイルエラー・構文エラーのファイルは、数えた順に先頭の 20 件を並べていた。数える順は、全件解析ではソースの順、
差分更新では「解析し直したファイル → 書き写したブロック（旧キャッシュの並び）」なので、同じソースでも並ぶファイルと
並びが違った。今は、パスの順で小さいものから 20 件を残す（`CachePhaseResult.keepSmallest`。上限を超えたら最後を捨てる
ので、ヒープは 20 件のまま）。test/warnings の 5a が、25 件のコンパイルエラーと 22 件の構文エラーのファイルで、
差分更新でも全件解析と同じ一覧になることを見る。

残るもの: 構文エラーのファイルごとの警告（「構文エラーのため本体を読めませんでした」）は、その実行で解析したファイルに
だけ出る。warnings.txt の項目の明細は 50 行で切れるので、構文エラーのファイルが多いと、明細に載る一覧の行数が
差分更新と全件解析で変わりうる（run.log には一覧が全部出て、同じになる）。

### Q49. 対になっていないサロゲートで、なぜ解析ごと失敗していたのか

キャッシュは、書けない文字で例外にする UTF-8 の書き手で書く（化けたまま書かないため）。列の符号化（`escape`）は
制御文字とバックスラッシュだけを符号化していたので、対になっていないサロゲートはそのまま書き手に届き、
`MalformedInputException` で解析が失敗した。キャッシュは一時ファイルのまま残り、次の実行も同じソースを解析し直して
また失敗する。現れ方は 2 つで、どちらも javac が通す正しい Java である。

- 文字列リテラル `"\uD800x"`（値が値グラフや K 行に入る）
- 条件式の文字列（G 行の text）を 60 文字で切るとき、ちょうど絵文字（サロゲートペア）の途中で切れる

今は、対になっていないサロゲートを `\uXXXX`（小文字の 16 進 4 桁。制御文字と同じ形）に符号化する。`unescape` は
同じ char に戻すので値は変わらない。対になったサロゲートはそのまま書く（UTF-8 に書ける）。条件式の文字列は、
切れ目が上位サロゲートなら 1 文字手前で切る。契約表のひな形（`contracts-suggested.txt`）は、キャッシュから戻した
キーを含みうるので、CSV と同じ置換する書き手で書く。

却下した案: キャッシュの書き手を置換する設定にする。`"\uD800x"` と `"\uDBFFx"` がどちらも置換文字になって等しく
なり、成り立たない `equals` の条件を「成り立つ」と読んで打ち切らない（逆に、成り立つ条件を打ち切る形も作れる）。
符号化なら値がそのまま残る（test/pruning の SurLit が、別のサロゲートを渡した経路を打ち切ることで見る）。
形式の版は上げた（Q47。書くバイトが変わる）。test/cachevalue は、単独のサロゲートを含む全 BMP の文字で
往復することと、符号化した結果を UTF-8 に書けることを見る。

### Q50. 式の型にだけ現れる型にメンバーを足しても、なぜ呼び出しが未解決のまま残ったのか

解決できなかった呼び出しは U 行にしか残らず、受け手の型は、ソースにその名前が書いてなければどこにも残らなかった
（6c41201 からあった）。`U` の `a.getB().x()` は、`B` に `x()` が無いうちは `BINDING_FAILED` で、`U` の I 行は
`java.lang.Object,p.A` だけである。`B` に `x()` を足すと、全件解析では `U.go -> B.x` に解決するのに、差分更新は `U` を
再利用し、`B.x` から先の階層が欠け、warnings.txt も `U.java` を挙げ続けた。同じ形がほかに 2 つある。

- `D extends E<Foo>` の `d.get().x()`。`Foo` は親の型引数にしか現れない
- `Box<T extends Mid>` の `b.get().n()` を `Box<?>` で受けたもの。受け手の型は捕捉された型変数で、`n()` は上限 `Mid` の
  親 `Base` に足す。`Box` は `Mid` を参照しているので解析し直すが、`Mid` の部分型ではないので連鎖しない

解決できた呼び出しにも同じ穴があった。`a.m(b.getC())` で `A` に `m(Object)` と `m(I)` があるとき、`C` に `implements I` を
足すと、選ばれるメソッドが `A#m(Object)` から `A#m(I)` に変わる（JLS 15.12.2）が、`C` は `U` の I 行に無いので、差分更新は
`A#m(Object)` のまま残した（`A#m(I)` への呼び出しが静かに落ちる）。フィールドも同じで、`a.getB().count` は `B` に親の
`count` を隠すフィールドを足すと `B#count` に変わる（A 行）。

今は、呼び出しの受け手と実引数の式の型（解決できたかどうかに関わらない）と、修飾された名前（`a.b.count`・`Outer.Inner`）・
フィールド参照（`a.getB().count`）の左側の型を I 行に数える（`CallSiteRecorder.noteOperandTypes`・
`FieldAccessRecorder.noteQualifier`）。型変数・捕捉された型変数・ワイルドカード・交差型は、飛ばさずに上限の消去で数える
（上限が複数なら全部。`BindingNames.noteReachedType`）。これまでの `noteDependency` は型変数を飛ばしていた。
test/incremental の「式の型にだけ現れる型にメソッドとフィールドを足す」「親の型引数にだけ現れる型にメソッドを足す」
「型変数の上限の親にメソッドを足す」「実引数の式の型の親を変える」「式の型に親のフィールドを隠すフィールドを足す」が、
どれも最初の修正のツールでは「差分更新と全件解析が違う」で落ち、今は通る。

解決できなかった呼び出しに限る案（レビューの提案）もあったが、オーバーロードの選択とフィールドの隠蔽は解決できた
呼び出し・参照で起きるので、どちらにも数えた。

費用: 載る型の多くは、ローカル変数の型（Q46 で載っている）か `java.lang` の型なので、I 行はあまり増えない。test/demo の
I 行の型の数は 407 から 409、キャッシュは 91,056 バイトから 93,081 バイト（型の形の指紋と解決できなかった名前の列を含む。
+2.2%）。このツールの src（6c41201。JDT の jar をクラスパスに置く）は、同じ手順で測ると 2,004,821 バイトから
2,007,858 バイト（+0.15%）。コメントだけの書き換えで解析し直す件数がこの変更で増えたのは `fx/dao/Dao.java`（21 → 22。
`Chain.java` の受け手の型に `Dao` が載った）だけである（Q44）。

### Q51. 親型の私的メンバーを型の形から外してよいのか。何を確かめたか

**結論: 名前の当たらない私的メンバーは外してよい。名前の当たるものは残す。型解決に失敗しているファイルだけは別の経路で
拾う。** 「全部外す」は成り立たないことを、差分更新と全件解析を突き合わせて確かめた。

型の形は、ソースの変わっていないファイルを解析し直したとき、その型を使う側へ連鎖させるかを決める（Q44）。これまでは
型とその親型（推移的に）の宣言したメンバーをすべて入れていたので、`AbstractDao` に `private void helper2() { }` を足すと、
`AbstractDao` を継承する型の形がすべて変わり、その利用者まで解析し直していた（test/demo で 20 件。コメントだけなら 4 件）。

JLS の上では、私的メンバーは宣言したトップレベルのクラスの本体の外からは参照できず（6.6.1）、継承もされない（8.2・
8.4.8・9.4.1）。部分型を使う側から見えるメンバーは、私的メンバーがあってもなくても同じはずである。ただし、私的メンバーは
**自分の親型の同じ名前のメンバーを隠す・継承を止める**ことがある:

- 私的フィールドは、親型の同じ名前のフィールドを隠す（8.3「A class inherits … all the non-private fields of the
  superclass … not hidden by a declaration in the class」）。`P` に `private int f;` を足すと、`P` は `G.f` を継承せず、
  `C extends P` にも `f` が無くなる
- 私的な入れ子の型は、親型の同じ名前の型を隠す（8.5）
- 私的メソッドは、親型の同じシグネチャのメソッドの継承を止める（8.4.8「No method declared in C has a signature that is
  a subsignature …」。インターフェースは 9.4.1）。`P` 自身は「弱いアクセス」のエラーになる（8.4.8.3）

そこで、仮に私的メンバーを全部外したツールを作り、ハザードごとに題材を作って、差分更新と全件解析（CSV・warnings.txt・
キャッシュ）を突き合わせた。題材はどれも `G <- P <- C`（別ファイル）で、利用者 `X` は別のパッケージにあり `C` だけを
参照する（`P` を参照していない）。書き換えるのは `P` だけである。

| 何を足したか（`P` に） | JLS | 全部外すと | 今の規則 |
|---|---|---|---|
| (a) `G.f` と同じ名前の私的フィールド。`X` は `c.f` | 8.3 | 食い違う（`c.f` が全件解析ではエラーになる） | 一致 |
| (b) `G.Inner` と同じ名前の私的な入れ子の型。`X` は `C.Inner.run()` | 8.5 | 食い違う（呼び出しが消える） | 一致 |
| (c) `G.m()` と同じシグネチャの私的メソッド。`X` は `c.m()` | 8.4.8 | 一致（JDT は `G.m` に解決したまま。`P` だけがエラー） | 一致 |
| (c') `G.n(long)` に対する私的な `n(int)`。`X` は `c.n(1)` | 15.12.1 | 一致（`X` は変わらない） | 一致 |
| (d) 私的な static `s(int)`・`s(long)`。`X` は `import static …C.s` / `C.*` で `s(1)` | 7.5.3・7.5.4 | 一致 | 一致 |
| (e) 同じファイルの入れ子のクラスが使う私的メンバーを変える | 6.6.1 | 一致（ファイルそのものが変わるので解析し直す） | 一致 |
| (f) 私的なコンストラクタ `P(int)`。`C` は暗黙の `super()` | 8.8.7・8.8.9 | 一致 | 一致 |
| (g)(h) `I2 extends I1` に、`I1` の default `m()` と同じ私的メソッド。実装はレコードと列挙型 | 9.4.1 | 一致（JDT は `I1.m` に解決したまま） | 一致 |
| 外側のクラスのメンバーと同じ名前の私的な `f`・`m()`・`Inner`（`X` の内部クラスが `C` を継承） | 6.4.1・15.12.1 | 一致（JDT も外側のメンバーに解決する） | 一致 |
| 部分型 `Z` の `h()`・static `h2()`・`h4()` と同じ名前の私的メソッド（上書きにも隠蔽にもならない） | 8.4.8.1 | 一致 | 一致 |
| `C extends P implements I` で、`I` のメンバーと同じ名前の私的メンバー（`P` の親ではない型との当たり） | 8.3・8.4.8 | 一致 | 一致 |
| `G.Inner`（型）と同じ名前の私的フィールド（種類をまたぐ当たり。6.5.2） | 6.4.2 | 一致（JDT は変わらない） | 一致 |
| 型解決に失敗している `X`（`c.helper2()`・`c.extra` が無い）に対し、同じ名前の私的メンバー | — | **食い違う** | 一致 |

最後の行は JLS ではなく JDT の回復の仕方による。型解決に失敗している式について、JDT は見えない私的メンバーにも
バインディングを返す。全件解析では `X` の `c.helper2()` が BINDING_FAILED の U 行から `P#helper2` への C 行に変わり
（`RESOLVED:STATIC_BOUND:PRIVATE`）、I 行に `P` が増える。warnings.txt の未解決の件数も変わる。

今の規則:

- **私的メンバーは、それを宣言した型の親型（推移的に）のどれかに、私的でない同じ名前のメンバー（種類は問わない）が
  あるときだけ型の形に入れる**（`TypeShape`）。(a)(b)(c) のように隠蔽・継承の停止が起きうるのは、名前が当たるときだけ
  である。JDT が (c)(h) で JLS どおりに振る舞わないことには頼らず、JLS が「変わる」とするものは残した。種類をまたぐ当たり
  （フィールドと型）も、JDT は変わらなかったが残した（名前の分類の扱いを JDT の実装に頼らない）。`java.*` の親型も、
  そのさらに上（JDK の親型・インターフェース）まで名前を数える（`toString` という名前の私的メソッドは残る。はじめは最初の
  `java.*` の親型のメンバーの名前までしか数えておらず、`HashMap` の子の私的な `Entry` を外していた。Q65）
- 私的なコンストラクタは入れない。コンストラクタは継承されず、暗黙の `super()` が呼ぶのは直接の親のもので、直接の子は
  親を参照している（`extends` に名前がある）ので、親が変われば解析し直す
- **型解決に失敗したファイルは、名前にした型すべての推移的な親を I 行に持つ**（`BindingNames.noteAncestorsOfNamedTypes`。
  ファイルの終わりで、F 行のエラー数か BINDING_FAILED があるときだけ）。`X` の I 行に `P` が載るので、`P` を書き換えれば
  私的メンバーの変化でも解析し直す

最初に試した 2 つの規則は、どちらも「差分更新と全件解析が一致する」を満たせなかった。

- **型の形を作っている型（`owner`）の見える名前と当たるかで決める。** `Z extends C` が `h()` を宣言していると、`P` の私的な
  `h()` は `Z` の形では「当たる」、`C` の形では「当たらない」になる。`C` の形は変わらないので `Z` は解析し直されず、`Z` の
  I 行の指紋だけが古いまま残った（キャッシュが全件解析と違う）。今の規則は、私的メンバーを宣言した型とその親だけで決まり、
  どの型の形にも同じ行が入るか入らないかのどちらかなので、子孫の指紋が古いまま残ることはない
- **私的メンバーの指紋を別に持ち、それだけが変わったら型解決に失敗した利用者だけを解析し直す。** 子孫の指紋にも親の私的
  メンバーが入るので、指紋を正しく保つには子孫をすべて解析し直す必要があり、子孫かどうかを I 行からは見分けられない
  （H 行の親型を依存の索引に足すことになる）。失敗したファイルの側で親を依存に持つほうが、仕組みが小さい

却下した案: 私的メンバーの名前だけを残す（シグネチャと本体の変更では連鎖しない）。補助メソッドを**足す**と名前が増えるので、
いちばん多い変更で効かない。

費用: `AbstractDao.java` に私的メソッドを足したときの再解析は 20 件から 4 件、私的フィールドを足したときも 20 件から 4 件に
なった（コメントだけの変更と同じ）。公開メソッドを足したときは 20 件のまま（利用者の解決が変わりうるので正しい）。
型解決に失敗したファイルの I 行は親（`java.*` を除く）のぶん長くなる（test/demo では失敗しているのは 2 ファイルで、
増えた型は無かった）。

### Q52. 可変長引数・throws・拡張 for・switch・throw・アノテーション・sealed で、何を見落としていたのか

どれも「別のファイルの変化がこのファイルの結果を変えるのに、その型がこのファイルの I 行にも、連鎖の元の型の形にも
無い」形である。

- **可変長引数**: `m(int[])` と `m(int...)` はバインディングのキーも修飾子の値も同じで、型の形が変わらなかった。祖父母の
  型の `m(int[])` を `m(int...)` にすると、全件解析では `U` の `d.m(1, 2)` が BINDING_FAILED から `F#m(int[])` への呼び出しに
  変わる（JLS 15.12.2.4）。型の形のメソッドの行に可変長引数の印を入れた
- **throws の型と検査例外か**: 呼び出し先の throws の型は、呼び出し側のソースに名前が無いことが多い。その型の親を
  `RuntimeException` から `Exception` にすると、全件解析では呼び出し側が「例外を処理していない」エラーになる（11.2.3）。
  呼び出し（暗黙の呼び出し・メソッド参照を含む。`CallSiteRecorder`）ごとに throws の型を I 行に数え、型の形のメソッドの行にも
  throws の型と検査例外か（`U`/`K`）を入れた（祖父母の型のメソッドの throws でも連鎖する）
- **throw する式の型**: `throw d.make();` の型も名前が無い。I 行に数えた
- **拡張 for 文の式の型**: `for (Object s : a.getRepo())` の `Repo` を `Iterable` にすると、全件解析ではエラーが消えて
  `iterator()` などの暗黙の呼び出しが増える（14.14.2）。I 行に数えた
- **switch のセレクタの型**: `switch (s.kind())` の列挙型に定数を足すと、`case C` の名前が解決し、網羅性（14.11.1.1）も
  変わる。I 行に数えた
- **アノテーションの型**: 宣言に付いたものは `annotationsOf` が数えていたが、引数・ローカル変数・型の使用に付いたものは
  数えていなかった。アノテーションの型の名前は `Name` の節で、型の名前の節（Q46）では拾えない。3 種類のアノテーションの節で
  数えた
- **sealed の permits**: `switch (s) { case A1 a -> …; case A2 a -> …; case B b -> …; }` は、`A` が `permits A1, A2` のとき
  網羅的で、`A3` を足すと網羅的でなくなる（エラー）。`U` は `A` を参照していない。permits は JDT 3.46 の DOM のバインディングから
  取れない（`ITypeBinding` に permits を返すメソッドが無い）ので、型の形には入れられない。そこで、switch の case に書いた型
  （型パターン・レコードパターン・列挙定数の型）とその推移的な親を I 行に数える。網羅性が依存する permits は、セレクタの型から
  case の型までの途中の型のものなので、それで足りる

### Q53. 見えなかった型を public にしても、完全修飾名で参照していたファイルをなぜ見落としたのか

`vq.U` の `vp.Hidden.run()` は、`Hidden` がパッケージ私的なうちは「The type vp.Hidden is not visible」で型解決に失敗していて、
I 行には `vp.Hidden` が無い（解決できなかった名前の列に `vp.Hidden` がある）。`Hidden` を public にしても、`Hidden` は
新しい型ではない（前回も宣言されていた）ので、解決できなかった名前と新しい型の突き合わせ（Q42）に当たらず、`U` は
再利用されて呼び出しが欠けたままだった。`import vp.Hidden;` で使う `U2` も同じである。

今は、解決できなかった名前を**変わった型（新しい型を含む）すべて**と突き合わせる。周回ごとに見直すので、連鎖で
変わった型に加わった型にも当たる。名前を 1 つも拾えなかったブロック（`*`）は、何かが変わればいつも解析し直す
（これまでは新しい型があったときだけ）。test/demo にはそういうブロックは無い。

### Q54. jar が自分と同じパッケージに型を足したとき、なぜ見落としたのか

`sp.Main` が `import sq.*;` で `Helper` を使っているとき、依存 jar に `sp.Helper` が入ると、同じパッケージの型が
オンデマンド import を隠す（JLS 6.4.1）ので `sp.Helper` に解決が変わる。Q43 は新しい**ソースの**型だけを数えていて、
jar の型は（どの型が増えたかを jar の差分からは知らないので）数えていなかった。`Main` の I 行は `sq.*,sq.Helper` で、
変わった jar のパッケージ `sp` に触れない。

今は、自分のパッケージが変わった jar のパッケージで、I 行にオンデマンド import か `java.lang` の型があるブロックを
解析し直す（`StaleTypes.touches`）。どの型が増えたかは分からないので単純名では絞らない。ソースと jar に同じパッケージを
分けて置く構成は多くないので、費用はそういう構成に限られる。

## キャッシュの健全性と一括解析の頑健さ（3 回目のレビュー。形式 v36）

3 回目のレビュー（52453ae に対するもの。前の節と同じレビュー）で、キャッシュの健全性とグラフ・一括解析の頑健さについて 8 件が見つかった。
F 行の件数と先頭の行が検査値に入っていない（Q59）だけがこの作業で入れたもので、ほかはこの作業より前（6227970）から
あった。どれも「壊れた・古いキャッシュを黙って再利用する」「呼び出しを黙って落とす」「1 ファイルの失敗で設定ごと止まる」の
どれかになる。

対応の要点:

- 同じキャッシュのフォルダを使う実行を、フォルダの錠（`jche.cache.CacheLock`。`analysis-cache.tsv.lock`）で 1 つずつにした。
  あとの実行は待ち（上限つき）、待ちきれなければ理由を言って失敗する。グラフを組む側は、最後まで書き終えたキャッシュかを
  確かめてから組む。差分更新は旧キャッシュを 1 回だけ開き、書き写しまで同じものを読む（Q56）
- 解析のあいだに書き換えられたソースは、F 行の内容ハッシュを空にして書き、次の実行で必ず解析し直す（Q57）
- ソースフォルダの並びをキャッシュの鍵（ヘッダ行の `folders=`）に入れた（Q58）
- ブロックの検査値に F 行（crc 列を空にした形）を入れ、T 行に先頭の行の検査値を足した（Q59）
- `test/cacheversion` に依存 jar のある題材を足し、L 行も指紋に入れた（Q60）
- ソースフォルダからの相対パスが同じファイルは必ず同じバッチで解析し、片方を解析するときはもう片方も解析し直す。
  名前の違うファイルで同じ型を宣言していれば、グラフを組むときに警告する（Q61）
- JDT の `StackOverflowError` をそのファイルの失敗として扱う（Q62）
- 網羅していない switch 式などを構文エラーに数えない（Q63）
- 形式を v36 に上げた（F 行の検査値の範囲・T 行の列・ヘッダ行の鍵・F 行の構文エラー数が変わる）

どれも、足した検査（`test/incremental` の「同じキャッシュのフォルダを使う実行は 1 つずつ」「解析のあいだに書き換えたソース」
「同じクラスが 2 つのソースフォルダにある」「ソースフォルダの並びを入れ替える」、`test/regression` の `cacheblocks` の 8・9 回目、
`test/warnings` の `switches`・`deep`・`twins`）が 52453ae では落ち、今は通る（解析のあいだの書き換えの検査は、52453ae に
検査用の差し込み口だけを足したもので確かめた）。`test/cacheversion` の題材は、jar の型を経由した親型の集め方を変える変異を
足した題材でだけ捕まえることで確かめた（Q60）。

### Q56. 同じキャッシュのフォルダを 2 つの実行で使うと、何が起きていたのか。どう直したのか

キャッシュ本体の一時ファイル `analysis-cache.tsv.tmp` と退避ファイル `.partial` は、中断からの引き継ぎのために決まった名前で
ある。2 つの実行（CLI と Eclipse・VS Code のプラグインの解析サーバー、同じフォルダを使う CI のジョブ）が重なると、
あとの実行は、先の実行が書いている途中の `.tmp` を「中断した実行の残り」とみなして `.partial` に移し、自分の `.tmp` を
書き始める。先の実行は書き終えたつもりで `.tmp` を本物へ差し替えるが、それはあとの実行の書きかけである。グラフの構築は
ヘッダも最終行も確かめずに読むので、呼び出しの 1 本も無い CSV が終了コード 0 で出た。差分更新も、パス1 で覚えた位置から
パス5 で書き写すときにキャッシュを名前で開き直していたので、そのあいだに差し替えられると関係の無いバイトを写しうる
（検査で 2 つを同時に走らせると、52453ae では片方が `EOFException` で失敗した）。Q41 は「気づける食い違いは内部エラーとして
止める」と書いていたが、グラフの構築では止まらなかった。

直し方は 3 つ。

- **錠**（`jche.cache.CacheLock`）。キャッシュを読み書きするあいだ（フェーズ1 の差分更新からフェーズ2 のグラフの構築まで。
  `jche.Exporter` が取る）、キャッシュのフォルダの `analysis-cache.tsv.lock` に OS のファイルの錠（`FileChannel#tryLock`）を
  かける。取れなければ `[cache]` のログを 1 行出して待つ（間隔を 50 ミリ秒から 1 秒まで延ばしながら取り直す）。待つのは既定で
  最長 30 分で、環境変数 `JCHE_CACHE_LOCK_WAIT_SECONDS` で変えられる。上限を過ぎたら「ほかの実行がフォルダを使い続けた」と
  言って実行を失敗にする（warnings.txt の「The run failed」）。待っているあいだも中止を受け付ける。同じ JVM の中の重なり
  （`OverlappingFileLockException`）も「ほかが持っている」として待つ。錠の仕組みが無いファイルシステム（`tryLock` が
  `IOException` を投げる）では、錠なしで続け、同じフォルダを同時に使わないよう警告する（そのフォルダを使えなくするより
  よい。下の 2 つ目の直し方があるので、重なっても黙って空の CSV を出すことはない）
- **グラフの構築が確かめる**（`CallGraphBuilder.scan`）。ヘッダの形式の版、最終行の Z 行のブロック数、Z 行の後ろに行が
  無いことを確かめ、違えば組まずに例外にする（`graph.cacheIncomplete`）。錠があれば起きないが、錠を知らない古い版の
  このツールや手での書き換えが相手なら起きうる。起きたときに黙って空の CSV を出さないための最後の砦
- **旧キャッシュを 1 回だけ開く**（`CacheUpdater#openOldCache`）。パス0 からパス5 まで同じチャネルで読み（`CacheReader` は
  チャネルの位置を使わず、自分の位置で読むようにした）、読むたびに大きさが開いたときのままかを確かめる。パス1 の中で
  変わっていれば読めないキャッシュとして丸ごと捨て、パス3・パス5 なら `analysis.cache.changedWhileReading` で止める。
  差し替え（名前の付け替え）なら、開いたままのチャネルは前のファイルを読み続けるので食い違わない。差し替える前に閉じる
  （Windows は開いているファイルを置き換えられない）

却下した案:

- **一時ファイルの名前に PID を入れる。** 奪い合いは無くなるが、中断した実行の一時ファイルをどれが引き継ぐかが決まらない
  （生きている実行の一時ファイルと、落ちた実行の残りを見分ける手段が要る。それは結局、錠である）。本物への差し替えも
  2 つの実行が交互に行い、差分更新の土台にした旧キャッシュと差し替え先が食い違う
- **中身で見るロックファイル**（PID と時刻を書き、古ければ奪う）。落ちた実行の錠を消す手順と、「古い」の判定が要る。
  OS の錠はプロセスが落ちれば OS が放すので要らない
- **錠が取れなければすぐ失敗する。** プラグインと CLI を同じプロジェクトに使うのはよくある使い方で、待てば済むのに失敗に
  するのは不親切。逆に、**上限なしで待つ**と、止まった実行（デバッガで止めた解析サーバーなど）に CI のジョブがつかまり続ける
- **錠のファイルを放すときに消す。** 消した直後に別の実行が同じ名前で作り直すと、消される前に開いていた実行と作り直した実行が
  別々のファイルに錠をかけ、2 つが同時に「持っている」ことになりうる。空のファイルが 1 つ残るだけなので、残す
- **フェーズ3（CSV の出力）まで錠を持つ。** 出力はキャッシュを読まない（型解決に失敗した呼び出しの一覧も、グラフの構築のときに
  一時ファイルへ拾ってある。その一時ファイルは名前で開き直さないので、あとの実行の掃除で消されても読める）。
  長く持つほど、あとの実行を待たせるだけになる

検査: `test/incremental` の「同じキャッシュのフォルダを使う実行は 1 つずつ（錠）」。錠を持つ役のプログラム（`tools/LockHolder`）が
錠を取ったのを確かめてから解析を始めるので、時間に頼らずに「待ちきれずに失敗する」「待って最後まで進む」を見る。
2 つの解析を同時に始めて、どちらも成功し、どちらの出力も全件解析と同じで、残ったキャッシュを全件再利用できることも見る。
`tools/GraphCheck` は、途中で切れた・最終行が無い・数が合わない・最終行の後ろにブロックが続く・版が違うキャッシュから
グラフを組まないことを直接たたく（52453ae ではどれも組んでしまう）。

### Q57. 解析のあいだにソースを書き換えて元に戻すと、なぜ古い事実が残り続けたのか

F 行の内容ハッシュはパス1（とソース一覧の指紋）で取り、JDT はそのあとでファイルを読む。そのあいだに書き換えられると、
前の中身のハッシュと後の中身の事実が組になって残る。あとで元に戻すと、ハッシュが一致するので、書き換えた中身の事実を
そのファイルを次に書き換えるまで再利用し続けた。IDE で保存しながら解析サーバーを走らせる使い方で起きうる。
JDT は解析するファイルのほかに、参照している型のソースもソースパスから読むので、再利用するブロックのファイル（Y）を
書き換えて戻した場合も、Y を読んで解析したファイル（X）に古い事実が残る（Y のブロックのハッシュは一致するので
Y は変わっていないとみなされ、X へも連鎖しない）。

直し方:

- 解析したファイルは、JDT が読んだ直後にハッシュを取り直し、前と違えば F 行の内容ハッシュを空にして書く
  （`BlockWriter#hashAfterParse`）。空のハッシュはどの中身とも一致しないので、次の実行で必ず解析し直す
- 書き終えたら、どのソースも一覧を作ったときの大きさと更新時刻のままかを見て、変わったファイルのブロックも内容ハッシュを
  空にする（`CacheUpdater#invalidateChangedDuringRun`。一時ファイルを行として読み直して書き直す。めったに通らない経路）。
  次の実行はそのファイルを解析し直し、宣言する型を「変わった型」にして依存するファイル（X）も解析し直す
- どちらも `[cache]` のログに件数と例を出す（この実行の結果は前後の中身が混ざっているかもしれない、と知らせる）

更新時刻は実行のあいだの見張りにだけ使い、キャッシュには書かない。「同じファイルか」は今までどおりパス・サイズ・内容
ハッシュで見る（[cache-identity-qa.md](cache-identity-qa.md)）。見張りが空振りしても（更新時刻の刻みが粗く、同じ大きさで
書き換えた）、解析したファイルそのものはハッシュの取り直しで捕まる。

却下した案:

- **JDT が読むバイト列そのものをハッシュする。** 一括パース（`createASTs`）は JDT がパスからファイルを読むので、読んだバイトを
  受け取れない。自分で読んで `setSource` で 1 ファイルずつ渡す形にすると、一括パースの速さ（1 ファイルずつより約 14 倍速い。
  `CallEdgeExtractor` の説明）を失う。ソースパスから読まれる参照先のファイルは、どのみち捕まえられない
- **終わりに全ソースのハッシュを取り直す。** 確実だが、書き換えた実行のたびに全ソースを読み直す。更新時刻と大きさの見張りで
  足り、解析したファイルは JDT が読んだ直後に取り直している（OS のキャッシュに載っているので安い）
- **変わっていたら実行を失敗にする。** 利用者が対処することは「もう一度実行する」だけで、次の実行が解析し直せば済む

限界: 同じバッチを解析しているあいだに書き換えて元に戻し、しかも更新時刻が変わらない（刻みの中で 2 回書いた）場合は
見分けられない。中断した実行の一時ファイルは終わりの見張りを通っていないので、中断のあいだに書き換えて戻したソースを
読んだブロックを引き継ぎうる（引き継ぐのはソース一覧が丸ごと同じときだけ）。

検査: `test/incremental` の「解析のあいだに書き換えたソース」。`tools/jche/analysis/EditDuringRunCheck` が、そのファイルを
含むバッチを JDT に渡す直前に書き換え（`CacheUpdater.beforeBatchForTest`。本番では null の差し込み口）、実行のあとで
元に戻す。解析するファイルそのものを書き換える場合と、参照されるファイル（再利用するブロック）を書き換える場合の 2 つで、
次の実行の差分更新が全件解析と CSV もキャッシュも一致することを見る。

### Q58. ソースフォルダの並びを、なぜキャッシュの鍵に入れたのか

JDT は、同じ名前の型が 2 つのソースフォルダにあると、ソースパスの先に並ぶ方で解決する（同じバッチなら後ろの方を重複の
エラーにする。Q61）。`source.folders` の並びを入れ替えると、どのソースも変わっていないのに解決先が変わるが、差分更新は
ソースの同一性と I 行しか見ないので、全件を再利用して前の並びの結果を出し続けた。依存 jar は L 行の並びまで見ている
（[cache-dependency-jars-qa.md](cache-dependency-jars-qa.md)）のに、ソースフォルダは見ていなかった。

ヘッダ行に `folders=<project.root からの相対パスを並びのまま改行でつないだもののハッシュ>` を足した。違えば丸ごと捨てて
全件解析する（中断した実行の一時ファイルも引き継がない）。フォルダを足した・外しただけでも全件解析になるが、設定を変えた
ときの 1 回だけで、安全側の費用として受け入れる。

（その後、形式 v38 で、ハッシュをやめてフォルダの一覧そのものを書き、フォルダを足した・外しただけなら使い続けるようにした。
同じ project.root・同じキャッシュのフォルダで source.folders だけが違う 2 つの設定を交互に動かすと、「1 回だけ」では
済まなかった。Q67）

却下した案:

- **L 行のように先頭の行で突き合わせ、影響するファイルだけを解析し直す。** 並びが効くのは同じ名前の型が 2 つのフォルダに
  あるときだけだが、どの型が重なっているかは、有効なブロックの H 行を全部覚えておかないと分からない。設定を変えたときの
  1 回のために、毎回の実行で持つものを増やすことになる
- **フォルダのパスそのものをヘッダ行に書く。** ヘッダ行は符号化しない行なので、タブ・改行を含むフォルダ名で行が壊れる。
  ハッシュにした（目で見て確かめたいときは run.log の「Source folders」の行を見る）。（v38 で、名前を列の規則で符号化した
  うえで書くようにした。Q67）

### Q59. ブロックの検査値に F 行を、なぜ入れたのか。先頭の行はどう守るのか

ブロックの検査値（Q25）は F 行の次の行からしか数えていなかった。書き写すブロックのエラー数・構文エラー数・未解決数は
U 行を読まずに F 行の列から数える（Q25・Q31）ので、F 行の件数が化けると、コンパイルエラーの警告や「型解決できなかった
呼び出しが N 件」の件数が黙って変わる（`test/regression` の `cacheblocks` で未解決数の列を 0 にすると、52453ae は 107 件を
再利用して件数が 4 件から 1 件に減った）。先頭の行（L 行・T 行）はどこにも検査値が無く、L 行のパッケージの一覧が化けると
jar の変化を見落としうる。

- **F 行は、自分の crc 列を空にした形（最後のタブまで）でブロックの検査値の先頭に入れる。** 書き手は crc 列を空にした F 行を
  組んで検査値を求め、それを最後の列に入れて書く。読み手は F 行の最後のタブまでのバイトを足す（`CacheReader#addWithoutLastColumnTo`）
- **先頭の行は T 行の最後の列に検査値を持つ。** ヘッダ行・L 行と、最後の列を空にした T 行を同じ手順で並べた CRC32。
  合わなければ、キャッシュなら丸ごと捨てて全件解析し（`analysis.cache.headDamaged`）、中断した実行の一時ファイルなら引き継がない。
  T 行が 2 つある・L 行が T 行より後ろにあるものも合わないとみなす

却下した案:

- **先頭の行の検査値を Z 行（最終行）に置く。** 中断した実行の一時ファイルには Z 行が無いので、引き継ぎの判定に使う T 行・L 行を
  守れない。T 行は先頭の行の最後にあるので、F 行と同じく「検査値を書く行がまとまりの最後」の形にできる
- **F 行の件数だけの検査値の列を別に足す。** 列が増えるだけで、ブロックの検査値に入れれば 1 つで済む
- **件数の列を書き写すときに U 行から数え直す。** 書き写しをバイトの範囲のまま行う（Q31）利点を失う

`test/regression` の `cacheblocks` に 2 つ足した。8 回目は F 行の未解決数だけを 0 にして、そのファイル（とその型を使う
1 ファイル）だけを解析し直し、件数の警告が残ること、9 回目は T 行の指紋だけを書き換えて、丸ごと作り直すことを見る。
キャッシュの検査値を確かめる検査のスクリプトも、F 行と先頭の行を含めて計算し直すようにした（列が足りない行で
スクリプトが例外になると「合う」と数えていたのも直した）。

### Q60. `test/cacheversion` に、なぜ依存 jar のある題材を足したのか

形式の版の上げ忘れの検査（Q21）は、jar の無い題材（test/demo・test/incremental・test/jls/project）しか見ていなかった。
jar を経由した親型（H 行）、jar の型への呼び出しの解決、L 行（jar の指紋とパッケージ）の作り方を変えても、どの題材の
事実も変わらないので捕まらない。test/demo を `library.folders=deps`（`missing-lib.jar`。jar の `missing.lib.LibDao` が
ソースの `fx.dao.Dao` を実装し、ソースの `fx.dao.LibBackedDao` がそれを継承する）で解析する題材 `demojar` を足し、
指紋に L 行も入れた。L 行の jar のパスはファイル名だけにする（置き場所は環境で変わる。指紋とパッケージは残す）。
題材の指紋には jar のバイト列も入れた。

確かめ方: `TypeContextTracker#collectSupertypes` を「jar の型の先にあるソースの親型を 1 段目でしか拾わない」に変える
変異を入れると、`demojar` の指紋だけが変わって落ちる（ほかの 3 つの題材の指紋は変わらない。以前の題材だけでは
素通りしていた）。

### Q61. 同じクラスが 2 つのソースフォルダにあると、なぜ差分更新と全件解析が食い違ったのか

JDT は、同じ名前の型を宣言する 2 つのファイルを同じバッチで渡されると、ソースフォルダの並びで後ろの方に「型が重複している」
エラーを出して、その型を読まない（その中の呼び出しは型の外の呼び出しとして未解決になる）。別々のバッチならどちらもエラーなしで
読む。全件解析では 2 つが同じバッチ（100 件）に入りやすく、差分更新は変わった片方だけを解析するので、同じソースから違う
事実ができた。グラフを組む側も、同じメソッドが 2 つのブロックで宣言されていると後から読んだ方を黙って勝たせていた
（`MethodTable#setDeclaration`）。キャッシュの中のブロックの並びは差分更新で変わるので、methods.csv の宣言の場所も変わった。

直し方（`jche.analysis.SameUnitFiles`）:

- **コンパイル単位の名前**（ソースフォルダからの相対パス。`p/Dup.java`）が同じファイルを組にし、全件解析でも差分更新でも、
  組は必ず同じバッチにソースフォルダの並びの順で並べる（バッチは組の最初のファイルの位置に組をまとめ、組を切らないので
  100 件を少し超えることがある）
- 組の 1 つを解析するときは、組のほかのファイルも再利用せずに同じ一覧に入れて解析し直す（パス2 とパス3。依存の判定そのものは
  変えず、一覧を作ったあとに足すだけ）。中断した実行の一時ファイルからは、組のファイルを引き継がない
- 名前の違うファイルで同じ型を宣言している場合（public でないトップレベルの型）は、ファイル名からは組にできない。
  グラフを組むときに同じメソッドキーが 2 つのファイルで宣言されていれば、`graph.duplicateType` を warnings.txt の
  「ソースにコンパイルエラーがある」に載せ（20 組まで）、メソッドの宣言は先に並ぶソースフォルダ（同じならパスの順）の
  ものを使う（キャッシュのブロックの並びに依らない）。この形は差分更新と全件解析とで食い違いうる（限界として残した。Q68）
- ~~`package-info.java`・`module-info.java` は組にしない。型を持たず、メインとテストのソースフォルダに同じ名前でよく置かれる~~
  （誤り。アノテーションの付いた `package-info.java` には JDT が `package-info` という型を作るので、組にしないと差分更新と
  全件解析とで warnings.txt が食い違った。v38 で組にした。Q66）

却下した案:

- **パス3 で、有効なブロックの H 行が「変わった型」に触れるものも解析し直す**（レビューの提案）。解析し直すことにはなるが、
  パス2 とは別のバッチになるので、JDT はどちらにも重複のエラーを出さず、全件解析とはやはり違う。有効なブロックの H 行を
  依存の索引に書き足す必要もある。組はパスだけで解析の前に決まるので、全件解析のバッチも同じ形にそろえられる
- **重複を見つけたら実行を止める。** Maven ではテストのソースフォルダにメインと同じクラスを置いて差し替えることがあり、
  それを解析対象に含めることもある。止めずに、どちらが読まれたかと直し方を案内する

検査: `test/incremental` の「同じクラスが 2 つのソースフォルダにある」は、片方にコメントを足した差分更新が全件解析と CSV も
キャッシュも一致し、後ろの方のファイルがどちらでも warnings.txt に載ることを見る（52453ae では差分更新だけ両方の型を読み、
呼び出しが 2 本多く、warnings.txt にも載らない）。`test/warnings` の `twins` は、名前の違う 2 つのファイルの間に 100 を
超えるファイルを置いて別々のバッチにし、警告が出ることを見る。

### Q62. 1 つのファイルのスタックが溢れると、なぜ設定ごと失敗したのか

JDT のフロー解析（`MessageSend.analyseCode` など）は式の入れ子を再帰でたどるので、メソッド呼び出しを数千段つないだ式
（生成されたコードの `StringBuilder` の連鎖など）でスタックが溢れる。一括パース（`CallEdgeExtractor#analyzeBatch`）は
`RuntimeException` しか捕まえておらず、`StackOverflowError` はその設定の解析をまるごと失敗させた（CSV は出ない）。

今は、一括パースの途中で溢れたら、そのバッチの残りを 1 ファイルずつ解析し（どのファイルかは分からないため）、1 ファイルの
解析で溢れたら、そのファイルだけを失敗として数える（`Sink#failed`。warnings.txt の「解析や出力が途中で打ち切られた」に、
式を分けるかスタックを大きくする案内つきで載る）。事実を集める側（`FactVisitor`）で溢れた場合も同じ。溢れたスタックは
例外が外へ抜けるあいだに戻るので、捕まえたあとは続けられる。

スタックを大きくする案内は `JDK_JAVA_OPTIONS=-Xss16m` にした（3,500 段の連鎖が通ることを確かめた）。`JAVA_TOOL_OPTIONS` の
`-Xss` は JVM が読むもので、ランチャーが main を走らせるスレッドの大きさには効かない（試して通らなかった）。

却下した案:

- **解析を大きなスタックのスレッドで走らせる。** 溢れる段数は上がるが、どこかで溢れることには変わらず、1 ファイルの失敗として
  扱う経路はどのみち要る。スレッドを分けると中止・進捗・ログの扱いも変わる
- **`Throwable` を捕まえる。** `OutOfMemoryError` まで 1 ファイルの失敗として飲み込むと、ヒープ不足という対処の違う事態を
  隠してしまう。捕まえるのは `StackOverflowError` だけにした

検査: `test/warnings` の `deep`（1 万段の連鎖）。実行が成功し、そのファイルが warnings.txt に載り、ほかのファイルの呼び出しが
出力に出ることを見る。

### Q63. 網羅していない switch 式が、なぜ「構文エラー（本体を読めなかった）」と報告されたのか

JDT は switch 式の検査（default が無い・列挙定数を網羅していない・switch 式の外への break / continue / return）の問題にも
`IProblem.Syntax` の印を付ける。これらは構文を読み終えたあとのフロー解析で出るもので、本体の呼び出しはすべて AST に残る
（確かめた）。構文エラーに数えると「このファイルの呼び出しは出力に出ない」と事実と違う警告になり、利用者は出ている呼び出しを
探し回ることになる。sealed の許可リストに型を足して switch を直していないときによく出る。var の使い方の誤り
（[syntax-error-report-qa.md](syntax-error-report-qa.md) の Q7）と同じく、構文エラーの数からは外し、コンパイルエラーとしては
数えたままにした。F 行の構文エラー数が変わるので、形式の版を上げた。

却下した案:

- **本物の構文エラー（パーサの問題）の印の一覧で数える。** JDT の版が上がってパーサの問題が増えると、数え落として
  「本体を読めていないファイル」を黙って通してしまう。外す一覧（本体が残ると確かめたもの）なら、数え落としの側には倒れない
- **AST の節の MALFORMED / RECOVERED の印で見る。** 構文エラーのすべてが節に印を残すわけではなく、どの節を見ればよいかも
  問題ごとに違う

検査: `test/warnings` の `switches`（sealed を網羅していないパターンの switch 式と、列挙定数を網羅していない switch 式）。
コンパイルエラーとしては案内し、構文エラーとは言わず、switch の中の呼び出しが出力に出ることを見る。

### Q64. I 行の解決できなかった名前に、なぜチェックアウトの場所のフォルダ名が入っていたのか

I 行の 3 列目（解決できなかった名前。Q42）は、JDT のエラーの引数（`IProblem#getArguments`）から点区切りの識別子を
拾っている（`CallEdgeExtractor#namesOf`）。型の名前が入りうる引数を取りこぼさないよう、エラーの種類では絞らない。
ところが型が重複しているエラー（`The type Dup is already defined`。同じクラスが 2 つのソースフォルダにある Q61 の形）は、
引数にソースファイルのパスを入れる。一括で解析するときのパスは絶対パスなので、

```
I			Dup,Dup.java,b0b5,call,claude,d9a7,...,home,java,p,s2,scratchpad,tmp,user
```

のように、チェックアウトの場所のフォルダ名がキャッシュに入っていた。同じソースでも、置き場所が違えばキャッシュの事実が
変わる（`test/cacheversion` の事実の指紋も置き場所に依存しうる）。拾った名前は変わった型の単純名・FQN の頭と突き合わせる
（`StaleTypes#matchesChangedType`）ので、`p` や `test` のような名前の型が変わるたびに、関係の無いブロックまで解析し直す
ことにもなる。

今は、パスの区切り（`/` か `\`）を含む引数は拾わない。

- 型の名前・パッケージの名前の引数は点で区切るので、パスの区切りを含まない。型が重複しているエラーの型の名前は、
  パスとは別の引数（`Dup`）に入るので残る
- パスの区切りを含む引数でほかに現れるのは演算子（`The operator / is undefined …` の `/`）で、識別子を含まないので
  落としても何も失わない
- 名前を 1 つも拾えなくなれば、これまでどおり `*`（どの新しい型にも当たる）を書く。取りこぼしは安全側に倒れる

キャッシュの事実（型が重複しているファイルの I 行）が変わるので、形式を v37 に上げた。決まった題材（`test/cacheversion`）には
型が重複しているファイルが無く、事実の指紋は変わらなかった（版の行だけを `--update` で合わせた）。

却下した案:

- **拾うのを「型が見つからない」「import が解決できない」などの問題の種類だけにする。** 名前が入る問題の種類は多く
  （見えない型・曖昧な型・間接的に参照される型など）、JDT の版が上がって種類が増えると黙って取りこぼす。取りこぼすと、
  型を足しても型解決に失敗したブロックを解析し直さない（Q42 の見落としに戻る）
- **`.java` で終わる引数を落とす。** パッケージの名前が `java` で終わる（`com.acme.java`）import のエラーの引数まで落とす

検査: `test/incremental` の「同じクラスが 2 つのソースフォルダにある」で、重複した型のファイルの解決できなかった名前が
空でなく、題材を置いたフォルダのパスの部分（`home`・`incremental` など）を含まないことを見る。直す前のツールでは落ちる。

### Q65. `HashMap` の子の私的な入れ子の型を足したのに、なぜ部分型の利用者が古いまま残ったのか

型の形は、私的メンバーを、それを宣言した型の親型に私的でない同じ名前のメンバーがあるときだけ入れる（Q51）。その判定
（`TypeShape#namesAbove`）は、`java.*` の親型に着くと、その型が宣言するメンバーの名前だけを数えて、さらに上を辿らなかった
（`walk` が JDK の型のメンバーを行にしないのに合わせた）。ところが私的メンバーが隠すのは直接の親のメンバーに限らない。

```java
public class Registry extends java.util.HashMap<String, Object> {
    private static final class Entry { }          // Map.Entry を隠す（JLS 8.5）
}
public class NamedRegistry extends Registry { }
public class Client extends NamedRegistry {
    void m(Object o) { ((Entry) o).getKey(); }    // 同じパッケージの pr.Entry に変わる
}
```

`Map.Entry` を宣言しているのは `HashMap` ではなく `Map` なので、名前は当たらないと判定され、`Entry` は型の形に入らなかった。
`Registry` を解析し直しても `NamedRegistry` の形が変わらず、`Registry` を参照していない `Client` は解析し直されない。全件解析では
`pr.Entry#getKey` への呼び出しになるのに、差分更新では `Map.Entry#getKey` のまま残った（`AbstractMap.SimpleEntry` を
`HashMap` の子で隠す場合も同じ。消す向きも同じ）。

今は、`java.*` の親型でも止めず、そのインターフェース・親型まで全部辿って名前を集める。JDK の型のメンバーを行にしない
（`walk`）のは JDK の版がキャッシュの鍵に入っているからで、名前が当たるかどうかとは別の話だった。あわせて見直したこと:

- **JDK の型のインターフェース**（`HashMap` の `Map`・`Cloneable`・`Serializable`）: 辿る
- **`Object` のメンバー**: クラスは親型の連鎖の終わりに `Object` があるので辿れる。インターフェースは `Object` を親に持たないが、
  その public メソッドに当たるメンバーを暗黙に宣言する（JLS 9.2）ので、`Object` のメソッドの名前を足す
- **JDK のインターフェースの入れ子の型**（`Map.Entry`）: `getDeclaredTypes` で数える
- **型引数のある親型**（`HashMap<String, Object>` とその `Map<String, Object>`）: 型引数を当てたバインディングのまま辿り、
  メンバーの名前は同じに取れる（検査の題材がこの形）

費用: 私的メンバーを持つ型ごとに、JDK の親型のメンバーの名前も集める（1 つの型の形を作るあいだは覚えておく）。
`javax.swing.JPanel` と `HashMap` を継承して私的メンバーを持つクラスを 300 個ずつ（600 ファイル）全件解析して、ソース解析の
時間は 01eb510 と差が無かった（どちらも 2.6〜2.8 秒で、ばらつきの範囲）。
test/demo の再解析の件数は変わらない（`fx/dao/AbstractDao.java` に私的メソッドを足す・私的フィールドを足す・公開メソッドを
足す・コメントだけ変える、で 4・4・20・4 件。Q51 と同じ）。

却下した案: **JDK の型のメンバーの名前を、あらかじめ一覧にして持つ。** JDK の版で変わり、一覧を作る手間も要る。JDT の
バインディングから取れば、実行中の JDK のものがそのまま取れる。

検査: `test/incremental` の「java.* の親型の上（Map.Entry）を隠す私的な入れ子の型を足す」「…を消す」「…（AbstractMap.SimpleEntry）を
隠す…を足す」。01eb510 では 3 つとも methods.csv とキャッシュが食い違い、今は通る。

### Q66. `package-info.java` が 2 つのソースフォルダにあると、なぜ warnings.txt が食い違ったのか

同じ名前のファイルの組（Q61）から、`package-info.java`・`module-info.java` を外していた（型を持たないと考えた）。ところが
JDT は、アノテーションの付いたパッケージ宣言（`@Deprecated package p;`）に `package-info` という型を作る。メインとテストの
ソースフォルダの両方にアノテーションの付いた `package-info.java` があると、全件解析では 2 つが同じバッチに入って後ろの方が
「型が重複している」エラーになり、片方だけを書き換えた差分更新ではそのファイルだけを解析するのでエラーにならない。
warnings.txt の「ソースにコンパイルエラーがある」のファイルの一覧が、差分更新と全件解析とで食い違った。

今は、この 2 つも組にする（`SameUnitFiles` の除外をやめた）。組は必ず同じバッチにソースフォルダの並びの順で並べ、片方を
解析するときはもう片方も解析し直すので、どちらを書き換えても全件解析と同じ事実になる。`module-info.java` は 2 つあると
どちらもエラーになり、組にしても結果は変わらない（試した）が、同じ理由で外す理由が無い。費用は、片方を書き換えたときに
もう片方も解析し直すことだけ。

却下した案: **アノテーションの付いた `package-info.java` だけを組にする。** 付いているかどうかはソースを読まないと分からず、
組は解析の前にパスだけで決める（Q61）。

検査: `test/incremental` の「アノテーションの付いた package-info.java が 2 つのソースフォルダにある」（後ろ・前のどちらを
書き換えても、CSV・warnings.txt・キャッシュが全件解析と同じ）。01eb510 では warnings.txt が食い違う。

### Q67. ソースフォルダを足しただけで、なぜ毎回全件解析になっていたのか

Q58 でヘッダ行に入れたのは、ソースフォルダの並びのハッシュだった。フォルダを足した・外しただけでも鍵が変わるので、
同じ project.root・同じキャッシュのフォルダで、source.folders だけが違う 2 つの設定（`src` と `src,test`。メインだけの解析と
テストを含めた解析）を交互に動かすと、毎回全件解析になっていた（52453ae では 4 ファイルの題材で再利用 3 件、01eb510 では毎回 0 件）。

正しさに効くのは、**両方にあるフォルダの相対的な並び**だけである。

- JDT は同じ名前の型を先に並ぶフォルダで解決する。両方にあるフォルダの並びが同じなら、両方にあるファイルどうしの勝ち負けは変わらない
- 足したフォルダのファイルは旧キャッシュに無いので、足したファイルとして解析する（宣言する型は「変わった型」になり、使う側も
  解析し直す。同じ名前のファイルの組は今のソースの一覧から作るので、足したフォルダに同じ名前のファイルがあれば、もう片方も
  一緒に解析し直す）
- 外したフォルダのファイルは、消したファイルとして扱う（宣言していた型は「変わった型」になる）

ただし、**入れ子のフォルダ**（`src` と `src/gen`）は別である。入れ子のフォルダを足す・外すと、同じファイル（同じ相対パス・
同じ中身）のソースフォルダからの相対パス（コンパイル単位の名前）と、ソースパスから見つかる型が変わる。足した・消した
ファイルとしては扱えない。

今の形:

- ヘッダ行の `folders=` に、project.root からの相対パス（`/` 区切り。project.root そのものは `.`）を並びのままカンマでつないで
  書く。名前は列の符号化（`CacheFormat#escape`）をしたうえで、カンマと空白も `,`・` ` にする（ヘッダ行は
  符号化しない行で、読むときに端の空白を削るため）。符号化は文字ごとの置き換えで、置き換えた形はどれもほかの形の頭に
  ならないので、符号化したままで「同じか」「`a/` で始まるか（入れ子か）」を見てよい
- 旧キャッシュは、ヘッダ行がフォルダの一覧のほかは同じで、両方にあるフォルダが同じ順に並び、どちらの一覧のフォルダも
  別のフォルダの中に無ければ使い続ける（`CacheFormat#headerReusable`。ログに `[cache] Source folders were added or removed`）。
  並びが入れ替わった・入れ子があるなら、これまでどおり丸ごと捨てる
- 中断した実行の一時ファイルは、ヘッダ行が丸ごと同じときだけ引き継ぐ（ソースの一覧が丸ごと同じときだけ引き継ぐのと同じ考え方）

却下した案:

- **ハッシュのまま、フォルダごとのハッシュを並べる。** 入れ子かどうかが分からない
- **フォルダの一覧を L 行のように別の行にする。** 行の種別が増え、先頭の行の検査値・何も変わらないときの判定・検査の
  スクリプトの行の読み方も直すことになる。ヘッダ行の中で完結させた
- **入れ子のときも、ファイルごとにコンパイル単位の名前が変わったかを見て使い続ける。** 旧キャッシュのフォルダの一覧から
  名前を求め直す仕組みが要る割に、入れ子のソースフォルダはまれである

検査: `test/incremental` の「ソースフォルダを足す・外す」（`s1` → `s2,s1` → `s1` → `s1,s2`。先に並べた `s2` に同じ名前の
`p/Dup.java` を置き、解決先が変わる題材。どの段でもキャッシュを使い続け、CSV・warnings.txt・キャッシュが全件解析と同じ）と
「入れ子のソースフォルダを足す」（使い続けない）。並びを入れ替えたときは、これまでどおり「ソースフォルダの並びを入れ替える」で
捨てることを見る。

### Q68. 名前の違う 2 つのファイルで同じ型を宣言していると、何が食い違うのか。なぜ直さなかったのか

`src1/p/X.java` と `src2/p/Y.java` がどちらも `class Hid` を宣言している（public でないトップレベルの型）とき、JDT は、2 つが同じ
バッチなら後ろの方の `Hid` を「重複している」として読まず、別々のバッチなら両方を読む。全件解析では 2 つが同じバッチに
入りやすく、`Y.java` を書き換えた差分更新は `Y.java` だけを解析するので両方の `Hid` を読み、グラフを組む側は 2 つの `Hid` の
メソッドを 1 つの型にまとめる。結果、全件解析では出ない `Hid.b` の呼び出しが差分更新では出る。しかも警告
（`graph.duplicateType`）は「片方しか解析できず、もう片方の呼び出しは出力に出ない」と書いていたが、差分更新ではまとめて
出しており、事実と違った。

同じ名前のファイル（Q61）と違い、どのファイルがどの型を宣言するかは解析の前には分からない。差分更新と全件解析を必ず
一致させるには、

- 全件解析でも、どのバッチに入ったかに依らない形（組を必ず同じバッチにする）にそろえる必要があり、解析の後で重なりを
  見つけたら、書き終えたブロックを捨てて組を解析し直し、さらにその型を使うファイル（同じバッチにいたかどうかで解決先が
  変わる）も解析し直すことになる（ブロックは書いたら捨てる作りなので、キャッシュを書き直す仕組みも要る）
- 差分更新でも、変わったファイルが宣言した型を、有効なブロックのどれが「文字の上で」宣言しているかを知る必要がある
  （重複のエラーになった側には H 行が無い）ので、宣言した型の名前をキャッシュに持たせることになる

ビルドの通らない状態（javac でも同じパッケージの同じ名前の型はエラー）のために、書き直しの仕組みと列を足すのは釣り合わない
と判断し、限界として残した（Q41）。代わりに、案内を事実に合わせた:

- `graph.duplicateType` の文言を「どちらの宣言を読むかは一緒に解析するファイルで決まり、片方の呼び出しが出ないことも、
  両方が 1 つの型にまとめられる（同じシグネチャのメソッドは 1 つにして X の宣言として出す）こともあり、実行によって（全件解析と
  差分更新とで）変わりうる」に変えた。「（同じクラスが 2 つのソースフォルダにある）」の決めつけも外した（同じフォルダの
  名前の違う 2 つのファイルでも出る。`test/warnings` の `twins`）
- 片方を読まなかったときは、そのファイルが「ソースにコンパイルエラーがある」の一覧に載る（これまでどおり）

どちらの場合も warnings.txt に載り、直し方（重複を消すか、source.folders にどちらかのフォルダだけを書く）は同じである。

却下した案:

- **重複のエラーが出たファイルを、1 ファイルだけで解析し直す**（どちらの型も必ず読む形にそろえる）。宣言した側はそろうが、
  その型を使う側は、同じバッチに宣言したファイルがいたかどうかで解決先が変わる（バッチの中の最初の宣言か、ソースパスの
  先勝ちか）。使う側まではそろわない
- **重複を見つけたら実行を止める。** Q61 と同じ理由で止めない

### Q69. 受け手の中でスタックが溢れると、なぜそのファイルが消えたのか

Q62 で、一括パースの途中の `StackOverflowError` を捕まえるようにしたが、ファイルごとの受け手（`Sink#accept`。キャッシュへ
書く側）の呼び出しは `RuntimeException` しか捕まえていなかった。受け手の中で溢れると、外の catch（一括パースの溢れ）まで
抜けて残りを 1 ファイルずつ解析するが、そのファイルは一括パースの控えから外した後なので、受け取ったとも失敗したとも
数えられずに消える（呼び出しも warnings.txt の案内も出ない）。1 ファイルずつ解析する経路では、例外が外へ抜けて設定ごと
失敗した。受け手は値グラフを組み終えたものを書くだけなので、ふつうは溢れない（理屈の上の穴）。

今は、どちらの経路でも受け手の `StackOverflowError` をそのファイルの失敗（`Sink#failed`。スタックの案内つき）にする。

検査: `test/incremental` の「受け手の中でスタックが溢れたファイルも失敗として数える」（`jche.analysis.SinkOverflowCheck`。
受け手が決まったファイルで溢れる。深い式のファイルを先に並べて、1 ファイルずつの経路も通す）。01eb510 では、一括パースの経路で
そのファイルがどちらにも数えられず、1 ファイルずつの経路では例外が外へ抜ける。

### Q70. 形式の版を上げたか。何を確かめたか
