# AST 解析の性能とメモリ使用量の改善 — 実装時の QA 一覧

フェーズ1（ソースを AST パースして事実を集め、キャッシュへ書く）の速度と、そこで作られる
ゴミ（GC の対象になる一時オブジェクト）を減らした。迷ったこと・結論・却下した案を Q&A の形で残す。

対応の要点:

- 同じ型の名前を何度も作り直さない（`BindingNames.typeNameOf` をバインディングのインスタンスごとに覚える）
- 修飾子の語（`public,static,final` 等）を組み立て済みで共有する（`BindingNames.modifiersOf`）
- 解決できなかった呼び出しのための候補の推定を、<b>実際に失敗したときまで遅らせる</b>（`CallSiteRecorder.externalGuessRef`）。
  あわせて import 文の線形探索を単純名の表に置き換えた
- フィールド参照（A行）の行番号を「フィールドだと分かってから」求める（`FieldAccessRecorder.record`）
- `MethodDeclaration` のバインディング解決を1回にまとめる（`FactVisitor`）
- キャッシュの行の組み立て・読み取りを軽くする（`CacheFormat.clean` / `joinRow` / `columnsOf`、`ModifierTokens.has`）
- ソースの読み込みで要らない写しを作らない（`CallEdgeExtractor.analyze`）

計測（1000 ファイル・1ファイルあたり import 30 本・フィールド参照が多い合成プロジェクト、JDK 21、`-Xmx3g`）:

| | フェーズ1 | GC が回収した合計 |
|---|---|---|
| 変更前 | 13.0〜13.2 秒 | 8.7〜9.1 GB |
| 変更後 | 12.1〜12.2 秒 | 6.5〜6.8 GB |

出力（`call-hierarchy.csv` / `methods.csv`）とキャッシュの中身は変わらない。
`test/regression` `test/dataflow` `test/conditions` `test/incremental` `test/cachevalue` `test/cachetail` で確認した。

## Q1. どこが遅いのかを、どうやって見分けたか

合成プロジェクトを解析しながら JFR（`-XX:StartFlightRecording=settings=profile`）でサンプリングし、
スタックの葉と、`jche.` で始まる一番内側のフレームで数えた。結果は次のとおり。

- JDT 自身の構文解析・型解決 … 5〜6 割。ここは外から減らせない
- JDT がクラスファイルを生成している … 7% 前後（Q2）
- JDT がソースフォルダの一覧を読み直している … 6% 前後（Q3）
- このツールのコード … 2 割弱。うち半分はキャッシュの読み書き（`CacheReader` / `CacheFormat`）で、
  残りが AST の走査（`FieldAccessRecorder` / `CallSiteRecorder` / `BindingNames`）

**結論**: 「AST の走査」だけを速くしても全体は動かない。走査・キャッシュの読み書きの両方から、
<b>同じ答えを何度も作り直している箇所</b>を消す方針にした。当て推量で書き換えず、
必ず計測してから直した（実際、最初に疑った箇所のいくつかは誤差の中だった）。

## Q2. JDT がクラスファイルを生成しているのを止められないか

止められない。`CompilerOptions` には
`org.eclipse.jdt.core.compiler.generateClassFiles`（値は `enabled` / `disabled`）があり、
設定すると `CompilerOptions.generateClassFiles` は確かに false になる。しかしこのフラグを見ているのは
`Compiler.compile()` の側で、`ASTParser.createASTs` が通る
`CompilationUnitResolver` → `Compiler.process()` の経路では参照されない。`process()` で
`generateCode()` を止められるのは `ignoreMethodBodies` だけで、これを立てるとメソッド本体の解析ごと
無くなる（呼び出しが一切取れない）。

**却下した案**: 設定だけ入れておく。読んだ人が「効いている」と誤解するうえ、JDT の版が上がって
経路が変わったときに気づけない。効かない設定は入れない。

## Q3. バッチのサイズ（`CallEdgeExtractor.BATCH_SIZE`）を大きくすれば速くならないか

速くはなる。ただしメモリと引き換えで、既定を変えるほどの差ではなかった。

1200 ファイルの合成プロジェクトで、フェーズ1 の時間と、その規模を解析しきれる最小の `-Xmx`:

| バッチ | フェーズ1 | 最小 `-Xmx` |
|---|---|---|
| 100（現状） | 8.9 秒 | 128 MB |
| 400 | 8.7 秒 | 192 MB |
| 1200（全件1バッチ） | 7.8 秒 | 512 MB |

速くなるのは、バッチごとに JDT が名前環境とソースフォルダの一覧を作り直すため（Q1 の 3 つ目）。
一方でメモリは 4 倍に増えた。

**却下した案1**: 既定を大きくする。このツールは規模の分からないプロジェクトに向けるもので、
1 割強の速さのために「大きなプロジェクトでヒープが尽きる」を招くのは割に合わない。

**却下した案2**: 実行環境のヒープ量からバッチのサイズを決める。速さは出るが、
<b>解析する機械によってバッチの切れ目が変わる</b>。バッチの切れ目で出力が変わらないことは
保証していない（JDT はバッチ単位で名前環境を作る）ので、
「同じソースなら同じ出力」（`docs/deterministic-row-order-qa.md`）が機械依存になりかねない。

## Q4. パースを並列に走らせなかったのはなぜか

バッチどうしは独立なので、複数スレッドで走らせれば 4 コアで数倍になりうる。それでも今回は入れなかった。
計測の結果は Q4b にある（4 コアで速くなるのは 1.4 倍どまり、そのかわりヒープの最大は 1.6 倍）。

- **拡張（プラグイン）が壊れる**。`CallSiteHintCollector` は利用者が書くもので、
  スレッド安全である保証がない。並列にすると、拡張を入れている利用者にだけ静かな誤りが出る
- **メモリが増える**。今は「1ファイル分の事実を作ってはキャッシュへ書いて捨てる」ので、
  ヒープに載るのは 1 バッチ分だけ。並列にすると、出力の順序を保つために
  スレッド数ぶんのバッチの結果を溜めることになり、今回の目的（メモリを減らす）と逆を向く
- **出力の決定性**。書き出す順は保てるが、バッチの切れ目そのものが変わると Q3 と同じ懸念が残る

**結論**: やるなら「拡張が無いときだけ」「並列度とバッチ数に上限を置く」「出力順を明示的に戻す」を
そろえた独立した変更として、計測付きで入れる。今回の変更とは切り離す。

## Q4b. 仮想スレッド（Virtual Thread）なら、メモリを増やさずに待ち時間を消せないか

**消せない。この処理には消せる待ち時間がほとんど無く、仮想スレッドはメモリをむしろ増やす。**

仮想スレッドが効くのは「たくさんのタスクが、ほとんどの時間ブロックして待っている」形。
フェーズ1 を JFR で見ると、待っている時間そのものが無かった（1000 ファイル・フェーズ1 12.2 秒）。

| 計測項目 | 値 |
|---|---|
| ファイル読み込み（`jdk.FileRead` 58,674 件） | 合計 359 ms（計測の overhead 込み） |
| キャッシュ書き出し（`jdk.FileWrite` 11,460 件） | 合計 507 ms（同上） |
| ロック待ち・パーク（`JavaMonitorEnter` / `JavaMonitorWait` / `ThreadPark`） | **0 件** |
| GC の停止時間（`GCPhasePause`） | 合計 884 ms（フェーズ1 の約 7%） |

読み書きを合わせても 1 秒に満たず（しかもページキャッシュに載っている）、ロック待ちは 1 件も無い。
残りの 10 秒以上は JDT の構文解析と型解決、つまり<b>1 コアを回し続けている純粋な計算</b>で、
仮想スレッドが肩代わりできるものではない。

**GC 待ちは仮想スレッドでは避けられない。** G1 の停止は stop-the-world で、
キャリアスレッドごと止まる。仮想スレッドは「割り当ての量」を変えないので、GC の回数も減らない。

実測（JDT 3.46.0 / JDK 21 / 4 コア / 1000 ファイル・1 ファイルあたり import 30 本 / バッチ 100 件、
JDT の一括パースだけを取り出して比較。`-Xmx3g`）:

| 走らせ方 | 時間 | ヒープ最大 |
|---|---|---|
| 逐次（現状） | 9,978 ms | 697 MB |
| プラットフォームスレッド 2 | 7,457 ms | 1,067 MB |
| プラットフォームスレッド 4 | **7,094 ms** | 1,095 MB |
| プラットフォームスレッド 8 | 8,410 ms | 1,126 MB |
| 仮想スレッド（上限なし） | 7,154 ms | 1,175 MB |
| 仮想スレッド（同時 4 本に制限） | 7,600 ms | 871 MB |

読み取れること:

1. **並列にしても 4 コアで 1.4 倍にしかならない。** バッチごとに JDT が名前環境とソースフォルダの
   一覧を作り直すので（Q1）、並列度を上げるとその重複が増える。8 本では逆に遅くなる
2. **仮想スレッドはプラットフォームスレッドより速くならない。** 同じ同時実行数で比べると
   7,600 ms 対 7,094 ms で、仮想スレッドのほうが 7% 遅い。待ちが無いので、
   継続（continuation）の載せ替えの手間だけが残る
3. **メモリは「そこまで変わらない」どころではない。** 逐次 697 MB に対し、どの並列でも 1 GB 前後。
   同時に走るバッチの数だけ AST と名前環境がヒープに載るので、当然の結果

さらに悪いことに、**上限を付けない仮想スレッドは自然な流量制御を失う**。
ヒープを絞って同じ比較をすると:

| `-Xmx` | 逐次 | プラットフォーム 4 | 仮想スレッド（上限なし） |
|---|---|---|---|
| 1 GB | 9,905 ms / 408 MB | 7,174 ms / 567 MB | 7,510 ms / 751 MB |
| 768 MB | 9,828 ms / 346 MB | 7,525 ms / 733 MB | 7,277 ms / 721 MB |
| 512 MB | 9,767 ms / 267 MB | 7,417 ms / 512 MB | **OutOfMemoryError** |
| 384 MB | 10,192 ms / 247 MB | 8,050 ms / 376 MB（GC 1,239 ms） | **OutOfMemoryError** |

固定数のスレッドプールは「走れるのは N 本まで」という背圧がそのまま効くが、
`newVirtualThreadPerTaskExecutor` はタスクの数だけスレッドを作るので、
全バッチが同時にヒープを掴みにいく。抑えるにはセマフォ等で同時実行数を縛ることになり、
そうすると<b>結局スレッドプールと同じもの</b>になる（しかも 7% 遅い）。

**ピン留め（pinning）のせいではない。** JDK 21 で `-Djdk.tracePinnedThreads=full` を付けて
走らせたが、ピン留めは 1 件も起きなかった。`synchronized` の中でブロックしていないからで、
これは JEP 491（JDK 24 でピン留めを解消）を待っても変わらない。裏を返すと、
<b>そもそも「外せる待ち」が無い</b>ことの裏付けでもある。

### しきい値

- **仮想スレッドが効き始めるのは、タスクのブロック時間が 5 割を超えるあたりから。**
  今回は 12.2 秒中 1 秒未満（8% 未満）なので、待ちを完全に消してもアムダールの法則で
  1.09 倍が上限。実際の差は測定誤差に埋もれる
- **並列化そのもの（プラットフォームスレッド）が意味を持つのは、ヒープの余裕が
  逐次時の最大使用量の 2 倍以上あるとき。** 余裕が 1.5 倍を切ると GC の時間が増え始め
  （384 MB で GC 833 ms → 1,239 ms）、速さの取り分を食いつぶす
- **ファイル数が 400 件（= 並列度 4 × バッチ 100 件）を下回るとそもそも効かない。**
  バッチが 4 つ未満ではコアが埋まらない。実測でも 123 ファイルのプロジェクト
  （このツール自身の `src/`）では 2,442 ms → 2,241 ms で、JVM の起動時間に紛れる程度だった

**結論**: 仮想スレッドは採らない。並列化するならプラットフォームスレッドを 3〜4 本に固定し、
Q4 に挙げた 3 つの条件（拡張、メモリ、決定性）を満たしたうえで別途入れる。

## Q5. 型の名前を覚えておく表は、ヒープに残らないか

残らない。`BindingNames` は `FactVisitor` がファイル1件ごとに作るので、表の寿命も 1 ファイル分で、
`FileAnalysis` をキャッシュへ書いて捨てるときに一緒に捨てられる。バインディングを `IdentityHashMap` の
鍵にしているが、同じバッチの AST は元々まとめてヒープに載っているので、この表が AST の寿命を
延ばすことはない。

`equals` ではなくインスタンスの同一性で引くのは、`ITypeBinding.equals` が名前まで比べるため
（覚える目的に対して高くつく）。JDT は 1 回のパースの中で同じ型に同じインスタンスを返すので、
取りこぼしても「覚えていないので作り直す」だけで、答えは変わらない。

## Q6. 候補の推定を遅らせて、出力は変わらないか

変わらない。`externalGuessRef`（import 文から呼び出し先の型を推定する最後の手段）の結果は、
<b>バインディング解決に失敗した U 行にしか書かれない</b>。それなのに、これまでは
`MethodInvocation` を訪れるたびに先に求めていた。呼び出しの大半は解決できるので、
求めた結果はそのまま捨てられていたことになる。

`CallSiteRecorder.record` に「推定の元になる呼び出し式」を渡し、解決に失敗した枝に入ってから
1 回だけ求める形にした。副作用の無い純粋な計算なので、求めるのを遅らせても他に影響しない。

同じ単純名の単一型インポートが 2 つあるソース（コンパイルは通らない）では、
表を作るときに `putIfAbsent` を使って<b>先に書かれている方</b>を残す。import 文を先頭から
走査していたときと同じ答えになる。

## Q7. `clean` は3回の置換をやめてよいのか

よい。`clean` はタブ・改行を空白に落とす「行を壊さないための最後の関所」で、置換の回数は
振る舞いに関係しない。これまでは `replace('\t',' ')` `replace('\n',' ')` `replace('\r',' ')` と
3 回通していた（どれも中身を走査する）。1 回走査して、該当する文字が 1 つも無ければ元の文字列を
そのまま返す形にした。キャッシュの値の大半は該当しないので、ほとんどの列で走査が 1 回で済む。

`joinRow` は先に長さを見積もってから `StringBuilder` を作る。行は 10 列を超えることもあり、
継ぎ足しのたびに内部の配列を作り直すのが、そのままゴミになっていた。

`columnsOf`（キャッシュを読む側）も `String.split` をやめ、区切りの数を数えてから配列を 1 つだけ
作る形にした。差分更新の実行では、変わっていないファイルのぶんだけこの経路を通るので、
ここは「キャッシュを再利用するほど効く」箇所になる。
