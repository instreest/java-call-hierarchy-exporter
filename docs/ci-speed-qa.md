# CI（smoke.yml）の所要時間を縮める — 実装時の QA 一覧

Issue なし（依頼: 「PR 作成時の自動テスト・スモークテストに時間がかかるようになってきた。遅くなっている検査の
検知する目的や意図を損なわないまま、速度を改善してほしい」）。迷ったこと・困ったことと、その結論を Q&A の形で残す。

対応の要点:

- 遅いのは `regression` ジョブ（約 12 分）で、そのうち `test/incremental`（キャッシュの健全性）が約 8 分 40 秒を占めていた。
  ほかのジョブは 3 分以内に終わる（Q1）
- `test/incremental` は「1 ケース＝本体の起動 3 回（全件解析 → 書き換えて差分更新 → キャッシュを消して全件解析）」が
  100 件を超え、1 回が 1.5 秒ほどなので直列では縮まない。JVM の起動を速くする手（AppCDS・JIT の段階制限）は 1 割ほどしか
  効かなかった（Q2）。節（section）に分けて `--shard K/N` で選べるようにし、CI は 4 つのジョブに分けて並列に回す（Q3・Q4）
- `regression` ジョブの残りの検査は、lint でコンパイルしたクラス（`build/classes`）と解決した classpath を環境変数で渡し、
  検査ごとの本体の再コンパイル（1 回 5 秒 × 10 本）を省く。回帰テストは `jbang run` ではなく `java -cp` で動かす（Q5・Q6）
- 検査の中身（ケース・比較・期待値）は変えていない。変えたのは「どこで・どの順で動かすか」だけ

---

## Q1. どこが遅いのかをどう調べたか

GitHub Actions のジョブのステップごとの開始・終了時刻（Actions API の `jobs` の `steps`）を見た。直近の成功した実行では
`regression` ジョブが 12 分で、ワークフロー全体の壁時計時間を決めていた。ステップの内訳は
`test/incremental` が 8 分 39 秒、`test/regression` が 58 秒、`test/warnings` が 30 秒、`test/server` が 27 秒で、残りは
15 秒以下。ほかのジョブ（`regression-windows` 2 分 20 秒、`eclipse-plugin`・`vscode-plugin`・`pom`・`action`・`jbangw` は
1 分以内）は並列に走っているので全体の時間に効いていない。

つまり縮めるべきは `test/incremental` 1 本で、次に「同じジョブの中で 10 本の検査が本体をそれぞれコンパイルし直している」ぶん。

## Q2. JVM の起動を速くする手（AppCDS など）は使わなかったのか

試して、採らなかった。`test/incremental` の 1 ケースは本体の起動 3 回で、1 回は 21 ファイルの題材の全件解析で 1.5 秒ほど、
キャッシュを再利用する差分更新で 1 秒ほど。JDK 25 で手元（4 コア）で測った結果:

| 起動の仕方 | 全件解析（中央値） | 差分更新（中央値） |
|---|---|---|
| そのまま（クラスフォルダを classpath に） | 1.51 秒 | 1.06 秒 |
| jar にして AppCDS の書庫を使う（`-XX:SharedArchiveFile`） | 1.47 秒 | 0.95 秒 |
| 上に加えて JIT を C1 だけに（`-XX:TieredStopAtLevel=1`） | 1.36 秒 | 0.90 秒 |
| 上に加えて `-XX:+UseSerialGC` | 1.31 秒 | 0.90 秒 |

全部足しても 1 割強で、起動の時間ではなく JDT の解析そのものが大半を占めている。そのうえ AppCDS は classpath に
クラスフォルダがあると書庫を作れず（`Cannot have non-empty directory in paths`。本体を jar に固める手間が増える）、
書庫と classpath が食い違うと標準出力に `[error][cds]` の行を出すので、ログの文言を照合する検査に雑音が混ざる。
得るものに対して仕組みが重いので採らない。

## Q3. どう分けるか — ケース単位か、節単位か、ファイルを分けるか

**節単位にした。** `test/incremental/run.sh` は `# --- 見出し ---` の区切りで並んでいて、区切りの中のケースは前のケースの
結果を使うことがある（「定数の値が変わらない書き換えでは解析し直す件数が少ない」は直前の 2 ケースの件数を比べる、
`salvage_case` の 2 件目は 1 件目の件数と比べる、`shape_case` のあとに `SHAPE_BASE_PARSED` を見る、など）。
ケース単位に割ると、こうした「ケースのあとの検査」を一緒に動かす仕組みが別に要る。区切り単位なら、中はそのまま
1 本で回すときと同じ順で動く。

区切りを `if section "見出し"; then … fi` で囲み、`section` が現れる順に番号を振って `(番号 - 1) % N == K - 1` の節だけを
動かす（`--shard K/N`）。長い区切り（26 ケースの「別のファイルの変化が I 行に載らない依存」など）は、独立したケースの
境目で複数の節に割った。節は 50 ほどで、剰余で割ると 4 つのシャードの時間はおおむねそろう。

却下した案:

- **ファイルを分ける**（`cases-*.sh` を `run.sh` が読む）。節をまたいで使う関数の置き場所を決める必要があるのは同じで、
  差分が「移動」になってレビューしにくい
- **ケース単位の剰余**。上記のとおり「ケースのあとの検査」の扱いが別に要る
- **1 つのジョブの中で並列に回す**（`xargs -P`）。ケースはどれも同じ `work/`・`.cache`・`out` を使うので、ケースごとに
  作業フォルダを分ける書き換えが全ケースに及ぶ。また 1 回の解析が 1.5〜2 コアを使うので 4 コアのランナーでは 2 倍ほどしか
  縮まない。ジョブを分けるほうが素直に N 倍になる

## Q4. 節の囲みで気をつけること

- **節をまたいで使う関数と変数は囲みの外に置く。** 囲みの中で定義した関数は、その節を飛ばしたシャードでは未定義になる
  （`jfile`・`jsrc`・`lib_jar`・`integrity_run`・`same_all`・`shape_javac`・`bc_setup_abort` など）。ケース専用の
  `setup_*` / `edit_*` は囲みの中でよい。どの関数がどこで使われているかは、定義行と使用行を機械的に拾って確かめた
- **「ケースのあとの検査」は同じ節に入れる。** 直前のケースが置いた変数（`INC_PARSED`・`OUT`・`IOUT`・`SHAPE_BASE_PARSED`）
  を見る `if` は、そのケースと同じ囲みの中に置く
- **節の番号はシャードによらず同じになること。** 全シャードが同じスクリプトを頭から読み、`section` を同じ順に呼ぶので
  番号はそろう。環境で動かすかどうかが変わる節（シンボリックリンクを作れない環境・`jmod` が無い環境）も `section` の
  呼び出し自体は環境によらず行う（中で飛ばす）
- **どの節をどのシャードで動かしたかを印字する**（`-- 節 n: 見出し`。飛ばした節は「シャード K/N では飛ばす」）。
  全シャードのログを合わせれば全部の節が 1 回ずつ動いたことを追える。最後に「節 X 個のうち Y 個を動かした」も出す
- `--shard` を付けなければ全部の節を動かす（手元では今までどおり 1 本で回せる）

分割の確かめ方: 手元で `--shard 1/4` 〜 `4/4` を順に回し、出力の `== … ==` の見出しの和集合が `--shard` なしの
出力の見出しと一致すること（重複も漏れも無いこと）を見た。

## Q5. ほかの検査の再コンパイルを省くのは「検査を弱める」ことにならないか

ならない。各 `run.sh` が単体で動くときに本体をコンパイルするのは「その検査だけを手元で回せるようにする」ための
用意であって、検査の内容ではない。CI では lint のステップが同じ引数（`--release 17 -Xlint:all -Werror -Xdoclint:all,-missing`）
でコンパイルし、警告ゼロであることを見ている。できる class は同じなので、それを渡して使う。

渡し方は検査ごとの既存の決まりに従う（`JCHE_CP` が「JDT の jar だけ」か「本体のクラスも含む」かが検査で違う。
各 `run.sh` の冒頭の使い方の行に書いてある）。`test/conditions`・`test/dataflow`・`test/nls` には渡す口が無かったので、
ほかと同じ名前（`JCHE_CP` / `JCHE_CLASSES` / `JCHE_JAVA` / `JCHE_JAVAC` / `JCHE_JAVA_HOME`）で足した。
`test/dataflow` は検査プログラムが本体と同じパッケージ（`jche.graph`）に入っているが、クラスフォルダを分けても
同じパッケージとしてコンパイル・実行できる（どちらも無名モジュール）。

## Q6. 回帰テスト（test/regression）を `jbang run` ではなく `java -cp` で動かすと、jbang の経路を見なくなるのではないか

Linux の回帰テストは 26 回本体を起動し、`jbang run` は毎回 jbang 自身の JVM を立ててスクリプトの指紋を照合するので
1 回 1 秒余りが重なっていた。`JCHE_CMD`（`run.sh` が元から持つ差し替えの口）でコンパイル済みのクラスを `java -cp` で
動かす。

jbang の経路（`//DEPS`・`//JAVA`・`//SOURCES` の指示行、`*.java **/*.java` の併記）は引き続き次が通す:

- `test/cli/run.sh`（`regression` ジョブ）… 起動コマンド `java-call-hierarchy-exporter.sh` → `jbang run src/jche/Jche.java`
- `action` ジョブ … `.github/action/run.sh` → `jbang run src/jche/CallHierarchyExporter.java`
- `regression-windows` ジョブ … `test\regression\run.cmd` → `jbangw\jbang.cmd run`

ツールのプロジェクトフォルダの特定（`jche.config.ToolRoot`。`whole` ケースがキャッシュの場所 `.cache/demo_*` を見る）は
作業ディレクトリから上へ目印を探すので、`java -cp` でも `jbang run` でも同じ場所になる。

## Q7. incremental のジョブでもコンパイルするが、lint を 2 回数えることにならないか

`incremental` の各シャードも同じ引数でコンパイルする（本体のクラスが要るため。6 秒）。結果は同じなので、
lint として数えるのは `regression` ジョブの「Compile with all lint warnings as errors」のままとし、
`incremental` 側のステップ名は「Compile（regression ジョブの lint と同じ引数）」にして役割を分けた。

`incremental` のジョブは `~/.jbang`・`~/.m2` のキャッシュを **読むだけ**（`actions/cache/restore`）にした。
`actions/cache` は同じキーに最初に終わったジョブしか保存できない。`regression` ジョブは `test/jls` のために
JDK 26 も `~/.jbang/cache/jdks` に取得するので、それより先に終わりがちな `incremental` のシャードが保存すると、
JDK 26 の入っていないキャッシュがそのキーに残り、以後の実行で `regression` が毎回 JDK 26 を取得し直す
（キーが変わるまで直らない）。保存は今までどおり `regression` ジョブに任せる。

## Q8. 何分になる見込みか

`regression` ジョブは約 12 分 → 3 分前後（incremental を外し、再コンパイルと jbang の起動を省く）。`incremental` の
各シャードは約 8 分 40 秒 ÷ 4 ＋ 用意（checkout・JDK・コンパイルで 30 秒ほど）で 2 分半〜3 分。並列に走る
`regression-windows`（2 分 20 秒）と並ぶので、ワークフロー全体は約 12 分 → 3 分前後になる見込み。ジョブの数は増える
（`incremental` が 4 つ）が、ランナーの合計時間はほぼ変わらない（分けたぶんの用意が 4 × 30 秒増え、再コンパイルと
jbang の起動が 1 分半ほど減る）。
