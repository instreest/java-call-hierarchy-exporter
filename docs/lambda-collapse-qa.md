# ラムダの合成メソッドを CSV に出さない — Q&A

[lambda-expansion-qa.md](lambda-expansion-qa.md)（Issue [#127](https://github.com/instreest/java-call-hierarchy-exporter/issues/127)）で、
ラムダの本体を合成メソッド `lambda$…` にして階層に出すようにした。その出し方を改めた判断を残す。
きっかけは「`forEach` や `stream()` の中で呼ぶ自分のメソッドを、コールバックを意識せずに『そのメソッドから呼んでいるメソッド』として読めないか」
という問い。このツールはソースを元にした静的解析なので、**ビルドでコンパイラが作る暗黙のメソッドは、健全性に影響しない限り CSV に出さない**。

## 結論

- `call-hierarchy.csv` に `lambda$…` の行・列を出さない。設定項目にはせず、常にこの出し方にする（Q2）。
  本体の中の呼び出しは、そのラムダを実行するメソッドの直下に出る。`depth` 列は `call-hierarchy` 列のノード数のまま
- 内部では合成メソッドと生成の辺を持ち続ける（辿る範囲・解決は変わらない。lambda-expansion-qa の Q1・Q2・Q10）
- 作った辺・契約の呼び戻し・`DATAFLOW_LAMBDA` が同じ本体に降りるときは、1 本の枝にまとめる（Q4）
- 全体でない起点の選び方（`entry.packages`）でも、ラムダの本体は起点にしない（Q5）
- 条件で打ち切る呼び出し（`[UNREACHABLE]`）と候補を並べるだけの行は、事実を残すため合成メソッドの行のまま出す（Q3）
- キャッシュに入る事実は変わらない（読み手の変更だけ）ので `CacheFormat.VERSION` は上げない。
  回帰テストの期待値（`call-hierarchy.csv`）から `lambda$…` の行を除いた

### Q1. Eclipse の呼び出し階層はどう取るのか。なぜそのまま取り込まないのか

Eclipse は「メソッド本体の範囲に書いてある呼び出しは、そのメソッドの呼び出し」とだけ見る。`list.forEach(x -> foo(x))` の `foo` は
そのまま囲みメソッドの呼び出し先に並ぶ。一方で、本体が字面の外にあるもの（`new Thread(new Job()).start()` の `Job.run`、
`orders.forEach(new OrderPrinter())` の `accept`、変数で運んだラムダ）は繋がらない。

このツールの生成の辺は同じ考え方で、契約表と値の追跡は「字面の外にある本体」を足すためのもの。外すと影響調査で漏れる
（AGENTS.md の「呼び出しを静かに落とさない」）ので仕組みは置き換えず、**CSV に出す形**だけを Eclipse に寄せた。

### Q2. 段を畳むとは何をするのか。なぜ設定にしないのか

`StreamingTreeWalker` が、ラムダの本体へ降りるところで、段（`path[]`）に本体を積まず、今の段を本体の段に差し替えて辺を辿る
（`collapseInto`。除外パッケージの読み飛ばし `skipThrough` と同じ作りで、隠すのが合成メソッドの側）。

- 辺は合成メソッドから引くので `PathFrame#methodId` は合成メソッドのまま。CSV の caller 列・call-hierarchy 列に出すのは
  `PathFrame#shownId`（畳んだ段では今の段のメソッド）
- 引数の環境と捕捉した値（`E:`）は本体の段のものを使うので、`DATAFLOW_PARAM` などの絞り込みは減らない。
  捕捉した値は、今の段がそのラムダを作ったメソッドのときだけ渡す（lambda-expansion-qa の Q10）
- 囲みメソッドは `path[]` から見えなくなるので `hiddenAncestors` に積む。ラムダの中から囲みメソッドへ戻る再帰は
  `[UNEXPANDED:CYCLE]` で止まる
- 入れ子のラムダも同じ。畳んだ段の中で作ったラムダは、さらに畳まれる

設定にしないのは、合成メソッドが CSV に出る形は「ソースに無いメソッド名が出る」ことで、読み手を迷わせるだけだから。
出力の形が設定で 2 通りあると、期待値・フィルタ・他のツールへの受け渡しも 2 通りになる。

失うもの: `RESOLVED:DATAFLOW_LAMBDA` や、契約の呼び戻しを示す行（`RESOLVED:CALLBACK`。ラムダが渡る形）が出ない。
ラムダを渡す呼び出し自体（`executor.submit(...)` の行）は残る。メソッド参照の呼び戻しは、参照先が実在するメソッドなので今までどおり出る。

別のメソッドが実行するラムダ（`runIt(Runnable r)` の `r.run()`）は、実行するメソッドの直下に本体の呼び出しが出る。
その行の caller 列の行番号はラムダを書いた場所を指す（実行するメソッドの範囲外のことがある）。それでも、
実際に実行時に流れる経路を落とさないことを優先した。

### Q3. 畳めない形は

- 条件分岐で打ち切る呼び出し: 「この経路では呼ばれない」ことを理由付きで 1 行残すので、行のまま出す
- 候補を並べるだけの行（`isMultiple`）: 降りない行なので畳む対象にならない

この 2 つでだけ、合成メソッドの名前が callee 列に出うる（まれ）。

### Q4. 同じ本体に降りる辺をどうまとめるのか

`executor.submit(() -> dao.findById(1))` は、生成の辺と、契約の呼び戻しの辺の両方が同じ本体へ降りて、同じ部分木が 2 回出ていた。
畳むと両方が同じ段の直下に出るので、**同じ環境（引数・捕捉した値）で降りるものは 1 回だけ降りる**（`CollapseSeen#firstTime`）。
環境が違っても行の文字列が同じになる（引数の値を使わない本体）ことが多いので、2 本以上の辺から降りる本体だけ、
降りている間に書いた行の文字列を覚えて、同じ行を 1 度しか書かない。文字列まで同じ行は読み手に区別できないので情報は減らない。
1 回しか降りない本体は覚えない（メモリを使わない）。

却下した案:

- **環境を無視して本体を 1 回だけ降りる**: 実行箇所の引数で絞った結果と CHA のどちらを採るかを決めることになり、落とす側の誤りが出うる
- **ラムダを作った行と実行した行が同じときだけ辺をまとめる（畳まない出し方のまま）**: 合成メソッドの行が残り、問いの目的に合わない

### Q5. 起点として選ばないのはなぜか

`entry.packages` を書いたとき、パターンに当たるソース上のメソッドが起点になるが、ラムダの本体は暗黙のメソッドで、
作ったメソッドから生成の辺で必ず届く。起点にすると root 列に `Main.lambda$lambdas$0` のような名前が出る。
作ったメソッドが同じ型にあるので、型・パッケージのパターンならそちらが起点になり、本体の呼び出しは落ちない。
全体モード（`entry.packages` 空欄）では、ラムダは生成の辺で呼ばれているので元から起点にならない。

### 補足

- 匿名クラスのメソッド（`Outer$1`）は、ソースに書いた型のメソッドなので今までどおり出す
- Eclipse プラグインと VSCode プラグインの木（`--server` の `TREE`）は別の作りで、まだこの出し方になっていない
- 実装: `StreamingTreeWalker`（`collapseInto` / `lambdaEntries` / `CollapseSeen`）、`PathFrame#shownId`、
  `CallHierarchyCsvWriter#formatRow`、`EntryPoints#select`。検査は `bash test/regression/run.sh`（期待値に `lambda$` が無いこと）
