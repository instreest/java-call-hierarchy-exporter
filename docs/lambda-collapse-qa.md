# ラムダの段を畳む設定と、同じ行から同じ本体へ降りる辺のまとめ — Q&A

[lambda-expansion-qa.md](lambda-expansion-qa.md)（Issue [#127](https://github.com/instreest/java-call-hierarchy-exporter/issues/127)）で、
ラムダの本体を合成メソッド `lambda$…` にして階層に出すようにした。その出し方への 2 つの手当てを残す。
きっかけは「`forEach` や `stream()` の中で呼ぶ自分のメソッドを、コールバックを意識せずに『そのメソッドから呼んでいるメソッド』として読めないか」
という問い。Eclipse の呼び出し階層（字面の包含で決める）に見え方を寄せる。

## 結論

- **`hierarchy.collapse.lambda=true`**（既定 false）で、ラムダの合成メソッドの段を出さず、本体の中の呼び出しを
  ラムダを書いたメソッドの直下に出す。辿る範囲・解決は変わらず、出し方だけが変わる（Q1・Q2）
- **畳む相手は「ラムダを作ったメソッドが実行する」場合だけ**。別のメソッドが実行するラムダ（`runIt(Runnable r)` の `r.run()`）は
  段のまま出す（Q3）
- **同じ行から同じ本体へ降りる辺は 1 本にまとめる**。畳まない既定でも同じ（Q4）
- 畳んだあとに同じ行が 2 度出ないよう、2 本以上の辺から降りる本体は、書いた行を覚えて 1 度しか書かない（Q5）
- キャッシュに入る事実は変わらない（読み手の変更だけ）ので `CacheFormat.VERSION` は上げない。
  `call-hierarchy.csv` の行が変わるので、回帰テストの期待値（`whole`・`cacheblocks`）を直し、`collapse` のケースを足した

### Q1. Eclipse の呼び出し階層はどう取るのか。なぜそのまま取り込まないのか

Eclipse は「メソッド本体の範囲に書いてある呼び出しは、そのメソッドの呼び出し」とだけ見る。`list.forEach(x -> foo(x))` の `foo` は
そのまま囲みメソッドの呼び出し先に並ぶ。一方で、本体が字面の外にあるもの（`new Thread(new Job()).start()` の `Job.run`、
`orders.forEach(new OrderPrinter())` の `accept`、変数で運んだラムダ）は繋がらない。

このツールにはその見方がすでにある（生成の辺。lambda-expansion-qa の Q2）。契約表と値の追跡は、その上に
「字面の外にある本体」を足すためのもので、外すと影響調査で漏れる（AGENTS.md の「呼び出しを静かに落とさない」）。
だから仕組みは置き換えず、**見え方だけ**を選べるようにした。

### Q2. 段を畳むとは、何をどう変えるのか

`StreamingTreeWalker` が、ラムダの本体 `lambda$…` へ降りるところで、段（`path[]`）に本体を積まず、今の段を本体の段に
差し替えて辺を辿る。除外パッケージの読み飛ばし（`skipThrough`）と同じ作りだが、隠すのが合成メソッドの側で、
囲みメソッドが表示に残る。

- 辺は合成メソッドから引くので、`PathFrame#methodId` は合成メソッドのまま。CSV の caller 列・call-hierarchy 列に出すのは
  `PathFrame#shownId`（畳んだ段では囲みメソッド）にした
- 引数の環境と捕捉した値（`E:`）は本体の段のものを使う（Q10 と同じ）ので、`DATAFLOW_PARAM` などの絞り込みは減らない
- 囲みメソッドは `path[]` から見えなくなるので `hiddenAncestors` に積む。ラムダの中から囲みメソッドへ戻る再帰は
  `[UNEXPANDED:CYCLE]` で止まる（検証済み）
- `depth` 列は `call-hierarchy` 列のノード数のまま（隠したノードは列にも数にも入らない）
- 条件分岐で打ち切る呼び出し（`[UNREACHABLE]`）と、候補を並べるだけの行は畳まない。畳むと「打ち切った」事実や候補の行が消える

失うもの: 畳んだ本体の行には `RESOLVED:DATAFLOW_LAMBDA` や `RESOLVED:CALLBACK` の行が出ない（ラムダのノードが無いため）。
どう繋がったかを見たいときは既定（false）で読む。

### Q3. 別のメソッドが実行するラムダも畳まないのはなぜか

`other(() -> h.work())` の `other` の中の `r.run()` から本体へ降りる形は、行番号が `other` の中ではなく書いた側のファイルの別の場所を指す。
本体の呼び出しを `other` の直下として出すと caller 列の `at Rec.other(Rec.java:25)` が `other` の範囲外の行を指し、スタックトレースとして
嘘になる。誰が実行したかという Eclipse には無い情報でもあるので、**作ったメソッドの中で実行する場合だけ畳む**
（`CallGraph#createsLambda`。Q10 の判定と同じ）。作ったメソッドの下では本体が畳まれて 1 回出るので、本体の呼び出しは落ちない。

### Q4. 同じ行から同じ本体へ降りる辺を 1 本にまとめた理由と範囲

`executor.submit(() -> dao.findById(1))` は、契約の呼び戻し（`RESOLVED:CALLBACK`）と生成の辺（`STATIC_BOUND:PRIVATE`）の
両方が同じ行から同じ本体へ降りて、同じ部分木が 2 回出ていた。**行・呼び出し元・呼び出し先が同じ**なので、読み手には重複でしかない。

- まとめる範囲は「同じ行」に限る。`Supplier<Object> s = () -> …;`（28 行）と `s.get();`（29 行）は、作った行と実行した行が違う
  別の呼び出し箇所なので、2 本のまま残す（Q2 のとおり別の経路）
- 残すのは、実行する側の辺（契約の呼び戻し・`DATAFLOW_LAMBDA`）。**なぜ動くか**（`resolved-by`・契約の注記）が分かる側だから
- 実行する側が 1 件に決まり、降りられるときだけ作った辺を省く。候補を並べるだけの行（`isMultiple`）や、条件で打ち切る行に
  任せると、本体の階層が消えてしまう
- 契約の呼び戻しの行は、ラムダを作ったメソッドの中なら捕捉した引数も渡すようにした。作った辺と同じ値で降りるので、
  まとめても本体の中の絞り込みが減らない
- 契約表に当たらない形（`unknown(() -> …)`）は、作った辺が唯一の行き先なので省かない（落とさない）

### Q5. 畳んだあとの重複を、どう除くのか。却下した案

畳むと、作った辺と、同じメソッドの中の実行箇所（`f.apply(9L)` など）が、同じ本体を別の環境で降りることがある。
環境（引数・捕捉した値）が違えば解決が変わりうるので、環境が同じときだけ降り直さない（`CollapseSeen#firstTime`）。
環境が違っても行の文字列が同じになる（引数の値を使わない本体）ことが多く、そのまま出すと同じ行が並ぶ。

そこで、**2 本以上の辺から降りる本体だけ**、降りている間に書いた行の文字列を覚えて、同じ行を 1 度しか書かない。
文字列まで同じ行は読み手に区別できないので、情報は減らない。1 回しか降りない本体は覚えない（メモリを使わない）。

却下した案:

- **経路の環境を無視して本体を 1 回だけ降りる**: 実行箇所の引数で絞った結果と、絞れなかった結果（CHA）の
  どちらを採るかを決めることになり、落とす側の誤りが出うる
- **畳む設定で作った辺と実行する辺を、本体ごと常に 1 回にする**: 同上
- **畳むのを既定にする**: `depth` 列の意味と既存の期待値・利用者の絞り込みが変わる。既定は変えず、設定で選ぶ
- **別のメソッドが実行するラムダも畳む**: Q3 のとおり行番号が合わなくなる

### 補足

- Eclipse プラグインと VSCode プラグインの木（`--server` の `TREE`）は別の作りで、この設定はまだ効かない
- 実装: `StreamingTreeWalker`（`lambdaEntries` / `mergedGenerations` / `collapseInto` / `CollapseSeen`）、`PathFrame#shownId`、
  `CallHierarchyCsvWriter#formatRow`、`Config#collapseLambda`。検査は `bash test/regression/run.sh` の `collapse` ケース（畳んだ出力）と
  `whole`・`cacheblocks`（同じ行の重複が 1 本になった期待値）
