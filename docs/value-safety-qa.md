# 値の読み違いで呼び出しを黙って落とさない — 実装時の QA 一覧

Issue なし（キャッシュを 1 ファイルにまとめる作業の途中で、書き手が作る値を見直して見つかったもの）。

条件分岐の打ち切り（`[UNREACHABLE]`）と具象クラスの絞り込み（`LOCAL_NEW`・`DATAFLOW_*`）は、
書き手（`jche.analysis`）がキャッシュに書いた値を読み手が当てはめて決める。値を 1 つ読み違えると、
読み手は「この経路では呼ばれない」「この実装だけ」と言い切り、実際に動く呼び出しがその先の階層ごと
出力から消える。エラーにも警告にもならない。見つけた書き手側の読み違いを直した。

対応の要点:

- **値を変えうるキャスト**: 値として使う経路（出所・値グラフ・条件）すべてで、剥がすのは値を変えない
  キャストだけにした（`OriginTracker.unwrapValue` / `preservesValue`。条件の判定で使っていたものを広げた）。
  値を変えうるキャストの式は、コンパイル時定数なら JDT が畳んだ値（`(byte)300` は `44`）、そうでなければ「分からない」
- **浮動小数**: 値グラフに浮動小数の定数を持たない。条件も、比べる片方が浮動小数なら判定しない
- **ローカル変数の書き換え**: 複合代入（`+=`）と `++` / `--` を書き換えとして数える。`catch` の引数・
  拡張 for の変数・パターンの変数は宣言の時点で「分からない」。出所の文字列が「分からない」になった変数は、
  値グラフのノードも必ず無しにする
- **匿名・ローカルクラスのフィールド初期化子（J 行）**: 囲むメソッドの枠から切り離して読む
- **new の証拠（X 行）**: 代入が**すべて** new のローカル変数にだけ残す（引数・フィールド・拡張 for の変数には残さない）
- **値グラフの大きさ**: 同じ式は 1 つのノードにする（式ごとの控えと、式の木の中での深さで打ち切る上限）
- **数値リテラル**: 値を表記から読まず、JDT が評価した値を使う（16 進・8 進の `int` は最上位ビットが立つと負）。
  条件の期待値と呼び出し元の値が同じところから来る
- **ローカル変数の先読み**: 表が変わらなくなるまで本体を読み直す。ループの中で後ろにある代入が、
  前の行で写した変数（`int copy = n;`・`Dao y = x;`）やファクトリの実引数に届く
- **`equals` の型**: 比べる相手の静的な型と定数の型が揃うとき（`String` どうし・同じ列挙型・
  ボックス型と箱詰めされる定数）だけ条件にする
- キャッシュの版を `jche-cache-v32` に上げた（書き手が作る事実が変わったため）
- **返す具象型の決まらない @Bean メソッド**（あとから足した。Q17）: その Bean を宣言した戻り値の型とその部分型の
  どれかとして数え、候補の型が触れる呼び出しを DI（段 5）で 1 つに絞らない。値を読まない指定でも効く
- 検査は `test/pruning/run.sh`（使い捨てのプロジェクトをその場で作る）。直した書き方ごとに「落とさない」ことと、
  仕組みごとに「打ち切られる・絞られる」対照を見る。`test/regression` の期待出力は変わっていない
- あとから足したもの（PR #167 の見直し（52453ae に対する 3 回目のレビュー。`docs/cache-unification-qa.md` の冒頭）で
  見つかった、以前からある穴。Q18〜Q24。キャッシュの版を `jche-cache-v35` に上げた）:
  - **フィールドへの書き込みの取りこぼし**（Q18）: 入れ子のクラス・外側のクラスからの書き込み、`++`・複合代入、
    初期化ブロック・初期化子のラムダ、条件の中や `return` の後ろのコンストラクタの書き込み、書き換えた引数を入れる代入
  - **別のインスタンスへのコンストラクタ実引数**（Q19）: `other.dao` を値にしない。レシーバの値が無いだけの呼び出しを this とみなさない
  - **拡張 for の要素**（Q20）: 要素を詰めた値だけと言い切れるローカルのコレクションに限る
  - **型名で書いたメソッド参照の引数の位置**（Q21）と **リフレクションの invoke の引き先**（Q22）
  - **DI の段 5 を注入点だけに**（Q23。`docs/spring-di-qa.md` の Q5・Q6 を書き直した）
- あとから足したもの（4 回目のレビュー（f491e2e に対するもの。`docs/cache-unification-qa.md` の「4 回目のレビューの修正」）で
  見つかった。Q26・Q27。キャッシュの版を `jche-cache-v39` に上げた）:
  - **`super.f` への書き込み**（Q26）: `super.dao = …`・`Outer.super.dao = …` もフィールドへの書き込みとして J 行に載せる
  - **フレームワークが書くフィールド**（Q27）: 注釈の付いたフィールドと、DI のステレオタイプ以外の注釈の付いた型のフィールドは
    値を 1 つに決めない（`@Autowired(required = false)` の既定など）。DI の段 5 も、ソースが引数でない値を入れるフィールドを
    注入点にしない（`docs/spring-di-qa.md` の Q15）

## Q2. キャストは、どこまで剥がしてよいのか

**値を変えないと言い切れるものだけ**（`OriginTracker.preservesValue`）。

| キャスト | 剥がすか | 根拠 |
|---|---|---|
| 参照型どうし（`(Dao) x`・`(Object) s`） | 剥がす | JLS 5.1.5 / 5.1.6。同じインスタンスを指す |
| 同じプリミティブ型 | 剥がす | JLS 5.1.1 |
| 値を保つ拡大（`byte`→`int`、`int`→`long`、`int`→`double`、`char`→`int` など） | 剥がす | JLS 5.1.2 |
| 精度を失いうる拡大（`int`・`long`→`float`、`long`→`double`） | 剥がさない | JLS 5.1.2 |
| 縮小（`(byte) p`）・拡大と縮小（`byte`→`char`） | 剥がさない | JLS 5.1.3 / 5.1.4 |
| ボックス化・非ボックス化 | 剥がさない | 従来どおり（`docs/jls-conformance-qa.md` の Q12） |
| 型が取れない | 剥がさない | 分からないものは畳まない |

`docs/jls-conformance-qa.md` の Q12 では「値の一致を判定する（ガード・定数）」だけがこの規則で、
「どのメソッドが動くかを追う（`originOf`）」は全部剥がしていた。ところが `originOf` の結果は
R 行・J 行・ローカル変数の表にも入り、読み手はそれを条件の判定に使う（引数 `A:0` に呼び出し元の値を当てる）。
値グラフ（呼び出し箇所の実引数）も同じである。1 か所でも剥がしすぎると同じ誤判定になるので、
値として使う経路は全部 `unwrapValue` を通すことにした。すべて剥がす `unwrap` が残るのは、
参照型の変数・レシーバがどのインスタンスを指すかだけを見る場面（代入先の変数・コレクションの変数・
`Class.forName(...)` の連鎖）で、そこに現れるキャストは値を変えない。

拡大を「剥がす」側に入れたので、条件の側で `(long) mode == 44` のように書いた条件も判定できるようになった
（従来は「プリミティブが絡めば変えうる」として判定しなかった）。値が保たれるので、打ち切りの誤りにはならない。

## Q3. 値を変えるキャストの式の値は、捨てるのか

コンパイル時定数なら使う。`(byte) 300` は JLS 15.29 のコンパイル時定数で、JDT は型変換まで済ませた `44` を
`resolveConstantExpressionValue()` で返す。値グラフはキャストを剥がす**前の元の式**で定数を求めるので、
`run((byte) 300)` の実引数は `44`、`run((byte) 301)` は `45` になる（`test/pruning` の対照）。
定数でなければ（`(byte) p`）「分からない」。

## Q4. 浮動小数はなぜ条件の側でも判定しないのか

値グラフに浮動小数の定数を持たないだけでは足りないからである。条件は値の**表記**を文字列の一致で比べる。
整数の実引数は `float` / `double` の引数へ暗黙に拡大され（JLS 5.3）、その拡大は精度を失いうる（JLS 5.1.2）。

```java
static void f(float x) { if (x == 16777216) hit(); }
f(16777217);   // x は 16777216f。条件は真
```

表記の比較では `16777217` と `16777216` は違う値なので偽と判定し、`hit` を落とす。
浮動小数の値の比較を正しく畳むには型ごとの丸めを真似る必要があり、得るもの（浮動小数の条件で打ち切れること）に
見合わない。`GuardCollector.comparableByValue` で、比べる片方が `float` / `double` なら条件を作らない。

## Q5. `n++` と `n += 1` は、なぜ見落とされていたのか

ローカル変数の表（`OriginTracker.scanOrigins`）は、代入の**右辺**を出所として足していた。
`n++` は代入（`Assignment`）ではなく `PostfixExpression` なので素通りし、`n` は宣言の `0` のまま。
`m += 1` は右辺 `1` が宣言の `1` と同じなので「同じ出所」と判定され、`m` は `1` のまま残った。
`int n = 0; … n++; if (n != 0)` は数を数える典型的な書き方で、`n != 0` の先をすべて落としていた。

複合代入・`++`・`--` は、どれも元の値から新しい値を作るので、出所の表では U（不明）にする。

## Q6. 引数に new を代入すると、なぜ値グラフまで new だけに見えたのか

変数の表は、同じ変数について出所の文字列とノードの 2 つを持つ。引数は文字列の表にだけ `A:0` が
最初から入っていて、ノードの表には何も無い（`paramScopeOf`。引数は葉なので作り直せるため）。
`d = new DaoA()` を足すと、文字列の表は `A:0` と `T:DaoA` が食い違って U になるが、ノードの表は
「前が無い」ので `new DaoA()` のノードがそのまま唯一の値になっていた。読み手は X 行（`LOCAL_NEW`）が
無くても、このノードから `DATAFLOW_NEW` で `DaoA` に絞る。

文字列が U になったら、ノードも必ず無しにした（`mergeOrigin`）。拡張 for の変数・`catch` の引数・
パターンの変数は、そもそも宣言が表に載っていなかった（代入 1 つが唯一の出所に見える）ので、
宣言の時点で U を入れる。要素の出所が分かった拡張 for の変数（`bindLoopVariable`）はそのまま使う。

## Q7. new の証拠（X 行）は、どの変数に残すのか

（その後、形式 v33 で X 行を無くし、証拠は書き手がファイルの中で結びつけて C 行・U 行の hints 列に持つようにした。
どの変数に残すかはここに書いたとおり。`docs/cache-unification-qa.md` の Q5）

**宣言文で宣言したローカル変数**（for 文の初期化部・try の資源を含む）のうち、初期化子とメソッドの中の
代入が**すべて** `new`（値を変えないキャストを挟んだものを含む）のものだけ。1 種類なら `LOCAL_NEW`、
複数なら `LOCAL_NEW_MULTI`（候補集合）になるのは従来どおり。

| 変数 | 残さない理由 |
|---|---|
| 引数・ラムダの引数 | 宣言そのものが呼び出し元から値を受け取る |
| フィールド | 別のメソッドからも代入される。遅延初期化（`if (dao == null) dao = new …`）の先に、ほかで入れた実装が来る |
| 拡張 for の変数・`catch` の引数・パターンの変数 | 宣言が要素・例外・照合した値を受け取る |
| `new` 以外の代入（複合代入・`++` を含む）が 1 つでもあるローカル変数 | 入ってくる値が `new` だけではない |

全部の代入を見終えるまで判断できないので、ファイルを読み終えたところ（`FactVisitor.endVisit(CompilationUnit)`）で
書く。同じ変数に同じ型の `new` が何度あっても 1 行にした（読み手は重複を捨てていた）。

`test/pruning` では、`new` した型と、それ以外（呼び出し元の実引数・コレクションの要素・ほかのメソッドが入れたフィールド）から
入る型が**同じ経路で**起こりうるように書き（`if (reset) d = new DaoA();` の `reset` は解析では決まらない）、
**両方**が出ることを見る。片方だけを見ると、もう片方を落とす誤り（引数の出所を残して `new` を捨てる、など）を見逃す。
キャストを挟んだ `new` は `LOCAL_NEW_MULTI`（2 種類）と `LOCAL_NEW`（1 種類。`Dao d = (Dao) new DaoA();`）の
resolved-by そのものを見る（CHA に戻っても候補は同じなので、候補が出ることだけでは区別できない）。

## Q8. 匿名クラスのフィールド初期化子は、なぜ囲むメソッドの引数を拾っていたのか

J 行（フィールドへの代入）は、型の宣言に入った時点（`FactVisitor.enterType` → `FieldFactCollector.collect`）で集める。
匿名クラス・ローカルクラスの宣言は囲むメソッドの中で訪ねられるので、その時点のスコープの一番上は
**囲むメソッドの表**である。`private final Dao inner = outer;` の `outer`（囲むメソッドの第 1 引数）は
「今のフレームの `A:0`」として返り、読み手（`jche.graph.FieldFacts`）はそれを
**この匿名クラスのコンストラクタの第 1 引数**と読んだ。`new Task(new DaoA()) { … }` の第 1 引数は `DaoA` なので、
`inner.find()` を `DaoA` に絞っていた。

`collect` の間は空の枠を 1 枚挟む。外側の変数は「捕捉した変数」として扱われ、メソッド本体の代入と同じ規則
（`OriginTracker.frameIndependent`）で `A:` / `F:` は捨て、`T:` / `M:` は頭だけを残す。
捕捉したローカル変数が `new DaoB()` なら、匿名クラスのフィールドも `DaoB` に絞れる（`test/pruning` の対照 `Capt`）。

## Q9. 値グラフが 1 ファイルで 1 万行を超えていたのはなぜか

`ValueGraph.HARD_CAP`（256）を、**辿り始めた位置からの深さ**で判定していたため。
300 段の連鎖 `new StringBuilder().append("…").append("…")…` では、呼び出し箇所ごとに違う段で打ち切られ、
同じ部分式が打ち切り位置の数だけ別のノードになる（ノードは構造で同一視するので、打ち切り位置が違えば別物）。
再現用の 300 段の連鎖 1 ファイルで N 行が **12,079 行**、キャッシュが 881 KB あった。

2 つ変えた。

- 式（AST のノード）ごとに作ったノードを控え、同じ式を呼び出し箇所ごとに辿り直さない
- 上限を**式の木の中での深さ**（`depthInTree`。辿る辺＝レシーバ・実引数・束縛したレシーバだけを数える）で判定する。
  同じ式はどこから辿っても同じ段で打ち切られ、打ち切ったノードも 1 つになる

同じファイルで N 行は **513 行**（メソッド呼び出し 257・文字列 255・フィールド 1）、キャッシュは 47 KB になった。
上限より深い式は「分からない」（`NONE`）のままで、呼び出しを落とさない側に倒れる。深さ 256 を超える連鎖の
末端の呼び出し箇所は、以前は（辿り始めが浅いので）値を持てていたが、今は持たない。実在のコードでは
起きない深さで、値が無ければ読み手は CHA に戻るだけである。

## Q10. 式ごとの控えは、いつ捨てるのか

スコープが変わるたび（`OriginTracker.enterScope` / `leaveScope`）と、先読みを読み直すたび（Q13）。
式の値はローカル変数の表に依存するが、表はメソッドに入る前の先読み（`scanOrigins`）で**作っている途中**の状態を通る。

```java
Dao x = new A();
Dao y = wrap(x);   // 先読みの 1 回目の時点では x は A だけ
x = new B();       // ここで x は U になる
```

先読みで作った `x` のノード（`T:A`）を本体の走査で使うと、`wrap(x)` の呼び出し箇所の実引数が `A` に見える。
先読みはスコープを積んで行い、終わると降ろすので、そこで捨てれば本体の走査は表ができた後の値で作り直す。
読み直しの 2 回目以降も、前の回の控えを使うと `y` の値が 1 回目の途中の表のまま残るので、回ごとに捨てる。

## Q11. 期待出力は変わったか

変わっていない。`test/regression` の各ケースの `call-hierarchy.csv` / `methods.csv` はそのまま通る。
題材（`test/demo` など）には、直した書き方（値を変えるキャストを実引数にする・浮動小数の比較・
`++` を挟む変数の比較・引数やフィールドへの `new`・匿名クラスのフィールドで外側の引数を受ける・
最上位ビットの立つ 16 進のリテラル・ループの中で後ろから書き換わる変数を写す・型の揃わない `equals`）が無いためである。
`test/cacheversion` の事実の指紋は変わる（X 行の対象と値グラフの作り方が変わった）ので、版を上げて記録を更新した。
Q12〜Q15 の変更だけでは題材の事実は変わらない（指紋は Q1〜Q9 の変更の後と同じ）。

## Q12. 16 進のリテラルは、なぜ表記から読まないのか

表記から読むと、Java の値と食い違うからである。`int` の 16 進・8 進のリテラルは、最上位ビットが立つと
負の値になる（JLS 3.10.1。`0x80000000` は `-2147483648`、`0xFF000000` は `-16777216`、`0xFFFFFFFF` は `-1`）。
条件の期待値（`OriginTracker.constantOf`）は数値リテラルを表記から `Long.decode` で読んでいたので、
`long` の正の値（`2147483648`）になっていた。

呼び出し元の値のうち、`static final int MASK = 0xFF000000;` のような定数は JDT の値（`getConstantValue`）で負になる。
ここは以前から食い違っていて、`run(MASK)` の経路で `flags == 0xFF000000` を偽と判定し、`hit` を落としていた。
この作業で値グラフの定数を JDT の評価に揃えたところ（Q3）、リテラルどうし
（`run(0x80000000)` と `flags == 0x80000000`、`case 0x80000000 ->`）も食い違うようになった。
以前は両側とも表記から読んでいたので、偶然揃っていただけである。

数値リテラルの値も JDT の評価（`resolveConstantExpressionValue`）から取るようにした。
条件の期待値・出所の文字列・値グラフが同じところから値を得るので、表記の揺れ（`1L`・`0x10`・`1_000`・8 進）で
食い違わない。JDT が値を返さないときは拾わない（判定しない側）。浮動小数は従来どおり拾わない（`constantText`）。
`test/pruning` の `Hex` / `Oct` / `HexConst` / `HexDec`（`run(-16)` と `flags == 0xFFFFFFF0`）/ `HexSwitch` で見る。
（表記から読んでいたときは、`e` / `E` を含む、または `f` / `F` / `d` / `D` で終わる 16 進を浮動小数と取り違えて
条件を作っていなかったので、`0xFFFFFFFF` や `0xFE000000` はたまたま落ちなかった。）
対照の `run(0x80000001)` は `flags == 0x80000000` で打ち切る。

## Q13. ループの中で写した変数は、なぜ古い値のままだったのか

先読み（`OriginTracker.scanOrigins`）が本体を 1 回しか通っていなかったからである。代入の右辺の出所は
**その時点**の表で求めるので、ループの中で後ろにある代入が、前の行で写した変数に届かない。

```java
int n = 0;
for (String s : items) { int copy = n; if (copy != 0) notFirst(); n++; }

Dao x = new DaoA();
for (…) { Dao y = x; y.find(); x = new DaoB(); }

String name = "pr.DaoA";
for (…) { Dao d = Factory.create(name); d.find(); name = "pr.DaoB"; }
```

Q5 で `n++` を書き換えとして数えても、`copy` は `n` がまだ `V:0` だった時点の値を写したまま残る。
`y` は `x` が `DaoA` だけだった時点の値、`d` の出所（`M:create|0=L:pr.DaoA`）は `name` が `pr.DaoA` だけだった
時点の実引数で作られる。3 つ目は別名を挟まなくても起きる。出所の文字列を持てない値
（識別子の形でない文字列 `"light mode"`。Q6）では、値グラフのノードだけが同じ理由で古いまま残る。

表（出所の文字列とノード）が変わらなくなるまで本体を読み直すことにした（`OriginTracker.Scan`）。
2 回目以降は前の回で揃った表で右辺を求めるので、`n` / `x` / `name` が U になったことが写した先に届く。

却下した案:

- 流れに沿った解析（到達定義）にする … どの代入がどの行に届くかを正確に求められるが、分岐・ループ・
  例外・ラムダの境界まで作り直すことになる。今の表はフロー非依存で「複数あれば U」に倒す作りなので、
  その作りのまま読み直すほうが小さく、安全側の性質も変わらない
- 写した変数だけを後から直す … 写した先がさらに実引数・レシーバ・コレクションの要素に入るので、
  直す先を追い切れない

## Q14. 読み直しは必ず止まるのか。遅くならないのか

止まる。表の値は「最初に入った値」から U（ノードは無し）へ動くだけで、戻らない（食い違えば U、U は何と合わせても U）。
読み直すたびにどれかの変数が U に動くか、何も動かずに止まるので、回数は変数の数で抑えられる。
念のため上限（`MAX_SCAN_PASSES` = 8 回）を置き、使い切ったら、その先読みで書いた変数をすべて U にする。
1 回読み直すごとに U が代入 1 段ぶん伝わるので、後ろから前へ写す代入が長く連なる書き方でなければ 3 回ほどで止まる。

1 回目で、どの変数にも 2 回目の書き込み（再代入・`++`・複合代入・引数への代入）が無ければ読み直さない。
ローカル変数は宣言より前では読めない（JLS 6.3）ので、1 回しか書かれない変数は、読んだ時点で既に最後の値である。

実測（先読み 1 回ごとに、何回で止まったかを数えた）では、このツール自身のソース（約 170 ファイル）で
1 回 2,095・2 回 259・3 回 15、JDK の `java.util` 以下（369 ファイル）で 1 回 12,735・2 回 2,037・3 回 67 だった。
4 回以上と上限に届いたものは無い。解析（フェーズ 1）の時間は直す前と測定の揺れの範囲で変わらず
（どちらも約 3.6 秒）、`call-hierarchy.csv` / `methods.csv` も同じだった。
このツール自身のソースで、N 行は 7,274 行から 7,330 行に増えた（読み直しの 1 回目の途中の表で作ったノードが、使われないまま残る。
1 回だけ読んでいたときも、先読みで作って本体の走査で使わないノードはあった）。

読み直すたびに次のものを捨てる。どちらも前の回の途中の表から作ったものである。

- 値グラフの式ごとの控え（Q10）
- コレクションの要素の出所（`Scope.elements`。`list.add(d)` の `d` を先読みの途中で読んだもの）

拡張 for の変数に要素の出所を当てるところ（`Scan.bindLoopVariable`）は、置き換えずに合わせる（食い違えば U）ようにした。
置き換えると、2 回目以降にその回の途中だけ要素の出所に戻る。

```java
for (Dao x : list) {                 // list には DaoA だけを入れている
    for (…) { Dao y = x; y.find(); x = new DaoB(); }
}
```

1 回目の後で `x` は U だが、2 回目に置き換えると `Dao y = x;` の時点で `x` が `DaoA` に戻り、`y` は `DaoA` のまま
変わらない（表が変わらないので止まり、`DaoB` を落とす）。`test/pruning` の `LoopVarInner` で見る。
要素の出所が前の回と変わったとき（`ElemLate`。`list.add(d)` の後で `d` が書き換わる）も U になる。

`test/pruning` では、読み直し・控えを捨てること・要素の出所を捨てること・拡張 for の変数を合わせることの
どれか 1 つを外すと、対応するケースが落ちることを確かめた。書き換えない別名（`AliasConst` / `AliasNewOnly` /
`FactoryConst`）は、読み直した後も打ち切り・絞り込みが効く。

## Q15. `equals` の条件は、なぜ型を見るのか

`equals` は、実行時の型が違えば値の表記が同じでも偽になるからである。条件は値を**表記**で比べる。

| 書き方 | 実際 | 表記の比較 |
|---|---|---|
| `void check(Long id) { if (!id.equals(0)) hit(); }` に `check(0L)` | `Long.equals(Integer)` は偽。`hit` は必ず呼ばれる | `0` と `0` で「成立しない」 |
| `void m(Object o) { if (!o.equals(5)) hit(); }` に `m(5L)` | 偽（`Long` と `Integer`） | 同上 |
| 同じく `!o.equals(65)` に `m('A')` | 偽（`Character` と `Integer`。`char` は数値 `65` で持つ。`jls-conformance-qa.md` の Q14） | 同上 |
| `if (!"5".equals(o)) hit();` に `m(5)` | 偽（`String` と `Integer`） | 同上 |
| `double d = 1; m(d);` と `!o.equals(1)` | 偽（`Double` と `Integer`） | 同上 |

どれも `hit` に `[UNREACHABLE]` を付けて落としていた。`==` は `comparableByValue` で型を見ていたが、`equals` は見ていなかった。

比べる相手（`subject`）の**静的な型**から実行時の型が 1 つに決まり、それが定数と同じ型のときだけ条件にする
（`GuardCollector.equalsComparable`）。

- `String` の相手と文字列の定数（`String` は final）
- 同じ列挙型の相手と列挙定数（`Enum.equals` は final で、同一性の比較）
- ボックス型の相手と、それに箱詰めされるプリミティブの定数（`Integer` と `int`、`Long` と `long`、
  `Character` と `char` など。ボックス型はどれも final）。`Float` / `Double` は除く（Q4 と同じ理由）

`Object`・インターフェース・型変数・型の食い違う組み合わせは条件にしない。呼び出すメソッドが `equals(Object)` で
ないとき（列挙型に `equals(Mode)` を多重定義した、など）も中身が分からないので条件にしない。
型はキャストを剥がす前の式で見る（`(String) o` は `String`。実行時に違う型ならキャストで例外になり、その先に進まない）。
対照（`s.equals("full")`・`i.equals(5)` の `Integer`・`id.equals(1L)` の `Long`・`m.equals(Mode.A)`）は打ち切る。

却下した案: 値に型を付けて持つ（`V:5` を `V:long:5` にする）… 実行時の型で比べられるが、
キャッシュの形式・読み手・注記の表記まで変わる。静的な型で判定するかどうかを決めれば、書き手だけで安全側に倒せる。

## Q16. まだ残っているもの

- **浮動小数の変数に入れた整数の定数**: `double d = 1;` の `d` は値 `V:1` を持つ（Q4 の「浮動小数の定数を持たない」は
  定数の型で見ているため）。条件の側で浮動小数の比較（Q4）と `Object` の `equals`（Q15）を判定しないので
  打ち切りにはつながらないが、値に型を持たない作りの穴として残る
- **符号の付いた定数**: 条件の期待値として読むのはリテラルと名前（定数・列挙定数）だけで、`x == -1` の `-1`
  （単項演算子の式）は読まない。判定しない側なので落とすことはなく、打ち切れる場面が減るだけである
- **読み手の出所の文法（打ち切りの誤りが残っている）**: 出所の文字列の区切りと同じ文字を値に持つ文字列は、
  読み手が値グラフから出所の文字列に組み直すときに区切りで切られる。`parse("x", ";")` → `if (";".equals(delim)) semicolon();`
  は、実引数が空文字に見えて `semicolon` に `[UNREACHABLE] … (argument 2 from the caller = )` が付く。
  書き手の値（N 行）は正しく、読み手（`jche.graph.OriginRenderer` / `jche.cache.Origin`）の問題なので、別の作業で扱う
  （stage B で直した。読み手は出所の文字列ではなく値の表を読む。`docs/cache-unification-qa.md` の「読み手が値の表を読む」）

## Q17. 返す具象型が値から決まらない @Bean メソッドで、なぜ DI の絞り込みが呼び出しを落としたのか

段 5（`CallResolver.springResolution`）は、候補の型のうちコンテナに登録された Bean が 1 つだけなら、それに絞る。
@Bean メソッドが登録する型は、戻り値（R 行）の値がどれも同じ型の `new` のときだけ決まる（`SpringBeans`）。
それ以外の @Bean メソッドは、これまで**何も登録しなかった**。すると次の形で、`@Repository` の RepoA だけが
Bean に見え、段 5 が RepoA に絞って、コンテナが実際に注入しうる RepoB の呼び出しを黙って落とした。

```java
@Repository class RepoA implements Repo { … }
class RepoB implements Repo { … }
@Configuration class Cfg { @Bean Repo repoB() { return RepoB.builder().build(); } }
@Service class Svc { @Autowired private Repo repo; void run() { repo.find(); } }   // → RepoA.find だけ
```

決まらない形は、ファクトリ・ビルダーの戻り値（`return FacB.make();`）、引数（`@Bean ParI b(ParB p) { return p; }`）、
フィールド（`return f;`）、条件演算子（`return c ? new B() : new B();`）、return が 2 通りの型。値を読まない指定
（`dataflow.enabled=false`）では R 行を読まないので、`return new RepoB();` でも決まらず、すべての @Bean メソッドが
この形になっていた（`config/config.properties` は「その Bean は数えない」とだけ書き、絞り込みを誤ることは書いていなかった）。

今は、返す具象型が決まらない @Bean メソッド（上書きした本体を含む）の Bean を、**宣言した戻り値の型とその部分型の
どれか**として覚え、候補の型（呼び出しを修飾する型とその部分型）がそこに触れれば段 5 で絞らない（CHA の候補を残す）。
宣言した戻り値の型は D 行に書く（形式 v34。アノテーションの付いたメソッドにだけ書く。読むのはここだけなので、
全メソッドに書いてキャッシュを嵩ませない）。値を読まない指定でも D 行は読むので効く。戻り値の型が分からない・
`Object` なら、どの呼び出しでも段 5 で絞らない（H 行の親型は `Object` を含まないので部分型を引けない）。
上書きした本体の戻り値の型は D 行に無いこと（`@Bean` を付け直していなければアノテーションが無い）があるので、
上書きされた宣言の型を使う（上書きした本体の型はその部分型で、広い側に倒れる）。

対照として、決まらない @Bean メソッドがあっても、宣言した型が候補の型に触れなければ（`@Bean SbUnOther other()` と
`SbUnI` の呼び出し）これまでどおり段 5 で絞る。決まる @Bean メソッド（`return new SkDaoA();`）も絞る（SbKeep）。

却下した案: 決まらない @Bean メソッドが 1 つでもあれば段 5 をまるごと止める。値を読まない指定では @Bean を使う
プロジェクトのほぼすべてで段 5 が効かなくなり、ステレオタイプだけで決まる呼び出しまで CHA に戻る。

検査は `test/pruning/run.sh` の SbFac・SbPar・SbFld・SbCond（値を読む指定で 4 つの形。両方の実装が残ること）と、
対照の SbUnrel・SbKeep、値を読まない指定の小さなプロジェクト（`work/nodf`。RepoA・RepoB の両方が残り、@Bean に
触れない呼び出しは `RESOLVED:SPRING_DI` のまま）。どれも 6c41201 では落ちる（対照は通る）。

## Q18. フィールドの値を「コンストラクタで入れた値だけ」と言い切ったのに、実際には別の値が入っていたのはなぜか

読み手（`jche.graph.FieldFacts`）は、private か final のフィールドへの書き込みが「コンストラクタ（this(...) 委譲しない
全部）かフィールド初期化子だけ」で、値の頭が揃えば、そのフィールドには必ずその値が入ると判定する
（コンストラクタの引数なら、経路で分かっているコンストラクタ実引数を当てる）。判定の材料の J 行を書き手
（`FieldFactCollector`）が**取りこぼしていた**ので、書き込みが他に無いように見えていた。

| 書き方 | 以前の J 行 | 以前の出力 |
|---|---|---|
| 内部クラスの `dao = d;`（`class Setter { void set(Dao d) { dao = d; } }`） | 拾わない（書いた型が違う） | `dao.find()` を DaoA だけに絞る |
| static な入れ子のクラスの `f.dao = d;` | 拾わない | 同上 |
| `n++` / `--n` | 拾わない（代入ではない） | `n` を 0 のままとみなして `x == 1` を打ち切る |
| `this.m += n;` | 右辺 `n` の値を入れたことにする | `m` を `n` とみなして `x == 2` を打ち切る |
| インスタンス初期化ブロック `{ dao = new DaoB(); }` | 拾わない | DaoA だけに絞る |
| 初期化子のラムダ `setter = x -> this.dao = x;` | 拾わない | DaoA だけに絞る |
| `if (use) { this.mode = m; }`（条件の中の書き込み） | コンストラクタの書き込みとして数える | 通らない経路の既定値 `0` を見落として `x == 0` を打ち切る |
| `if (skip) return; this.on = v;` | 同上 | 既定値 `false` を見落とす |
| `d = new DaoB(); this.dao = d;`（書き換えた引数） | 右辺を引数の `A:0` とする | 渡された DaoA に絞る |

今の規則（`FieldFactCollector`）:

- **書き込みはどこにあっても拾う。** 自分の型の本体（メソッド・コンストラクタ・初期化ブロック・static 初期化ブロック・
  フィールド初期化子の中のラムダ）の書き込みと、別の型の本体（入れ子のクラス・外側のクラス）からの **private な
  インスタンスフィールド**への書き込み。後者は書いた側の型を拾うときに、宣言した型の事実として残す。private な
  フィールドに書けるのは同じコンパイル単位の中だけ（JLS 6.6.1）なので、同じファイルのブロックに V 行と並び、
  読み手はブロックの終わりで一緒に判定できる。private でない final なフィールドには宣言した型の初期化の中でしか
  書けない（JLS 8.3.1.2）ので、外からの書き込みを探す必要は無い
- **`++` / `--` / 複合代入は値が分からない書き込み**（ノード無し）。値の頭が揃わなくなり、そのフィールドは決まらない
- **コンストラクタ・インスタンス初期化ブロックの中でも、生成のたびに必ず通る `this` への書き込みだけを
  「そのコンストラクタの書き込み」にする。** 本体の直下の式文で、それより前の文に `return` が無いこと。条件・ループ・
  try・ラムダ・入れ子の型の中、`this` 以外（`other.f`・`Outer.this.f`）への書き込みは site を `?`
  （`FieldAssignFact.SITE_ELSEWHERE`）にする。読み手はコンストラクタでも初期化子でもない site を「生成後に差し替わりうる」
  と読むので、そのフィールドは決まらない。通らない経路では既定値（`0` / `false` / `null`）が残り、それも実在する値である
- **本体の中で書き換えられる引数を右辺が読む代入は、値が分からない**。引数の表の `A:n` は呼ばれた時点の値で、
  書き換えた後の値ではない

却下した案:

- **条件の中の書き込みでも、全部の分岐で書いていれば数える**（`if (c) f = a; else f = b;`）。分岐の網羅を判定する
  流れの解析が要る。決まらない側に倒れるだけなので、まずは直下の式文だけにした
- **参照型のフィールドは既定値 `null` を無視する**（`null` なら呼び出し自体が例外になるので、絞っても落とさない）。
  `if (dao == null)` のような条件の判定や、`null` を別の実装に差し替える後続の書き込みがあると成り立たない。型で分けずに同じ規則にした
- **読み手が J 行の site を見て「条件の中か」を判定する**。site はメソッドのシグネチャしか持たず、文の位置は書き手にしか分からない

## Q19. 別のインスタンスのフィールドに、今のオブジェクトのコンストラクタ実引数を当てていたのはなぜか

2 か所で「今のオブジェクト（this）」の判定が緩かった。

1. **書き手**: フィールドの読み取りは、修飾に関係なく値 `F:型#名前` にしていた（`OriginTracker.variableOriginOf` は
   バインディングだけを見る）。`other.dao.find()`・`check(other.mode)` の `other.dao` も `F:`。読み手は `F:` を
   「今のオブジェクトのフィールド」と読み、経路で分かっている**今のオブジェクト**のコンストラクタ実引数を当てる
   （`DataflowResolver.fieldSlotOf`）ので、`other` の中身を this の中身と取り違えた
2. **読み手**: 呼び出しのレシーバの値が無い（`ValueStore.NONE`）ことを this への呼び出しとみなし、コンストラクタ実引数を
   呼び出し先へ引き継いでいた（`StreamingTreeWalker.bindConstructorArguments`）。値が無いのは `m()` / `this.m()` だけでなく、
   拡張 for の変数（`for (H h : all) h.go();`）・パターンの変数（`o instanceof H other`）・配列の要素（`peers[0].go()`）の
   ように値を追えなかったレシーバも同じ

今の規則:

- 書き手は、`this` 以外（別の変数・`Outer.this`・メソッドの戻り値など）で修飾した**インスタンスフィールド**の読み取りを
  値にしない（コンパイル時定数なら値だけは使う）。修飾の無い名前と `this.f` だけを `F:` にする。static フィールド・
  列挙定数・定数は修飾に関係なく今までどおり
- 書き手は `this.m()` のレシーバの由来（`RecvKind`）を、修飾の無い `m()` と同じ this（`T`）にする（`Outer.this.m()` は含めない）
- 読み手は、レシーバの由来が this の呼び出しでだけ、コンストラクタ実引数を引き継ぐ

`this.m()` を this にしたので、CHA で絞れなかった `new Thread(this::hook)` の注記の理由が `receiver unknown` から
`own class (this)` に変わった（`test/regression` の期待出力。行の数と呼び出し先は変わらない。Q24）。

却下した案: **読み手で、レシーバの値の種別が無いときは引き継がない**だけにする。`this.m()` もレシーバの値が無いので、
今まで絞れていた `this.use()` からのフィールドの呼び出しまで CHA に戻る。書き手に「this だった」を残すほうが正確で、
残す場所（RecvKind）は既にある。

## Q20. 拡張 for の変数を、`add` で詰めた値だけに絞っていたのはなぜか

要素の出所（`OriginTracker.elementOriginOf`）は「本体の中で、そのローカル変数をレシーバにして `add` などを呼んだ実引数」を
集めていた。コレクションに要素が入る経路はそれだけではない。

| 書き方 | 見落としていた要素 |
|---|---|
| `new ArrayList<>(List.of(new DaoB()))` | コンストラクタの実引数 |
| `list.addAll(…)`・`Collections.addAll(list, …)`・`list.replaceAll(…)` | 足すメソッドの一覧に無い |
| `fill(list);`（渡した先で詰める） | 別のメソッドの中 |
| `alias = list; alias.add(b);` | 別名 |
| `list = make();` | 再代入 |
| `void run(List<Dao> tasks) { tasks.add(a); for (… : tasks) … }` | 呼び出し元が詰めた要素 |
| `list.listIterator().add(b)`・`forEach(list::add)` | 反復子・メソッド参照 |

今は、次を**全部**満たすときだけ要素の出所を使い、それ以外は「分からない」にする。

- この本体の中で、引数も匿名クラスの本体も無い `new` で初期化したローカル変数で、作る型が `java.util` のもの
  （利用者の型は、コンストラクタや反復子が何を返すか分からない）
- 再代入しない（宣言がちょうど 1 つ）
- 使うのは、要素を足すメソッド（Q7 の一覧は変えない）のレシーバ、拡張 for の回す式、要素を足さず外へも漏らさない
  問い合わせ（`size`・`isEmpty`・`contains`・`clear`・`remove`・`hashCode`・`toString`）のレシーバだけ

引数・フィールドのコレクションは、外で何が詰められたか分からないので使わない。

却下した案: **足すメソッドの一覧に `addAll` などを足す**。`addAll` の実引数の要素を追うにはその実引数のコレクションの
中身が要り、渡した先・別名・反復子まで一覧で塞ぐことはできない。「漏れる使い方をしていない」ことを確かめるほうが確実で、
実務で多い「その場で作って、詰めて、回す」形は今までどおり絞れる（対照 ElemOnly）。

## Q21. 型名で書いたメソッド参照で、条件を別の実引数で判定していたのはなぜか

`Mode::chk`（`void chk(Mode other)`）を `BiConsumer<Mode, Mode>` にして `c.accept(Mode.B, Mode.A)` と呼ぶと、第 1 実引数
（`Mode.B`）がレシーバで、2 番目（`Mode.A`）が `other` になる（JLS 15.13.3）。経路を歩く側
（`StreamingTreeWalker.bindArguments`）は `c.accept` の実引数を位置のまま `chk` の引数に当てていたので、`other` を `Mode.B` と
読んで `other == Mode.A` を偽と判定し、`[UNREACHABLE]` にした。引数の具象型でも同じで、`Merger::merge`（`merge(Dao other)`）を
`c.accept(new Merger(), new DaoB())` で呼ぶと、`other.find()` を Merger の実装に絞っていた。

今は、宣言どおりの呼び出し先と実際に降りる先が違うとき、実引数の位置をずらす数を決める（`argumentShift`）。

- 引数の数が同じ（上書き・ラムダの本体・束縛したメソッド参照・static メソッドの参照）… ずらさない
- 降りる先がインスタンスメソッドで、引数が 1 つ少ない（型名で書いたメソッド参照）… 1 つずらす
- `Method.invoke(obj, a, b)` から降りる先 … 1 つずらす（第 1 実引数はレシーバ）
- 降りる先の最後の引数が配列（可変長引数にまとめられているかもしれない）、それ以外で数が合わない … 引数の環境を渡さない

却下した案: **型名で書いたメソッド参照だけを見分けて、束縛したものと分ける**。値のノードには、束縛したレシーバの値が
追えなかった参照（`r=` が無い）と型名で書いた参照の区別が無い。引数の数で決めれば、区別が要らない。

## Q22. リフレクションの invoke で、動かないメソッドに繋いでいたのはなぜか

`Method.invoke(obj, …)` の先（`DataflowResolver.invokeTargets`）は、`obj` の具象型が分かれば、いつもその型から実装を
引き直していた。

- **private のメソッド**（`P.class.getDeclaredMethod("m")` の `private void m()`）は上書きされない（JLS 8.4.8）。
  `invoke(new C())` でも動くのは `P.m` なのに、`C` の同名同引数の `public void m()` に繋いでいた
- **static のメソッド**は受け手を使わない。`P.class.getMethod("s").invoke(new C())` で動くのは `P.s` なのに `C.s` に繋いでいた
- **引数型が分からない `getMethod`**（`C.class.getMethod("m", types)`）は、名前が一致する本体付きメソッドを
  「最初に見つかった型」だけから集めていた。`getMethod` は継承したメソッドも返すので、親の `P.m(int)` を落として
  `C.m(String)` に決めていた

今は、見つけたメソッドが private か static なら実行時のクラスで選び直さない。引数型が分からない `getMethod` は、
型と親の型すべてから名前の一致する本体付きメソッドを集め（親の private は `getMethod` で見つからないので除く）、
仮想メソッドは受け手の実行時のクラス（分からなければ getMethod の受け手のクラス）から実装を引き直す。
`getDeclaredMethod` はその型が宣言したものだけ（親を探さない）。

却下した案: **受け手の具象型を使わない**。上書きされたメソッドへの invoke（対照 ReflRecv）で、宣言の本体に繋いで
実際に動く部分型の実装を落とす。

## Q23. DI（段 5）で、注入と関係ない引数・フィールドまで唯一の Bean に絞っていたのはなぜか

段 5 はレシーバがフィールドか引数なら、どれでも候補を Bean に絞っていた（`docs/spring-di-qa.md` の Q5・Q6）。
Bean でないクラスの static メソッドの引数（`static void process(Dao d) { d.find(); }` に `new DaoB()` を渡す）や、
Bean でないクラスがコンストラクタで受け取るフィールドまで、`@Repository` の DaoA だけに絞り、実際に渡した DaoB の
呼び出しを落とした。段 5 で絞った結果は経路の値で覆さなかったので、経路で DaoB と分かっていても DaoA のままだった。

今は、レシーバがコンテナの値を入れうる**注入点**のときだけ絞り、経路で具象型が分かればそちらを採る。
規則と却下した案は `docs/spring-di-qa.md` の Q5・Q6 に書き直した。

## Q24. 期待出力は変わったか。キャッシュの版は

`test/regression` の期待出力で変わったのは、`fx.lambda.CallbackRefs.viaThread` の `new Thread(this::hook)` の注記の
理由だけ（`call-hierarchy.csv` の 2 行と `methods.csv` の 1 行。`receiver unknown` → `own class (this)`）。
メソッド参照のレシーバが `this` なので、書き手がレシーバの由来を this にした結果（Q19）。候補の数・呼び出し先・

書き手が作る事実（J 行の範囲と site、`F:` にする読み取り、`this.m()` の RecvKind、拡張 for の変数の値）が変わったので、
キャッシュの版を `jche-cache-v35` に上げた（`test/cacheversion/facts.txt` も更新）。

## Q25. 別のインスタンスのフィールドを値にしなくなって、何が絞れなくなったのか。どう戻したのか

Q19 で、`this` 以外で修飾したインスタンスフィールドの読み取り（`other.dao`）を値にしないようにした。読み手は `F:` を
「今のオブジェクトのフィールド」と読み、経路で分かっている今のオブジェクトのコンストラクタ実引数を当てるので、別の
インスタンスの中身を取り違えていたからである。ところが、これで次の 2 つまで絞れなくなった（最後のレビューで見つかった。
呼び出しを落とす向きではないが、精度の後退）。

| 書き方 | 52453ae | 01eb510 | 今 |
|---|---|---|---|
| `private final Dao dao = new DaoA();` を持つ型の `o.dao.find()` | `DATAFLOW_FIELD` で DaoA | `UNEXPANDED:CHA`（DaoA・DaoB） | `DATAFLOW_FIELD` で DaoA |
| `final Consumer<Dao> setter;` をどのコンストラクタでも `x -> this.dao = x` にし、`f.setter.accept(new DaoB())` | ラムダの本体に繋ぐ | `UNEXPANDED:LAMBDA`（本体への行が出ない） | `DATAFLOW_LAMBDA` で本体に繋ぐ |

どちらも、フィールドに入る値が**どのインスタンスでも同じ**形である。コンストラクタ実引数から来た値（Q19 の OtherFld・OtherInt）
だけが、インスタンスごとに違う。

今の規則:

- **書き手**は、`this` 以外で修飾したインスタンスフィールドの読み取り（`other.dao`・`getPeer().mode`・`Outer.this.dao`）を、
  別の種別 `O:型#名前`（`Origin.OTHER_FIELD`）のノードにする（`OriginTracker#otherFieldOriginOf`）。コンパイル時定数
  （定数変数）はこれまでどおり値だけを持つ。修飾の無い名前と `this.f` は `F:` のまま
- **読み手**は、`O:` にコンストラクタ実引数を当てない（経路を渡さずにフィールドの値を引く。`DataflowResolver#concreteSlotOf`）。
  使えるのは、フィールドの事実（`FieldFacts`。private か final・書き込みはコンストラクタと初期化子の必ず通る位置だけで、
  条件の中・ラムダの中・別のインスタンスへの書き込み（site が `?`）が 1 つでもあれば判定しない・どの生成経路でも代入される・
  値の頭が 1 つに揃う）が「必ずこの値が入る」と判定したフィールドのうち、値の頭が
  - `new` の型（`T:`）… `new X(a)` の頭は `T:X` で、実引数は頭に入らない。コンストラクタで入れていても、どのインスタンスでも同じ型
  - ラムダ・メソッド参照（`Z:`）… 本体はどのインスタンスでも同じ合成メソッド。束縛したレシーバはフィールドの値の頭に持たない
    ので、仮想メソッドの参照はこれまでどおり CHA の候補になる。ただし、本体が**捕捉した引数**（`E:`。`this.r = () -> d.find();` の
    `d`）を呼び出しのレシーバ・実引数に使うラムダは使わない（`DataflowFacts#usesCapturedValues`）。捕捉した値はそのインスタンスを
    作ったときのフレームのものだが、経路を歩く側は、ラムダを生成したメソッドの段から降りると今のフレームの引数を捕捉した値として
    渡す（[lambda-expansion-qa.md](lambda-expansion-qa.md) の Q10）。コンストラクタの中で別のインスタンスのラムダを呼ぶ
    （`prev.r.run()`）と、今のオブジェクトの `d` を当てて誤った実装に絞る（対照 OtherCap。この条件を外すと落ちることを確かめた）

  のものだけ。頭がコンストラクタの引数（`A:n`）なら使わない。`this.h = new Holder(d)` の `o.h.dao` のように、別の型のフィールドの
  頭が引数のものも使わない（対照 OtherNewArg）
- DI（段 5）は `O:` を注入点にしない（Q23 のまま。別のインスタンスが Bean かどうかは分からない）
- 経路を歩く側（`StreamingTreeWalker#bindConstructorArguments`）は、レシーバが `O:` の呼び出しにコンストラクタ実引数を
  引き継がない（new 以外のレシーバと同じ。Q19 のまま）

確かめたこと:

- `test/pruning` に対照 OtherInit（上の表の 1 行目）・OtherLambda（2 行目）と、使ってはいけない側の OtherNewArg・OtherCap を足した。
  OtherInit・OtherLambda は 01eb510 では落ち、今は通る。Q19 の OtherFld・OtherInt・EachRecv・PatRecv・ArrRecv はそのまま通る
- 実行の記録との突き合わせ: 題材（レビューの p1・p3・p20。p1 の F3 が表の 2 行目）の main を javaagent 付きで動かし、
  実際に通った呼び出しの連鎖（106 本）がすべて call-hierarchy.csv にあり、`[UNREACHABLE]` が付かないことを見た。01eb510 では
  p1 の `F3.main → F3.lambda$new$0` が欠けていた

却下した案:

- **書き手はこれまでどおり `other.f` も `F:` にし、読み手で頭が引数のときだけ当てない。** 読み手は `F:` がどのインスタンスかを
  区別できないので、`this` のフィールドにコンストラクタ実引数を当てることまでやめることになる（ThisDotInj などの対照が落ちる）。
  種別で分ければ取り違えようがない
- **書き手が、フィールドの値がどのインスタンスでも同じかを見て `F:` にする。** フィールドの書き込み（J 行）は宣言した型の
  ブロックにあり、別のファイルのことが多い。どう使うかは読み手の判断（事実と判断を分ける。`CacheFormat` の原則）
- **使ってよいのを初期化子だけで決まる値に限る。** 表の 2 行目（コンストラクタで入れるラムダ）が絞れない。`FieldFacts` が既に
  「どの生成経路でも同じ頭」を確かめているので、頭の種別（引数に依らない `T:`・`Z:`）で分ければ足りる

書き手の作る事実（値グラフのノードの種別）が変わるので、キャッシュの版を `jche-cache-v38` に上げた
（[cache-unification-qa.md](cache-unification-qa.md) の Q70）。

## Q26. `super.dao = …` と書いたのに、なぜ初期化子の値だけが入ると判定したのか

4 回目のレビュー（f491e2e に対するもの）で見つかった。書き手（`FieldFactCollector#assignedFieldOf`）は、代入先がフィールドかを
修飾の無い名前（`f`）・名前で修飾したもの（`obj.f`）・式で修飾したもの（`this.f`・`Outer.this.f`・`((Base) this).f`）の 3 つで
見ていて、**`super` で修飾したもの（`super.f`・`Outer.super.f`。JDT の `SuperFieldAccess`）を拾っていなかった**。
入れ子の子クラスは外側の親クラスの private なフィールドに `super.f` で書ける（JLS 6.6.1・15.11.2）。

```java
public class SupF {
    private Dao dao = new DaoA();
    void use() { dao.find(); }                       // → DaoA.find だけ（実際は DaoB）
    static class Sub extends SupF {
        Sub() { super.dao = new DaoB(); }
    }
}
```

J 行に初期化子の書き込みしか無いので、読み手（`FieldFacts`）は「必ず `new DaoA()` が入る」と判定し、`this` の読み取り（`F:`）も
別のインスタンスの読み取り（`o.dao`。`O:`、Q25）も `DATAFLOW_FIELD` で DaoA に絞って、DaoB の呼び出しを黙って落とした。
`super.dao = (super.dao instanceof DaoA) ? … : …`・`Sub.super.dao = …`（内部クラスから）・`(super.dao) = …`・
`super.n++`・`super.n += 1` も同じ（どれも同じ代入先の判定を通る）。

今は `SuperFieldAccess` も代入先として拾う。書いたのは子クラスの本体なので、宣言した型の事実としては「よそからの書き込み」
（site が `?`。Q18 の入れ子のクラスからの書き込みと同じ）になり、そのフィールドは判定しない。

代入先の形をほかにも見直した（JLS 15.26 の左辺）:

| 形 | 扱い |
|---|---|
| `f`・`obj.f`・`Outer.f` | 以前から拾う |
| `this.f` | 以前から拾う（コンストラクタの中なら「そのコンストラクタの書き込み」） |
| `Outer.this.f`・`((Base) this).f`・`get().f` | 以前から拾う（別のインスタンスかもしれないので site は `?`） |
| `super.f`・`Outer.super.f`（括弧で囲んでも同じ） | **今回から拾う**（site は `?`） |
| `f[0] = x`（フィールドが指す配列の要素） | フィールドの書き込みではない（フィールドが指す配列は変わらない） |

書き手の作る事実（J 行）が変わるので、キャッシュの版を `jche-cache-v39` に上げた（[cache-unification-qa.md](cache-unification-qa.md) の Q74）。

検査: `test/pruning` の FfSuper（`F:`）・FfSuperO（`(super.dao) = …` と `O:`）・FfOuterSuper（`Sub.super.dao`）・FfCastThis
（`((FfCastThis) this).dao`。以前から通る対照）。FfCastThis 以外は f491e2e で落ち、今は通る。`test/jls` の §15.11.2
（`SuperAccess`。`test/cacheversion` の題材にもなる）。

## Q27. `@Autowired(required = false) private Dao dao = new DaoA();` を、なぜ既定の DaoA に絞っていたのか

同じレビューで見つかった。読み手（`FieldFacts`）の判定は「private か final で、書き込みがコンストラクタと初期化子の必ず通る
位置だけ」で、**フィールドの注釈を見ていなかった**。`@Autowired(required = false)` の初期化子は「注入されなかったときの既定」で、
コンテナが Bean を注入すれば別の値になる。ソースに書き込みが見えないので、既定の `new DaoA()` だけが入ると判定して DaoA に
絞っていた（`F:` の読み取りも `O:` の読み取りも）。`@Inject`・`@Resource`・`@Value` も同じで、生成の後にリフレクションが書く。

注入に限らない。フィールドにアノテーションを付けるのは、ほとんどがフレームワークにそのフィールドを扱わせるためで
（JPA の列・関連、JSON の項目、モックの差し込み、Lombok の setter の生成）、どれもソースに見えない書き込みをしうる。
型に付けるものも同じで、`@ConfigurationProperties` は設定値を結び付け、JPA の `@Entity`・`@Embeddable` はデータベースから読んだ
値を注釈の無いフィールドにも書く。

今の規則（`FieldFacts` の条件 (f)）: 次のフィールドは判定しない（値を 1 つに決めない）。

- フィールドにアノテーションが付いている（キャッシュの V 行に載るもの。`java.lang` の注釈（`@Deprecated` など）は書き手が
  記録しないので数えない）
- 宣言した型に、DI のステレオタイプ注釈（`@Component`・`@Service` など。`SpringBeans.DEFAULT_STEREOTYPES`）以外の
  アノテーションが付いている。ステレオタイプはコンテナがインスタンスを作るだけで、注釈の無いフィールドには書かない

注釈も V 行・H 行も以前から書いているので、読み手だけの変更で、キャッシュの版は上げなくてよい（この Q の分は）。

あわせて、DI（段 5）がこのフィールドを唯一の Bean に絞らないようにした（[spring-di-qa.md](spring-di-qa.md) の Q15）。
`FieldFacts` が判定しなくなっただけでは、上の例は段 5 で `@Repository` の DaoB に絞られ、既定の DaoA（Bean が無いとき・
コンテナの外で `new` したインスタンス）の呼び出しを落とす。

却下した案:

- **注入の注釈（`@Autowired`・`@Inject`・`@Resource`・`@Value`）の一覧だけを見る。** 一覧に無い注釈（`@PersistenceContext`・
  `@Column`・`@JsonProperty`・`@Mock`・独自の合成注釈）で誤って絞る。一覧は絞る側（段 5 の Bean の判定）に使うなら漏れても
  絞らないだけだが、ここは絞らない側に使うので、漏れがそのまま呼び出しの取りこぼしになる
- **害の無い注釈（`@Nullable`・`@Getter` など）を一覧にして、それ以外で判定しない。** 害が無いと言い切れる注釈を選べない
  （`@Getter` と並ぶ `@Setter` は書き込みを生成する）。精度の損は注釈の付いたフィールドの初期化子だけで小さい
- **型の注釈をすべて数える。** `@Service` の Bean の `private final Helper h = new HelperA();` まで絞れなくなる。
  コンテナが注釈の無いフィールドに書かないことは Spring の仕様で決まっている

残る限界: 注釈の無いフィールドを、注釈の無い型のままリフレクションで書くもの（Gson・Jackson のフィールドの推定・
`ObjectInputStream`）は見えない。書き込みがソースに無い以上、書き手の事実からは分からない
（[static-analysis-limits.md](static-analysis-limits.md)）。

検査: `test/pruning` の FwAuto（`F:`）・FwAutoO（`O:`）・FwInject・FwResource・FwValue（`O:`）・FwProps（`@ConfigurationProperties`
の型の注釈の無いフィールド）と、DI の SnReq（`@Autowired(required = false)` の既定と Bean の両方が残る）・SnReset、対照の
FwDeprecated（`java.lang` の注釈だけなら絞る）・SnStereo（ステレオタイプの Bean の注釈の無いフィールドは絞る）。
対照以外は f491e2e で落ち、今は通る。段 5 の変更を外すと SnReq・SnReset が落ちることも確かめた。
