# 値の読み違いで呼び出しを黙って落とさない — 実装時の QA 一覧

Issue なし（キャッシュを 1 ファイルにまとめる作業の途中で、書き手が作る値を見直して見つかったもの）。

条件分岐の打ち切り（`[UNREACHABLE]`）と具象クラスの絞り込み（`LOCAL_NEW`・`DATAFLOW_*`）は、
書き手（`jche.analysis`）がキャッシュに書いた値を読み手が当てはめて決める。値を 1 つ読み違えると、
読み手は「この経路では呼ばれない」「この実装だけ」と言い切り、実際に動く呼び出しがその先の階層ごと
出力から消える。エラーにも警告にもならない。見つけた書き手側の読み違いを直した。

対応の要点:

- **値を変えうるキャスト**: 値として使う経路（出所・値グラフ・条件）すべてで、剥がすのは値を変えない
  キャストだけにした（`OriginTracker.unwrapValue` / `preservesValue`。条件の判定で使っていたものを広げた）。
  値を変えうるキャストの式は、コンパイル時定数なら JDT が畳んだ値（`(byte)300` は `44`）、そうでなければ「分からない」
- **浮動小数**: 値グラフに浮動小数の定数を持たない。条件も、比べる片方が浮動小数なら判定しない
- **ローカル変数の書き換え**: 複合代入（`+=`）と `++` / `--` を書き換えとして数える。`catch` の引数・
  拡張 for の変数・パターンの変数は宣言の時点で「分からない」。出所の文字列が「分からない」になった変数は、
  値グラフのノードも必ず無しにする
- **匿名・ローカルクラスのフィールド初期化子（J 行）**: 囲むメソッドの枠から切り離して読む
- **new の証拠（X 行）**: 代入が**すべて** new のローカル変数にだけ残す（引数・フィールド・拡張 for の変数には残さない）
- **値グラフの大きさ**: 同じ式は 1 つのノードにする（式ごとの控えと、式の木の中での深さで打ち切る上限）
- **数値リテラル**: 値を表記から読まず、JDT が評価した値を使う（16 進・8 進の `int` は最上位ビットが立つと負）。
  条件の期待値と呼び出し元の値が同じところから来る
- **ローカル変数の先読み**: 表が変わらなくなるまで本体を読み直す。ループの中で後ろにある代入が、
  前の行で写した変数（`int copy = n;`・`Dao y = x;`）やファクトリの実引数に届く
- **`equals` の型**: 比べる相手の静的な型と定数の型が揃うとき（`String` どうし・同じ列挙型・
  ボックス型と箱詰めされる定数）だけ条件にする
- キャッシュの版を `jche-cache-v32` に上げた（書き手が作る事実が変わったため）
- 検査は `test/pruning/run.sh`（使い捨てのプロジェクトをその場で作る）。直した書き方ごとに「落とさない」ことと、
  仕組みごとに「打ち切られる・絞られる」対照を見る。`test/regression` の期待出力は変わっていない

---

## Q1. 何が起きていたのか

`test/pruning/run.sh` の題材で、直す前の出力は次のとおりだった（すべて実際には呼ばれる）。

| 書き方 | 直す前の出力 |
|---|---|
| `run((byte) 300)` → `void run(byte mode) { if (mode == 44) hit(); }` | `hit` に `[UNREACHABLE] … (argument 1 from the caller = 300)` |
| `int m = (byte) p;` → `if (m == 44) hit();`（`alias(300)` から） | 同上。`m` が `p` の別名に見えていた |
| `dbl(1.0)` → `void dbl(double x) { if (x == 1) one(); }` | `one` に `[UNREACHABLE] … = 1.0)` |
| `f(16777217)` → `void f(float x) { if (x == 16777216) hit(); }` | `hit` に `[UNREACHABLE]`（`(float)16777217` は `16777216f`） |
| `int n = 0; for (…) n++; if (n != 0) notEmpty();` | `notEmpty` に `[UNREACHABLE] … (constant = 0)` |
| `int m = 1; m += 1; if (m == 2) two();` | `two` に `[UNREACHABLE] … (constant = 1)` |
| `void use(Dao d, boolean reset) { if (reset) d = new DaoA(); d.find(); }`（`use(new DaoB(), …)` から） | `DaoA.find` だけ（`LOCAL_NEW`）。直した後も値グラフが `DATAFLOW_NEW` で同じく落としていた |
| `Dao d = new DaoA(); if (useGiven) d = given; d.find();` | `DaoA.find` だけ（`LOCAL_NEW`） |
| `if (reset \|\| dao == null) dao = new DaoA(); dao.find();`（`dao` はフィールド） | `DaoA.find` だけ（`LOCAL_NEW`） |
| `for (Dao x : daos) { if (reset) x = new DaoA(); x.find(); }` | `DaoA.find` だけ（`LOCAL_NEW`、直した後も `DATAFLOW_NEW`） |
| `m = new DaoA();` / `m = (Dao) new DaoB();` の後の `m.find()` | `DaoA.find` だけ。キャストを挟んだ `new` を数えていなかった |
| `new Task(new DaoA()) { private final Dao inner = outer; … inner.find(); }`（`outer` は囲むメソッドの引数） | `DaoA.find` だけ（`DATAFLOW_FIELD`）。ローカルクラスでも同じ |

| `check(0L)` → `void check(Long id) { if (!id.equals(0)) hit(); }` | `hit` に `[UNREACHABLE]`。`Long.equals(Integer)` は常に偽なので、実際は必ず呼ばれる |

| `int n = 0; for (…) { int copy = n; if (copy != 0) notFirst(); n++; }` | `notFirst` に `[UNREACHABLE] … (constant = 0)`。`n++` を直した後も `copy` は `0` のままだった |
| `Dao x = new DaoA(); for (…) { Dao y = x; y.find(); x = new DaoB(); }` | `DaoA.find` だけ（`DATAFLOW_NEW`）。`Dao y = wrap(x);` でも同じ |
| `String name = "pr.DaoA"; for (…) { Dao d = Factory.create(name); d.find(); name = "pr.DaoB"; }` | `DaoA.find` だけ（`DATAFLOW_FACTORY`）。別名を挟まなくても起きる |

## Q2. キャストは、どこまで剥がしてよいのか

**値を変えないと言い切れるものだけ**（`OriginTracker.preservesValue`）。

| キャスト | 剥がすか | 根拠 |
|---|---|---|
| 参照型どうし（`(Dao) x`・`(Object) s`） | 剥がす | JLS 5.1.5 / 5.1.6。同じインスタンスを指す |
| 同じプリミティブ型 | 剥がす | JLS 5.1.1 |
| 値を保つ拡大（`byte`→`int`、`int`→`long`、`int`→`double`、`char`→`int` など） | 剥がす | JLS 5.1.2 |
| 精度を失いうる拡大（`int`・`long`→`float`、`long`→`double`） | 剥がさない | JLS 5.1.2 |
| 縮小（`(byte) p`）・拡大と縮小（`byte`→`char`） | 剥がさない | JLS 5.1.3 / 5.1.4 |
| ボックス化・非ボックス化 | 剥がさない | 従来どおり（`docs/jls-conformance-qa.md` の Q12） |
| 型が取れない | 剥がさない | 分からないものは畳まない |

`docs/jls-conformance-qa.md` の Q12 では「値の一致を判定する（ガード・定数）」だけがこの規則で、
「どのメソッドが動くかを追う（`originOf`）」は全部剥がしていた。ところが `originOf` の結果は
R 行・J 行・ローカル変数の表にも入り、読み手はそれを条件の判定に使う（引数 `A:0` に呼び出し元の値を当てる）。
値グラフ（呼び出し箇所の実引数）も同じである。1 か所でも剥がしすぎると同じ誤判定になるので、
値として使う経路は全部 `unwrapValue` を通すことにした。すべて剥がす `unwrap` が残るのは、
参照型の変数・レシーバがどのインスタンスを指すかだけを見る場面（代入先の変数・コレクションの変数・
`Class.forName(...)` の連鎖）で、そこに現れるキャストは値を変えない。

拡大を「剥がす」側に入れたので、条件の側で `(long) mode == 44` のように書いた条件も判定できるようになった
（従来は「プリミティブが絡めば変えうる」として判定しなかった）。値が保たれるので、打ち切りの誤りにはならない。

## Q3. 値を変えるキャストの式の値は、捨てるのか

コンパイル時定数なら使う。`(byte) 300` は JLS 15.29 のコンパイル時定数で、JDT は型変換まで済ませた `44` を
`resolveConstantExpressionValue()` で返す。値グラフはキャストを剥がす**前の元の式**で定数を求めるので、
`run((byte) 300)` の実引数は `44`、`run((byte) 301)` は `45` になる（`test/pruning` の対照）。
定数でなければ（`(byte) p`）「分からない」。

## Q4. 浮動小数はなぜ条件の側でも判定しないのか

値グラフに浮動小数の定数を持たないだけでは足りないからである。条件は値の**表記**を文字列の一致で比べる。
整数の実引数は `float` / `double` の引数へ暗黙に拡大され（JLS 5.3）、その拡大は精度を失いうる（JLS 5.1.2）。

```java
static void f(float x) { if (x == 16777216) hit(); }
f(16777217);   // x は 16777216f。条件は真
```

表記の比較では `16777217` と `16777216` は違う値なので偽と判定し、`hit` を落とす。
浮動小数の値の比較を正しく畳むには型ごとの丸めを真似る必要があり、得るもの（浮動小数の条件で打ち切れること）に
見合わない。`GuardCollector.comparableByValue` で、比べる片方が `float` / `double` なら条件を作らない。

## Q5. `n++` と `n += 1` は、なぜ見落とされていたのか

ローカル変数の表（`OriginTracker.scanOrigins`）は、代入の**右辺**を出所として足していた。
`n++` は代入（`Assignment`）ではなく `PostfixExpression` なので素通りし、`n` は宣言の `0` のまま。
`m += 1` は右辺 `1` が宣言の `1` と同じなので「同じ出所」と判定され、`m` は `1` のまま残った。
`int n = 0; … n++; if (n != 0)` は数を数える典型的な書き方で、`n != 0` の先をすべて落としていた。

複合代入・`++`・`--` は、どれも元の値から新しい値を作るので、出所の表では U（不明）にする。

## Q6. 引数に new を代入すると、なぜ値グラフまで new だけに見えたのか

変数の表は、同じ変数について出所の文字列とノードの 2 つを持つ。引数は文字列の表にだけ `A:0` が
最初から入っていて、ノードの表には何も無い（`paramScopeOf`。引数は葉なので作り直せるため）。
`d = new DaoA()` を足すと、文字列の表は `A:0` と `T:DaoA` が食い違って U になるが、ノードの表は
「前が無い」ので `new DaoA()` のノードがそのまま唯一の値になっていた。読み手は X 行（`LOCAL_NEW`）が
無くても、このノードから `DATAFLOW_NEW` で `DaoA` に絞る。

文字列が U になったら、ノードも必ず無しにした（`mergeOrigin`）。拡張 for の変数・`catch` の引数・
パターンの変数は、そもそも宣言が表に載っていなかった（代入 1 つが唯一の出所に見える）ので、
宣言の時点で U を入れる。要素の出所が分かった拡張 for の変数（`bindLoopVariable`）はそのまま使う。

## Q7. new の証拠（X 行）は、どの変数に残すのか

（その後、形式 v33 で X 行を無くし、証拠は書き手がファイルの中で結びつけて C 行・U 行の hints 列に持つようにした。
どの変数に残すかはここに書いたとおり。`docs/cache-unification-qa.md` の Q5）

**宣言文で宣言したローカル変数**（for 文の初期化部・try の資源を含む）のうち、初期化子とメソッドの中の
代入が**すべて** `new`（値を変えないキャストを挟んだものを含む）のものだけ。1 種類なら `LOCAL_NEW`、
複数なら `LOCAL_NEW_MULTI`（候補集合）になるのは従来どおり。

| 変数 | 残さない理由 |
|---|---|
| 引数・ラムダの引数 | 宣言そのものが呼び出し元から値を受け取る |
| フィールド | 別のメソッドからも代入される。遅延初期化（`if (dao == null) dao = new …`）の先に、ほかで入れた実装が来る |
| 拡張 for の変数・`catch` の引数・パターンの変数 | 宣言が要素・例外・照合した値を受け取る |
| `new` 以外の代入（複合代入・`++` を含む）が 1 つでもあるローカル変数 | 入ってくる値が `new` だけではない |

全部の代入を見終えるまで判断できないので、ファイルを読み終えたところ（`FactVisitor.endVisit(CompilationUnit)`）で
書く。同じ変数に同じ型の `new` が何度あっても 1 行にした（読み手は重複を捨てていた）。

`test/pruning` では、`new` した型と、それ以外（呼び出し元の実引数・コレクションの要素・ほかのメソッドが入れたフィールド）から
入る型が**同じ経路で**起こりうるように書き（`if (reset) d = new DaoA();` の `reset` は解析では決まらない）、
**両方**が出ることを見る。片方だけを見ると、もう片方を落とす誤り（引数の出所を残して `new` を捨てる、など）を見逃す。
キャストを挟んだ `new` は `LOCAL_NEW_MULTI`（2 種類）と `LOCAL_NEW`（1 種類。`Dao d = (Dao) new DaoA();`）の
resolved-by そのものを見る（CHA に戻っても候補は同じなので、候補が出ることだけでは区別できない）。

## Q8. 匿名クラスのフィールド初期化子は、なぜ囲むメソッドの引数を拾っていたのか

J 行（フィールドへの代入）は、型の宣言に入った時点（`FactVisitor.enterType` → `FieldFactCollector.collect`）で集める。
匿名クラス・ローカルクラスの宣言は囲むメソッドの中で訪ねられるので、その時点のスコープの一番上は
**囲むメソッドの表**である。`private final Dao inner = outer;` の `outer`（囲むメソッドの第 1 引数）は
「今のフレームの `A:0`」として返り、読み手（`jche.graph.FieldFacts`）はそれを
**この匿名クラスのコンストラクタの第 1 引数**と読んだ。`new Task(new DaoA()) { … }` の第 1 引数は `DaoA` なので、
`inner.find()` を `DaoA` に絞っていた。

`collect` の間は空の枠を 1 枚挟む。外側の変数は「捕捉した変数」として扱われ、メソッド本体の代入と同じ規則
（`OriginTracker.frameIndependent`）で `A:` / `F:` は捨て、`T:` / `M:` は頭だけを残す。
捕捉したローカル変数が `new DaoB()` なら、匿名クラスのフィールドも `DaoB` に絞れる（`test/pruning` の対照 `Capt`）。

## Q9. 値グラフが 1 ファイルで 1 万行を超えていたのはなぜか

`ValueGraph.HARD_CAP`（256）を、**辿り始めた位置からの深さ**で判定していたため。
300 段の連鎖 `new StringBuilder().append("…").append("…")…` では、呼び出し箇所ごとに違う段で打ち切られ、
同じ部分式が打ち切り位置の数だけ別のノードになる（ノードは構造で同一視するので、打ち切り位置が違えば別物）。
再現用の 300 段の連鎖 1 ファイルで N 行が **12,079 行**、キャッシュが 881 KB あった。

2 つ変えた。

- 式（AST のノード）ごとに作ったノードを控え、同じ式を呼び出し箇所ごとに辿り直さない
- 上限を**式の木の中での深さ**（`depthInTree`。辿る辺＝レシーバ・実引数・束縛したレシーバだけを数える）で判定する。
  同じ式はどこから辿っても同じ段で打ち切られ、打ち切ったノードも 1 つになる

同じファイルで N 行は **513 行**（メソッド呼び出し 257・文字列 255・フィールド 1）、キャッシュは 47 KB になった。
上限より深い式は「分からない」（`NONE`）のままで、呼び出しを落とさない側に倒れる。深さ 256 を超える連鎖の
末端の呼び出し箇所は、以前は（辿り始めが浅いので）値を持てていたが、今は持たない。実在のコードでは
起きない深さで、値が無ければ読み手は CHA に戻るだけである。

## Q10. 式ごとの控えは、いつ捨てるのか

スコープが変わるたび（`OriginTracker.enterScope` / `leaveScope`）と、先読みを読み直すたび（Q13）。
式の値はローカル変数の表に依存するが、表はメソッドに入る前の先読み（`scanOrigins`）で**作っている途中**の状態を通る。

```java
Dao x = new A();
Dao y = wrap(x);   // 先読みの 1 回目の時点では x は A だけ
x = new B();       // ここで x は U になる
```

先読みで作った `x` のノード（`T:A`）を本体の走査で使うと、`wrap(x)` の呼び出し箇所の実引数が `A` に見える。
先読みはスコープを積んで行い、終わると降ろすので、そこで捨てれば本体の走査は表ができた後の値で作り直す。
読み直しの 2 回目以降も、前の回の控えを使うと `y` の値が 1 回目の途中の表のまま残るので、回ごとに捨てる。

## Q11. 期待出力は変わったか

変わっていない。`test/regression` の各ケースの `call-hierarchy.csv` / `methods.csv` はそのまま通る。
題材（`test/demo` など）には、直した書き方（値を変えるキャストを実引数にする・浮動小数の比較・
`++` を挟む変数の比較・引数やフィールドへの `new`・匿名クラスのフィールドで外側の引数を受ける・
最上位ビットの立つ 16 進のリテラル・ループの中で後ろから書き換わる変数を写す・型の揃わない `equals`）が無いためである。
`test/cacheversion` の事実の指紋は変わる（X 行の対象と値グラフの作り方が変わった）ので、版を上げて記録を更新した。
Q12〜Q15 の変更だけでは題材の事実は変わらない（指紋は Q1〜Q9 の変更の後と同じ）。

## Q12. 16 進のリテラルは、なぜ表記から読まないのか

表記から読むと、Java の値と食い違うからである。`int` の 16 進・8 進のリテラルは、最上位ビットが立つと
負の値になる（JLS 3.10.1。`0x80000000` は `-2147483648`、`0xFF000000` は `-16777216`、`0xFFFFFFFF` は `-1`）。
条件の期待値（`OriginTracker.constantOf`）は数値リテラルを表記から `Long.decode` で読んでいたので、
`long` の正の値（`2147483648`）になっていた。

呼び出し元の値のうち、`static final int MASK = 0xFF000000;` のような定数は JDT の値（`getConstantValue`）で負になる。
ここは以前から食い違っていて、`run(MASK)` の経路で `flags == 0xFF000000` を偽と判定し、`hit` を落としていた。
この作業で値グラフの定数を JDT の評価に揃えたところ（Q3）、リテラルどうし
（`run(0x80000000)` と `flags == 0x80000000`、`case 0x80000000 ->`）も食い違うようになった。
以前は両側とも表記から読んでいたので、偶然揃っていただけである。

数値リテラルの値も JDT の評価（`resolveConstantExpressionValue`）から取るようにした。
条件の期待値・出所の文字列・値グラフが同じところから値を得るので、表記の揺れ（`1L`・`0x10`・`1_000`・8 進）で
食い違わない。JDT が値を返さないときは拾わない（判定しない側）。浮動小数は従来どおり拾わない（`constantText`）。
`test/pruning` の `Hex` / `Oct` / `HexConst` / `HexDec`（`run(-16)` と `flags == 0xFFFFFFF0`）/ `HexSwitch` で見る。
（表記から読んでいたときは、`e` / `E` を含む、または `f` / `F` / `d` / `D` で終わる 16 進を浮動小数と取り違えて
条件を作っていなかったので、`0xFFFFFFFF` や `0xFE000000` はたまたま落ちなかった。）
対照の `run(0x80000001)` は `flags == 0x80000000` で打ち切る。

## Q13. ループの中で写した変数は、なぜ古い値のままだったのか

先読み（`OriginTracker.scanOrigins`）が本体を 1 回しか通っていなかったからである。代入の右辺の出所は
**その時点**の表で求めるので、ループの中で後ろにある代入が、前の行で写した変数に届かない。

```java
int n = 0;
for (String s : items) { int copy = n; if (copy != 0) notFirst(); n++; }

Dao x = new DaoA();
for (…) { Dao y = x; y.find(); x = new DaoB(); }

String name = "pr.DaoA";
for (…) { Dao d = Factory.create(name); d.find(); name = "pr.DaoB"; }
```

Q5 で `n++` を書き換えとして数えても、`copy` は `n` がまだ `V:0` だった時点の値を写したまま残る。
`y` は `x` が `DaoA` だけだった時点の値、`d` の出所（`M:create|0=L:pr.DaoA`）は `name` が `pr.DaoA` だけだった
時点の実引数で作られる。3 つ目は別名を挟まなくても起きる。出所の文字列を持てない値
（識別子の形でない文字列 `"light mode"`。Q6）では、値グラフのノードだけが同じ理由で古いまま残る。

表（出所の文字列とノード）が変わらなくなるまで本体を読み直すことにした（`OriginTracker.Scan`）。
2 回目以降は前の回で揃った表で右辺を求めるので、`n` / `x` / `name` が U になったことが写した先に届く。

却下した案:

- 流れに沿った解析（到達定義）にする … どの代入がどの行に届くかを正確に求められるが、分岐・ループ・
  例外・ラムダの境界まで作り直すことになる。今の表はフロー非依存で「複数あれば U」に倒す作りなので、
  その作りのまま読み直すほうが小さく、安全側の性質も変わらない
- 写した変数だけを後から直す … 写した先がさらに実引数・レシーバ・コレクションの要素に入るので、
  直す先を追い切れない

## Q14. 読み直しは必ず止まるのか。遅くならないのか

止まる。表の値は「最初に入った値」から U（ノードは無し）へ動くだけで、戻らない（食い違えば U、U は何と合わせても U）。
読み直すたびにどれかの変数が U に動くか、何も動かずに止まるので、回数は変数の数で抑えられる。
念のため上限（`MAX_SCAN_PASSES` = 8 回）を置き、使い切ったら、その先読みで書いた変数をすべて U にする。
1 回読み直すごとに U が代入 1 段ぶん伝わるので、後ろから前へ写す代入が長く連なる書き方でなければ 3 回ほどで止まる。

1 回目で、どの変数にも 2 回目の書き込み（再代入・`++`・複合代入・引数への代入）が無ければ読み直さない。
ローカル変数は宣言より前では読めない（JLS 6.3）ので、1 回しか書かれない変数は、読んだ時点で既に最後の値である。

実測（先読み 1 回ごとに、何回で止まったかを数えた）では、このツール自身のソース（約 170 ファイル）で
1 回 2,095・2 回 259・3 回 15、JDK の `java.util` 以下（369 ファイル）で 1 回 12,735・2 回 2,037・3 回 67 だった。
4 回以上と上限に届いたものは無い。解析（フェーズ 1）の時間は直す前と測定の揺れの範囲で変わらず
（どちらも約 3.6 秒）、`call-hierarchy.csv` / `methods.csv` も同じだった。
このツール自身のソースで、N 行は 7,274 行から 7,330 行に増えた（読み直しの 1 回目の途中の表で作ったノードが、使われないまま残る。
1 回だけ読んでいたときも、先読みで作って本体の走査で使わないノードはあった）。

読み直すたびに次のものを捨てる。どちらも前の回の途中の表から作ったものである。

- 値グラフの式ごとの控え（Q10）
- コレクションの要素の出所（`Scope.elements`。`list.add(d)` の `d` を先読みの途中で読んだもの）

拡張 for の変数に要素の出所を当てるところ（`Scan.bindLoopVariable`）は、置き換えずに合わせる（食い違えば U）ようにした。
置き換えると、2 回目以降にその回の途中だけ要素の出所に戻る。

```java
for (Dao x : list) {                 // list には DaoA だけを入れている
    for (…) { Dao y = x; y.find(); x = new DaoB(); }
}
```

1 回目の後で `x` は U だが、2 回目に置き換えると `Dao y = x;` の時点で `x` が `DaoA` に戻り、`y` は `DaoA` のまま
変わらない（表が変わらないので止まり、`DaoB` を落とす）。`test/pruning` の `LoopVarInner` で見る。
要素の出所が前の回と変わったとき（`ElemLate`。`list.add(d)` の後で `d` が書き換わる）も U になる。

`test/pruning` では、読み直し・控えを捨てること・要素の出所を捨てること・拡張 for の変数を合わせることの
どれか 1 つを外すと、対応するケースが落ちることを確かめた。書き換えない別名（`AliasConst` / `AliasNewOnly` /
`FactoryConst`）は、読み直した後も打ち切り・絞り込みが効く。

## Q15. `equals` の条件は、なぜ型を見るのか

`equals` は、実行時の型が違えば値の表記が同じでも偽になるからである。条件は値を**表記**で比べる。

| 書き方 | 実際 | 表記の比較 |
|---|---|---|
| `void check(Long id) { if (!id.equals(0)) hit(); }` に `check(0L)` | `Long.equals(Integer)` は偽。`hit` は必ず呼ばれる | `0` と `0` で「成立しない」 |
| `void m(Object o) { if (!o.equals(5)) hit(); }` に `m(5L)` | 偽（`Long` と `Integer`） | 同上 |
| 同じく `!o.equals(65)` に `m('A')` | 偽（`Character` と `Integer`。`char` は数値 `65` で持つ。`jls-conformance-qa.md` の Q14） | 同上 |
| `if (!"5".equals(o)) hit();` に `m(5)` | 偽（`String` と `Integer`） | 同上 |
| `double d = 1; m(d);` と `!o.equals(1)` | 偽（`Double` と `Integer`） | 同上 |

どれも `hit` に `[UNREACHABLE]` を付けて落としていた。`==` は `comparableByValue` で型を見ていたが、`equals` は見ていなかった。

比べる相手（`subject`）の**静的な型**から実行時の型が 1 つに決まり、それが定数と同じ型のときだけ条件にする
（`GuardCollector.equalsComparable`）。

- `String` の相手と文字列の定数（`String` は final）
- 同じ列挙型の相手と列挙定数（`Enum.equals` は final で、同一性の比較）
- ボックス型の相手と、それに箱詰めされるプリミティブの定数（`Integer` と `int`、`Long` と `long`、
  `Character` と `char` など。ボックス型はどれも final）。`Float` / `Double` は除く（Q4 と同じ理由）

`Object`・インターフェース・型変数・型の食い違う組み合わせは条件にしない。呼び出すメソッドが `equals(Object)` で
ないとき（列挙型に `equals(Mode)` を多重定義した、など）も中身が分からないので条件にしない。
型はキャストを剥がす前の式で見る（`(String) o` は `String`。実行時に違う型ならキャストで例外になり、その先に進まない）。
対照（`s.equals("full")`・`i.equals(5)` の `Integer`・`id.equals(1L)` の `Long`・`m.equals(Mode.A)`）は打ち切る。

却下した案: 値に型を付けて持つ（`V:5` を `V:long:5` にする）… 実行時の型で比べられるが、
キャッシュの形式・読み手・注記の表記まで変わる。静的な型で判定するかどうかを決めれば、書き手だけで安全側に倒せる。

## Q16. まだ残っているもの

- **浮動小数の変数に入れた整数の定数**: `double d = 1;` の `d` は値 `V:1` を持つ（Q4 の「浮動小数の定数を持たない」は
  定数の型で見ているため）。条件の側で浮動小数の比較（Q4）と `Object` の `equals`（Q15）を判定しないので
  打ち切りにはつながらないが、値に型を持たない作りの穴として残る
- **符号の付いた定数**: 条件の期待値として読むのはリテラルと名前（定数・列挙定数）だけで、`x == -1` の `-1`
  （単項演算子の式）は読まない。判定しない側なので落とすことはなく、打ち切れる場面が減るだけである
- **読み手の出所の文法（打ち切りの誤りが残っている）**: 出所の文字列の区切りと同じ文字を値に持つ文字列は、
  読み手が値グラフから出所の文字列に組み直すときに区切りで切られる。`parse("x", ";")` → `if (";".equals(delim)) semicolon();`
  は、実引数が空文字に見えて `semicolon` に `[UNREACHABLE] … (argument 2 from the caller = )` が付く。
  書き手の値（N 行）は正しく、読み手（`jche.graph.OriginRenderer` / `jche.cache.Origin`）の問題なので、別の作業で扱う
  （stage B で直した。読み手は出所の文字列ではなく値の表を読む。`docs/cache-unification-qa.md` の「読み手が値の表を読む」）
