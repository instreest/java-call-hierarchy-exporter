# 出力の探索の歯止め（行にならないノードにも max.rows） — 実装時の QA 一覧

Issue なし（v42 の穴探しの指摘 38。`docs/cache-unification-qa.md` の「v42 の穴探し（形式 v43）」の Q128・Q129）。
出力の探索（`jche.report.StreamingTreeWalker`）が、行を 1 行も書かないまま終わらなくなる形を塞いだ。
迷ったこと・結論・却下した案を Q&A の形で残す。

対応の要点:

- 出力の探索は、経路ごとに辿って訪問済みの集合を持たない（別の経路で同じ呼び出しがあっても行にする）。
  組合せ爆発の歯止めは行数の上限（`max.rows`）と深さの上限（`max.depth`）だけだった
- コンストラクタ呼び出しは経路に積んで降りるが行にせず、除外パッケージ（`exclude.packages`）のメソッドも読み飛ばして
  降りるが行にしない。この 2 つだけでつながる部分木は `max.rows` に当たらず、経路の数だけ辿られていた
- **行を書かずに続けて通ったノード（コンストラクタ呼び出し・除外メソッドの読み飛ばし）の数にも、`max.rows` と同じ上限を
  掛ける**（`silentRun`。行を書くたびに 0 に戻す）。越えたら行数の上限と同じく探索全体を打ち切り、warnings.txt の
  「解析や出力が途中で打ち切られた」の項目に `report.walker.maxSilentNodes` を載せる。`max.rows` が 0 以下（無制限）なら、
  こちらも無制限
- 最初の直し（合計で数える）は普通の出力の行を落としたので、レビューで「続けて通った数」に直した（Q2）
- キャッシュに入る事実は変わらない（読み手だけの変更）。回帰テストの期待値も変わらない
- 検査は `test/warnings/run.sh` の 9

---

## Q1. 出力が 0 行のまま探索が終わらなくなったのはなぜか

出力の探索は経路ごとに辿り、訪問済みの集合を持たない（ダイヤモンドを潰さないため）。組合せ爆発の歯止めは行数の上限
（`max.rows`）だけだった。ところがコンストラクタ呼び出しは経路に積んで降りるが行にはせず（「new したこと」より
「その先で何を呼ぶか」を出すため）、除外パッケージのメソッドも読み飛ばして降りるが行にしない。行にならないノードだけで
つながる部分木は `max.rows` に当たらず、経路の数だけ辿られる。

最小の例: `C_i`（i < N-2）が `private final Object a = new C_{i+1}(); private final Object b = new C_{i+2}();`、
最後の 2 つは空、`Main.main` が `new C0()`。経路の数はフィボナッチ数で、N=34 で 2 秒、N=38 で 13 秒、N=40 で 35 秒、
深さの上限（既定 50）までなら何時間もかかる。どれも 0 行で、警告も warnings.txt も無い。同じ形を static メソッド
（`q.M_i.m()` が `M_{i+1}.m()` と `M_{i+2}.m()` を呼ぶ）で作り、`exclude.packages` に `q.**` を入れても同じ
（こちらの深さの上限は読み飛ばしの 512）。コンストラクタの中で 1 つでもメソッド（JDK のものでも）を呼べば行になるので
`max.rows` が効く。行を 1 つも出さない部分木だけが抜けていた。

**今の決まり: 行を書かずに続けて通ったノードの数にも、`max.rows` と同じ上限を掛ける。** 数えるのは、コンストラクタを
経路に積んで行にしなかったときと、除外メソッドの読み飛ばし（`skipThrough`）に入ったとき。行を書くたびに 0 に戻す
（Q2）。越えたら行数の上限と同じく打ち切り、「途中で止まった」の項目（`Warnings.Topic.INCOMPLETE`）に
`report.walker.maxSilentNodes` を載せる。warnings.txt の対処（`exporter.warnings.incomplete.remedy2`）にも、同じ上限が
掛かることを書いた。

**却下した案**:

- *「この部分木は行を出さない」を（コンストラクタ, 経路の文脈）ごとに覚えて、2 回目から飛ばす*。行が出るかどうかは
  経路ごとの循環の打ち切り・引数やコンストラクタ実引数の値・条件の判定（`GuardEvaluator`）に左右されるので、
  正しい鍵を作るのが難しく、間違えると行が黙って消える
- *行数と合わせて 1 つの上限にする*（行数 + 行にしないノード ≧ `max.rows`）。上限に近い既存の出力が、以前より少ない行で
  切れるようになる（出力が変わる）
- *別の設定項目を足す*。利用者が気にする上限が増えるだけで、`max.rows` と同じ役目（組合せ爆発の歯止め）なので同じ値でよい

**費用**: 行を書かずに続けて通るノードが `max.rows`（既定 500 万）を越える探索は打ち切られる。以前はそこから先も
（何時間でも）辿っていたが、その先で出る行は失われる。warnings.txt と run.log に出るので、黙っては落とさない。

## Q2. 行にならないノードの「合計」を max.rows で打ち切ると、何が壊れたのか

最初の直しは、行にならないノードの**合計**が `max.rows` に達したら打ち切っていた。「行数と別に数えるので、上限に届かない
探索の出力は 1 行も変わらない」としていたが、そうではなかった。行にならないノードには、コンストラクタ呼び出しと利用者の
除外パッケージだけでなく、**既定の `exclude.packages`（`java.**,javax.**`）に当たる JDK の呼び出しの読み飛ばしも入る**。
普通のコードでは JDK の呼び出し（`sb.append`・`list.add`・`System.out.println` …）はプロジェクトのメソッドの呼び出しより
多いので、行数が `max.rows` に届くより先に、行にならないノードの合計が `max.rows` に届く。

最小の例（`max.rows=100`。どれも直す前の版は 40 行すべてを出し、warnings.txt も無い）:

- `m_i(StringBuilder sb) { sb.append(1); sb.append("a"); System.out.println(sb); Leaf.x(); }` を 40 個 → 合計で数えると 31 行で打ち切り
- 除外パッケージ `q` の `U.m()` が中で 10 個の私的メソッドを呼んでから `p.Leaf.x()`、`m_i() { q.U.m(); }` を 40 個 → 8 行
- 5 段の継承の DTO を `new` するだけ（`new D4(); new D4(); new D4(); Leaf.x();`）を 40 個 → 6 行

回帰テストの題材でも、`values` は行 30 に対し行にならないノード 35（`whole` は行 368 に対し 245、`jls` は 145 に対し 49）。
既定の `max.rows`（500 万）でも、行が数十万〜数百万になるプロジェクトでは、以前は出ていた行が上限の手前で落ちる
（警告は出るが、上限に届いていない設定の出力が変わる）。

**今の決まり: 数えるのは「最後に行を書いてから、行を書かずに続けて通ったノードの数」（`silentRun`）で、行を書くたびに
0 に戻す。** 行を書き進めている探索は、行数の上限まで止まらない（上の 3 つの例は 40 行すべてが出る）。
Q1 の形（`new` だけでつながるコンストラクタの枝分かれ・除外メソッドの枝分かれで 0 行）は、行を 1 行も書かないので
合計と同じ数で止まる（N=40・既定の `max.rows` で 2 秒、0 行、warnings.txt あり）。

**却下した案**:

- *合計のまま、行を持たない読み飛ばし（JDK・jar のメソッド。辺を持たないので爆発の元にならない）を数えない*。
  コンストラクタの連鎖（5 段の継承の DTO）と利用者の除外パッケージの中の呼び出しはやはり行より多くなりうるので、
  上の 2 つ目・3 つ目の例は直らない
- *合計に「`max.rows` + 書いた行 × K」のような上限を掛ける*。K の値に根拠が無い（除外パッケージを重いユーティリティに
  掛けた利用者では、1 行あたり数十〜数百のノードを通るのが普通にありうる）。決まりも 1 つ増える
- *起点（root）ごとに数え直し、上限に達したらその起点だけをやめて次の起点へ進む*。0 行の爆発を多くの起点が共有すると
  （乱数で作ったプロジェクトの形）、時間が起点の数 × `max.rows` になり、打ち切りの効き目が薄れる

**費用**: 無し（数える場所は最初の直しと同じで、行を書くたびに 0 に戻すだけ）。

## Q3. まだ遅い形は残っているか

残っている（直す前の版から変わらない）。行を出すメソッドの枝分かれの葉ごとに、`max.rows` より小さい「行を出さない部分木」が
ぶら下がる形（`M_i.m()` が `M_{i+1}.m()` と `M_{i+2}.m()` を呼び、葉が `new C0()`、`C_j` のフィールド初期化子が
`C_{j+1}` と `C_{j+2}` を new）は、1 回の「行を書かない続き」が上限に届かないので止まらず、時間は
（葉の数）×（部分木の大きさ）になる（M 16 段・C 25 段で 25 秒、1973 行）。

行は書き進むので、黙って固まるのではなく出力は増え続け、いずれ行数の上限に届く。合計で打ち切れば止まるが、Q2 のとおり
普通の出力まで落ちる。乱数で作った題材でしか見ていない形なので、上限を増やさず、`max.depth` で浅くしてもらう扱いにする
（`docs/cache-unification-qa.md` の Q129）。

## Q4. 検査は何を見ているか

`test/warnings/run.sh` の 9。

- `dag_ctor` / `dag_excluded`: Q1 の 2 つの形（30 個のクラスのコンストラクタの枝分かれ・`exclude.packages=q.**` の static
  メソッドの枝分かれ）を `max.rows=1000` で動かし、解析が終わり、warnings.txt に `The walk passed 1000 constructor calls and
  excluded methods` が載ること。直す前の版では 0 行で warnings.txt ができない
- `busy_jdk` / `busy_excluded` / `busy_ctor`: Q2 の 3 つの例を `max.rows=100` で動かし、起点 `Main.m1`〜`m40` から `Leaf.x`
  へ届く 40 行がすべて出て、warnings.txt が無いこと。合計で数える最初の直しでは 31・8・6 行で落ちる（直す前の版では通る）

回帰テストの期待値は変わらない（どの題材も `max.rows` は 10 万以上で、行を書かずに続けて通るノードはそれよりずっと少ない）。
