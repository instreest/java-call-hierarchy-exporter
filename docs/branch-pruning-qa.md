# 変数値と条件分岐の静的解析による打ち切り — 実装時の QA 一覧

[Issue #67](https://github.com/instreest/java-call-hierarchy-exporter/issues/67)
「変数値と条件分岐の静的解析によりその経路で発生しない呼び出しを区別したい」への対応で、
迷ったこと・困ったことと、その結論を Q&A の形で残す。

対応の要点:

- フェーズ1（`jche.analysis.GuardCollector`）で、呼び出し箇所を囲む条件（`if` / `?:` /
  `&&` / `||` / アロー形式の `switch`）を**事実**としてキャッシュに記録する（C行・U行の `guard` 列）
- フェーズ3（`jche.graph.GuardEvaluator`）で、その条件が**この経路では成立しない**と
  言い切れるかを判定する。言い切れたら、その呼び出しの行は理由付きで出し、そこから先へは降りない
- コンパイル時定数の値を出所（`jche.cache.Origin` の `V:`）として記録するようにした。
  これまでの `L:`（クラス名・メソッド名の形の文字列）は「何のクラスか」を追うためのもので、
  真偽値・数値・任意の文字列は持っていなかった
- 設定 `branch.pruning.enabled`（既定 `true`）で丸ごと切れる
- キャッシュ形式は v12 → v13（列と収集範囲が変わったため）

---

## 仕様の決め方

### Q1. 「呼ばれない」と分かったとき、その呼び出しの行自体は出すのか消すのか

Issue の文面は「呼び出し元は出力するが、…それより先のメソッド呼び出し階層は出力せず、
解析を止めた理由とともに階層末尾に出力したい」。読み方が 2 つある。

1. 呼び出しの行も消し、呼び出し元の行の末尾に理由を書く
2. 呼び出しの行は理由付きで出し、その先の階層だけを出さない

**2 を採った**。理由は 3 つ。

- ソースにその呼び出しが書かれているのは事実で、消すと「影響調査で見落とす」側の間違いになる。
  このツールは一貫して「分かったことを注記で足す」方針を採っており、事実の行は消していない
- 既存の `[CYCLE]`・深さ制限・CHA 候補が、まさに「その辺は 1 行出して、先へは降りない」形。
  同じ形にすれば読み手の解釈が増えない
- 「解析を止めた理由を階層末尾に出力」という要望は、注記が `call-hierarchy` 列の
  最後の要素として出る既存の仕組みでそのまま満たせる

### Q2. どこまでの条件を判定するか

「変数値の静的解析」を広く取ると、抽象解釈やパス条件の SMT ソルバまで行き着く。
このツールが持っている情報（経路ごとの引数の出所）で**間違いなく言い切れる**範囲に限った。

判定するのは「引数か定数」と「定数」の比較だけ:

| 形 | 例 |
|---|---|
| boolean の変数・引数そのもの | `if (debug)` |
| `==` / `!=`（プリミティブ・列挙型・文字列） | `if (mode == Mode.FULL)` |
| `equals` | `if ("full".equals(name))` |
| アロー形式 `switch` の `case` / `default` | `switch (kind) { case 1 -> … }` |

それ以外（メソッドの戻り値、フィールドの状態、コレクションの中身、`null` 判定…）は
**条件そのものを記録しない**。記録しなければ読み手は打ち切りの判断ができず、
これまでどおりの出力になる。

### Q3. 「分からない」をどちらに倒すか

**必ず「辿る（消さない）」に倒す**。呼び出し階層は影響調査に使うので、
「本当は呼ばれるのに出力から消えた」は致命的、「呼ばれないのに出ている」は従来どおりで害が小さい。
`GuardEvaluator` は 3 値（成立しない／成立する／分からない）で判定し、
分からない場合はアトムを読み飛ばす。

### Q4. `x == null` を条件にしてよいか

**しない**。`Dao d = new UserDaoImpl();` から `d` が `T:UserDaoImpl` だと分かっても、
それは「代入されうる値の集合が 1 つ」というだけで、その時点で null でないことの証明ではない
（条件付き代入・宣言だけして後で代入、など）。出所の解析はフロー非依存（同じ変数に別の出所が
現れたら `U` に倒す）なので、null かどうかを言い切る材料が無い。

### Q5. コロン形式の `switch`（`case X:`）はなぜ扱わないか

フォールスルーがあるため。`case 1:` のブロックに break が無ければ `case 2:` の
本体も実行される。ある文がどの `case` の下にあるかは AST の並びから分かるが、
「その文に到達する `case` の集合」を出すには制御フローを追う必要がある。
アロー形式（`case 1 -> …`）はフォールスルーが無いので、ラベルの値がそのまま条件になる。
コロン形式が 1 つでも混ざっている `switch` は、その `switch` 全体を諦める。

### Q6. ラムダ式・匿名クラスの外側の条件は引き継ぐか

**引き継がない**。`if (flag) { list.add(() -> dao.find()); }` のラムダ本体は、
その場では実行されず、後で（別の条件のもとで）呼ばれる。生成が条件付きでも
本体の実行が同じ条件下とは限らないので、`GuardCollector` はラムダとメソッド宣言の
境界で親を辿るのを止める。

### Q7. ループの条件・早期 return は使えないか

使えない。`for (int i = 0; i < n; i++) { f(); }` で `n = 0` なら `f()` は呼ばれないが、
「呼ばれない」ことを言うには回数の解析が要る。早期 `return` / `throw` の後ろも同様に
制御フローの解析が必要。どちらも今回の「経路ごとの引数の値」だけでは判定できないので入れていない。

## 実装で困ったこと

### Q8. 条件をキャッシュにどう書くか（区切り文字の衝突）

条件には「判定の種別・式の出所・比較する値・注記に出すソースのテキスト」の 4 つが要る。
既存の出所（`Origin`）は `: | ; = { }` を、キャッシュ行はタブを使っており、
条件式のテキストには `& | ~ ^ , ; =` が普通に現れる。エスケープを増やすと
読み書きの両側が複雑になるので、**制御文字（`\u0001` / `\u0002` / `\u0003`）を区切りに使った**
（`jche.cache.Guard`）。ソースにも出所にも現れないので、エスケープ無しで往復できる。

### Q9. なぜ判定を読み手（フェーズ3）に置いたか

`CacheFormat` の原則「キャッシュは事実だけを持ち、判断は読み手でする」に従った。
「条件が成立するか」は経路ごとに変わるので、そもそもキャッシュに書けない。
書けるのは「どの式がどの値でなければならないか」という、ソースを読めば決まる事実だけ。
判定の文言や打ち切りの方針を変えても、全件再解析にならない。

### Q10. 経路ごとの引数の値をどうやって条件へ渡すか

`StreamingTreeWalker` は既に「経路上で確定した実引数の具象型」を `DataflowContext` として
持ち回っている。ここに具象型（FQN）と値（`L:` / `K:`）が混ざって入る仕組みだったので、
定数の値（`V:`）も同じ器で運ぶことにした。新しい経路情報を足していない。

そのために `DataflowResolver` を 2 か所直した。

- `valueOriginOf` … `V:` を「値」として次の深さへ渡す
- `usesContext` … これまでは「引数をレシーバや実引数として使うメソッド」にだけ経路情報を渡していた。
  条件の判定に引数を使うメソッドも対象に加えないと、値が届かず一切判定できない

### Q11. コンパイル時定数を出所として拾うと、既存の解決に影響しないか

`OriginTracker.originOf` は、これまでの判定で決まらなかったときだけ `V:` を返すようにした
（既存の `T:` / `M:` / `A:` / `F:` / `L:` / `K:` の結論は変えない）。
`V:` は `':'` を含むので、具象型（FQN）を期待する箇所では従来どおり「値であって型ではない」と
扱われる。実測でも、回帰テストのうち demo を使わないケース（maven / mavenmulti / gradle）の
出力は 1 バイトも変わらなかった。

### Q12. 文字列を無制限に拾うとキャッシュが膨らむのでは

64 文字までに制限した（`L:` の既存の上限と同じ）。ログ文言や SQL のような長い文字列は
条件の比較対象になることがほぼ無く、拾っても使われないまま容量だけ食う。
浮動小数点リテラルも、一致判定に意味が無いので拾わない。数値リテラルは
`1L` / `0x10` / `1_000` のような表記の揺れを 10 進の値に正規化してから持つ
（正規化しないと `case 16:` と `0x10` が別の値に見える）。

### Q13. 判定できる条件が複数あるときは

すべて「かつ」で結ぶ（`if (a) { if (b) { f(); } }` は a と b の両方）。
1 つでも成立しないと言い切れれば打ち切り、その条件を理由として出す。
入れ子が深いときのために、1 つの呼び出しに付ける条件は 8 個までにした
（それ以上は打ち切りの判断に効かず、キャッシュを膨らませるだけ）。

### Q14. `a && b` の右側はどう扱うか

`a` が成立していないと `b` は評価されない、という短絡評価の意味をそのまま条件にした。
`if (a && flag) { … }` の内側は「a が true」「flag が true」の 2 つ。
逆に `a || b` の `b` 側は「a が false」。
`if (a || b)` の内側（then 節）については、どちらが成立したか決まらないので条件にしない。

### Q15. 列挙定数が判定できなかった（実装後に見つかった）

`switch (mode) { case FULL -> … }` と `if (mode == Mode.FULL)` が、
呼び出し元が `select(Mode.NONE)` と定数を渡していても打ち切られなかった。

原因は、列挙定数 `Mode.NONE` の出所がフィールド（`F:fx.branch.Feature.Mode#NONE`）に
なっていたこと。フィールドの出所は「コンストラクタ注入されたフィールドの表」を引いて
具象型を求めるためのもので、列挙定数はその表に載らないため値が経路に届かなかった。

列挙定数は「値」なので、`V:` として持つことにした（`OriginTracker.variableOriginOf`）。
`F:` のままでも具象型は決まらないので失うものは無く、実測でも既存ケースの出力は変わっていない。
値は宣言型で修飾する（`V:fx.branch.Feature.Mode.NONE`）。単純名 `NONE` だけだと、
別の列挙型の同名定数や `"NONE"` という文字列と一致してしまうため。

### Q16. 条件が複数あるとき、注記にはどれが出るか

**最初に成立しないと分かった条件が1つだけ**出る。アトムは呼び出し箇所から外側へ
親を辿って集めるので、最も内側の条件が先に来る。

```java
void nested(boolean a, boolean b, String name) {
    if (a && b) {
        if (!"skip".equals(name)) { deep1(); }   // b=false でも name="skip" でも呼ばれない
    }
}
```

`nested(true, false, "skip")` の経路では、内側の `"skip".equals(name)` が理由として出る
（`b` も成立していない）。理由は「なぜ打ち切ったか」を1つ示せば読み手が追えるので、
全部を並べて注記を長くはしていない。

### Q17. 除外パッケージ（`exclude.packages`）と重なったら

除外されたノードは行にせず、その先を辿り続ける仕組みがある。
この経路で呼ばれないと分かった呼び出しは、除外ノードの先も辿らない。
「呼ばれない」の方が強い判断であり、辿ると呼ばれないはずの階層が
除外ノード経由で出力されてしまうため。

## 確認

`test/demo/src/fx/branch/Feature.java` を回帰テストの demo に追加し、
`whole` / `entry` ケースの期待出力で次を固定した。

- `run(false)` の経路で `report()` が「条件「verbose」が成立しない（呼び出し元から渡された第1引数 = false）」
  として打ち切られ、`summary()` は普通に辿られる
- `static final boolean DEBUG = false` の中の `dump()` が「定数 = false」で打ち切られる
- `mode("full")` の経路で `"light".equals(name)` 側が打ち切られる
- `pick(2)` の経路で `case 1` と `default` が打ち切られ、`case 2` だけ辿られる
- `select(Mode.NONE)` の経路で `case FULL` と `mode == Mode.FULL` が打ち切られ、
  `case LIGHT, NONE` だけ辿られる（列挙定数の判定）

打ち切った件数は実行ログにも出る（`条件分岐の静的解析で「その経路では呼ばれない」と判定して打ち切り: N 件`）。
