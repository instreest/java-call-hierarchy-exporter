# 実装QA — データフロー解析（Issue #17 / #18）

ファクトリメソッドの戻り値（#17）と、呼び出し元から渡された引数（#18）から
具象クラスを特定する機能を実装したときに、迷った点とその判断を残します。

判断の軸は一貫して **「絞れないことより、間違って絞ることの方が有害」** です。
このツールの出力は改修時の影響調査に使われるため、
「候補が多くて絞れなかった」は追加調査で済みますが、
「1つに絞ったが実は違った」は調査対象の取りこぼしに直結します。

---

## Q1. ラムダ式の中の `return` は、囲みメソッドの戻り値か

**いいえ。ラムダ自身の戻り値です。**

このツールは以前から「ラムダ式の中の**呼び出し**は囲みメソッドに帰属させる」
方針を採っています（ソース上そこに書かれているため）。同じ考えで `return` も
囲みメソッドのものとして扱うと、次のコードで壊れます。

```java
Dao create() {
    list.forEach(x -> { ... });
    return new UserDao();
}

Supplier<Dao> supplier() {
    return () -> { return new OrderDao(); };   // ← これは Supplier の戻り値
}
```

`supplier()` の戻り値を `OrderDao` と記録すると、`supplier().get()` の解決を
誤ります（実際に返るのは `Supplier` の実装）。ラムダの入れ子の深さを数えて、
0 のときだけ R行を記録しています。

匿名クラスのメソッドがラムダの中に書かれることもあるため、
`MethodDeclaration` に入るときに深さを一旦0に戻し、抜けるときに復元しています。

## Q2. 追跡できなかった `return` を記録する必要があるか

**あります。むしろこれが要です。**

最初は「追跡できた return だけ記録すれば十分」と考えましたが、それでは
次のメソッドを `UserDao` を返すと決め打ちしてしまいます。

```java
Dao create(boolean useCache) {
    if (useCache) { return cache.get(); }   // 追跡できない
    return new UserDao();                    // 追跡できる
}
```

そのため「1つでも追跡できない return があれば、そのメソッドの戻り値は
特定しない」という判定にし、追跡できない return も `U` としてキャッシュに
書いています。

ただし **全ての return が `U` のメソッドは行そのものを書きません。**
判定に寄与しない（記録が無い＝特定しない、と同じ結論）うえ、
return を持つメソッドは大量にあるためキャッシュだけが膨らみます。

## Q3. 変数の出所を「走査しながら」作ってよいか

**いけません。本体を先読みしてから作ります。**

ASTの走査順（≒ソース順）に「変数 -> 出所」の表を作ると、次で誤ります。

```java
Dao d = new UserDao();
for (int i = 0; i < n; i++) {
    d.select();        // 走査時点では d は UserDao に見える
    d = new OrderDao(); // 2周目以降は OrderDao
}
```

メソッド本体に入る前に1回だけ先読みし、**同じ変数に出所の違う代入が複数あれば
`U`（不明）に倒す**ことで、フロー非依存・安全側に寄せています。
段2の `LOCAL_NEW` / `LOCAL_NEW_MULTI` と同じ考え方です。

先読みは1回だけなので、ローカル変数どうしの別名付け
（`Dao b = a;` で `a` が `b` より後ろで宣言されている場合）は追えません。
これは `U` に倒れるだけなので、実害は「解決できない」に留まります。

## Q4. 「解析するのは必要な場合のみ」をどう担保したか

3か所で絞っています。

| 場所 | 絞り方 |
|---|---|
| 呼び出しの解決 | CHAで**候補が複数になった**呼び出しだけデータフローを試す。1つに定まっている呼び出しでは何もしない |
| 経路を降りるとき | 呼び出し先が「引数をレシーバとして使う」か「引数をそのまま次へ渡す」メソッドのときだけ、引数の環境を作る（`usesParameters`）。それ以外は `null` を渡して以降の深さでも何もしない |
| ファクトリの戻り値 | 経路に依存しないのでメソッド単位でメモ化する。同じファクトリを何度呼んでも解析は1回 |

`usesParameters` はメソッド単位の `boolean[]` で、グラフ構築後に全エッジを
1回走査して作ります。O(エッジ数) を1回だけです。

## Q5. 実測すると性能はどうなったか

**遅くなるどころか速くなりました。**

40実装あるインターフェースを引数で受け渡す合成プロジェクト（841ファイル）での実測:

| | 所要時間（キャッシュ再利用時） | 出力行数 |
|---|---|---|
| データフローあり | 0.65〜0.70秒 | 19,200 |
| データフローなし | 1.01〜1.29秒 | 100,800 |

具象クラスが1つに定まると、CHAの候補数ぶんの枝分かれが消えるためです。
探索の分岐が減る効果が、解析コストを上回りました。

とはいえ全てのプロジェクトでこうなる保証はないので、
`dataflow.enabled=false` で丸ごと止められるようにしてあります。

## Q6. 経路依存の結果をキャッシュ・メモ化できるか

**引数由来（#18）はできません。ファクトリ由来（#17）はできます。**

```java
void rootA() { shared(new UserDao()); }
void rootB() { shared(new OrderDao()); }
void shared(Dao dao) { dao.select(); }
```

`shared` の中の `dao.select()` は、`rootA` から来たなら `UserDao.select`、
`rootB` から来たなら `OrderDao.select` です。**同じ呼び出し箇所でも経路が違えば
答えが違う**ので、エッジ単位でメモ化できません。これは実装の都合ではなく、
「起点からの経路のデータフローを解析する」という要件そのものの帰結です。

そのため実装は次のように分けています。

- **ファクトリ由来** … `resolveEdge()` の中（段4）。メソッド単位でメモ化。
  経路に依存しないので `methods.csv` の集計にもそのまま効く
- **引数由来** … `StreamingTreeWalker` の中。現在の経路の引数の環境
  （`pathParamTypes[深さ]`）を使う。深さぶんの配列だけなのでメモリ設計を崩さない

## Q7. 「呼び出し元の候補から遡らない」とは具体的に何をしないことか

要件で明示されていた点です。やっていないのは次です。

```java
void shared(Dao dao) { dao.select(); }
```

`shared` を単体で見て「`shared` を呼んでいる箇所を全部集めると、引数は
`UserDao` か `OrderDao` のどちらかだ」という推論は**しません**。

これは (a) 呼び出し元が多いと候補が発散し、(b) 実際には通らない経路の型が
混ざり、(c) 結果が経路と対応しなくなるためです。
やっているのは逆向きで、**起点から降りていく途中で、実際に渡している値を
前向きに持ち回るだけ**です。1本の経路に対して答えは決定的に決まります。

## Q8. ファクトリの戻り値型がインターフェースで、ファクトリ自身も
インターフェース越しに呼ばれている場合

**解決しません（AsIs）。**

```java
interface DaoFactory { Dao create(); }
factory.create().select();   // factory の具象クラスが分からない
```

`create()` の宣言はインターフェース側で本体を持たないため R行がありません。
「まず `factory` をCHAで絞り、絞れたらその実装の `create()` の return を見る」
という多段解決も考えられますが、段数を増やすと
「どの段の推測が結論に効いたか」が追えなくなるため見送りました。
実装ごとに違う型を返す可能性もあり、1つに絞れる保証もありません。

## Q9. ファクトリが引数をそのまま返す場合

**解決しません（AsIs）。**

```java
Dao pick(Dao a, Dao b) { return flag ? a : b; }
```

戻り値の出所が「そのメソッドの引数」になるケースです。原理的には
ファクトリ呼び出し側の実引数を見れば追えますが、レシーバ式として現れた
メソッド呼び出しの**実引数までは記録していない**ため、現状は追えません。
出所としては `A:位置` を記録しているので、必要になれば拡張できます。

## Q10. 具象クラスが分かった後、メソッドの実装をどう探すか

**その型から親を辿ります。**

```java
abstract class AbstractDao { public void select() { ... } }
class UserDao extends AbstractDao { }

DaoFactory.createUser().select();   // createUser は UserDao を返す
```

`UserDao#select()` という宣言は存在しないので、型名だけで引くと見つかりません。
親クラスへ幅優先で辿り、本体を持つ最初の実装を採ります。
これまで型階層は「親 -> 子」の向きだけ持っていたので、
「子 -> 親」の向きも持つようにしました。

## Q11. 具象クラスが宣言型と同じだった場合、「解決した」と言うか

**言います。**

ファクトリが返す型が、たまたま呼び出しの宣言型そのものだった場合、
結論としては宣言型のままです。しかし「CHAでは候補が複数あったが、
データフローで1つに定まった」という事実は利用者にとって意味があるので、
`解決:DATAFLOW_FACTORY` の注記を出します。
注記が無いと「候補が複数のまま出力された行」と区別が付きません。

## Q12. フィールド変数はどこまで追うのか

**コンストラクタで確定するフィールドだけ追います。**

```java
class Service {
    private final Dao dao;
    Service(Dao dao) { this.dao = dao; }   // 生成時に確定する -> 追える
    void exec() { dao.select(); }
}

class Other {
    private Dao dao;                        // DI/setterで後から入る -> 追えない
    void setDao(Dao d) { this.dao = d; }
    void exec() { dao.select(); }
}
```

前者は「`new Service(new UserDaoImpl())` と書いた経路なら、`dao` は必ず
`UserDaoImpl`」と言い切れます。**引数（#18）の仕組みを1段延ばしただけ**です。
後者は代入がソースの外（DIコンテナの設定）にあり、同じ仕組みでは扱えません。

「言い切れる」の条件は Q13 に書いた4つです。1つでも崩れたら
`CHA候補N件（未展開）: フィールド変数` に戻します。

## Q13. 「コンストラクタで確定する」と言い切る条件は何か

次の4つを全部満たすときだけです。1つでも崩れたら追跡しません。

| # | 条件 | 崩れる例 |
|---|---|---|
| a | `private` または `final` | `Dao dao;`（パッケージ内の他クラスから代入できる） |
| b | 代入がコンストラクタ本体かフィールド初期化子の中だけ | `void setDao(Dao d) { this.dao = d; }` |
| c | 初期化子を持つか、`this(...)`委譲していない**全ての**コンストラクタで代入される | 引数なしコンストラクタが代入しない |
| d | それらの代入の出所が全て一致する | コンストラクタごとに違うものを入れる |

**(c) が要点です。** 「あるコンストラクタでは代入するが、別のコンストラクタでは
代入しない」型は、後者の経路で中身が別物になります。
`new Service(dao)` と書かれた経路だけを見て決め打ちすると、
`new Service()` の経路を取りこぼします。

判定は1ファイルの中で完結します。(a) の条件があるおかげで、
そのフィールドへの代入がこのファイルの外に存在しないと言えるためです。

## Q14. 親クラスのフィールドはどうなるか

**追いません（AsIs）。**

```java
class Base {
    private final Dao dao;
    Base(Dao dao) { this.dao = dao; }
    void exec() { dao.select(); }
}
class Sub extends Base {
    Sub(Dao dao) { super(dao); }
}

new Sub(new UserDao()).exec();   // 解決しない
```

`Base.dao` の出所は「`Base` のコンストラクタの0番目の引数」ですが、
経路上で分かっているのは「`Sub` のコンストラクタに何を渡したか」です。
`super(dao)` を通じた受け渡しは追跡していないため、両者は繋がりません。

繋げないだけでなく、**繋げてはいけません。** `Sub` の実引数を `Base` の
フィールドに当ててしまうと、引数の順番が違う場合に別の型を割り当てます。
そのため経路の環境には「どの型のコンストラクタ実引数か」を必ず持たせ、
フィールドの宣言型と一致しなければ使わないようにしています。

## Q15. 文字列のクラス名でインスタンス化するファクトリは追えるか

**追えます。** 次の形に対応しています。

```java
static Dao create(String className) {
    return (Dao) Class.forName(className).newInstance();
}
static Dao createModern(String className) {
    return (Dao) Class.forName(className).getDeclaredConstructor().newInstance();
}
...
create("jp.co.xxx.UserDaoImpl").select();   // -> UserDaoImpl.select
create(Names.USER_DAO).select();            // 定数フィールドでも可
```

仕組みは2つの追加で成り立っています。

1. **戻り値の出所に「呼び出し箇所依存」の形を持たせた。**
   `create` の戻り値は `C:0`（＝0番目の引数が名前で指す型）と記録します。
   具象型ではないので、この時点では確定しません。
2. **メソッド呼び出しの出所に、その呼び出しの実引数も付けた。**
   `create("jp.co.xxx.UserDaoImpl")` の出所は
   `M:...#create(java.lang.String)|0=L:jp.co.xxx.UserDaoImpl` になります。

解決時に (1) の `C:0` を (2) の `0=L:...` で埋めて型名を得ます。
`static final String` のコンパイル時定数は JDT が値を教えてくれるので、
定数フィールド経由でも同じように追えます。

**得た型名がプロジェクトに存在しない場合は使いません。**
文字列の見た目だけで決めると、たまたまクラス名の形をした文字列
（設定キーなど）を型と誤認するためです。

実行時にしか決まらない文字列（`System.getProperty("dao")` など）は、
当然ながら追えません。AsIs に戻します。

## Q16. 文字列リテラルを全部記録するとどうなるか

**キャッシュが文字列で埋まります。** ログの文言・SQL・メッセージなど、
Javaのソースにある文字列リテラルの大半はクラス名ではありません。

そこで「ドットを含み、各要素が識別子で、最後の要素が英大文字で始まる」
という形だけを出所として記録しています。
誤って拾っても、解決時にその型がプロジェクトに無ければ使われないだけで
害はありません（Q15の最後）。

この絞り込みを入れても、実引数の出所を持つようになったぶん
キャッシュは1割弱増えました。所要時間の増加は数%です。

## Q17. 実質的final（effectively final）を使うと、どこがもっと絞れるか

**匿名クラス・ローカルクラスが捕捉した変数だけです。** 調べた範囲では、それ以外に
効く場所はありませんでした。順に挙げます。

| 検討した箇所 | 実質的finalで改善するか |
|---|---|
| 匿名クラス・ローカルクラスが捕捉した変数 | **する**（下記） |
| ループ内で再代入されるローカル変数 | しない。実質的finalでないので、そもそも絞ってはいけない |
| `LOCAL_NEW_MULTI`（同一メソッド内に複数の `new`） | しない。実質的finalなら代入は1回なので MULTI にならない |
| 出所が食い違ったとき `U` に倒す判定 | しない。同上の理由で食い違いが起きない |
| フィールド | しない。実質的finalは局所変数・引数の概念で、フィールドには無い。フィールドは別の4条件（7.5.4）で判定済み |
| 拡張for（`for (Dao d : list)`）の変数 | しない。反復ごとに別のインスタンスなので絞ってはいけない |

### 捕捉した変数で何が変わるか

匿名クラスのメソッドは `MethodDeclaration` なので独自のスコープを持ちます。
変数を1段しか引かないと、囲みメソッドの変数が見えず追跡が切れていました。

```java
void run() {
    Dao dao = new UserDaoImpl();
    exec(new Task() {
        public void run() { dao.select(); }   // 修正前: CHA候補N件（未展開）: ローカル変数
    });
}
```

スコープを外側へ辿るようにしました。**これが安全だと言えるのは実質的finalのおかげ**で、
捕捉できる変数は `final` か実質的finalだと言語仕様が保証しているため、捕捉後に中身が
別のインスタンスへ差し替わることがありません。囲みメソッドで分かった型がそのまま通用します。

実質的finalでない変数はそもそも捕捉できずコンパイルが通らないので、この確認は
理屈の上では冗長です。それでも `isEffectivelyFinal()` を明示的に呼んでいるのは、
**「なぜ外側の値を持ち込んでよいのか」の根拠をコードに残すため**です。

### 持ち込んでよい出所と、いけない出所

ここが実装上いちばん間違えやすい点でした。外側から持ち込めるのは
**どのメソッドから見ても同じものを指す出所**だけです。

| 出所 | 持ち込める | 理由 |
|---|---|---|
| `T:`（new された具象型） | ○ | どこから見ても同じ型 |
| `M:`（メソッドの戻り値） | ○ | 同上 |
| `A:`（引数） | × | 「**今実行しているメソッド**の第n引数」の意味。匿名クラスの `run()` に引数は無い |
| `F:`（フィールド） | × | 「**今のオブジェクト**のフィールド」の意味。匿名クラスは別のオブジェクト |

`A:` や `F:` をそのまま持ち込むと、別のフレームの値を当ててしまいます。
検証では、**同じフィールドが通常メソッドからは解決し、匿名クラスの中からは
解決しない**ことを確認しました（後者はフレームが違うため絞ってはいけない）。

捕捉された引数を追うには匿名クラスの生成箇所まで遡る必要がありますが、
それは現在の経路の持ち方（`pathParamTypes` / `pathCtorArgs` は「今の深さの
メソッド／オブジェクト」の値）では表現できないため、見送りました。

## Q18. オーバーロードはどこで区別しているか

**メソッドのキー `typeFqn#name(引数の型,...)` ひとつです。** ID化・CHAの候補探索・
出所（`M:`）・被参照の照合が、すべてこの同じキーを使っています。
引数の型は `IMethodBinding.getMethodDeclaration()` の消去（erasure）で作るので、
`List<String>` と `List<Integer>` が別物になることはありません。

検証したところ、ソース側は素のオーバーロード・可変長引数・ジェネリクス・
内部クラス引数・コンストラクタ・CHA候補との組み合わせのいずれも正しく
区別できていました。

**バイトコード側（被参照スキャン）に1件だけ不具合がありました。**
ディスクリプタ `Lov/Api$Key;` を `/` → `.` だけ変換して `ov.Api$Key` と
していたため、JDT側の `ov.Api.Key` と一致せず、**内部クラスを引数に取る
オーバーロードだけ**が未照合に落ちていました。owner には `$` → `.` の
読み替えを入れていたのに、引数の型には入れていなかったのが原因です。

修正では、まず生の形で引き、外れたら `$` を `.` に直した形でもう一度引きます。
順序が逆だと、クラス名に `$` を含む型（生成コードなど）を誤って読み替える
可能性があるためです。

この不具合は「参照している側が見つからない」という形で出るため、
影響調査では**取りこぼし**になります。未照合の件数はログに出ていたので
完全に黙って消えるわけではありませんが、件数だけでは何が漏れたか分かりません。

## 要件・前提についての提案

Issue #18 の「要件や前提を見直したほうがよい場合は提案してください」への回答です。

### 提案1: 残るのは setter/DI設定によるフィールド

コンストラクタ注入されたフィールドは追えるようになりました（Q12・Q13）。
残るのは setter 注入と、DIコンテナの設定ファイルで決まる形です。

```xml
<bean id="userService" class="jp.co.xxx.UserService">
  <property name="dao" ref="userDaoImpl"/>
</bean>
```

これは Java のソースに答えが書かれていないため、静的解析だけでは
原理的に追えません。既存の拡張ポイント `TypeCandidateProvider` で
設定ファイルを読ませるのが素直だと考えます。
（`resolver.candidate.providers` にFQNを書けば差し込めます）

同じ理由で、`super(...)` を通じた親クラスのフィールドへの受け渡し（Q14）も
未対応です。こちらはソースに書かれているので実装可能ですが、
コンストラクタ間の引数の受け渡しを追う仕組みが別途必要になります。

### 提案2: 「解決した根拠」を出力に残すかどうかを決めておきたい

現在は `解決:DATAFLOW_PARAM` のようにラベルだけを出しています。
「どの呼び出し元が、どの `new` を渡したから、そう決まったのか」までは出していません。
`call-hierarchy` 列に経路自体が出ているので追えなくはありませんが、
誤りを疑ったときの検証コストは残ります。
根拠まで出すなら列が増えるため、必要になった時点で判断したいところです。

### 提案3: 起点メソッドの引数は永久に不明である、という前提の確認

起点（`root`）のメソッドの引数には、その経路の中に渡し元がありません。
現在は「不明」として扱っています。
`entry.packages` で指定する起点がフレームワークから呼ばれるメソッド
（Action や Servlet）である場合、引数の具象型は設定ファイル側にあることが多く、
これも `TypeCandidateProvider` で外から与える形が向いています。
