# 実装QA — データフロー解析（Issue #17 / #18）

ファクトリメソッドの戻り値（#17）と、呼び出し元から渡された引数（#18）から
具象クラスを特定する機能を実装したときに、迷った点とその判断を残します。

判断の軸は一貫して **「絞れないことより、間違って絞ることの方が有害」** です。
このツールの出力は改修時の影響調査に使われるため、
「候補が多くて絞れなかった」は追加調査で済みますが、
「1つに絞ったが実は違った」は調査対象の取りこぼしに直結します。

---

## Q1. ラムダ式の中の `return` は、囲みメソッドの戻り値か

**いいえ。ラムダ自身の戻り値です。**

このツールは以前から「ラムダ式の中の**呼び出し**は囲みメソッドに帰属させる」
方針を採っています（ソース上そこに書かれているため）。同じ考えで `return` も
囲みメソッドのものとして扱うと、次のコードで壊れます。

```java
Dao create() {
    list.forEach(x -> { ... });
    return new UserDao();
}

Supplier<Dao> supplier() {
    return () -> { return new OrderDao(); };   // ← これは Supplier の戻り値
}
```

`supplier()` の戻り値を `OrderDao` と記録すると、`supplier().get()` の解決を
誤ります（実際に返るのは `Supplier` の実装）。ラムダの入れ子の深さを数えて、
0 のときだけ R行を記録しています。

匿名クラスのメソッドがラムダの中に書かれることもあるため、
`MethodDeclaration` に入るときに深さを一旦0に戻し、抜けるときに復元しています。

## Q2. 追跡できなかった `return` を記録する必要があるか

**あります。むしろこれが要です。**

最初は「追跡できた return だけ記録すれば十分」と考えましたが、それでは
次のメソッドを `UserDao` を返すと決め打ちしてしまいます。

```java
Dao create(boolean useCache) {
    if (useCache) { return cache.get(); }   // 追跡できない
    return new UserDao();                    // 追跡できる
}
```

そのため「1つでも追跡できない return があれば、そのメソッドの戻り値は
特定しない」という判定にし、追跡できない return も `U` としてキャッシュに
書いています。

ただし **全ての return が `U` のメソッドは行そのものを書きません。**
判定に寄与しない（記録が無い＝特定しない、と同じ結論）うえ、
return を持つメソッドは大量にあるためキャッシュだけが膨らみます。

## Q3. 変数の出所を「走査しながら」作ってよいか

**いけません。本体を先読みしてから作ります。**

ASTの走査順（≒ソース順）に「変数 -> 出所」の表を作ると、次で誤ります。

```java
Dao d = new UserDao();
for (int i = 0; i < n; i++) {
    d.select();        // 走査時点では d は UserDao に見える
    d = new OrderDao(); // 2周目以降は OrderDao
}
```

メソッド本体に入る前に1回だけ先読みし、**同じ変数に出所の違う代入が複数あれば
`U`（不明）に倒す**ことで、フロー非依存・安全側に寄せています。
段2の `LOCAL_NEW` / `LOCAL_NEW_MULTI` と同じ考え方です。

先読みは1回だけなので、ローカル変数どうしの別名付け
（`Dao b = a;` で `a` が `b` より後ろで宣言されている場合）は追えません。
これは `U` に倒れるだけなので、実害は「解決できない」に留まります。

## Q4. 「解析するのは必要な場合のみ」をどう担保したか

3か所で絞っています。

| 場所 | 絞り方 |
|---|---|
| 呼び出しの解決 | CHAで**候補が複数になった**呼び出しだけデータフローを試す。1つに定まっている呼び出しでは何もしない |
| 経路を降りるとき | 呼び出し先が「引数をレシーバとして使う」か「引数をそのまま次へ渡す」メソッドのときだけ、引数の環境を作る（`usesParameters`）。それ以外は `null` を渡して以降の深さでも何もしない |
| ファクトリの戻り値 | 経路に依存しないのでメソッド単位でメモ化する。同じファクトリを何度呼んでも解析は1回 |

`usesParameters` はメソッド単位の `boolean[]` で、グラフ構築後に全エッジを
1回走査して作ります。O(エッジ数) を1回だけです。

## Q5. 実測すると性能はどうなったか

**遅くなるどころか速くなりました。**

40実装あるインターフェースを引数で受け渡す合成プロジェクト（841ファイル）での実測:

| | 所要時間（キャッシュ再利用時） | 出力行数 |
|---|---|---|
| データフローあり | 0.65〜0.70秒 | 19,200 |
| データフローなし | 1.01〜1.29秒 | 100,800 |

具象クラスが1つに定まると、CHAの候補数ぶんの枝分かれが消えるためです。
探索の分岐が減る効果が、解析コストを上回りました。

とはいえ全てのプロジェクトでこうなる保証はないので、
`dataflow.enabled=false` で丸ごと止められるようにしてあります。

## Q6. 経路依存の結果をキャッシュ・メモ化できるか

**引数由来（#18）はできません。ファクトリ由来（#17）はできます。**

```java
void rootA() { shared(new UserDao()); }
void rootB() { shared(new OrderDao()); }
void shared(Dao dao) { dao.select(); }
```

`shared` の中の `dao.select()` は、`rootA` から来たなら `UserDao.select`、
`rootB` から来たなら `OrderDao.select` です。**同じ呼び出し箇所でも経路が違えば
答えが違う**ので、エッジ単位でメモ化できません。これは実装の都合ではなく、
「起点からの経路のデータフローを解析する」という要件そのものの帰結です。

そのため実装は次のように分けています。

- **ファクトリ由来** … `resolveEdge()` の中（段4）。メソッド単位でメモ化。
  経路に依存しないので `methods.csv` の集計にもそのまま効く
- **引数由来** … `StreamingTreeWalker` の中。現在の経路の引数の環境
  （`pathParamTypes[深さ]`）を使う。深さぶんの配列だけなのでメモリ設計を崩さない

## Q7. 「呼び出し元の候補から遡らない」とは具体的に何をしないことか

要件で明示されていた点です。やっていないのは次です。

```java
void shared(Dao dao) { dao.select(); }
```

`shared` を単体で見て「`shared` を呼んでいる箇所を全部集めると、引数は
`UserDao` か `OrderDao` のどちらかだ」という推論は**しません**。

これは (a) 呼び出し元が多いと候補が発散し、(b) 実際には通らない経路の型が
混ざり、(c) 結果が経路と対応しなくなるためです。
やっているのは逆向きで、**起点から降りていく途中で、実際に渡している値を
前向きに持ち回るだけ**です。1本の経路に対して答えは決定的に決まります。

## Q8. ファクトリの戻り値型がインターフェースで、ファクトリ自身も
インターフェース越しに呼ばれている場合

**解決しません（AsIs）。**

```java
interface DaoFactory { Dao create(); }
factory.create().select();   // factory の具象クラスが分からない
```

`create()` の宣言はインターフェース側で本体を持たないため R行がありません。
「まず `factory` をCHAで絞り、絞れたらその実装の `create()` の return を見る」
という多段解決も考えられますが、段数を増やすと
「どの段の推測が結論に効いたか」が追えなくなるため見送りました。
実装ごとに違う型を返す可能性もあり、1つに絞れる保証もありません。

## Q9. ファクトリが引数をそのまま返す場合

**解決しません（AsIs）。**

```java
Dao pick(Dao a, Dao b) { return flag ? a : b; }
```

戻り値の出所が「そのメソッドの引数」になるケースです。原理的には
ファクトリ呼び出し側の実引数を見れば追えますが、レシーバ式として現れた
メソッド呼び出しの**実引数までは記録していない**ため、現状は追えません。
出所としては `A:位置` を記録しているので、必要になれば拡張できます。

## Q10. 具象クラスが分かった後、メソッドの実装をどう探すか

**その型から親を辿ります。**

```java
abstract class AbstractDao { public void select() { ... } }
class UserDao extends AbstractDao { }

DaoFactory.createUser().select();   // createUser は UserDao を返す
```

`UserDao#select()` という宣言は存在しないので、型名だけで引くと見つかりません。
親クラスへ幅優先で辿り、本体を持つ最初の実装を採ります。
これまで型階層は「親 -> 子」の向きだけ持っていたので、
「子 -> 親」の向きも持つようにしました。

## Q11. 具象クラスが宣言型と同じだった場合、「解決した」と言うか

**言います。**

ファクトリが返す型が、たまたま呼び出しの宣言型そのものだった場合、
結論としては宣言型のままです。しかし「CHAでは候補が複数あったが、
データフローで1つに定まった」という事実は利用者にとって意味があるので、
`解決:DATAFLOW_FACTORY` の注記を出します。
注記が無いと「候補が複数のまま出力された行」と区別が付きません。

## Q12. フィールド変数はなぜ追わないのか

**今回のスコープ外にしました。**

```java
class Service {
    private Dao dao;              // DIで注入される
    void exec() { dao.select(); } // ← 追えない
}
```

フィールドは「いつ・どこから代入されるか」がメソッドの外にあり、
DIコンテナ経由なら Java のソースに書かれてすらいません。
経路の中で決まる引数・戻り値とは性質が違うため、同じ仕組みでは扱えません。

現状は `CHA候補N件（未展開）: フィールド変数` として、
**追えなかったこと自体は必ず出力**しています。
実プロジェクトで最も多いのはおそらくこのパターンなので、
次の課題としては筆頭だと考えます（後述の提案1）。

## 要件・前提についての提案

Issue #18 の「要件や前提を見直したほうがよい場合は提案してください」への回答です。

### 提案1: 次に効くのはフィールド（DI）経由の解決

引数・ファクトリを追えるようにしても、業務アプリで最も多い
「フィールドにDIされたDAO/サービスを呼ぶ」形は残ります（Q12）。
ここは経路のデータフローでは原理的に追えず、別の材料が要ります。

- コンストラクタで代入されるフィールドは、コンストラクタの引数を追えば決まる
  （今回の #18 の仕組みをフィールドへ延長できる）
- setter/DI設定ファイル（Spring の XML やアノテーション）は、
  既存の拡張ポイント `TypeCandidateProvider` で外から与えるのが素直

順序としては前者（コンストラクタ注入のフィールド）が費用対効果が高いと考えます。

### 提案2: 「解決した根拠」を出力に残すかどうかを決めておきたい

現在は `解決:DATAFLOW_PARAM` のようにラベルだけを出しています。
「どの呼び出し元が、どの `new` を渡したから、そう決まったのか」までは出していません。
`call-hierarchy` 列に経路自体が出ているので追えなくはありませんが、
誤りを疑ったときの検証コストは残ります。
根拠まで出すなら列が増えるため、必要になった時点で判断したいところです。

### 提案3: 起点メソッドの引数は永久に不明である、という前提の確認

起点（`root`）のメソッドの引数には、その経路の中に渡し元がありません。
現在は「不明」として扱っています。
`entry.packages` で指定する起点がフレームワークから呼ばれるメソッド
（Action や Servlet）である場合、引数の具象型は設定ファイル側にあることが多く、
これも `TypeCandidateProvider` で外から与える形が向いています。
