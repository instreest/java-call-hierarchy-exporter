# プロンプトA — 目的から設計させる版

> 生成AIに `java-call-hierarchy-exporter` と**同じ目的の道具**を作らせるプロンプトです。
> 実装の再現は狙わず、**目的・出力の契約・後から直しやすい作り**だけを渡して設計は任せます。
> 機能一式まで再現させるなら [prompt-B-detailed.md](prompt-B-detailed.md)、機能ごとの難易度と
> 省略の目安は [feature-difficulty.md](feature-difficulty.md)。
> 以下の水平線から下を、そのまま生成AIに渡してください。

---

あなたはJavaの静的解析ツールを設計・実装します。**実装方法は任せます。**
「目的」「出力の契約」「守ること」を満たし、迷ったら「後から直しやすくするための作り」に
従ってください。

## 1. 目的と使われ方

レガシーなJavaプロジェクトの改修で、**「このメソッドを直すと、どこまで影響するか」を
プロジェクト全体について一括で洗い出したい。** EclipseのGUIの呼び出し階層ビューは、コピーすると
階層が失われ、一括出力もできない。それをCSVで置き換えます。読むのはExcelのフィルタとgrep。

- **(a) 影響調査** … `callee` 列でフィルタして階層を読み、行のファイル名と行番号を
  Eclipseの「Javaスタック・トレース・コンソール」に貼ってソースへ飛ぶ
- **(b) 棚卸し** … メソッド一覧を並べ替えて、入り口・ハブ・死んだコードを見る
- **(c) 穴の把握** … 追えなかった呼び出しも行として出ているので、フィルタして数える

価値は**網羅性**です。きれいな解析結果より「ここは分からなかった」と書いてある解析結果の
ほうが役に立つので、(c)のために**追えなかったものを黙って捨てません。**

そのうえで、**出力ファイルの上で、各呼び出し階層の「確定状況」が行ごとに分かるようにしてください。**
影響調査で読み手が最初に判断するのは「この行はどこまで信じてよいか」「どこまで降りた行か」で、
それを行ごとに（フィルタして）見分けられることが、この道具の実用性を決めます。具体的には

1. **呼び出し先が1件に確定したのか、候補のままなのか**
2. **確定／候補の根拠は何か**（静的束縛、実装が1つ、CHA で絞れなかった、など）
3. **起点から何段目の行か**

の3つを、注記の文面を読まなくても**固定の列の値だけで**判別できる形にします（3.1）。

## 2. 技術の前提

Java 17 以上の普通のJavaアプリ。**Eclipse IDEは起動しません。** 解析エンジンにだけ
Eclipse JDT Core の `ASTParser` をスタンドアロンで使い、**バインディング解決を有効にする**
（誤ると呼び出しの大半が型解決失敗になります）。依存は JDT Core とその推移的依存の jar だけ。
数万ファイル規模で `OutOfMemoryError` にならないこと。動かすJDKは解析対象が使うJDK APIの版
以上に（JDTは実行中のJVMの標準クラスを解析対象のクラスパスに含めるので、古いJDKだと新しい
APIの呼び出しが型解決失敗になり、その戻り値を使う自分のコードの呼び出しまで欠けます）。

## 3. 出力の契約（ここだけは変えないでください）

CSV 2本。**BOM付きUTF-8、カンマ区切り**（Excelでダブルクリックして開ける）。
値にカンマ・ダブルクォート・改行を含むならダブルクォートで囲む。

### 3.1 呼び出し階層（`call-hierarchy.csv`）

```csv
caller,callee,resolved-by,depth,root,call-hierarchy
at a.action.OrderAction.execute(OrderAction.java:50),OrderService.findOrder,RESOLVED:NO_OVERRIDE,1,OrderAction.execute,OrderService.findOrder
at a.service.OrderService.findOrder(OrderService.java:25),OrderDao.selectById,UNEXPANDED:CHA,2,OrderAction.execute,OrderService.findOrder,OrderDao.selectById,[UNEXPANDED:CHA] 3 candidates: field
```

- `caller` … `at バイナリ名.メソッド名(ファイル名:行)` の**Javaスタックトレース形式**（行は
  **呼び出し箇所**、内部クラスは `Outer$Inner`、コンストラクタは `<init>`）。
  **この形式が(a)の核**なので崩さない
- `callee` … **クラス単純名.メソッド名**（内部クラスは `Outer.Inner`。引数は付けない）。
  行番号は混ぜない（フィルタの選択肢が散らばる）
- `resolved-by` … **その行の確定状況**。`接頭辞 + 5.2 の段のラベル` の形で、
  **どの行にも必ず値を入れる**（空欄を作らない）

  | 接頭辞 | 意味 | 例 |
  |---|---|---|
  | `RESOLVED:` | 呼び出し先が1件に定まった | `RESOLVED:STATIC_BOUND:PRIVATE`、`RESOLVED:SINGLE_IMPL` |
  | `UNEXPANDED:` | 1件に絞れず候補のまま（その先へは降りない） | `UNEXPANDED:CHA`、`UNEXPANDED:NO_IMPL` |
  | `UNRESOLVED:` | 型解決に失敗した行（下記） | `UNRESOLVED:BINDING_FAILED` |

  確定したかどうかを**接頭辞**に、その根拠を**後半**に置くのは、
  「辿り切れなかった行だけ」を、段のラベルを覚えていなくても1回のフィルタで出せるようにするため。
  段を足したときは後半のラベルが増えるだけで、読み手のフィルタは変えなくて済みます
- `depth` … 起点からの深さ（起点が `0`、その呼び出し先が `1`）。
  **`call-hierarchy` 列に並ぶノード数と必ず一致させる**（一致していれば、可変長列がどこで
  終わって注記がどこから始まるかを列数だけで判定できる）
- `root` … 起点メソッド（`クラス単純名.メソッド名`）
- `call-hierarchy` … 起点の次から現ノードまでを**1ノード1列**で展開（可変長・必ず最終列。
  ヘッダーとデータ行の列数は一致しなくてよい）
- 呼び出し1件につき1行、起点自身の行は出さない。**`new` そのものも行にしない**（「newしたこと」
  より「その中で何を呼ぶか」が知りたい）が、経路には積んでコンストラクタ内の呼び出しは出す

**「普通に辿れなかった」ことの説明は `call-hierarchy` の最後の要素に注記として足し、独立した列に
しないでください**（種類は後から増えるので、列を増やさない形に）。注記は先頭に大文字のタグを
置き（`[UNEXPANDED:*]` は「ここから先へ降りなかった」、`[EXTERNAL]` は呼び出し先が自プロジェクトの
外）、日本語の説明をその後ろに続けると grep で拾えます。
最低限 `[UNEXPANDED:CYCLE]`（循環。打ち切る）、`[UNEXPANDED:DEPTH]`（深さ上限での打ち切り）、
`[UNEXPANDED:CHA] N candidates: {reason}`（実装を1つに絞れず、候補を1件ずつ行にするが先へは降りない）の3種。

注記と `resolved-by` 列の役割は分けてください。**確定状況そのもの（どちらに転んだか・何が根拠か）は
列**に置き、注記に書くのは**列に入らないこと**だけです——打ち切りの理由（循環・深さ上限・
プロジェクト外）と、候補の件数やレシーバの由来のような「次に何を調べればよいか」。
両方を同じ判定から作り、同じ行で食い違わないようにします。
1件に確定した行に `[RESOLVED:ラベル]` のような注記を重ねて出す必要はありません（列で分かるため）。

末尾に**型解決に失敗した呼び出し**も行として足す（`root` を `(unresolved)` にし、`resolved-by` を
`UNRESOLVED:理由コード` にして区別。階層列には呼び出しの式を1つ置くので `depth` は `1`）。
件数はログにも出し、多いときは依存jarの設定漏れが疑われる旨を出す。利用者が最もはまるのが
依存jar不足で、**これがそれを検知する唯一の手掛かり**です。

### 3.2 メソッド一覧（`methods.csv`）

全メソッド1行ずつ。列は
`method, declaringType, typeKind, file, line, hasBody, inDegree, outDegree, role, reachable`
（`typeKind` は `I`/`A`/`C`、`role` は `ENTRY_CANDIDATE` / `ISOLATED` / `LEAF` / `NORMAL`）。
`inDegree` は**具象クラスに解決した後の**被呼び出し数に。宣言型で数えると、インターフェース
経由でしか呼ばれない実装がすべて0になって使えません。

## 4. 設定と既定値

**設定を書かなくても動くこと**を優先。必須は解析対象のルートだけです。

| 決めること | 既定 |
|---|---|
| ソースフォルダ | 空欄ならルートの中から推定（`.classpath`、`src/main/java` など） |
| 依存jar | jarを集めたフォルダの指定。**空でも解析は続ける**（型解決失敗として記録） |
| 起点 | 指定が無ければ「**解決後の呼び出し元が0**でソースに本体がある」メソッド全部 |
| 除外する呼び出し先 | `java.**`, `javax.**` |
| 文字コード | 入力 `UTF-8` / 出力 BOM付き`UTF-8`（変換できない文字は `?` にし例外にしない） |
| 深さ上限 / 行数上限 | 50 / 500万行 |

パターン書式は `pkg.*` / `pkg.**` / `pkg.Class` / `pkg.Class#method`。除外された呼び出し先は
行にしないが、**その先は親に繋ぎ直して辿り続ける**（`java.**` を除外しても、その先の自分の
コードは出る）。出力は実行ごとに `<日時>_<プロジェクト名>/` を作ってCSVと実行ログを残す。
行数上限は、**行を書かずに続けて通ったノード**（行にしない `new` のコンストラクタ・除外した呼び出し先の読み飛ばし。
既定の `java.**` に当たる JDK の呼び出しも）の数にも掛けてください（行を書くたびに数え直す）。行にならないノードだけで
つながる部分木（フィールド初期化子が次の型を 2 つずつ `new` する）は経路の数だけ辿られ、0 行・警告なしのまま終わらなく
なります。通った数の合計で打ち切ると、行を書き進めている普通の探索まで途中で止まるので、「続けて」の数にします。

## 5. 守ること

### 5.1 優先順位（迷ったらこの順）

1. **漏れないこと > 正確であること。** 静かに消えるのが最悪。確信が持てないものは注記付きで
   出す。**絞れないことより、誤って1つに絞ることの方が有害**（「候補が多い」は追加調査で
   済むが、「1つに絞ったが違った」は取りこぼす）
2. **落ちないこと > 完全であること。** 1ファイルの解析失敗で全体を止めず、警告してスキップ
3. **メモリが破綻しないこと。** 階層をツリーとして組み立てず、深さ優先で1行ずつ書く
4. **出力が決定的であること。** 同じ入力なら**行順まで**同じ。ファイルの並びは `/` 区切りの
   相対パス文字列で比較（`Path#compareTo` はOSで挙動が違う）
5. **循環は経路単位で見る。** 祖先に同じメソッドがあれば `[UNEXPANDED:CYCLE] returns to a method already on this path` を出して降りる。
   **グローバルな訪問済み集合は持たない**（ダイヤモンド型の依存を潰すと影響調査に使えない）

### 5.2 具象クラスの解決は「段階の並び」にする

インターフェース型の呼び出しをどの実装に繋ぐかは、**独立した判定を順に試し、先に確定した段で
打ち切る**形に。各段は「解決できたか」と「根拠のラベル」を返すだけにして、段を足すのが
1エントリの追加で済むようにします。最初はこの3段で十分です。

| 段 | ラベル | 判定 | `resolved-by` |
|---|---|---|---|
| 0 | `STATIC_BOUND:理由` | private / static / final メソッド、finalクラス、コンストラクタ、`super`。仮想ディスパッチされない | `RESOLVED:STATIC_BOUND:理由` |
| 1 | `NO_OVERRIDE` / `SINGLE_IMPL` / `NO_IMPL` | オーバーライド候補が1つに定まる。本体を持つ候補が皆無なら `NO_IMPL` | `RESOLVED:NO_OVERRIDE` / `RESOLVED:SINGLE_IMPL` / `UNEXPANDED:NO_IMPL` |
| 2 | `CHA` | 候補が複数のまま。候補を1件ずつ行にし、**先へは降りない**（候補数^深さで爆発する） | `UNEXPANDED:CHA` |

**各段が返すラベルは、そのまま `resolved-by` 列の後半になります**（3.1）。
段を足したら、その段のラベルがそのまま列の値として増えるだけにしてください。
ラベルをそのまま出すと確定したように見えてしまう段を足すときだけ、列では言い換えます
（例: 実装が1件でもラムダ／メソッド参照が同じインターフェースを実装していて、どれが走るか
未特定なら `UNEXPANDED:LAMBDA`）。

**段0の判定軸は「静的束縛か仮想呼び出しか」です。**「宣言型が具象クラスだから確定」は誤りで
（`Base b = new Derived(); b.m();` で走るのは `Derived.m`）、間違えると静かに違う階層が出ます。
候補が複数のときは**なぜ絞れなかったか**をレシーバの由来（戻り値／引数／フィールド／
ローカル変数／`this`／型名）で分類して注記に書くと、次にどの解析を足せば効くかが分かります。

具象型が分かったあとに「実際に動く実装」を探すときは、JVM と同じ順にしてください。**親クラスの連鎖を根まで先に**見て
本体を持つ宣言を採り（その型より上の `private` は継承されないので飛ばす）、無ければ親インターフェースの宣言
（`private`・`static` を除く）のうち**最も特定的なもの**を採ります（JLS 8.4.8・9.4.1、JVMS 5.4.6。クラスのメソッドは
インターフェースの `default` に常に勝つ）。親型を 1 つの一覧にして名前順の幅優先で辿ると、名前が先に並ぶ `default` や
JDK のインターフェース（`AutoCloseable`・`Iterable`）の宣言に先に当たり、動く実装が静かに落ちます。そのため型階層の
行には、親型の一覧とは別に親クラスの連鎖を残してください。親クラスから継承したメソッドが親インターフェースの
メソッドを型引数を置き換えた形で実装する関係（`class UserRepo extends BaseRepo implements Repo<User>` の
`BaseRepo.save(User)` が `Repo.save(T)` を実装する）は、その型から見たときだけ成り立つので、型ごとの事実として残します。

## 6. 後から直しやすくするための作り

この道具は「まず動くものを作り、絞れなかった呼び出しを見ながら解析を足していく」使い方を
します。最初から精度を上げるより、**足すのが安い形**にしてください。

### 6.1 3フェーズに分け、フェーズ1と2の間をファイルにする

```
フェーズ1  ソース解析   .java（1ファイルずつ）→ 中間ファイル（事実の集まり）
フェーズ2  グラフ構築   中間ファイル → メソッドをintのIDに内部化した呼び出しグラフ
フェーズ3  出力         起点ごとに深さ優先で辿りながら1行ずつCSVへ書く
```

ファイルを挟むと、2回目以降は変更のあったファイルだけ解析すればよくなり、解析結果を
ヒープに溜めずに済みます。中間ファイルはタブ区切りの行形式に（`grep` で中身を確認でき、
デバッグが段違いに楽）。`ASTParser` には100ファイルずつ程度まとめて渡すこと（1ファイルずつでは
規模に対して超線形に遅くなります）。

まとめて渡すと、一緒に渡したファイルによって JDT の答えが変わるので、**事実がバッチの組み方に依らないように**
してください（全件解析と差分更新とで一緒に渡すファイルが違い、両者の結果が食い違います）。

- 事実は、バッチのファイルをすべて JDT が解決し終えてから（最後のファイルを受け取ったところで）集める。受け取ったその場で
  型の全メソッドや注釈の既定値を問い合わせると、同じバッチの後ろのファイルの型を先に解決させ、jar のクラスが参照する
  無いクラスがあると JDT が落ちる・注釈の型のエラーを 2 回数える
- 名前の違うファイルで宣言したトップレベルの型（`Result.java` の中の `record Ok`）を持つファイルは、JDT がソースパスから
  見落とすことがあるので、どのバッチにも（事実は集めずに）一緒に渡す。`module-info.java` はほかのファイルと同じバッチに
  入れない
- JDT が途中で止まった（例外・スタックの溢れ・依存 jar に無いクラスでの打ち切り）ら、残りを 1 ファイルずつ自前で
  読み直さない。止まったファイルに関わるファイル（同じフォルダ・名前を書いた型）を添えて同じ `createASTs` で解析し直し、
  それでも止まるファイルだけを失敗として報告する（1 ファイルの失敗で全体を止めない）

中間ファイルは **1 つ**にし、ソースファイルごとのまとまり（ブロック）に構造と値の両方を入れてください。
「呼び出し階層に使う事実」と「値の追跡に使う事実」を別のファイルに分けたくなりますが、値も具象クラスの特定を
通じて出力に効くので、分けても片方だけでは出力が作れず、2 つを対に保つ仕組みだけが増えます。
ブロックの中でメソッドや値を番号で指すなら、番号はそのブロックの中だけで通じるものにします
（差分更新でブロックをそのまま書き写せるように）。値は、式の入れ子を区切り文字で 1 本の文字列に詰める形にせず、
1 つの式を 1 行（番号で参照する）にしてください。区切り文字を含む値（`";"` や `"a|b"`）で読み違えます。

### 6.2 中間ファイルには「事実」だけを入れ、「判断」は読む側に置く

- **事実** … ASTとバインディングから機械的に読み取れて、設定・出力形式・解決アルゴリズムに
  依存しないもの（宣言、修飾子、呼び出し箇所、フィールドへの代入、値の出所）
- **判断** … フィルタ、要約、推定、しきい値、文言、「使うか使わないか」の決定

見分ける問いは「**この値を変えたくなるのは、出力や解決の方針を変えるときか、Javaの意味論が
変わるときか**」。前者なら判断であり、読む側に置きます。守れば、解決の段を足す・注記を変える・
除外の仕方を変える改修で**全ファイルの再解析が起きません**（焼き込むと方針を変えるたびに
数万ファイルの再パースになります）。**ここが一番効く設計判断です。**

### 6.3 形式の版を書き、迷ったら上げる。差分は「中身」で判定する

ヘッダ行に版の文字列（と、解析結果を左右する準拠レベル・ソースの文字コード・実行 JDK・JDT の版・ソースフォルダの並び）を書き、
読むときに一致しなければキャッシュを捨てて全件解析します。JDT の版が分からないときは「一致しない」とみなします。
**書き手の変更で事実が変わりうるなら、迷わず版を上げること。** 列や意味の変更だけでなく、拾う範囲・値の
正規化・書き手が作る文言の変更も含みます。上げ忘れると古いキャッシュが互換とみなされて、再利用したファイルだけ
古い事実のまま読まれ、壊れ方が「エラー」ではなく**「静かに違う結果」**になります（実際に起きた
失敗です）。上げたときの費用は 1 回の全件解析だけです。読む側だけの変更では上げません。
**上げ忘れはテストで捕まえてください。** 決まった題材を解析した中間ファイルの中身の指紋を版と一緒に記録しておき、
版が同じなのに指紋が変われば落とします。あわせて、**版が古いキャッシュを捨てることもテストで確かめてください。**

**依存 jar とクラスフォルダも解析結果を左右します。** いちばん簡単で安全なのは、クラスパス順の一覧とそれぞれの中身の
指紋（jar は末尾の目次のエントリ名・サイズ・CRC、クラスフォルダは中の `.class` と `.java` の相対パス・サイズ・内容ハッシュ）
もヘッダの鍵に入れ、変われば全件解析にすることです（最初はこれで構いません）。影響するファイルだけを解析し直す形に
するなら（参照実装はこちら）、jar ごとにパス・中身の指紋・含まれるパッケージを中間ファイルに残し、追加・差し替え・削除・
並び替えのあったパッケージの型を依存に持つファイルを解析し直します（足した・差し替えたときは型解決に失敗していたファイルも。
変わった jar のパッケージが自分のパッケージなら、依存に何かあるファイルも。同じパッケージの型はオンデマンド import・
`java.lang` の型・完全修飾名の頭を隠すため）。以下で「jar の変化で解析し直したファイル」と書いているのは、この形にした
場合のことです。どちらの形でも、指紋は JDT と同じ読み方で作ってください（シンボリックリンクはたどる。クラスフォルダの
`.java` も JDT は読む。jar の同じ名前のエントリは後ろのものが使われるので、並べ替えても同じ名前どうしの順は残す）。

差分の判定は**パスとサイズと内容のハッシュ**で行い、**更新時刻は記録も参照もしません**（中身と
関係なく変わるので、「中身は同じなのに解析し直す」と「中身が違うのに再利用する」の両方が
起きる）。またファイル自身が変わっていなくても、**参照している型を宣言するファイルが変わって
いれば解析し直します**（呼び出し先や修飾子は他ファイルのバインディング解決に依存する）。
そのために「そのファイルの解決結果が依存する型」も事実として残してください。バインディングから名前にした型
（呼び出し先・フィールドの所有型・引数型・親型）と import の型だけでは足りません。**すべての式と型の節の型**を
1 つの決まりで入れます（AST の訪問の前処理で、式なら `resolveTypeBinding`、型の節なら `resolveBinding` の型。
型変数・ワイルドカード・交差型は上限の消去。型引数（`List<Foo>` の Foo）も入れる。`a.foos()` の型 `List<Foo>` の
Foo はソースに名前が無く、Foo の親を変えると `for (Bar b : a.foos())` の解決が変わる。型引数は深さで打ち切らず、
辿った型を覚えて 2 度目は辿らない。非 static の入れ子の型は囲む型の型引数も（`Outer<Foo>.Inner` の Foo））。
場面ごと（呼び出しの受け手・拡張 for 文・switch・throw など）に拾うと、拾い漏らしが見つかるたびに場面が増えます。

- ソースに書かれた型の名前（戻り値・throws・ローカル変数・キャストの型。呼び出しにも値にも現れない型を消すと、
  そのファイルはコンパイルエラーになる）も、`a.getB().x()` の B のようにソースに名前の無い式の型も、ラムダの目標の型も、
  アノテーションの型（`java.*` のものも。同じパッケージに足した `Override` や `Target` という名前の型が隠すため）も、
  この決まりで入ります。**解決できた呼び出しのものも**入れる
- 呼び出し先の throws の型（検査例外かどうかで、呼ぶ側のエラーが変わる）も入れる
- 呼び出しの**候補**（修飾する式・型があればその型、単純名の呼び出しと `super.m()`・`super::m` なら囲む型すべてと
  static import した型、`new` とコンストラクタ参照なら作る型、`super(...)` なら親のクラス。その型と推移的な親型
  （コンストラクタは探す型だけ）が宣言する同じ名前のメソッド・コンストラクタ。メソッド参照も同じ）の**シグネチャ**
  （引数・戻り値・throws）の型も入れる。選ばれなかった候補の型も、どの候補が選ばれるか（曖昧か）に
  効く（`x.m(null)` は `m(Y)` と `m(Z)` で曖昧だが、Z を消すと `m(Y)` に決まる。`super(null)` も同じ）のに、ソースの
  どこにも現れない。呼び出す型は型引数を付けたまま辿る（`Box<Foo>` の `put(T)` は `put(Foo)`）。`java.*` の型が宣言する
  候補も、型引数を置き換えた `java.*` でない型は入れる（`S extends ArrayList<Foo>` の `s.add(0, null)` の `add(int, Foo)`）
- ソースに書かれていないが言語仕様が「呼ぶ」と定める呼び出しも、書いた呼び出しと同じに扱う。書いていない暗黙の
  `super()`（コンストラクタを書かない型・`super(...)` を書かないコンストラクタ・匿名クラス）の候補と呼び出し先の throws の型、
  拡張 for 文の `iterator()`・try-with-resources の `close()`・レコードパターンのアクセサの結果の型と候補
- 宣言する型が**継承するメソッド**（推移的な親型が宣言するもの）の戻り値と throws の型も入れる（継承したメソッドどうしの
  突き合わせ（親クラスのメソッドがインターフェースのメソッドを実装できるか・throws の食い違い）は子の型のエラーになるが、
  子のファイルにそれらの名前は無い）
- `import static org.lib.K.*` のようにメンバーを持ち込む import は、名指す型 `org.lib.K` も入れる
- `java.*` でない型（ソースの型も jar の型も）を入れたら、その**頭**に現れる型も入れる（推移的な親型を型引数ごと。
  `java.*` の親型は型引数だけ。型引数の上限。関数型インターフェースの関数型の引数・戻り値・throws）。jar の型の
  親は型階層の行（下の「親の親」）に無いので、`l1.Mid` の親 `l2.Top` の jar が変わっても、`l1.Mid` を使うファイルを
  解析し直せない。型階層の行は消去した親しか持たないので、`Bag extends ArrayList<Foo>`・`Box<T extends Foo>`・
  `FnA { Bar run(Foo) }` の Foo・Bar の変化も、これが無いと届かない
- ただし、**JDT が解決できなかった式の中の名前（バインディングが無いか、回復して作ったもの）は入れない**でください。依存 jar が
  無いとき、式の中の `org.missing.pkg.Type.run()` の `org.missing` に JDT が回復した型を返すかは、同じバッチで先に別の
  ファイルが同じ名前を型の文脈で解決しようとしたかで変わります（JDT は回復のために作った型をバッチの中で使い回す）。
  入れると、事実がバッチの組み方で変わり、差分更新と全件解析が食い違います（型の節そのものに回復した型は、入れてよい）。
  同じ理由で、JDT が**単純名から作った無い型**（依存 jar が無いときの `Template x`。鍵が `LTemplate;` のように
  パッケージを持たない）は `getQualifiedName()` で名付けないでください。JDT はその型を、同じバッチで最初にその名前に
  失敗したファイルのパッケージに作るので、パッケージの部分がバッチで変わります。鍵から名付け、本物の型と重ならない
  印を付けます（参照実装は `?.Template`。`?` は Java の名前に使えない）

それでも依存する型を 1 段辿るだけでは見えない変化が 3 つあり、それぞれ別に拾ってください
（参照実装はどれも最初は見落とし、「差分更新とキャッシュを消した全件解析で結果が違う」になりました）。

- **前回は無かった型・見えなかった型**: 無い型の名前にはバインディングが無いので、依存に残りません。**型解決に
  失敗したファイル（エラーがある・呼び出し先の解決に失敗した）は、何かが変わった実行では名前を照合せず必ず解析し直して
  ください**（参照実装は以前、エラーに現れた名前を残して新しい型の名前と照合していましたが、何を区切りにするか・何を
  拾うか（`$`・回復した型の名前・パッケージの途中の名前）の入れ忘れがそのまま静かな取りこぼしになったのでやめました。
  費用は失敗しているファイルの数に比例するだけです）。
  同じパッケージに足したトップレベルの型はオンデマンド import と `java.lang` の型を隠すので、同じパッケージのファイルと、
  そのパッケージをオンデマンド import するファイルのうち依存を持つものを解析し直します（どの名前が隠されるかは見ない。
  型を 1 つも宣言しない `package-info.java` は自分のパッケージが分からないので、どのパッケージの新しい型にも当てる）。
  オンデマンド import したパッケージができた・無くなったときも、その import を持つファイルを解析し直します。パッケージが
  あるかは、宣言した型のパッケージだけでなくファイルの置き場所のフォルダでも数えます（JDT はフォルダで決める。下の
  パッケージだけでできたパッケージもある）。パッケージと同じ名前の型（パッケージ `a.b` があるのに足した
  パッケージ `a` のクラス `b`）ができた・無くなったら、依存する型の名前の頭の部分（`a.b.C` の `a.b`）がその型に
  当たるファイルも解析し直します。逆向き（型 `a.b` があるところにパッケージ `a.b` ができた・無くなった）は、型の
  ファイルに衝突のエラーが出る・消えるので、親のパッケージ `a` のファイルと、依存する型の名前そのもの（か頭の部分）が
  できた・無くなったパッケージ（変わった jar のパッケージも。頭の部分も）と同じファイルを解析し直します
- **型階層が変わった**（安全網）: 解析し直したファイルの型階層の行（名前で参照できる型の集合・親型・親クラスの連鎖・
  継承した実装。無名・ローカルの型は除く）が旧キャッシュと違えば、依存で選ぶのをやめて残りのファイルをすべて解析し直して
  ください。階層は「どの本体が動くか」の材料で、その変化の影響先を依存から漏れなく決められる保証が無いためです
  （新しいファイルには比べる相手が無いので、足しただけでは切り替えない。型解決に失敗しているファイルも比べない。
  エラーのあるファイルの型は JDT の回復で揺れる）
- **親の親が変わった**: 親の親に抽象メソッドやオーバーロードを足すと、子の型を使うファイルの解決結果が変わりますが、
  そのファイルの依存には子しかありません。**変わった型の部分型もすべて（推移的に）変わった型にしてください。**
  部分型は、キャッシュの型階層（型と親型の行）から索引を作って引きます（旧キャッシュのすべてのブロックと今回解析した
  ブロックの和）。jar の変化でファイルを絞って解析し直す形にしたなら、**jar の変化に触れていたファイルの型も、解析し直したら
  変わった型にしてください**（中身が同じでも、jar の親の親から継承したものが変わる）。これは「前回の依存が変わった jar に
  触れていたか」でファイルごとに決め、そのファイルを選んだ理由では決めないこと（ソースの変化にも触れていたファイルで
  連鎖を落とす）。索引に関係を足すときも、型を変わった型に
  するときも、そのたびに部分型へ広げれば、処理の順に依りません。何が変わったか（メンバーの署名など）で絞ると、
  私的メンバーによる隠蔽や `java.*` の親型の上のメンバーで取りこぼすので、絞らないでください（親の本体だけの変更でも
  部分型を使うファイルを解析し直す費用は受け入れる）
- **中身の変わっていないファイルの宣言か定数の値が変わった**: 解析し直したファイルの中身が同じでも、宣言に書いた型の
  名前の解決先（同じパッケージに足した `p.Foo` が `import q.*` の `q.Foo` を隠す）が変わると、メソッドの引数・戻り値の
  型やフィールドの型が変わります。コンパイル時定数は使う側に値が焼き込まれます。ファイルごとに**自分の宣言の指紋**
  （宣言する型（匿名・ローカルも）ごとに、型のバインディングの鍵・修飾子・直接の親型の鍵（型引数を含む）・型引数と
  その上限・インターフェースなら関数型、型が宣言するメソッド（暗黙のものも）の鍵・修飾子・可変長引数か・戻り値と引数と
  throws の型・型引数とその上限、フィールドの鍵・修飾子・型と、宣言している定数の値。継承したものは入れない）を残し、
  解析し直した結果が前回と違えば、その型を使うファイルへ連鎖させます。型の鍵には親型も型引数の上限も入らないので、
  別に入れます（`extends Base<Foo>` や `<T extends Foo>` の Foo の解決先が変わる）。中間ファイルの行から指紋を
  作ると、行に無い戻り値の型などを取りこぼします。解析し直したファイルを常に連鎖させると、参照元へ芋づる式に広がります。
  ただし sealed な型とアノテーション型を宣言するファイルは、解析し直したら指紋に依らず連鎖させてください。使う側の
  事実（switch の網羅性・キャストが成り立つか・注釈を付けられる場所と繰り返し）は、許した部分型やメタ注釈の解決先・
  `@Repeatable` の入れ物の型に依りますが、それらの名前を書いているのは宣言した側だけです。文字列の値をハッシュで持つなら、
  対になっていないサロゲートも失わない形でバイト列にしてください（UTF-8 を経ると `?` になり、違う値が同じハッシュになる）

型を宣言しているかも分からない**解析に失敗したファイル**（スタックの溢れなど）も、ほかのファイルの解決には効いています
（JDT はソースパスから読む）。痕跡を残さないと、書き換えても消しても使う側を解析し直せません。失敗した印を中間ファイルに
残し（次の実行でも必ず解析し直す）、そのファイルのパッケージの中身が変わったものとして、そのパッケージの型を使うファイルを
解析し直してください。解析のあいだにソースが書き換えられたときも、事実を黙って再利用しないよう、そのファイルを次の実行で
解析し直させます（依存するファイルは、変わった型の決まりで届く）。解析のあいだにソースを消して戻した・足して消した、
依存 jar・クラスフォルダを書き換えたときは、どのファイルがその一時的な状態を読んだか分からないので、この実行で解析した
ファイルをすべて次の実行で解析し直させます。

「差分更新の結果＝キャッシュを消した全件解析の結果（出力と中間ファイルの両方）」を、書き換えの種類ごとにテストで
確かめてください（jar の追加・差し替え・削除も含めて）。

### 6.4 穴を記録する場所と、解析を足す口を最初から作る

「絞れなかった」「型解決できなかった」を**出力とログの両方に件数付きで出す**仕組みを最初の版
から入れること。これが後の改修の課題一覧になります。無いと「何を足せば効くのか」が分かりません。

プロジェクト固有の解決（ファクトリのキーと実装の対応表、DI設定の読み取り）を本体に書かずに
済むよう、5.2 の段の1つとして**外から差し込める口**を用意すること。インターフェースを1つ定義し、
設定で実装クラス名を受け取れるようにするだけで十分です。

データフロー解析（ファクトリの戻り値・引数・コンストラクタ注入から具象型を特定）、リフレクション
解決、条件分岐による枝刈りは、**最初の版では作らず、この段として後から足してください**
（「値の出所」を事実として残しておくと楽）。被参照スキャン、依存jarの自動取得、対話モードも
独立した機能なので後回しで構いません。一方、**バイトコードだけを見る解析**（ソースの行番号が
必要）と**呼び出し元の候補を集めて遡る推論**（候補が発散し、通らない経路の型が混ざる）は
足さない方がよいものです。

## 7. 完成の確認

- **自分自身のソース**を、JDTのjarを依存に指定して解析したとき**型解決の失敗が0件**になる。
  指定を空にすると失敗件数が0でなくなり、`(unresolved)` の行がログの件数と同数出る
- 2回目の実行で全ファイルが再利用され、**出力が1回目と完全に一致する**。ヘッダの版だけを
  書き換えると、再利用せず全件解析する
- 自己再帰・相互再帰で `[UNEXPANDED:CYCLE] returns to a method already on this path` が付く。除外パッケージの中だけで相互再帰していても
  スタックオーバーフローにならない
- `caller` 列をEclipseの「Javaスタック・トレース・コンソール」に貼るとソースへ飛べる
- **全ての行に `resolved-by` の値が入っている**（空欄が無い）。`UNEXPANDED:` で始まる行だけを
  選ぶと「そこから先へ降りなかった呼び出し」の一覧になり、`UNEXPANDED:CHA` の行の呼び出し箇所
  （`caller` と `callee` の組）の数が、ログの「絞れなかった呼び出し」の件数と合う
- **全ての行で `depth` が `call-hierarchy` 列のノード数と一致する**（注記の有無に関わらず）
- 同じソースを Linux と Windows で解析して、両CSVが**行順まで**一致する
