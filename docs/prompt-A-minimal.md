# プロンプトA — 目的から設計させる版

> 生成AIに `java-call-hierarchy-exporter` と**同じ目的の道具**を作らせるプロンプトです。
> 実装の再現は狙わず、**目的・出力の契約・後から直しやすい作り**だけを渡して設計は任せます。
> 機能一式まで再現させるなら [prompt-B-detailed.md](prompt-B-detailed.md)、機能ごとの難易度と
> 省略の目安は [feature-difficulty.md](feature-difficulty.md)。
> 以下の水平線から下を、そのまま生成AIに渡してください。

---

あなたはJavaの静的解析ツールを設計・実装します。**実装方法は任せます。**
「目的」「出力の契約」「守ること」を満たし、迷ったら「後から直しやすくするための作り」に
従ってください。

## 1. 目的と使われ方

レガシーなJavaプロジェクトの改修で、**「このメソッドを直すと、どこまで影響するか」を
プロジェクト全体について一括で洗い出したい。** EclipseのGUIの呼び出し階層ビューは、コピーすると
階層が失われ、一括出力もできない。それをCSVで置き換えます。読むのはExcelのフィルタとgrep。

- **(a) 影響調査** … `callee` 列でフィルタして階層を読み、行のファイル名と行番号を
  Eclipseの「Javaスタック・トレース・コンソール」に貼ってソースへ飛ぶ
- **(b) 棚卸し** … メソッド一覧を並べ替えて、入り口・ハブ・死んだコードを見る
- **(c) 穴の把握** … 追えなかった呼び出しも行として出ているので、フィルタして数える

価値は**網羅性**です。きれいな解析結果より「ここは分からなかった」と書いてある解析結果の
ほうが役に立つので、(c)のために**追えなかったものを黙って捨てません。**

そのうえで、**出力ファイルの上で、各呼び出し階層の「確定状況」が行ごとに分かるようにしてください。**
影響調査で読み手が最初に判断するのは「この行はどこまで信じてよいか」「どこまで降りた行か」で、
それを行ごとに（フィルタして）見分けられることが、この道具の実用性を決めます。具体的には

1. **呼び出し先が1件に確定したのか、候補のままなのか**
2. **確定／候補の根拠は何か**（静的束縛、実装が1つ、CHA で絞れなかった、など）
3. **起点から何段目の行か**

の3つを、注記の文面を読まなくても**固定の列の値だけで**判別できる形にします（3.1）。

## 2. 技術の前提

Java 17 以上の普通のJavaアプリ。**Eclipse IDEは起動しません。** 解析エンジンにだけ
Eclipse JDT Core の `ASTParser` をスタンドアロンで使い、**バインディング解決を有効にする**
（誤ると呼び出しの大半が型解決失敗になります）。依存は JDT Core とその推移的依存の jar だけ。
数万ファイル規模で `OutOfMemoryError` にならないこと。動かすJDKは解析対象が使うJDK APIの版
以上に（JDTは実行中のJVMの標準クラスを解析対象のクラスパスに含めるので、古いJDKだと新しい
APIの呼び出しが型解決失敗になり、その戻り値を使う自分のコードの呼び出しまで欠けます）。

## 3. 出力の契約（ここだけは変えないでください）

CSV 2本。**BOM付きUTF-8、カンマ区切り**（Excelでダブルクリックして開ける）。
値にカンマ・ダブルクォート・改行を含むならダブルクォートで囲む。

### 3.1 呼び出し階層（`call-hierarchy.csv`）

```csv
caller,callee,level,resolved-by,root,call-hierarchy
at a.action.OrderAction.execute(OrderAction.java:50),OrderService.findOrder,1,RESOLVED:NO_OVERRIDE,OrderAction.execute,OrderService.findOrder
at a.service.OrderService.findOrder(OrderService.java:25),OrderDao.selectById,2,UNEXPANDED:CHA,OrderAction.execute,OrderService.findOrder,OrderDao.selectById,[UNEXPANDED:CHA] 候補3件: フィールド変数
```

- `caller` … `at バイナリ名.メソッド名(ファイル名:行)` の**Javaスタックトレース形式**（行は
  **呼び出し箇所**、内部クラスは `Outer$Inner`、コンストラクタは `<init>`）。
  **この形式が(a)の核**なので崩さない
- `callee` … **クラス単純名.メソッド名**（内部クラスは `Outer.Inner`。引数は付けない）。
  行番号は混ぜない（フィルタの選択肢が散らばる）
- `level` … 起点からの深さ（起点が `0`、その呼び出し先が `1`）。
  **`call-hierarchy` 列に並ぶノード数と必ず一致させる**（一致していれば、可変長列がどこで
  終わって注記がどこから始まるかを列数だけで判定できる）
- `resolved-by` … **その行の確定状況**。`接頭辞 + 5.2 の段のラベル` の形で、
  **どの行にも必ず値を入れる**（空欄を作らない）

  | 接頭辞 | 意味 | 例 |
  |---|---|---|
  | `RESOLVED:` | 呼び出し先が1件に定まった | `RESOLVED:STATIC_BOUND:PRIVATE`、`RESOLVED:SINGLE_IMPL` |
  | `UNEXPANDED:` | 1件に絞れず候補のまま（その先へは降りない） | `UNEXPANDED:CHA`、`UNEXPANDED:NO_IMPL` |
  | `UNRESOLVED:` | 型解決に失敗した行（下記） | `UNRESOLVED:BINDING_FAILED` |

  確定したかどうかを**接頭辞**に、その根拠を**後半**に置くのは、
  「辿り切れなかった行だけ」を、段のラベルを覚えていなくても1回のフィルタで出せるようにするため。
  段を足したときは後半のラベルが増えるだけで、読み手のフィルタは変えなくて済みます
- `root` … 起点メソッド（`クラス単純名.メソッド名`）
- `call-hierarchy` … 起点の次から現ノードまでを**1ノード1列**で展開（可変長・必ず最終列。
  ヘッダーとデータ行の列数は一致しなくてよい）
- 呼び出し1件につき1行、起点自身の行は出さない。**`new` そのものも行にしない**（「newしたこと」
  より「その中で何を呼ぶか」が知りたい）が、経路には積んでコンストラクタ内の呼び出しは出す

**「普通に辿れなかった」ことの説明は `call-hierarchy` の最後の要素に注記として足し、独立した列に
しないでください**（種類は後から増えるので、列を増やさない形に）。注記は先頭に大文字のタグを
置き（`[UNEXPANDED:*]` は「ここから先へ降りなかった」、`[EXTERNAL]` は呼び出し先が自プロジェクトの
外）、日本語の説明をその後ろに続けると grep で拾えます。
最低限 `[UNEXPANDED:CYCLE]`（循環。打ち切る）、`[UNEXPANDED:DEPTH]`（深さ上限での打ち切り）、
`[UNEXPANDED:CHA] 候補N件: 理由`（実装を1つに絞れず、候補を1件ずつ行にするが先へは降りない）の3種。

注記と `resolved-by` 列の役割は分けてください。**確定状況そのもの（どちらに転んだか・何が根拠か）は
列**に置き、注記に書くのは**列に入らないこと**だけです——打ち切りの理由（循環・深さ上限・
プロジェクト外）と、候補の件数やレシーバの由来のような「次に何を調べればよいか」。
両方を同じ判定から作り、同じ行で食い違わないようにします。
1件に確定した行に `[RESOLVED:ラベル]` のような注記を重ねて出す必要はありません（列で分かるため）。

末尾に**型解決に失敗した呼び出し**も行として足す（`root` を `(型解決失敗)` にし、`resolved-by` を
`UNRESOLVED:理由コード` にして区別。階層列には呼び出しの式を1つ置くので `level` は `1`）。
件数はログにも出し、多いときは依存jarの設定漏れが疑われる旨を出す。利用者が最もはまるのが
依存jar不足で、**これがそれを検知する唯一の手掛かり**です。

### 3.2 メソッド一覧（`methods.csv`）

全メソッド1行ずつ。列は
`method, declaringType, typeKind, file, line, hasBody, inDegree, outDegree, role, reachable`
（`typeKind` は `I`/`A`/`C`、`role` は `ENTRY_CANDIDATE` / `ISOLATED` / `LEAF` / `NORMAL`）。
`inDegree` は**具象クラスに解決した後の**被呼び出し数に。宣言型で数えると、インターフェース
経由でしか呼ばれない実装がすべて0になって使えません。

## 4. 設定と既定値

**設定を書かなくても動くこと**を優先。必須は解析対象のルートだけです。

| 決めること | 既定 |
|---|---|
| ソースフォルダ | 空欄ならルートの中から推定（`.classpath`、`src/main/java` など） |
| 依存jar | jarを集めたフォルダの指定。**空でも解析は続ける**（型解決失敗として記録） |
| 起点 | 指定が無ければ「**解決後の呼び出し元が0**でソースに本体がある」メソッド全部 |
| 除外する呼び出し先 | `java.**`, `javax.**` |
| 文字コード | 入力 `UTF-8` / 出力 BOM付き`UTF-8`（変換できない文字は `?` にし例外にしない） |
| 深さ上限 / 行数上限 | 50 / 500万行 |

パターン書式は `pkg.*` / `pkg.**` / `pkg.Class` / `pkg.Class#method`。除外された呼び出し先は
行にしないが、**その先は親に繋ぎ直して辿り続ける**（`java.**` を除外しても、その先の自分の
コードは出る）。出力は実行ごとに `<日時>_<プロジェクト名>/` を作ってCSVと実行ログを残す。

## 5. 守ること

### 5.1 優先順位（迷ったらこの順）

1. **漏れないこと > 正確であること。** 静かに消えるのが最悪。確信が持てないものは注記付きで
   出す。**絞れないことより、誤って1つに絞ることの方が有害**（「候補が多い」は追加調査で
   済むが、「1つに絞ったが違った」は取りこぼす）
2. **落ちないこと > 完全であること。** 1ファイルの解析失敗で全体を止めず、警告してスキップ
3. **メモリが破綻しないこと。** 階層をツリーとして組み立てず、深さ優先で1行ずつ書く
4. **出力が決定的であること。** 同じ入力なら**行順まで**同じ。ファイルの並びは `/` 区切りの
   相対パス文字列で比較（`Path#compareTo` はOSで挙動が違う）
5. **循環は経路単位で見る。** 祖先に同じメソッドがあれば `[UNEXPANDED:CYCLE] 経路上で既に呼んでいるメソッドへ戻る` を出して降りる。
   **グローバルな訪問済み集合は持たない**（ダイヤモンド型の依存を潰すと影響調査に使えない）

### 5.2 具象クラスの解決は「段階の並び」にする

インターフェース型の呼び出しをどの実装に繋ぐかは、**独立した判定を順に試し、先に確定した段で
打ち切る**形に。各段は「解決できたか」と「根拠のラベル」を返すだけにして、段を足すのが
1エントリの追加で済むようにします。最初はこの3段で十分です。

| 段 | ラベル | 判定 | `resolved-by` |
|---|---|---|---|
| 0 | `STATIC_BOUND:理由` | private / static / final メソッド、finalクラス、コンストラクタ、`super`。仮想ディスパッチされない | `RESOLVED:STATIC_BOUND:理由` |
| 1 | `NO_OVERRIDE` / `SINGLE_IMPL` / `NO_IMPL` | オーバーライド候補が1つに定まる。本体を持つ候補が皆無なら `NO_IMPL` | `RESOLVED:NO_OVERRIDE` / `RESOLVED:SINGLE_IMPL` / `UNEXPANDED:NO_IMPL` |
| 2 | `CHA` | 候補が複数のまま。候補を1件ずつ行にし、**先へは降りない**（候補数^深さで爆発する） | `UNEXPANDED:CHA` |

**各段が返すラベルは、そのまま `resolved-by` 列の後半になります**（3.1）。
段を足したら、その段のラベルがそのまま列の値として増えるだけにしてください。
ラベルをそのまま出すと確定したように見えてしまう段を足すときだけ、列では言い換えます
（例: 実装が1件でもラムダ／メソッド参照が同じインターフェースを実装していて、どれが走るか
未特定なら `UNEXPANDED:LAMBDA`）。

**段0の判定軸は「静的束縛か仮想呼び出しか」です。**「宣言型が具象クラスだから確定」は誤りで
（`Base b = new Derived(); b.m();` で走るのは `Derived.m`）、間違えると静かに違う階層が出ます。
候補が複数のときは**なぜ絞れなかったか**をレシーバの由来（戻り値／引数／フィールド／
ローカル変数／`this`／型名）で分類して注記に書くと、次にどの解析を足せば効くかが分かります。

## 6. 後から直しやすくするための作り

この道具は「まず動くものを作り、絞れなかった呼び出しを見ながら解析を足していく」使い方を
します。最初から精度を上げるより、**足すのが安い形**にしてください。

### 6.1 3フェーズに分け、フェーズ1と2の間をファイルにする

```
フェーズ1  ソース解析   .java（1ファイルずつ）→ 中間ファイル（事実の集まり）
フェーズ2  グラフ構築   中間ファイル → メソッドをintのIDに内部化した呼び出しグラフ
フェーズ3  出力         起点ごとに深さ優先で辿りながら1行ずつCSVへ書く
```

ファイルを挟むと、2回目以降は変更のあったファイルだけ解析すればよくなり、解析結果を
ヒープに溜めずに済みます。中間ファイルはタブ区切りの行形式に（`grep` で中身を確認でき、
デバッグが段違いに楽）。`ASTParser` には100ファイルずつ程度まとめて渡すこと（1ファイルずつでは
規模に対して超線形に遅くなります）。

### 6.2 中間ファイルには「事実」だけを入れ、「判断」は読む側に置く

- **事実** … ASTとバインディングから機械的に読み取れて、設定・出力形式・解決アルゴリズムに
  依存しないもの（宣言、修飾子、呼び出し箇所、フィールドへの代入、値の出所）
- **判断** … フィルタ、要約、推定、しきい値、文言、「使うか使わないか」の決定

見分ける問いは「**この値を変えたくなるのは、出力や解決の方針を変えるときか、Javaの意味論が
変わるときか**」。前者なら判断であり、読む側に置きます。守れば、解決の段を足す・注記を変える・
除外の仕方を変える改修で**全ファイルの再解析が起きません**（焼き込むと方針を変えるたびに
数万ファイルの再パースになります）。**ここが一番効く設計判断です。**

### 6.3 形式の版を書き、事実を変えたら上げる。差分は「中身」で判定する

ヘッダ行に版の文字列を書き、読むときに一致しなければキャッシュを捨てて全件解析します。
**列や事実の意味を変えたら必ず版を上げること。** 上げ忘れると古いキャッシュが互換とみなされて
列がずれたまま読まれ、壊れ方が「エラー」ではなく**「静かに違う結果」**になります（実際に起きた
失敗です）。読む側だけの変更では上げません。**版が古いキャッシュを捨てることをテストで
確かめてください。**

差分の判定は**パスとサイズと内容のハッシュ**で行い、**更新時刻は記録も参照もしません**（中身と
関係なく変わるので、「中身は同じなのに解析し直す」と「中身が違うのに再利用する」の両方が
起きる）。またファイル自身が変わっていなくても、**参照している型を宣言するファイルが変わって
いれば解析し直します**（呼び出し先や修飾子は他ファイルのバインディング解決に依存する）。
そのために「参照した型のFQN」も事実として残してください。

### 6.4 穴を記録する場所と、解析を足す口を最初から作る

「絞れなかった」「型解決できなかった」を**出力とログの両方に件数付きで出す**仕組みを最初の版
から入れること。これが後の改修の課題一覧になります。無いと「何を足せば効くのか」が分かりません。

プロジェクト固有の解決（ファクトリのキーと実装の対応表、DI設定の読み取り）を本体に書かずに
済むよう、5.2 の段の1つとして**外から差し込める口**を用意すること。インターフェースを1つ定義し、
設定で実装クラス名を受け取れるようにするだけで十分です。

データフロー解析（ファクトリの戻り値・引数・コンストラクタ注入から具象型を特定）、リフレクション
解決、条件分岐による枝刈りは、**最初の版では作らず、この段として後から足してください**
（「値の出所」を事実として残しておくと楽）。被参照スキャン、依存jarの自動取得、対話モードも
独立した機能なので後回しで構いません。一方、**バイトコードだけを見る解析**（ソースの行番号が
必要）と**呼び出し元の候補を集めて遡る推論**（候補が発散し、通らない経路の型が混ざる）は
足さない方がよいものです。

## 7. 完成の確認

- **自分自身のソース**を、JDTのjarを依存に指定して解析したとき**型解決の失敗が0件**になる。
  指定を空にすると失敗件数が0でなくなり、`(型解決失敗)` の行がログの件数と同数出る
- 2回目の実行で全ファイルが再利用され、**出力が1回目と完全に一致する**。ヘッダの版だけを
  書き換えると、再利用せず全件解析する
- 自己再帰・相互再帰で `[UNEXPANDED:CYCLE] 経路上で既に呼んでいるメソッドへ戻る` が付く。除外パッケージの中だけで相互再帰していても
  スタックオーバーフローにならない
- `caller` 列をEclipseの「Javaスタック・トレース・コンソール」に貼るとソースへ飛べる
- **全ての行に `resolved-by` の値が入っている**（空欄が無い）。`UNEXPANDED:` で始まる行だけを
  選ぶと「そこから先へ降りなかった呼び出し」の一覧になり、`UNEXPANDED:CHA` の行の呼び出し箇所
  （`caller` と `callee` の組）の数が、ログの「絞れなかった呼び出し」の件数と合う
- **全ての行で `level` が `call-hierarchy` 列のノード数と一致する**（注記の有無に関わらず）
- 同じソースを Linux と Windows で解析して、両CSVが**行順まで**一致する
