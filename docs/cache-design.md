# キャッシュファイルの設計

解析結果のキャッシュの置き場所と設計方針。
行の形式は [CacheFormat.java](../src/jche/cache/CacheFormat.java) のクラスコメント、依存 jar の変更との関係で迷った点は
[cache-dependency-jars-qa.md](cache-dependency-jars-qa.md) にある。

## キャッシュは 1 ファイル

キャッシュは `analysis-cache.tsv` の 1 ファイルで、呼び出し階層の構造（宣言・呼び出し・型階層）と、
値の追跡に使う値（値グラフ・戻り値の出所・フィールドへの代入・条件分岐）を同じファイルに持ちます。
以前は 2 ファイル（`analysis-cache.tsv` / `dataflow-cache.tsv`）に分けていましたが
（[cache-split-qa.md](cache-split-qa.md)）、値も呼び出し階層の出力に効くので分けても片方だけでは足りず、
対を保つための仕組みだけが残っていたため 1 ファイルにまとめました
（[cache-unification-qa.md](cache-unification-qa.md)）。以前の版が残した `dataflow-cache.tsv` は次の実行で消します。

ファイルの並びは次のとおりです（ブロックの中の行の並びは `F I S N G R H D O V C/U M A K J`）。

```
ヘッダ行   形式の版・ソースレベル・文字コード・実行 JDK・JDT の版・ソースフォルダの一覧（どれかが違えば丸ごと作り直す。
           ただしソースフォルダを足した・外しただけ（両方にあるフォルダの並びが同じで入れ子が無い）なら使い続ける。
           JDT の版が読めないときは ? と書き、一致しないとみなす）
L 行       依存 jar
T 行       ソース一覧の指紋と、先頭の行（ヘッダ行・L 行・T 行）の検査値
ブロック   ソースファイル 1 つにつき 1 つ。F 行（パス・サイズ・内容ハッシュ・検査値など）から次の F 行の手前まで
Z 行       ブロック数（最後まで書き終えた印）
```

- **記号表**: メソッドを指す列（宣言・呼び出し元・呼び出し先など）は、4 列（パッケージ・型・名前・引数）を
  繰り返さず、ブロックの先頭にある S 行の番号で指します。番号はブロックの中だけで通じるので、
  差分更新でブロックをまるごと書き写しても参照が壊れません。目で追うときは `jche.cache.CacheDump` で
  4 列に戻した形を出せます
- **値は値グラフのノードで持つ**: レシーバ・実引数の値、戻り値（R 行）、フィールドへの代入（J 行）は、
  ブロックの N 行（値グラフ）のノード番号で指します。呼び出しを囲む条件分岐はブロックの G 行（条件の表。
  subject もノード番号）に置き、呼び出しの行（C 行・U 行）は末尾の列でガード番号を指します。new の証拠
  （hints）は C 行・U 行の最後の列にそのまま持ちます。どの番号もブロックの中だけで通じるので、
  突き合わせはブロックの中で閉じ、ブロックをまるごと書き写しても参照が壊れません。
  読む側は、ノードを値の表（`jche.graph.ValueStore`）に取り込んで番号で引きます（文字列に組み直さないので、
  値が区切り文字を含んでも読み違えません）
- **ブロックごとの検査値**: F 行の最後の列に、F 行（検査値の列を空にした形。エラー数・未解決数などの件数も含む）と
  ブロックの残りの行の CRC32 を持ちます。差分更新は毎回ブロックごとに計算し直し、合わないブロック（書き換え・文字化け）は
  ソースが変わったブロックと同じ扱いにして、そのファイルと、そのファイルの型を使うファイルを解析し直します
  （全件解析にはしません）。先頭の行（ヘッダ行・L 行・T 行）の検査値は T 行の最後の列にあり、合わなければ
  丸ごと作り直します（L 行を信用できなければ、jar の変化を見落とすため）
- **列の符号化は 1 つの規則**: どの列も同じ規則で、タブ・改行・制御文字を `\t` `\n` `\uXXXX` のように
  符号化します。長い SQL や改行を含む文字列も、長さの上限なしに 1 行に持てます
- **型の行（`H` 行）は親クラスの連鎖も持つ**: 親型の列は親クラスとインターフェースを区別しません（読み手は名前順に
  並べ替えます）。実行時に動く実装を JVM と同じ順（親クラスの連鎖を根まで先に見て、無ければ親インターフェースの
  最も特定的な宣言。JLS 8.4.8・JVMS 5.4.6。クラスのメソッドはインターフェースの `default` に勝つ）で探せるよう、
  7 列目に親クラスの連鎖（直接の親クラスから親へ、ソース上の型に当たるまで。途中の jar のクラスも並べ、
  `java.lang.Object` は含めない）を持ちます。8 列目は、親クラスから継承したメソッドが親インターフェースのメソッドを、
  消去した引数型の違う形で実装する組（`class UserRepo extends BaseRepo implements Repo<User>` の `BaseRepo.save(User)` が
  `Repo.save(T)` を実装する）です。同じ `BaseRepo` を継承して `Repo<Order>` を実装する型では成り立たない、その型から
  見たときだけの関係なので、メソッドの上書きの行（`O` 行）ではなく型の行に持ちます
  （[jls-conformance-qa.md](jls-conformance-qa.md)）。9 列目は、その型から親型を辿って到達した jar の型の推移的な親型の組
  （`jar の型>親型`。`class MyList extends ArrayList<String>` なら `java.util.ArrayList>java.util.List` など。
  `java.lang.Object` は含めない）です。jar の型には `H` 行が無いので、読み手はこれで jar の型を経由した部分型
  （`MyList` は `List` の部分型）と、jar のインターフェースを経由した親子（最も特定的な `default` の判定）を知ります
  （[jls-conformance-qa.md](jls-conformance-qa.md) の Q38・Q39）。親型（3 列目）と親クラスの連鎖（7 列目）の解決できなかった型は
  `?.` を付けて書きます（`?.Template.Inner`。無名パッケージの本物の型と重ねない。[cache-unification-qa.md](cache-unification-qa.md) の Q135）
- 型の名前は完全修飾名で書きます。例外は、依存 jar が無いときに JDT が単純名から作った無い型（`Template x` の
  `Template`）で、`?.Template` と書きます。JDT はこの型を、同じバッチで最初にその名前の解決に失敗したファイルの
  パッケージに作るので、完全修飾名にすると一緒に解析したファイルで名前が変わるためです（`?` は Java の名前に
  使えないので、無名パッケージの本物の型 `Template` とも重なりません）
- 行の区切りは OS によらず `\n` です（どの OS で書いても同じバイト列になり、検査値も同じになる）

行の種別と列の意味、ブロックの中の行の並びは [CacheFormat.java](../src/jche/cache/CacheFormat.java) の
クラスコメントにあります。`dataflow.enabled=false` のときも値の行は書きます（読まないだけ）。

大規模なコードベースでも `OutOfMemoryError` にならないよう、4点で対策しています。

1. **解析結果をヒープに溜めない** — 1ファイル解析するたびにキャッシュへ書き出して破棄
2. **エッジをオブジェクトで持たない** — メソッドをintのIDに内部化し、CSR形式のプリミティブ配列で保持
3. **ツリーを組み立てない** — 深さ優先で辿りながら1行ずつ書き出す
4. **読み直しを減らすための索引や中間データをヒープに置かない** — キャッシュと同じフォルダの一時ファイルに置く
   （下の「1 回の実行で読む回数と一時ファイル」）

## 置き場所の決め方

キャッシュは解析対象プロジェクトごとの「サイドカー」として、このツールのプロジェクトフォルダの
`.cache/<project.root のフォルダ名>_<project.root の絶対パスの SHA-256 先頭 8 桁>/` に作ります。

```
java-call-hierarchy-exporter/
└── .cache/
    ├── myapp_3f2a9c1e/     project.root=.../myapp
    │   └── analysis-cache.tsv
    └── batch_b71e0d44/     project.root=.../batch
        └── analysis-cache.tsv
```

ツールのプロジェクトフォルダは、作業ディレクトリとその上位（次に、実行中のクラスの置き場所とその上位）から
`src/jche/CallHierarchyExporter.java` を探して決めます。リポジトリ直下で実行すれば見つかります。
見つからないときは警告を出して作業ディレクトリの `.cache/` に作ります。

`cache.folder` を指定すると、そのフォルダ（設定ファイルからの相対パス、または絶対パス）の下に
同じ形のプロジェクト別フォルダを作ります。回帰テストのようにケースごとにキャッシュを分けたいときに使います。
`cache.enabled=false` でもフェーズ 2 が読むためにキャッシュファイル自体は同じ場所に書かれます（再利用はしない）。

## キャッシュに入れるもの

キャッシュには「ASTから分かった事実」だけを入れ、判断は読む側で行います。
事実とは、宣言と修飾子、呼び出し箇所、フィールドへの代入、値の出所など、
設定や出力形式に依存しない情報です。静的束縛かどうか、コンストラクタ注入と言い切れるか、
import からの推定を呼び出し先として採用するか、といった判断はキャッシュを読む側で行うため、
出力や解決の方針を変えてもキャッシュを作り直さずに済みます。
キャッシュの版（`CacheFormat.VERSION`）は、書き手の変更で事実が変わりうるなら**迷わず上げます**
（列や意味の変更に限らず、収集範囲・値の正規化・書き手が作る文字列の文言も含む）。上げると 1 回だけ
全件解析になりますが、上げ忘れると再利用したファイルだけが古い事実のまま残り、静かに違う結果になるためです。
上げ忘れは `test/cacheversion/run.sh`（決まった題材の事実の指紋を記録と比べる検査）が捕まえます。

## 何をもって「同じファイル」とみなすか

**パスとサイズと内容の指紋**で見ます。更新時刻は記録も参照もしません。

更新時刻はソースの中身と関係なく変わります（git のチェックアウト、コピー、CI のたびに
作り直されるワークスペース）。当てにすると、中身が同じでも全件解析し直しになります。
逆に、更新時刻を復元する設定（`git restore-mtime` 相当、アーカイブの展開、`rsync -t`）では
**更新時刻もサイズも同じで中身だけ違う**ファイルができます。同じ長さの書き換え
（`"ALPHA"` → `"OMEGA"`）なら普通に起きます。このとき更新時刻を信じると、
古い解析結果をそのまま再利用してしまいます。どちらも中身を見れば起きません。

同じ見方をソース（`F` 行）、ソース一覧（`T` 行）、依存 jar とクラスフォルダ（`L` 行）に
そろえています。
サイズを先に見るのは、違えば中身も違うと分かり、ファイルを読まずに済むからです
（サイズが同じなら必ず中身を見ます）。
設計上の判断は [docs/cache-identity-qa.md](cache-identity-qa.md) にまとめています。

## 差分更新

差分更新では、サイズと内容の指紋が一致するファイルでも、そのファイルが参照している型
（キャッシュの `I` 行）を宣言するファイルが変わっていれば解析し直します。
呼び出し先やフィールドの所有型は他のファイルのバインディング解決に依存するためです。
`I` 行には、呼び出しやフィールドで名前にした型のほか、**すべての式と型の節の型**（ソースに書かれた型の名前、
呼び出しの受け手と実引数の式の型（`a.getB().x()` の B）、ラムダの目標の型、拡張 for 文・switch・throw の式の型、
アノテーションの型（`java.*` のものも。同じパッケージに足した `Override` などが隠すため）など。型変数は上限の消去で、
型引数（`List<Foo>` の Foo。内部クラスは囲む型の型引数も。深さでは打ち切らない）も）、拡張 for 文・try-with-resources・
レコードパターンの暗黙の呼び出しの結果の型、呼び出しの候補（同じ名前のメソッド・コンストラクタ。選ばれなかったものも。
書いていない暗黙の `super()` の候補も。型引数を付けたまま辿るので `Box<Foo>` の `put(T)` は Foo。`java.*` の型が宣言する
候補は、型引数を置き換えた `java.*` でない型だけ）のシグネチャ（引数・戻り値・throws・メソッドの型変数の上限。上限は
引数・戻り値・throws に現れなくても載せる。`<T extends Comparable<? super Foo>> void m()` を `x.<Bar>m()` と呼ぶと、
上限が合うかは Foo の親に依る）の型、呼び出し先の throws の型、
import 文の型（`import static org.lib.K.*` のようにメンバーを持ち込む import は、名指す型 `org.lib.K` も）、
このファイルの型が継承するメソッドの戻り値と throws の型（継承したメソッドどうしの突き合わせに効く）が載ります。
さらに、名前にした `java.*` でない型（ソースの型も jar の型も）の**頭**に現れる型（親型を型引数ごと・型引数の上限・
関数型インターフェースの関数型の引数と戻り値と throws）も載ります。`Bag extends ArrayList<Foo>`・`Box<T extends Foo>`・
`FnA { Bar run(Foo) }` の Foo・Bar は、使う側のソースにも `H` 行にも宣言の指紋にも現れないのに、Foo の親を変えると
使う側の解決が変わるためです。
JDT が解決できなかった式の中の名前（バインディングが無いか、回復して作ったもの）は載せません（同じバッチで先に
解析したファイルによって、JDT が回復した型を返したり返さなかったりするため）。型解決に失敗したファイルは、名前を
照合せず、何かが変わった実行では必ず解析し直します（下の「型解決に失敗していたファイル」）。
正確な一覧は [CacheFormat.java](../src/jche/cache/CacheFormat.java) のクラスコメントの I 行の説明にあります。

判定は**型かパッケージの単位**で行い、名前の一部（単純名・コンパイルエラーに現れた名前）は照合しません。名前を切って
照合する規則は、何を区切りにするか・何を拾うかの入れ忘れがそのまま静かな取りこぼしになったのでやめました
（[cache-unification-qa.md](cache-unification-qa.md) の Q131）。

`I` 行の依存だけでは見えない変化が 3 つあり、それぞれ次のように拾います。型解決に失敗していたファイル・解析に失敗した
ファイル・型階層の変化は別に扱います（[cache-unification-qa.md](cache-unification-qa.md) の Q43・Q54・Q77・Q83〜Q87・
Q131 と「v42 の穴探し（形式 v43）」）。

- **前回は無かった型ができた**（ファイルを足した・戻した、既存のファイルに型を書き足した）: 無い型の名前は依存に
  残らないので、前回型解決に失敗していたファイルは名前に依らず解析し直します（下の「型解決に失敗していたファイル」）。
  同じパッケージにできたトップレベルの型はオンデマンド import（`import q.*`）と `java.lang` の型を隠すので、同じパッケージの
  ファイルと、そのパッケージをオンデマンド import するファイルのうち、`I` 行に何かあるものを解析し直します（どの名前が
  隠されるかは見ない。依存 jar に同じパッケージの型ができたときも同じ）。無名クラス・ローカルクラス・入れ子の型は
  名前で隠せないので数えません。型を 1 つも宣言しないファイル（`package-info.java`）は自分のパッケージが分からないので、
  どのパッケージの新しい型にも当てます。
  オンデマンド import（`import a.*`）のパッケージができた・無くなったときも、その import を持つファイルを解析し直します
  （`a` が下のパッケージ `a.b` だけでできていると、`a.b` が無くなったときに import のエラーになる）。パッケージがあるかは、
  `H` 行のパッケージに加えてファイルの置き場所のフォルダでも数えます（JDT はパッケージがあるかをフォルダで決める）。
  パッケージと同じ名前の型（パッケージ `a.b` があるのに、パッケージ `a` にクラス `b` を足した）ができた・無くなったときは、
  `I` 行の型の名前の頭の部分（`a.b.C` の `a.b`）がその型に当たるファイルを解析し直します。逆に、型 `a.b` があるところに
  パッケージ `a.b` ができた・無くなった（jar のパッケージも）ときは、型のファイルの「パッケージと衝突する」エラーが
  出る・消えるので、親のパッケージ `a` のファイルを解析し直します。使う側も同じで、`I` 行の型の名前そのもの（か頭の部分）が、
  できた・無くなったソースのパッケージ（とその頭の部分）か、変わった jar のパッケージ・中身の分からないパッケージ（とその頭の
  部分）と同じファイルも解析し直します（`a.b.C` の解決先が型 `a.b` のメンバーからパッケージ `a.b` の型へ変わりうる。Q93）
- **親の親が変わった**: 子の `I` 行には直接の親しか無いので、変わった型の**部分型もすべて（推移的に）変わった型**に
  します。部分型は、各ブロックの `H` 行（型と親型）から作る索引で引きます（旧キャッシュのすべてのブロックと今回解析した
  ブロックの和）。親のメソッドの本体やコメントだけを
  変えたときも、部分型を使うファイルまで解析し直します（何が変わったかは見ない。以前は型の形の指紋で絞っていましたが、
  取りこぼしが続いたのでやめました。Q77）。層になった型階層の根の型（すべてのエンティティの親など）では、コメントだけの
  変更でもプロジェクトの半分を超えるファイルを解析し直すことがあります（安全側の費用として受け入れています）。jar の型の親は `H` 行に無く、`H` 行は消去した親しか持たないので、
  名前にした型の頭（親型を型引数ごと）を `I` 行に載せ、jar の変化で解析し直したファイルの型は変わった型にします
  （下の「依存 jar を変えたとき」）
- **中身の変わっていないファイルの宣言か定数の値が変わった**: 下の「宣言と定数の値が変わったとき」
- **型解決に失敗していたファイル**（`F` 行のエラー数が 0 でない、または `U` 行に BINDING_FAILED がある）: 無い型・
  見えない型の名前を依存に残せないので、何が変われば解けるかを `I` 行からは決められません。何かが変わった実行
  （変わったファイル・jar・できた／無くなったパッケージ・中身の分からないパッケージのどれかがある）では、名前を照合せず
  必ず解析し直します。連鎖させるかはほかの解析し直したファイルと同じ決まりです。何も変わっていない実行では解析し直しません。
  費用は失敗しているファイルの数に比例するので、コンパイルエラーが常態のプロジェクト（生成ソースを置かずに解析する・
  Lombok）では毎回それらを解析し直すことになります（`warnings.txt` の「コンパイルエラーがある」の項目で、ビルドしてから
  解析するよう案内します）。Doma のように生成物（`UserDaoImpl`）をソースが名指さないフレームワークでは、生成物が無くても
  エラーにならないので、この費用はかかりません
- **型階層が変わった**（安全網）: 解析し直したファイルの `H` 行のうち名前で参照できる型（無名・ローカルの型を除く）の
  集合・親型・親クラスの連鎖・継承した実装が旧キャッシュと違えば、依存で選ぶのをやめて、残りのファイルをすべて
  解析し直します。型階層は「どの本体が動くか」（選択）の材料で、その変化がどのファイルの事実に効くかを `I` 行と部分型の
  索引から漏れなく決められる保証が無いためです。親の付け替え・インターフェースの抽出・入れ子の型の追加はその実行だけ
  全件になります（本体にラムダや無名クラスを足しただけでは全件になりません。新しいファイルには比べる相手が無いので、
  足しただけでも全件になりません。型解決に失敗しているファイルも比べません。エラーのあるファイルの型は JDT の回復で揺れるため）
- **解析に失敗したファイル**（JDT のスタックが溢れた・Java のパーサが途中で止まった）: 事実は書けませんが、その型は
  JDT がソースパスから読むので、ほかのファイルの解決には効いています。どの型を宣言しているかも分からないので、
  `F` 行と空の `I` 行だけの印のブロック（内容ハッシュは空なので、次の実行でも必ず解析し直す）を書き、そのファイルの
  置き場所のパッケージを「中身の分からないパッケージ」にして、変わった jar のパッケージと同じ決まりで、そのパッケージの
  型を使うファイルを解析し直します（解析し直したファイルの型も変わった型にする）。失敗が続くあいだは、実行のたびに
  そのパッケージの型を使うファイルも解析し直します（失敗は warnings.txt の「打ち切られた」に毎回載ります）。
  失敗していたファイルを消したときも、型を宣言していなかったブロックとして同じように扱います。`package-info.java` も
  型を宣言できる（推奨されないだけ）ので同じです（型を宣言できない `module-info.java` だけを除きます）。検査値の合わない
  （壊れた）ブロックも、`H` 行が読めてもそれが本当の型か分からないので、置き場所のパッケージを中身の分からない
  パッケージにします（[cache-unification-qa.md](cache-unification-qa.md) の Q138）

フィールドの参照箇所（読み取り・書き込み、他の型のフィールドも含む）は `A` 行に残ります。
行の種別と列の意味は [src/jche/cache/CacheFormat.java](../src/jche/cache/CacheFormat.java) のクラスコメントにあります。

## 何も変わっていないとき

解析し直すファイルが 1 つも無く（変更・追加・削除・壊れたブロック・jar の変化が無い）、先頭の行（ヘッダ・`L` 行・`T` 行）も
同じなら、書き直しても同じバイト列になります。そのときはキャッシュのファイルに触らず、そのまま残します
（ログに `[cache] Nothing changed; the cache is kept as is`）。改行が CRLF のキャッシュなど、書き手の書く形でないものは
1 回だけ書き直します。`library.*` に読めない jar（zip として開けない・書きかけ・一覧を作ったあとで消えた）があると、
その jar は毎回「変わった」ものとして扱われ（指紋を作れないため）、設定を直すまで何も変えていない実行でも「変わった」
扱いになります（キャッシュを書き直し、jar が変わったときの解析し直しと検査を毎回する）。`warnings.txt` の
「その他の警告」に載る「Cannot read a dependency jar (it counts as changed every time)」の jar を直してください。

## 1 回の実行で読む回数と一時ファイル

キャッシュを先頭から最後まで読むのは、何も変わっていない実行とファイルを変えた実行で 2 回（差分更新のパス1 と
グラフの構築）、キャッシュが無い実行で 1 回（グラフの構築）です。そのほかは次の一時ファイルで補い、キャッシュを
読み直しません。

| 一時ファイル | 作るところ | 中身 |
|---|---|---|
| `analysis-cache.tsv.deps-*.tmp` | 差分更新のパス1 | 有効なブロックの依存（`I` 行）。依存での再解析の判定（パス3）はこれだけを読む |
| `analysis-cache.tsv.edges-*.tmp` | グラフの構築 | エッジの記録（1 本 34 バイト）。呼び出し元ごとの本数が分かってから、ちょうどの大きさの配列へ読み戻す |
| `analysis-cache.tsv.unresolved-*.tmp` | グラフの構築（CLI だけ） | 型解決に失敗した呼び出しの一覧（`call-hierarchy.csv` の末尾）に出す行 |
| `analysis-cache.tsv.rewrite-*.tmp` | 差分更新の終わり（解析のあいだにソースが書き換えられた・消えた・増えたとき、依存 jar・クラスフォルダが書き換えられたとき、同じプロセスの JDK が jar の前の目次を見せ続けていたときだけ） | 書き終えたキャッシュの書き直し先（書き換えられたファイルなどの内容ハッシュを空にする。下の「解析のあいだにソースや依存 jar を書き換えたとき」） |

差分更新の最後の書き写しは、有効なブロックをバイトの範囲のまま写します（行に戻さない）。
一時ファイルの名前は実行ごとに変わり（同じキャッシュのフォルダを使うほかの実行と取り違えない）、使い終われば
失敗・中止でも消します。Ctrl+C などで強制終了したときは JVM の終了フックが消し、それでも残ったものは次の実行の最初に消します。
GitHub Actions のアクションも、キャッシュのフォルダを保存する前に消します。
キャッシュ本体の一時ファイル（`analysis-cache.tsv.tmp`）だけは、中断からの引き継ぎ（次の節）のために残ります。
なぜヒープではなく一時ファイルにしたか、何も変わっていないときの条件は
[cache-unification-qa.md](cache-unification-qa.md) の Q31〜Q37 にあります。

## 同じキャッシュのフォルダを使う実行

CLI と Eclipse・VS Code のプラグインの解析サーバー、同じフォルダを使う CI のジョブなど、2 つの実行が同じキャッシュの
フォルダを同時に使うことがあります。キャッシュを読み書きするあいだ（フェーズ1 の差分更新とフェーズ2 のグラフの構築）は
フォルダの錠（`analysis-cache.tsv.lock`。OS のファイルの錠）を持ち、あとから来た実行は `[cache]` のログを 1 行出して
先の実行が終わるまで待ちます。待つのは最長 30 分で、環境変数 `JCHE_CACHE_LOCK_WAIT_SECONDS` で秒数を変えられます。
待ちきれなければ、何を待っていたかを言って実行を失敗にします（錠なしで進めない）。錠はプロセスが落ちれば OS が放すので、
錠のファイルが残っていても次の実行を止めません（中身は空で、消さなくて構いません）。錠の仕組みの無いファイルシステム（一部のネットワークドライブ）では錠なしで続け、同じフォルダを同時に使わないよう警告します。

以前は錠が無く、片方がもう片方の書きかけの一時ファイル（`analysis-cache.tsv.tmp`）を中断からの引き継ぎのつもりで
奪って本物に差し替え、呼び出しの 1 本も無い CSV が「成功」として出ることがありました。今は錠に加えて、グラフを組む側も
最後まで書き終えたキャッシュか（形式の版・最終行のブロック数）を確かめ、違えば組まずに止めます。差分更新は旧キャッシュを
最初に 1 回だけ開き、書き写しまで同じものを読みます（読んでいるあいだに大きさが変われば止めます）
（[cache-unification-qa.md](cache-unification-qa.md) の Q56）。

## 解析のあいだにソースや依存 jar を書き換えたとき

ソースの内容ハッシュは解析の前に取り、JDT はそのあとでファイルを読みます。そのあいだにソースを書き換えると、前の中身の
ハッシュと後の中身の事実が組になり、あとで元に戻すと古い事実を再利用し続けていました。今は、解析したファイルは
JDT が読んだ直後にハッシュを取り直し、書き終えたらどのソースも実行の始めの大きさと更新時刻のままかを見て、
変わったファイルは `F` 行の内容ハッシュを空にします（ログに `[cache]` で件数を出します）。次の実行はそれらのファイルと、
それらを使うファイルを解析し直します。更新時刻は実行のあいだの見張りにだけ使い、キャッシュには書きません
（[cache-unification-qa.md](cache-unification-qa.md) の Q57）。

解析のあいだにソースを消して戻した・足して消したときは、どのブロックにも痕跡が残りません。そこで書き終えたときに
ソースフォルダを歩き直し、消えた（読めない）ファイルか一覧に無かったファイルがあれば、そのブロックと、この実行で解析した
ファイル（解析に失敗したものも）のブロックの内容ハッシュを空にします。JDT がその一時的な状態を読んだかもしれないのは、
この実行で解析したファイルだけです（再利用したブロックは前の実行で作ったもの）。

依存 jar・クラスフォルダも同じです。指紋（`L` 行）は解析の前に取り、JDT はそのあとバッチごとに読みます。兄弟モジュールの
clean ビルドのように、解析のあいだに書き換えて同じ中身に戻すと、指紋は一致するのに書き換えた中身の事実が残り続けて
いました。今は解析の前に見かけ（jar は大きさ・更新時刻・ファイルの識別子、クラスフォルダは中の `.class` / `.java` の一覧と
大きさ・更新時刻。解析の前に読めなかった jar・クラスフォルダも）を覚えておき、書き終えたときに変わっていれば、この実行で
解析したファイルの内容ハッシュを空にします（どのファイルが書き換えた中身を読んだかは分からないので、解析したものすべて。
ログに `[cache]` で件数を出します）。解析サーバー（Eclipse・VS Code のプラグイン）のように同じプロセスで解析を繰り返すと、
JDK は同じ更新時刻のまま上書きされた jar の前の目次を見せ続け、JDT もそれを読みます。目次はファイルのバイトから自分で
読むので変化は分かり、JDK の目次が今の中身にそろうまで待ちます。待ちきれなければ警告し（warnings.txt に載ります）、
この実行で解析したファイルを次の実行で解析し直させます。JDK は閉じられていない `ZipFile` が持つすべての鍵（ファイルの
識別子と更新時刻。パスには依らない）で目次を共有するので、このプロセスで見た鍵ごとに指紋をすべて覚えて比べます
（更新時刻を進めてから元に戻す上書きや、同じ jar をシンボリックリンクの別のパスで読む形も。
[cache-unification-qa.md](cache-unification-qa.md) の Q136）。

残る限界: 1 回の解析の中で書き換えて戻し終え、大きさも更新時刻も元のままなら見えません（Q57 と同じ）。

## 同じクラスが 2 つのソースフォルダにあるとき

JDT は、同じ名前の型を宣言する 2 つのファイルを同じバッチで渡されると、後のほう（ソースフォルダの並びで後ろ）に
「型が重複している」コンパイルエラーを出してその型を読みません。別々のバッチならどちらも読みます。そこで、ソースフォルダからの
相対パスが同じファイル（`src1/p/Dup.java` と `src2/p/Dup.java`）は、全件解析でも差分更新でも必ず同じバッチに並べ、
片方を解析するときはもう片方も解析し直します。後のほうのファイルは warnings.txt の「ソースにコンパイルエラーがある」に
載ります。アノテーションの付いた `package-info.java`（JDT は `package-info` という型を作る）と `module-info.java` も
同じように組にします（Q66。`module-info.java` は下の「JDT に一緒に渡すファイル」のとおり、組ごと別のバッチにします）。
名前の違うファイルで同じ型を宣言している場合（public でないトップレベルの型）は、
ファイル名からは組にできません。一緒に解析したかどうかで、片方の呼び出しが出ないことも、両方が 1 つの型に
まとめられることもあり、差分更新と全件解析とで結果が変わりえます。両方を読んだときは、グラフを組むときに
「型 X が A と B の両方で宣言されている」とそのことを警告し、メソッドの宣言は先に並ぶソースフォルダのものを使います（Q68）。
（名前の違うファイルで宣言した型を持つファイルは、下のとおりどのバッチにも添えますが、添えたファイルは解析するファイルの
後ろに並ぶので、解析するファイルの宣言が読まれます。この限界は変わりません。）
ソースフォルダの並びを入れ替えるとどちらが読まれるかが変わるので、並びはキャッシュの鍵（ヘッダ行）に入っています。
フォルダを足した・外しただけなら、そのフォルダのファイルを足した・消したファイルとして扱い、キャッシュは使い続けます
（入れ子のフォルダを足した・外したときは作り直します）
（[cache-unification-qa.md](cache-unification-qa.md) の Q58・Q61・Q67）。
ソースの一覧は、JDT と同じくシンボリックリンクをたどって作ります（ソースフォルダ自体やパッケージのフォルダがリンクでも
一覧から抜けない。祖先を指すリンクの先には入りません）。

## JDT に一緒に渡すファイル（バッチ）

解析は 100 ファイルずつまとめて JDT に渡します（差分更新は解析し直すファイルだけを）。全件解析と差分更新とでは一緒に
渡すファイルが違うので、事実がバッチの組み方に依ると、差分更新の結果が全件解析と食い違います。全件解析でも、
ファイルを 1 つ足しただけで 100 件の切れ目が動いて出力が変わります。そこで次のようにしています
（[cache-unification-qa.md](cache-unification-qa.md) の「v42 の穴探し（形式 v43）」）。

- **事実は、解析するファイルをすべて JDT が解決し終えてから集めます。** JDT はファイルを 1 つずつ本体まで解決して
  渡してきます。受け取ったその場で型の全メソッドや注釈の既定値を問い合わせると、同じバッチの後ろのファイルの型を、
  どのファイルのコンパイルの中でもない状態で先に解決させてしまいます（jar のクラスが参照する無いクラスがあると JDT の
  中で例外になって一括解析が落ちる、注釈の型のエラーを 2 回数える）。受け取った AST は預かるだけにし、解析するファイルの
  最後を受け取ったところでまとめて事実を集めます。JDT はバッチの AST をもともと最後まで辿れる形で持っているので、
  ヒープはほとんど増えません
- **バッチによって見えたり見えなかったりする型のファイルは「添えるファイル」として渡します。** 名前の違うファイルで
  宣言したトップレベルの型（`Result.java` の中の `record Ok`）は、JDT がソースパスから探すときに見落とすことがあるので、
  そういうファイルを、解析するファイルの後ろに並べて渡します（事実は集めず、解析するファイルを受け取り終えたら JDT を
  止めるので本体も読ませない）。どれが当たるかをソースの中身だけで決めるため、実行のたびにソースの全体を構文だけで読みます
  （1 ファイル 1 ミリ秒を切る）。渡すのは、バッチのファイルから名前でたどって届くもの（解析するファイルは本体も含めた名前で、
  届いたファイルは本体の外の名前で閉包までたどる）だけです。JDT がその型を探すのは届くファイルの名前を解決するときだけなので、
  届かないものは付けても効きません（すべてを付けると、各ファイルが補助クラスを持つ書き方で費用が二乗で増えた。Q142）。
  事実に現れた型が届く範囲の外にあれば（jar のシグネチャがソースの型を指す）、そこから届くものを足して解析し直します。
  jar のクラスが参照するソースの入れ子の型（`app.Outer$Inner`）も、JDT は
  宣言するファイル（`app/Outer.java`）を読んでいないと見つけられないので、そういう名前が事実に残ったら、そのファイルを
  添えて解析し直します
- **解析するファイルは、どのパスでもソースの一覧の順に並べて渡します。** JDT はバッチの中を渡した順に解決し、
  解決できない型が絡む結果（戻り値の型が無いパッケージを参照するメソッドのバインディングを捨てるか・無い型を引数に
  持つ候補と継承した候補のどちらを選ぶか）はその順で変わります。差分更新の依存するファイルの一覧は旧キャッシュの
  ブロックの順（差分更新のたびに動く）だったので、全件解析（ソースの一覧の順）と食い違っていました
  （`CacheUpdater#analyzeInBatches`。[cache-unification-qa.md](cache-unification-qa.md) の Q137。順をそろえても、
  パス2 とパス3・4 が別の呼び出しであることによる違いは残ります。Q129）
- **`module-info.java` はほかのファイルと同じバッチに入れません。** JDT はソースのモジュール宣言を同じバッチにいるとき
  だけ知っているので、`import module app;` がエラーになるかがバッチで変わっていました（JDT は同じバッチにいてもこの
  import から型を解決しないので、別にしても呼び出しは失いません）
- **JDT が途中で止まったら**（スタックの溢れ・JDT の中の例外・依存 jar に無いクラスでの例外なしの打ち切り）、止まる前に
  受け取ったファイルはそれだけで 1 つのバッチとして解析し直し、止まったファイルからあとは次のどれか 1 つをして続けます。
  (1) 止まったファイルに関わるファイル（同じフォルダのファイルと、名前を書いた型のファイル）に JDT へ渡していないものが
  あれば、バッチの残りにもずっと添えて解析し直す（依存 jar に無いクラスによる打ち切りは、原因の型を同じバッチに入れれば
  起きないため。スタックの溢れでは添えても直らないので飛ばす）。(2) 1 つも受け取らないうちに止まってどのファイルか
  分からなければ、最初のファイルだけで（関わるファイルを添えて）試し、止まらなければバッチを半分に分ける。(3) 最初の
  ファイルだけでも止まったら、添えるファイルだけで JDT が止まるかを確かめ、止まれば原因のファイルをその実行の残りでは
  添えない（名前の違う副次クラスを数千段つないだファイルは、添えるだけでどのバッチも止めた。Q141）。(4) それ以外は
  止まったファイルを脇に置き、最後に 1 つだけで（関わるファイルを添えて）解析する。それでも止まれば、そのファイルだけを
  失敗として warnings.txt の「打ち切られた」に理由とともに載せます（1 ファイルの失敗で設定ごと止めない。JDT が明示的に
  投げる `AssertionError` も同じ。例外なしに止まったなら、ほかのファイルの例外を理由にせず「理由を示さずに打ち切った」と
  する。失敗したファイルの扱いは上の「差分更新」）。入れ子の型のために解析し直すファイルは、同じ名前のファイルの組ごと
  解析し直します（Q140）。以前は残りを 1 ファイルずつ自前で読み直していて、読み方も同じ名前のファイルの組の扱いもバッチと違い、1 ファイルずつではほかのファイルの型も
  見えませんでした
- **パッケージの宣言がフォルダと合わないファイル**（`src/x/Foo.java` が `package q;`）の型は、JDT がソースパスから
  見つけられず、一緒に解析したときにしか見つかりません。どのバッチにも添えると、`source.folders` が 1 段ずれているとき
  （`src/main/java` のつもりで `src`）にソースの全体を毎回添えることになるので、構文だけで読んだパッケージの宣言をフォルダと
  比べ、実行のたびに（差分更新でも同じ行で）warnings.txt の「ソースにコンパイルエラーがある」に警告するだけにしています。
  そういうファイルの型を使うファイルの事実は、バッチの組み方で変わりえます（受け入れた限界）

ほかにも、依存 jar に無いクラスがあると、JDT がどのファイルで打ち切るか・見つからないクラスのエラーをどのファイルに付けるか
（1 回の JDT の呼び出しで最初に出会ったファイルにだけ付く）がバッチで変わることがあり、そのときの `I` 行・エラーの数・
暗黙の呼び出しの解決ラベルは全件解析と違いえます。どれも warnings.txt に依存 jar の不足かコンパイルエラーとして載り、
jar を足せば起きません。循環した継承（コンパイルエラー）も、JDT がどの型で循環を断つかが一緒に解析したファイルで変わるので、
型の行・宣言の指紋・呼び出しの解決が全件解析と違いえます（循環を直せばそろいます）
（受け入れた限界。[cache-unification-qa.md](cache-unification-qa.md) の「v42 の穴探し（形式 v43）」）。

## 実行を途中で止めたとき

キャッシュは一時ファイル（`analysis-cache.tsv.tmp`）へ書いてから本物に差し替えるので、
フェーズ1（ソース解析）の途中で実行が終わっても本物は無傷です。
残った一時ファイルは次回の実行で `analysis-cache.tsv.partial` に退避され、
**そこまでに解析したファイルはパースし直さずに書き写します**（中断・CI のタイムアウト・
OOM・強制終了のどれでも効きます）。引き継ぎが終わったら退避先は消えます。

引き継ぐのは次の条件がすべて揃ったときだけです。1 つでも違えば引き継がず、
差分更新はこれまでどおり働きます。

- 形式・ソースレベル・文字コード・実行 JDK・JDT の版・ソースフォルダの一覧（ヘッダ行）が当時と同じで、
  一時ファイルの先頭の行の検査値（`T` 行の最後の列）が合う
- 依存 jar が当時から変わっていない
- **ソース一覧（パス・サイズ・内容ハッシュ）が丸ごと当時と同じ**（`T` 行）。
  呼び出し先・親型・定数の値はバインディング解決の結果なので、
  そのファイル自身が変わっていなくても、別のファイルが変わればブロックは古くなります
- そのブロックが最後まで書けている（最後の 1 ブロックは切れている可能性があるので使いません）
- そのブロックの検査値が合う（合わなければ引き継がず、ほかの変わったファイルと同じくそのファイルを解析し直します）

フェーズ2・3 まで進んでから止めた場合は、キャッシュは既に差し替わっているので、
次回は普通に再利用されます。

## 壊れたキャッシュ

キャッシュは一時ファイルへ書いてから移すので、このツール自身が半端なファイルを残すことはありません。
それでも外から壊れたファイルが来ることがあるため（GitHub Actions のキャッシュの復元、コピーの失敗、
ディスクの異常）、最終行に「ここまで書き終えた」印（`Z` 行とブロック数）を置いています。
印が無い・数が合わないキャッシュは途中で切れているとみなして丸ごと捨て、全件解析し直します。
読めないキャッシュ（文字が壊れている等）も、解析を止めずに破棄して全件解析に倒します。
どちらも理由をログに出します。

行の形を保ったまま中身だけが変わったブロック（書き換え・文字化け）は、ブロックごとの検査値
（`F` 行の最後の列）が合わないことで見分けます。そのブロックは再利用せず、ソースが変わったのと同じ扱いで、
そのファイルと、そのファイルが宣言する型（壊れたブロックの `H` 行）を使うファイルを解析し直します
（ほかのブロックはそのまま再利用します。壊れたブロックからは前回の事実の何が変わったかを言えないため）。これは利用者が対処することではないので、
`[cache]` で始まる情報のログを出すだけで、`warnings.txt` には載せません
（[cache-unification-qa.md](cache-unification-qa.md) の Q25）。

## 宣言と定数の値が変わったとき

ファイルが変わっていなくても、解析し直すと宣言が変わることがあります。宣言に書いた `Foo` が `import q.*` の `q.Foo` から、
同じパッケージに足した `p.Foo` に変わる（JLS 6.4.1）と、メソッドの引数や戻り値の型、フィールドの型が変わり、そのメソッドを
呼ぶ側のオーバーロードの選び方や式の型も変わります。解析し直したファイルを「変わった」として常に連鎖させると、
参照元へ芋づる式に広がるので、`I` 行の最後の列に**自分の宣言の指紋**を持ち、解析し直した結果が
前回の指紋と違うときだけ、その型を参照しているファイルも解析し直します。指紋の材料は、宣言する型（匿名・ローカルも）
ごとに、型のバインディングの鍵・修飾子・直接の親型の鍵（型引数を含む）・型引数とその上限・インターフェースならその
関数型（JLS 9.9。関数型インターフェースでなければ無しの印）、型が宣言するメソッド（暗黙のもの＝既定のコンストラクタ・
レコードのアクセサも）の鍵・修飾子・可変長引数か・戻り値と引数と throws の型・型引数とその上限、フィールドの鍵・修飾子・型と、
宣言している定数の値です。継承したものは入れません（親の変化は部分型の決まりで届く）。JDT の型の鍵には親型も
型引数の上限も入らないので、別に入れます（`extends Base<Foo>` や `<T extends Foo>` の Foo の解決先が変わる）。
関数型は継承した抽象メソッドから決まり、この型を目標にするラムダやどのオーバーロードが選ばれるかを変えるので入れます
（継承したものを並べるのではなく、JDT がこの型について求める値を 1 つだけ）。行（`H`・`D`・`V`）から指紋を作らないのは、
`D` 行が戻り値の型を持たない（アノテーションの付いたメソッドだけ）ためです
（[cache-unification-qa.md](cache-unification-qa.md) の Q83）。

次のファイルは、解析し直したら指紋に依らず、宣言する型を変わった型にします（連鎖させます）。

- **旧キャッシュの `I` 行が、変わった jar のパッケージか中身の分からないパッケージに触れていた
  ファイル**。jar の親の親から継承したものは、指紋にも `H` 行にも現れないためです。どの理由で解析し直すことになったか
  （ソースの変化にも触れていた・型解決に失敗していた・同じ名前のファイルの組として引き込まれた）には依らず、
  ファイルごとに決めます。以前は選ばれた理由で決めていて、ソースの側の理由が先に当たると連鎖を落とし、jar を更新した
  だけでも、そのファイルの型を使うファイルが古い呼び出し先のまま残っていました（Q84 と「v42 の穴探し（形式 v43）」）
- **sealed な型かアノテーション型を宣言するファイル**。使う側の事実（switch の網羅性、キャストと `instanceof` が
  成り立つか、注釈を付けられる場所と繰り返せるか）は、許した部分型（入れ子の sealed の先まで）の宣言や、メタ注釈
  （`@Target`）の解決先・`@Repeatable` の入れ物の型に依りますが、それらの名前を書いているのは宣言したファイルの側
  （`permits`・メタ注釈）だけです。何が変わったかを言語仕様から選んで指紋に入れる代わりに、そのファイルを解析し直したら
  使う側へ連鎖させます

中身の変わったファイル・増えたファイル・壊れたブロックのファイルは、もともと宣言する型を変わった型にします。

## 定数の値を変えたとき

コンパイル時定数（`static final` の値と、注釈のメンバの既定値）は、Java の言語仕様どおり
**使っている側のファイルに値そのものが焼き込まれます**。そのため「ファイルの事実は、
そのファイルが `I` 行に持つ型の宣言にだけ依存する」という差分更新の前提が、定数では成り立ちません
（成り立たない場合はほかに 2 つあり、上の「差分更新」の「親の親が変わった」と「前回は無かった型ができた」です）。

```
P.java   static final String KIND = "ALPHA";
X.java   static final String KIND = P.KIND;     ← "ALPHA" が焼き込まれる
C.java   if (X.KIND.equals("BETA")) { … }       ← ここにも "ALPHA" が焼き込まれる
```

C.java が参照しているのは X だけなので、P.java を変えても C.java の `I` 行には引っかかりません。
これを取りこぼさないよう、宣言している側に定数の値を `K` 行として残し、その指紋を自分の宣言の指紋（上の節）に入れます。
解析し直した結果**値が変わっていたとき**（指紋が変わったとき）だけ、その型を参照しているファイルも解析し直します
（値が変わっていなければ連鎖しないので、再解析は増えません）。差分更新は `K` 行そのものは読み直さず、I 行の最後の列の
指紋だけを比べます。長い値や行形式を壊す文字を含む値は、`K` 行ではハッシュにして持ちます。文字列のハッシュは、
対になっていないサロゲートだけが違う値も区別する形でとります（正しい文字列では UTF-8 のハッシュと同じ。UTF-8 を経ると
`?` に置き換わって同じハッシュになり、値の変化を見落としていました）。

列挙定数は値ではなく宣言型で修飾した名前（値グラフの定数のノード。`CacheDump` の表記で `V:fx.Mode.FULL`）として持つため、
この連鎖は要りません。定数の追加・削除・改名は必ず enum のソースの変更になり、
参照側の `I` 行に enum 型が載っているので、これまでどおり 1 段の依存で追随できます。

設計の判断と、行形式を壊す値（複数行の注釈の値など）の扱いは
[cache-integrity-qa.md](cache-integrity-qa.md) の Q1〜Q15 にまとめています。

## 依存 jar を変えたとき

キャッシュには解析時の依存 jar（パス・中身の指紋・含まれるパッケージ。`L` 行）も残します。
jar の指紋は、末尾の目次（セントラルディレクトリ）にある `エントリ名 / サイズ / CRC` から作ります。目次はファイルの
バイトから自分で読みます（`java.util.zip.ZipFile` は、同じプロセスの中で同じ更新時刻のまま上書きされた jar の前の目次を
返しうるため）。ただしその前に `ZipFile` で開いて閉じ、開けなければ（JDT も読めずにクラスパスから外す壊れ方）読めない jar
として警告し、毎回変わったものとして扱います（[cache-dependency-jars-qa.md](cache-dependency-jars-qa.md) の Q22）。
作り直して並びだけが変わった jar を同じと見るよう名前で並べ替えますが、同じ名前のエントリが 2 つあれば
その 2 つの順は残します（JDK と JDT は後ろのものを使うので、入れ替われば読むクラスが変わる）。jmod（`*.jmod`）は
クラスが `classes/` の下にあり、JDT はその下をパッケージとして読むので、パッケージは `classes/` を外した名前から取ります。
jar の無名パッケージ（デフォルトパッケージ）のクラスは、`<unnamed>` というパッケージとして載せます（無名パッケージの
ソースからは参照できる。`module-info.class` は除く）。
jar を展開も読み込みもしないので、大きな jar が何本あってもエントリ数に比例するだけです。
クラスフォルダ（マルチモジュールの兄弟モジュールの `target/classes` 等）は
`.class` と `.java` の `相対パス / サイズ / 内容ハッシュ` から作ります。JDT はクラスパスのフォルダの `.java` もソースとして
読み、同じ名前の `.class` より新しければ `.java` を使うので、どちらが新しいかも指紋に入れます（更新時刻そのものは
入れません）。フォルダはソースフォルダと同じくシンボリックリンクをたどって歩きます。
`library.jars` と `.classpath` の `kind="lib"` に書いたフォルダはクラスフォルダとしてそのまま JDT に渡し、中の jar は
使いません（jar を集めたフォルダとして直下の `*.jar` に展開するのは `library.folders` と `project.root` 直下の `lib` だけ。
以前は 1 件ずつの指定のフォルダも展開していて、Eclipse プラグインが渡す依存プロジェクトの出力フォルダの型がどれも
解決できませんでした。jar しか無いフォルダを 1 件ずつの指定に書いたときは警告します）。
次回の実行で jar が追加・差し替え・削除されていれば、その jar のパッケージの型を参照している
ファイルを解析し直します（クラスフォルダは中の `.class` が 1 つ変わってもフォルダのパッケージすべてを変わったとみなすので、
兄弟モジュールの `target/classes` を作り直すと、解析するソースの型がクラスパスの型に勝って結果が変わらない場合でも、
マルチモジュールのプロジェクトの大半を解析し直すことがあります。安全側の費用です）。`I` 行には名前にした型の頭（jar の型なら推移的な親型。`java.*` の親型は型引数だけ）も載るので、
`l1.Mid` だけを使うファイルも、`l1.Mid` の親 `l2.Top` の jar が変われば解析し直します。オンデマンド import
（`import org.lib.*`、メンバーを持ち込む `import static org.lib.K.*`・`import org.lib.Outer.*`）は、名指すパッケージか型の
名前の頭の部分が変わった jar のパッケージでも当てます。
旧キャッシュの `I` 行が変わった jar のパッケージに触れていたファイルは、解析し直したら
型を変わった型にします（中身が同じでも、jar の親の親から継承したものが変わりうる。その型の利用者と部分型の利用者も
解析し直す。上の「宣言と定数の値が変わったとき」のとおり、ファイルごとに決め、ほかの理由でも選ばれていたかには依らない。
[cache-unification-qa.md](cache-unification-qa.md) の Q84・Q86 と「v42 の穴探し（形式 v43）」）。
追加・差し替えのときは、前回型解決に失敗していたファイル（`F` 行のエラー数、
`U` 行の BINDING_FAILED）も解析し直します（無い型の名前は `I` 行に残らないので、パッケージでは当たらないため）。
削除だけのときは、解決できる型が増えず、失敗していた型解決が成功に変わる理由にならないので、失敗していたファイルは
解析し直しません（jar の型を使っていたファイルと、そのファイルの型を使うファイルは解析し直します）。
自分のパッケージが変わった jar のパッケージ（無名パッケージなら `<unnamed>`）にあるときは、jar の型がオンデマンド import・
`java.lang` の型・完全修飾名の頭（`a.b.C` の `a`）を隠しうるので、`I` 行に何かあればそのファイルも解析し直します
（[cache-unification-qa.md](cache-unification-qa.md) の Q54）。解析に失敗したファイルのパッケージ（中身の分からない
パッケージ）も同じ決まりで扱います。変わった jar のパッケージ（とその頭の部分）のすぐ上のパッケージのファイルも
解析し直します（jar がパッケージ `a.b` を足した・消したとき、型 `a.b` とパッケージ `a.b` が衝突するエラーが出る・消えるため）。
`L` 行の**並び順**も見ます。JDT は同名クラスをクラスパスの先勝ちで解決するので、jar の集合が
同じでも並びが変われば解決先が変わりうるためです（`pom.xml` の依存の並べ替えでも変わります）。
効くのは同じパッケージが 2 つ以上の jar にあるときだけなので、並びの変わったパッケージの型を参照している
ファイルだけを解析し直します（並びが変わっただけでは、失敗していたファイルは解析し直しません）。
「型解決できなかった呼び出しが N 件あります」と出たときに `library.folders` へ jar を足せば、
キャッシュを消さなくても次の実行で反映されます。
CHA の候補（インターフェースの実装クラス）はキャッシュせず、毎回 `H` 行から計算するので、
jar の追加で実装クラスが増えた場合も、呼び出し側のファイルを解析し直さずに反映されます
（jar の基底クラスがソースのインターフェースを実装している構成では、その子クラスの `H` 行に
インターフェースも親として記録します）。
実行する JDK を変えたときはキャッシュ全体を作り直します（JDT は実行中の JVM の標準クラスも
解析対象のクラスパスに含めるため。何が変わるかは下記 docs の Q20）。
ソースの文字コード（`source.encoding`）とソースレベル（`source.level`）も同じ理由で
1 行目の鍵に入っていて、変えるとキャッシュ全体を作り直します。
設計上の判断と限界は [docs/cache-dependency-jars-qa.md](cache-dependency-jars-qa.md) にまとめています。
