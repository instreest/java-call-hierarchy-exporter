# キャッシュファイルの設計

解析結果のキャッシュの置き場所と設計方針。
行の形式は [CacheFormat.java](../src/jche/cache/CacheFormat.java) のクラスコメント、依存 jar の変更との関係で迷った点は
[cache-dependency-jars-qa.md](cache-dependency-jars-qa.md) にある。

## キャッシュは 1 ファイル

キャッシュは `analysis-cache.tsv` の 1 ファイルで、呼び出し階層の構造（宣言・呼び出し・型階層）と、
値の追跡に使う値（値グラフ・戻り値の出所・フィールドへの代入・条件分岐）を同じファイルに持ちます。
以前は 2 ファイル（`analysis-cache.tsv` / `dataflow-cache.tsv`）に分けていましたが
（[cache-split-qa.md](cache-split-qa.md)）、値も呼び出し階層の出力に効くので分けても片方だけでは足りず、
対を保つための仕組みだけが残っていたため 1 ファイルにまとめました
（[cache-unification-qa.md](cache-unification-qa.md)）。以前の版が残した `dataflow-cache.tsv` は次の実行で消します。

ファイルの並びは次のとおりです（ブロックの中の行の並びは `F I S N G R H D O V C/U M A K J`）。

```
ヘッダ行   形式の版・ソースレベル・文字コード・実行 JDK・JDT の版・ソースフォルダの並び（どれかが違えば丸ごと作り直す。
           JDT の版が読めないときは ? と書き、一致しないとみなす）
L 行       依存 jar
T 行       ソース一覧の指紋と、先頭の行（ヘッダ行・L 行・T 行）の検査値
ブロック   ソースファイル 1 つにつき 1 つ。F 行（パス・サイズ・内容ハッシュ・検査値など）から次の F 行の手前まで
Z 行       ブロック数（最後まで書き終えた印）
```

- **記号表**: メソッドを指す列（宣言・呼び出し元・呼び出し先など）は、4 列（パッケージ・型・名前・引数）を
  繰り返さず、ブロックの先頭にある S 行の番号で指します。番号はブロックの中だけで通じるので、
  差分更新でブロックをまるごと書き写しても参照が壊れません。目で追うときは `jche.cache.CacheDump` で
  4 列に戻した形を出せます
- **値は値グラフのノードで持つ**: レシーバ・実引数の値、戻り値（R 行）、フィールドへの代入（J 行）は、
  ブロックの N 行（値グラフ）のノード番号で指します。呼び出しを囲む条件分岐はブロックの G 行（条件の表。
  subject もノード番号）に置き、呼び出しの行（C 行・U 行）は末尾の列でガード番号を指します。new の証拠
  （hints）は C 行・U 行の最後の列にそのまま持ちます。どの番号もブロックの中だけで通じるので、
  突き合わせはブロックの中で閉じ、ブロックをまるごと書き写しても参照が壊れません。
  読む側は、ノードを値の表（`jche.graph.ValueStore`）に取り込んで番号で引きます（文字列に組み直さないので、
  値が区切り文字を含んでも読み違えません）
- **ブロックごとの検査値**: F 行の最後の列に、F 行（検査値の列を空にした形。エラー数・未解決数などの件数も含む）と
  ブロックの残りの行の CRC32 を持ちます。差分更新は毎回ブロックごとに計算し直し、合わないブロック（書き換え・文字化け）は
  ソースが変わったブロックと同じ扱いにして、そのファイルと、そのファイルの型を使うファイルを解析し直します
  （全件解析にはしません）。先頭の行（ヘッダ行・L 行・T 行）の検査値は T 行の最後の列にあり、合わなければ
  丸ごと作り直します（L 行を信用できなければ、jar の変化を見落とすため）
- **列の符号化は 1 つの規則**: どの列も同じ規則で、タブ・改行・制御文字を `\t` `\n` `\uXXXX` のように
  符号化します。長い SQL や改行を含む文字列も、長さの上限なしに 1 行に持てます
- 行の区切りは OS によらず `\n` です（どの OS で書いても同じバイト列になり、検査値も同じになる）

行の種別と列の意味、ブロックの中の行の並びは [CacheFormat.java](../src/jche/cache/CacheFormat.java) の
クラスコメントにあります。`dataflow.enabled=false` のときも値の行は書きます（読まないだけ）。

大規模なコードベースでも `OutOfMemoryError` にならないよう、4点で対策しています。

1. **解析結果をヒープに溜めない** — 1ファイル解析するたびにキャッシュへ書き出して破棄
2. **エッジをオブジェクトで持たない** — メソッドをintのIDに内部化し、CSR形式のプリミティブ配列で保持
3. **ツリーを組み立てない** — 深さ優先で辿りながら1行ずつ書き出す
4. **読み直しを減らすための索引や中間データをヒープに置かない** — キャッシュと同じフォルダの一時ファイルに置く
   （下の「1 回の実行で読む回数と一時ファイル」）

## 置き場所の決め方

キャッシュは解析対象プロジェクトごとの「サイドカー」として、このツールのプロジェクトフォルダの
`.cache/<project.root のフォルダ名>_<project.root の絶対パスの SHA-256 先頭 8 桁>/` に作ります。

```
java-call-hierarchy-exporter/
└── .cache/
    ├── myapp_3f2a9c1e/     project.root=.../myapp
    │   └── analysis-cache.tsv
    └── batch_b71e0d44/     project.root=.../batch
        └── analysis-cache.tsv
```

ツールのプロジェクトフォルダは、作業ディレクトリとその上位（次に、実行中のクラスの置き場所とその上位）から
`src/jche/CallHierarchyExporter.java` を探して決めます。リポジトリ直下で実行すれば見つかります。
見つからないときは警告を出して作業ディレクトリの `.cache/` に作ります。

`cache.folder` を指定すると、そのフォルダ（設定ファイルからの相対パス、または絶対パス）の下に
同じ形のプロジェクト別フォルダを作ります。回帰テストのようにケースごとにキャッシュを分けたいときに使います。
`cache.enabled=false` でもフェーズ 2 が読むためにキャッシュファイル自体は同じ場所に書かれます（再利用はしない）。

## キャッシュに入れるもの

キャッシュには「ASTから分かった事実」だけを入れ、判断は読む側で行います。
事実とは、宣言と修飾子、呼び出し箇所、フィールドへの代入、値の出所など、
設定や出力形式に依存しない情報です。静的束縛かどうか、コンストラクタ注入と言い切れるか、
import からの推定を呼び出し先として採用するか、といった判断はキャッシュを読む側で行うため、
出力や解決の方針を変えてもキャッシュを作り直さずに済みます。
キャッシュの版（`CacheFormat.VERSION`）は、書き手の変更で事実が変わりうるなら**迷わず上げます**
（列や意味の変更に限らず、収集範囲・値の正規化・書き手が作る文字列の文言も含む）。上げると 1 回だけ
全件解析になりますが、上げ忘れると再利用したファイルだけが古い事実のまま残り、静かに違う結果になるためです。
上げ忘れは `test/cacheversion/run.sh`（決まった題材の事実の指紋を記録と比べる検査）が捕まえます。

## 何をもって「同じファイル」とみなすか

**パスとサイズと内容の指紋**で見ます。更新時刻は記録も参照もしません。

更新時刻はソースの中身と関係なく変わります（git のチェックアウト、コピー、CI のたびに
作り直されるワークスペース）。当てにすると、中身が同じでも全件解析し直しになります。
逆に、更新時刻を復元する設定（`git restore-mtime` 相当、アーカイブの展開、`rsync -t`）では
**更新時刻もサイズも同じで中身だけ違う**ファイルができます。同じ長さの書き換え
（`"ALPHA"` → `"OMEGA"`）なら普通に起きます。このとき更新時刻を信じると、
古い解析結果をそのまま再利用してしまいます。どちらも中身を見れば起きません。

同じ見方をソース（`F` 行）、ソース一覧（`T` 行）、依存 jar とクラスフォルダ（`L` 行）に
そろえています。
サイズを先に見るのは、違えば中身も違うと分かり、ファイルを読まずに済むからです
（サイズが同じなら必ず中身を見ます）。
設計上の判断は [docs/cache-identity-qa.md](cache-identity-qa.md) にまとめています。

## 差分更新

差分更新では、サイズと内容の指紋が一致するファイルでも、そのファイルが参照している型
（キャッシュの `I` 行）を宣言するファイルが変わっていれば解析し直します。
呼び出し先やフィールドの所有型は他のファイルのバインディング解決に依存するためです。
`I` 行には、呼び出しやフィールドで名前にした型のほか、ソースに書かれた型の名前（戻り値・throws・ローカル変数の型など）、
ラムダの目標の型とその親、呼び出しの受け手と実引数の式の型（`a.getB().x()` の B。解決できた呼び出しも、できなかった
呼び出しも）、修飾された名前・フィールド参照の左側の型（`a.getB().count` の B）、呼び出し先の throws の型、拡張 for 文・
switch のセレクタ・throw の式の型、アノテーションの型、switch の case に書いた型とその親（sealed の permits で網羅性が
変わるため）、import 文の型も載ります。型解決に失敗したファイルには、参照した型の親も載ります。正確な一覧は
[CacheFormat.java](../src/jche/cache/CacheFormat.java) のクラスコメントの I 行の説明にあります。

`I` 行の依存だけでは見えない変化が 3 つあり、それぞれ次のように拾います
（[cache-unification-qa.md](cache-unification-qa.md) の Q42〜Q44・Q50〜Q54）。

- **前回は無かった型ができた**（ファイルを足した・戻した、既存のファイルに型を書き足した）: 無い型の名前は依存に
  残らないので、前回型解決に失敗していたファイル（`F` 行のエラー数、`U` 行の BINDING_FAILED）のうち、コンパイルエラーに
  現れた名前（`I` 行の 3 列目）が新しい型の名前に当たるものを解析し直します。無名クラス・ローカルクラスは名前で
  参照できないので、足しても何も解析し直しません。
  同じパッケージにできた型はオンデマンド import（`import q.*`）と `java.lang` の型を隠すので、同じパッケージで
  同じ単純名の型を参照しているファイルも解析し直します（依存 jar に同じパッケージの型ができたときも同じ）。
  見えなかった型を public にしたときも、コンパイルエラーに現れた名前が変わった型の名前に当たるファイルを解析し直します
- **親の親が変わった**: 子の `I` 行には直接の親しか無いので、解析し直したファイルの型の形（継承したものを含む
  メンバーの署名。`I` 行の 2 列目）が前回と違えば、そのファイルの型も変わったとみなして、参照しているファイルへ
  連鎖させます。親のメソッドの本体やコメントだけを変えたときは形が変わらないので連鎖しません。
  私的メンバーは、親のメンバーと名前が当たる（隠す・継承を止める）ものだけを形に入れるので、親に私的な補助メソッドを
  足しても連鎖しません
- **定数の値が変わった**: 下の「定数の値を変えたとき」

フィールドの参照箇所（読み取り・書き込み、他の型のフィールドも含む）は `A` 行に残ります。
行の種別と列の意味は [src/jche/cache/CacheFormat.java](../src/jche/cache/CacheFormat.java) のクラスコメントにあります。

## 何も変わっていないとき

解析し直すファイルが 1 つも無く（変更・追加・削除・壊れたブロック・jar の変化が無い）、先頭の行（ヘッダ・`L` 行・`T` 行）も
同じなら、書き直しても同じバイト列になります。そのときはキャッシュのファイルに触らず、そのまま残します
（ログに `[cache] Nothing changed; the cache is kept as is`）。改行が CRLF のキャッシュなど、書き手の書く形でないものは
1 回だけ書き直します。

## 1 回の実行で読む回数と一時ファイル

キャッシュを先頭から最後まで読むのは、何も変わっていない実行とファイルを変えた実行で 2 回（差分更新のパス1 と
グラフの構築）、キャッシュが無い実行で 1 回（グラフの構築）です。そのほかは次の一時ファイルで補い、キャッシュを
読み直しません。

| 一時ファイル | 作るところ | 中身 |
|---|---|---|
| `analysis-cache.tsv.deps-*.tmp` | 差分更新のパス1 | 有効なブロックの依存（`I` 行）。依存での再解析の判定（パス3）はこれだけを読む |
| `analysis-cache.tsv.edges-*.tmp` | グラフの構築 | エッジの記録（1 本 34 バイト）。呼び出し元ごとの本数が分かってから、ちょうどの大きさの配列へ読み戻す |
| `analysis-cache.tsv.unresolved-*.tmp` | グラフの構築（CLI だけ） | 型解決に失敗した呼び出しの一覧（`call-hierarchy.csv` の末尾）に出す行 |
| `analysis-cache.tsv.rewrite-*.tmp` | 差分更新の終わり（解析のあいだにソースが書き換えられたときだけ） | 書き終えたキャッシュの書き直し先（書き換えられたファイルの内容ハッシュを空にする。下の「解析のあいだにソースを書き換えたとき」） |

差分更新の最後の書き写しは、有効なブロックをバイトの範囲のまま写します（行に戻さない）。
一時ファイルの名前は実行ごとに変わり（同じキャッシュのフォルダを使うほかの実行と取り違えない）、使い終われば
失敗・中止でも消します。Ctrl+C などで強制終了したときは JVM の終了フックが消し、それでも残ったものは次の実行の最初に消します。
GitHub Actions のアクションも、キャッシュのフォルダを保存する前に消します。
キャッシュ本体の一時ファイル（`analysis-cache.tsv.tmp`）だけは、中断からの引き継ぎ（次の節）のために残ります。
なぜヒープではなく一時ファイルにしたか、何も変わっていないときの条件は
[cache-unification-qa.md](cache-unification-qa.md) の Q31〜Q37 にあります。

## 同じキャッシュのフォルダを使う実行

CLI と Eclipse・VS Code のプラグインの解析サーバー、同じフォルダを使う CI のジョブなど、2 つの実行が同じキャッシュの
フォルダを同時に使うことがあります。キャッシュを読み書きするあいだ（フェーズ1 の差分更新とフェーズ2 のグラフの構築）は
フォルダの錠（`analysis-cache.tsv.lock`。OS のファイルの錠）を持ち、あとから来た実行は `[cache]` のログを 1 行出して
先の実行が終わるまで待ちます。待つのは最長 30 分で、環境変数 `JCHE_CACHE_LOCK_WAIT_SECONDS` で秒数を変えられます。
待ちきれなければ、何を待っていたかを言って実行を失敗にします（錠なしで進めない）。錠はプロセスが落ちれば OS が放すので、
錠のファイルが残っていても次の実行を止めません（中身は空で、消さなくて構いません）。錠の仕組みの無いファイルシステム（一部のネットワークドライブ）では錠なしで続け、同じフォルダを同時に使わないよう警告します。

以前は錠が無く、片方がもう片方の書きかけの一時ファイル（`analysis-cache.tsv.tmp`）を中断からの引き継ぎのつもりで
奪って本物に差し替え、呼び出しの 1 本も無い CSV が「成功」として出ることがありました。今は錠に加えて、グラフを組む側も
最後まで書き終えたキャッシュか（形式の版・最終行のブロック数）を確かめ、違えば組まずに止めます。差分更新は旧キャッシュを
最初に 1 回だけ開き、書き写しまで同じものを読みます（読んでいるあいだに大きさが変われば止めます）
（[cache-unification-qa.md](cache-unification-qa.md) の Q56）。

## 解析のあいだにソースを書き換えたとき

ソースの内容ハッシュは解析の前に取り、JDT はそのあとでファイルを読みます。そのあいだにソースを書き換えると、前の中身の
ハッシュと後の中身の事実が組になり、あとで元に戻すと古い事実を再利用し続けていました。今は、解析したファイルは
JDT が読んだ直後にハッシュを取り直し、書き終えたらどのソースも実行の始めの大きさと更新時刻のままかを見て、
変わったファイルは `F` 行の内容ハッシュを空にします（ログに `[cache]` で件数を出します）。次の実行はそれらのファイルと、
それらを使うファイルを解析し直します。更新時刻は実行のあいだの見張りにだけ使い、キャッシュには書きません
（[cache-unification-qa.md](cache-unification-qa.md) の Q57）。

## 同じクラスが 2 つのソースフォルダにあるとき

JDT は、同じ名前の型を宣言する 2 つのファイルを同じバッチで渡されると、後のほう（ソースフォルダの並びで後ろ）に
「型が重複している」コンパイルエラーを出してその型を読みません。別々のバッチならどちらも読みます。そこで、ソースフォルダからの
相対パスが同じファイル（`src1/p/Dup.java` と `src2/p/Dup.java`）は、全件解析でも差分更新でも必ず同じバッチに並べ、
片方を解析するときはもう片方も解析し直します。後のほうのファイルは warnings.txt の「ソースにコンパイルエラーがある」に
載ります。名前の違うファイルで同じ型を宣言している場合（public でないトップレベルの型）は、グラフを組むときに
「型 X が A と B の両方で宣言されている」と警告し、メソッドの宣言は先に並ぶソースフォルダのものを使います。
ソースフォルダの並びを入れ替えるとどちらが読まれるかが変わるので、並びはキャッシュの鍵（ヘッダ行）に入っています
（[cache-unification-qa.md](cache-unification-qa.md) の Q58・Q61）。

## 実行を途中で止めたとき

キャッシュは一時ファイル（`analysis-cache.tsv.tmp`）へ書いてから本物に差し替えるので、
フェーズ1（ソース解析）の途中で実行が終わっても本物は無傷です。
残った一時ファイルは次回の実行で `analysis-cache.tsv.partial` に退避され、
**そこまでに解析したファイルはパースし直さずに書き写します**（中断・CI のタイムアウト・
OOM・強制終了のどれでも効きます）。引き継ぎが終わったら退避先は消えます。

引き継ぐのは次の条件がすべて揃ったときだけです。1 つでも違えば引き継がず、
差分更新はこれまでどおり働きます。

- 形式・ソースレベル・文字コード・実行 JDK・JDT の版・ソースフォルダの並び（ヘッダ行）が当時と同じで、
  一時ファイルの先頭の行の検査値（`T` 行の最後の列）が合う
- 依存 jar が当時から変わっていない
- **ソース一覧（パス・サイズ・内容ハッシュ）が丸ごと当時と同じ**（`T` 行）。
  呼び出し先・親型・定数の値はバインディング解決の結果なので、
  そのファイル自身が変わっていなくても、別のファイルが変わればブロックは古くなります
- そのブロックが最後まで書けている（最後の 1 ブロックは切れている可能性があるので使いません）
- そのブロックの検査値が合う（合わなければ引き継がず、ほかの変わったファイルと同じくそのファイルを解析し直します）

フェーズ2・3 まで進んでから止めた場合は、キャッシュは既に差し替わっているので、
次回は普通に再利用されます。

## 壊れたキャッシュ

キャッシュは一時ファイルへ書いてから移すので、このツール自身が半端なファイルを残すことはありません。
それでも外から壊れたファイルが来ることがあるため（GitHub Actions のキャッシュの復元、コピーの失敗、
ディスクの異常）、最終行に「ここまで書き終えた」印（`Z` 行とブロック数）を置いています。
印が無い・数が合わないキャッシュは途中で切れているとみなして丸ごと捨て、全件解析し直します。
読めないキャッシュ（文字が壊れている等）も、解析を止めずに破棄して全件解析に倒します。
どちらも理由をログに出します。

行の形を保ったまま中身だけが変わったブロック（書き換え・文字化け）は、ブロックごとの検査値
（`F` 行の最後の列）が合わないことで見分けます。そのブロックは再利用せず、ソースが変わったのと同じ扱いで、
そのファイルと、そのファイルが宣言する型（壊れたブロックの `H` 行）を使うファイルを解析し直します
（ほかのブロックはそのまま再利用します。壊れたブロックからは前回の事実の何が変わったかを言えないため）。これは利用者が対処することではないので、
`[cache]` で始まる情報のログを出すだけで、`warnings.txt` には載せません
（[cache-unification-qa.md](cache-unification-qa.md) の Q25）。

## 定数の値を変えたとき

コンパイル時定数（`static final` の値と、注釈のメンバの既定値）は、Java の言語仕様どおり
**使っている側のファイルに値そのものが焼き込まれます**。そのため「ファイルの事実は、
そのファイルが `I` 行に持つ型の宣言にだけ依存する」という差分更新の前提が、定数では成り立ちません
（成り立たない場合はほかに 2 つあり、上の「差分更新」の「親の親が変わった」と「前回は無かった型ができた」です）。

```
P.java   static final String KIND = "ALPHA";
X.java   static final String KIND = P.KIND;     ← "ALPHA" が焼き込まれる
C.java   if (X.KIND.equals("BETA")) { … }       ← ここにも "ALPHA" が焼き込まれる
```

C.java が参照しているのは X だけなので、P.java を変えても C.java の `I` 行には引っかかりません。
これを取りこぼさないよう、宣言している側に定数の値を `K` 行として残し、解析し直した結果
**値が変わっていたとき**だけ、その型を参照しているファイルも解析し直します
（値が変わっていなければ連鎖しないので、再解析は増えません）。

列挙定数は値ではなく宣言型で修飾した名前（値グラフの定数のノード。`CacheDump` の表記で `V:fx.Mode.FULL`）として持つため、
この連鎖は要りません。定数の追加・削除・改名は必ず enum のソースの変更になり、
参照側の `I` 行に enum 型が載っているので、これまでどおり 1 段の依存で追随できます。

設計の判断と、行形式を壊す値（複数行の注釈の値など）の扱いは
[cache-integrity-qa.md](cache-integrity-qa.md) の Q1〜Q15 にまとめています。

## 依存 jar を変えたとき

キャッシュには解析時の依存 jar（パス・中身の指紋・含まれるパッケージ。`L` 行）も残します。
jar の指紋は、末尾の目次（セントラルディレクトリ）にある `エントリ名 / サイズ / CRC` から作ります。
jar を展開も読み込みもしないので、大きな jar が何本あってもエントリ数に比例するだけです。
クラスフォルダ（マルチモジュールの兄弟モジュールの `target/classes` 等）は
`.class` の `相対パス / サイズ / 内容ハッシュ` から作ります。
次回の実行で jar が追加・差し替え・削除されていれば、その jar のパッケージの型を参照している
ファイルを解析し直します。追加・差し替えのときは、前回型解決に失敗していたファイル（`F` 行のエラー数、
`U` 行の BINDING_FAILED）も解析し直します（無い型の名前は `I` 行に残らないので、パッケージでは当たらないため）。
削除だけのときは、解決できる型が増えず、失敗していた型解決が成功に変わる理由にならないので、失敗していたファイルは
解析し直しません。
jar の型が自分と同じパッケージにできたときは、オンデマンド import と `java.lang` の型を隠しうるので、そのパッケージで
オンデマンド import か `java.lang` の型を参照しているファイルも解析し直します
（[cache-unification-qa.md](cache-unification-qa.md) の Q54）。
`L` 行の**並び順**も見ます。JDT は同名クラスをクラスパスの先勝ちで解決するので、jar の集合が
同じでも並びが変われば解決先が変わりうるためです（`pom.xml` の依存の並べ替えでも変わります）。
効くのは同じパッケージが 2 つ以上の jar にあるときだけなので、並びの変わったパッケージの型を参照している
ファイルだけを解析し直します（並びが変わっただけでは、失敗していたファイルは解析し直しません）。
「型解決できなかった呼び出しが N 件あります」と出たときに `library.folders` へ jar を足せば、
キャッシュを消さなくても次の実行で反映されます。
CHA の候補（インターフェースの実装クラス）はキャッシュせず、毎回 `H` 行から計算するので、
jar の追加で実装クラスが増えた場合も、呼び出し側のファイルを解析し直さずに反映されます
（jar の基底クラスがソースのインターフェースを実装している構成では、その子クラスの `H` 行に
インターフェースも親として記録します）。
実行する JDK を変えたときはキャッシュ全体を作り直します（JDT は実行中の JVM の標準クラスも
解析対象のクラスパスに含めるため。何が変わるかは下記 docs の Q20）。
ソースの文字コード（`source.encoding`）とソースレベル（`source.level`）も同じ理由で
1 行目の鍵に入っていて、変えるとキャッシュ全体を作り直します。
設計上の判断と限界は [docs/cache-dependency-jars-qa.md](cache-dependency-jars-qa.md) にまとめています。
